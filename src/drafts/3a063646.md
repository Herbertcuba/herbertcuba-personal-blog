A $200 AI subscription came with a $7,470.35 meter. In July 2026, `claude-cost`, a local reporting tool for Claude Code, placed one subscriber’s payment beside what the same recorded usage would have cost at public application programming interface rates. Claude Code is the terminal coding agent from AI company Anthropic, and an application programming interface, or API, is the metered interface software uses to send requests to a model.

The comparison came from [Om Patel, who posted the report on the social platform X](https://x.com/om_patel5/status/2083401185172541449) on 1 August 2026. Its screenshot reported 6,156,261,087 tokens across 36,881 responses. A token is a small unit of text processed by a language model, and $7,470.35 divided by $200 produces the arresting ratio: 37.4 to one.

It was not a $7,470.35 bill. [Claude Code’s cost guide](https://code.claude.com/docs/en/costs) says the software calculates its local dollar figure from token counts at standard list rates, which can differ from the customer charge. The available evidence does not include the reporting-tool version or raw provider logs, and the screenshot tells us nothing about Anthropic’s internal serving cost.

A second self-report points toward the mechanism. [Nate B. Jones, the author of a video about his own Codex workspace](https://www.youtube.com/watch?v=Y8vAQ1FgNbM), said his tracker recorded 3.77 billion tokens across 143 threads in one working day. Codex is the coding agent from AI company OpenAI. Jones’s tracker classified 3.59 billion tokens as reused input, meaning previously supplied material counted again in his workspace. The rounded figures yield 95.2 percent, which he described as “almost 96%.”

That number is one tracker-reported category from one instrumented day, not an industry benchmark. Jones did not publish the raw event schema needed to reconstruct request-level changes. I think the honest shock is still useful: flat subscription pricing can hide a request loop dominated by old material, so context needs the same lifecycle, telemetry, and outcome test as any other production resource.

## Read the three meters separately

The July report contains three accounting views that must not be collapsed. Cash cost is what the subscriber actually paid. Public-list-price exposure applies a dated retail API schedule to recorded traffic as a comparison. Token traffic describes what crossed the model boundary, regardless of whether the plan charged for each token.

The report’s line items also separate two cache operations. Prompt caching is Anthropic’s feature for reusing the processing of an unchanged prefix, such as stable instructions at the start of a request. Cache creation writes input into a new cache entry, while cache retrieval reads an existing entry again.

Cache retrieval accounted for $3,595.52 of the report’s public-list estimate. The one-hour and five-minute cache-write rows add up to $2,844.72, generated output was $1,015.97, and ordinary fresh input was $14.14. The cache-read row plus the two cache-write rows total $6,440.24, or 86.2 percent of the displayed $7,470.35.

That 86.2 percent is not a reuse rate. It combines retrieval with creation, and a write does not become reused input merely because it creates cache state. The distinction matters because a dashboard that labels all cache operations as waste will punish the stable prefixes that make repeated input cheaper.

The cache-read row supports a narrower check. Dividing $3,595.52 by 5.878 billion retrieved tokens gives about $0.61 per million. In [Anthropic’s public price table](https://platform.claude.com/docs/en/about-claude/pricing) available in August 2026, cache hits were listed at $0.50 per million tokens for Opus 5 and $1 per million for Fable 5, two model tiers named in the screenshot. The combined report-level rate falls inside that range, although the screenshot does not split cache reads by model, so this is a plausibility check rather than a reconstruction.

Jones’s 95.2 percent belongs to another measurement system. His tracker classified counts inside a Codex workspace, while the Claude report exposed provider cache events and a retail-rate estimate. A July 2025 note from [the team behind Manus, a general-purpose AI agent](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus), offers one more bounded comparison: Manus reported an average input-to-output ratio around 100 to one. It supports input asymmetry, but it cannot verify Jones’s category or the Claude cache split.

I don’t know Anthropic’s cost to serve the month in Patel’s screenshot. The public evidence does not disclose it. I think these reports are strongest when they stay in their lanes: one shows the gap between a flat payment and a retail-rate meter, while the others show why engineers should inspect the composition of their own requests.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Cash payment, dated public-list-price exposure, and token traffic answer different questions. The Claude report’s cache operations represent 86.2 percent of its retail-rate estimate, but only retrieval is a cache read. Jones’s tracker category and Manus’s input-to-output ratio are separate observations, not interchangeable proof.</p></div>

## Why old context keeps returning

For a stateless language-model interface, the client must supply or reference the prior context needed for the next call. Claude Code’s documented behavior is more specific: it sends the current conversation with every request, and each tool use leads to another request carrying that batch of tool results. The complete payload is the request envelope: instructions, conversation, tool definitions, selected source material, tool output, and the newest message.

Repetition is therefore structural. As a session continues, the envelope grows, and each additional tool step creates another occasion to send it. Prompt caching can make an unchanged prefix cheaper to process, but it does not make the envelope smaller or decide whether an old item still deserves to be there.

Consider a coding agent preparing a database migration that prevents duplicate payment records. The first request may need the current schema, the migration policy, and a failing test. By the twentieth request, the envelope may also contain rejected index designs, search output, tool errors, old explanations, and copies of material that no longer affect the decision. The task has not become twenty times more complex, but the request has accumulated its own history.

That history carries a quality cost as well as traffic. [Lost in the Middle](https://arxiv.org/abs/2307.03172), a study first released in 2023 by Nelson Liu and colleagues and later published in the peer-reviewed journal *Transactions of the Association for Computational Linguistics*, tested multi-document question answering and key-value retrieval in long prompts. Models often performed better when relevant evidence appeared near the beginning or end and worse when it sat in the middle, including models designed to accept long contexts. The study was not a coding-agent cost experiment, but it shows why available capacity does not guarantee usable attention.

I call the carrying cost context debt. It returns on later requests, and it can bury the evidence that matters now. The practical limit should still follow the job rather than a universal token ceiling: a broad investigation may need many sources, while a narrow correction may need one failing test and a small code region.

A cheaper model changes the price of processing each token. Request construction changes how many tokens enter, how often they return, and whether the model can find the decisive evidence. I think that is the control point worth testing first in multi-turn agent work, while one-shot tasks that genuinely require a broad body of evidence may benefit much less from aggressive removal.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A growing request envelope repeatedly carries old conversation, tool results, and source material across a stateless boundary. Caching lowers the price of an unchanged prefix, but it does not choose what still belongs. Context policy should reduce repeated traffic without removing evidence the task still needs.</p></div>

## Give context an exit condition

Context hygiene means deciding what enters a request, why it remains, and when it leaves. An agent can use its transcript as both a durable task record and active working state. The durable record should preserve prompts, tool returns, failed attempts, decisions, and source trails. The active envelope should contain only the current goal, constraints still in force, admitted evidence, and the newest working artifact.

My take is to make admission a state transition rather than a sentence in a prompt. A candidate item should identify its source, purpose, version, exit condition, and approval event before it becomes active. It should retire from the envelope when the task ends, its evidence is replaced, or its decision is accepted. Retirement removes it from the next request, not from durable storage.

This synthetic example in the Python programming language makes the lifecycle executable. It permits `candidate → active`, `candidate → rejected`, and `active → retired`; terminal states cannot return to the envelope, and activation fails when an admission field is empty.

```python
ALLOWED = {"candidate": {"active", "rejected"}, "active": {"retired"},
           "retired": set(), "rejected": set()}
REQUIRED = ("source_ref", "purpose", "version", "exit_condition", "approval_event_id")

def transition(item, target):
    current = item["state"]
    if target not in ALLOWED.get(current, set()):
        raise ValueError(f"illegal transition: {current} -> {target}")
    missing = [key for key in REQUIRED if not item.get(key)]
    if target == "active" and missing:
        raise ValueError(f"cannot activate; missing {missing}")
    return {**item, "state": target}
```

For the migration, a valid candidate might point to `repo://payments/schema.sql`, say that it defines the current uniqueness rule, carry a source revision, expire when migration review closes, and name the check that approved admission. Calling `transition(item, "active")` with those fields succeeds. Calling it with an empty `source_ref` raises `cannot activate`, while calling `transition(retired_item, "active")` raises `illegal transition`.

This rule prevents rejected work from quietly returning as evidence after a retry. If a rejected design exposed a real constraint, admit the constraint as a new version and retain a reference to the full trace. Carry the accepted artifact or the still-valid fact, not forty turns of debate.

The familiar failure modes now become lifecycle bugs. Forever threads lack an exit condition. Whole files and raw attachments bypass selective admission. Retry loops keep adding tool errors without retiring failed paths. Bloated tool definitions enter every envelope even when the task cannot call them. The remedy is equally concrete: start a new task when the job changes, search before loading, admit the smallest useful region, cap output to what the next step can use, and expose only the tools required for that state.

Automatic compaction remains useful when a session approaches a model’s context limit. Claude Code summarizes older conversation so work can continue. Yet a late summary is a recovery mechanism, not application state: without explicit roles, a summarizer can preserve a vivid dead end and compress the test that actually defines success.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep the complete task trace in durable storage and enforce a smaller active envelope. Every admitted item needs a source, purpose, version, exit condition, and approval event. Legal transitions let completed or rejected work leave future requests without erasing the audit record.</p></div>

## Meter the request boundary

A context policy becomes enforceable where the application sends a request to the provider. At that boundary, record the task and request identifiers, policy version, provider, provider-schema version, model revision, price-schedule version, input categories, output, latency, and retries. Add retention policy, data region, and export method so a later provider or contract change does not silently alter the meaning of the comparison.

The example below is synthetic. Its values test the record shape; they are not evidence from Anthropic or a production team.

```json
{
  "schema_version": "agent-request/v1",
  "task_id": "migration-042",
  "request_id": "req-001",
  "policy_version": "context-v2",
  "provider": "anthropic",
  "provider_schema_version": "example-v1",
  "model": "example-model-revision",
  "price_schedule_version": "example-2026-08-01",
  "data_region": "example-region",
  "retention_policy_id": "retention-example-v1",
  "export_method": "example-jsonl-v1",
  "usage": {"input_tokens": 100, "cache_creation_input_tokens": 50, "cache_read_input_tokens": 150, "output_tokens": 20},
  "actual_cash_cost_usd": null,
  "retry_index": 0,
  "latency_ms": 1800
}
```

Anthropic’s response schema, the structured usage fields returned with a call, separates ordinary `input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, and `output_tokens`. A provider-specific cache-read share divides retrieved input by total input, where total input is the sum of all three input fields. Cache creation belongs in the denominator because those tokens were processed to create new state, but only retrieval belongs in the numerator.

A small provider adapter can calculate that metric. An adapter is simply the mapping from a provider’s fields into the team’s stable measurement. Save these two synthetic JSON Lines fixtures, a text format with one JSON object per line, as `requests.jsonl`:

```json
{"usage":{"input_tokens":100,"cache_creation_input_tokens":50,"cache_read_input_tokens":150,"output_tokens":20}}
{"usage":{"input_tokens":50,"cache_creation_input_tokens":0,"cache_read_input_tokens":50,"output_tokens":10}}
```

Then run this `jq` query. `jq` is a command-line tool for reading and transforming JSON.

```bash
jq -s '
  map(.usage) |
  {
    ordinary:  (map(.input_tokens // 0) | add // 0),
    created:   (map(.cache_creation_input_tokens // 0) | add // 0),
    retrieved: (map(.cache_read_input_tokens // 0) | add // 0)
  } |
  (.ordinary + .created + .retrieved) as $total |
  {
    metric_version: "anthropic-cache-read-share/v1",
    total_input: $total,
    cache_read_share: (if $total == 0 then null else .retrieved / $total end)
  }
' requests.jsonl
```

The fixtures return 400 total input tokens and a cache-read share of 0.5. An empty file returns zero and `null`, so the adapter does not hide missing data behind a division error. Keep both checks beside the query in version control. If a provider changes a field’s meaning, publish a new adapter and metric version rather than rewriting history.

The same request record must keep traffic separate from money. Actual cash cost comes from the contracted bill or a subscription allocation chosen before analysis. Public-list-price exposure applies a dated retail schedule to the recorded traffic. A high cache-read share can coexist with low spend because retrieval is discounted, and repeated policy or source material can be necessary rather than wasteful.

I think the useful alert is a change against a task-class baseline, not a universal red line. A task class is a group of jobs judged by the same acceptance rule. Compare migrations with migrations and narrow fixes with narrow fixes, then inspect cache-read share, envelope size, retries, latency, and review time together. If changes in the traffic metric stop predicting changes in the full cost of checked and reviewed work for two review cycles, demote the traffic metric instead of defending the dashboard.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Record a versioned, provider-specific request at the application boundary and test the adapter with synthetic fixtures, including an empty-input case. Cache-read share describes traffic; the contracted bill or a predeclared subscription allocation describes cash; a dated public price schedule describes exposure. None can stand in for the others.</p></div>

## Start with one task, then earn the replay

The meter should pass a smoke test before it produces a dashboard. Take one closed task with known source revision and checks, then replay it three times under the current context policy and three times under the proposed policy. Six runs cannot establish that one policy is better. They can establish whether the request records, policy versions, costs, artifacts, and review events join correctly from start to finish.

Hold the model revision, tools, retry limit, source revision, automated checks, and reviewer guidance constant. Randomize run order and hide the policy label from the reviewer where possible. Define the acceptance event before the first request: for a closed coding task, a candidate must pass every required automated check and receive an `approved_for_merge` event from a reviewer within seven days.

The smoke test has a hard stop. If any run lacks a request record, artifact reference, failed-check record, review duration, or attributable cost, do not compare the policies. Fix the evidence pipeline and repeat. Rollback is equally plain: restore the previous policy version at the request boundary while keeping both policies and all attempts in the durable log.

Once the measurement chain works, expand to a bounded replay rather than a vague pilot.

<div class="keymsg">
<span class="keymsg__label">A decision-grade context-policy replay</span>
<p class="keymsg__text"><strong>Cohort:</strong> 12 representative closed tasks: four narrow fixes, four migrations, and four investigations. Run both policies three times on every task for 72 isolated runs.</p>
<p><strong>Window and budget:</strong> Two calendar weeks, a seven-day acceptance window for each task, and 12 reviewer-hours reserved before the replay begins.</p>
<p><strong>Controls:</strong> Freeze the model, tools, retry limit, source revision, checks, and reviewer rubric. Randomize order and blind reviewers to the policy label where possible.</p>
<p><strong>Go or stop:</strong> Adopt only if the 95 percent paired-bootstrap confidence interval for proposed-minus-current cost per accepted result lies entirely below zero, the approval rate falls by no more than five percentage points, median review time rises by no more than 10 percent, and no critical correctness or security failure appears. An exhausted review budget makes the result inconclusive.</p>
<p><strong>Rollback:</strong> Restore the prior policy version. Preserve raw requests, outcomes, rejected attempts, fixtures, and analysis code.</p>
</div>

Repeating each condition exposes model variance, the run-to-run differences that remain even when the setup is fixed. First sum the costs and accepted candidates across the three runs for each task and policy, preserving the task as the unit of comparison. A paired-bootstrap confidence interval then estimates uncertainty by repeatedly resampling the 12 matched task pairs, calculating cohort cost per accepted result under both policies, and recording proposed minus current. Report the middle 95 percent of those differences. If a resample has no accepted candidate, record its outcome cost as unbounded rather than dropping it; if the final interval includes zero, the honest result is inconclusive.

The source set behind the $7,470.35 and 95.2 percent headlines contains no public controlled enterprise replay of this kind, and Jones’s raw event schema is unavailable. That limits the claims, but it also makes the next step clear. Freeze an evidence package with the cohort manifest, policy files, model and tool versions, raw request records, adapter fixtures and tests, acceptance events, reviewer rubric, cost-allocation rule, and analysis code. Another engineer should be able to reproduce the denominator before debating the result.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use one task and six controlled runs to prove the evidence pipeline before comparing policies. Then run a bounded, reversible replay across representative task classes, keep every attempt, report uncertainty, and stop when data integrity, review budget, quality, or security crosses a declared limit.</p></div>

## Price the result that survives review

Token counts are operational signals, but they are the wrong final denominator. An accepted result is a dated event tied to a specific artifact, not a model saying that it finished. In the replay, acceptance means every required automated check passed and a blinded reviewer emitted `approved_for_merge` within seven days of the first request. In live reporting, the approved commit must reach the default branch inside the same window.

A failed test, reviewer rejection, abandoned retry, or late candidate remains a cost without becoming an accepted result. Store the event type, acceptance time, artifact reference, review minutes, and failed-check identifiers with the task outcome. This keeps rejection visible instead of allowing a cheap failed run to improve the average.

The final metric is full cost per accepted result. Add actual model charges, or a predeclared share of a flat subscription, to loaded review cost and relevant platform expense, then divide by accepted outputs. Loaded review cost values reviewer time at a labor rate that includes compensation and employer costs. Platform expense covers the proxy, evaluation runner, storage, and other infrastructure used by the measured workflow.

For a flat seat, freeze the allocation rule before seeing the result. One defensible method allocates the monthly subscription by task-attributed agent-active minutes, using the same clock for both policies. The $7,470.35 public-list estimate stays outside this calculation because the plan did not charge it.

A policy with no accepted candidate has no finite outcome cost and fails the test. Every retry and rejection inside the seven-day attribution window stays in the numerator. Less context is a loss when it creates more failures or review work; more context is justified when it improves acceptance enough to pay for itself.

I think ownership belongs with the platform team that controls the request boundary and can join requests to outcomes. Finance supplies the loaded labor rate and validates subscription allocation. Procurement records retention, regional handling, export rights, price-schedule changes, and notice of provider-schema changes. Review the evidence monthly, but change policy only when a new version passes the same replay.

The $200 plan muted the cash signal, and the $7,470.35 retail-rate meter made hidden traffic visible. Jones’s 95.2 percent count gives engineers a reason to inspect their own loops, not a percentage to copy into a forecast. The decisive number begins after the tokens have been spent: what it cost to produce work that the organization was willing to accept.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Define acceptance as a dated event tied to a checked and reviewed artifact, keep failed attempts in the numerator, and divide actual model or allocated subscription cost, loaded review cost, and platform expense by accepted work. The winning context policy is the one that lowers that full outcome cost without crossing the declared quality limits.</p></div>
