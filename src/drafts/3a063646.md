Om Patel [posted a July 2026 Claude Code usage screenshot](https://x.com/om_patel5/status/2083401185172541449): $200 paid and $7,470.35 at API list prices.

The screenshot recorded 36,881 responses and 6.16 billion tokens. Cache reads and one-hour cache writes accounted for 86.2 percent of the displayed value. Output accounted for 13.6 percent.

The 37.4x gap measures API retail value. Anthropic's serving cost and margin remain private, so I don't know what the company spent on this user. I think the shape of the bill is more useful: most of its displayed value came from material carried into requests.

## Reuse can be cheap and still be waste

A second field observation shows why the cache line deserves investigation.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>One Codex workspace classified 95.2 percent of a day's tokens as reused input. Caching can lower the rate while stale material keeps adding cost and noise.</p></div>

Nate B. Jones [reported 3.77 billion tokens across 143 threads](https://www.youtube.com/watch?v=Y8vAQ1FgNbM) in one working day. His tracker classified 3.59 billion as reused input, or 95.2 percent. It is a sample of one. The pattern is worth testing in your own traces.

Consider a checkout bug: a discount code appears but never changes the total. The first request needs the bug report, pricing function and failing test. By attempt ten, the thread may also carry old replies, dead-end files and rejected patches.

Anthropic's [Messages API is stateless](https://platform.claude.com/docs/en/build-with-claude/working-with-messages), so the caller supplies the history. Prompt caching can price a repeated prefix at 0.1x the base input rate. A cache hit proves cheaper repetition. Relevance needs its own test.

## Keep the evidence, expire the search

The checkout task needs selective memory instead of a permanently growing transcript.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Carry the specification, current evidence and latest patch. End the thread when the job changes, while caching and compaction keep doing their narrower jobs.</p></div>

Claude Code already [compacts history near the context limit](https://code.claude.com/docs/en/costs). That helps capacity. Caching helps price. Structured state separates fields. A context policy decides which evidence earns another attempt.

For the discount bug, a curated attempt can begin with stable instructions, the acceptance test, relevant function and latest patch. The discussion behind a rejected patch can expire. Once the fix passes and a reviewer accepts it, the task ends. This gives the task loop in [Everyone Discovered Loops](/posts/everyone-discovered-loops/) an economic boundary.

## Make the policy falsifiable

The checkout example becomes useful when both policies face the same test.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Hold the model, tools, retry cap and acceptance test steady. Adopt curated context only when accepted-result cost falls without moving correction work to the reviewer.</p></div>

Choose 30 completed checkout tasks and replay each under both policies. Fix the model version, tool versions and three-attempt cap first. Give the reviewer only the final patch and test output. For the discount bug, acceptance means the code applies the discount, the test passes and the reviewer requests no correction.

Define reused input as provider-reported cache-read tokens. Log retrieved artifacts and retained transcript separately. Keep a short failure note instead of replaying a dead end in full.

Predeclare the rule. Adopt the curated policy if model cost per accepted patch falls, its accepted count stays within one result of the baseline and median review time does not rise. A cheaper run that consumes more reviewer time has failed. I think that guardrail keeps the experiment honest.

## Price the change that reaches production

Token prices become useful when they roll into the cost of an accepted result.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Cost per accepted result includes failed attempts and review work. One owner can turn context hygiene into an operating metric with a clear adoption rule.</p></div>

My take is simple: add model spend across every attempt to reviewer labor, then divide by accepted changes. Keep review minutes visible when labor rates are sensitive. Rejected checkout patches stay in the numerator because the team paid for them.

For this pilot, the platform owner maintains the trace and product engineering owns acceptance. FinOps verifies prices. Security sets prompt retention and redaction. Procurement records cache pricing, rate limits and price-change notice. Each role defends a specific field.

This turns the economics question in [Welcome to the Orchestration Era](/posts/welcome-to-the-orchestration-era/) into a number a team can inspect. I think the expensive model will be only part of the bill. The larger blind spot is the context policy wrapped around it.
