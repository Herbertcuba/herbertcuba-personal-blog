Om Patel's [July Claude Code screenshot](https://x.com/om_patel5/status/2083401185172541449) put two prices on the same month: $200 for the plan and $7,470.35 at API list prices. His tool counted 36,881 responses and 6.16 billion tokens. Cache reads and writes made up about 86 percent of the displayed total.

Nate B. Jones [logged 3.77 billion tokens across 143 coding threads](https://www.youtube.com/watch?v=Y8vAQ1FgNbM) in one day. His tracker marked 3.59 billion as reused input, or 95.2 percent. That is one person's instrumented workspace, measured for one day. I think the useful lesson sits in the mechanism: an agent can carry far more old text than new work.

Reuse alone tells us little. A stable system prompt is useful context. Old searches and dead retries can become context debt. Separate the two, then price the result that survives review.

## What $7,470 of usage looks like

Patel's screenshot shows how much text surrounded each answer.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Cache operations made up about 86 percent of the displayed list-price usage. The workflow consumed about 186 tokens for every token it generated.</p></div>

The screenshot listed 5.88 billion cache-read tokens at $3,595.52. One-hour cache writes were $2,841.89. Output cost $1,015.97.

A cache write stores a reusable request prefix. A cache read uses it again at a lower price. Dividing the reported read cost by cache-read volume gives about $0.61 per million tokens, within [Anthropic's published rates](https://platform.claude.com/docs/en/about-claude/pricing). This checks the internal arithmetic. It cannot audit the underlying account.

The account used 6.16 billion tokens to produce about 33 million output tokens. That is roughly 186 consumed for each one generated. I think junior engineers should inspect the request envelope before swapping models. A cheaper model still charges for stale context sent again.

## What 37.4 times the plan price means

The ratio needs a clear boundary before it can guide a budget decision.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The 37.4 ratio compares a capped subscription with API retail pricing. It exposes workflow dependence while leaving Anthropic's serving cost unknown.</p></div>

The $7,470.35 figure is an API list-price equivalent. Patel paid $200 under a plan with [rolling and weekly usage limits](https://claude.com/pricing). Anthropic's public pricing pages do not state its per-request cost or margin. I don't know what his month cost the company to serve.

Flat pricing can hide a context habit until the provider changes a limit or cache term. A team that discovers this during renewal lacks its own baseline.

## Reuse can be healthy or expensive

Follow one checkout bug through the mechanism: a discount code reaches the cart, yet the total stays unchanged.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Healthy reuse carries required instructions and task evidence. Context debt carries stale work that raises cost or makes the accepted result harder to reach.</p></div>

A token is a small unit of text. The context window is the text a model can use for one request. Some model APIs are stateless. [Anthropic's Messages API](https://platform.claude.com/docs/en/build-with-claude/working-with-messages) requires the caller to send conversational history, while other APIs can manage or chain conversation state. Depending on the API and harness settings, earlier messages and tool results may return on later turns.

For the checkout bug, stable system instructions belong in every request. The useful lines from `pricing.py` stay until the discount test passes. A failed search stops helping after it points to the wrong file. Sprint-planning notes never belonged in this task.

By turn twenty, a small request may travel with nineteen earlier replies. The [Lost in the Middle study](https://arxiv.org/abs/2307.03172) found that models often struggle when useful information sits inside a long context. The paper tested retrieval tasks, so the checkout agent still needs its own evaluation. I think teams should trim stale trajectory first and keep the evidence tied to the acceptance check.

## Put context hygiene into the workflow

A state boundary turns a good prompt habit into code.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep required instructions stable. Pass verified checkout state between steps, and remove the route that lets dead searches enter the next request.</p></div>

Modern coding harnesses may summarize long threads automatically. That helps, although the harness still chooses what to forget and when. Deliberate context hygiene sets the boundary earlier.

LangGraph is a Python library for workflows that branch or repeat. A `StateGraph` connects steps and gives them shared state. Edges decide which step runs next. A `TypedDict` describes the expected keys in that state for Python's type checker. It does not check values while the program runs.

The checkout state can hold `bug_id`, `relevant_lines`, `patch`, `test_passed` and `reviewer_decision`. The search step returns useful lines. Its raw transcript has no state key, so the patch step never receives it. This is the workflow side of [owning the agent layer](/posts/who-owns-the-agent-layer/).

Application code must still guard the transition. The outcome becomes `accepted` only when the discount test passes and a reviewer approves the patch. Agent narration cannot grant approval. I think this boundary makes context hygiene testable because every carried item needs an engineering reason.

A cache hit reports reuse. It cannot tell you whether the reused text belongs in the task. Keep the required prefix stable, then measure task evidence separately from old trajectory.

## Prove it with a bounded pilot

A paired replay can test the checkout policy without changing the production default first.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Replay the same completed tasks under the baseline and hygiene strategies. Hold the model and acceptance rule steady, then compare paid cost with reviewer effort.</p></div>

Take a bounded set of completed checkout tasks. Run each task once with the current harness and once with curated state. Alternate which strategy runs first. Keep the model, token budget and acceptance criteria version fixed.

Log every paid attempt:

```yaml
task_id: string
attempt: integer
context_strategy: baseline | hygiene
stable_prefix_tokens: integer
retrieved_evidence_tokens: integer
prior_trajectory_tokens: integer
cache_read_input_tokens: integer
billed_cost: number
latency_ms: integer
review_minutes: number
acceptance_criteria_version: string
test_passed: boolean
reviewer_decision: approve | reject
outcome: accepted | rejected
```

The runtime rule should reject `outcome: accepted` whenever `test_passed` is false or the reviewer decision is `reject`. Then group all attempts by task before comparing strategies:

```sql
WITH task_totals AS (
  SELECT context_strategy,
         task_id,
         SUM(billed_cost) AS task_cost,
         SUM(review_minutes) AS review_minutes,
         MAX(CASE WHEN test_passed = TRUE
                   AND reviewer_decision = 'approve'
                  THEN 1 ELSE 0 END) AS accepted
  FROM agent_attempts
  WHERE acceptance_criteria_version = 'checkout-v3'
  GROUP BY context_strategy, task_id
)
SELECT context_strategy,
       SUM(task_cost) / NULLIF(SUM(accepted), 0)
         AS cost_per_accepted_result,
       AVG(accepted) AS acceptance_rate,
       AVG(review_minutes) AS review_minutes
FROM task_totals
GROUP BY context_strategy;
```

Choose the decision rule before the replay. Roll back if acceptance falls. Keep testing if reviewer time consumes the saving. The pilot proves a local workflow claim, and the team can widen it only after the result repeats.

## Measure cost per accepted result

The checkout patch counts only when its discount test passes and a reviewer accepts the diff.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Cost per accepted result keeps every paid attempt in the numerator. Reuse ratio locates possible context debt, while acceptance shows whether removing it helped.</p></div>

<div class="keymsg">
<span class="keymsg__label">The unit economics of agentic work</span>
<p class="keymsg__text">Cost per accepted result = billed agent cost across all attempts ÷ accepted tasks.</p>
<p>The rejected checkout patch, its retries and the final approved answer stay in the numerator.</p>
</div>

Suppose the first attempt costs $0.80 and fails its test. The second costs $0.60 and gets approved. The accepted result costs $1.40. Reporting only the final attempt would hide 57 percent of the paid cost.

Before renewal, baseline your highest-volume agent workflows. Record accepted-result cost for each one. Put reviewer time beside it. Then ask the supplier which usage fields you can export and which cache terms or limits can change during the contract.

Broad context can be useful for frontier reasoning or a one-shot synthesis. Hygiene earns its keep in looping work, where stale context returns on later requests.

My take: reuse ratio tells you where to inspect. Cost per accepted result tells you whether the smaller context still produced approved work. I think every failed attempt and reviewer minute belongs in that cost. If the agent spent $1.40 to land the checkout fix, engineering and finance should both see $1.40.
