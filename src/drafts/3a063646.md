Om Patel's July Claude Code screenshot put two prices on the same month: a $200 Claude plan and $7,470.35 of API list-price usage. It showed 36,881 responses and 6.16 billion tokens.

API retail value and Anthropic's private serving cost are different numbers. The screenshot still exposes the shape of the work. Cache reads and writes made up about 86 percent of its total.

A separate measurement gives the mechanism. Nate B. Jones [logged 3.77 billion tokens across 143 coding threads](https://www.youtube.com/watch?v=Y8vAQ1FgNbM) in one day. His tracker marked 3.59 billion as reused input, or 95.2 percent. One instrumented workspace cannot describe an industry, but I think it gives agent teams a strong hypothesis: the expensive part may be the context wrapped around each answer.

## What $7,470 of usage looks like

Nearly half of the reported total came from 5.88 billion cache-read tokens.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Cache operations made up about 86 percent of the displayed list-price usage. The 186-to-1 ratio points toward the request carried around each generated token.</p></div>

A cache write stores a reusable request prefix. A cache read uses that prefix again at a lower price. Patel's screenshot showed $3,595.52 in reads, $2,841.89 in one-hour writes and $1,015.97 in output tokens.

At [Anthropic's published cache prices](https://docs.anthropic.com/en/docs/about-claude/pricing), the blended read rate was about $0.61 per million tokens. Divide the 6.16 billion total tokens by 33 million output tokens and you get about 186 consumed tokens for each generated token.

I think the first place to inspect is the envelope: instructions, files and old conversation sent with the answer request.

## What 37.4 times the plan price means

The displayed API retail value was 37.4 times the plan price for that month.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The ratio compares a subscription with API list-price value. Plan limits and private serving costs keep it from becoming a forecast of Anthropic's margin.</p></div>

Claude plans have [rolling and weekly usage limits](https://claude.com/pricing). API prices also include a retail margin for developers building products on Claude. I don't know Anthropic's internal cost for Patel's month.

The screenshot gives us a workflow meter, rather than a clean subsidy estimate. I think that meter is useful because flat pricing can hide how much context an agent carries through one accepted task. Better caching may make the bill look calmer while the workflow grows dependent on a large prefix. A pricing or limit change can expose that dependency at renewal.

## Reuse can be healthy or expensive

Reuse ratio measures repetition, while relevance needs its own classification.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A stable, intentional prefix is healthy reuse. Context debt begins when stale turns or unrelated files keep travelling with the task and raise the cost of an accepted result.</p></div>

Use one running example. A checkout agent must fix a discount code that never reaches the cart total. Its stable system instructions and tool contract belong in every request. Keeping that prefix identical lets the cache lower its price.

The bug report and the useful lines from `pricing.py` are retrieved task evidence. They belong until the fix passes. The failed searches from turn three and an old sprint-planning thread are prior trajectory. They become context debt once they stop helping the checkout task.

By turn twenty, a small question can travel with nineteen older replies and a pile of tool results. The [Lost in the Middle study](https://arxiv.org/abs/2307.03172) found that models often struggle when useful information sits inside a long context. It tested retrieval tasks, so the checkout fix still needs its own evaluation.

I think teams should optimise prior trajectory and task-irrelevant material first. Required instructions stay. Useful evidence stays until the test proves the task is done.

One failed tool loop can carry a growing transcript through many more requests.

## Put context hygiene into the workflow

The checkout task needs a small state that can survive without carrying the whole conversation.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Stable instructions stay cacheable. Verified task state moves between steps while dead searches remain where they were produced.</p></div>

LangGraph is a Python library for workflows that branch or repeat. A `StateGraph` is the graph that connects those steps and passes shared state between them. A `TypedDict` describes the expected keys in that state for Python's type checker. Runtime checks still belong in code.

For the checkout task, the state can hold `bug_id`, `relevant_lines`, `patch`, `test_passed` and `reviewer_decision`. The search step returns only the relevant lines. Its raw transcript has no state key, so it has no route into the patch step.

An `accepted` transition should require `test_passed: true` plus reviewer approval. Agent narration cannot mark its own work complete. I think this boundary makes context hygiene testable because every carried item has a reason to exist.

## Prove it with a bounded pilot

A small pilot can test the claim before a team changes its default.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Replay the same completed tasks with baseline and hygiene strategies. Hold the model and acceptance checks steady, then compare cost per accepted result and reviewer time.</p></div>

Ten seats can be a starting boundary, subject to the variance in your own tasks. Pair each completed checkout task with two runs. The baseline uses the current harness. The second run uses curated state. Keep the model, budget and acceptance criteria version fixed.

Log every attempt with enough detail to separate healthy reuse from debt:

```yaml
task_id: string
attempt: integer
context_strategy: baseline | hygiene
stable_prefix_tokens: integer
retrieved_evidence_tokens: integer
prior_trajectory_tokens: integer
cache_read_input_tokens: integer
billed_cost: number
latency_ms: integer
review_minutes: number
acceptance_criteria_version: string
test_passed: boolean
reviewer_decision: approve | reject
outcome: accepted | rejected
```

Define the decision rule before the run. Roll back when acceptance falls or reviewer time erases the saving. Keep testing when the result is noisy. Scale the default when accepted-result cost falls inside the team's quality limit.

The platform team captures usage and owns the default. Engineering defines acceptance, and the combined report goes into the monthly FinOps review. I think that turns hygiene into an engineering decision instead of a cleanup ritual.

## Measure cost per accepted result

The checkout patch counts only when its discount test passes and a reviewer accepts the diff.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Cost per accepted result keeps every paid attempt in the numerator. Reuse ratio helps locate context debt, while acceptance and review time show whether removing it improved the work.</p></div>

<div class="keymsg">
<span class="keymsg__label">The unit economics of agentic work</span>
<p class="keymsg__text">Cost per accepted result = billed agent cost across all attempts ÷ accepted tasks.</p>
<p>The rejected checkout patch, retries and final approved answer all stay in the numerator.</p>
</div>

Suppose the first checkout attempt costs $0.80 and fails its test. The second costs $0.60 and gets approved. The accepted result cost is $1.40. Reporting only the final attempt would hide almost half the work.

For a larger organisation, baseline its three highest-volume agent workflows before renewal. Record accepted-result cost beside cache mix and reviewer time, then give each workflow an owner. Procurement needs two answers from the supplier: which usage fields can be exported, and which cache or limit terms can change during the contract?

Reuse ratio tells you where to inspect. Cost per accepted result tells you whether the inspection improved anything. My take is that this is the meter worth putting beside the cloud bill.

The $200 plan concealed a meter. Cost per accepted checkout fix puts that meter beside the work it paid for.
