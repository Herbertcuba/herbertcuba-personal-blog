In July 2026, developer [Om Patel](https://x.com/om_patel5/status/2083401185172541449) posted a screenshot on X, a social network, from `claude-cost`, a tracker for Claude Code. Claude Code is the terminal-based coding agent made by Anthropic, the company behind Claude. The tracker counted 6.16 billion tokens, the chunks of text a model counts for processing and billing, across 36,881 responses. It priced that traffic at $7,470.35 through Anthropic's public application programming interface (API), the metered route software uses to call Claude directly. Patel's subscription invoice was $200.

The comparison is 37.4 times the subscription price. The $7,470.35 is a retail counterfactual, meaning the recorded model mix and traffic priced at public API rates. It never appeared on Patel's invoice, and Anthropic keeps its own serving cost private. Without the subscription, the same recorded month sent through the public API at those rates would have produced the $7,470.35 charge.

Generated output represented 13.6 percent of the estimate. Cache reads represented 48.1 percent and one-hour cache writes represented 38.0 percent. A cache write stores a prompt prefix, the unchanged opening block of a request, while a cache read retrieves a matching prefix. The two cache operations account for $6,437.41, or 86.2 percent of the estimate, although that total cannot tell us whether the stored material helped the result.

AI practitioner [Nate B. Jones](https://www.youtube.com/watch?v=Y8vAQ1FgNbM) reported a second observation from Codex, the coding agent made by the AI company OpenAI. His tracker recorded 3.77 billion tokens across 143 threads in one day, with 3.59 billion classified as reused input, material sent in an earlier request and sent again. That is 95.2 percent in one self-instrumented workspace. Jones sells Ringer, a context-management product. His public material omits the raw records, collection code, model versions, and a reproducible field-level definition of reuse, so the percentage describes his setup and cannot establish an industry rate.

Patel measured cache operations while Jones measured reused input under his own definition, so their figures cannot be merged into one statistic. They still show that context-related input can dominate generated output and needs its own meter. Context is the bundle of instructions, history, files, and tool results sent with a model call. I think the overlooked downside of flat subscriptions is that they let us consume this bundle without learning how to make it efficient. Context engineering, the deliberate choice of what enters a request and what survives into the next one, is the skill the discount gives us time to learn.

## The bill without the subscription

Remove the subscription while preserving Patel's model mix and July traffic, and the public API estimate is $7,470.35 for that month. Three equally heavy months would reach $22,411.05, compared with $600 in subscription fees. An enterprise with negotiated rates should run the same calculation against its own contract because public retail prices describe the counterfactual, while contract prices determine actual exposure.

The cached-read subtotal can be checked against Anthropic's [July 2026 price table](https://docs.anthropic.com/en/docs/about-claude/pricing). Cache reads cost $0.50 per million tokens for Opus, one Claude model family, and $1 per million for Fable 5, another Claude model shown in the source. The screenshot's $3,595.52 across 5.878 billion cached-read tokens implies a blended rate near $0.61 per million, which is consistent with that portion of the estimate. The public screenshot lacks the raw request log, complete model-version record, collection code, and dated calculation file needed to rebuild every line independently.

Direct API billing supplies a feedback loop that a flat plan can weaken. Anthropic's API responses expose separate usage fields for fresh input, cache creation, cache retrieval, and output. Store those fields beside the task outcome, change one retention choice, then compare the next run. A team can see whether removing an obsolete file reduced cost while preserving the result.

I think flat pricing trains an expensive habit because another turn feels free at the margin, even while repeated context grows in the background. My take is to keep the bargain and recreate the missing meter: record request-level usage, attach the provider's dated price table, and calculate the API equivalent while the invoice stays flat.

## Why old context keeps returning

Anthropic's [Messages API](https://platform.claude.com/docs/en/build-with-claude/working-with-messages), the public endpoint software uses to send conversations to Claude, is stateless. The model retains no conversation memory between calls, so the client reconstructs that memory by sending the history again. The context window is the maximum working bundle the model can receive in one call.

Consider an agent fixing a checkout bug. The first request contains its instructions and the bug report. The next call carries those items again, followed by the first response and an opened file. By turn twenty, one new question can arrive behind nineteen earlier exchanges, repository text, and retry history. Each new turn pays to carry the old turns, even when the job has moved on.

[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), Anthropic's system for storing and retrieving a stable prompt prefix, lowers the delivery price. A matching cache read costs one tenth of base input. That discount says the prefix matched; it says nothing about whether an old patch, resolved debate, or unused tool description improves the next answer. I think cheap repeated input can still become expensive context when it keeps consuming model and reviewer attention without raising the acceptance rate.

Long inputs can also bury the evidence that deserves attention. [*Lost in the Middle*](https://arxiv.org/abs/2307.03172), a 2023 study by language-model researchers at Stanford University, the University of California, Berkeley, and the AI company Samaya AI, found that models often performed worse when relevant information appeared in the middle of a long input. The study was later published in *Transactions of the Association for Computational Linguistics*, a peer-reviewed language-technology journal. As the input grows, decisive evidence can sit among more competing material, and its position affects how reliably the model uses it.

In the 2014 science-fiction film *Edge of Tomorrow*, Major William Cage relives the same battle but carries the lesson from each failed loop while the battlefield resets. An AI model begins every call without that memory. The client decides whether to carry the lesson or the entire battle transcript.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Stateless model calls rebuild memory by resending history, and prompt caching discounts matching delivery without judging relevance. Old context can therefore increase traffic while making decisive evidence harder for the model to use.</p></div>

## Choose what survives the next request

Modern coding agents already compact long threads. [Claude Code's cost documentation](https://code.claude.com/docs/en/costs) says it automatically summarizes conversation history as the context limit approaches. Compaction, the compression of earlier turns into a shorter summary, helps a run continue. It also arrives after the thread has grown and leaves the survival decision to the summarizing process. I think context engineering should make that decision earlier, before the next request is assembled.

Start with an explicit carry-forward rule. An artifact is a checkable result such as a code patch, design decision, or extracted source passage. Give every candidate item a task ID and a request-trace ID, then allow only the `carried` state into the next request.

| State | Who records it | Rule |
| --- | --- | --- |
| `candidate` | The tool or engineer that found the item | Captured with its source and task identity; excluded from the next request. |
| `approved` | A named reviewer or an automated acceptance check | Verified as relevant and linked to the artifact it supports; eligible for carry-forward. |
| `carried` | The agent orchestrator, the software that builds the next request | Included with an approval event, a reason, and an expiry condition. |
| `expired` | The workflow owner or an automatic task-close event | Excluded after task closure, rejection, supersession, or the retention deadline. |

The transition checks should fail closed. A candidate cannot become carried unless its approval event names the reviewer or automated check, timestamp, and supported artifact. A rejected artifact cannot return as context. Closing the task expires every carried item, while a supersession event names the replacement artifact and expires the older one. These checks make carry-forward behavior testable.

Existing tools cover part of this job. JSON Schema, a standard for describing valid JSON data, and Pydantic, a Python validation library, can reject malformed event records. Temporal, a durable workflow platform, can preserve and resume recorded steps after a failure. Those mechanisms enforce state and durability; the carry-forward policy decides which evidence remains relevant enough to spend another request on.

To audit a retention decision, map each provider's documented fresh-input, cache-write, cache-read, and output fields into the team's common trace columns. This provider field mapping sits beside the request and task identities, model version, price-table date, artifact identity, retention state, acceptance result, retry count, and reviewer minutes. Store the records as redacted JSONL, a text file with one JSON record per line, beside the mapping and calculation script. Patel's screenshot and Jones's video lack this complete evidence package, so a production team should create one for its own claims.

A new job gets a clean thread, and a repository or document search selects the section that enters it. Stable instructions and tool definitions stay at the front so caching can match them. The approved artifact moves forward in the smallest useful form while the debate and failed retries expire.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Select evidence before compaction, allow only approved items into the carried state, and expire them when the task closes or the artifact changes. Provider-specific traces connect every retention decision to usage and outcome.</p></div>

## Price the result that survives review

An accepted result is an output that clears a fixed technical gate and human review. For a code patch, the technical gate may be continuous integration, the automated build-and-test process triggered as code changes are integrated into a shared repository; reviewer approval confirms that the patch solves the intended problem. Cost per accepted result is `(model spend + loaded review cost + material operating overhead) / accepted results`. Loaded review cost includes pay and employment overhead for the time people spend checking outputs, while operating overhead covers tracing, storage, and workflow work when those costs are large enough to change the decision.

I think this unit exposes savings that token counts can hide because a shorter prompt can produce more retries, while a cheaper model can push work onto reviewers. A strict retention policy can also lower model spend while increasing audit or storage cost. Cost per accepted result puts those movements in the same calculation.

Test the carry-forward policy on paired work before rollout. A practical starting design could replay 30 closed defects twice, once with the current growing-thread process and once with the new policy. Hold the model, prompt, tools, retry cap, and test environment constant, then hide the policy from reviewers. If two reviewers independently assess all 60 outputs at four minutes each, each reviewer spends four hours and the pair spends eight reviewer-hours before calibration or disagreement resolution. Price that time at the team's chosen loaded hourly rate.

Write the adoption rule before the trial begins. The team chooses a minimum reduction in cost per accepted result that would repay rollout effort, an acceptance-rate floor (the minimum share of outputs that must pass), and a maximum increase in reviewer time. Adopt only when the measured saving clears that local minimum while quality and review time stay inside their limits. Hold when the result remains too noisy to decide, and redesign when any quality, review, privacy, or retention limit fails. There is no universal saving threshold because task value and error cost vary by team.

Rollout needs one named policy owner in the platform team, short onboarding for the four retention states, and a weekly exception review for task classes that fail. Domain engineers own the acceptance rules. Procurement and privacy owners review trace-retention terms, data residency, the region where traces are stored or processed, and changes to supplier usage fields. A monthly dashboard can stay small: policy version, model spend, reviewer hours, attempts, accepted results, cost per accepted result, and exceptions. For an executive review, the $7,470 figure remains one subscriber's public-list-price signal; enterprise exposure comes from the organization's own contract, measured usage, and accepted-result cost.

Broad research and difficult reasoning may earn a larger context budget. Compliance records may need long retention outside the live model prompt. The metric can support those choices because it includes the human and operating costs that a token-only target would miss.

I don't know when providers will tighten heavy-use limits or change the price of access. They can change the meter faster than an engineering team can learn a new operating discipline. The $200 plan gives us room to learn now, and I think that room is valuable only if we use it to decide what earns another trip through the model.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Compare the full cost of outputs that pass technical checks and human review, then adopt a context policy only when it clears the team's predeclared saving, quality, review-time, and governance limits. When access becomes less forgiving, efficiency learned in advance is the difference between tuning a system and rebuilding it under pressure.</p></div>
