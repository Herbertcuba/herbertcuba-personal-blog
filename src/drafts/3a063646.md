[Om Patel shared](https://x.com/om_patel5/status/2083401185172541449) a screenshot of a Claude subscriber's July 2026 usage: a $200 plan and 6.16 billion tokens that a tracker priced at $7,470.35 using API list rates. The 37.4x gap never appeared on the subscriber's invoice.

The shape is more useful than the shock. Cache reads represented 48.1 percent of displayed value, one-hour cache writes 38.0 percent, and output 13.6 percent. The dollar lines for reads and writes total $6,437.41, or 86.2 percent; their displayed shares add to 86.1 because each is rounded. A write stores a prefix, while a read retrieves one. The combined figure describes cache activity, while the read line describes retrieval.

A separate report points at the mechanism. Nate B. Jones [reported](https://www.youtube.com/watch?v=Y8vAQ1FgNbM) 3.77 billion tokens across 143 Codex threads in one day, with 3.59 billion classified as reused input. That is 95.2 percent for one instrumented day. His video leaves the raw records, collection code, model versions, and reuse definition unpublished, so I think the number is a strong signal and a weak benchmark.

## A cheap cache hit can carry expensive context

Anthropic's [Messages API](https://platform.claude.com/docs/en/build-with-claude/working-with-messages) is stateless, so the client sends conversation history on every call. [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) prices a matching cache read at one tenth of base input. That measures delivery efficiency. Relevance has to appear in accepted outputs, review time, or fewer retries.

I think context debt is retained material whose removal lowers cost without reducing acceptance or increasing review work. This definition predicts something cache-hit rate cannot: a highly cached thread can still be wasteful. Long inputs can also bury useful evidence, as the [Lost in the Middle](https://arxiv.org/abs/2307.03172) study found.

*Edge of Tomorrow* gives the policy a useful shape. Cage carries the lesson into each reset while the battlefield disappears. An agent should carry reviewed evidence that changed the outcome and let the sprawling debate expire.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A cache hit proves discounted delivery. Context hygiene asks whether the retained material improves an accepted result.</p></div>

## Give carry-forward a typed boundary

Accepted artifacts may survive until superseded. Reviewed failure evidence may enter one more attempt of the same task, then expires when the task closes. Raw transcripts and unreviewed patches carry `false`. I think this boundary should be a recorded state transition with a validator, rather than a convention hidden in prompts.

A first deployment needs three field groups. Billing covers provider, model, region, rate card, raw usage, and model cost; outcome evidence covers task, artifact, check, acceptance, and reviewer minutes; retention covers class, carry-forward state, and expiry. Reviewer identity and payload hashes can follow as audit fields. An illustrative record stays small:

```json
{
  "task_id":"renewal-417","artifact":"patch:v2",
  "provider":"anthropic","model":"opus-5","region":"eu","rate_card":"2026-07",
  "usage":{"input_tokens":820,"cache_creation_input_tokens":0,"cache_read_input_tokens":18420,"output_tokens":740},
  "model_cost_usd":1.84,"retry_cap":2,
  "check":"ci:pass","accepted":true,
  "review":{"status":"accepted","minutes":6},
  "retention":{"class":"accepted_artifact","carry_forward":true,"expires":"superseded"}
}
```

The validator should reject an illegal transition explicitly:

```python
if r["retention"]["carry_forward"] and r["review"]["status"] == "unreviewed":
    raise ValueError("carry_forward requires reviewed evidence")
```

For Anthropic, retrieved-input share is `cache_read_input_tokens / (input_tokens + cache_creation_input_tokens + cache_read_input_tokens)`. Each other provider needs its own raw-field mapping and separately named proxy. I think an anonymised trace sample and mapping belong in the evidence package before anyone quotes a cross-provider percentage.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Carry-forward is an auditable admission decision. The minimum record joins raw billing fields to outcome evidence and retention state.</p></div>

## Test the policy on paired work

Replay 30 closed defects from one product domain under the growing-thread policy and the admission policy. Run both versions in clean environments, alternate run order, and pin the model, prompt, tools, retry cap, and rate card. Slice results by task class before the run so one easy category cannot hide a failure elsewhere.

Two blinded reviewers score all 60 outputs against one frozen rubric. Each reviewer gets four minutes per output, four hours across the benchmark. Both must accept; a split counts as rejected. Cost per accepted result is `(model spend + reviewer hours × loaded hourly rate) / accepted outputs`, and zero accepted outputs fails the policy.

Adopt only when the point estimate falls at least 10 percent, a 95 percent interval from resampling paired task results excludes zero reduction, accepted count does not fall, median review time rises by no more than 5 percent, and no task class loses acceptance. A broad miss keeps the default. An isolated miss sends that task class back for redesign. Any saving that moves debugging into review is accounting fiction, I think.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The public traces justify measurement. A paired replay with predeclared cost, acceptance, uncertainty, and review bounds earns the policy decision.</p></div>

## Put accepted results on the scorecard

Start with one product domain. The platform owner runs the pilot and owns the monthly number; the domain engineering lead approves retention classes and the acceptance rubric; Finance supplies the loaded review rate. Procurement joins when cache terms, data residency, or usage-field definitions change.

At the decision meeting, choose one outcome:

| Result | Decision | Evidence to retain |
|---|---|---|
| All bounds pass | Adopt in the domain, then expand one domain at a time | Raw usage export, rate card, field mapping, paired results |
| Broad bound fails | Hold the current policy | Failure distribution and review record |
| One task class fails | Redesign that class and rerun | Class slice, rejected outputs, revised rule |

My take: model spend, reviewer minutes, accepted count, retention class, and supplier exposure belong together in the monthly FinOps review. I don't know when today's subscription limits will tighten. I think teams should behave as if the meter already belongs to them, because cost per accepted result makes every carried token answer to the work that survives review.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Give one platform owner a domain-level pilot, a three-way decision rule, and a monthly scorecard built around model plus review cost per accepted result.</p></div>
