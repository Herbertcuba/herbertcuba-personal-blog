A $200 Claude subscription just generated $7,470 worth of API calls. A developer named Om Patel ran his own July usage through a cost tool and posted the screenshot on X. One month, one user, 6.16 billion tokens. Eighty-six percent of the bill was cache operations: the agent re-reading context it had already seen.

The mechanism showed up in someone else's logs. Engineer Nate Jones logged 3.77 billion tokens across 143 agent threads in one day, and 96% of it was text his setup had already sent.

Cheap AI is a subsidy, and the subsidy runs on resend. That makes context hygiene, deciding what enters the window and what stays out, the most unoptimized part of how we work with AI.

## What $7,470 of usage looks like

Patel ran a tool called claude-cost over his July 2026 usage, and the line items tell the story.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>86 percent of the bill is cache operations, generation is 13.6 percent, and the 37x subsidy is real. Sized honestly, it costs Anthropic compute in the low thousands, a long way from the $43.6 billion fiction.</p></div>

Cache reads: $3,596, nearly half the total. Cache writes: $2,842. Actual output tokens: $1,016, or 13.6 percent. Most of the money pays for re-reading old context. Writing new text is a rounding error.

I tried to poke holes in the screenshot before I believed it. The math holds: 5.88 billion cached tokens at the blended cache-read rate sit right on the $3,596 line item against Anthropic's public price sheet. The screenshot also shows the input-output skew directly: 186 tokens consumed for every one generated. I think that ratio is the whole article in one number.

The subsidy, sized honestly. This month it is 37x at list price. Run it for a quarter: $600 paid against roughly $22,410 consumed, call it $21,810 in discount. I think this is the number that should worry Anthropic, because it repeats every quarter for every heavy user. Scale it to a million Max subscribers and you get a $43.6 billion gap. That number is fiction. Most users are light, Anthropic caps usage with rolling five-hour windows it can tighten at will, and the API sticker is retail. What serving Patel actually costs in compute is far lower. How much lower, I don't know. Epoch AI's work suggests compute eats roughly two thirds of revenue, which would put the true cost of that month in the low thousands. A real subsidy, sized nothing like $7,470.

## Why every thread gets expensive in a curve

The physics of the tool explain the 96%.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Every turn resends the whole conversation, so threads get expensive in a curve, and stale context degrades answers on top of the cost. Treat context like memory in C: allocate, use, free.</p></div>

A token is roughly three quarters of a word. The context window is everything the model can see at once. And a language model has no memory between requests. None. Every turn, your agent framework sends the full conversation again with the new question stapled to the end.

Say I ask an agent to fix a checkout bug where the cart total ignores a discount code. Turn one sends the system prompt and the bug report. By turn twenty, I am resending nineteen replies and a pile of file contents to ask one more question. Every new turn pays for every old turn.

I think about this the way C programmers think about memory: allocate, use, free, and leak it and the process bloats until it dies. Context is a consumable resource with compounding cost.

The stale part of a long thread is context debt. Like technical debt, it charges interest, due on every turn, in dollars. It costs accuracy too. A [2023 study out of Stanford and Berkeley](https://arxiv.org/abs/2307.03172) found models get measurably worse at using information buried in the middle of long contexts. The 300k token thread is a liability twice: once on the invoice, once in the answer.

## Four ways agents burn the budget

The failure modes are boring. That is exactly why they are expensive.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Forever threads, whole files, retry loops, and fat tool servers. All four are the same bug: sending more than the question needs.</p></div>

The forever thread is the worst offender. You fixed the checkout bug in the same thread where you also planned next quarter, and now every new request carries hundreds of thousands of stale tokens. The model wades through all of it before it can think, and you pay for the wading.

Whole files read to find twelve lines. The discount logic lives in twelve lines of pricing.py, and the agent reads all 2,000 lines of checkout.py to find them. Grepping with your eyes is the most expensive search engine you own.

Retry loops. Many agents run on ReAct, a loop where the model thinks, calls a tool, reads the result, and thinks again. A tool that fails ten times means ten copies of the transcript, sent to produce one error message.

Fat tool servers. MCP, the Model Context Protocol, is a standard way to plug tools into a model, and a few generous servers can burn around 55,000 tokens in definitions before the model reads your first sentence, paid again on every request.

## Five habits that move the number

None of this needs new tooling. It is habits, plus one query against your logs.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>New thread per job, carry the artifact, cap the output, smallest model that passes, stable prefix for the cache. Boring habits, real money.</p></div>

Modern harnesses already compact long threads automatically, but they decide what to forget, and you keep paying for whatever they keep. Hygiene means you decide first.

Start a clean thread when the job changes. The checkout bug is fixed, the thread is done. New job, new thread. In my experience, this one habit does more for the bill than any model downgrade I have tried.

Carry the artifact, skip the argument. When a task ends, move forward the accepted result, the diff plus three lines on why. Some frameworks make this explicit. LangGraph wires agent steps together as a graph and threads a state object between them. That state is often a TypedDict, a Python dictionary where you declare the keys and their types up front. The StateGraph, the piece that decides which step runs next, passes that tidy state along and nothing else. The mess stays out by design.

Ask for exactly the length you need. "Reply with the twelve lines and nothing else." A long answer gets resent on the next turn, so verbosity bills you twice.

Use the dumbest model that still clears the bar. A small model can classify and route. Escalate when it fails. Put something between your agent and the API that is allowed to say no.

Then let the cache do its job. Prompt caching gives you the 0.1x price on repeated input, but only if the front of your request stays identical. Keep the system prompt and tool list stable and the reused part of every turn gets 90% cheaper on its own. Caching rewards hygiene. It cannot substitute for it.

Most providers split fresh from cached input in the usage block of every API response. Your reuse ratio is a few lines of jq, a command line tool for JSON:

```bash
jq -s 'map(.usage) |
  { fresh:  (map(.input_tokens) | add),
    cached: (map(.cache_read_input_tokens // 0) | add) } |
  .cached / (.fresh + .cached)' requests.jsonl
```

Above 0.5, most of what you pay for is text you already sent. Jones's tracker suggests it will come back a lot higher.

## Cost per accepted result

Token price is the visible number. It is rarely the decisive one.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The KPI is cost per accepted result: total spend to land one change you actually merge. Hygiene moves that number directly, and at org scale it becomes a budget line someone needs to own.</p></div>

My take: the KPI is cost per accepted result. How much did you spend, end to end, to produce one change you actually merged? Token price is an input to that number. Context hygiene is the multiplier: less input per turn shrinks every request, and cleaner context raises first-pass accuracy, because the model reasons over the twelve lines that matter instead of 2,000 lines of noise.

Now scale it. Say 200 developers each push 50 million tokens a day through agent loops. At Jones's ratio, 9.6 billion of those 10 billion daily tokens are reused input, close to $3,000 a day even at cache-read prices, about $5,000 per seat per year. Any org running [agents in production](/posts/2026-03-27-anatomy-level-3-agent/) has this invoice already. I think every org past a handful of seats needs a named owner for that number, and the report should live where the cloud bill lives: the monthly FinOps review.

You get 200 developers to close their threads the same way you get them to write tests: set a thread limit in the harness config, put the reuse ratio on the dashboard, and let the owner watch the number.

## Who pays for cheap AI

The gap between $200 and $7,470 has to be paid by someone.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Enterprise API margins fund the consumer discount, subscriptions work like unlimited mobile data, and the meter is coming.</p></div>

My take: the gap is the business model. API prices carry enterprise margins, and those margins likely cross-subsidize the consumer plans. I say likely because Anthropic's books are private, so treat the mechanism as a hypothesis. The pricing shape is plain either way: light users cover the heavy ones, same as unlimited mobile data.

Meanwhile the land grab is funded: Anthropic's run-rate went from $9 billion at the end of 2025 to $47 billion this May. Profitability is a promise dated later.

We have seen how it ends. GitHub Copilot let power users burn 25 times their subscription fee, then switched to token billing, and the user revolt was immediate. I think the meter comes for Claude Max too, eventually. Cheap AI was never cheap. Somebody else is paying, and the invoice is due later.

One honest limit on the claim: for one-shot tasks where broad context is the whole point, hygiene buys little. The claim covers looping, multi-turn agent work, which is where the bills are. I don't know where the floor is. I do know where the meter starts: one query against your logs, run tonight. I will be running it on mine.

This is the orchestration thesis at the smallest scale there is, the same argument I made in [Welcome to the Orchestration Era](/posts/welcome-to-the-orchestration-era/), applied to a single request. Decide what enters the room. Carry forward only what earned its place. The cheapest token is the one you never send.
