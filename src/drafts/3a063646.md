In July 2026, Claude Code user Om Patel put a number on a cost most subscribers never see. His $200 Claude Max plan carried 6.16 billion tokens through [Claude Code, Anthropic's terminal-based coding agent](https://x.com/om_patel5/status/2083401185172541449). At API list prices, the same month came to $7,470.35, or 37.4 times his subscription fee.

That figure is the clearest answer to what Patel would have paid without the subscription, assuming identical use through the API. It is not Anthropic's compute cost, which the company does not disclose. API prices are retail prices, and the Max plan also has rolling session and weekly limits.

I think the larger risk is what the flat fee prevents us from learning. When every extra turn appears free, teams get little feedback about the old instructions, tool definitions, file contents, and conversation history moving through the system again.

## The costly part is coming back

An agentic coding tool can inspect files, call tools, edit code, and respond across many turns. On each turn, the model receives a context: the instructions and working material it can use for that response. As the thread grows, much of that material returns with the next request.

Prompt caching makes repetition cheaper, but it does not make it free. When a stable part of the request has been processed before, the provider can charge a discounted cache-read rate rather than the full input rate. In Patel's record, cache reads and writes still accounted for 86.2% of the API-list-price total, while model output accounted for 13.6%. His usage consumed 186 tokens for every output token.

The exact ratio varies, but the shape appears elsewhere. [Nate B. Jones](https://www.youtube.com/watch?v=Y8vAQ1FgNbM), a practitioner who instrumented one day in his OpenAI Codex coding workspace, recorded 3.59 billion reused-input tokens out of 3.77 billion, almost 96%, across 143 threads. Jones sells a context-management framework, so this is one person's measurement rather than an industry benchmark. Separately, [the team behind Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus), a general-purpose AI agent, reports an average input-to-output ratio of about 100 to one in production.

<span class="chapter-tldr__label">In short</span>
<p>Agentic coding repeatedly processes the active context. Caching lowers the rate, yet measured workflows still spend most token traffic on input rather than new output.</p>
</div>

## Context engineering is a quality practice

Context engineering means choosing what information the model receives, in what order, and for how long. Cost is only one reason to care. A [2024 peer-reviewed study by Nelson Liu and colleagues](https://arxiv.org/abs/2307.03172) at Stanford and Berkeley found that language models often performed worse when relevant information sat in the middle of a long input, even when the models supported long contexts. More material can make the right material harder to use.

Claude Code already uses caching and automatic compaction, which summarizes old conversation history as the context window fills. Those defaults help, but a generated summary cannot know every detail the next task will need. Deliberate context engineering starts by opening a clean thread when the task changes, searching before loading large files, and limiting verbose tool output. When work must continue, carry a short handoff artifact with the objective, constraints, decisions, changed files, and test status instead of the entire debate that produced them.

This is curation rather than aggressive deletion. Failed attempts may contain evidence worth preserving, and broad context may be necessary for one-off research or difficult reasoning. The practical aim is to give the model the smallest context that remains sufficient for the result being asked of it.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Good context engineering improves the model's odds of finding what matters: reset unrelated work, select evidence before loading it, and preserve useful decisions without carrying every prior turn.</p>
</div>

The mapping is precise: a flat subscription gives the user an interface of abundance, while token processing remains metered underneath. Convenience is useful, but it can weaken the habit of seeing what each request consumes.

## Put cost next to acceptance

The better operating measure is cost per accepted result: the total model cost for a class of tasks, including failed attempts and retries, divided by the outputs that pass their required tests or review. Log fresh input, cached input, output, retries, and acceptance together. For subscription use, keep the seat fee and the API-equivalent amount separate; the latter is a shadow price for comparing workflows, not cash saved.

This measure changes the engineering question. A longer context can be worth paying for when it raises the acceptance rate, while cheap model output is waste when it repeatedly fails. No public controlled benchmark proves that context hygiene always matters more than switching models, so teams should test both against stable task types.

Pricing can make this skill urgent without warning. Technology critic [Ed Zitron reported](https://www.wheresyoured.at/the-more-you-buy-the-more-you-lose/) that heavy users of GitHub Copilot, GitHub's AI coding assistant, consumed more than 25 times their monthly fee before a move toward token-based limits triggered user resistance. That precedent does not predict Anthropic's next move, but it shows why a hidden subsidy is a poor operating assumption.

A $200 invoice tells finance what was paid. Cost per accepted result tells engineering whether useful work became cheaper or merely looked free. Learning that distinction while the subscription is forgiving is the advantage.

<p>Track every retry and judge spend against work that passes. That discipline pays under flat pricing and becomes essential if limits tighten or token billing returns.</p>
