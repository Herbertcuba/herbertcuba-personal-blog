I tried to read the $7,470 screenshot as one extreme month. The $200 subscription made it harder to dismiss.

Om Patel [posted a `claude-cost` screenshot on X](https://x.com/om_patel5/status/2083401185172541449) for July 2026. It showed 36,881 responses and 6.16 billion tokens. At API list prices, the displayed usage added up to $7,470.35. The post paired it with a $200 Claude plan.

The shape of the report was stranger than its size. Cache reads and writes made up about 86 percent of its list-price total. In a separate one-day measurement, Nate B. Jones [logged 3.77 billion tokens across 143 coding threads](https://www.youtube.com/watch?v=Y8vAQ1FgNbM). His tracker marked 3.59 billion as reused input, or 95.2 percent. This is one workspace. I think it gives every agent team a useful hypothesis to test.

## What $7,470 of usage looks like

Nearly half of the reported total came from 5.88 billion cache-read tokens.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Cache operations made up about 86 percent of the displayed list-price usage. The 186-to-1 ratio points toward the request wrapped around each answer.</p></div>

A cache write stores a reusable request prefix. A cache read uses it again at a lower price. The report showed $3,595.52 in reads, $2,841.89 in one-hour writes, and $1,015.97 in output tokens.

At [Anthropic's published cache prices](https://docs.anthropic.com/en/docs/about-claude/pricing), the blended read rate was about $0.61 per million tokens. It lands on the same $3,596 line item.

Divide the 6.16 billion total by 33 million output tokens and you get about 186 consumed tokens for each generated token. I think the surrounding prompt, tools, files, and conversation are the first place to look.

## What 37 times the plan price means

The displayed API retail value was 37.4 times the plan price for that month.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The 37.4x ratio compares a subscription with API list-price value. Anthropic's serving cost remains private, and plan limits keep this observation from becoming a forecast.</p></div>

That still says nothing precise about Anthropic's margin. API prices are retail prices, and [Claude plans have rolling and weekly usage limits](https://claude.com/pricing). I don't know Anthropic's internal cost for this month. The useful signal is that flat pricing can hide a large amount of metered work.

## Context is a consumable resource

Our running example is a checkout bug where a discount code never reaches the cart total.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Each request is billed against the context the coding harness makes available. Long threads carry old turns into new work, even when caching lowers the price of that reused input.</p></div>

A token is a small unit of text, roughly three quarters of an English word. The context window is what the model can use in one request. The model API starts fresh, while the harness around [a Level 3 agent](/posts/2026-03-27-anatomy-level-3-agent/) keeps earlier material available.

On turn one, the checkout agent receives the bug report, instructions, and a tool list. It opens `pricing.py`. Turn two is metered against that material plus the first reply and file contents. By turn twenty, one small question may travel with nineteen older replies and a pile of tool results.

I think of this as context debt. Each stale file or failed command can charge interest on later requests. The [Lost in the Middle study](https://arxiv.org/abs/2307.03172) found that models often struggle when useful information sits inside a long context. It tested retrieval tasks, so the checkout fix still needs its own test.

## Five ways the checkout agent wastes context

One failed test loop can carry the growing checkout transcript through ten more requests.

## Put context hygiene into the workflow

A fresh checkout run can begin with the bug report and the useful lines from `pricing.py`.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Carry the accepted patch and test result into the next step. Leave dead searches behind, keep stable instructions cacheable, and escalate models only when the checkout eval requires it.</p></div>

Start a new thread when the job changes. Search before sending a whole file. Ask for the patch plus a short explanation. Keep the request prefix stable so it stays cacheable. In my experience, closing a finished thread is the cheapest place to begin.

LangGraph can make the boundary visible in code. LangGraph is a library for arranging agent steps as a graph. A `TypedDict` is a Python dictionary whose allowed keys and value types are declared up front. A `StateGraph` connects the steps and passes that typed state between them. For our checkout run, the state can keep the bug ID, accepted diff, and test result while leaving the search transcript in the finished step.

Pruning can remove a detail the next step needs. Keep the test command, failing behavior, and accepted decision. Drop a piece only after the checkout eval proves quality holds. I think hygiene earns trust through that guardrail.

## Prove it with a two-week pilot

Ten seats and a fixed task set are enough to test the claim before changing a team default.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Compare a baseline week with a hygiene week using the same tasks, model, and budget. Roll back any change that lowers acceptance or raises review time enough to erase the saving.</p></div>

Log one provider-neutral event for every attempt:

```yaml
run_id: string
task_id: string
attempt: integer
model: string
fresh_input_tokens: integer
cache_read_input_tokens: integer
cache_write_input_tokens: integer
output_tokens: integer
billed_cost: number
outcome: accepted | rejected
reviewer_decision: string
```

Attempt one on the checkout bug might end as `rejected` because the discount test failed. Attempt two keeps a new event under the same `task_id`. Its accepted patch closes the task, while both attempts stay in the cost total.

Use real completed tasks. Week one records the current harness. Week two turns on fresh-thread defaults and curated state. Keep the model, task set, budget, and acceptance tests fixed. Inspect traces where cost falls and review time rises. Engineering owns acceptance. Platform owns metering and defaults. FinOps reviews the result.

The stop condition is simple: revert a hygiene change when acceptance drops or rework rises beyond the team's agreed limit. I think this is how context hygiene becomes an engineering result instead of a tidy theory.

## Measure cost per accepted result

Our checkout patch counts when the discount test passes and a reviewer accepts the diff.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Cost per accepted result includes every paid attempt in the numerator and only reviewed outcomes in the denominator. Reuse ratio diagnoses context waste, while acceptance protects quality.</p></div>

<div class="keymsg">
<span class="keymsg__label">The unit economics of agentic work</span>
<p class="keymsg__text">Cost per accepted result = billed agent cost across all attempts ÷ accepted tasks.</p>
<p>The rejected checkout patch, cache writes, retries, and final answer all stay in the numerator.</p>
</div>

Define acceptance before the run. For this bug, the discount test passes, the cart total stays correct, and a reviewer approves the diff. A partial patch remains rejected unless the team defines a weighted policy first. Track human review time beside cost, because a cheap patch that needs an hour of repair has moved the bill to a person.

Reuse ratio shows where to inspect. Cost per accepted result shows whether smaller context preserved useful work. My take is to put both on the platform dashboard beside acceptance rate, latency, and rework.

At renewal, procurement should ask whether token units, cache rates, or usage limits can change. Engineers should already have the traces needed to model the answer.

The $200 plan hid the meter. A team that can trace one accepted checkout fix through every paid attempt already knows what its agent work is worth.
