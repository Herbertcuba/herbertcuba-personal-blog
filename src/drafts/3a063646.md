I tried to read the $7,470 screenshot as a story about one extreme Claude user. But the $200 subscription attached to it changed the story.

A developer named Om Patel ran a July usage report through a tool called `claude-cost` and [posted the screenshot on X](https://x.com/om_patel5/status/2083401185172541449). The report covered one user, 36,881 responses, and 6.16 billion tokens. At API list prices, the month added up to $7,470.35.

The shape of the bill was stranger than its size. Cache operations made up 86 percent of the total. The agent spent most of the money reading context it had already seen.

Another engineer, Nate B. Jones, [measured 3.77 billion tokens across 143 coding threads](https://www.youtube.com/watch?v=Y8vAQ1FgNbM) in one day. His setup had already sent 3.59 billion of them, almost 96 percent. That figure comes from one instrumented workspace, so it cannot stand in for every engineering team. I think the mechanism behind it is the part worth carrying forward.

## What $7,470 of usage looks like

The line items show where an agent bill grows.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Cache reads and writes made up 86 percent of this bill. Generation took 13.6 percent. The screenshot supports a 186-to-1 ratio between all tokens consumed and output tokens generated.</p></div>

A cache lets the provider reuse the matching start of an earlier request. A cache write stores that prefix. A cache read uses it again at a lower price.

The posted report showed $3,595.52 in cache reads and $2,841.89 in one-hour cache writes. Output tokens cost $1,015.97. The report logged 5.88 billion cache-read tokens, and their blended price lands around $0.61 per million. That sits between Anthropic's published cache-read prices for the models in the report.

Divide the 6.16 billion total tokens by 33 million output tokens and you get 186 tokens consumed for every one generated. I think that ratio gives a junior engineer a better debugging target than the model name. It points toward the request envelope: the prompt, files, tool definitions, and conversation sent around the answer.

The $7,470 figure uses API retail prices. Anthropic's compute cost is lower and private, so the screenshot proves list-price consumption rather than a $7,470 loss for Anthropic.

## Three calculations

The same screenshot changes meaning as the time window grows.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The month consumed 37 times the subscription price at API list rates. Flat usage over a quarter creates about $21,810 in implied discount. A million-user ceiling produces a huge number that breaks once caps and real compute costs enter the calculation.</p></div>

For the month, $7,470 divided by $200 is 37.4. That is the cleanest number in the story.

Hold usage flat for a quarter and the developer pays $600 while consuming roughly $22,410 of list-price API value. The implied discount is about $21,810. The repeatability of that gap deserves more attention than the first month's shock.

Now give the same usage to one million subscribers for six months. Revenue reaches $1.2 billion while list-price value reaches $44.8 billion, leaving a $43.6 billion gap. That ceiling is fiction. Most users are lighter, Claude plans have rolling five-hour and weekly limits, and retail API prices exceed the provider's compute cost.

Epoch AI's work suggests inference compute can absorb roughly two thirds of revenue at a frontier lab. Applying that ratio here would place the cost of the month in the low thousands. Anthropic does not publish enough detail to know exactly how much lower.

## Context is a consumable resource

A checkout bug makes the resend loop easy to see.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A model starts each API request without memory of the last one, so an agent resends the conversation. Long threads grow in a curve because every turn carries the old turns again. Stale context can also hide the few lines the model needs.</p></div>

Suppose the cart total ignores a discount code. On turn one, the coding agent receives the system prompt, its tool list, and the bug report. On turn two, it receives all of that again, plus its first reply and the file it opened. By turn twenty, a small follow-up question travels with nineteen old replies and a pile of file contents.

A token is a small unit of text, roughly three quarters of an English word. The context window is the text the model can see for one request. The model API is stateless, which means your agent framework must rebuild that context on every turn.

This is the memory layer inside [a Level 3 agent](/posts/2026-03-27-anatomy-level-3-agent/). The harness assembles what the model sees before each step, even when the model itself starts fresh.

I think of context the way a C programmer thinks about memory: allocate it, use it, free it. A thread that keeps every failed search and tool response builds context debt. The debt charges interest on each later request.

There is a quality risk too. The [Lost in the Middle study](https://arxiv.org/abs/2307.03172) found that models often perform worse when useful information sits inside a long context. The study tested retrieval rather than checkout patches, so it does not prove that clean threads improve coding accuracy. It gives us a reason to measure the hypothesis instead of assuming a larger window always helps.

## Five ways agents burn the budget

Our checkout bug can waste context in five ordinary ways.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A forever thread, oversized files, raw documents, retry loops, and large tool schemas all send more text than the checkout fix needs. Each failure adds old material to every later request.</p></div>

1. **The forever thread.** The checkout bug shares a thread with sprint planning and naming debates. Every fix attempt pays to carry those older conversations.

2. **Whole files.** The discount logic lives in twelve lines of `pricing.py`, but the agent reads all 2,000 lines of `checkout.py`. Search first and send the useful lines.

3. **Raw documents.** A forty-page pricing specification enters the context even though the answer lives in two paragraphs. Extract the relevant section before the model sees it.

4. **Retry loops.** Many agents use ReAct, short for reason and act. The model chooses a step, calls a tool, reads the result, and repeats. Ten failed test commands can resend the growing checkout transcript ten times.

5. **Large tool schemas.** MCP, the Model Context Protocol, is a standard way to expose tools to a model. [One widely cited count](https://simonwillison.net/2025/Aug/22/too-many-mcps/) found that the GitHub MCP server could place about 55,000 tokens of tool definitions in the window before the first user sentence. Connect only the tools this checkout task needs.

## The practices that move the number

Context engineering already has a canon, and hygiene turns it into daily operating rules.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Close the thread when the job ends, carry the accepted artifact forward, limit answer length, search before sending files, and keep cacheable prefixes stable. A small log query reveals how much input your agent reuses.</p></div>

[Anthropic calls context a finite resource](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), and modern coding harnesses compact long threads automatically. Compaction helps. The harness still chooses what to forget and when, while the engineer keeps paying for whatever remains.

For the checkout bug, start a fresh thread. Send the bug report and the twelve relevant lines from `pricing.py`. Ask for the patch and the test. Once both pass, carry those accepted artifacts into the next task and leave the debate in the old thread. I think this is the cheapest intervention here because it begins with one click and a team norm.

LangGraph can make that boundary explicit. LangGraph is a Python library for arranging agent steps as a graph. A `TypedDict` is a Python type that declares which keys a dictionary should contain and the type of each value. A `StateGraph` connects the LangGraph steps and passes that typed state between them. Our checkout state might contain the bug ID, the accepted diff, and the test result. The graph carries those fields forward while the search transcript stays behind.

That is [orchestration](/posts/welcome-to-the-orchestration-era/) at the scale of one bug: decide which artifact survives the handoff.

Keep the system prompt and tool list stable at the start of each request. Anthropic charges one tenth of the normal input price for a matching cache read. Then append the changing checkout material at the end. Caching makes repeated context cheaper. Hygiene reduces how much repeated context exists.

If each API response is stored as one JSON object in `requests.jsonl`, `jq`, a command-line tool for JSON, can estimate the reuse ratio:

```bash
jq -s 'map(.usage) |
  { fresh:  (map(.input_tokens) | add),
    cached: (map(.cache_read_input_tokens // 0) | add) } |
  .cached / (.fresh + .cached)' requests.jsonl
```

Run it before changing the harness. Run it again after the team starts closing completed threads.

## Cost per accepted result

The checkout patch needs a unit of economics tied to work that shipped.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Cost per accepted result divides total agent spend by the changes a team actually merges. It captures reused context, retries, and rejected answers in one number. At organization scale, a named AI FinOps owner should report it beside the cloud bill.</p></div>

My take is cost per accepted result: the total model spend required to produce one checkout change the team accepts and merges. A cheap token helps. A shorter thread changes how many tokens, retries, and rejected patches the result requires.

Cleaner context may raise first-pass accuracy because the model sees the twelve useful lines with less noise. We still need an eval to prove it. For this task, the eval is simple: does the discount test pass, does the cart total stay correct, and does a reviewer accept the diff? Measure the spend across every attempt that led there.

Put that checkout team inside a 5,000-person Nordic company with 200 developer seats. If each seat pushes 50 million tokens through agent loops per day, the company sends 10 billion. Apply Jones's almost-96-percent ratio as an illustration and 9.6 billion are reused input. At $0.30 per million cached tokens, the reuse costs about $2,880 a day. That is roughly $3,700 per seat per year on 260 working days, or $5,300 if the agents run every calendar day.

I think a platform team should name an AI FinOps owner once agent usage reaches this scale. Put reuse ratio and cost per accepted result in the monthly review beside build time and cloud spend. Defaults can do the rest: set a thread limit in the harness and make a fresh task the normal path.

## Who pays for cheap AI

The subscription hides the context bill until a provider changes the meter.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Light subscribers and enterprise API margins may help fund heavy consumer usage, while investor capital supports the expansion. GitHub Copilot shows the supplier risk: a flat plan can move to token billing. Your logs and cost-per-result metric survive that change.</p></div>

My take is that the gap between $200 and $7,470 is part of the acquisition model. Light users likely support heavy users, and enterprise API prices carry margins that subscriptions can spend. Anthropic's books are private, so this remains a hypothesis.

Anthropic's self-reported run-rate revenue moved from about $9 billion at the end of 2025 to $47 billion in May 2026, while it announced $95 billion across two funding rounds, as [Simon Willison documented](https://simonwillison.net/2026/May/29/anthropic/). Capital gives the company room to subsidize usage while it grows.

GitHub Copilot offers the procurement warning. Ed Zitron reported that power users could burn [more than 25 times their monthly subscription fee](https://www.wheresyoured.at/the-more-you-buy-the-more-you-lose/) before the switch to token billing triggered a user revolt. A team buying a flat agent plan should ask at renewal how usage limits and billing units can change.

One-shot tasks and frontier reasoning may need broad context, so hygiene buys less there. Looping agent work behaves differently because old text returns on every turn.

I don't know when the meter reaches Claude Max or what shape it takes. I know the subscription discount belongs to the vendor, while the reuse ratio in your logs belongs to you. When pricing changes, cost per accepted result tells you whether the agent still earns its seat.
