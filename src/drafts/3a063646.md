A $200 subscription can conceal a $7,470.35 month.

On August 1, 2026, AI practitioner Om Patel [shared a dashboard](https://x.com/om_patel5/status/2083401185172541449) for an unidentified person's July use of Claude Code, the command-line coding agent from AI company Anthropic. It recorded 6.16 billion tokens, the small units of text processed by a language model. Pricing that traffic through Anthropic's application programming interface, or API, produced a list-price estimate of $7,470.35: 37.4 times the subscription fee.

That estimate is a counterfactual API bill, not an invoice, a claim about Anthropic's serving cost, or money the subscriber literally saved. It still shows that identical measured traffic, billed by the token at those list rates, would cost thousands rather than hundreds. I think the more useful problem is what flat pricing prevents us from learning while the bill stays fixed.

## Flat pricing hides the request

A direct API bill separates fresh input, cached input, cache writes, and model output. Subscription users can collect the same measurements, but the next oversized request creates no visible marginal charge. A low monthly payment can therefore be mistaken for an efficient way of working.

The missing signal matters because [Claude Code sends the full conversation history with each request](https://code.claude.com/docs/en/costs). That history is part of the context: the instructions, messages, files, tool definitions, and tool results supplied for the next response. As a thread grows, old material keeps travelling with new work.

Prompt caching makes exact matching parts of that material cheaper to process again. Those matching tokens appear as cache reads, also called reused input, but cheaper repetition is still repetition. In Patel's dashboard, cache reads accounted for $3,595.52 of the list-price estimate; the one-hour and five-minute cache writes together accounted for $2,844.72. Cache operations represented 86.2% of the estimate.

In one working day with Codex, the coding agent from AI company OpenAI, AI practitioner Nate B. Jones [reported](https://www.youtube.com/watch?v=Y8vAQ1FgNbM) that 3.59 billion of 3.77 billion tokens were reused input, or 95.2%. Jones sells a context-management framework, and this was one self-instrumented day, so 96% is a signal rather than an industry benchmark. Patel's separate dashboard shows the same broad pattern.

  <p>Coding-agent requests repeatedly carry old context. Caching discounts that traffic, while two individual reports show how large the repeated share can become.</p>

## Context engineering is selective memory

Context engineering means deliberately choosing what the model receives, in what order, and in what form. When a task changes, start a clean thread and carry forward a compact state note with the goal, constraints, decisions and their reasons, relevant files, failed approaches, and open checks. Preserve the evidence needed to continue the work rather than the conversation that produced it.

Keep stable instructions and tool definitions at the beginning because prompt caches depend on an unchanged opening segment. Retrieve large files and tool output only when relevant, and compact before reaching the model's limit. Claude Code already provides automatic caching and compaction, but those defaults cannot know which project constraint will matter tomorrow.

The work is subtle because aggressive pruning can make cost and quality worse. Remove a failed approach and the agent may repeat it; remove a quiet constraint and a plausible answer may become unusable. The 2023 study [*Lost in the Middle*](https://arxiv.org/abs/2307.03172), peer-reviewed in 2024 by researchers from Stanford University, the University of California, Berkeley, and AI company Samaya, found that models often used relevant information less reliably when it sat in the middle of long input. Too much context can bury evidence, while too little can erase it.

Test the balance instead of guessing. Define acceptance checks for a representative task set, then compare the normal workflow with a context-managed version under the same model and tools. Record fresh input, cache reads, cache writes, output, retries, review time, and acceptance. Because responses vary between runs, repeat both conditions and set the minimum sample and uncertainty rule before seeing the outcome.

<div class="chapter-tldr">
  <span class="chapter-tldr__label">In short</span>
  <p>Good context engineering preserves the smallest useful state, then tests whether the reduction lowers repeated input without erasing evidence or weakening the result.</p>
</div>

## Count the work that survives review

Token reduction is not the final measure. An accepted result is an output that passes predeclared technical checks and any required human review, without immediately returning as reopened work. To find full cost per accepted result, add all API spend, the cost of reviewer time, and allocated context-tooling cost. Keep failed attempts and retries in that numerator, then divide by the number accepted.

For subscriptions, report the $200 cash payment separately from a shadow estimate based on API list prices. Keep fresh input, cache reads, cache writes, and output separate as well. A rising cache-hit rate can look efficient while the total request grows, and a cheaper request is a poor trade if it produces more failures or review.

Today's flat-rate access gives teams room to learn under forgiving economics. Use that room to meter requests, practice selective context, and establish the acceptance denominator. If API migration, usage caps, or new commercial terms sharpen the price signal later, the team will already know which context earns its place and what completed work costs.
