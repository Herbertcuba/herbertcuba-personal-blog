Om Patel [posted a July 2026 Claude Code usage screenshot](https://x.com/om_patel5/status/2083401185172541449) with two numbers side by side: $200 paid and $7,470.35 at API list prices.

The same screenshot logged 36,881 responses and 6.16 billion tokens. Cache reads and one-hour cache writes accounted for 86.2 percent of the displayed value. Output accounted for 13.6 percent.

I don't know the provider's margin on this user because Anthropic's serving cost remains private. The 37.4x gap measures API retail value.

The line items show where the work went. I think the output number is almost a distraction. Most of the displayed value sat in the material carried into each request.

## One day, 95.2 percent reused

In [a video about his tracker](https://www.youtube.com/watch?v=Y8vAQ1FgNbM), Nate B. Jones reported 3.77 billion tokens across 143 Codex threads in one working day, with 3.59 billion classified as reused input.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The almost-96-percent figure covers one instrumented workspace on one day. A separate screenshot shows 186 total tokens per output token, so both cases make context worth measuring on its own.</p></div>

Jones's figure works out to 95.2 percent. That makes it a field observation with a sample of one. The monthly screenshot offers a separate view: 6.16 billion total tokens produced about 33 million output tokens, a ratio of roughly 186 to one.

I think cache efficiency and context relevance belong on separate meters. A cache hit says old text moved at a lower price. Usefulness depends on whether that text helps the current task.

## The checkout transcript grows

Imagine one task: `SAVE10` is accepted at checkout, but the total stays unchanged.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The first request may need the bug report and a few pricing lines. By turn twenty, a transcript-carrying harness may also resend old searches, failed patches, and earlier tool output.</p></div>

Anthropic's [Messages API is stateless](https://platform.claude.com/docs/en/build-with-claude/working-with-messages), so the caller supplies the conversation history. Other APIs and harnesses can manage state differently. The cost pressure appears whenever earlier material returns in later calls.

The first checkout request might contain instructions, tool definitions, and the bug report. The next adds `pricing.py`, a proposed patch, and a failed test. After enough retries, one more test can arrive wrapped in the whole route used to reach it.

Long input also creates a quality risk. The [Lost in the Middle study](https://arxiv.org/abs/2307.03172) found weaker retrieval when useful information appeared inside long contexts. Its experiments were retrieval tasks, so the checkout workflow still needs its own evaluation.

I think stale trajectory becomes a recurring charge. Each later call pays for it in tokens and model attention.

## Keep the evidence

For the checkout fix, the next call needs the relevant pricing lines, the current patch, and the latest test result.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Curated state carries verified task evidence and removes expired search paths. Stable instructions can still benefit from prompt caching, while clean threads keep unrelated work outside the request.</p></div>

Start a clean thread when the job changes. Search before sending a whole repository file. Ask for the patch instead of a long explanation. Keep stable instructions together so [prompt caching](https://platform.claude.com/docs/en/about-claude/pricing) can price repeated prefixes at the cache rate.

Claude Code already documents [automatic compaction](https://code.claude.com/docs/en/costs) near the context limit. That helps late in a long session. An explicit context policy acts earlier by deciding what the checkout task carries forward.

Fresh context is why [task loops reset between attempts](/posts/everyone-discovered-loops/): they preserve the accepted artifact and its evidence while removing a disproved search path from later requests.

I think teams often treat a high cache-hit rate as proof of healthy context. It proves cheap reuse. The next-call evaluation still has to show that the reused material improves the result.

## Count every paid attempt

The checkout patch only counts when the discount test passes and a reviewer approves it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Cost per accepted result includes every paid attempt behind the approved checkout change. Track review time beside it, then compare the current harness with a curated-context version under the same model and acceptance rule.</p></div>

<div class="keymsg">
<span class="keymsg__label">The unit that reaches production</span>
<p class="keymsg__text">Cost per accepted result = total model cost across all attempts ÷ accepted results.</p>
<p>Every failed checkout patch stays in the numerator.</p>
</div>

If five attempts produce one accepted fix, all five belong to its cost. Reviewer time belongs beside the number. A cheaper run that creates a longer review can still lose.

Run completed checkout tasks through both context policies for 30 days. Hold the model and [acceptance spec](/posts/the-spec-is-the-cognitive-work/) steady. Record input by category, output cost, attempts, acceptance, and review minutes. Adopt the policy when cost falls while acceptance holds. Roll it back when quality drops or review expands.

I think a team spending materially on agent loops needs a named platform owner for this metric, with FinOps checking the price fields each month. Trace retention, redaction, and data residency belong in the same review. That is the practical version of [owning the agent layer](/posts/who-owns-the-agent-layer/).

My take: a flat plan can hide the meter. Cost per accepted result makes every paid loop answer for what reached production.
