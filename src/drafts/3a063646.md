Om Patel's [July Claude Code screenshot](https://x.com/om_patel5/status/2083401185172541449) put two prices on the same month: $200 for the plan and $7,470.35 at API list prices. His tool counted 36,881 responses and 6.16 billion tokens. Cache reads and writes made up about 86 percent of the displayed total.

Nate B. Jones [logged 3.77 billion tokens across 143 coding threads](https://www.youtube.com/watch?v=Y8vAQ1FgNbM) in one day. His tracker marked 3.59 billion as reused input, or 95.2 percent. That is one instrumented workspace. I think context around each answer may carry the cost.

Reuse alone says little about relevance. A stable system prompt can be a healthy cached prefix. Old searches and dead retries can become context debt. The engineering job is to separate those two kinds of reuse, then measure what each accepted result costs.

## What $7,470 of usage looks like

The shape of Patel's usage points to the request wrapped around each answer.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Cache operations made up about 86 percent of the displayed list-price usage. The 186-to-1 ratio points toward the request carried around each generated token.</p></div>

Nearly half of the listed dollar total came from 5.88 billion cache-read tokens. A cache write stores a reusable request prefix. A cache read uses that prefix again at a lower price. Patel's screenshot showed $3,595.52 in reads, $2,841.89 in one-hour writes and $1,015.97 in output tokens.

At [Anthropic's published cache prices](https://platform.claude.com/docs/en/about-claude/pricing), the blended read rate was about $0.61 per million tokens. Divide 6.16 billion total tokens by 33 million output tokens and the workflow consumed about 186 tokens for each token it generated.

I think the envelope deserves inspection first because later requests can carry its instructions, tool definitions and old conversation again.

## What 37.4 times the plan price means

The ratio becomes useful only when its boundary stays visible.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The ratio shows metered retail value inside a capped plan. It reveals a workflow dependency while leaving Anthropic's private serving cost unknown.</p></div>

The 37.4 ratio compares a subscription fee with API list price. Claude plans have [rolling and weekly usage limits](https://claude.com/pricing). Anthropic does not disclose its per-request cost or margin. I don't know what Patel's month cost the company to serve.

The screenshot still works as a workflow meter. Flat pricing can hide a large context dependency until a new limit or cache term exposes it at renewal.

## Reuse can be healthy or expensive

Follow one discount bug through the rest of the article: the code reaches the cart, yet the total never changes.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Healthy reuse carries required instructions and useful evidence. Context debt carries stale work that raises cost or weakens the accepted result.</p></div>

A token is a small unit of text. The context window is the text a model can use in one request. Model APIs start fresh, so an agent harness may resend earlier messages, file contents and tool results on each turn. A [Level 3 agent](/posts/2026-03-27-anatomy-level-3-agent/) wraps tools and state around that stateless call.

Stable system instructions and the tool contract belong in every checkout request. The bug report and useful lines from `pricing.py` remain relevant until the test passes. A failed search from turn three becomes prior trajectory once it stops helping. Sprint-planning notes are irrelevant from the start.

By turn twenty, a small question can travel with nineteen earlier replies. The [Lost in the Middle study](https://arxiv.org/abs/2307.03172) found that models often struggle when useful information sits inside a long context. It tested retrieval tasks, so the checkout fix still needs its own evaluation.

I think teams should trim prior trajectory and irrelevant material first. Required instructions stay stable. Useful evidence stays until the acceptance check closes the task.

## Put context hygiene into the workflow

State boundaries turn hygiene from a prompt habit into code.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Stable instructions stay cacheable. Verified checkout state moves between steps, while dead searches lose their route into the next request.</p></div>

Modern coding harnesses may summarize long threads automatically. That helps. The harness still chooses what to forget and when, so deliberate hygiene sets the boundary earlier.

LangGraph is a Python library for workflows that branch or repeat. A `StateGraph` connects the steps and passes shared state between them. A `TypedDict` describes the expected keys in that state for Python's type checker. Runtime validation still belongs in code.

The state can hold `bug_id`, `relevant_lines`, `patch`, `test_passed` and `reviewer_decision`. The search step returns the useful lines. Its raw transcript has no state key, so it has no route into the patch step. This is the workflow side of [owning the agent layer](/posts/who-owns-the-agent-layer/).

An `accepted` transition requires `test_passed: true` plus reviewer approval. Agent narration has no power to mark the patch complete. I think this boundary makes context hygiene testable because every carried item needs an engineering reason.

A cache hit measures reuse. It says nothing about relevance. Keep the required prefix stable, then measure retrieved evidence and prior trajectory separately.

## Prove it with a bounded pilot

A paired replay can show whether pruning context survives contact with quality.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A paired pilot can compare baseline and hygiene strategies under the same model and acceptance checks. The decision includes billed cost, reviewer time and quality.</p></div>

Replay completed checkout tasks with two context strategies. The baseline uses the current harness. The hygiene run uses curated state. Keep the model, budget and acceptance criteria version fixed. Run each task through both strategies so task difficulty cannot hide the effect.

Log every paid attempt:

```yaml
task_id: string
attempt: integer
context_strategy: baseline | hygiene
stable_prefix_tokens: integer
retrieved_evidence_tokens: integer
prior_trajectory_tokens: integer
cache_read_input_tokens: integer
billed_cost: number
latency_ms: integer
review_minutes: number
acceptance_criteria_version: string
test_passed: boolean
reviewer_decision: approve | reject
outcome: accepted | rejected
```

A short SQL query can put both strategies side by side:

```sql
SELECT context_strategy,
       SUM(billed_cost) /
       COUNT(DISTINCT CASE WHEN outcome = 'accepted' THEN task_id END)
         AS cost_per_accepted_result,
       AVG(review_minutes) AS review_minutes,
       AVG(latency_ms) AS latency_ms
FROM agent_attempts
WHERE acceptance_criteria_version = 'checkout-v3'
GROUP BY context_strategy;
```

Write the decision rule before the first replay. Roll back if acceptance falls or reviewer time eats the saving. An unclear result earns more testing. I think the owner should deliver one page with cost, acceptance rate, reviewer burden and the proposed default. Platform can collect the trace, Engineering can define acceptance, and FinOps can carry the result into the budget review.

## Measure cost per accepted result

The checkout patch counts only when its discount test passes and a reviewer accepts the diff.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Cost per accepted result keeps every paid attempt in the numerator. Reuse ratio locates possible context debt, while acceptance and review time show whether removing it improved the work.</p></div>

<div class="keymsg">
<span class="keymsg__label">The unit economics of agentic work</span>
<p class="keymsg__text">Cost per accepted result = billed agent cost across all attempts ÷ accepted tasks.</p>
<p>The rejected checkout patch, its retries and the final approved answer stay in the numerator.</p>
</div>

Suppose the first attempt costs $0.80 and fails its test. The second costs $0.60 and gets approved. The accepted result costs $1.40. Reporting only the final attempt would hide 57 percent of the paid cost.

Before renewal, baseline the three highest-volume agent workflows. Record accepted-result cost beside cache mix and reviewer time, then give each workflow an owner. Ask the supplier which usage fields you can export and which cache or limit terms can change during the contract.

Broad context can be necessary for frontier reasoning or a one-shot synthesis. Hygiene earns its keep in looping, multi-turn work, where stale context returns on every request.

My take: reuse ratio shows where to inspect. Cost per accepted result shows whether smaller context still produced accepted work. I think every failed attempt and reviewer minute belongs beside the cloud bill.

Cheap AI has to tell the truth at the accepted result.
