A July 2026 report from `claude-cost`, a local usage-reporting tool for Claude Code, put a $200 subscription beside $7,470.35 of traffic valued at public application programming interface rates. Claude Code is the terminal coding agent made by AI company Anthropic, and an application programming interface, or API, is the metered interface software uses to send model requests. The ratio was 37.4 to one, large enough to look like a bill.

The comparison appeared in [an X post from developer Om Patel](https://x.com/om_patel5/status/2083401185172541449) on 1 August 2026. The screenshot showed 6,156,261,087 tokens across 36,881 responses. A token is a small unit of text processed by a language model. These figures are evidence of what the local tool reported, not independently audited provider logs.

[Claude Code’s cost guide](https://code.claude.com/docs/en/costs) says the software applies standard list rates to local token counts, so its estimate can differ from the customer charge. The subscriber was not billed $7,470.35. That number is a what-if total at retail API rates, and it cannot reveal Anthropic’s internal compute cost, which the public material does not disclose.

A second report points toward the mechanism that the retail-rate comparison cannot establish by itself. Coding-agent practitioner [Nate B. Jones](https://www.youtube.com/watch?v=Y8vAQ1FgNbM), who sells Ringer, his framework for coordinating multiple agents, said his tracker recorded 3.77 billion tokens across 143 Codex threads in one working day. Codex is the coding agent from OpenAI, a company that researches and deploys AI systems.

Jones’s tracker classified 3.59 billion tokens as reused input, his term for previously supplied material counted again in the workspace. The rounded figures yield 95.2 percent, which he described as “almost 96%.” This is one self-instrumented workspace, not an industry benchmark, and the recording does not provide the raw event schema needed to reproduce a request-by-request delta.

I think the useful shock is the distance between the cash meter and the traffic meter. A flat seat can make an expanding request loop feel free while that loop repeatedly moves old instructions, files, tool results, and conversation back through the model. The engineering response is to manage context as state, observe it at the request boundary, and judge it by results the team accepts and uses.

## The expensive part keeps returning

A language-model API call does not automatically inherit the prior call’s state. The client rebuilds what the model can see. Claude Code’s documentation says it sends the conversation with every request, and a tool use leads to another request containing the returned tool results. Here, that complete payload is the request envelope: current instructions, conversation, tool definitions, selected source material, tool output, and the newest message.

This design makes repetition structural. As a session continues, the envelope grows, while each additional tool step creates another occasion to send it. Old material can therefore cross the boundary many times, even when only the final question is new.

The July report uses two cache categories that need to be separated before reading the amounts. Prompt caching is a provider feature that reuses processing for an unchanged prefix, such as stable instructions at the beginning of a request. Cache creation writes input into a new entry; cache retrieval reads an existing entry again.

Cache retrieval accounted for $3,595.52 of the report’s public-list-price value. Cache creation accounted for another $2,844.72, while generated output was $1,015.97 and ordinary fresh input was $14.14. The two cache-operation rows total $6,440.24, or 86.2 percent of the displayed $7,470.35.

That 86.2 percent describes both cache writes and cache reads, so it cannot be called the share of input reused from an earlier request. Combining the rows reconciles the report’s categories, but a write does not become reused input merely because it created cache state.

The cache-read row supports a narrower arithmetic check. Dividing $3,595.52 by 5.878 billion retrieved tokens gives an implied average rate of about $0.61 per million. In [Anthropic’s public price table](https://docs.anthropic.com/en/docs/about-claude/pricing) available in August 2026, cache hits were listed at $0.50 per million tokens for Opus 5 and $1 per million for Fable 5, two Claude model tiers shown in the report. The combined report-level rate sits inside that range. Because the screenshot does not split cache reads by model, this is a plausibility check rather than a reconstruction of the hidden requests.

Jones’s tracker measures a different category. It labels counts inside his Codex workspace, while the Claude report exposes provider cache events and a retail-rate estimate. Treating the two percentages as interchangeable would turn two useful signals into false precision.

A production account offers another point of comparison. In a July 2025 engineering note, [the team behind Manus, a general-purpose AI agent](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus), reported an average input-to-output ratio around 100 to one. That ratio cannot verify Jones’s 95.2 percent or distinguish a cache write from a cache read. It supports only the narrower point that an agent may process far more text on input than it produces on output.

I think this is why a cheaper model can leave the central problem untouched. Model selection changes the price of processing. Request construction changes how much material enters the process, how often it returns, and whether decisive evidence remains easy to find.

## Give every context item an exit condition

Context hygiene means deciding what enters a model request, why it remains there, and when it leaves. An agent system can use the transcript as both a durable task record and active working state. The first job asks for a reliable history; the second requires selection. Mixing them makes the easiest implementation, “send everything again,” look like the safest one.

My take is to treat admission as a state transition. A candidate item should identify its source, task, purpose, version, exit condition, and approval event before it becomes active context. It should retire from the envelope when its task ends, its evidence is replaced, or its decision is accepted. Retirement removes the item from the next request, not from durable storage.

A compact record is enough to make the rule concrete. This example is synthetic, so its identifiers describe the shape rather than a real migration:

```json
{"id":"ctx-17","task_id":"migration-042","state":"candidate","source_ref":"repo://payments/schema.sql@example-1","purpose":"defines the current uniqueness rule","version":"example-1","exit_condition":"migration_review_closed","approval_event_id":"check-009"}
```

The lifecycle then needs legal and illegal transitions, not a hopeful comment in a prompt. The following Python function permits `candidate` to become `active` or `rejected`, permits `active` to become `retired`, and makes `retired` and `rejected` terminal. It also rejects activation when any admission field is empty.

```python
ALLOWED = {"candidate": {"active", "rejected"}, "active": {"retired"},
           "retired": set(), "rejected": set()}
REQUIRED = ("source_ref", "purpose", "version", "exit_condition", "approval_event_id")

def transition(item, target):
    missing = [key for key in REQUIRED if not item.get(key)]
    if target not in ALLOWED.get(item.get("state"), set()):
        raise ValueError(f"illegal transition: {item.get('state')} -> {target}")
    if target == "active" and missing:
        raise ValueError(f"cannot activate; missing {missing}")
    return {**item, "state": target}
```

This matters because a rejected artifact should not quietly return as active evidence after a retry. Corrected work enters as a new candidate with a new version and approval event. The old record remains available for audit, but the active envelope cannot inherit it by accident.

Consider an agent preparing a database migration that adds a uniqueness rule to stop duplicate payment records. The next decision may require the current schema, the migration policy, the relevant service code, the failing test, and the approved maintenance window. It does not automatically require two rejected index designs, an unrelated dependency log, or every search result that led to the relevant file. If a rejected design exposed a real constraint, carry the constraint and a reference to the full trace rather than the entire debate.

This gives the system two honest records. The durable task log preserves prompts, tool returns, failed attempts, decisions, and source trails for recovery or audit. The active envelope holds the immediate goal, constraints still in force, admitted source material, and the newest working artifact. The archive remains complete while attention stays deliberate.

Automatic compaction helps when a long session approaches a model’s context limit. Claude Code summarizes older conversation so work can continue. Yet a late summary is a recovery mechanism rather than a substitute for application state. The summarizer may preserve a vivid dead end and compress the test that actually defined acceptance unless the client marks those roles explicitly.

When old material remains active by default, I call the carrying cost context debt. It adds traffic to every later request, and it can also make the useful evidence harder to find. [Lost in the Middle](https://arxiv.org/abs/2307.03172), a study first released in 2023 by Nelson Liu and colleagues and later published in the peer-reviewed journal Transactions of the Association for Computational Linguistics, tested how the position of relevant evidence affects long-prompt performance. Its tasks included multi-document question answering and key-value retrieval, where a model had to find a stored value from a supplied key. Models often did better when relevant evidence appeared near the beginning or end and worse when it sat in the middle, including models designed to accept long contexts. The study was not a coding-agent cost experiment, but it shows why available capacity does not guarantee usable attention.

I think the practical rule is purpose rather than a universal token ceiling. A broad investigation may need many sources, while a narrow fix may need one failing test and a small code region. Keep instructions that rarely change and only the required tool definitions at the front, where identical prefixes can benefit from prompt caching. Put changing evidence later, remove duplicates, cap output to what the next step can use, and keep references to retired material so the full record remains retrievable.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Context hygiene separates a complete durable trace from a selective active envelope. Each item needs a source, purpose, version, exit condition, and approval event, enforced through legal transitions so completed or rejected work can leave the request without disappearing from the record.</p></div>

## Put the meter at the request boundary

A context policy becomes enforceable where the application sends a request to the provider. At that boundary, write one telemetry record that begins with identity: task and request identifiers, policy version, provider, provider-schema version, model revision, and metric version. The policy version connects a change in request construction to the outcome that followed.

Group the remaining fields by the decision they support. Traffic includes every input counter, generated tokens, envelope size, retries, and latency. Money includes the actual cash charge and any dated public-list estimate. Outcome includes review minutes and the eventual acceptance event. Contract fields such as data region, retention policy, export method, price-schedule version, and provider notice for schema changes make the same record useful when Procurement asks whether a comparison still means what it meant last month.

The input categories must follow the provider’s documented meanings. Anthropic’s response schema, the structured fields returned with each call, separates ordinary `input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, and `output_tokens`. Calculate cache-read share by dividing `cache_read_input_tokens` by total input, where total input is the sum of the three input fields.

Cache creation belongs in that denominator because those tokens were processed to make a new entry rather than retrieved from an existing one. The numerator contains only input fetched from an existing cache entry. Call the result cache-read share, not universal reuse.

A reproducible meter needs fixtures before it needs a dashboard. The following two JSON Lines records, a text format with one JSON object per line, are synthetic. They exercise the Anthropic field mapping without pretending to be provider evidence:

```json
{"schema_version":"agent-request/v1","task_id":"migration-042","request_id":"req-001","policy_version":"context-v2","provider":"anthropic","model":"example-model-revision","provider_schema_version":"example-v1","price_schedule_version":"example-2026-08-01","data_region":"example-region","retention_policy_id":"retention-example-v1","usage":{"input_tokens":100,"cache_creation_input_tokens":50,"cache_read_input_tokens":150,"output_tokens":20},"actual_cash_cost_usd":null,"latency_ms":1800}
{"schema_version":"agent-request/v1","task_id":"migration-042","request_id":"req-002","policy_version":"context-v2","provider":"anthropic","model":"example-model-revision","provider_schema_version":"example-v1","price_schedule_version":"example-2026-08-01","data_region":"example-region","retention_policy_id":"retention-example-v1","usage":{"input_tokens":50,"cache_creation_input_tokens":0,"cache_read_input_tokens":50,"output_tokens":10},"actual_cash_cost_usd":null,"latency_ms":900}
```

The smallest provider adapter can be a `jq` query, using the command-line tool that reads and transforms JSON. This version names the metric, includes cache creation in total input, and returns `null` for an empty or zero-input file instead of dividing by zero:

```bash
jq -s '
  map(.usage) |
  {
    ordinary:  (map(.input_tokens // 0) | add // 0),
    created:   (map(.cache_creation_input_tokens // 0) | add // 0),
    retrieved: (map(.cache_read_input_tokens // 0) | add // 0)
  } |
  (.ordinary + .created + .retrieved) as $total |
  {
    metric_version: "anthropic-cache-read-share/v1",
    total_input: $total,
    cache_read_share:
      (if $total == 0 then null else .retrieved / $total end)
  }
' requests.jsonl
```

Against the two synthetic records, the query returns 400 total input tokens and a cache-read share of 0.5. Against an empty file, it returns zero and `null`. Those two checks belong beside the adapter in version control. Another provider may expose different fields or no equivalent field, so give each mapping its own provider name, source-schema version, fixtures, tests, and metric version. If a field changes meaning, publish a new metric version rather than silently rewriting history.

The same record must keep traffic separate from money. Cache-read share describes the composition of input tokens. Actual cash cost comes from the contracted bill or a subscription allocation chosen before the analysis. Public-list-price value applies a dated retail schedule to the traffic as a comparison. A high cache-read share can coexist with low spend because retrieval is discounted, and repeated policy or source material can be essential rather than wasteful.

The July report makes the boundary concrete: $200 belongs in the cash view, $7,470.35 in the public-list-price view, and the cache fields in the traffic view. Moving one number into another category produces a dramatic dashboard and a bad decision.

I think the useful alert is a change against a task-class baseline, not a universal red line. A task class is a group of jobs evaluated with the same acceptance rules. A repository-wide migration and a one-file correction have different context needs, so compare each class with its own recent distribution and inspect changes in retrieved share, envelope size, latency, retries, and review time together.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Instrument every request with a versioned, provider-specific record and test the adapter with synthetic fixtures, including an empty-input case. Cache-read share describes traffic, a contracted bill or predeclared subscription allocation describes cash, and a dated public price schedule describes exposure; none can stand in for the others.</p></div>

## Let accepted work settle the price

Token totals are operational signals, but they are a poor final denominator. Define the acceptance event before the meter starts, and keep replay evidence separate from live production evidence. In a closed-task replay, an accepted result is a candidate that passes every required automated check and receives a blinded reviewer’s `approved_for_merge` event within seven days of its first model request. In live reporting, acceptance means that the approved commit reaches the default branch inside the same window.

Store `acceptance_event_type`, `accepted_at`, `artifact_ref`, review minutes, and failed-check identifiers with the task result so the two denominators never blend. A patch with failing tests, a reviewer rejection, an abandoned retry, or a candidate that misses the window remains a cost without becoming an accepted result.

The metric is full cost per accepted result. Add actual model charges, or a predeclared share of a flat subscription, to loaded review cost and relevant platform expense, then divide by accepted outputs. Loaded review cost values reviewer minutes at a fully burdened labor rate that includes compensation and employer costs. Platform expense includes the proxy, evaluation runner, storage, and other infrastructure used by the measured workflow. Keep the $7,470.35 public-list estimate outside this calculation because it was never charged to the plan.

For a flat seat, choose the allocation rule before seeing the outcome. One defensible option is to allocate the monthly subscription by task-attributed agent-active minutes, using the same clock for both policies. The method will shape the reported cost, so freeze it before the run and apply it to every attempt.

A decision-grade replay can still be small, but it cannot be vague. The following pilot is a proposed starting point, not a universal sample-size rule:

<div class="keymsg">
<span class="keymsg__label">A bounded context-policy replay</span>
<p class="keymsg__text"><strong>Cohort:</strong> 12 representative closed tasks, with four narrow fixes, four migrations, and four investigations. Run the current and proposed policy three times each on every task: 72 isolated runs.</p>
<p><strong>Owner and review:</strong> The platform lead owns the run, Finance freezes the cost-allocation rule, and assigned engineering reviewers decide acceptance. Review integrity after each task class and make one final go-or-stop decision.</p>
<p><strong>Controls:</strong> Hold the model snapshot, tools, retry limit, checks, source revision, and reviewer rubric constant. Randomize run order and hide the policy label from reviewers where possible.</p>
<p><strong>Window and budget:</strong> Two calendar weeks, a seven-day acceptance window per task, and 12 reviewer-hours reserved before the replay begins.</p>
<p><strong>Go or stop:</strong> Adopt only if the 95 percent confidence interval for proposed-minus-current outcome cost lies below zero, the replay approval rate falls by no more than five percentage points, median review time rises by no more than 10 percent, and no critical correctness or security failure appears. An exhausted review budget makes the result inconclusive.</p>
<p><strong>Rollback:</strong> Restore the previous policy version at the request boundary. Keep both policies, raw request records, outcomes, and rejected attempts in the durable log.</p>
</div>

Repeating each condition helps expose model variance, the run-to-run differences that remain even when the prompt and model stay fixed. A paired bootstrap confidence interval estimates uncertainty by repeatedly resampling the 12 matched tasks with replacement. For each resample, sum all costs and accepted candidates under each policy, calculate the two outcome costs, and record proposed minus current.

The middle 95 percent of those differences is the interval. With only 12 tasks, it may be wide. Report it anyway. If it includes zero, the honest result is inconclusive.

The attribution window starts with the first request for a task and closes at acceptance or after seven days. Every retry, rejected candidate, review minute, and platform event inside that window stays in the numerator. A policy with no accepted candidate across the full cohort has no finite outcome cost and fails the pilot. If a bootstrap resample has no accepted candidate, record its cost as unbounded rather than dropping the resample. The analysis must not hide failure behind a division error.

I don’t know which policy will win for a given task class. That is the point of the replay. Fewer tokens are a loss when they create more retries, slower reviews, or lower acceptance. More context is justified when it improves the result enough to pay for itself. For one-shot work where a broad body of evidence is the task, aggressive removal may offer little or cause harm.

The sources behind the $7,470.35 and 95.2 percent headlines do not include a public enterprise replay, and Jones’s raw event schema is unavailable. They should not enter a portfolio forecast as if they did. A team can produce stronger evidence by freezing a small package with the cohort manifest, policy files, model and tool versions, raw request records, adapter fixtures and tests, acceptance events, reviewer rubric, cost-allocation rule, and analysis code. Publish it internally, or publicly when the source material permits, so another engineer can reproduce the denominator before debating the result.

I think ownership belongs with the platform team that controls the agent boundary and can join requests to outcomes. Finance supplies the loaded labor rate and validates the subscription allocation. Procurement records retention, regional handling, export rights, price-schedule changes, and provider-schema notice terms. Review the evidence package monthly, but change policy only when a new version passes the same replay.

The $200 plan muted the cash signal, and the $7,470.35 public-list meter made hidden traffic visible. Jones’s 95.2 percent count across 143 Codex threads in one working day gives engineers a reason to inspect their own loops, not a percentage to copy into a forecast. I think the real control point is the request boundary, where context either earns admission or becomes another cost carried forward. Context earns its place only when it helps create work the organization accepts.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Define acceptance as a dated, typed event, keep every failed attempt in the numerator, and divide actual model or allocated subscription cost, loaded review cost, and platform expense by accepted work. Test context policy with a bounded, reversible replay and report uncertainty. The winning policy is the one that lowers full outcome cost without crossing the declared quality limits.</p></div>
