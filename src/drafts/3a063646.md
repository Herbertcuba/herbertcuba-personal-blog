On August 1, 2026, Om Patel posted a screenshot on the social platform X that looked like an impossible bill. A community command-line dashboard called [`claude-cost`](https://www.npmjs.com/package/claude-cost) had counted his July use of Claude Code, Anthropic's terminal-based coding agent: 36,881 responses, 6,156,261,087 tokens, and $7,470.35 at public API list prices. Patel had paid $200 for a Claude Max subscription.

The ratio is 37.4 to one. The two dollar figures still measure different things. Patel's cash charge was the flat subscription fee, while the larger number estimated what the same token traffic would have cost through Anthropic's application programming interface, or API, where software calls the model at published per-token rates. A token is a small unit of text processed by the model. Anthropic's own [Claude Code cost guide](https://code.claude.com/docs/en/costs) warns that a local list-price estimate can differ from the actual charge, and included subscription use is not billed as API traffic.

That boundary makes the screenshot more useful, not less. It turns the dramatic number into a map of the agent loop. Only a small part of the traffic was the answer being generated; most of the estimated value came from storing or retrieving matching request prefixes so they could be reused as the work continued.

I think the real story begins there. A flat plan can hide an architecture that repeatedly moves enormous amounts of old text, and a cheaper invoice does not make that movement free of latency, quality risk, or future pricing exposure. The engineering response begins with the context lifecycle: rules for what enters, remains in, and leaves each request. From there, the team can observe the request that actually leaves the application and judge the system by the cost of work that survives tests and review.

## The receipt is a traffic map

Prompt caching is a provider feature that saves a matching beginning of a request so it can be reused. Cache creation writes that reusable prefix; cache retrieval reads it on a later request. In Patel's [original post and screenshot](https://x.com/om_patel5/status/2083401185172541449), retrieval accounted for 5.88 billion tokens and $3,595.52. Two kinds of cache creation added $2,844.72, output cost $1,015.97, and ordinary fresh input cost $14.14. Together, the cache line items contributed $6,440.24, or 86.2% of the $7,470.35 estimate.

Anthropic's [API pricing](https://platform.claude.com/docs/en/about-claude/pricing) charges a cache retrieval at one tenth of ordinary input, although the exact rate depends on the model family. The screenshot mixed Anthropic's Opus and Fable 5 API model families, whose listed cache-read rates were $0.50 and $1 per million tokens. Its blended rate works out to about $0.61 per million, exactly where a mixed workload should land between those two tiers.

That arithmetic makes the screenshot internally plausible while leaving two questions unanswered: Anthropic's serving cost and how much context could be removed safely. Cached repository instructions may be essential, and a repeated tool definition can be cheaper to retrieve than to rebuild. The line items show where traffic and public-list-price exposure accumulated; deciding what was useful requires task-level evidence.

I think the word *waste* gets ahead of that evidence. The stronger conclusion is that context had become the dominant resource in this one workload, while the subscription kept its cost shape out of view. Once a team sees the receipt as a traffic map, the next question becomes precise: why does so much already-seen material keep returning?

<p>Cache creation and retrieval produced 86.2% of this public-list-price estimate, but cache activity is a location signal rather than a waste verdict. It tells engineers where to inspect the request, then task outcomes must determine what can safely leave.</p>

## The 96% clue is about repetition

In a July 29, 2026 video, AI practitioner [Nate B. Jones](https://www.youtube.com/watch?v=Y8vAQ1FgNbM) reported telemetry from one working day in his OpenAI Codex workspace, a coding-agent environment. His tracker counted 3.77 billion tokens across 143 threads and classified 3.59 billion as *reused input*, his term for the part of a request the model had already seen. The rounded figures produce 95.2%.

That is Jones's tracker category, based on one self-instrumented workspace and one day; it is not an industry benchmark. It is also different from Anthropic's cache-read billing field. Reused input describes repetition at the request level, while a provider reports cache retrieval only when that repeated material qualifies for and hits its cache. Mixing the two categories would make the 96% headline sound more universal than the evidence allows.

The repetition follows from how Claude Code constructs requests. Anthropic says the tool sends the full conversation with every request, then sends another request carrying tool results after the model uses tools. Each turn can therefore include stable instructions, tool descriptions, repository files, prior conversation, earlier tool output, and the latest user message. As the thread grows, the newest instruction can become a thin layer on top of a large body of old text.

Other evidence points in the same direction without turning 95.2% into a law. In a July 2025 engineering note, the team behind [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus), an AI-agent product, reported an average input-to-output ratio of about 100 to one in its production loop. Patel's screenshot shows a total-token-to-output ratio of about 186 to one. These are different systems and measurements, but all three expose the same structural pressure: an agent often reads far more than it writes.

That pressure affects more than a price estimate. [*Lost in the Middle*](https://arxiv.org/abs/2307.03172), a study led by computer scientist Nelson F. Liu and first released in 2023, tested long-context retrieval and question answering. The work was [published](https://doi.org/10.1162/tacl_a_00638) in the peer-reviewed journal *Transactions of the Association for Computational Linguistics* in 2024 and found that models often performed worse when relevant information sat in the middle of a long input. It was not a coding-agent cost experiment, so it cannot tell us how much context to remove from a repository task. It does show why a larger context window should not be confused with reliable use of every item inside it.

Anthropic made the same resource constraint explicit in a [2025 engineering article](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents): “Context is a critical but finite resource for AI agents.” I don't know how much of Jones's 95.2% or Patel's cache activity could disappear without damaging their results, because neither observation includes that counterfactual. I think the exact percentage is the provocation; the durable finding is that context needs ownership before repetition becomes the default.

<span class="chapter-tldr__label">In short</span>
<p>One instrumented Codex workspace classified 95.2% of a day's tokens as input the model had already seen. That scoped result aligns with other agent workloads and documented full-conversation replay, but it is a reason to test context policy, not a universal removal target.</p>
</div>

## Give context an exit condition

Context hygiene is the policy for deciding what enters a model request, what remains active, and what leaves. The final collection sent on a turn is the context envelope. Without an exit condition, every useful discovery competes for permanent residence: a file opened during diagnosis, an obsolete plan, raw test output, an earlier correction, or a tool result whose job is already finished.

A lifecycle turns that accumulation into an enforceable system. A candidate item needs a source, a current task, a reason for admission, an owner, and an expiry condition before it becomes active. Rejection and retirement should remain visible in logs, while their full contents stay outside the live request. If a later task needs the same source, the system creates a new candidate tied to that task instead of reviving the terminal item. It permits `candidate → active`, `candidate → rejected`, and `active → retired`; terminal states cannot return to the envelope, and activation fails when an admission field is empty.

The distinction matters because retirement is not deletion. Suppose an agent explores several files, runs tests, and reaches an accepted implementation plan. The durable artifact is the plan with links to the relevant files and test evidence. The exploratory transcript, duplicate file dumps, and superseded guesses have completed their purpose. Carrying the artifact forward preserves the decision; carrying every step forward forces the model to reconstruct which parts still matter.

This policy should act at a few concrete points. Clear the thread when work moves to an unrelated task, a practice Anthropic's cost guide also recommends. Put limits on tool output before a search result or build log enters the envelope, and retain a pointer to the full artifact outside the prompt. Keep stable instructions and tool definitions at the beginning of the request, then place changing task material after them. Manus's engineering team recommends a stable prompt prefix and treats cache hit rate, the share of eligible prefixes successfully retrieved from cache, as a production metric.

Those practices can pull in different directions. Removing stale text may reduce volume, while frequently changing the beginning of the prompt can destroy cache eligibility and raise the price of what remains. A good policy therefore watches both admitted context and provider cache fields. Smaller is not automatically cheaper, and a high cache-hit rate does not prove that the cached material helps the task.

Claude Code already uses automatic compaction, which summarizes conversation history as its context window approaches capacity. That is a useful safety valve. It acts after the thread has grown, however, and its summary is not governed by the team's definition of an accepted result. I think compaction belongs behind an explicit lifecycle: the harness can compress what remains, while the application decides what deserved to remain in the first place.

My take is that context debt behaves like any other unmanaged state. It feels cheap while one thread works, then appears as slower requests, harder debugging, uncertain cache behavior, and results that cannot be traced back to the evidence that shaped them. An exit condition makes that state testable.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Admit context with a source, purpose, owner, and expiry condition; retire completed material while preserving its durable artifact outside the live request. Automatic compaction can support that lifecycle, but it should not be the policy that decides relevance.</p>
</div>

An agent can receive authentic test output, a real requirement, or a correct design note and still be misled if that material belongs to an earlier state of the work. A context lifecycle supplies the missing provenance by asking where each memory came from, why it is active now, and when it must leave.

## Put the meter at the request boundary

The lifecycle needs evidence from the request itself. The request boundary is the last point inside an application before the final payload goes to a model provider. Measuring there captures the request the model was actually asked to process, after the agent has assembled instructions, tools, conversation, retrieved files, and tool results.

Each attempt needs a trace identifier linking that outbound request to one task and one eventual result. Preserve the provider's raw usage fields before translating them into a common schema. For Anthropic, the [Messages API response](https://platform.claude.com/docs/en/api/beta/messages/create) distinguishes ordinary input, cache-creation input, cache-read input, and output. Record the model, latency, retries, context-item identifiers and states, the public-list-price estimate, and the cash charge when one exists.

Keep four accounting views separate. Actual cash cost comes from metered API charges and invoices. A flat subscription allocation is an internal rule chosen in advance, such as assigning the monthly fee by active seat-day or completed task. Public-list-price exposure is the counterfactual meter used in Patel's screenshot. Token volume describes traffic. Combining those views into one number would turn a useful dashboard into false precision.

I think the boundary is also the right place to test lifecycle changes. Run the same class of task with the same model and acceptance rule, then compare total input, cache creation, cache retrieval, output, latency, retries, and reviewer outcome. If a leaner envelope lowers tokens but causes more failed attempts, the saving may be imaginary. If a stable prefix raises cache retrieval while acceptance stays level, the system has improved even when raw repeated-token volume remains high.

The instrument should preserve provider detail first and normalize second. The difference between Anthropic's cache-read field and Jones's reused-input category already shows how a friendly common label can erase an important boundary. Engineers need the original evidence when a bill, regression, or cache miss has to be explained.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Measure the final outbound request, retain provider-specific usage fields, and link every attempt to a task and result. Cash cost, flat-plan allocation, public-list-price exposure, and token volume answer different questions and should remain separate.</p>
</div>

## Price the result that survives review

Traffic metrics become useful when they meet an acceptance rule. An accepted result is an output that satisfies criteria declared before the run. For a coding change, that might mean the required tests pass, the change survives human review, and no related rollback or repair appears during a defined attribution window, the period in which follow-up work is charged to the original attempt.

The numerator should include every attempt that led to that outcome: metered model charges or the predeclared subscription allocation, relevant platform cost, and reviewer time valued at the organization's loaded rate, which includes pay and overhead. The denominator is the number of accepted results. Public-list-price exposure can remain beside this calculation as a risk signal, but adding it to cash cost would count a counterfactual as money spent.

`cost per accepted result = total attributable cash and reviewer cost across all attempts / accepted results`

This metric changes the engineering conversation. Seat price rewards a team for fitting work under a flat plan, even when requests swell and reviewers repair weak output. Output-token price rewards a model for speaking cheaply, even when it has reread a huge context or needed several retries. Cost per accepted result makes those failures visible because the unsuccessful attempts stay in the numerator.

The metric also gives context hygiene a fair trial. Choose one repeatable task class, define acceptance and the attribution window, record a baseline, then change one context rule at a time. A policy earns adoption when accepted-result cost falls without an unacceptable loss in quality, latency, or cache efficiency. For one-shot work or frontier reasoning where broad source material is the point, pruning may buy little and can remove evidence the model needs. The evidence in these cases does not prove that context hygiene always beats a model change, so the comparison belongs in an evaluation rather than a slogan.

Anthropic's [subscription terms](https://claude.com/pricing) reinforce why the internal metric matters. The plans use rolling five-hour windows, add weekly limits, and allow other discretionary caps, so a flat price does not promise permanent capacity at today's traffic level. A team that understands only the seat fee inherits the vendor's pricing decision. A team that understands accepted-result cost can compare a subscription, an API deployment, a different model, or a different context policy on the same unit of useful work.

I think that is the strategic shift hidden inside Patel's screenshot. The $7,470.35 meter draws attention, and the 95.2% observation explains why the meter can grow so quickly. Neither number tells a team what to cut. The result becomes governable only when context has an owner, every request has a trace, and acceptance has a price.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Define acceptance before the run, charge every attempt to the same outcome, and compare context policies on cash, quality, latency, cache efficiency, and reviewer effort. The vendor can change the seat price; engineering must own the cost of accepted work.</p>
</div>
