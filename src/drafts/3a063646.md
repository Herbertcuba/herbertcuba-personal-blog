On 1 August 2026, [Om Patel shared a screenshot](https://x.com/om_patel5/status/2083401185172541449) from `claude-cost`, a usage-reporting tool for Claude Code, Anthropic’s terminal coding agent. The image covered July 2026 and displayed 6,156,261,087 tokens across 36,881 responses. A token is a piece of text processed by a model, and the report assigned those tokens a value of $7,470.35 at public application programming interface, or API, prices. Patel’s post paired that number with a $200 subscription payment.

The division is startling: $7,470.35 is 37.4 times $200. It is also easy to misuse. The screenshot says the subscription user would not be charged the API total, and [Claude Code’s cost documentation](https://code.claude.com/docs/en/costs) says its dollar figure is calculated locally from token counts at standard list rates. The image is evidence of what the tool displayed, not an audited request log, an invoice, or a view into Anthropic’s undisclosed serving cost.

A second report makes the traffic more interesting than the price shock. In a [video about coding-agent context](https://www.youtube.com/watch?v=Y8vAQ1FgNbM), practitioner Nate B. Jones said his tracker recorded 3.77 billion tokens across 143 Codex threads in one working day. Codex is OpenAI’s coding agent. Jones classified 3.59 billion of those tokens as reused input, meaning text already supplied and included again in later model calls. That is 95.2 percent using his rounded totals, which he described as “almost 96%.”

Neither case establishes an industry average. One is a social post with a screenshot; the other is a self-instrumented day without a public raw-data package. I think their value lies elsewhere: they expose a system boundary that flat access makes easy to ignore. A coding agent does not merely generate an answer. It repeatedly assembles, sends, and pays attention to a body of context, and that body should be engineered as deliberately as the tools the agent is allowed to call.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The 37.4-times figure is a public-price shadow estimate, while the 95.2 percent figure belongs to one person’s instrumented day. Together they raise a testable engineering question: which parts of each model request earned the right to be sent again?</p></div>

## A shadow price is useful only when it stays a shadow

The $7,470.35 figure belongs in a different ledger from the $200 payment. The payment is cash. The larger number is API list-price value, a counterfactual estimate of what the displayed traffic would cost if each token were billed directly at the public rates used by the reporting tool. I think teams should keep both, because actual cost tells Finance what left the account while shadow value reveals the traffic that a flat plan, negotiated discount, or temporary promotion can hide.

The category rows explain why the distinction matters. The screenshot shows $3,595.52 for cache reads, $2,841.89 for one-hour cache writes, $2.83 for five-minute cache writes, $14.14 for fresh input, and $1,015.97 for output. Those five dollar lines add to the reported total. The three cache rows add to $6,440.24, or 86.2 percent of the list-price estimate, but that does not mean 86.2 percent was retrieved text.

Prompt caching is a provider feature that saves work on a repeated prefix, such as stable instructions or an earlier conversation. Under [Anthropic’s prompt-caching semantics](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), cache creation records tokens when a new entry is written; cache retrieval records tokens fetched from an existing entry. A retrieval also refreshes the entry’s lifetime at no extra refresh charge. The screenshot’s $2,844.72 of cache creation therefore cannot be silently relabeled as retrieved input.

The cache-read row does provide a useful internal check. Its $3,595.52 spread across 5,878,394,153 tokens implies about $0.61 per million tokens. That sits between the [published cache-hit prices](https://platform.claude.com/docs/en/about-claude/pricing) for the Claude Opus and Claude Fable model families shown in the report, $0.50 and $1 per million respectively. This makes the screenshot internally consistent with the price table; it does not independently prove the unseen request mix or the underlying usage.

This is the first discipline: keep actual cash, list-price exposure, and technical traffic separate. A flat plan can suppress the first signal without changing the second, while a cache discount can lower the price of repeated context without proving that the repeated context was useful. Once those ledgers are mixed, an optimization can look successful simply because the provider priced the same waste more cheaply.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Actual payment, public-price exposure, and token traffic answer different questions. Cache activity dominated the screenshot’s list-price value, but only cache reads represent retrieval, and even a cheap retrieval says nothing about whether the text helped the task.</p></div>

## The agent is packing a new request every turn

The repeated traffic is not mysterious once the request path is visible. [Claude Code’s documentation](https://code.claude.com/docs/en/costs#why-usage-climbs-in-a-long-session) says the tool sends the full conversation with every request, and each tool call causes another request carrying that batch of tool results. I will call the complete payload assembled for one model call the request envelope: instructions, conversation, tool definitions, retrieved files, tool output, and the latest user message.

That envelope grows because the model call does not inherit human memory from the previous call. The client rebuilds the relevant state in text. Caching can make a repeated prefix cheaper and faster to process, but it does not decide whether an old stack trace, superseded requirement, duplicate source file, or failed patch still belongs in the envelope. The provider can reuse computation while the application keeps resending a bad packing list.

Jones’s one-day figure is a sharp example of that mechanism, not a benchmark for everyone else. His 3.59 billion reused-input tokens divided by 3.77 billion total tokens produce the 95.2 percent share. I don’t know how representative that workload is, because the video does not publish the raw event records, collector, model versions, or classification rules needed for an independent reproduction. The responsible move is to treat 95.2 percent as a local hypothesis and instrument your own request path.

A production account points in the same direction without validating the same percentage. In July 2025, [the team behind Manus, a general-purpose AI agent, reported](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus) an average input-to-output token ratio of roughly 100 to 1 in its system. That ratio describes how much text went in for each token generated; it does not separate retrieved input from newly created cache entries. It does show that agent traffic can be dominated by reading rather than writing.

More reading is not automatically more understanding. [Lost in the Middle](https://arxiv.org/abs/2307.03172), a 2023 study of how language models use long inputs, found that performance was often strongest when relevant information appeared near the beginning or end and fell when the same information sat in the middle, including for models designed for long context. The experiment was not a coding-agent cost benchmark, but it establishes the quality risk behind the accounting problem: position and length can make relevant evidence harder for a model to use.

I think this changes the architecture question. The model’s context window is capacity, not a requirement to fill it. Every additional item in the request envelope should have a reason to be present now, for this task, under this policy. Without that reason, calling the repeated input memory disguises an unreviewed deployment decision made again on every turn.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>An agent client reconstructs state for each model call, so long sessions repeatedly carry conversation and tool output. Caching reduces the cost of matching prefixes, but only an application-level policy can decide whether the carried material remains relevant, current, and safe to use.</p></div>

## Compile context instead of replaying conversation

Context hygiene is the practice of selecting, updating, and expiring the material placed in a model request. It starts by separating storage from attention. The full transcript, raw tool output, and failed attempts can remain in an append-only task record for audit and recovery, while the request envelope carries only the material needed to make the next decision.

My take is that an agent runtime needs a context compiler: a component that turns stored task state into the exact request sent to the model. Its output should have four layers. A stable layer contains the current system policy and only the tool definitions available to this task. An active layer contains the latest requirement and acceptance checks. An evidence layer contains approved artifacts such as a passing test, a current interface contract, or a source excerpt. A small working layer contains the latest observation and the immediate next action.

The dynamic items in those layers need a context manifest, which is a machine-readable packing list. At minimum, each entry should record an artifact identifier, task identifier, source location, content hash, approval reference, expiry rule, and any artifact it replaces. A schema alone is documentation. The runtime must enforce the admission rule before serialization, reject an item with no valid approval or expired evidence, and log both the policy version and the reason for exclusion.

```text
pack(item, task, now) only if:
  item.task_id matches task.id
  item.approval_ref verifies the current artifact hash
  item.expires_at is later than now
  item.superseded_by is empty
```

This is deliberately stricter than automatic conversation compaction, which summarizes older history when a session approaches its context limit. Compaction is useful because it keeps the session running, but it delegates the forgetting decision to a general summary produced late in the process. A context compiler acts before every request and can preserve exact accepted evidence while excluding bulky discussion that produced it.

Consider an agent updating an OAuth callback after a library upgrade. The next request may need the active requirement, the failing regression test, the new library interface, and the current diff. It does not need three complete dependency searches, two rejected patches, or every line of installation output. If one rejected patch revealed that a callback must remain idempotent, carry that constraint as a short evidence item linked to the full failed attempt rather than replaying the entire attempt as conversation.

The same policy helps caching rather than fighting it. Put stable instructions first, keep volatile observations near the end, load large tool definitions only when their tools are available, and deduplicate artifacts by content hash. The stable prefix then has a better chance of producing cache reads, while the changing suffix remains small enough to review. I think expiry is the decisive part: a requirement that has been replaced and an artifact from a closed task should stop entering requests even if both remain perfectly cacheable.

Scope the first implementation to one platform engineer, one sprint, one provider, and one task class, using existing response fields, task records, and review events. This boundary does not require a redesign of the whole agent platform. Its first deliverable should be a request trace showing what was eligible, what was packed, what was excluded, and why.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Store the full trace outside the prompt, then compile each request from stable policy, active requirements, approved evidence, and the latest working delta. A manifest with provenance, approval, replacement, and expiry fields turns context from accumulated conversation into an enforceable input policy.</p></div>

## Let accepted work set the price

A context policy needs telemetry that respects the provider’s billing semantics. Anthropic exposes `input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, and `output_tokens` as separate usage fields. For that provider, retrieved-input share can be calculated as cache-read tokens divided by the sum of ordinary input, cache creation, and cache reads. Cache creation belongs in the denominator because it is input processed to create a new entry; it stays out of the numerator because no existing entry was retrieved.

Keep that formula provider-specific. If a supplier renames a field, changes what an event means, or moves retrieval into a managed-session product, the adapter and the historical series need a version boundary. Each request record should therefore include provider, model version, usage fields, actual charge, dated price schedule, task identifier, context-policy version, latency, review time, and acceptance event. Public API-list value can sit beside actual charge as exposure, never inside the actual-cost numerator.

Now define the result. An accepted result is an agent output that passes the predeclared automated checks and human review for its task class and then enters use. A plausible answer, a patch that fails tests, and a retry abandoned by the reviewer are attempts, not accepted results. Loaded review cost is reviewer time multiplied by the organization’s fully loaded labor rate, including compensation and employer costs rather than salary alone.

The operating metric is then straightforward:

```text
cost per accepted result =
  (actual model cost + loaded review cost + allocated platform cost)
  / accepted results
```

For a flat subscription, document how the subscription fee is allocated across the measured task class. For a metered enterprise account, use the actual contracted charge. In both cases, keep the $7,470.35 shadow estimate out of the numerator because no one paid it. Its job is to show how exposed the workload would be to another price surface, not to manufacture savings.

The policy should earn adoption in a paired replay. Select completed tasks that represent the intended workload, then run each task once with the current context behavior and once with the compiled policy. Hold the model version, tool permissions, retry cap, acceptance checks, and reviewer instructions constant. Reviewers should not know which policy produced an output, and the team should declare in advance how much quality loss, reviewer-time increase, or latency increase would block adoption.

Report the task-by-task differences and an uncertainty interval rather than one blended percentage. A confidence interval is a range calculated from the sample to show the uncertainty around the estimated change. If the sample is too small to distinguish a useful reduction from noise, the result is “measure more,” not “ship because tokens fell.” I think a context policy has failed when it wins the token chart but sends more work back through review.

This meter also gives Procurement and Finance something concrete to govern. The platform owner reviews actual spend, shadow exposure, context composition, acceptance, and reviewer time each month; Finance supplies the loaded labor rate; Procurement tracks cache terms, data location, retention, and usage-field changes. A task class remains a pilot until it holds its acceptance guardrail and cost-per-accepted-result limit for a full review period under a named owner.

Provider pricing will not stand still. My falsifiable prediction is that before the end of 2027, at least one major model provider will introduce a distinct enterprise charge or quota for managed agent memory, retained context, or its retrieval. That would price what the system remembers, not only what the model generates, and it would reward teams that can distinguish approved state from transcript residue.

The $200 plan makes this a good time to build the discipline because the cash penalty is muted. It does not make the discipline optional. I think the only durable meter is the one that joins architecture, provider cost, human review, and accepted work in the same line of sight.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Measure provider events without merging cache creation into retrieval, and test context policy on paired tasks with fixed quality guardrails. Judge the system by actual model, review, and platform cost per accepted result. Every carried token must answer to work that survives review.</p></div>
