A July 2026 activity report puts a $200 flat payment beside 6,156,261,087 tokens from Claude Code, a terminal-based coding agent made by Anthropic, the AI company behind Claude. A token is a small piece of text that an AI model reads or writes. The report then values the same traffic at $7,470.35 under Anthropic's public application programming interface, or API, rates, the per-token prices charged when software calls its models directly.

[Om Patel, the author who shared the report](https://x.com/om_patel5/status/2083401185172541449), posted it on 1 August 2026 to X, the social network formerly called Twitter. The image showed 36,881 responses and stated that a subscription user would not be charged its API total. The $7,470.35 therefore reflects a different buying arrangement.

The multiplication is still startling. The public-price value is 37.4 times the $200 payment, although the screenshot does not identify the subscriber or establish Anthropic's serving cost. What it exposes with confidence is traffic that carried no marginal price for the user.

A second signal gives that traffic a shape. [AI practitioner Nate B. Jones reported](https://www.youtube.com/watch?v=Y8vAQ1FgNbM) that his tracker counted 3.77 billion tokens in 143 OpenAI Codex threads during one working day. Codex is a coding agent made by the AI company OpenAI. Jones labeled 3.59 billion of those tokens as reused input, meaning already-sent text carried into another call. Dividing those rounded figures gives 95.2 percent.

That measurement belongs to one person, one workspace, and one day. I think its importance lies in the question it forces on every team running an agent loop: when old material enters a new request, what has it done to earn another turn? The answer should begin with the result the system is meant to produce, then work backward through context, telemetry, and price.

## Start with the result that must survive

Call an output an accepted result only after it clears the declared automated checks, receives every required human approval, and enters use. A patch that looks plausible but fails review is an attempt. It consumed resources, but it did not create an accepted result.

That distinction gives the system an economic denominator:

```text
cost per accepted result =
    actual provider or allocated plan cost
    + loaded review cost
    + material task overhead
    ------------------------------------------------
    accepted results
```

Allocated plan cost is the share of a flat subscription assigned to a task under one consistent rule. Loaded review cost is review time multiplied by an hourly rate that includes salary, benefits, and any other employment costs Finance chooses to count. Material overhead can include tracing, storage, or paid tools when those costs could change the decision.

Every attempt belongs in the numerator because failed output still uses model traffic and human attention. Only checked work that enters use belongs in the denominator. This prevents a cheaper request from looking successful when it produces more retries, longer reviews, or defects that someone must repair later.

Context hygiene is the practice of deciding what a model may see and how long each item remains eligible for another request. It can affect both sides of the formula. Smaller request payloads may lower provider cost, while clearer evidence may improve acceptance and reduce review. Removing necessary evidence can reverse both gains, which is why token reduction alone cannot be the target.

I think the order matters. Define acceptance and the costs that count before examining a dramatic token report. Otherwise the dashboard will reward whatever is easiest to count, even when the work that survives becomes more expensive.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Define the accepted result before optimizing the model call. Put every attempt's actual or allocated provider cost, human review, and material overhead in the numerator, then divide by outputs that passed checks and entered use. Token reduction is useful only when this full cost falls without weakening acceptance.</p></div>

## Read $7,470.35 as a shadow price

The July figure is a shadow price, a dated calculation of what recorded traffic would cost under a public rate card rather than the user's actual contract. Its value depends on reading the report's billing events correctly.

[Anthropic's prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) stores a matching beginning of a request so the provider can process it faster and at a lower price later. Cache creation writes that material into a new entry for a set period. Cache retrieval, also called a cache read, uses the stored match on a later call and refreshes its lifetime at no extra charge.

| Reported event | Public API value | What the event records |
| --- | ---: | --- |
| Cache read | $3,595.52 | Matching input was retrieved from an existing entry |
| One-hour cache creation | $2,841.89 | Input was written to a one-hour cache entry |
| Five-minute cache creation | $2.83 | Input was written to a five-minute cache entry |
| Fresh input | $14.14 | Input was processed outside those cache events |
| Output | $1,015.97 | The models generated new text |

The three cache rows total $6,440.24, or 86.2 percent of the report's $7,470.35 value. That is a cache-activity share, not a retrieved-input share, because $2,844.72 came from creating entries. Combining writes with reads would make the reuse story larger by changing the meaning of the measurement.

The cache-read row is internally consistent with Anthropic's published range. It assigns $3,595.52 to 5,878,394,153 cache-read tokens, an implied rate of about $0.61 per million. [Anthropic's August 2026 pricing table](https://docs.anthropic.com/en/docs/about-claude/pricing) listed one million cache-hit tokens at $0.50 for Claude Opus and $1 for Claude Fable 5, two model tiers present in the report. The implied blend sits between them, but it cannot independently verify the requests behind the screenshot.

[Anthropic's plan page](https://claude.com/pricing) also describes rolling five-hour usage windows and extra weekly limits, so flat access remains bounded. I don't know Anthropic's cost of serving this user's month, and API retail prices cannot reveal it. The defensible conclusion is smaller and more useful: a flat payment muted the user's price signal while billions of tokens continued to move.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The report's rows reconcile to a credible public-price shadow calculation, but they do not reveal an invoice or Anthropic's serving cost. Cache creation and retrieval are different events, so 86.2 percent describes cache-related value rather than the share of input retrieved from storage.</p></div>

## The client keeps rebuilding the past

[Anthropic's Messages API documentation](https://docs.anthropic.com/en/api/messages-examples) calls the interface stateless, which means the client sends the conversational history again with every request. A context window is the maximum material a model can receive at once. A request envelope is the payload assembled for one call: instructions, tool definitions, source excerpts, previous messages, tool results, and the new question.

Imagine an agent upgrading a database client after an interface change. Its first envelope may need one migration note, a failing test, and the affected module. After twenty turns, the client may also be carrying an obsolete patch, repeated test output, broad search results, and explanations written before the engineer corrected the requirement. The new question can be tiny while the surrounding envelope contains the whole investigation.

Prompt caching can discount a stable prefix, but it cannot decide whether an old patch still deserves influence. The provider recognizes repeated content. The client constructing the envelope owns the harder judgment: whether that content remains current, relevant, and approved.

Jones's 95.2 percent observation gives the mechanism a memorable scale without establishing an industry rate. A separate production account points in the same direction. In July 2025, the team behind [Manus, a general-purpose AI agent, reported](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus) an average input-to-output ratio near 100 to 1. That means the system read roughly one hundred tokens for every token it produced; it does not confirm Jones's exact percentage.

Long inputs can affect quality as well as cost. [*Lost in the Middle*](https://arxiv.org/abs/2307.03172) was submitted in 2023 by researchers with affiliations including Stanford University and the University of California, Berkeley. The peer-reviewed journal *Transactions of the Association for Computational Linguistics* published the study in 2024. Its experiments found that models often performed worse when relevant evidence appeared in the middle of a long input, including models designed for long contexts. The study does not claim that every large coding request fails. It shows that evidence can fit into a context window without remaining equally usable.

Automatic compaction is a useful capacity safeguard. [Claude Code's cost documentation](https://code.claude.com/docs/en/costs) says the tool summarizes conversation history as a thread approaches its context limit. A summary replaces detail with a shorter representation. An admission policy acts before that late safeguard by choosing which exact items belong in the next request at all.

I think the 95.2 percent figure should become a local hypothesis. Measure your own envelope, then ask how much repeated input came from stable instructions, current evidence, accepted artifacts, and material whose purpose had already expired.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A stateless model interface makes the client reconstruct every request, so old text becomes new workload whenever the request builder carries it forward. One Codex workspace measured 95.2 percent reused input, Manus reported an input-output ratio near 100 to 1, and peer-reviewed research shows why a larger window does not make every item equally usable.</p></div>

## Admit evidence, then let it expire

The model does not need the same record as an auditor. Keep the complete event history in an append-only audit trail, a log that preserves earlier events without silently changing them. Build the model's working set from a context manifest, a small record of which items may enter the next envelope, why they are needed, where they came from, and when their permission ends.

For the database-client upgrade, the audit trail keeps every failed patch and test run. The manifest can carry the current migration excerpt, the latest source revision, the still-failing test, and a patch that cleared its declared check. History remains available for investigation, while the model receives evidence selected for the decision in front of it.

Each manifest entry needs an artifact identity, source revision, purpose, estimated token count, expiry condition, status, and approval reference. An artifact is a concrete output such as a patch, test report, or decision record. A content hash is a compact fingerprint of its bytes, allowing approval to bind to the exact version that was checked rather than to a filename that may later change.

The lifecycle can use four states. New output begins as `candidate`. Checked material becomes `carried` and may enter a later request. Failed work becomes `rejected`. Material that no longer has a current purpose becomes `expired`.

An approval event is the logged result of an automated check or human review, and `approval_event_id` is its identifier. A runtime gate permits `candidate` to move to `carried` only when its `approval_event_id` points to a passing check or reviewer approval for the same artifact and task. The gate should also match the content hash and policy version so edited output cannot borrow approval from an earlier version.

The blocked paths protect the meaning of those states. A `rejected` item never moves to `carried`: corrected work enters as a new candidate with a new artifact identity. When the task closes, every remaining carried item expires, and when a requirement supersedes an artifact, the system expires the old one. An `expired` item cannot return to `carried` either. Reopening the work creates a fresh candidate and a visible decision.

I think expiry is the missing half of most context controls. Teams often inspect what enters an agent, then let accepted material travel indefinitely. Giving each item a purpose and an exit condition makes retention a deliberate state change rather than an accidental property of a long thread.

The policy should still admit broad evidence when the task requires it. A research synthesis may need many current sources, while a narrow code change may need only a few files and tests. The target is sufficient, justified context. A universal token ceiling would be easier to enforce and easier to misuse.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep the full event history outside the prompt and assemble each request from a manifest with provenance, purpose, approval, and expiry. Candidate output must pass a check before it travels, while rejected and expired artifacts remain visible in the audit trail without returning as active evidence.</p></div>

## Instrument one policy boundary

The first meter should cover one provider and preserve that provider's own event meanings. Store the raw usage response with the provider, model, request identifier, task identifier, active context-policy version, and a version for the usage schema, meaning the field names and definitions returned by the provider. A provider adapter is the small translation layer that produces common measures without deleting the original record.

Anthropic exposes fresh input, cache creation, cache reads, and output separately. Its retrieved-input share should be calculated as:

```text
retrieved-input share =
    cache_read_input_tokens
    ----------------------------------------------------------------
    input_tokens + cache_creation_input_tokens + cache_read_input_tokens
```

Cache creation stays out of the numerator because the request writes a new cache entry rather than retrieving one. It remains in the denominator because creating that entry still requires the provider to process the input, and the denominator represents all input traffic. Output remains outside this ratio because the question concerns input composition. If a field's meaning changes, version the adapter and begin a new comparison period instead of joining unlike records into one trend line.

The log should also record retries, review minutes, outcome, actual provider charge, allocated plan cost, and public-price shadow value. Actual cost says what the organization paid under its contract. Shadow value shows exposure to another dated price schedule. Mixing the two produces a dashboard that Engineering cannot explain and Finance cannot reconcile.

For a pilot, set a constraint rather than pretending the meter is free: one platform engineer, 16 hours, one provider, and one repeatable task class. Use raw provider usage records as the data source and review the results monthly beside actual spend. If the team cannot explain the field mapping within that envelope, the logging gap becomes the first finding.

Procurement should check cache duration, retention location, export access, and usage-field changes during the same review. These supplier details belong inside the technical boundary because the measurement depends on them remaining available and stable.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Start with one provider, preserve its raw usage fields, and translate them through a versioned adapter. For Anthropic, only cache reads belong in the retrieved-input numerator, while cache creation stays in total input. Keep actual spend separate from shadow value and time-box the first meter with a named owner and monthly review.</p></div>

## Make the rollout able to lose

Choose one repeatable task class before changing production. Dependency upgrades with deterministic test suites work because the evidence and acceptance checks can be declared in advance. State which tests must pass, which review is required, what evidence must accompany the change, and what counts as entering use.

Then compare the current request builder with the manifest-based version. Randomly assign eligible live tasks where operationally safe, or replay a fixed set of closed tasks through both routes when live assignment is impractical. Hold the model, prompt version, tool permissions, retry ceiling, and acceptance rubric constant. When feasible, reviewers should not know which route produced an output.

Predeclare how far acceptance may fall, how much review time may rise, and which required evidence may never be omitted. Set a reviewer-hour budget before the run and count time spent aligning reviewers or resolving disagreements. A lower model bill cannot compensate for human effort the experiment chose not to price.

Report the difference in cost per accepted result with a 95 percent confidence interval, a range that expresses uncertainty in the estimated difference. For paired replays, one reproducible method is a task-level percentile bootstrap: repeatedly resample task pairs with replacement, calculate the difference for each resample, and use the central 95 percent of those estimates. Declare the method before seeing the result. If the interval still crosses the adoption limit, the sample does not support the change.

Failure traces matter alongside the average. A rejected patch that appears in later requests reveals an admission defect even when total tokens fall. A task that launches repeated searches after useful evidence expires reveals the opposite mistake. I think a context policy has lost when it wins the token chart but weakens acceptance, review time, or evidence quality.

Pricing may soon make this control more urgent. The July report already separates five-minute and one-hour cache creation from later reads, so duration and retrieval are visible billing events. My take is that a major enterprise coding-agent plan will expose a retained-context allowance, memory quota, or separate retrieval term by August 2027. That is a falsifiable prediction rather than a disclosed supplier plan.

There is precedent for preparing before a flat plan changes. [Technology critic Ed Zitron reported](https://www.wheresyoured.at/the-more-you-buy-the-more-you-lose/) that some heavy users of GitHub Copilot, GitHub's AI coding assistant, consumed more than 25 times their monthly fee before a move to token-based billing produced user anger. His account does not predict Anthropic's next action. It shows why an architecture should understand its traffic before a contract gives that traffic a new price.

The flat plan may change, and the model rate certainly will. A team with explicit admission rules and a provider-aware meter can still compare architectures on the same honest denominator. The agent has earned production only when the work people keep is worth the full cost of producing it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Test context policy under fixed model and acceptance conditions, price reviewer effort, and let the experiment reject a token-saving design that harms quality. Supplier terms may change, but cost per accepted result remains an honest denominator. If the work that survives cannot carry its full cost, the agent has not earned production.</p></div>
