One unnamed Claude subscriber paid $200 for July 2026. On August 1, AI practitioner [Om Patel shared a community dashboard](https://x.com/om_patel5/status/2083401185172541449) showing that Claude Code, the coding assistant from AI company Anthropic, had processed 6.16 billion tokens during that month. A token is a unit of text a language model reads or writes. The dashboard priced the same activity at $7,470.35 through Anthropic’s public application programming interface, or API, the metered route software uses to call a model.

That second number was not an invoice, an audited provider record, or Anthropic’s cost to serve the user. It was API list-price exposure: a counterfactual built from public rates. If the dashboard’s usage, model mix, cache classifications, and rate card were accurate, direct API billing would have been about 37.4 times the subscription fee. Anthropic’s underlying compute cost remains unknown.

I think the more important warning is behavioral. Flat pricing protects the user from a metered bill, but it also weakens the feedback that teaches efficient use. Coding agents can send their accumulated context, including instructions, messages, files, tool definitions, and tool results, with each request. Context engineering means deliberately choosing which of that material the model receives and how it is arranged. Under tighter allowances or direct API pricing, that subtle skill becomes budget control.

## Why 96% is a signal, not a baseline

[Anthropic documents](https://code.claude.com/docs/en/costs) that Claude Code sends the full conversation with every request. Prompt caching reuses a stored computation for the unchanged beginning of a request, lowering its price and delay, but it does not make repeated material disappear. Cached tokens remain in usage records and can draw against a subscription allowance.

In July 2026, AI practitioner Nate B. Jones, who sells a context-management framework, [reported](https://natesnewsletter.substack.com/p/reduce-ai-token-usage) that his local tracker labelled 3.59 billion of 3.75 billion input tokens as “reused input” across 143 threads in Codex, the coding agent from AI company OpenAI, during one working day. That is 95.73%, or almost 96%. His broader recorded total was 3.77 billion tokens.

The label needs care. In Jones’s tracker, reused input meant prior material reported again as input; it was not an OpenAI cached-input billing field. His local event log also contained cumulative usage updates, so those records cannot be treated as unique billable traffic without a rule that keeps final updates or otherwise removes duplicates. The percentage is an investigation signal from one workspace, not an industry baseline.

Patel’s dashboard used different fields but pointed at the same mechanism. Cache reads, which reuse stored prompt material, and cache writes, which create material for later reuse, made up 86.2% of its $7,470.35 list-price estimate. Neither trace proves a universal percentage. Together, they tell an engineer where to look first: the history repeatedly carried into the next request.

## The subtle work is deciding what survives

Reducing context blindly can lower the token count while increasing retries and review. The 2024 peer-reviewed paper [*Lost in the Middle*](https://arxiv.org/abs/2307.03172), written by researchers from Stanford University, the University of California, Berkeley, and AI company Samaya, found that models often performed worse when relevant information sat in the middle of long inputs, even when the models supported long context. More material can therefore cost more and make the useful evidence harder to use.

A sound context policy preserves the current objective, constraints, decisions, evidence, and acceptance checks. It removes superseded debate, duplicate output, and tools unrelated to the present task. The practical choices follow from the trace:

| What the trace shows | Likely failure | Policy change | Guardrail |
|---|---|---|---|
| A thread continues after the objective changes | Old dialogue and files return on every turn | Start a fresh thread and carry a compact handoff artifact | Keep decisions, evidence, constraints, and acceptance checks |
| Tool descriptions dominate the input | Every available tool is exposed regardless of need | Expose only tools required for the current task | Restore a tool when a capability check fails |
| Cache creation jumps after minor edits | Stable instructions are mixed with changing task material | Put stable instructions first and volatile material later | Track cache creation separately by cache lifetime |
| Tokens fall while retries or review rise | Useful evidence was removed | Retrieve current evidence when it becomes necessary | Roll back if quality or latency crosses its limit |

Automatic compaction, where agent software summarizes an aging conversation, is useful as a safety net. It is also lossy because the software chooses what to omit. The team’s policy should decide what deserves to survive before the model’s input limit forces that decision.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Context hygiene is selective carry-forward, not indiscriminate deletion. Preserve the evidence needed to pass the task, stabilize reusable material, and reverse any change that saves tokens by creating more failed work.</p>
</div>

## Run the price change before it arrives

A team does not need a perfect industry benchmark to improve its own system. It needs a bounded trial with a named technical owner, one recurring task class, a decision date, and a rollback owner. Freeze the starting repository state, instructions, tool set, sampling rule, and acceptance checks. Then compare the current context policy with the proposed policy from matched starting states, declaring whether each run starts with an empty cache or one that already contains the stable prompt. Repeat enough runs to report a median and range. When judgment is human, hide the policy from the reviewer and calibrate the grading on a small shared sample. Set quality, latency, privacy, engineering-effort, stop, and rollback limits before the first run.

Preserve each raw usage event, then normalize it through a versioned provider adapter, a small mapping layer that translates vendor-specific fields into a common record. Record the provider, model, raw field-format version, rate-card date, task and policy identifiers, fresh input, output, latency, retries, reviewer time, and acceptance. Keep Anthropic cache reads and cache writes separated by time-to-live, the period a cached prompt remains reusable. Map OpenAI cached input only when OpenAI reports it. For cumulative logs, define the final-update or duplicate-removal rule before summing anything.

The financial record also needs three separate fields: actual cash charges, a predeclared allocation of flat subscription and platform costs, and public API list-price exposure. An accepted result is a run that passes the checks declared before the trial. To calculate full cost per accepted result, add the metered API charges, allocated flat costs, and reviewer-labor costs incurred across every attempt, retry, and reopened task, without double-counting them. Divide that amount by the accepted-result count. If no result passes, the ratio is undefined and the trial has failed its acceptance guardrail.

Lower repeated input creates business value only when it reduces an API bill or subscription tier, releases constrained capacity, or cuts review time without lowering quality. A flat subscription lets us postpone that accounting; it does not remove the engineering need. Learning the system now means the next pricing change becomes a rate-card update, rather than the first time we discover how much old context our agents keep buying.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Run a controlled context-policy trial, keep vendor fields and cost concepts separate, and count all failed and reviewed work. The metric that survives a pricing change is full cost per accepted result.</p>
</div>
