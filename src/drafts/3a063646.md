One screenshot put two prices on the same month of AI-assisted coding: $200 and $7,470.35. The first was a subscription to Claude, the AI service made by Anthropic. The second was what a usage tool said the same traffic would have cost at public API list rates. An application programming interface, or API, lets software call Claude directly, and Anthropic prices those calls by the tokens processed.

[Technology founder Om Patel shared the image on 1 August 2026](https://x.com/om_patel5/status/2083401185172541449) as another user’s result. The image covered July 2026 and came from `claude-cost`, which reports usage from Claude Code. Claude Code is Anthropic’s coding agent for the terminal. The screen showed 36,881 responses and 6,156,261,087 tokens. A token is a unit of text processed by a model. Divide the displayed API-list-price value by the subscription payment and the gap is 37.4 times.

That larger figure was not the subscriber’s invoice, verified savings, or Anthropic’s cost of serving the traffic. [Claude Code’s cost documentation](https://code.claude.com/docs/en/costs) says the software creates its dollar estimate locally by applying standard list rates to token counts, so the result can differ from what a customer pays. I don’t know Anthropic’s underlying compute cost, and the screenshot cannot reveal it.

A separate measurement points to the mechanism. Practitioner [Nate B. Jones](https://www.youtube.com/watch?v=Y8vAQ1FgNbM), who publishes about coding agents, described a one-day context trace in a video. His tracker, he said, saw 3.77 billion tokens while 143 Codex threads ran during that working day. Codex is a coding agent made by OpenAI, an AI research and product company.

Jones put 3.59 billion tokens in the reused-input category, meaning text supplied before and included again in later model calls. Those rounded figures work out to 95.2 percent, which he called “almost 96%.” The video also promotes his Ringer multi-agent framework, so this is a self-reported lead, not a neutral industry benchmark.

I think the two reports matter because they expose something subscription pricing conceals. An agent can feel cheap at the seat level while its request path moves enormous amounts of repeated text. What matters is whether each piece of context still deserves to enter the next call, and whether carrying it improves work that survives review.

## The list-price shock reveals the request path

The category rows make the screenshot useful. Generated output accounts for $1,015.97, ordinary fresh input for $14.14, cache retrieval for $3,595.52, and new cache entries for $2,841.89 at one hour plus $2.83 at five minutes. Combining the read with both writes gives $6,440.24. That is 86.2 percent of the $7,470.35 shadow value, although the printed row percentages total 86.1 percent after rounding.

That 86.2 percent is cache activity, not 86.2 percent reused input. Prompt caching lets a provider reuse work it already performed on the beginning of an earlier request, such as fixed instructions or prior conversation. Cache creation measures input written into a new entry, while cache retrieval, shown as a read, measures an entry used again. Under [Anthropic’s current prompt-caching rules](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), using cached content also refreshes its lifetime at no additional refresh charge. A write and a read therefore describe different events and must stay separate.

The cache-read row offers a limited plausibility check. Dividing $3,595.52 by 5.878 billion cache-read tokens gives an implied blended rate of about $0.61 per million. Anthropic’s [current price table](https://platform.claude.com/docs/en/about-claude/pricing) lists cache hits at $0.50 per million for Claude Opus and $1 per million for Claude Fable, the two model families that dominate the report. The implied rate sits between them. This shows that the screenshot is internally consistent with the public price range; it does not independently verify the hidden allocation of tokens by model or the underlying logs.

The traffic shape follows from how the client works. Claude Code’s documentation says each request includes the conversation so far; after the model uses tools, another call carries the collected tool output. One model call therefore receives a payload made from instructions, dialogue, available tool definitions, fetched file fragments, tool returns, and the newest message. In this article, that payload is the request envelope. The client reconstructs state on every call, which makes a long session carry its own history again and again.

Caching lowers price and latency when the opening blocks of a request match. It cannot judge whether an old error trace, a superseded requirement, or a duplicate file deserves another trip. The same bytes may become cheaper for the provider to process even as they become less useful to the application.

Manus offers a production-side comparison without confirming Jones’s reuse percentage. The team builds a general-purpose AI agent and [wrote in July 2025](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus) that its system received about 100 input tokens for every output token on average. This input-to-output ratio does not divide cache creation from retrieval. It supports only the narrower point that reading can dominate an agent’s traffic.

I think that is the real warning inside the $7,470.35 display. The list-price total did not become this subscriber’s invoice, yet the request architecture behind it still affects latency, rate limits, and the model’s ability to find the evidence that matters.

Caching discounts repeated prefixes; it does not decide whether the repeated material remains useful.</p></div>

## Build the next request from the decision backward

Context hygiene means deciding which material enters a model call, keeping that material current, and removing it when its purpose expires. I think the simplest way to apply it is to begin with the next decision. What is the agent trying to decide now, which checks define success, and what evidence can change that decision? Those answers should shape the request envelope before another turn is added.

Consider a coding agent investigating a queue worker that sometimes processes the same job twice. The next call may need the current failure, the idempotency requirement that a retry must not apply the work twice, the relevant handler, the queue configuration, and the test that proves the duplicate is gone. It does not need every repository search, two rejected patches, or the full installation log. If a rejected patch exposed a real constraint, carry that constraint with a link to the full trace rather than carrying the whole debate.

Thread boundaries should follow deliverables. Once the queue defect is accepted, a request to write release notes belongs in a new thread, with only the approved change and live constraints carried across. This prevents an unrelated job from inheriting the entire investigation by accident.

This separation matters. The complete transcript can live in a task log where new records are added but earlier records are never rewritten, preserving audit and recovery evidence. The active envelope can hold the current objective, live constraints, approved evidence, and the smallest current change needed for the next action. Context hygiene should remove clutter from attention without deleting history from storage.

Automatic compaction is a useful fallback. Claude Code summarizes old conversation as a session approaches its context limit, which keeps the session running. Yet a general summary produced late in the session does not know by itself which test was accepted, which requirement was replaced, or which failed attempt contains a safety constraint. The application needs explicit task state if those distinctions must survive compression.

The request should also be arranged for the cache. Keep stable instructions and the tool definitions actually available to the task at the front. Put changing observations later, deduplicate repeated artifacts, retrieve narrow source regions when they are enough, and cap output at the length the next step can use. A long answer costs output tokens now and becomes input again when the conversation is resent.

Smaller requests need a quality guard because omission can be as damaging as clutter. [Lost in the Middle](https://arxiv.org/abs/2307.03172), a 2023 study by Nelson Liu and colleagues, tested how well language models use information across long prompts. Performance often fell when the relevant material moved from the beginning or end into the middle. The pattern appeared even in models built to accept long contexts. This was not a coding-agent cost trial, but it shows why context capacity and usable attention should not be treated as the same thing.

There is no universal token limit that makes an envelope clean. One task may require a long contract or a broad code search; another may turn on twelve lines and one failing test. I think the enforceable rule is provenance plus purpose: every dynamic item should identify its source, the task it belongs to, why it is present now, and when it should stop returning.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Start with the next decision and its acceptance checks, then admit only current instructions, relevant evidence, and the latest change. Preserve the full history outside the prompt, because reducing active context should never erase the trace.</p></div>

## Put three ledgers on one trace

A context policy cannot be governed from a subscription receipt alone. It needs three ledgers that meet at the request identifier. The cash ledger records what the organization actually paid. The exposure ledger applies a dated public API price schedule to show what the same traffic would cost under that schedule. The traffic ledger records what the model processed, split by the provider’s documented event types.

For each request, keep the task identifier, provider, model version, context-policy version, input categories, output tokens, actual charge or subscription allocation, latency, reviewer time, and final acceptance event. This is enough to connect a packing decision to both cost and outcome. It also preserves a boundary when a provider changes a field name or billing meaning.

Anthropic’s current usage response separates `output_tokens` from three input buckets: `input_tokens` for input that was neither read from nor used to create a cache entry, `cache_creation_input_tokens` for writes, and `cache_read_input_tokens` for retrieval. For this provider, cache-read share of total input is:

```text
cache_read_input_tokens
────────────────────────────────────────────────────────────────────────
cache_read_input_tokens + cache_creation_input_tokens + input_tokens
```

Tokens written to create an entry belong in the denominator because the model processed them as input. Only cache reads belong above the line because only they retrieved an existing entry. Keeping that boundary prevents all cache activity from being mislabeled as reused input. The formula must remain provider-specific and versioned, since another supplier may expose different events or change their meaning.

A high cache-read share still does not prove high spend or wasted context. Cache hits are discounted, output has a different price, and repeated policy or source material may be essential. Calculate money from the dated price schedule or contracted charge, then test usefulness against acceptance. Token share describes traffic composition. It cannot answer the value question on its own.

I think the operational dashboard should show all three ledgers beside acceptance rate and reviewer minutes for each task class, meaning a group of jobs judged by the same acceptance checks. Record the baseline distribution before setting a budget, because a repository migration and a one-file bug fix should not inherit the same threshold. An alert should identify a change worth inspecting, not declare failure without looking at the work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep actual cash, API-list exposure, and token composition separate, then join them by request and task. For Anthropic, cache creation counts in total input but not retrieved input, and a high retrieval share says nothing by itself about money or value.</p></div>

## Let accepted work set the price

The denominator decides what the system optimizes. Call a result accepted only after it passes the declared checks for its task class, clears any required human review, and enters use. A plausible answer, a patch with failing tests, and an abandoned retry are attempts. To calculate loaded review cost, multiply review time by the organization’s labor rate after compensation and employer costs are included.

The operating metric is simple:

```text
cost per accepted result =
  total actual cost of model calls, review labor, and platform support
  / number of accepted outputs
```

Under a flat plan, allocate the subscription fee to the measured task class using a rule chosen before the analysis. Under metered access, use the contracted charge. Keep the $7,470.35 API-list estimate in the exposure ledger, outside this numerator, because the subscriber did not pay it.

A new context policy should earn adoption against representative completed work. Run each selected task in two isolated conditions, one with the current request behavior and one with the proposed policy. Randomize the order and keep these controls unchanged: model version, permitted tools, maximum retries, acceptance checks, and reviewer guidance. Keep reviewers blind to the condition behind each output. Before any result is visible, record the acceptable limits for quality, review time, and latency.

The uncertainty calculation should be reproducible too. Resample the task pairs with replacement 10,000 times using a fixed random seed, the recorded value that makes the resampling sequence repeatable. Recompute cost per accepted result for both conditions in each sample, then take the 2.5th and 97.5th percentiles of the difference as a 95 percent bootstrap confidence interval. A confidence interval is a sample-based range that shows how uncertain the estimated change remains. If a resample contains no accepted result for one condition, report the share of undefined resamples instead of hiding it. If the interval is too wide to support the predeclared decision, the honest result is to measure more work.

My take is that fewer tokens count as a loss when they create more retries or more review. The policy earns its place only when the same class of work reaches acceptance at lower full cost without crossing the quality, latency, or reviewer-time limits. One platform owner should review that result monthly, while Finance supplies the loaded labor rate and Procurement tracks provider pricing, retention, and usage-field changes.

The $200 plan makes this discipline easier to postpone because the cash signal is muted. I think postponement is the mistake. The 37.4-times shadow value is a warning about exposure, and Jones’s 95.2 percent finding from 143 Codex threads in one working day is a reason to inspect the request path. The number that settles the argument is the cost of work you can actually keep.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Define acceptance before measuring cost, include model, review, and platform expense, and test context policy under fixed quality guardrails. A cheaper request matters only when it produces a cheaper result that survives review.</p></div>
