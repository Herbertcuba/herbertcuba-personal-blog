On August 1, 2026, [Om Patel](https://x.com/om_patel5/status/2083401185172541449) shared on X, the social network, a screenshot that reports July usage from `claude-cost`, a tool that estimates Claude Code usage at public API prices. Claude Code is Anthropic's terminal-based coding agent, and Anthropic is the AI company behind the Claude model family. The image reports 6.16 billion tokens, the units of text that models process and providers bill, across 36,881 responses. The subscriber paid $200 for a Claude Max plan; the screenshot does not identify that person.

Hold that workload and model mix constant, then send it through Anthropic's public application programming interface (API), the metered route software uses to call Claude directly. The estimated customer bill becomes $7,470.35 for the month, or 37.4 times the subscription price. This is an API list-price counterfactual. That total never appeared on the subscriber's invoice, and Anthropic's private cost of serving the traffic remains undisclosed.

The shape of the estimate explains why it grew so large. Generated output represented 13.6 percent of the estimated cost, while cache reads represented 48.1 percent and one-hour cache writes added 38.0 percent. A cache write stores an unchanged opening block of a request, called a prompt prefix, and a cache read retrieves a matching block later. Together, those operations account for $6,437.41, or 86.2 percent of the public-price estimate. Cache activity reveals how the request was delivered, though it cannot tell us whether the stored material helped.

A second observation exposes the same mechanism from another angle. In a July 2026 video, AI practitioner [Nate B. Jones](https://www.youtube.com/watch?v=Y8vAQ1FgNbM) reported 3.77 billion tokens across 143 Codex threads in one instrumented day, with 3.59 billion classified as reused input. Codex is OpenAI's coding agent. That works out to 95.2 percent in his workspace, rather than an industry rate. Jones is building and promoting Ringer, his own context-management framework, and his public video leaves the raw records, collection code, model versions, and exact rule used to label reused input unpublished.

I think the bargain removes a price signal engineers urgently need. Under a flat plan, another turn feels free at the margin, so old files and stale debate keep riding into new requests. Direct token billing makes that behavior visible on every call. Context engineering, the deliberate choice of what a model receives and what survives into its next call, is the subtle skill between those two worlds. The subscription gives us time to learn it before every inefficient request has an obvious price.

## The counterfactual restores the missing signal

The direct API counterfactual is simple: keep the recorded behavior unchanged and charge each request at the public rate. One month costs $7,470.35. Three equally heavy months cost $22,411.05, compared with $600 for the subscription, leaving an implied list-price discount of $21,811.05. Those numbers assume behavior would stay fixed under metered billing, which is unlikely once every turn reaches an invoice.

Public list price also differs from provider cost. It includes the commercial price Anthropic charges developers and enterprises, while its internal compute cost is private. Negotiated rates, service discounts, [rolling five-hour limits and weekly caps](https://claude.com/pricing), and changed user behavior would all move the customer bill. I think the $7,470 figure earns attention because its boundary is clear: it tells us what the same recorded usage would cost through the public API. It does not reveal Anthropic's internal serving cost or the margin left after that cost.

The screenshot is internally consistent with Anthropic's [published API price table](https://docs.anthropic.com/en/docs/about-claude/pricing). Cache reads cost $0.50 per million tokens for Opus, one Claude model family in the image, and $1 per million for Fable 5, another family shown there. The reported $3,595.52 subtotal across 5.878 billion cache-read tokens implies a blended rate near $0.61 per million, which falls between the two published rates. This is a plausibility check because both figures come from the screenshot; an exact recomputation would require the cache-read allocation by model.

The public evidence still stops at the screenshot. Without a redacted request export, a reader cannot rebuild every model call, usage field, or price lookup. A defensible internal claim needs the raw provider records in JSONL, a format that stores one JSON object per line, plus model identifiers, a dated rate card, the provider-field mapping, and a reproducible calculation. The collection date and any excluded traffic belong in that evidence package too.

Direct API billing naturally creates most of this trail because Anthropic returns separate usage fields for fresh input, cache creation, cache retrieval, and output. A team can preserve the subscription and build a shadow meter beside it: record those fields, apply the dated public rate, and join each request to a task outcome. A monthly review should show the API-equivalent value as a behavior signal, separate from enterprise invoice exposure, along with accepted results and human review time. The bargain remains, but the missing feedback returns.

The figure is a list-price counterfactual with known limits, and a request-level shadow meter can recover its feedback without giving up the subscription.</p></div>

## Why context keeps coming back

Anthropic's [Messages API](https://platform.claude.com/docs/en/build-with-claude/working-with-messages), the public endpoint software uses to send conversations to Claude, is stateless. The model retains no conversation memory between calls. The client rebuilds that memory by sending the instructions, conversation history, files, and tool results with each request. Context is this complete working bundle, while the context window is the maximum bundle a model can receive in one call.

Consider an agent fixing a checkout bug where a discount code fails. The first request carries the operating instructions and bug report. The second carries those items again, followed by the first answer and an opened file. By turn twenty, one new question arrives behind nineteen earlier exchanges, repository text, and retry history. Each turn pays to carry the old turns, even after some have stopped helping.

[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), Anthropic's system for storing and retrieving a stable request prefix, lowers the delivery price of this repetition. A matching cache read costs one tenth of base input. That discount is valuable, but relevance remains outside the cache's job. A cheap cache hit can still fill the model's working window with stale evidence and accumulate cost across thousands of calls.

This is why the screenshot's 86.2 percent and Jones's 95.2 percent must stay separate. The first combines cache reads and one-hour cache writes valued at list prices. Jones used his own classification of reused input across a day of Codex work. Combining them would produce a statistic neither source supports, yet both observations expose the same architecture: old material can dominate the traffic around a small amount of new work.

Repeated context also has a quality cost. [*Lost in the Middle*](https://arxiv.org/abs/2307.03172), a 2023 study by language-model researchers at Stanford University, the University of California, Berkeley, and the AI company Samaya AI, found that models often performed worse when useful information appeared in the middle of long inputs. The paper reached the peer-reviewed journal *Transactions of the Association for Computational Linguistics* in 2024. As stale material surrounds decisive evidence, the model can use that evidence less reliably, which creates retries and adds work for reviewers.

I think context debt is a useful name for this accumulation. Like technical debt, it charges interest through future work. Every retained dead end returns on the next call, takes space beside the useful evidence, and may return again inside the model's answer. The cost curve and the quality curve begin to reinforce each other.

The 2014 science-fiction film *Edge of Tomorrow* gives us the right mental model. Major William Cage relives the same battle, while the battlefield resets and he carries the lesson from each failed loop. An API call begins each loop without that memory. The engineer decides whether the next request receives the useful lesson or the whole battlefield transcript.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Stateless calls rebuild memory by resending context, while caching discounts a matching prefix without judging its usefulness. Repeated material can dominate traffic and bury decisive evidence, so every item carried forward should have to earn another trip.</p></div>

## The subtle art is deciding what survives

Character count is too crude for a retention policy. A short false assumption can do more damage than a long, verified requirement, so each retained item needs an answer to one question: which future decision will this help? The orchestrator, the software that assembles the next model request, can then carry approved evidence and accepted artifacts, such as patches or decision records that survived review, while letting debate and dead ends expire.

A small lifecycle makes that judgment testable:

| State | Meaning | Eligible for the next request? |
| --- | --- | --- |
| `candidate` | Evidence captured with a source, task identity, and request trace identity, a unique label connecting it to the model call | No |
| `approved` | Evidence linked to a passing check or named reviewer decision | Yes |
| `carried` | Approved evidence selected under a policy version and expiry rule | Yes |
| `rejected` | Evidence or an artifact that failed its acceptance rule | No |
| `expired` | Evidence closed by task completion, supersession, or retention deadline | No |

The transitions should fail closed, which means rejecting missing or invalid state changes by default. A `candidate` needs an approval event before it becomes `carried`, and evidence attached to a `rejected` artifact stays out of later requests. Task closure must emit an expiry event for every carried item. When one artifact supersedes another, the event expires the older artifact, records the replacement identity, and preserves the link between them. These small rules turn “keep the useful context” into behavior a test can reject.

Each event needs enough identity to reconstruct the decision. At minimum, record the task, request trace, artifact, source evidence, policy version, lifecycle state, event time, and approving or expiring event. The request record should add the provider's raw usage fields, model version, rate-card version, retry count, acceptance result, and review minutes. A redacted export of those records, along with the field mapping and calculation script, is the minimum evidence package behind any public efficiency claim.

Existing engineering tools can enforce the record without choosing the retention policy. JSON Schema is a machine-readable contract for required fields and allowed values. Pydantic is a Python validation library that can apply a similar contract inside an application. Temporal is a durable workflow system that records completed steps and resumes work after failures. These tools provide shape and continuity. The team still decides which evidence deserves another model call and which outcome proves that decision was sound.

Modern coding agents also compact long conversations. [Claude Code's cost documentation](https://code.claude.com/docs/en/costs) says the tool summarizes earlier history as it approaches the context limit. Compaction is a shorter retelling that helps a run continue after the original thread becomes too large. I think of it as a safety valve. Deliberate retention acts earlier, while the system still knows which evidence supported an accepted artifact and which material belongs to a failed path.

Return to the checkout bug. Once the patch passes its test and a reviewer accepts it, the next step may need the patch, the requirement it satisfies, and the passing test identity. The twenty-turn argument that produced it can expire. If a later requirement replaces the patch, a supersession event closes the old artifact and points to the new one. This preserves the engineering result and its proof without forcing every future request to relive the debate.

The everyday practices follow from the same rule. Start a clean thread when the job changes, and search for the relevant lines before loading a whole repository or document. Keep stable instructions and tool definitions at the front of a request so the cache can match them, then append changing evidence later. Ask for the output length the next step needs, because a long answer becomes input on the following turn, and route simple classification or summarization to the least expensive model that still passes the task's acceptance rule.

Measurement closes the loop. For Anthropic requests, a useful delivery metric is:

`retrieved-input share = cache_read_input_tokens / (input_tokens + cache_creation_input_tokens + cache_read_input_tokens)`

This is an Anthropic-specific proxy for the share of input retrieved from cache. Other providers need their own field mapping, and a high share says nothing about whether the retrieved text improved the result. Join it to retention events and acceptance, then the team can see which retained-item category earns its cost and which one merely travels cheaply.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Context engineering means admitting approved evidence and accepted artifacts into future requests under explicit lifecycle rules. Schema validation, durable workflows, and compaction can enforce or support the process, while trace identities and outcome data reveal whether retained context earned its place.</p></div>

## Price the result that survives review

An accepted result is an output that clears a fixed technical gate and human review. For a code patch, the technical gate may be continuous integration, the automated build-and-test process used before changes enter a shared codebase. Reviewer approval then confirms that the patch solves the intended problem. This gives the team a unit of useful work instead of a count of model activity.

The operating metric is:

`cost per accepted result = (model spend + loaded review cost + material tracing and workflow cost) / accepted results`

Loaded review cost includes pay and employment overhead for the time people spend checking outputs. Tracing, storage, policy work, and audit effort belong in the numerator when they are large enough to affect the decision. I think this metric blocks a familiar accounting trick: smaller contexts can reduce model spend while causing more retries, and a cheaper model can move work onto reviewers. The full unit cost exposes both shifts.

A paired replay can test the policy before rollout. Start with 30 closed defects and run each one twice in clean environments, once under the current growing-thread process and once under the proposed carry-forward rules. Keep the model, prompt, tools, retry cap, test environment, and acceptance rubric fixed. Reviewers should assess the 60 outputs without knowing which policy produced them.

The human-cost envelope must be explicit. If two reviewers each assess all 60 outputs at four minutes per output, each person spends four hours and the pair spends eight reviewer-hours before calibration or disagreement resolution. Add those extra hours, then multiply the total by the team's loaded reviewer rate. The model-cost comparison is incomplete until that amount enters the calculation.

Set the decision rule before the replay. Choose the minimum reduction in cost per accepted result that repays rollout effort, the acceptance-rate floor, and the largest reviewer-time increase the team will tolerate. The policy then has three possible decisions: adopt when the saving clears the local bar and every guardrail holds; hold when the confidence range, the estimated span of plausible effects, crosses the decision threshold; redesign when quality, privacy, retention, or review limits fail. These thresholds should come from the team's economics and risk, rather than a universal percentage borrowed from someone else's workload.

Rollout needs an owner and a routine. The platform team owns telemetry, the usage and outcome records produced by the system, along with the policy version and monthly cost report. Domain engineers own task acceptance. New teams receive short onboarding on the lifecycle states, while a weekly exception review handles task classes that fail and gives engineers a documented escalation path. Privacy and procurement owners review trace retention, regional processing, supplier terms, and changes to cache or usage fields before the policy expands.

The monthly dashboard can stay compact: task class, policy version, model spend, reviewer minutes, accepted results, cost per accepted result, and open exceptions. At a 5,000-person organization, the policy should expand by task class only where the accepted-result saving exceeds tracing and governance overhead. That row lets an engineering leader or board see whether improvement came from cleaner context or from moving cost and risk somewhere less visible.

Some work will justify a larger live context. Broad research and difficult reasoning with the strongest available models may depend on evidence spread across many sources. Compliance records may require long storage outside the live prompt, and regional processing rules may make traces more expensive to keep. Cost per accepted result catches these cases because the model bill, review burden, storage overhead, and acceptance rate move together in one decision.

In a July 2026 article, technology critic [Ed Zitron](https://www.wheresyoured.at/the-more-you-buy-the-more-you-lose/) reported that GitHub Copilot, GitHub's AI coding assistant, once let power users consume more than 25 times their monthly subscription fee before a move toward token billing triggered a revolt. Claude can follow a different path. I don't know when Anthropic will tighten a limit, change a rate, or redesign the plan. A provider can change its meter much faster than an engineering team can learn a new discipline.

My take is that the $200 plan buys more than cheap access. It buys a training window in which teams can build the meter, test what deserves to survive, and learn where context improves accepted work. The durable edge belongs to teams that use this period well. When the meter changes, cost per accepted result will reveal who learned to engineer context while access was cheap.

Generous subscriptions create a temporary training window; cost per accepted result shows whether a team used it to build durable efficiency.</p></div>
