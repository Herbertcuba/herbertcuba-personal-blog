On 1 August 2026, [Om Patel, the author of an X post, shared a screenshot](https://x.com/om_patel5/status/2083401185172541449) of an unidentified Claude Code subscriber's July activity. X is the social network formerly called Twitter. Claude Code is a coding agent that works from the terminal and is produced by Anthropic, the AI company behind the Claude model family. Patel's text said “$200 paid,” while the report showed 36,881 responses, 6,156,261,087 tokens, and $7,470.35 at public prices for Anthropic's application programming interface, or API.

A token is a small unit of text that an AI model reads or writes. API list prices are the public per-token rates charged when software calls a model directly, so the report was asking what the same traffic would have cost under a different buying arrangement. Its own note says: “This is what the same usage would cost per-token on the API. On a subscription you are not charged any of it.”

The arithmetic still gets your attention. The reported API value was 37.4 times the $200 payment. Yet neither the post nor the image identifies the subscriber or plan tier, and the image does not reveal Anthropic's cost to serve those requests. The number is a counterfactual meter reading, not a missing invoice.

A second, unrelated measurement suggests why the meter can run so fast. AI practitioner [Nate B. Jones said](https://www.youtube.com/watch?v=Y8vAQ1FgNbM) that his tracker recorded 3.77 billion tokens across 143 threads in OpenAI Codex, a coding agent from the AI company OpenAI, during one working day. Of those tokens, 3.59 billion, or 95.2 percent, were labeled reused input, which is the source of the “almost 96 percent” shorthand. This is one self-instrumented workspace rather than an industry benchmark, but I think it points to the engineering problem behind the price shock: agent systems can spend most of their traffic carrying old material into the next request.

The practical response is selective retention, with context hygiene, the practice of deciding what a model sees and for how long, built into the system design. That lets the team connect context volume to the only economic result that matters: work that passes its checks and enters use.

## The meter is real, but the bill is hypothetical

Prompt caching is a provider feature that reuses a matching block from an earlier request so it can be processed more cheaply and quickly later. A cache write, also called cache creation, stores or refreshes that block for a defined lifetime. A cache read retrieves the matching block on a later call. Those events belong to the same mechanism, but they are not the same event.

The five rows visible in the July report add up to the stated total:

| Reported category | API-list-price value | What happened |
| --- | ---: | --- |
| Cache read | $3,595.52 | A previously stored matching block was retrieved |
| One-hour cache write | $2,841.89 | Input was stored or refreshed with a one-hour lifetime |
| Five-minute cache write | $2.83 | Input was stored or refreshed with a five-minute lifetime |
| Fresh input | $14.14 | Input fell outside the reported cache operations |
| Output | $1,015.97 | The models generated new text |

The three cache rows total $6,440.24, or 86.2 percent of the $7,470.35 counterfactual. Those dollars measure all cache-related processing. They cannot serve as a retrieved-input ratio because two rows record a cache being populated or renewed before any later retrieval occurs. Collapsing creation and retrieval would strengthen the headline by breaking the measurement.

The cache-read line offers a useful consistency check. The report shows 5,878,394,153 cache-read tokens with a value of $3,595.52, which is about $0.61 per million tokens. On [Anthropic's price table](https://docs.anthropic.com/en/docs/about-claude/pricing), checked in August 2026, one million cache-hit tokens cost $0.50 for Claude Opus and $1 for Claude Fable 5; both model families appear in the report. The blended result sits between those rates, which supports the screenshot's arithmetic without reconstructing the underlying requests.

The economic boundary matters just as much as the arithmetic. [Anthropic documents rolling five-hour usage windows and additional weekly limits](https://claude.com/pricing) for paid plans, so flat access is bounded. I don't know what Anthropic spent to serve this traffic, and public API prices cannot answer that question. They include a commercial rate for builders, not a receipt for electricity and chips.

I think the honest reading is more useful than the dramatic one. A $200 payment removed the user's marginal price signal while billions of tokens still moved through the system. Flat pricing can hide traffic from the person holding the card, but it cannot remove the latency, evidence-selection burden, or exposure to a future pricing change that comes with that traffic.

Retrieval and creation must remain separate: a cache hit brings back stored input, while a write stores or renews it. The arithmetic makes this a credible traffic signal under API list prices, not an audited bill or a measure of Anthropic's cost.</p></div>

## Reuse begins in the request builder

[Anthropic's Messages API documentation](https://docs.anthropic.com/en/api/messages-examples) says the interface is stateless, meaning the client sends the conversational history again with every call. The context window is the maximum amount of material a model can receive in one request. I use *request envelope* for the payload actually assembled for a call: system instructions, tool definitions, conversation history, source material, tool results, and the new question.

Imagine a coding agent investigating a date parser that fails only on leap day. Its first envelope might contain the bug report, the parser, and one failing test. After several turns, the envelope may also contain a rejected patch, an entire test log, documentation found during search, a reviewer correction, and the model's earlier explanations. The current question can shrink to one assertion while the payload preserves the whole excavation.

That is how old text becomes a workload. Prompt caching can discount a stable prefix and reduce latency, but it cannot make irrelevant material useful. The model still has to locate the current evidence among everything the client decided to resend. Context hygiene starts one layer earlier than caching by asking whether each item belongs in the envelope at all.

Jones's 95.2 percent observation gives this pattern a memorable number, although its boundary should stay visible. The cited video and description did not supply the raw export, collection code, model versions, or complete labeling rule required for an independent reproduction. Nor should his reused-input label be treated as identical to every provider's cache-read field without a documented mapping. The claim belongs to his day, tracker, and Codex workspace.

There is production evidence for the broader shape. In July 2025, the team behind [Manus, a general-purpose AI agent, reported](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus) an average input-to-output ratio of roughly 100 to 1 in its agent loop. That does not validate Jones's exact percentage, but it shows that an input-heavy loop is not unique to his setup.

Long input can also weaken the result. [*Lost in the Middle*](https://arxiv.org/abs/2307.03172) was submitted in 2023 by a research team whose affiliations included Stanford University and the University of California, Berkeley. The peer-reviewed journal *Transactions of the Association for Computational Linguistics* published the work in 2024. Its experiments found that models often performed worse when relevant information appeared in the middle of long inputs, including models built to accept long contexts.

The study does not prove that every large coding request fails, and a short prompt can be missing crucial evidence. It establishes a more careful point: available context and usable context are different quantities. I think repeated input should therefore be treated as state management with both a price and a quality effect, rather than as harmless exhaust from the agent loop.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A stateless model API makes the client rebuild the request envelope on every call, so yesterday's useful material can become today's repeated load. Caching discounts matching content but does not make stale content relevant. The 95.2 percent observation is bounded to one workspace, while production reporting and peer-reviewed research support the broader need to manage long, input-heavy loops.</p></div>

The mapping is precise: an instruction can remain valid in the record while becoming wrong for the current decision. An agent needs the same separation between history and active context, with a way for new evidence to supersede an old directive instead of carrying it forever.

## Separate the audit trail from the working set

An audit trail should preserve what happened, including failed attempts, tool output, and human decisions. A model's working set should contain what it needs for the next call. When the transcript serves both purposes, retaining evidence for accountability also forces the model to reread it as active context.

A cleaner design keeps an immutable event log outside the prompt and builds each envelope from a context manifest. A manifest is a small record describing which material may enter the next request and why. Stable instructions and the minimum required tool definitions form the cacheable front of the envelope. Current source excerpts and the latest test failure carry a source revision, purpose, measured token count, and expiry. Model outputs must earn the right to travel further.

That last rule needs explicit states. A new patch, answer, or decision record begins as `candidate`. If it passes the task's declared automated check or required human review, it becomes `carried` and may enter a later request. Failed work becomes `rejected`. Material that was once accepted becomes `expired` when the task closes, a deadline passes, or a newer artifact replaces it.

The transition must bind approval to exact content. An artifact identifier names the output, while a content hash is a compact digital fingerprint of its bytes. An approval event records the check, outcome, task, artifact, time, and policy version. A runtime validator, the software gate that checks a proposed state change, permits `candidate` to move to `carried` only when its `approval_event_id` points to a passing check or reviewer approval for the same artifact and task.

Rejected and expired records stay in the audit trail, but the request builder excludes them from the active envelope. A corrected patch receives a new artifact identifier instead of borrowing the approval attached to its predecessor. Supersession expires the old artifact, and reopening the question creates a new candidate. This preserves history without allowing history to masquerade as current evidence.

Automatic compaction is a useful backstop, not a complete admission policy. [Claude Code's cost documentation](https://code.claude.com/docs/en/costs) says the tool summarizes conversation history as it approaches the context limit. That protects capacity late in a thread, while a manifest acts before each request and makes the team's retention decision inspectable.

My take is that the target is sufficient context, not minimal context. A broad research task may need many sources, and difficult reasoning may benefit from a larger evidence set. In a repeated agent loop, however, every carried item should have a current purpose, a source identity, and an exit condition. That is how the team removes stale volume without starving the model of facts.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep the complete event history outside the prompt and construct each request from an explicit context manifest. Current evidence needs a source, purpose, size, and expiry, while generated artifacts move forward only after a logged check or review approves the exact content. Compaction manages capacity; an admission policy manages meaning.</p></div>

## Build a meter that respects provider semantics

A context policy is difficult to improve if the request log flattens every token into one total. Preserve the provider's raw usage fields together with the provider, model, request identifier, task identifier, policy version, and a version tag for the provider's usage schema, meaning the structure and definitions of the returned fields. A provider adapter, the small translation layer that interprets those fields, can then produce common measures without erasing the original evidence.

[Anthropic reports fresh input, cache creation, cache reads, and output separately](https://code.claude.com/docs/en/prompt-caching). For that provider, the retrieved-input numerator should contain `cache_read_input_tokens` only. The denominator should contain all input traffic, including fresh input, cache creation, and cache reads:

```text
retrieved-input share =
    cache_read_input_tokens
    ---------------------------------------------------------------
    input_tokens + cache_creation_input_tokens + cache_read_input_tokens
```

Cache-creation tokens stay out of the numerator because the request is writing or refreshing them, not retrieving them. They stay in the denominator because the model system still received that input. Output is excluded because this ratio asks what share of input was retrieved. If a provider changes a field's meaning, version the adapter and start a new comparison period rather than splicing unlike measurements together.

[JSON Lines](https://jsonlines.org/) is a simple format in which each line contains one valid JSON value. The proposed log should use one JSON object per line so an engineer can inspect, stream, and replay individual request records. Add the actual provider charge when it exists, the allocated subscription cost when access is flat, retry count, review minutes, outcome, and the active context-policy version. Keep the $7,470.35 API-list scenario in a separate `shadow_value` field so it never appears as money the organization actually paid.

That separation creates two honest views. Actual cost answers what the organization spent under its contract. Shadow value asks what the same recorded traffic would look like under a dated public price sheet, which is useful for contract exposure and architectural comparison. Mixing them produces a dramatic dashboard that Finance cannot reconcile and Engineering cannot trust.

I think the first implementation should be deliberately narrow: one provider, one repeatable task class, one owner, and a fixed setup budget. The platform team can own the adapter and context policy. Finance can supply contracted prices and an hourly review rate covering salary, benefits, and any other employment costs it elects to include, while Procurement watches retention terms, cache prices, export access, and schema changes. Record the meter's own build and operating cost as well, because a monitoring layer is not free merely because it is sensible.

The monthly view should put retrieved-input share beside input tokens per accepted result, cache-creation volume, retry count, review time, and context items rejected or expired by policy. No single line proves success. Together they show whether the system is carrying less irrelevant material while preserving enough evidence to complete the task.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Preserve raw provider usage fields and translate them through a versioned adapter. For Anthropic, cache reads belong in the retrieved-input numerator, while fresh input and cache creation remain in the total-input denominator. Keep actual spend separate from API-list shadow value, then start with one provider and task class before scaling the meter.</p></div>

## Let accepted work set the price

An accepted result is an output that passes the task's declared automated checks and required human review, then enters use. For the leap-day defect, that might be a patch that passes the reproduction test, the surrounding test suite, and review. A plausible patch that is rejected, rewritten, or abandoned still consumed model traffic and human attention, so its cost remains in the numerator.

The metric is simple:

```text
cost per accepted result =
    actual provider or allocated plan cost
    + loaded review cost
    + material task overhead
    ------------------------------------------------
    accepted results
```

Loaded review cost multiplies review time by an agreed hourly rate covering salary, benefits, and any other employment costs the organization counts. Material overhead can include paid tools, tracing, or storage when those amounts can change the decision. The aim is consistent comparison, not accounting theater. API-list shadow value belongs beside this formula, never inside its actual-cost numerator.

Then test the context policy as a production change. Choose a repeatable task class and define acceptance before the trial starts. Random assignment can send eligible tasks through either the current request builder or the manifest-based version. Keep the model, prompt version, tool permissions, and retry ceiling unchanged. When practical, reviewers should not know which route produced the result.

Before seeing the results, set limits for how far acceptance may fall, review time may rise, or required evidence may be omitted. Report cost-per-accepted-result differences with a confidence interval, a range calculated from sample data under a stated method to show how uncertain the estimated difference remains. A policy that sends fewer tokens but creates more retries, more reviewer work, or more defects has failed.

This is also where model choice becomes a fair comparison. A cheaper model lowers the rate applied to each token. Context hygiene changes the amount and quality of evidence sent on every turn. I think hygiene is the earlier lever for repeated agent work, but the research does not establish that it always beats switching models. Single-pass tasks and problems that push the strongest available models may need broad context, and the experiment should be allowed to say so.

Supplier pricing can change before the architecture does. According to [technology critic Ed Zitron](https://www.wheresyoured.at/the-more-you-buy-the-more-you-lose/), some heavy users of GitHub Copilot, GitHub's AI coding assistant, consumed value exceeding 25 monthly subscription payments. User anger followed when the product moved to token-based billing. His account does not predict Anthropic's next decision, but it shows why a team should learn its traffic shape while flat access still mutes the signal.

The two headline measurements have clear limits: the $7,470 meter cannot reveal Anthropic's loss, while one 95.2 percent observation cannot represent every agent. Their value is to expose a system-design question that each team can answer with its own logs: what did we carry, what survived review, and what did that accepted result truly cost? The subscription price tells you the price of entry. Cost per accepted result tells you whether the system deserves to stay.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Put every attempt's actual provider or allocated plan cost, human review, and material overhead in the numerator. Use only checked results that enter service in the denominator, and test context policy without changing the model or acceptance bar. Flat access can conceal repeated traffic; accepted work gives that traffic an honest price.</p></div>
