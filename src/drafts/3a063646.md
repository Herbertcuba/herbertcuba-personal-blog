On August 1, 2026, [Om Patel, founder of the research database BigIdeasDB](https://bigideasdb.com/authors/om-patel), [posted a screenshot on the social platform X](https://x.com/om_patel5/status/2083401185172541449) reporting two figures: $200 paid for Claude Max and $7,470.35 for the same July activity at public API prices. Claude Max is a high-usage subscription from the AI company Anthropic. The post and image do not identify the subscriber or establish that the account belonged to Patel, so this is a claim about the posted meter, not his personal usage.

The image came from [`claude-cost`, an independently published command-line dashboard](https://registry.npmjs.org/claude-cost/latest) for Claude Code, Anthropic's coding agent for reading repositories, editing files, and running commands. It showed 36,881 responses and 6,156,261,087 tokens, the small units of text that model providers count.

The two dollar figures are 37.4 times apart, but they belong to different ledgers. The $200 was reported subscription cash. The $7,470.35 was API-list-price exposure, a what-if estimate at the public pay-per-token rates for Anthropic's application programming interface, or API. Anthropic's internal cost of serving those requests remains undisclosed. I don't know that number, and the screenshot cannot reveal it.

I think the careful version of this story is more important than the sensational one. A flat seat can make an enormous request loop feel free at the moment an engineer chooses what to send. The meter exposes the volume, while a separate measurement in which almost 96% of one day's tokens were prior input sent again helps explain how a loop can grow so large.

**Status: implementation protocol; no savings demonstrated yet.**

The governing idea is contract-grade request telemetry: evidence detailed enough to reconstruct what crossed the provider boundary, how each attempt was priced under separate ledgers, and whether the output was accepted. Platform Engineering owns the technical boundary and rollback. One named business sponsor owns the pilot budget and the final go-or-no-go decision. The unit of value is the full cost per accepted result, with failures and reviewer effort still attached.

## Three prices are hiding in one screenshot

The posted dashboard separated the estimate into $14.14 of fresh input, $1,015.97 of model output, $2,844.72 of cache creation, and $3,595.52 of cache retrieval. Prompt caching is a provider feature that stores a stable block of input so later requests can reuse it at a lower rate. Cache creation writes that block; cache retrieval reads it again.

Together, cache creation and retrieval represented $6,440.24, or 86.2% of the public-rate estimate. The dashboard also reported 5.878 billion cache-read tokens. Dividing their $3,595.52 estimated value by that volume gives about $0.61 per million tokens, which falls inside [Anthropic's published cache-retrieval price range](https://platform.claude.com/docs/en/about-claude/pricing) for the models shown. That cross-check does not prove the dashboard captured every request perfectly, but it does show that the displayed cache arithmetic is internally coherent.

Repeated does not mean removable. A cached security policy may be essential on every request, while yesterday's test log may be stale. Provider billing fields can prove that material was repeated and show how it was priced; only the application can explain why each piece remained relevant.

The clean operating view therefore keeps three columns separate:

| Economic view | What it answers | What the screenshot supplies |
|---|---|---|
| Subscription cash | What did the post report as paid for access? | $200 for the month |
| API-list-price exposure | What would the recorded usage cost at public per-token rates? | $7,470.35 |
| Provider serving cost | What did Anthropic spend to run it? | No disclosed figure |

This separation matters because [Claude's paid plans use rolling five-hour windows, weekly limits, and discretionary caps](https://claude.com/pricing). A flat fee is a commercial access rule, not a promise that every possible request volume has the same economics. I think API-list-price exposure still earns a place in engineering telemetry, provided nobody quietly converts it into cash paid or verified savings. It gives teams a stable public rate card for comparing request designs while Finance keeps the actual ledger intact.

Contract-grade telemetry preserves both views without blending them. The event can carry a predeclared allocation of subscription cash, the provider's native token fields, and a price-sheet version used to calculate public-rate exposure. If the provider changes a model price or usage field later, the team can reproduce the old comparison rather than rewriting history with the new rate.

Keep subscription cash, public-rate exposure, and provider serving cost separate, and version the rate card used for every comparison.</p></div>

## The agent resends before it reasons

[Anthropic's Claude Code cost guide](https://code.claude.com/docs/en/costs) describes the mechanism plainly: “Claude Code sends your full conversation with every request, and each time Claude uses tools it sends another request carrying that batch of tool results.” The agent answers, searches, reads, runs a command, and then asks the model to reason again over a larger package. History is counted on every trip, not only when it first entered the thread.

Caching lowers the price of an unchanged prefix, the stable opening block of a request. Automatic compaction can summarize a conversation as it approaches the context limit. Both are useful defaults, yet neither decides relevance for the team. A cheaper repeated block is still repeated, while a summary created near a limit follows the agent tool's schedule rather than a task's acceptance criteria.

There is also a serious countercase to aggressive cleanup. Removing or reordering a stable prefix can reduce cache retrieval and create new cache writes, so a smaller request may cost more or respond more slowly. Dropping a tool definition while retaining an old call to that tool can leave the model with an event it can no longer interpret. The useful question is which material belongs in a stable prefix, which belongs in the current working set, and which should remain in a durable record outside the request.

A second measurement shows how large the repeated share can become. In a video published on July 29, 2026, [AI practitioner Nate B. Jones](https://www.youtube.com/watch?v=Y8vAQ1FgNbM), who also sells a context-management product, reported 3.77 billion tokens across 143 threads in Codex, a coding agent from the AI company OpenAI, during one working day. His tracker classified 3.59 billion tokens as reused input, meaning prior material sent again. Using the rounded figures, that is 95.2%, or almost 96%.

That percentage belongs to one person, one workspace, and one day. It also differs from Anthropic's cache-read field because a tracker-defined category and a provider billing category measure different things. The wider pattern has independent support: [Manus, a company building general-purpose AI agents, reported in 2025](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus) an average input-to-output ratio of about 100 to 1. The dashboard Patel posted showed roughly 186 total tokens consumed for each output token. These measurements share a direction, not a denominator.

Volume can become a quality problem as well. *[Lost in the Middle](https://arxiv.org/abs/2307.03172)*, a study first released in 2023 and published in the peer-reviewed journal *Transactions of the Association for Computational Linguistics* in 2024, tested retrieval and question answering over long inputs. Computer scientist Nelson F. Liu and his co-authors found weaker performance when relevant information sat in the middle. Its direct evidence concerns those tasks, so a coding team still needs its own evaluation, but the paper removes any reason to treat a larger context as automatically safer.

Context hygiene means deciding what deserves another trip. The following failure patterns turn that principle into request rules:

| Failure pattern | Request rule | Evidence to retain |
|---|---|---|
| One thread absorbs unrelated objectives | Start a task-scoped thread when the objective changes | Task identifier and thread start reason |
| The whole discussion survives after a decision | Carry the accepted decision, current constraints, and source references | Artifact version and approval |
| Old tool output remains beside current evidence | Give volatile results an expiry time and refresh them when needed | Source time, expiry, and refresh event |
| Every available tool schema loads on every turn | Admit only tools authorized and required for the current task stage | Toolset version and admitted tool names |
| Outputs and retries expand without attribution | Cap outputs where the task permits and link each retry to its originating task | Attempt identifier, parent attempt, and outcome |

That final link is retry lineage: every new attempt points back to the same piece of work, so failed and abandoned calls remain visible. My take is that context hygiene begins as an operator habit but becomes dependable only when thread scope, evidence expiry, tool admission, cache policy, and retry lineage are properties of the system.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Coding agents repeatedly resend conversations and tool results. One instrumented Codex workspace measured 95.2% reused input in a day, while other production observations confirm input-heavy loops without creating a universal percentage. Control relevance without ignoring cache-prefix stability, tool dependencies, or the durable history needed to explain a result.</p></div>

## Build a context budget at the request boundary

Good operator habits weaken under long sessions, parallel work, and automated retries. The durable control sits at the request boundary, the final application-owned step that assembles material before it reaches the model provider. A context item is one discrete piece of that material, such as a policy, source passage, tool definition, test result, or approved decision.

Admission and traceability answer different questions. To earn admission, an item needs a source, a current task, a reason for inclusion, an owner, and an expiry condition. Once admitted, the system retains an item identifier, task identifier, lifecycle state, original text, and content hash for traceability. A content hash is a fixed-length fingerprint calculated from the text; SHA-256, a standard cryptographic hash used below, can detect changed or duplicate material, while authorization still comes from the source and owner records.

The admitted items become a request envelope, the assembled provider-bound context. The lifecycle is intentionally small. It permits `candidate → active`, `candidate → rejected`, and `active → retired`; terminal states cannot return to the envelope, and activation fails when an admission field is empty. If rejected or retired content becomes useful again, it returns as a new candidate with a current reason and expiry.

The boundary must read state from an authoritative lifecycle store, the application's persisted transition history, instead of trusting an incoming object's claim that it is active. Without that lookup, a directly constructed payload can disguise a rejected or retired item as current.

The runtime must fail closed. In plain language, one malformed or unauthorized item rejects the whole request instead of disappearing silently. [TypeScript, a typed form of JavaScript, removes its type declarations when code is compiled](https://github.com/microsoft/TypeScript/wiki/FAQ#what-is-type-erasure), so types alone cannot validate records loaded from storage, plugins, or tool responses. The boundary must check actual state, non-empty admission fields, identifiers, a finite future expiry, the recomputed hash, task affinity, authorization, item count, and the total bytes of admitted text.

I think a design this specific should carry an executable kernel. The following dependency-free program runs in Node.js, a server-side JavaScript runtime. Save it as `boundary.mjs` and run `node boundary.mjs`; a clean run prints `13 boundary assertions passed`. It accepts lifecycle identifiers rather than caller-supplied item objects, reads authoritative state, enforces task and authorization policy, caps item count and UTF-8 text bytes, gates tools, and compares the complete provider-shaped fixture payload field by field.

```js
import assert from "node:assert/strict";
import { createHash } from "node:crypto";

const EDGES = new Set([
  "candidate>active",
  "candidate>rejected",
  "active>retired",
]);
const REQUIRED_TEXT = [
  "id", "taskId", "source", "owner", "reason", "text", "expiresAt",
  "contentHash",
];
const digest = (text) =>
  createHash("sha256").update(text, "utf8").digest("hex");

function transition(store, id, next) {
  const current = store.get(id);
  const allowed = current == null
    ? false
    : EDGES.has(`${current.state}>${next}`);
  if (allowed === false) throw new Error(`illegal transition for ${id}`);
  const updated = Object.freeze({ ...current, state: next });
  store.set(id, updated);
  return updated;
}

function validatePolicy(policy) {
  const valid =
    typeof policy.taskId === "string" &&
    policy.taskId.trim().length > 0 &&
    policy.authorizedItemIds instanceof Set &&
    policy.allowedTools instanceof Set &&
    Number.isFinite(policy.now) &&
    Number.isInteger(policy.maxItems) &&
    policy.maxItems > 0 &&
    Number.isInteger(policy.maxContextBytes) &&
    policy.maxContextBytes > 0;
  if (valid === false) throw new Error("invalid boundary policy");
}

function validateActive(item, policy) {
  if ((item.state === "active") === false) {
    throw new Error(`${item.id}: not active`);
  }
  for (const field of REQUIRED_TEXT) {
    const valid =
      typeof item[field] === "string" && item[field].trim().length > 0;
    if (valid === false) throw new Error(`${item.id}: invalid ${field}`);
  }
  const expiry = Date.parse(item.expiresAt);
  if (Number.isFinite(expiry) === false || expiry <= policy.now) {
    throw new Error(`${item.id}: invalid expiry`);
  }
  if ((digest(item.text) === item.contentHash) === false) {
    throw new Error(`${item.id}: hash mismatch`);
  }
  if ((item.taskId === policy.taskId) === false) {
    throw new Error(`${item.id}: cross-task context`);
  }
  if (policy.authorizedItemIds.has(item.id) === false) {
    throw new Error(`${item.id}: unauthorized context`);
  }
}

function buildEnvelope(store, submittedIds, policy) {
  validatePolicy(policy);
  if (submittedIds.length > policy.maxItems) {
    throw new Error("context item limit exceeded");
  }

  const items = submittedIds.map((id) => {
    const item = store.get(id);
    if (item == null) throw new Error(`${id}: missing lifecycle record`);
    return item;
  });

  const hashes = new Set();
  let contextBytes = 0;
  for (const item of items) {
    validateActive(item, policy);
    if (hashes.has(item.contentHash)) {
      throw new Error(`${item.id}: duplicate content`);
    }
    hashes.add(item.contentHash);
    contextBytes += Buffer.byteLength(item.text, "utf8");
  }
  if (contextBytes > policy.maxContextBytes) {
    throw new Error("context byte limit exceeded");
  }

  return Object.freeze({
    taskId: policy.taskId,
    contextBytes,
    items: items.map(({ id, text, contentHash }) =>
      Object.freeze({ id, text, contentHash })),
  });
}

function toProviderPayload(envelope, request, policy) {
  for (const tool of request.tools) {
    const allowed =
      typeof tool.name === "string" && policy.allowedTools.has(tool.name);
    if (allowed === false) throw new Error(`${tool.name}: unauthorized tool`);
  }
  return Object.freeze({
    model: request.model,
    max_tokens: request.maxTokens,
    system: envelope.items.map(({ text }) => ({ type: "text", text })),
    messages: request.messages,
    tools: request.tools,
  });
}

const NOW = Date.parse("2026-08-16T12:00:00Z");
function candidate(id, changes = {}) {
  const initial = {
    id,
    taskId: "task-17",
    state: "candidate",
    source: "policy-store",
    owner: "platform",
    reason: "required security policy",
    text: `policy:${id}`,
    expiresAt: new Date(NOW + 60_000).toISOString(),
  };
  const merged = { ...initial, ...changes };
  return {
    ...merged,
    contentHash: changes.contentHash ?? digest(merged.text),
  };
}

function activatedStore(...items) {
  const store = new Map(items.map((item) => [item.id, item]));
  for (const item of items) transition(store, item.id, "active");
  return store;
}

const allowedItemIds = new Set([
  "ctx-1", "ctx-empty", "ctx-expiry", "ctx-hash", "ctx-cross",
  "ctx-big", "dup-1", "dup-2", "ctx-good", "ctx-bad",
]);
const POLICY = Object.freeze({
  taskId: "task-17",
  now: NOW,
  authorizedItemIds: allowedItemIds,
  allowedTools: new Set(["read_file"]),
  maxItems: 3,
  maxContextBytes: 64,
});
const REQUEST = Object.freeze({
  model: "model-from-frozen-manifest",
  maxTokens: 1024,
  messages: [{ role: "user", content: "Fix fixture 17" }],
  tools: [{
    name: "read_file",
    description: "Read a fixture",
    input_schema: {
      type: "object",
      properties: { path: { type: "string" } },
      required: ["path"],
    },
  }],
});

let passed = 0;
function check(assertion) {
  assertion();
  passed += 1;
}

const admitted = candidate("ctx-1");
const admittedStore = activatedStore(admitted);
const envelope = buildEnvelope(admittedStore, [admitted.id], POLICY);
check(() => assert.deepEqual(
  toProviderPayload(envelope, REQUEST, POLICY),
  {
    model: "model-from-frozen-manifest",
    max_tokens: 1024,
    system: [{ type: "text", text: "policy:ctx-1" }],
    messages: [{ role: "user", content: "Fix fixture 17" }],
    tools: REQUEST.tools,
  },
));

const rejected = candidate("ctx-rejected");
const rejectedStore = new Map([[rejected.id, rejected]]);
transition(rejectedStore, rejected.id, "rejected");
check(() => assert.throws(
  () => buildEnvelope(rejectedStore, [rejected.id], POLICY),
  /not active/,
));
check(() => assert.throws(
  () => transition(rejectedStore, rejected.id, "active"),
  /illegal transition/,
));

const invalidCases = [
  [candidate("ctx-empty", { owner: "" }), /invalid owner/],
  [candidate("ctx-expiry", { expiresAt: "NaN" }), /invalid expiry/],
  [candidate("ctx-hash", { contentHash: "wrong" }), /hash mismatch/],
  [candidate("ctx-cross", { taskId: "task-99" }), /cross-task/],
];
for (const [item, pattern] of invalidCases) {
  check(() => assert.throws(
    () => buildEnvelope(activatedStore(item), [item.id], POLICY),
    pattern,
  ));
}

const unauthorized = candidate("ctx-unauthorized");
check(() => assert.throws(
  () => buildEnvelope(activatedStore(unauthorized), [unauthorized.id], POLICY),
  /unauthorized context/,
));

const countA = candidate("ctx-good");
const countB = candidate("ctx-bad");
const countStore = activatedStore(countA, countB);
check(() => assert.throws(
  () => buildEnvelope(countStore, [countA.id, countB.id], {
    ...POLICY,
    maxItems: 1,
  }),
  /item limit/,
));

const tooLarge = candidate("ctx-big", { text: "x".repeat(65) });
check(() => assert.throws(
  () => buildEnvelope(activatedStore(tooLarge), [tooLarge.id], POLICY),
  /byte limit/,
));

const duplicateA = candidate("dup-1", { text: "same text" });
const duplicateB = candidate("dup-2", { text: "same text" });
check(() => assert.throws(
  () => buildEnvelope(
    activatedStore(duplicateA, duplicateB),
    [duplicateA.id, duplicateB.id],
    POLICY,
  ),
  /duplicate content/,
));

const validMixed = candidate("ctx-good");
const expiredMixed = candidate("ctx-bad", {
  expiresAt: new Date(NOW - 1).toISOString(),
});
check(() => assert.throws(
  () => buildEnvelope(
    activatedStore(validMixed, expiredMixed),
    [validMixed.id, expiredMixed.id],
    POLICY,
  ),
  /invalid expiry/,
));

check(() => assert.throws(
  () => toProviderPayload(envelope, {
    ...REQUEST,
    tools: [{ name: "shell", input_schema: { type: "object" } }],
  }, POLICY),
  /unauthorized tool/,
));

assert.equal(passed, 13);
console.log(`${passed} boundary assertions passed`);
```

The kernel covers the application-owned boundary, and its assertions include terminal-state revival, empty admission data, non-finite expiry, hash mismatch, cross-task context, missing authorization, excessive count or size, duplicate content, mixed validity, and an unauthorized tool. A production adapter still needs an integration test after system text, messages, and tool schemas have been assembled. That test should compare the final vendor payload with the recorded envelope and prove that each admitted item appears once while retired content and unapproved tools remain absent.

A cache-aware policy also needs more than physical deletion:

| Technique | What it changes | Main risk to test | Evidence to compare |
|---|---|---|---|
| Pinned stable prefix | Keeps approved system policy and stable tool definitions in a fixed order | Stale policy or unnecessary schemas persist | Cache reads, cache writes by configured lifetime, prefix version, latency |
| Compaction | Replaces older detail with a shorter summary | The summary drops evidence or changes meaning | Summary source range, acceptance, failure category |
| Physical removal | Omits expired or irrelevant material | A required dependency disappears or the cache prefix changes | Removed item identifiers, cache behavior, retries, acceptance |
| Masking | Replaces sensitive values with controlled placeholders | Hidden values remain inferable or placeholders still consume space | Data class, mask rule, review finding, token count |
| Authorization gate | Excludes tools or records the task is not allowed to use | A later call lacks a required capability | Authorization decision, admitted toolset, failure category |
| Durable external record | Keeps the full event history outside the model request | The request cannot retrieve a needed artifact in time | Record version, retrieval event, latency, final acceptance |

The useful shape is a pinned stable prefix, an append-only task trace, a replaceable working suffix, and a durable external record. “Append-only” means earlier events are not silently rewritten; it does not require every event to ride inside every prompt. The request can carry current decisions and references while the full trace remains available for reconstruction.

[Anthropic's Messages API, the programmatic interface for model requests](https://platform.claude.com/docs/en/api/beta/messages/create), returns separate usage fields for ordinary input, cache creation, cache retrieval, and output. Preserve that raw usage object before adding common labels. Renaming every repeated category as “reused input” would erase the provider-specific meaning that makes the event auditable.

A reconstructable request event needs five linked layers:

| Layer | Fields to retain | Decision it supports |
|---|---|---|
| Provider | Raw usage object, model response identifier, API-schema revision, and price-sheet version | Reproduce token counts and public-rate exposure |
| Request | Task, request, attempt, and parent-attempt identifiers | Charge retries and abandonment to the same work |
| Configuration | Model, prompt, toolset, context policy, cache lifetime, and network-policy versions | Compare runs under known conditions |
| Context | Admitted item identifiers and hashes, plus boundary rejections | Explain what changed in the request envelope |
| Outcome | Acceptance, reviewer time, latency, security findings, and final status | Connect request design to usable work |

The public sources from Patel, Jones, and Manus provide aggregates rather than request-level traces. They establish scale and mechanism, but they cannot demonstrate savings from a particular context rule. There is no real redacted provider event in the supplied evidence, and inventing one would defeat the point. A pilot should not advance until its evidence packet contains one real redacted raw event, the exact normalized row produced from it, the boundary-test output, and two paired traces, one improving and one regressing.

Enforce task affinity, authorization, count, and byte limits; test the final provider payload; preserve cache effects and raw vendor fields; and keep the durable trace outside the prompt.</p></div>

## Make accepted work the denominator

A smaller request can still be a worse system. It may omit evidence, trigger more retries, increase reviewer effort, destroy a useful cache prefix, or produce a fast answer that fails the task. Token reduction earns its value only when the resulting work survives the same acceptance standard.

An accepted result is an output that meets criteria declared before the run and within a fixed attribution window, the period during which every related attempt is counted. For a comparable group of code-fix tasks, which evaluators call a cohort, acceptance might require designated tests, a security check, and reviewer approval without a follow-up repair. The exact rule belongs to the team and task, but it cannot move after the results appear.

Test one context change, the treatment, against the current policy, the baseline, on the same tasks. This is a paired comparison because each task is evaluated under both policies. Freeze enough of the starting state that another engineer can explain any remaining difference:

| Decision fixed before the run | Required commitment |
|---|---|
| Task cohort | Named task class, sample count, fixture hashes, attribution window, and failure categories |
| Starting state | Repository commit, dependency lockfiles, database or service fixtures, mocks, and network policy |
| Provider stack | Exact model identifier, API-schema revision, tool versions, prompt version, and context-policy version |
| Run budgets | Output limit, decoding settings exposed by the provider, timeout, retry count, and total attempt budget |
| Cache conditions | Stable-prefix version, configured cache lifetime, cold-or-warm starting condition, and recorded cache reads and writes |
| Review method | Randomized run order, reviewer blinded to baseline or treatment, and fixed functional, human, and security criteria |
| Repeat rule | Repeated runs or a predeclared precision rule, plus a paired confidence interval for the within-task change |
| Effort envelope | Maximum implementation hours, reviewer hours, provider cash, and calendar duration |
| Decision rule | Minimum material improvement, guardrails, stop condition, review date, and rollback owner |
| Evidence packet | Every attempt, sample spread, failure distribution, raw-event mapping, and one improving plus one regressing trace |

A paired confidence interval is a range around the average within-task difference, rather than a claim based on two unrelated averages. It will not rescue a poor task sample, but it makes uncertainty visible. If the team cannot afford repeated runs, it should declare a precision rule or minimum effect large enough to act on before seeing results, then report that limitation.

The practical start can happen quickly without inventing an effort estimate. On Monday morning, the business sponsor names the task class, budget owner, and final decision owner. Within one working day, Platform Engineering estimates and caps instrumentation hours and calendar time, while the product or engineering lead names reviewers and caps their hours.

The control owners then record their conditions. Security and the data protection officer responsible for privacy oversight record the data class, processing region, retention rule, and risk-classification owner. FinOps, the practice of linking technology use to financial accountability, records the cash-allocation method. Procurement and Legal record export requirements, provider-change notice, exit rights, and emergency rollback authority. The pilot does not start until those caps, conditions, and owners are visible.

The same named sponsor remains accountable through three gates:

| Gate | Evidence produced by | Final accountable decision |
|---|---|---|
| Pilot approval | Platform supplies the boundary and effort estimate; the evaluation lead supplies fixtures and acceptance rules; control owners record data and supplier conditions | Business sponsor funds, narrows, or stops the pilot |
| Production approval | Evaluation lead supplies the full evidence packet; Platform supplies rollback proof; Finance confirms the cash view | Business sponsor approves production use or restores the baseline |
| Provider-change review | Platform reports schema and model changes; control owners review price, retention, region, notice, and exit effects | Business sponsor continues, pauses, changes provider, or invokes exit; Platform retains emergency rollback authority |

The table assigns operating responsibility. For a European deployment, legal and privacy owners still have to map its evidence to the organization's actual duties and risk classification. The engineering value is simpler: distributed consultation no longer hides who can spend, approve, stop, or exit.

If a guardrail breaks, restore the baseline policy. Report the sample count and spread rather than a single average, and show failures by category, such as missing evidence, tool error, security rejection, timeout, or reviewer rejection. A cohort with zero accepted outputs fails the evaluation; it cannot produce a flattering efficiency number by dividing only the calls that looked good.

Then calculate two results and keep them separate:

```text
actual cost per accepted result =
  (allocated subscription cash + incremental provider cash
   + reviewer labor + relevant platform cost across every attempt)
  / accepted results

API-list-price exposure per accepted result =
  public-rate value of every provider request in the cohort
  / accepted results
```

The subscription allocation must be chosen before the comparison. Reviewer minutes should remain visible beside their monetary conversion, and every retry stays in the numerator through retry lineage. The second equation helps compare architectures and supplier terms; the first describes the team's actual economics.

I think this creates a falsifiable procurement prediction. If request telemetry becomes an operating control, buyers will begin requiring stable usage exports, historical rate cards, advance notice of field or retention changes, regional commitments, and enforceable rollback or exit rights at renewal. The prediction fails if teams can reconstruct the same cohort economics and preserve the same stop authority after a provider change without those clauses.

Once every context item has a current reason to cross the boundary and every attempt remains attached to an outcome, teams can compare context policies and model tiers without confusing a cheap-looking seat with productive work. The decision-relevant price of an AI agent is the full cost of the work a reviewer can accept, with every failed attempt still attached.
