Om Patel [shared a Claude Code usage screenshot](https://x.com/om_patel5/status/2083401185172541449) for July 2026. He paid $200. The same usage came to $7,470.35 at API list prices, a 37.4x gap.

The screenshot logged 36,881 responses and 6.16 billion tokens. Cache reads represented 48.1 percent of the displayed value. One-hour cache writes represented 38.0 percent, while output represented 13.6 percent. Reads retrieve an existing cached prefix. Writes put content into the cache. The combined 86.2 percent describes cache operations, so it cannot serve as a reuse figure.

The screenshot reveals nothing about Anthropic's serving cost. I don't know what the company spent on this user. I think the useful part is the shape of the meter: agent work can move enormous amounts of context behind a flat monthly price.

## Cheap reuse can still be waste

A separate trace points to the mechanism behind the cost pressure.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>One instrumented Codex workspace classified 95.2 percent of a day's tokens as reused input. A cache discount lowers the rate on old text, while relevance determines whether that text helps the next attempt.</p></div>

Nate B. Jones [reported 3.77 billion tokens across 143 threads](https://www.youtube.com/watch?v=Y8vAQ1FgNbM) in one working day. His tracker classified 3.59 billion as reused input. That works out to 95.2 percent. It is one person's instrumented day rather than an industry benchmark.

Use one checkout bug as the test case. A discount code appears, but the total stays unchanged. The first attempt needs the failing test and pricing function. By attempt ten, a growing thread may also carry rejected patches, old tool output and explanations of paths already disproved.

Anthropic's [Messages API is stateless](https://platform.claude.com/docs/en/build-with-claude/working-with-messages), so the caller supplies the conversation history. Prompt caching can price a repeated prefix at 0.1x the base input rate. That measures cheaper movement. I think context debt begins when carried material grows while accepted results stay flat.

## Give context an expiry rule

The checkout task needs a clear boundary around what survives another attempt.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Carry the acceptance test, current evidence and latest patch. Expire the rejected discussion when its lesson has been captured, and end the thread when the job changes.</p></div>

Claude Code already [compacts history near the context limit](https://code.claude.com/docs/en/costs). That creates room. A stable prefix can earn a cache discount. The remaining decision belongs to the team: which evidence earns space in the next request?

For the discount bug, the answer is small. Keep the failing test, pricing function, latest patch and a short note about the last failure. Once the fix passes and a reviewer accepts it, store the patch and test result. The next job starts clean.

## Make the policy prove itself

A context rule should beat the growing thread on completed checkout work before it becomes a default.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Replay matched tasks with fixed models, tools and retry limits. Adopt curated context only when accepted-result cost falls without reducing acceptance or shifting correction work to reviewers.</p></div>

Start with 30 completed checkout tasks. Replay each under two policies: the original growing thread and the expiry rule. Hold the model version, tool version, prompt and three-attempt cap steady. Give the reviewer the final patch and test output without revealing the policy.

Set the decision rule first. Keep the expiry policy if model cost per accepted patch falls, the accepted count stays within one result of the baseline and median review time stays level or improves. Roll it back when acceptance drops beyond that tolerance or reviewers inherit more work. I think this is a fair test because it prices the whole checkout result instead of rewarding a lower token line by itself.

## Price the change that reaches production

The checkout fix becomes the unit of account once every attempt and review minute follows it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Cost per accepted result includes failed attempts and review effort. A named owner can use it to govern context, supplier terms and task quality together.</p></div>

Cost per accepted result is total model spend across all attempts, plus reviewer effort, divided by accepted changes. A rejected checkout patch stays in the numerator because the team paid for it.

The platform owner maintains the trace. Product engineering defines acceptance. FinOps verifies prices. Security sets retention, redaction and residency rules. Procurement records cache pricing, rate limits, export access and price-change notice. Each role owns a field the monthly review can inspect.

I think this is the smallest useful economics layer beneath [Welcome to the Orchestration Era](/posts/welcome-to-the-orchestration-era/). One accepted checkout fix now has a visible cost, a context policy and a person who can change the default.
