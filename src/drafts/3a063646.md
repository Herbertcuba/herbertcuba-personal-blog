Om Patel's [July Claude Code screenshot](https://x.com/om_patel5/status/2083401185172541449) put two prices on the same month: $200 for the plan and $7,470.35 at API list prices. His tool counted 36,881 responses and 6.16 billion tokens. Cache reads and writes made up about 86 percent of the displayed total.

Nate B. Jones [logged 3.77 billion tokens across 143 coding threads](https://www.youtube.com/watch?v=Y8vAQ1FgNbM) in one day. His tracker marked 3.59 billion as reused input, or 95.2 percent. The result describes one instrumented workspace. I think it gives agent teams a useful hypothesis: the expensive part may be the context wrapped around each answer.

Reuse alone says little about relevance. A stable system prompt can be a healthy cached prefix. Old searches and dead retries can become context debt. The engineering job is to separate those two kinds of reuse, then measure what each accepted result costs.

## What $7,470 of usage looks like

Nearly half of the listed dollar total came from 5.88 billion cache-read tokens. A cache write stores a reusable request prefix. A cache read uses that prefix again at a lower price. Patel's screenshot showed $3,595.52 in reads, $2,841.89 in one-hour writes and $1,015.97 in output tokens.

At [Anthropic's published cache prices](https://docs.anthropic.com/en/docs/about-claude/pricing), the blended read rate was about $0.61 per million tokens. Divide 6.16 billion total tokens by 33 million output tokens and the workflow consumed about 186 tokens for each token it generated.

I think the envelope deserves inspection first. That envelope can contain system instructions, tool definitions and old conversation. Each later request can carry all of it again.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Cache operations made up about 86 percent of the displayed list-price usage. The 186-to-1 ratio points toward the request carried around each generated token.</p></div>

## What 37.4 times the plan price means

The 37.4 ratio compares a subscription fee with API retail value. Claude plans have [rolling and weekly usage limits](https://claude.com/pricing), and API prices include retail margin for developers building products on Claude. I don't know Anthropic's internal cost for Patel's month.

The screenshot still works as a workflow meter. Flat pricing can hide how much context an agent needs to finish one accepted task. Better caching may keep the monthly price calm while the workflow grows dependent on a large prefix. A new limit or cache term can expose that dependency at renewal.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The ratio shows metered retail value inside a capped plan. It reveals a workflow dependency while leaving Anthropic's private serving cost unknown.</p></div>

## Reuse can be healthy or expensive

Take one checkout bug through the rest of the article. A discount code reaches the cart, yet the total never changes.

A token is a small unit of text. The context window is the text a model can use in one request. Model APIs start fresh, so an agent harness may resend earlier messages, file contents and tool results on each turn. The [anatomy of a Level 3 agent](/posts/2026-03-27-anatomy-level-3-agent/) lives around that stateless model call.

For the checkout agent, stable system instructions and the tool contract belong in every request. The bug report and useful lines from `pricing.py` remain relevant until the test passes. A failed search from turn three becomes prior trajectory once it stops helping. Sprint-planning notes are task-irrelevant from the start.

By turn twenty, a small question can travel with nineteen earlier replies. The [Lost in the Middle study](https://arxiv.org/abs/2307.03172) found that models often struggle when useful information sits inside a long context. It tested retrieval tasks, so the checkout fix still needs its own evaluation.

I think teams should trim prior trajectory and task-irrelevant material first. Required instructions stay stable. Useful evidence stays until the acceptance check closes the task.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Healthy reuse carries required instructions and useful evidence. Context debt carries stale work that raises cost or weakens the accepted result.</p></div>

## Put context hygiene into the workflow

Modern coding harnesses may summarize long threads automatically. This reduces the load, while the harness chooses what to forget and when. Deliberate hygiene sets the state boundary earlier.

LangGraph is a Python library for workflows that branch or repeat. A `StateGraph` connects those steps and passes shared state between them. A `TypedDict` describes the expected keys in that state for Python's type checker. Runtime validation still belongs in code.

For the checkout task, the state can hold `bug_id`, `relevant_lines`, `patch`, `test_passed` and `reviewer_decision`. The search step returns only the relevant lines. Its raw transcript has no state key, so it has no route into the patch step. This is the workflow side of [owning the agent layer](/posts/who-owns-the-agent-layer/).

An `accepted` transition requires `test_passed: true` plus reviewer approval. Agent narration has no power to mark the patch complete. I think this boundary makes context hygiene testable because every carried item needs an engineering reason.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Stable instructions stay cacheable. Verified checkout state moves between steps, while dead searches lose their route into the next request.</p></div>

## Prove it with a bounded pilot

Replay completed checkout tasks with two context strategies. The baseline uses the current harness. The hygiene run uses curated state. Keep the model, budget and acceptance criteria version fixed.

Start with a bounded group that fits your team. Ten seats may be practical for one organization, and the variance in your tasks decides how much evidence you need. Pairing the same task across both strategies makes the comparison easier to read.

Log every paid attempt:

```yaml
task_id: string
attempt: integer
context_strategy: baseline | hygiene
stable_prefix_tokens: integer
retrieved_evidence_tokens: integer
prior_trajectory_tokens: integer
cache_read_input_tokens: integer
billed_cost: number
latency_ms: integer
review_minutes: number
acceptance_criteria_version: string
test_passed: boolean
reviewer_decision: approve | reject
outcome: accepted | rejected
```

Define the decision rule before the run. Roll back when acceptance falls or reviewer time eats the saving. Keep testing when the result is noisy. Scale the default when accepted-result cost falls inside the team's quality limit.

The platform team captures usage and owns the default. Engineering defines acceptance. FinOps receives the combined report. I think the owner should deliver one page with savings, acceptance rate, reviewer burden and the proposed default.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A paired pilot can compare baseline and hygiene strategies under the same model and acceptance checks. The decision includes billed cost, reviewer time and quality.</p></div>

## Measure cost per accepted result

The checkout patch counts only when its discount test passes and a reviewer accepts the diff.

<div class="keymsg">
<span class="keymsg__label">The unit economics of agentic work</span>
<p class="keymsg__text">Cost per accepted result = billed agent cost across all attempts ÷ accepted tasks.</p>
<p>The rejected checkout patch, its retries and the final approved answer stay in the numerator.</p>
</div>

Suppose the first attempt costs $0.80 and fails its test. The second costs $0.60 and gets approved. The accepted result cost is $1.40. Reporting only the final attempt would hide almost half the paid work.

For a larger organization, baseline its three highest-volume agent workflows before renewal. Record accepted-result cost beside cache mix and reviewer time, then give each workflow an owner. Procurement needs answers to two supplier questions: which usage fields can be exported, and which cache or limit terms can change during the contract?

Reuse ratio tells you where to inspect. Cost per accepted result tells you whether a smaller context still produced work a human accepted. My take is simple: put that number beside the cloud bill, with every failed checkout attempt and reviewer minute still attached.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Cost per accepted result keeps every paid attempt in the numerator. Reuse ratio locates possible context debt, while acceptance and review time show whether removing it improved the work.</p></div>
