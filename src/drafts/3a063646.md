On 1 August 2026, Claude Code user [Om Patel posted a screenshot on X](https://x.com/om_patel5/status/2083401185172541449), the social network formerly called Twitter. Claude Code is the command-line coding agent made by Anthropic, an AI model provider, and the screenshot came from `claude-cost`, a tool that recalculates its usage at public API prices. Patel had paid $200 for a Claude Max subscription. His July report showed 36,881 responses and 6,156,261,087 tokens, with a public-price value of $7,470.35.

A token is a small unit of text that a model reads or writes and that providers use for billing. Divide the reported value by the subscription fee and the month comes to 37.4 times the price of the plan. The screenshot also carries the sentence that keeps this comparison honest: “This is what the same usage would cost per-token on the API. On a subscription you are not charged any of it.”

So there was no $7,470.35 invoice, and the screenshot tells us nothing about Anthropic’s serving cost. I don’t know what the company spent to handle those requests. What the report does reveal is the amount and shape of the traffic that a flat fee made almost invisible to its user.

A separate measurement points at the mechanism. In one self-instrumented day, AI practitioner Nate B. Jones reported that 3.59 billion of 3.77 billion tokens in his OpenAI Codex coding workspace were labeled reused input. That is 95.2 percent across 143 threads. It is one person’s instrument, not an industry benchmark, but it raises the right engineering question: why are agent systems moving so much old text to produce a small amount of new work?

For a 5,000-person company, Patel’s consumer subscription is not a budget forecast. It is a warning that thousands of agent loops may be operating without traffic accounting because the plan price has removed the immediate feedback. I think the useful response is to put a shadow meter, an internal traffic ledger, beside actual provider spend, then make every piece of carried context justify its next trip through the model.

Its value is diagnostic: flat access can hide enormous input traffic, and one separately measured workspace found that 95.2 percent of a day’s tokens were labeled reused input.</p></div>

## Read the report as a traffic ledger

Prompt caching lets Anthropic charge less when a later request begins with a matching block of text. A cache write stores or refreshes that block for a set period, while a cache read retrieves the match on a later request at a lower input price. The two events are related, but they answer different questions about traffic.

The five rows in Patel’s report reconcile exactly:

| Reported category | API-list-price value | What the row represents |
| --- | ---: | --- |
| Cache read | $3,595.52 | A matching cached block retrieved on a later request |
| Cache write, one hour | $2,841.89 | Input stored or refreshed with a one-hour lifetime |
| Cache write, five minutes | $2.83 | Input stored or refreshed with a five-minute lifetime |
| Fresh input | $14.14 | Input outside the reported cache operations |
| Output | $1,015.97 | Text generated by the models |

The three cache categories add up to $6,440.24, or 86.2 percent of the $7,470.35 counterfactual value. That percentage describes cache activity. It is not a reused-input percentage, because the two write rows record content entering or refreshing the cache rather than content retrieved from it. Treating writes as reuse would turn a billing category into a false claim about traffic.

The cache-read row is also internally consistent with [Anthropic’s published price table](https://docs.anthropic.com/en/docs/about-claude/pricing). The report shows 5,878,394,153 cache-read tokens and $3,595.52 of value, which works out to about $0.61 per million tokens. That sits between the published cache-hit prices of $0.50 per million for Claude Opus and $1 per million for Claude Fable 5, the model families present in the report. This check supports the arithmetic inside the screenshot. It cannot reproduce the underlying request log or prove who generated every token.

That boundary matters because “37 times the price” invites a claim about losses, although the underlying comparison uses a flat consumer plan on one side and retail API rates for builders on the other. Anthropic also [documents rolling five-hour and weekly usage limits](https://code.claude.com/docs/en/costs), so even the flat plan is bounded. The dramatic gap still tells us something useful: within those bounds, the user sees almost no marginal price for carrying another file, tool definition, or page of transcript.

When marginal traffic looks free, inefficient context becomes easy to ignore. The architecture still pays in latency and a harder evidence-selection problem, while any later move to usage billing exposes the volume that this month’s card charge concealed.

Cache operations account for $6,440.24, or 86.2 percent, but only cache reads represent retrieved input; cache writes create or refresh stored content. The report is an internally consistent traffic signal, not an audited provider ledger.</p></div>

## The request grows even when the question gets smaller

Anthropic’s [Messages API documentation](https://docs.anthropic.com/en/api/messages-examples) states that the interface is stateless, which means the client sends the full conversational history again with each call. The context window is the maximum material a request can contain. I use *request envelope* for the actual payload assembled for one call: system instructions, tool definitions, messages, source files, tool results, and the latest question.

Consider an agent handling a dependency upgrade in a large codebase. The first request might contain the issue, a package manifest, and a failing test. Several turns later, the envelope can also contain rejected patches, full command output, files opened during exploration, corrections from the user, and the model’s own explanations. The current question may be a single failing assertion, yet the system resends the path it took to reach that assertion.

Prompt caching can make a stable prefix cheaper and faster to process, but it cannot make stale material relevant. The model still has to find the useful evidence within the context it receives, and a long request can make that search harder. This is why cache-hit rate and context quality belong on the same dashboard rather than being treated as substitutes.

Jones’s measurement makes the scale vivid. In [the cited video](https://www.youtube.com/watch?v=Y8vAQ1FgNbM), he says his tracker recorded 3.77 billion tokens across 143 Codex threads in one working day, including 3.59 billion labeled reused input, or 95.2 percent. He also sells a context-management framework called Ringer. The cited video does not include the raw export, collection code, model versions, or full labeling rule needed to reproduce the measurement independently, so the percentage should remain attached to that day and workspace.

The direction has another production signal. In July 2025, the engineering team behind [Manus, a general-purpose AI agent, reported](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus) an average input-to-output token ratio of roughly 100 to 1 in its agent loop. Different product, different meter, similar shape: an agent often reads far more than it writes.

Cost is only half the problem. [*Lost in the Middle*](https://arxiv.org/abs/2307.03172), a 2023 study by researchers affiliated with Stanford University and the University of California, Berkeley, was published in the peer-reviewed journal *Transactions of the Association for Computational Linguistics* in 2024. It found that language-model performance often fell when relevant information sat in the middle of a long input, including for models designed to accept long contexts. The study does not prove that every long coding thread will fail. It shows that available context and usable context are different things.

I think repeated input is best understood as a state-management decision with a price attached. Context hygiene is the practice of deciding what enters the next request, why it belongs there, and when it should leave. Once that decision becomes explicit, teams can improve cost and answer quality with the same control.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A stateless API makes the client send conversational history again, so the request envelope grows as an agent works. Caching can discount a matching prefix, but it cannot make irrelevant history useful. The 95.2 percent observation is one bounded signal of a broader input-heavy pattern, not a universal rate.</p></div>

The mapping to agent context is practical. A large context window is storage capacity, not permission to fill every request. The engineering advantage comes from knowing which evidence supports the current task, how much room it consumes, and when it no longer deserves a place in the next call.

## Build the next request from an inventory

A transcript records how work unfolded, while the next model call needs a working set for what should happen now. When one object serves both jobs, a useful conversation hardens into a permanent payload.

A practical request builder can assemble the envelope from four classes of material. The stable core contains the system instructions and the smallest tool catalog needed across tasks, kept unchanged when possible so prompt caching can match it. Current evidence contains the exact issue, source spans, test failures, and reference material needed for this task. Accepted artifacts contain decisions or outputs that have already cleared the relevant check, such as the chosen migration plan or the latest passing patch. Short-lived working notes contain the active hypothesis and recent tool result, then expire quickly.

Every item outside the stable core should carry a small inventory record: `task_id`, `source`, `source_revision`, `purpose`, `token_count`, and `expires_at`. A source revision identifies the exact version from which the material came. The purpose says why the next model call needs it, while the expiry prevents a useful fact from becoming permanent background noise.

The inventory becomes a control only when the request builder enforces it. The builder must refuse an item when its purpose is missing, its source revision is stale, its expiry has passed, or the envelope would breach the task’s context budget. It should log that refusal so an engineer can see whether the policy removed waste or essential evidence. A schema can describe the expected record; the running request builder is what makes the rule real.

This changes several familiar habits. Start a new envelope when the task changes. Search before attaching an entire file, and send the exact section when that is enough. Carry a checked artifact forward while leaving discarded proposals and repeated explanations behind. Cap output to the form the next step needs, because verbose output becomes input on the following turn. Keep cacheable instructions stable, then append changing evidence after them.

[Claude Code already uses automatic compaction](https://code.claude.com/docs/en/costs), which summarizes conversation history as it approaches the context limit. That helps preserve capacity. A deliberate inventory acts earlier and under a policy the team can inspect, rather than waiting for a long thread to decide what a generated summary should retain.

My take is that context hygiene should aim for sufficient evidence, not the smallest possible prompt. A one-shot research task or a frontier reasoning problem may genuinely need a broad source set. For looping agent work, however, every retained item should be current, purposeful, and worth its effect on the next result. Only after controlling that volume does it make sense to compare cheaper model tiers.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Build each request from a stable core, current evidence, checked artifacts, and short-lived working notes. Give changing material a source, purpose, measured size, and expiry, then enforce those fields in the request builder. Context hygiene removes unneeded volume without starving the model of evidence.</p></div>

## Put a shadow meter beside the plan

The shadow meter should apply consistent accounting without pretending a counterfactual price is an invoice. Start with provider usage records. Anthropic exposes fresh input, cache creation, cache reads, and output as separate fields, but the field names and meanings are provider-specific and should be versioned in the adapter, the small translation layer that reads them.

Aggregate request records by completed task, then add the outcome and review fields. JSONL, short for JSON Lines, stores one complete JSON object per line and makes that evidence easy to inspect or rerun. Each task record needs at least the usage totals, actual allocated provider charge, review minutes, an agreed loaded review rate that includes the employment costs the organization chooses to count, material task overhead, and whether the result was accepted, meaning it passed its declared checks and entered use.

This small Python program reads those task records from standard input and prints two measures:

```python
import json
import sys

rows = [json.loads(line) for line in sys.stdin if line.strip()]
if any(type(r.get("accepted")) is not bool for r in rows):
    raise ValueError("accepted must be JSON true or false")

retrieved = sum(r.get("cache_read_input_tokens", 0) for r in rows)
input_base = sum(
    r.get("input_tokens", 0)
    + r.get("cache_creation_input_tokens", 0)
    + r.get("cache_read_input_tokens", 0)
    for r in rows
)
accepted = sum(r["accepted"] for r in rows)
total_cost = sum(
    r["provider_cost_usd"]
    + (r["review_minutes"] / 60) * r["loaded_review_rate_usd"]
    + r.get("task_overhead_usd", 0)
    for r in rows
)

print(json.dumps({
    "retrieved_input_share": retrieved / input_base if input_base else None,
    "cost_per_accepted_result_usd": total_cost / accepted if accepted else None,
}, indent=2))
```

The retrieved-input numerator contains cache reads only. Cache-creation tokens stay in the denominator because they are input being stored for the first time in that cache lifetime, not input retrieved from it. If a provider changes these semantics, preserve the raw record, update the adapter version, and break the time series rather than silently comparing unlike fields.

Keep actual spend and shadow value separate. For a flat subscription, define task classes as repeatable categories such as dependency upgrades, then allocate the fee across the classes that used it. Do not insert API list-price value into the actual-cost column. The counterfactual can live beside it as a what-if measure showing how exposed the workload would be to a different contract.

A 5,000-person company can keep the first pass small. I think a sensible pilot is to give one platform engineer a two-day setup cap, connect one provider’s existing usage export, and review one task class monthly. Record the setup hours so the meter’s own cost does not disappear. The platform team should own the usage adapter and context policy. Finance should supply contracted rates and the loaded cost of review time. Procurement should review cache pricing, retention, storage-region, export-access, usage-commitment, and schema-change terms rather than assuming they will remain favorable.

Pricing history gives this work a deadline. Technology critic [Ed Zitron reported](https://www.wheresyoured.at/the-more-you-buy-the-more-you-lose/) that heavy users of GitHub Copilot, GitHub’s AI coding assistant, consumed more than 25 times their monthly subscription fee before a move to token-based billing prompted a user revolt. His account provides a precedent, although it does not establish Anthropic’s next move.

Here is my falsifiable bet: by 31 August 2027, Anthropic, OpenAI, or GitHub will expose persistent agent memory, retained workspace state, or completed agent tasks as a separate billed unit. A public pricing page will settle the claim. If none does, the prediction fails. Once a provider carries state across sessions, token counts no longer describe the whole service, and that stored state becomes something the provider can price directly.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A shadow meter should preserve raw provider fields, keep cache creation separate from retrieval, and report actual spend beside any API-list-price scenario. Start with one owner, one task class, a fixed setup budget, and a monthly review before supplier pricing or field semantics change.</p></div>

## Price the work that survives

An accepted result is an output that passes the task’s declared automatic checks and required human review, then enters use. For the dependency upgrade, that might mean a patch with passing continuous-integration tests and reviewer approval. A plausible answer that is rejected, rewritten, or abandoned still belongs in the cost numerator because the system spent money and human time producing it.

Use this cost-per-accepted-result metric:

```text
(provider charges + loaded review cost + material task overhead)
----------------------------------------------------------------
                       accepted results
```

Loaded review cost multiplies that agreed hourly review rate by the time spent. Material task overhead can include tracing, storage, and paid tools when they are large enough to affect the decision. The point is consistency, not false precision. On a flat plan, use the allocated subscription charge in this formula and keep Patel-style API list value in a separate scenario column.

Then test the context policy rather than admiring the dashboard. Pick one repeatable task class and define acceptance before the trial begins. Randomly route eligible tasks between the current envelope and the inventory-built envelope while holding the model, prompt version, tool permissions, and retry limit fixed. Reviewers should be blind to the route when practical. Predeclare the largest acceptable drop in acceptance rate, increase in review time, and risk of missing required evidence.

Report the difference in cost per accepted result together with a confidence interval, an interval computed from sample data under a stated method and confidence level to express uncertainty about the underlying difference. If the sample is too small to support the declared decision, keep the pilot open. A shorter request that produces more retries or more review work has failed even if its token chart looks excellent.

I think this denominator repairs several bad incentives at once. A model team cannot claim victory by lowering token price while rejected work rises. A platform team cannot call a cache-hit increase a success while stale evidence lengthens review. Finance gets a number tied to retained work, and engineering keeps quality inside the decision rather than treating it as a footnote.

Patel’s 37.4-times comparison is not a forecast, and Jones’s 95.2 percent is not a benchmark. They do not need to be universal to expose the measurement gap. Flat access can hide repeated input from the user, but it cannot make retries, latency, review, and discarded output disappear. Once the denominator is work that survives review, every unnecessary token finally has somewhere to show up.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Count provider charges, human review, and material task overhead across every attempt, then divide by results that pass declared checks and enter use. Flat pricing can hide repeated input, but it cannot hide from a denominator made of work that survives review.</p></div>
