I tried to read the $7,470 screenshot as one extreme user's story. The $200 subscription changed the story.

A developer named Om Patel ran a July usage report through `claude-cost` and [posted the screenshot on X](https://x.com/om_patel5/status/2083401185172541449). It covered one user, 36,881 responses, and 6.16 billion tokens. At API list prices, it added up to $7,470.35.

The shape of the bill was stranger than its size. Cache reads and writes made up about 86 percent of the list-price total. In one day, Nate B. Jones [measured 3.77 billion tokens across 143 coding threads](https://www.youtube.com/watch?v=Y8vAQ1FgNbM). His tracker marked 3.59 billion as reused input, or 95.2 percent. That came from one workspace, so I think the right response is to measure your own reuse.

## What $7,470 of usage looks like

Nearly half of the reported total came from 5.88 billion cache reads.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Cache operations made up about 86 percent of the list-price usage. The 186-to-1 ratio points the investigation toward the request around each answer.</p></div>

A cache write stores the start of a request. A cache read reuses it at a lower price. The report showed $3,595.52 in reads, $2,841.89 in one-hour writes, and $1,015.97 in output tokens.

The blended cache-read price was about $0.61 per million tokens, between [Anthropic's published prices](https://docs.anthropic.com/en/docs/about-claude/pricing) for the models in the report. The cross-check lands on the same $3,596 line item.

Divide 6.16 billion total tokens by 33 million output tokens and the ratio is 186 to 1. I think that points a junior engineer toward the system prompt, tools, files, and conversation around each answer.

## What 37 times the plan price means

The clean calculation is $7,470.35 divided by $200, which equals 37.4.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The screenshot proves a 37.4x gap between the plan and API retail value for that month. Internal compute cost remains private, and usage limits turn large projections into ceilings.</p></div>

Hold the same usage flat for three months and the developer would pay $600 for roughly $22,411 of API list-price value. The implied discount would be about $21,811.

Stretch that behavior to one million subscribers for six months and the gap reaches $43.6 billion. It is a stress test. Most subscribers use less, [Claude plans have usage limits](https://claude.com/pricing), and API retail prices exceed the private cost of serving requests.

I don't know Anthropic's internal cost for that month. The 37.4x figure is useful as an API retail comparison and a warning that the flat plan may change.

## Context is a consumable resource

Our running example is a checkout bug where a discount code never reaches the cart total.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A model API starts each request without memory of the last one, so the agent rebuilds the context every time. Long threads become expensive because each new turn carries the old turns again.</p></div>

A token is a small unit of text, roughly three quarters of an English word. The context window is what the model can see during one request. The API is stateless, so the harness around [a Level 3 agent](/posts/2026-03-27-anatomy-level-3-agent/) rebuilds that window for the next turn.

On turn one, the agent receives the bug report, its instructions, and a tool list. It opens `pricing.py`. Turn two carries that material again, plus the first reply and file contents. By turn twenty, a small question travels with nineteen older replies and every saved tool result.

I think of this as context debt. Each stale file or failed command charges interest on later requests. The [Lost in the Middle study](https://arxiv.org/abs/2307.03172) also found that models often struggle when useful information sits inside a long context. It tested retrieval, so checkout accuracy still needs its own eval.

One failed test loop can resend the growing checkout transcript ten times.

## Put context hygiene into the workflow

A fresh thread can carry only the bug report and twelve useful lines from `pricing.py`.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A clean request contains the relevant code and preserves the accepted patch as state. Stable system instructions keep that smaller request cacheable.</p></div>

These ideas belong to [context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents). I use context hygiene for the daily, measurable part: deciding what enters each request.

LangGraph can make that boundary explicit. It is a library for arranging agent steps as a graph. A `TypedDict` declares the keys and value types in a Python dictionary. A `StateGraph` connects the steps and passes that typed state between them. Our state can hold the bug ID, accepted diff, and test result while the search transcript stays in the finished run.

This is [orchestration](/posts/welcome-to-the-orchestration-era/) at the scale of one bug. I think the first move is still closing the thread when the job ends. Harnesses can compact old turns, but a clean boundary gives the choice to the engineer.

## The flat price can disappear

GitHub Copilot has already shown how a generous subscription can meet a different meter.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Flat plans can move toward token billing when heavy usage becomes too expensive. Context hygiene lowers the exposure before that pricing change reaches your team.</p></div>

Ed Zitron reported that Copilot power users could burn [more than 25 times their monthly subscription fee](https://www.wheresyoured.at/the-more-you-buy-the-more-you-lose/) before a move to token billing triggered a user revolt. Claude is a different product with different economics, so this is a precedent rather than a prediction.

A procurement team can ask how billing units may change at renewal. An engineer can act sooner. I think products built around long, noisy threads will feel a meter change first.

## Measure cost per accepted result

Our checkout patch counts only when the discount test passes, the cart total stays correct, and a reviewer accepts the diff.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Cost per accepted result divides total agent spend by the changes the team accepts. Reuse ratio helps explain the number, while the accepted result keeps the metric tied to work that shipped.</p></div>

<div class="keymsg">
<span class="keymsg__label">The unit economics of agentic work</span>
<p class="keymsg__text">Cost per accepted result = total agent spend across every attempt ÷ accepted results.</p>
<p>For the checkout bug, include the failed patches and repeated tool calls that came before the merged fix.</p>
</div>

If each API response is one JSON object in `requests.jsonl`, `jq`, a command-line tool for working with JSON, can estimate the reuse ratio:

```bash
jq -s 'map(.usage) |
  { fresh:  (map(.input_tokens) | add),
    cached: (map(.cache_read_input_tokens // 0) | add) } |
  .cached / (.fresh + .cached)' requests.jsonl
```

Compare the ratio before and after the team starts closing finished threads. It tells you where to inspect. Cost per accepted result tells you whether the agent earned its keep.

Once several seats share a harness, the platform or FinOps team should own the measure. Track total spend, accepted changes, and reuse ratio from your own logs.

My take is that cost per accepted result is the unit economics of agentic work. It survives model and pricing changes because it stays tied to an accepted outcome.

A flat plan can hide 186 consumed tokens around each generated token. When the meter changes, cost per accepted result tells you whether the checkout fix was worth it.
