Om Patel [shared a July 2026 Claude Code usage screenshot](https://x.com/om_patel5/status/2083401185172541449). It placed $200 paid beside $7,470.35 at Anthropic's API list prices.

It tracked 36,881 responses and 6.16 billion tokens. Cache reads and writes accounted for about 86 percent of the displayed value. Cache reads reuse a stored prefix. Cache writes create one. The combined figure describes cache activity, and only the reads represent text pulled from an existing cache.

A separate case makes the pattern easier to see. Nate B. Jones [reported 3.77 billion tokens across 143 coding threads](https://www.youtube.com/watch?v=Y8vAQ1FgNbM) in one day. His tracker classified 3.59 billion, or 95.2 percent, as reused input. That percentage belongs to one instrumented workspace on one day.

I think junior engineers should learn the three meters early. Cache efficiency tells you how cheaply old text moved. Context relevance tells you whether that text helped. Cost per accepted result tells you whether the whole run earned its bill.

## The answer was the cheap part

The screenshot shared by Patel makes the request envelope visible.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The workflow processed about 186 total tokens for every output token. The 37.4x gap compares a subscription with API retail value, while Anthropic's serving cost remains undisclosed.</p></div>

The screenshot lists 5.88 billion cache-read tokens at $3,595.52. One-hour cache writes cost $2,841.89. Output cost $1,015.97.

Across the month, 6.16 billion total tokens produced about 33 million output tokens. That is roughly 186 consumed for each one generated. I think this ratio says more about the workflow than the plan price does. Generation sat at the end of a much larger system for finding, carrying, and resending context.

Dividing the cache-read cost by its volume gives about $0.61 per million tokens. That sits within [Anthropic's published cache-read rates](https://platform.claude.com/docs/en/about-claude/pricing), so the screenshot is internally consistent. This calculation cannot audit the underlying account.

The retail-value ratio is $7,470.35 divided by $200, or 37.4x. Anthropic's [plan page](https://claude.com/pricing) describes rolling and weekly limits. Its public pricing pages omit the cost and margin for serving those requests. I don't know what the reported month cost Anthropic to serve.

## One checkout bug can carry a whole sprint

A discount-code failure shows how the envelope grows around a small task.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Each checkout attempt may resend earlier messages, file contents, and tool results. In a harness that carries the full transcript, a ReAct loop keeps growing that envelope after old searches stop helping.</p></div>

Picture the bug. A shopper enters `SAVE10`. The cart accepts the code, yet the total stays unchanged.

A token is a small unit of model text. A context window is the material the model can use for one request. Anthropic's [Messages API is stateless](https://platform.claude.com/docs/en/build-with-claude/working-with-messages), which means the caller supplies the conversation history again. Other APIs and harnesses can manage state differently.

The first request may contain the system instructions, tool descriptions, and bug report. The next can include all of that plus the first answer and `pricing.py`. By turn twenty, a request for one more test can arrive with nineteen earlier replies and several tool results attached.

One common pattern is [ReAct](https://arxiv.org/abs/2210.03629), short for reasoning and acting. The model chooses a step, calls a tool, reads the result, then chooses again. For this bug, it might inspect pricing code, run the discount test, read the failure, and revise the patch. If the harness keeps the full trajectory, each cycle carries a larger transcript.

Long context can hurt the answer too. The [Lost in the Middle study](https://arxiv.org/abs/2307.03172) found weaker retrieval when useful information appeared inside long inputs. Its experiments were retrieval tasks, so your checkout agent still needs its own evaluation.

I call stale trajectory context debt. Every later turn pays interest in tokens and model attention.

## A cache hit can still carry bad context

The cache records reuse without judging whether the reused text belongs in the task.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Stable instructions and verified evidence are healthy reuse. Old search paths become context debt when they keep returning after their job has ended.</p></div>

Prompt caching makes repeated prefixes cheaper. Anthropic prices cache reads at 0.1 times the base input rate. Keeping the system prompt and tool definitions stable can earn that discount.

Cheaper stale context can still send the agent down an old path. A high cache-hit rate may lower the request price while retries and review time continue to rise. I think a strong cache metric and strong context hygiene can coexist because they answer different questions.

Modern coding harnesses can help. Claude Code documents [automatic compaction](https://code.claude.com/docs/en/costs), which summarizes conversation history near the context limit. Compaction is useful. The harness still chooses when to compress and what the summary keeps. An explicit context policy makes the choice earlier.

## Make the state smaller than the conversation

The checkout workflow gets easier to inspect once every carried item has a named field.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>LangGraph can route a small shared state through search, patch, test, and review steps. A typed shape helps developers see what moves forward, while a runtime guard blocks false acceptance.</p></div>

LangGraph is a [Python library for building workflows that branch or repeat](https://docs.langchain.com/oss/python/langgraph/graph-api). Its `StateGraph` connects steps called nodes and passes shared state between them. Edges choose which node runs next.

A [`TypedDict`](https://docs.python.org/3/library/typing.html#typing.TypedDict) is a Python type hint that names the expected keys and value types in a dictionary. It helps your editor and type checker catch mistakes. Python leaves those hints unenforced while the program runs, so acceptance still needs a real guard.

```python
from typing import TypedDict
from langgraph.graph import StateGraph

class CheckoutState(TypedDict):
    relevant_lines: str
    patch: str
    test_passed: bool
    reviewer_approved: bool

def accept(state: CheckoutState) -> str:
    if state["test_passed"] and state["reviewer_approved"]:
        return "accepted"
    raise ValueError("Acceptance requires a passing test and review")

builder = StateGraph(CheckoutState)
```

The search node writes only the relevant pricing lines into state. The patch node reads those lines. The test node records a boolean result. The review node records approval. Raw search chatter never becomes a state field, so the workflow has no reason to carry it into the next request.

This is the code-level version of [owning the agent layer](/posts/who-owns-the-agent-layer/). Every field crossing the boundary needs an engineering reason.

## Test the policy for 30 days

Change the harness in a replay before changing the production default.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Replay the same completed checkout tasks with the current context strategy and a curated one. Hold the model and acceptance rule steady, then compare paid attempts, review effort, and accepted outcomes.</p></div>

Use a bounded set of completed checkout tasks. Run each task with the current harness and with curated state. Alternate which strategy goes first. Keep the model version, token budget, acceptance criteria, prompt template, tool schema, and pricing version fixed.

Every paid attempt needs its own row:

```yaml
task_id: checkout-184
context_strategy: baseline | hygiene
model_version: string
harness_version: string
prompt_template_hash: string
tool_schema_hash: string
pricing_version: string
cache_creation_input_tokens: integer
cache_read_input_tokens: integer
prior_trajectory_tokens: integer
billed_cost: number
review_minutes: number
test_passed: boolean
reviewer_approved: boolean
```

The acceptance rule should come from a versioned spec. That connects directly to [the idea that the spec is the cognitive work](/posts/the-spec-is-the-cognitive-work/): the model can change a file, but the test and reviewer decide whether the task counts.

A simple 30-day rhythm is enough. Instrument during week one. Run paired replays during weeks two and three. Review the result in week four. A platform engineer owns the harness, the participating engineers run the tasks, and the reviewer applies the fixed rule. A FinOps partner checks the price fields.

I think a month is long enough to expose direction without pretending you have an industry benchmark. Roll back if acceptance falls. Keep testing if reviewer time consumes the saving.

## Charge every retry to the result

The checkout fix earns an outcome only after its test passes and a reviewer approves the patch.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Cost per accepted result keeps every paid attempt in the numerator. Reuse ratio helps locate context debt, while acceptance shows whether removing it improved the work.</p></div>

<div class="keymsg">
<span class="keymsg__label">The unit economics of the checkout agent</span>
<p class="keymsg__text">Cost per accepted result = billed agent cost across all attempts ÷ accepted checkout tasks.</p>
<p>Failed patches and rejected retries stay attached to the result they were trying to produce.</p>
</div>

Suppose the first attempt costs $0.80 and fails the discount test. The second costs $0.60, passes, and gets approved. The accepted result cost $1.40. Reporting only the final attempt would hide 57 percent of the paid cost.

Reviewer time belongs beside this metric. Converting minutes into dollars requires a labor rate, so keep the units separate until your team chooses one. A cheaper agent run that doubles review time may have worse economics.

I think every paid failure belongs in the numerator. The metric forces the agent bill to answer a plain question: how much did we spend to land a checkout change someone would merge?

## Give the context budget an owner

A dashboard without an owner turns into wallpaper.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Context hygiene should live in harness defaults and a monthly engineering review. As token prices fall, selecting relevant evidence becomes a harder management problem than buying cheaper input.</p></div>

Start each task ID in a clean thread. Set retry and turn limits in the harness. Require explicit carried state for the checkout workflow. This makes clean context a team default instead of a test of developer discipline.

Before renewal, ask the supplier for exportable fresh-input, cache-write, cache-read, and output fields. Ask which cache terms or usage limits can change during the contract. Document trace retention, redaction, and data residency. Name the platform owner who reviews accepted-result cost each month.

Broad context still has a place in one-shot synthesis and frontier reasoning. This argument covers looping agent work, where stale trajectory returns on later calls.

My take is that [the orchestration era](/posts/welcome-to-the-orchestration-era/) starts with deciding what enters the next step. Providers can make cached tokens cheaper. They cannot make irrelevant context useful.

A $200 plan can hide the meter. Cost per accepted result tells you what every paid loop bought.
