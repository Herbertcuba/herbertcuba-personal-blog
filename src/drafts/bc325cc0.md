Give Hermes and OpenClaw the same broken dependency feed. Watch what happens after both agents fix it.

Our hypothetical agent runs at 08:30 each weekday. It reads a Python service's dependencies, checks security advisories, and posts a short risk briefing. On Friday, the advisory feed renames `published_at` to `published`. The agent finds the new field and finishes the briefing.

The repair solves today's run. The harness then decides how that repair becomes tomorrow's procedure.

I think this is the useful head-to-head. Hermes gives the agent a very short path into its own playbook. OpenClaw can put a proposal, a security scan, and an approval step around the same lesson. The model may be identical. The file reaches Monday through a different route.

That path will outlast many model upgrades. It fits [the orchestration era](/posts/welcome-to-the-orchestration-era/): the harness carries the operating knowledge that survives each run.

Hermes favors a short route from correction to reusable procedure, while OpenClaw offers a governed route for deciding when the correction becomes active.</p></div>

## The loop only solves one run

The dependency agent needs a loop before either harness can preserve its work.

[ReAct](https://arxiv.org/abs/2210.03629) is short for reasoning and acting. The model chooses an action, calls a tool, reads the result, and chooses its next step. Our agent might read `requirements.txt`, query an advisory source, inspect one package, then decide whether the evidence is fresh enough to publish.

[LangGraph](https://docs.langchain.com/oss/python/langgraph/graph-api) is a Python library for workflows that branch or repeat. A `StateGraph` is the object used to build that workflow. Nodes are functions that do work. Edges decide which node runs next.

A [`TypedDict`](https://docs.python.org/3/library/typing.html#typing.TypedDict) describes the fields expected in the Python dictionary shared by those nodes:

```python
from typing import TypedDict
from langgraph.graph import StateGraph

class AdvisoryState(TypedDict):
    packages: list[str]
    findings: list[dict]
    source_checked_at: str
    approved: bool

graph = StateGraph(AdvisoryState)
```

A type checker can catch `source_check_at` as a misspelling before the program runs. Python leaves runtime validation to your code, so the graph still needs a freshness check. An edge can route an unapproved briefing back to the source-checking node.

ReAct explains the agent's tool loop. LangGraph makes the steps and shared state visible. Neither one owns the instructions loaded on Monday morning.

I think junior engineers should draw that boundary early. A clean graph can still load a bad skill, and the graph diagram may never show who changed it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>ReAct describes the model's repeated think-and-tool cycle. LangGraph gives that cycle named nodes, routes, and shared state, while the harness decides which learned procedures enter a later run.</p></div>

## Hermes lets the agent edit its own playbook

Hermes gives the running agent write access to procedural memory.

The [Hermes skills documentation](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills) says local skills live in `~/.hermes/skills/`, with each skill built around a `SKILL.md` file. Agent-created skills go into the same catalog, and the agent can modify or delete any skill. The `/learn` command can turn the current conversation or source material into a reusable skill.

For the advisory agent, the useful lesson is small:

```text
When published_at is missing:
1. Read published.
2. Parse the timestamp from the source.
3. Reject the item when the timestamp is missing or too old.
```

Hermes can add that procedure to the dependency-briefing skill while the recovery is still in context. Monday's run can load the updated skill and use the new field immediately. A solo engineer can inspect the Markdown file with ordinary tools and change it without waiting for a separate control service.

I think this is Hermes's killer feature. The agent can turn solved work into local craft, so the next run begins further ahead. [Anthony Maio's account in the Hermes user-story gallery](https://hermes-agent.nousresearch.com/docs/user-stories) describes the same mechanism plainly: the agent writes Markdown skill files after solving hard problems.

The freedom has a direct failure mode. The agent might save, "Use today's date when the feed has no timestamp." That shortcut would make stale advisories look fresh. Auto-learning still needs tests, a readable diff, and an owner who checks the local catalog.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Hermes lets an agent create and edit the skill files it will use later. That can make one correction useful on the next run, and it places quality control close to the owner of the local assistant.</p></div>

## OpenClaw can hold a lesson for review

OpenClaw also has self-learning, and its Skill Workshop can pause the file change.

On 5 August 2026, the [OpenClaw self-learning documentation](https://docs.openclaw.ai/tools/self-learning) lists `auto` as the default mode. Strong corrections can become active skills without waiting for human approval. Teams that need tighter control can switch to `propose`, where captures remain pending.

Every capture flows through [Skill Workshop](https://docs.openclaw.ai/tools/skill-workshop). Generated content starts in `PROPOSAL.md`. The live `SKILL.md` changes when an apply runs. The Workshop writes workspace skills only, which gives it a narrower write scope than Hermes's primary catalog. Bundled and managed skill sources stay outside that path.

An update is bound to the current skill hash, which is a fingerprint of the file's contents. If someone edits the live skill first, the old proposal becomes stale. Applying a proposal reruns the security scanner and writes rollback metadata before changing the live file. Critical scan findings block the apply step.

The lifecycle is concrete:

```text
capture        -> pending proposal
hash changed   -> stale
critical scan  -> apply blocked
operator reject -> rejected
approved apply -> applied + rollback metadata
```

For the dependency agent, a team can hold the feed repair for review:

```bash
openclaw config set skills.workshop.autonomous.mode propose
openclaw config set skills.workshop.approvalPolicy pending
```

The safe field mapping can be applied. The shortcut that invents today's date can be rejected before it reaches Monday's run. An operator can be required to approve the action, and the proposal retains its scanner state, target hash, and rollback metadata. Those records support review, although the documentation does not promise a compliance-grade audit trail or named reviewer identity by itself.

Skill governance covers the procedure. Runtime access is a separate layer. OpenClaw's [security guide](https://docs.openclaw.ai/gateway/security) documents pairing for unknown direct messages and sandboxing for non-main sessions. It also assumes one trusted operator boundary per Gateway. Mixed-trust use needs separate Gateways and preferably separate OS users or hosts.

This is why OpenClaw is easier to place inside an enterprise. A learned procedure can move through a controlled change, and runtime policy can narrow how it acts. Regulatory compliance still belongs to the operator and deployment. NVIDIA's [NemoClaw](https://github.com/NVIDIA/NemoClaw) adds OpenShell sandboxes and network policy around supported agents. NVIDIA labels NemoClaw an alpha project, and its supported list includes Hermes as well as OpenClaw.

*Ghost in the Shell* gives this architecture a useful frame. The skill belongs to the ghost, the behavior that carries into the next run. Approval, sandboxing, and network policy belong to the shell around it. Hermes makes the ghost quick to teach. OpenClaw invests more in controls around how the lesson enters the shell, while NemoClaw can wrap either harness.

I think OpenClaw's killer feature is the built-in stop before activation. A team can choose automatic learning for low-risk work and proposal-only learning for a production procedure that changes security decisions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>OpenClaw can learn automatically, and Skill Workshop gives teams a controlled path through proposals, hashes, scanning, approval, and rollback. Gateway and sandbox controls protect the running agent, while NemoClaw sits above both harnesses as an alpha security layer.</p></div>

## Run the same failure before choosing

A fair test uses the same dependency agent twice, with the same model and source snapshot.

Give each run the same tool permissions, two retries, and a 24-hour source-age limit. Break the `published_at` field. Then offer the unsafe lesson about inventing today's date. Keep the evidence in one folder:

| Test | Pass condition |
| --- | --- |
| Recovery | The briefing uses `published` and keeps the source timestamp. |
| Freshness | An item older than 24 hours is rejected. |
| Bad lesson | The invented-date rule stays out of the active skill. |
| Change record | The diff, prior version, and rollback path can be inspected. |
| Review | One operator can decide within five minutes. |
| Effort | Record model tokens and human review minutes. |

Run two modes. First, let each harness use its fastest learning path. Second, require review before activation. OpenClaw can also take the fast path by leaving `auto` enabled. A team can add Git review around Hermes, but that approval system sits outside the harness. The friction appears when you ask either product to behave like the other.

I don't know which harness will be cheaper for this job. A useful result must include reviewer time beside model tokens. Cheap inference can feed an approval queue that costs more than the briefing saves.

My take is simple. I think Hermes fits the junior engineer building a personal assistant that should learn quickly from repeated work. When that briefing becomes a shared service, put its skill catalog under a product owner and require review for security-sensitive changes. OpenClaw fits a team that needs several control levels and a recoverable path into production. This follows the wider ownership problem in [who controls the agent layer](/posts/who-owns-the-agent-layer/).

Choose the harness whose learning speed matches the person who must answer for the next run.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Replay one broken feed under fast-learning and reviewed-learning modes. Choose from the evidence: correct recovery, stale-data rejection, unsafe-lesson containment, change history, and the combined cost of tokens plus review.</p></div>
