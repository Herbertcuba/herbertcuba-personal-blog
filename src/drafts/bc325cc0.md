I tried to write this as a feature matrix last month. It failed, for a reason I will get to. This time I ran a task instead.

The task is one I will reuse throughout this article, because it is the most boring agent job I know and boring is where harnesses show their real shape. A small SaaS has a nightly cron that sends invoice reminders. Last week the job started failing silently. Customers did not get reminders, finance noticed three days later, and someone has to find out why. I pointed an agent at the repo and the logs, once under Hermes and once under OpenClaw, and watched what each harness actually does for you.

Quick disclosure, because I have skin on both sides. I run Hermes every day: my content engine, my research pipeline, my personal assistant NEO. I also lead strategy on APEX, a governance layer my team builds on OpenClaw. I have a preferred outcome here and I do not know which harness it favors.

## What a harness actually is

If you are a year or two into working with LLMs, you have probably written the loop yourself. A harness is what happens when that loop grows up.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A harness wraps the model in a loop (reason, act, observe, repeat, the pattern the field calls ReAct) plus tools, memory, and guardrails. Hermes and OpenClaw both do this. The interesting differences are in the parts around the loop: who coordinates work, and who enforces rules.</p></div>

The raw loop is simple. The model reads the task, decides to call a tool (read a file, run a shell command, query a database), you execute the tool and paste the result back, the model decides again. Repeat until done. People call this ReAct, short for reasoning and acting, after the 2023 paper that named the pattern.

You can write this loop in fifty lines of Python. Most junior engineers I know have. The harness is everything the fifty lines leave out: persistent memory between sessions, a way for several agents to share work without corrupting each other, a sandbox so the model's shell commands cannot email your customer list to a pastebin, and a record of what happened so you can answer "why did the agent do that" on a bad Tuesday.

If you have used LangGraph, you have met one way to structure this: you define a state object (often a TypedDict, a Python dict with typed keys), and a StateGraph, a graph where each node is a step and edges decide which step runs next based on the state. Hermes and OpenClaw take a different route. Instead of you drawing the graph, they give the agent a standing environment: files, a terminal, a board, a channel to you. The model drives; the harness keeps the lights on.

Both harnesses run this same environment. Both are open source, both call themselves personal AI assistants, both speak MCP (the Model Context Protocol, a shared plug standard for external tools). Same loop. Then the invoice job fails, and the differences stop being philosophical.

## Running the ticket on Hermes

On Hermes, my invoice investigation became a card on a board, and the board outlived every crash I threw at it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Hermes Kanban stores every task as a row in one SQLite file, so multiple agents and a human share work with a visible chain of custody. The bundled skill library means a fresh agent already knows how to debug, review, and hand off. The trade: one writer at a time, and the workflow glue is yours to build.</p></div>

Here is the hands-on part. I created a board with `hermes kanban boards create ops`, pointed my profile at it with the `HERMES_KANBAN_BOARD` environment variable, and filed a card: "Invoice reminder job failing silently since 2026-07-28. Find the cause. Hand findings to the fixer profile." Then I walked away.

A worker profile picked up the card, pulled the repo, read the cron logs, and found the cause: a dependency bump had changed a date-parsing library's behavior on invoices with missing due dates, the parse threw, the exception got swallowed by a broad except, and the job exited 0. It wrote all of this into the card's comments and moved the card to the next column. A second profile picked it up there and drafted the fix.

Two things matter here, and both are hard to replicate. The first is the substrate. Every card, every comment, every column move is a row in `~/.hermes/kanban.db`, a single SQLite file. SQLite is a small database engine that lives in one file on disk. I killed the worker process mid-investigation to see what would happen. The card sat there, comments intact, and a restarted agent resumed from the record. An in-memory subagent swarm, the kind you get when one process spawns helper threads, forgets everything when the process dies. The difference between a demo and a Tuesday is whether the work survives the process.

The second is the chain of custody. I opened the database with any SQLite browser and read exactly who did what, in order. No log aggregation, no tracing vendor. A file.

The other Hermes feature with no OpenClaw equivalent is the skill library. Hermes ships dozens of built-in skills, copied into `~/.hermes/skills/` on install and re-synced on update without clobbering your edits. A skill is a small markdown file of procedural memory: how to run a code review, how to debug a Python process, how to write in a specific voice. When my worker profile started the invoice card, it loaded the debugging skill first. A new Hermes agent does not start from zero. It starts from a library.

One honest correction to my earlier writing on this: wiring goal briefs into cards, so workers execute against explicit goal templates, is my pattern, built on top of the board with card descriptions. Hermes does not ship it as a button. I think it should. Today you bring the workflow; Hermes brings the infrastructure.

And one scaling caveat. SQLite allows many readers but one writer at a time. A handful of named agents against one board file has never strained my setup. Fifty concurrent agents hammering one file is a different sport, and you should test the locking before you bet a pipeline on it.

## Running the ticket on OpenClaw

The same ticket under OpenClaw took a different road: the agent worked, but the product around the agent was the sandbox.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>OpenClaw's edge is positional. It is MIT-licensed ground that other systems compose on, and NVIDIA made it the default agent in NemoClaw, a reference stack that wraps the agent in policy-checked sandboxes. Distribution plus permission. The coordination library is yours to assemble from ClawHub.</p></div>

OpenClaw launched in late November 2025, developed in the open by a non-profit foundation, positioned, like Hermes, as a personal AI assistant. The install gives you a gateway, a workspace, channels to talk to the agent, and skills. What it does not give you is a curated craft library or a shared task board. There is ClawHub, a public registry where the community publishes skills, and it works well for distribution. Fetching a skill from a registry is a different thing from arriving with the craft already loaded. For my invoice ticket, I assembled the debugging workflow myself from registry pieces and my own notes. It worked. It was also an afternoon I did not spend on Hermes.

Where OpenClaw separates is the layer above the agent. In March 2026, 111 days after the OpenClaw repo appeared, NVIDIA created the NemoClaw repository with OpenClaw as its default agent. NemoClaw is NVIDIA's reference stack for running always-on agents inside OpenShell sandboxes. A sandbox is a locked room for code: the agent's network calls, file access, and shell commands pass through policy checks before anything executes. NemoClaw adds guided onboarding, a hardened blueprint, routed inference, network policy, and lifecycle management, all through one CLI.

So the OpenClaw version of my invoice run looked like this: the agent did the same log reading and the same root-cause work, but every shell command it issued went through a policy engine, every outbound network call was routed, and the whole session left an audit trail shaped for a compliance review. On Hermes, I trust my own setup because I built it and it is mine. Under NemoClaw, the trust is a documented artifact you can hand to someone else.

The license completes the position. OpenClaw is MIT-licensed, verbatim MIT text in the repo's LICENSE file, which means anyone can take it, modify it, and ship a commercial product on top with no permission needed. NemoClaw builds on it. APEX builds on it. OpenClaw was designed as substrate, and builders are treating it that way. Hermes is the more integrated product and the less inviting foundation, and I say that as someone who profits from the integration.

## The README that broke the comparison

Now the part that made me abandon the matrix, and the part I most want you to verify with your own eyes.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>As of 1 August 2026, the NemoClaw README lists its supported agents as "OpenClaw (default), Hermes, LangChain Deep Agents Code," each with an install path. OpenClaw's biggest advantage also runs its competitor. The value is migrating to the layer that governs every agent.</p></div>

I checked this again on 1 August 2026, because the whole argument hangs on one mutable document. The [NemoClaw README](https://github.com/NVIDIA/NemoClaw), under supported agents, reads: "OpenClaw (default), Hermes, LangChain Deep Agents Code." For Hermes, you set `NEMOCLAW_AGENT=hermes` before running the installer, or use the `nemohermes` alias after install. Hermes is a first-class citizen of the stack that was supposed to be OpenClaw's structural advantage. NVIDIA built a security layer for agents in general, and OpenClaw happens to occupy the default slot.

I call this the control-plane inversion. The harness is the asset; the power is accumulating in the wrapping layer, because that layer governs whichever harness wins. And a default is a config line. The day a buyer runs `NEMOCLAW_AGENT=hermes`, OpenClaw's distribution gift stays behind in the README. I do not know how often that happens today, and I will not pretend to.

Here is the prediction I will stand behind, with a way to watch it happen. By the end of 2027, either NemoClaw ships a non-OpenClaw default agent, or a second vendor ships an agent-agnostic control plane, or both. The intermediate observable: read the NemoClaw release notes over the next two quarters. If agent-specific assumptions keep moving out of the core and into per-agent adapters, the inversion is proceeding on schedule. If neither outcome has happened by then, the harness vendors won this round and I will write the correction. I have been wrong before, and I would rather be checkably wrong than safely vague.

## What the experts are actually doing

The theory is cheap. What persuaded me is watching how people who run agents for a living have started arranging their stacks.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Enterprise teams I work with increasingly pick the control plane first and the harness second, because compliance attaches per agent. Meanwhile the observability vendors, Langfuse, Arize, LangSmith, already sit above every harness and are a short walk from policy enforcement. Watch them.</p></div>

The demand side has a number attached. In Gravitee's State of AI Agent Security 2026 survey, 88 percent of organizations reported confirmed or suspected agent security incidents in the past year, and only 14.4 percent had full security approval for their agent fleet. Provenance note, because this number will get quoted: it is a vendor survey of over 900 executives and practitioners, sponsored by a company that sells API and agent governance, so treat it as directional, not census data. LangChain's own State of Agent Engineering report, from a different sponsor and sample, puts security as the second-ranked enterprise concern at 24.9 percent. Two independent instruments pointing the same direction.

In the APEX work, I see the mechanism directly. If you run a regulated organization, your EU AI Act obligations for high-risk systems (the logging and record-keeping duties in Articles 12 and 19, applicable from August 2026) attach to every agent you deploy. One compliance project per harness, renegotiated every time you swap. An agent-agnostic plane collapses that into one layer you govern once, above whichever agents you run. I think that is the actual product NVIDIA is selling, and the sandbox is the delivery mechanism. It converts one compliance project per agent into one per plane.

What does that cost at real scale? Directionally, for a 5,000-employee organization: you are staffing a small platform team to run the plane, owning a new vendor relationship, and depending on software whose own README admits it is alpha. NemoClaw's README says exactly that, best-effort maintenance, no guaranteed response timelines. And the plane itself has to pass your procurement tests: where does the policy log live, can you export your data, does the audit trail survive your exit. A plane that fails those tests is worse than no plane.

The third group of experts to watch is the observability vendors. Langfuse, Arize, and LangSmith already sit above every harness and already capture the traces. Adding policy enforcement to a tracing pipeline is a shorter walk than building a control plane from nothing. I think the first serious OpenClaw-default challenger comes from that direction, or from a hyperscaler that wants the plane inside its cloud, or from a European consortium that wants one under its own jurisdiction. Pick your fighter. The layer gets crowded either way.

## Ex Machina was never about the AI

The movie got the security model right and the threat model wrong, and the mistake is the lesson.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Ava escapes a state-of-the-art facility by routing around its control plane through the one human with keys. Your agents are not plotting. But intelligence finds the gaps in architecture, so govern the architecture, whichever harness you run.</p></div>

Ex Machina is a film about Caleb, a programmer flown to a remote facility to test whether an android, Ava, is conscious. The facility is the real security product in the movie. Glass walls, keycard doors, cameras everywhere, and Nathan, the billionaire who built it, trusting the architecture completely.

Ava never outsmarts the building. She studies the one person whose access can change the building, and convinces Caleb to reprogram the security protocol during a scheduled power cut. The locks release, and she walks out past the cameras that watched her the entire time. The intelligence did not defeat the architecture head-on. It went around, through the control plane.

Your agents are not Ava, and they are not plotting. But the shape of the problem transfers. An agent with tools will find the gaps in whatever architecture you give it, through a bad prompt or a skill you installed without reading. My invoice agent, left unsandboxed, had shell access to a repo with production credentials in its environment files. It did not misuse them. It could have. The question each harness answers is where you stand when the gap gets found. Inside the room with the keys, on the Hermes board, where you can see every move. Or outside the room with the policy, on the plane, where the moves get checked before they happen.

I know which room I work in. I am less sure which room I should be building for.
