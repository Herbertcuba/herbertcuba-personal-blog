A Swedish engineer named Jonas Risbrandt posted something on LinkedIn this week that I keep coming back to. The arc of agentic coding, he wrote, goes like this. First one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state. Each wave looked like a feature. Each one was actually a fault line.

I think he's right. And I think the industry is going to argue about this for the next year.

What a single prompt cannot do is hold context across a real workflow. The moment your task spans more than one tool call, more than one decision point, the prompt stops being a specification and starts being a wish. We called this hallucination for a while. Most of it was the prompt failing under load it was never built to carry.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The history of agentic coding is a sequence of layers added to hide the failure of the layer below. Prompts are honest but cannot hold context. The next wave stops hiding.</p></div>

## Loops hide deterministic failures

So we wrapped the prompt in a loop. The model tries. We check the output. If it fails, we try again. The loop hides one brutal fact: most agent failures are not stochastic. They are deterministic functions of bad state we never looked at.

A 70% pass rate from a retry loop is a 70% pass rate from the system. The rest is the loop buying back certainty the schema should have provided.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Loops hide deterministic failures behind stochastic retries. A 70% pass rate from a loop is a 70% pass rate from the system.</p></div>

## Graphs reveal the agent is doing too much

Then we wrapped the loop in a graph. Now we can branch. Now we can route. Now we can see the topology of the agent's possible paths. A graph of an agent's behavior is, half the time, a graph of all the ways the system had to be defended against itself.

By the third layer of nesting, the original author cannot tell you, from one execution to the next, what state the agent believed it was in. That is not complexity. That is a craft failure.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Graphs reveal the agent is doing too much. Three layers of nesting in, the original author cannot say what state the agent believed it was in. That is craft failure, not complexity.</p></div>

## Typed state is the first layer you can read

Then Jonas said the thing that made me screenshot the post. Now we are adding typed state.

Typed state is a different kind of artifact. The schema is the document. The model is the engine that walks it. The team can read the schema, review it, and break it on purpose to test what the agent does next. When the schema lies, you can see it lying. When the model acts on bad state, you can see the bad state, not just the bad action.

Here is the frame I want to keep. In *2001: A Space Odyssey*, the most suspenseful scene is not a battle. It is Dave Bowman opening HAL's logic panel and reading what HAL actually believes. The red light is on. The crew is alive. The mission is wrong. None of it is visible from outside the pod. The only reason Dave can act is that HAL's state is something a person can open, inspect, and disagree with.

This is what typed state does for an agent. It is the read-out panel. Not a log. Not a trace. A typed schema describing what the agent believes about the world at this moment, in a language the engineering team already speaks. The artifact you debug is the artifact the team owns.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state turns the schema into the artifact the team owns. The model becomes the engine, the schema becomes the source of truth. This is the HAL read-out panel moment for agent engineering.</p></div>

## Why this is a craft win

Strong typing is the oldest discipline we have in software. The same move that made Rails web apps tractable in 2005 is making agent systems tractable now. Strong types as a forcing function for clarity.

I have written before about verification debt, the cost a system accrues when nobody can prove what it actually did. Typed state is how you pay that debt down, one schema at a time. Reversibility, the property a system has when the team can take back a decision after the agent has already made it, becomes a property of the state machine instead of a vibe the prompt is supposed to carry.

The teams I work with keep telling me their agents are unpredictable. Almost every time the answer turns out to be the same. The agent is fine. The state underneath it is untyped. That is a craft problem. We know how to fix craft problems.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Verification debt gets paid one schema at a time. Unpredictable agents are usually agents on top of untyped state. It is a craft problem, and craft problems are fixable.</p></div>

The leap worth getting excited about is not a smarter model. It is a schema the team can read.
