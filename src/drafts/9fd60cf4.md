I tried to reduce agent architecture to the four concepts I wish someone had shown me first: prompt, loop, graph, and typed state.

They belong to one stack. The prompt instructs the model. The loop lets it act repeatedly. The graph controls the route. Typed state defines the data passed along that route.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>An agent workflow has four layers: instruction, repetition, routing, and shared data. Each gives the engineer a different kind of control.</p></div>

## 1. Prompt: the instruction

A prompt is the text sent to a model. It usually contains the role, task, context, tools, constraints, and desired output.

```python
prompt = """
You are a research assistant with a search tool.
Answer the question using cited sources.
Return JSON with: answer, sources.
"""

response = model.run(prompt, question, tools=[search])
```

The prompt matters because it shapes one model call. Clear instructions improve tool selection and output. But prose can only request behavior. The program must still check whether the model searched, returned valid JSON, or failed.

My take is simple: a prompt is an instruction, not an execution engine.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A prompt tells the model what to do during one call. The surrounding program enforces what actually happened.</p></div>

## 2. Loop: repeated action

A loop calls the model more than once. After each call, the program runs the requested tool, gives the result back to the model, and asks for the next action.

```python
messages = [prompt, question]

for step in range(8):
    reply = model.run(messages, tools=[search])
    if reply.is_final:
        return reply.text

    result = run_tool(reply.tool_call)
    messages.extend([reply, result])

raise AgentError("Step limit reached")
```

This is the smallest useful agent. It can search, inspect the result, adjust the query, and answer. The step limit is important. Without one, a confused agent can continue spending time and money while making no progress.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A loop lets the model act, observe, and act again. Limits keep that repetition under engineering control.</p></div>

## 3. Graph: explicit routes

A graph turns workflow steps into named nodes connected by edges. A node may plan, search, write, review, or request approval. Routing rules choose which node runs next.

```python
def route(state):
    if state.status == "needs_search":
        return "search"
    if state.status == "needs_review":
        return "review"
    if state.status == "approved":
        return "done"
    return "failed"
```

Graphs become useful when a loop fills with conditionals. They make branches visible and give failures distinct recovery paths. A failed search can retry, while a rejected draft can return to writing.

The graph owns the route. Its nodes still need a shared language for the work moving between them.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A graph makes the possible routes explicit. Use one when the workflow branches, pauses for review, or needs different recovery paths.</p></div>

## 4. Typed state: the shared contract

Typed state is a declared schema for the data carried through the loop or graph. It names each field and limits which values are valid.

```python
from typing import Literal
from pydantic import BaseModel, Field

class ResearchState(BaseModel):
    question: str
    status: Literal["planning", "searching", "writing", "done", "failed"]
    sources: list[str] = Field(default_factory=list)
    draft: str | None = None
    error: str | None = None
```

Now every node reads and writes the same contract. The writing node can reject state without sources. A dashboard can show where the run stopped. A test can pass known state into the router and inspect the next step. The program can save the state and resume after a restart.

*The Martian* gives us the right metaphor. Mark Watney survives by making food, water, time, and equipment explicit enough to calculate. Typed state is the mission board for an agent. Critical context gets named fields instead of hiding inside a long conversation transcript.

A schema can prove that `sources` is a list of strings. Truth and relevance still require validation, tests, and human judgment.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state is the shared data contract between steps. It makes an agent run inspectable and recoverable, while validation remains responsible for data quality.</p></div>

## Build the layers in this order

Start with a prompt. Add a loop when the task needs several actions. Introduce a graph when the route branches. Define typed state when multiple steps must share progress reliably.

I think smarter models improve decisions inside the workflow. Typed state improves the system that surrounds those decisions. When a run fails, the team can see where it stopped, what it knew, and which transition comes next.

That legibility is the leap.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The four layers build from instruction to repetition, routing, and shared data. Typed state turns an opaque agent run into an engineering system a team can inspect and improve.</p></div>
