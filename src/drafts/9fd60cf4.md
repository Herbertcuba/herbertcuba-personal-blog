I tried to reduce agent architecture to the four concepts I wish someone had shown me before I wrote my first one: prompt, loop, graph, and typed state. Each layer buys a different kind of control, and the order matters.

If you have never built an agent, read this top to bottom. By the end you should be able to look at any framework on GitHub and see how it splits these four jobs.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>An agent workflow has four layers: instruction, repetition, routing, and shared data. Add each one only when the layer below it stops being enough.</p></div>

## 1. Prompt: the instruction you send

A **prompt** is the text you send to a model. It usually packs four things into one message: who the model should act as, what the task is, what tools it can call, and how the answer should look.

```python
prompt = """
You are a research assistant with access to a search tool.
Answer the user's question using cited sources.
Return JSON with two fields: answer (string), sources (list of URLs).
"""

reply = model.run(prompt, user_question, tools=[search])
```

The prompt shapes one model call. Clear instructions improve tool selection and output format. Prose can only request behavior; it cannot enforce it. The program around the prompt still has to check whether the model searched, whether the JSON parsed, and what to do when the answer is wrong.

My take: a prompt is an instruction. It is not an execution engine. The moment you need the agent to do more than one thing in a row, you have left the prompt behind.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A prompt tells the model what to do in one call. The surrounding program enforces what really happened.</p></div>

## 2. Loop: let the model act more than once

A **loop** calls the model repeatedly. After each call, the program runs the tool the model asked for, hands the result back, and asks for the next action. The agent keeps going until it returns a final answer or hits a step limit.

```python
messages = [system_prompt, user_question]

for step in range(8):
    reply = model.run(messages, tools=[search])
    if reply.is_final:
        return reply.text

    result = run_tool(reply.tool_call)
    messages.extend([reply, result])

raise AgentError("Step limit reached")
```

This is the smallest useful agent. It can search, inspect the result, adjust the query, and answer. Three details matter more than they look:

- The **step limit** keeps a confused agent from spending the night buying API calls.
- The **message list** is the only thing the model sees. Everything it "knows" lives there.
- The **tool dispatch** is regular Python. You can log it, test it, swap it.

I think this is the layer most tutorials skip. They show you a single clever prompt and stop. The moment you wrap that prompt in a loop with a step limit and observable messages, you have crossed from demo to agent.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A loop turns one model call into an agent. Step limits and a readable message history keep the repetition under engineering control.</p></div>

## 3. Graph: name the routes between steps

A **graph** turns the workflow into named nodes connected by edges. A node may plan, search, write, review, or ask for approval. A router decides which node runs next based on the current state.

```python
def route(state):
    if state.status == "needs_search":
        return "search"
    if state.status == "needs_review":
        return "review"
    if state.status == "approved":
        return "done"
    return "failed"
```

Graphs earn their keep when a loop fills with `if` statements. Once you have a node that retries a failed search, a node that rewrites a rejected draft, and a human-approval step in the middle, the loop stops being readable. A graph makes those branches visible and gives failures distinct recovery paths. I think this is also where most teams overshoot first. They reach for a graph on day one, when a twenty-line loop would still be fine.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A graph makes the routes explicit. Reach for one when the workflow branches, pauses for review, or needs different recovery paths.</p></div>

## 4. Typed state: the contract between steps

**Typed state** is a declared schema for the data carried through the loop or graph. Every field has a name and a type. Every node reads and writes the same contract.

```python
from typing import Literal
from pydantic import BaseModel, Field

class ResearchState(BaseModel):
    question: str
    status: Literal["planning", "searching", "writing", "done", "failed"]
    sources: list[str] = Field(default_factory=list)
    draft: str | None = None
    error: str | None = None
```

The schema can prove that `sources` is a list of strings and that `status` is one of five allowed values. Truth and relevance still need tests and human judgment. What the schema buys you is everything else: the writing node can reject state without sources, a dashboard can show where the run stopped, a test can pass known state into the router and inspect the next step, and the program can save and resume the run after a restart.

*Alien* gives the right metaphor. The Nostromo crew survives by tracking oxygen and hull integrity as named numbers on a screen instead of vibes. Typed state is the mission board for an agent. Critical context gets named fields. Without them it hides inside a long conversation transcript, and I think that hiding is where most agent bugs are born.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state is the shared data contract between steps. It makes a run inspectable and recoverable. Validation still owns data quality.</p></div>

## Build the layers in this order

Start with a prompt. Add a loop when the task needs more than one action. Introduce a graph when the route starts branching. Define typed state when several steps must share progress reliably. I don't know a better order, and I've tried to skip steps enough times to trust this one.

I think smarter models improve decisions inside the workflow. Typed state improves the system around them. When a run fails, the team can see where it stopped, what it knew, and which transition comes next. That legibility is the leap.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The four layers build on each other. Typed state turns an opaque agent run into an engineering system a team can inspect and improve.</p></div>
