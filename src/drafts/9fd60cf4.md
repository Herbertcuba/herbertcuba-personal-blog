Jonas Risbrandt recently described agentic coding as four layers: prompt, loop, graph, and typed state. I think this is a useful map for anyone building an agent for the first time.

These layers are parts of one system. The prompt tells the model what to do. The loop lets it act more than once. The graph controls which step runs next. Typed state defines the data moving between those steps.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>An agent workflow can be understood as four layers: prompt, loop, graph, and typed state. Each layer adds a form of control that the previous layer cannot enforce on its own.</p></div>

## 1. Prompt: the instruction for one model call

A prompt is the text sent to a model: its role, the task, relevant context, tool descriptions, constraints, and examples. It shapes what the model does during one call.

```python
prompt = """
You are a research assistant with a search tool.
Answer the user's question using cited sources.
Return JSON with two fields: answer and sources.
If the evidence is weak, say so.
"""

response = model.run(prompt, user_question, tools=[search])
```

Prompts matter because model behavior begins there. Clear instructions improve tool selection and output shape. But prose can only request a workflow. It cannot prove that a search ran, preserve progress after a crash, or decide what the program should do with malformed output.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A prompt gives the model its instructions for one call. It can describe a workflow, while the surrounding program must enforce and track that workflow.</p></div>

## 2. Loop: repeated action and observation

A loop is the runtime that calls the model repeatedly. After each call, it executes any requested tool, adds the result to the conversation, and lets the model choose the next action. The loop stops when the model returns a final answer or reaches a limit.

```python
messages = [system_prompt, user_question]

for step in range(8):
    reply = model.run(messages, tools=[search])
    if reply.is_final:
        return reply.text

    result = run_tool(reply.tool_call)
    messages.extend([reply, result])

raise AgentError("Step limit reached")
```

This is what gives a simple agent persistence across several actions. It can search, read the result, refine the query, and answer. My take is that every loop needs a step limit and a visible failure state. Otherwise a confused agent can keep spending time and money without getting closer to done.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A loop lets the model act, observe the result, and act again. Limits and explicit failure states keep repeated calls under engineering control.</p></div>

## 3. Graph: explicit paths through the workflow

A graph turns workflow steps into named nodes connected by edges. A node might plan, search, write, review, or ask a human for approval. Routing rules choose the next node from the current result.

```python
def route(state):
    if state.status == "needs_search":
        return "search"
    if state.status == "needs_review":
        return "review"
    if state.status == "approved":
        return "done"
    return "failed"
```

Graphs matter when one loop accumulates too many conditionals. They make branches visible, allow checkpoints, and give different failures different recovery paths. The graph owns the route. The nodes still need shared data so that a search result produced in one step can be understood by the writer in another.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A graph makes the possible workflow paths explicit. It becomes useful when the agent needs branching, checkpoints, review steps, or different recovery routes.</p></div>

## 4. Typed state: the contract between steps

Typed state is a declared schema for the data carried through the loop or graph. It names the fields, their allowed shapes, and the current stage of the workflow.

```python
from typing import Literal
from pydantic import BaseModel, Field

class ResearchState(BaseModel):
    question: str
    status: Literal["planning", "searching", "writing", "done", "failed"]
    queries: list[str] = Field(default_factory=list)
    sources: list[str] = Field(default_factory=list)
    draft: str | None = None
    error: str | None = None
```

Now every node reads and writes the same contract. A writing node can reject state with no sources. A dashboard can show where the run stopped. A test can feed the review node a known state and check its route. The system can also save that state and resume after a restart.

*The Martian* offers a useful analogy. Mark Watney survives by making food, water, time, and equipment explicit enough to calculate. An agent needs the same kind of mission board. Typed state gives every part of the workflow named fields instead of leaving critical context buried in a conversation transcript.

Types still have limits. A schema can prove that `sources` is a list of strings. It cannot prove those sources are true or relevant. Tests, validation, and human judgment still carry that responsibility.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state defines the data contract shared by every step. It makes progress inspectable and recoverable, while validation remains responsible for whether the stored data is correct.</p></div>

## Build the layers in this order

Start with a prompt. Add a loop when the task needs several tool calls. Introduce a graph when the route branches or requires checkpoints. Define typed state once multiple steps must share progress reliably.

I think smarter models improve individual decisions inside an agent. Typed state improves the engineering system around those decisions. When a run fails, the team can see where it was, what it knew, and which transition should happen next. That legibility is the leap.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The four layers build on one another, from instruction to repeated action, explicit routing, and shared data. Typed state turns an opaque agent run into a system an engineering team can inspect and improve.</p></div>
