# Anthropic took Microsoft's old seat in the open-weights fight

I tried to read Anthropic's absence from the July 24 open-weights letter as a small policy disagreement. Then OpenAI and Amazon added their names. Anthropic stayed out.

The document is called [Open Weights and American AI Leadership](https://www.microsoft.com/en-us/corporate-responsibility/topics/open-weight/). Nvidia, Microsoft, Meta and more than 20 other companies launched it. The letter argues that downloadable models can strengthen American AI and help defenders inspect weaknesses. Three days later, Anthropic CEO Dario Amodei published a response saying broad access may help attackers faster.

I think the missing signature puts Anthropic in an old role. Microsoft once used security language against open source while Linux threatened its server business. Anthropic now uses safety language while downloadable models put pressure on the economics of paid model access.

The resemblance is uncomfortable. The difference is worse: a Linux bug can be patched, while a capable model copied across thousands of machines cannot be recalled.

AI adds an irreversible capability risk, so the safety case carries more weight than it did in the Linux era.</p></div>

## A letter turned policy into a lineup

The letter launched with 25 companies. OpenAI and Amazon joined after launch, leaving Anthropic as the only major frontier model lab outside the coalition.

Open weights means you can download the numbers a model learned during training and run them on your own hardware. Those numbers shape the model's behavior. The code and training data can stay private, which is why open weights are narrower than open source AI.

Take a small security alert agent. It receives a suspicious login alert and searches company logs before deciding whether a human should investigate. With open weights, your team can run the model next to those logs. With a closed model, the agent sends a request to a provider's API and receives an answer.

That choice affects [who owns the agent layer](/posts/who-owns-the-agent-layer/). A local model gives the engineering team more control over deployment and replacement. An API gives the provider more control over updates and access.

Amodei's [response](https://www.anthropic.com/news/position-open-weights-models) deserves a fair reading. He says Anthropic supports open models below dangerous capability thresholds and favors safety tests for both open and closed systems. His disagreement concerns what happens when broad access gives an attacker the same powerful tool as a defender.

I think he sees a real safety problem inside a real commercial threat. Both motives can shape the same decision.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The July 24 letter made the split visible: most major AI companies backed open weights, while Anthropic held out. For an engineer, the choice decides where the model runs and who can change the terms later.</p></div>

## Microsoft left a useful paper trail

In August 1998, Microsoft engineer Vinod Valloppillil wrote an internal memo titled [Open Source Software: A (New?) Development Methodology](http://www.catb.org/~esr/halloween/halloween1.html). Eric S. Raymond published the leak that October. It became the first of the Halloween Documents.

The memo called open source a "direct, short-term revenue and platform threat" to Microsoft. It also admitted that open projects could meet or exceed commercial quality. One line was almost painfully honest: "FUD tactics can not be used to combat it."

Microsoft's public language went the other way. Steve Ballmer compared Linux to communism in 2000. In 2001, he called it a "cancer" in the intellectual property sense.

Linux kept improving. Today every system on the TOP500 supercomputer list runs Linux. Microsoft's Azure cloud depends on Linux, and Microsoft bought GitHub in 2018.

The awkward detail is almost too good: Microsoft now hosts the 2026 open-weights letter. I think that reversal shows how quickly a threat to one revenue model can become infrastructure for the next.

Anthropic occupies the same structural seat today. It sells access to closed models and argues for stronger control around the rival distribution model. The comparison maps incentives rather than intent.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Microsoft privately understood open source as a credible commercial threat while publicly presenting Linux as dangerous. Its later dependence on Linux makes Anthropic's position worth examining through both safety and business incentives.</p></div>

## The code-level trade-off is mundane

The alert agent's workflow follows ReAct, short for reasoning and acting. The model chooses a step, calls a tool such as log search, reads the result, then chooses again. It is a loop rather than a single prompt.

A junior engineer might build that loop with LangGraph, a Python framework for workflows that branch or repeat. A `TypedDict` describes the shared data passed through the workflow, perhaps an `alert` field and an `evidence` field. LangGraph's `StateGraph` connects the functions as nodes and decides which node runs next.

The model call sits inside one of those nodes. It can point at a provider API or a model running on your own server. The ReAct loop can remain the same.

That makes the business pressure easy to see. Your team can compare models on saved alerts and replace one without rebuilding the workflow. Private logs can stay inside your network. The durable value moves toward the agent design and the judgment around it, a shift I explored in [When Software Becomes Disposable](/posts/when-software-becomes-disposable/).

I think this is where open weights will earn adoption first. Routine, narrow systems reward control. They rarely need the most capable model available, and the ability to swap the model reduces dependence on one provider.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>ReAct is the agent's tool-using loop, while LangGraph carries shared state through that loop. Keeping the workflow separate from the model lets a team replace an API call with a local model without rebuilding the whole agent.</p></div>

## Safety gets stronger after the download

The same alert agent becomes more dangerous if it can turn a vague request into a working exploit for an unpatched server.

A closed provider can block the request and patch the model later. A downloaded copy can run offline after every public safeguard changes. Its owner can also remove the safety tuning.

This is where the 1999 comparison breaks. Model weights behave less like a shared codebase and more like the dinosaurs in *Jurassic Park*. Restoring power in the control room does little once the animals have crossed the fence. The release creates a one-way door.

Amodei uses biology rather than cyber as his hardest case. He worries that a strong model could help someone weaponize a pandemic-level virus quickly, while defense would take years. I think this is the best argument for control at the frontier.

Openness also gives no automatic safety guarantee. Heartbleed remained in the public OpenSSL codebase for about two years before researchers disclosed it in 2014. Many eyes help only when skilled people have time to inspect the right part of the system.

I don't know where the dangerous capability threshold belongs. I also haven't found an independent dataset that settles whether open access gives defenders a lasting advantage across cyber and biology. Confidence on either side is running ahead of evidence.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Open weights become harder to defend once a model crosses a dangerous capability threshold, because later safeguards cannot recover downloaded copies. Heartbleed also warns against treating public inspection as an automatic security win.</p></div>

## The same test should bind every model

For policy, generating a working exploit can become the capability threshold. Evaluators should test for it in the local model and the API model. The local release may need a higher bar because intervention becomes difficult after download. The API provider should prove that its monitoring and response controls work.

Anthropic's call for capability tests across both distribution types passes that test. Its support for chip controls and action against industrial-scale distillation lands more heavily on foreign open-weight rivals. The commercial effect deserves attention even when the safety goal is sincere.

The coalition has incentives too. Nvidia's chip business and Microsoft's cloud business gain when teams run more models. OpenAI's signature complicates any story that divides the market into pure open challengers and closed incumbents.

My take is that the old pattern will repeat across routine AI, with a controlled frontier above it. I expect teams to run replaceable local models for ordinary alert triage, then use a restricted frontier model for harder cases. That keeps routine logs local and reserves expensive API calls for the work that needs them.

To age better than Microsoft's Linux campaign, Anthropic needs the same capability threshold for Claude and the downloadable model in our alert agent. Until then, its missing signature will remain a commercial signal alongside a serious safety warning.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Capability rules earn trust when they bind open and closed models, with stricter release checks where intervention becomes impossible. Anthropic's holdout carries a credible safety argument and a commercial signal at the same time.</p></div>
