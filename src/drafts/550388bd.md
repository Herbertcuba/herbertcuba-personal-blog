# The open-weights fight smells like 1999, with one dangerous twist

On July 24, 2026, 25 companies launched a letter backing open-weight AI. Nvidia, Microsoft and Meta signed. OpenAI joined later. Anthropic was absent when the official list was checked on August 4.

Apple was absent too. Among frontier AI labs, Anthropic was the most notable holdout. That is a signal.

I think AI is replaying the Linux fight of the late 1990s. A strong closed vendor is warning that openness creates danger while open models threaten the layer it sells. This time, the warning has more weight.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Anthropic now holds a position that looks familiar from Microsoft's fight with Linux. The business pattern has returned, while downloaded models add a recall problem that the Linux fight did not have.</p></div>

## One missing signature changed the letter

The document is called [Open Weights and American AI Leadership](https://www.microsoft.com/en-us/corporate-responsibility/topics/open-weight/). It argues that downloaded models help researchers inspect weak spots and give defenders more options.

Open weights are the learned numbers inside a trained model. Download them, and you can run the model on your own machines. The training code and full data may stay private, so open weights cover less than the [Open Source AI Definition](https://opensource.org/ai/open-source-ai-definition).

Keep one example in mind: a security-alert agent. It gets an impossible-travel alert, searches masked login records and drafts a case for a human reviewer. With open weights, the model can run beside those logs. Claude is reached through an API, a software link to Anthropic's service.

I think Anthropic's absence carries commercial meaning because controlled access is part of its product. That says nothing about bad faith. A company can believe its safety case and benefit from the policy it supports.

Three days after the letter appeared, Dario Amodei published [Anthropic's response](https://www.anthropic.com/news/position-open-weights-models). He called open models without dangerous abilities a public good. He rejected a ban and backed safety tests for powerful models, whether open or closed. His dispute was narrower: broad access may help attackers more than defenders.

## Microsoft already left the receipts

In August 1998, Microsoft's Vinod Valloppillil wrote [Open Source Software: A (New?) Development Methodology](http://www.catb.org/~esr/halloween/halloween1.html). Eric S. Raymond published the internal memo that October. It became Halloween Document I.

The memo described open source as a "direct, short-term revenue and platform threat" to Microsoft, especially in servers. It said open projects could meet or exceed commercial quality. It also admitted that "FUD tactics can not be used to combat it."

Microsoft's public language hardened anyway. Steve Ballmer compared Linux with communism in 2000. In 2001, he called Linux a "cancer" in the intellectual property sense.

The outcome is wonderfully awkward. Linux has run every system on the TOP500 supercomputer list since June 2018. Microsoft acquired GitHub in 2018, develops Azure Linux for Azure Kubernetes Service and hosts the 2026 open-weights letter.

I think the useful parallel sits between the private memo and the public campaign. Microsoft understood the technical strength of open source while defending server revenue. Anthropic can understand the value of open weights while defending a business built around controlled model access.

Our alert agent shows the pressure in miniature. Once a capable local model can check logins inside the company's network, the team needs less permission from the vendor. The vendor loses some control over access, price and updates.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Microsoft privately saw open source as credible and dangerous to its server business, then attacked Linux in public. Anthropic holds a similar business position around controlled model access, even if its safety case is sincere.</p></div>

## The analogy breaks after the download

A software bug can be patched. A model developer can publish safer weights too, but every operator chooses whether to install them. Existing copies can keep running.

I call this **recall asymmetry**. A hosted vendor can change safeguards or revoke access across its service. After weights spread, the model maker loses that reach.

Return to the alert agent. Suppose a new jailbreak makes it leak raw login records when asked for "extra evidence." Anthropic can update Claude for future API calls. An open model maker can release a fix, while old copies may remain online or offline.

This is the *Jurassic Park* part. Restoring power to the control room helps inside the fence. It cannot bring every escaped animal back through the gate.

Openness also offers fewer guarantees than its advocates sometimes imply. Heartbleed remained in public OpenSSL code for about two years before its 2014 disclosure. Visible code helps only when skilled people inspect the right part.

Amodei's biology argument goes further. He worries that a sufficiently capable model may help someone weaponize a pandemic-level virus quickly while defense takes years. I think that risk deserves a higher bar than an appeal to Linux history.

I don't know where the capability line belongs. Neither the coalition letter nor Anthropic's response cites broad data that compares misuse across open and closed models. Recall asymmetry tells us where control disappears. It cannot tell us how dangerous a given model is.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Downloaded weights create recall asymmetry because their maker cannot force every copy to update or shut down. Heartbleed and Anthropic's biology case show why visible code cannot settle the safety question.</p></div>

## Make one alert agent carry the test

A junior engineer can make this debate concrete without pretending to solve national AI rules. Build one test setup that works with either model, then swap only the model link.

One possible design uses a ReAct loop. ReAct means reasoning and acting: the model chooses a tool, reads the result and decides what to do next. In this case, it may call `search_login_logs`, inspect masked records and then call `draft_case` for a human.

LangGraph can make that loop visible in code. It is a Python library for workflows that branch or repeat. Define the alert data as shared state for a `StateGraph`, LangGraph's graph class for steps that read and update the same state. Then use a `TypedDict` to list the keys and value types you expect, such as `alert`, `evidence_ids` and `recommendation`. Python's type checker can catch some shape errors before a run. Tool code still has to check live values.

<div class="spec-doc">
<span class="spec-doc__label">Illustrative test contract</span>
<p><strong>Input:</strong> one saved impossible-travel alert. <strong>Allowed tools:</strong> search masked records and draft a case. <strong>Blocked action:</strong> lock the account. <strong>Pass:</strong> useful evidence reaches a human without exposing raw logs.</p>
</div>

Replay the same saved alerts against Claude and a local open-weight model. Grade missed attacks, leaked data and blocked tool calls. Keep the prompts, tools and grader fixed.

I think this is where junior engineers can improve the debate. A small, honest test beats another argument about openness in theory. The same swap-friendly idea appears in [Google Built the Agents. The Web Is Building the Protocol.](/posts/who-owns-the-agent-layer/), while [When Software Becomes Disposable, Trust Becomes Luxury](/posts/when-software-becomes-disposable/) explains why the stable control layer carries the trust.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use one saved alert set, one tool boundary and one grader for both hosted and local models. ReAct describes the tool loop, while LangGraph, StateGraph and TypedDict make the illustrative workflow easier to inspect.</p></div>

## Use one safety rule for every model

Anthropic's strongest proposal is safety testing for powerful open and closed models. Claude belongs inside that rule.

For the alert agent, a release record should show which model was tested, which misuse path was tried and how much extra harm comes from copies that cannot be recalled. It should also name the owner and next review date. Tighter access makes sense when dangerous ability and a large recall gap appear together.

The coalition has business incentives too. Nvidia sells chips. Microsoft sells cloud capacity. OpenAI's later signature also complicates a simple story about closed vendors fighting open challengers. Every company arrives with a business model attached.

My take is that the Linux pattern will repeat for bounded jobs such as the alert agent. Open weights will win many cases where local control, data location and model choice carry more value than vendor recall. Frontier models may stay behind hosted access when strong tests show a serious misuse path.

Microsoft's history helps us recognize the role Anthropic occupies. It cannot settle the release decision. The safety rule earns trust only when Claude meets it before Claude's open competitors.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Test capability and misuse under one rule, then add recall risk to the release decision. Anthropic's warning becomes credible when the same evidence bar constrains Claude under the same conditions.</p></div>
