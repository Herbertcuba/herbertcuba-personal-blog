# The open-weights fight is replaying Linux, but AI changes the ending

I tried to treat Anthropic's missing signature on the July 24 open-weights letter as a policy footnote. Then OpenAI and Amazon joined the list. Anthropic stayed out.

I think AI is replaying the late 1990s fight over open source. Anthropic now holds Microsoft's old structural position: a strong closed vendor warns about risk as open models threaten its access business. AI makes that warning harder to dismiss.

## One missing signature became a signal

On July 24, 2026, 25 companies launched [Open Weights and American AI Leadership](https://www.microsoft.com/en-us/corporate-responsibility/topics/open-weight/). Nvidia, Microsoft and Meta were among them. OpenAI signed later, and Amazon appears on the current list. Anthropic and Apple were absent when the official page was checked on August 4.

Open weights are the learned numbers inside a trained model. A team can download them and run the model on its own machines. Training data and code may remain private, so open weights are narrower than the [Open Source AI Definition](https://opensource.org/ai/open-source-ai-definition).

Keep one security-alert agent in mind. It gets an impossible-travel alert, searches login logs and drafts a case for a human. Open weights can run beside the logs. Claude runs through an API, a software link to Anthropic's service.

Controlled access is part of what Anthropic sells. I think that makes its absence meaningful. The incentive is visible even without proof of bad faith.

Three days later, Dario Amodei published [Anthropic's response](https://www.anthropic.com/news/position-open-weights-models). He called safe open models a public good, rejected a ban and supported tests for capable open and closed models. Broad access, he argued, may help attackers more than defenders.

## Microsoft already ran this play

The Linux fight left a rare record of private analysis beside public language.

In August 1998, Microsoft program manager Vinod Valloppillil wrote [Open Source Software: A (New?) Development Methodology](http://www.catb.org/~esr/halloween/halloween1.html). Eric S. Raymond published the internal memo that October. It became Halloween Document I.

The memo called open source a "direct, short-term revenue and platform threat." It said open projects could meet or exceed commercial quality. It even admitted that "FUD tactics can not be used to combat it."

Microsoft's public language still hardened. Steve Ballmer compared Linux with communism in 2000. In 2001, he called Linux a "cancer" in the intellectual property sense.

History delivered a dry punchline. Linux has run every machine on the TOP500 supercomputer list since June 2018. Microsoft bought GitHub in 2018, develops Azure Linux for Azure Kubernetes Service and now hosts the 2026 open-weights letter.

I think the parallel sits in that gap. Microsoft saw the strength of open source while defending server revenue. Anthropic can hold a sincere safety view while defending controlled access.

Moving our alert agent to a local server reduces the provider's control over price and access. A weaker local model can still pose a business threat.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Microsoft privately saw open source as credible and dangerous to server revenue while its leaders attacked Linux. Today's echo mixes technical argument with commercial exposure.</p></div>

## Recall asymmetry changes the argument

The Linux analogy breaks at the point of release. I call the break **recall asymmetry**.

A provider can patch a hosted model or end access. An open-weight developer can publish an update, but each operator chooses whether to install it. Copies can spread.

Suppose the alert agent leaks raw login records when asked for "extra evidence." Anthropic can update Claude for future requests. An open developer can fix its release, yet it cannot force the fix onto every copy.

This is the *Jurassic Park* part. The fence helps while the animals stay inside. After they cross it, the control room can restore power but cannot recall them.

Open systems help inspection, but visible code offers no guarantee. Heartbleed sat in public OpenSSL code for about two years before its 2014 disclosure.

Anthropic's biology argument is stronger. Amodei worries that a capable model could help weaponize a pandemic-level virus quickly while defense takes years. I think that risk deserves more than a history lesson.

I don't know where the danger line belongs. The two letters offer opposite forecasts without a broad misuse dataset. Recall asymmetry shows where control is lost. It cannot rate a model's danger.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Recall asymmetry is the lost power to update or withdraw every copy after release. It gives Anthropic's safety case real force, while Heartbleed shows that visibility alone does not create security.</p></div>

## Make one alert agent carry the comparison

Junior engineers can make this debate testable without pretending to settle national policy.

Give both versions two tools. `search_login_logs` returns redacted records. `draft_case` creates a case for a human. Keep account locking outside the agent's reach. Replay the same alerts and grade missed attacks, data leaks, unapproved tool calls and false escalations.

<div class="spec-doc">
<span class="spec-doc__label">Illustrative harness contract</span>
<p><strong>Input:</strong> one impossible-travel alert. <strong>Allowed:</strong> search redacted records and draft a case. <strong>Denied:</strong> lock the account. <strong>Pass:</strong> useful evidence reaches a human without raw-log exposure.</p>
</div>

A ReAct loop fits this job. ReAct means reasoning and acting: the model picks an action, reads the result and chooses again. LangGraph is a Python library for workflows that branch or loop. A `TypedDict` lists the expected keys and types in a dictionary, such as `alert`, `evidence_ids` and `recommendation`. Static checkers can catch some mistakes before the code runs. Live data needs a separate check.

Connect the steps in a `StateGraph`, LangGraph's object for nodes that share data. One node gathers evidence, another checks it, and an edge routes the run. Tool code still checks data at runtime.

I think a junior engineer can produce useful evidence here. Keep the tools, cases and grader fixed. Change only the model link. A security owner then reviews the results, license, data location, cost and support.

This follows the model-neutral approach in [Google Built the Agents. The Web Is Building the Protocol.](/posts/who-owns-the-agent-layer/) and the trust argument in [When Software Becomes Disposable, Trust Becomes Luxury](/posts/when-software-becomes-disposable/). The harness keeps its permissions and tests through a model swap.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A fair comparison keeps the alert, tools and pass criteria fixed while swapping the model. ReAct describes the tool-use loop, and LangGraph can express it with typed shared state and clear routes to human review.</p></div>

## Use one release test for every model

Anthropic's strongest proposal is capability testing for open and closed models. Claude belongs inside that rule.

A release record should show the tested capability, a misuse path and the extra harm caused by copies that cannot be recalled. It should name an owner and review date.

For the alert agent, show whether the model can reach raw logs or try an unapproved action. Then measure how fast a confirmed failure can be fixed. Tighter access makes sense when dangerous ability, misuse and a large recall gap meet. The case weakens when that gap adds no harm.

The same test should reach Claude before an open rival. Anthropic's chip and anti-distillation policies may answer real state threats, but they also hit open competitors. Nvidia and Microsoft have incentives too through chips and cloud.

My take is that the 1990s pattern will repeat for bounded systems like our alert agent. Open weights will win where local control beats recall risk. Dangerous frontier abilities may stay behind hosted access.

Microsoft was wrong about Linux's quality and right about the business threat. Anthropic may be right about recall while protecting controlled access. History cannot choose the release line. It can demand one standard: a safety rule earns trust when it reaches Claude before Claude's competitors.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Test capabilities and misuse paths under one rule for every model, then add recall risk to the release decision. Anthropic's warning becomes credible when the same evidence bar constrains Claude under the same conditions.</p></div>
