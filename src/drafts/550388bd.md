# Anthropic took the Microsoft seat in the open-weights fight

I tried to treat Anthropic's absence from the July 24 open-weights letter as a small policy disagreement. Then OpenAI and Amazon added their names. Anthropic stayed out.

The letter now brings together Nvidia, Microsoft, Meta, Google, OpenAI, Amazon, and dozens of others. It argues that downloadable weights can help defenders find weaknesses. Anthropic answered three days later: broad access may help attackers first.

I think the disagreement carries an old shape. Microsoft used security language against open source while Linux threatened its server business. Anthropic now raises safety concerns while open weights threaten the economics of closed model access. The resemblance is real. AI also adds a risk that software in 1999 never carried.

<div class="article-tldr"><span class="article-tldr__label">In short</span><p>Open weights are likely to spread because engineers want control over where models run and how they are adapted. Anthropic's holdout echoes Microsoft's old position against open source, while irreversible model releases give the safety case more weight this time.</p></div>

## The letter made the split visible

The document gave a quiet industry disagreement a date and a list of names.
<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Twenty-five companies launched "Open Weights and American AI Leadership" on July 24, 2026. OpenAI joined later, leaving Anthropic as the only major frontier lab outside the coalition.</p></div>

[Open Weights and American AI Leadership](https://www.microsoft.com/en-us/corporate-responsibility/topics/open-weight/) launched with 25 signers, including Nvidia, Microsoft, Meta, Google, and the Linux Foundation. More companies joined over the following days. The letter defines an open-weight model as one whose learned parameters can be downloaded and run on private infrastructure.

Weights are the billions of numbers a model learns during training. They shape how it responds. Engineers receive a runnable model, while its training data and code can remain private. The Open Source Initiative treats open weights as narrower than full open source AI.

Anthropic CEO Dario Amodei published [his response](https://www.anthropic.com/news/position-open-weights-models) on July 27. He wrote that Anthropic has never called for a ban and described models without dangerous capabilities as a public good. His dispute concerns models that cross a dangerous capability threshold.

The absence is still a signal. I think Anthropic sees a commercial threat inside a safety problem. Those motives can exist together without making either one fake.

## Microsoft wrote the earlier version

The open-source fight left unusually clear records of what the incumbent knew.
<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Microsoft's 1998 internal memo admitted that open source could meet or exceed commercial quality and threatened server revenue. Its public campaign still cast Linux as dangerous, while Linux later became core infrastructure.</p></div>

In August 1998, Microsoft engineer Vinod Valloppillil wrote an internal memo called [Open Source Software: A (New?) Development Methodology](http://www.catb.org/~esr/halloween/halloween1.html). Eric S. Raymond published the leak that October. The memo called open source a "direct, short-term revenue and platform threat" and said commercial quality could be "achieved / exceeded" by open projects.

The memo said fear, uncertainty, and doubt would fail as a long-term response. Microsoft's public language went in the other direction. Steve Ballmer compared Linux to communism in 2000 and called it a "cancer" in 2001.

Every TOP500 supercomputer has run Linux since 2018. Azure depends on it. Microsoft bought GitHub and became a major corporate contributor to open-source projects.

The detail I like most is wonderfully awkward: Microsoft hosts the 2026 open-weights letter. I think its reversal tells us how quickly a threat to one business model can become shared infrastructure for the next one.

## Open weights change a system you can build

A small incident-response agent makes the engineering trade-off concrete.
<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Open weights let you run the model inside your own network and swap providers without rebuilding the agent workflow. The same control also makes every downloaded copy harder to monitor or withdraw.</p></div>

Imagine you are building an agent that helps a security team triage alerts. It reads an alert, searches logs, and decides whether to escalate. The loop uses ReAct, short for reasoning and acting. The model reasons about the next useful step, calls a tool such as log search, reads the result, and chooses again.

You could build that loop with LangGraph, a Python framework for workflows that branch and repeat. The agent carries shared state through the graph. A `TypedDict` defines its expected fields, perhaps `alert`, `evidence`, and `severity`. `StateGraph` connects each step and passes that state between them.

With a closed model, `StateGraph` calls a provider's API. The provider can patch the model or revoke access. With open weights, the model can run beside your logs. You can tune or replace it while keeping the ReAct loop intact.

That portability affects [who owns the agent layer](/posts/who-owns-the-agent-layer/). A team can test two local models on the same saved alerts and compare their escalation decisions without sending production logs elsewhere.

I think this is where open weights will spread first. Routine enterprise systems reward local control, stable costs, and the ability to change suppliers. As the model layer gets cheaper, the durable value moves into the workflow and the judgment around it, a shift I explored in [When Software Becomes Disposable](/posts/when-software-becomes-disposable/).

## Anthropic's warning survives the history lesson

Downloaded weights create a one-way door that Linux never had.
<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A provider can patch or disable a closed model after release. Copies of an open-weight model can keep running offline, so a dangerous capability may survive every later safeguard.</p></div>

Suppose the incident agent becomes capable enough to produce a working exploit chain from a vague request. The API version leaves logs with the provider and gives the provider a chance to block misuse. A downloaded copy can run without those controls. Its owner can also remove the safety tuning.

Amodei makes the same point with biology. He worries that a powerful model could help someone weaponize a pandemic-level virus quickly, while defense would take years. He supports safety testing across both distribution types.

I think this is his strongest argument. A Linux bug can be patched. Model weights copied across thousands of machines stay where they landed. *Jurassic Park* gives that part of the problem a useful image: restoring power in the control room cannot recover the animals already moving beyond the fences.

Open code also offers no automatic safety guarantee. Heartbleed sat in the public OpenSSL codebase for about two years before researchers disclosed it in 2014. Many eyes can inspect a system only when skilled people have the time and funding to look.

I don't know where the dangerous capability threshold belongs. No independent dataset yet settles whether broad model access gives defenders a lasting lead over attackers across cyber and biology. Anyone claiming a clean answer is moving ahead of the evidence.

## Read the remedy before the rhetoric

The policy itself reveals how much weight to place on a safety claim.
<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Apply the same capability test to open and closed models, then account for the controls each distribution type leaves available. Proposals aimed mainly at rival distribution channels deserve extra scrutiny.</p></div>

Use the incident agent again. If generating an exploit chain is the dangerous capability, test for that behavior in the local model and the API model. The open version may need a higher bar before release because later intervention is limited. The closed provider should face the same capability evaluation, plus proof that its monitoring works.

Anthropic's call for testing across both types passes that check. Its support for chip controls and action against industrial-scale distillation lands heavily on foreign open-weight rivals, including companies it has accused of extracting knowledge from Claude.

The coalition has its own incentives. Nvidia sells more chips when more teams run models. Cloud providers sell the infrastructure. Meta gains when the base model becomes abundant. OpenAI's decision to sign also complicates the idea of a single closed-incumbent camp.

My take is that the open-source pattern will repeat across routine AI. Engineers will choose downloadable models for private data, predictable workloads, and supplier freedom. Frontier capabilities will stay controlled for longer when release removes the chance to intervene.

The Microsoft analogy tells us to inspect who benefits when danger becomes the sales pitch for control. Anthropic's response tells us to inspect what happens after the file leaves the server. A useful AI policy has to survive both inspections, because our incident agent should remain replaceable without turning its most dangerous capability into a permanent download.
