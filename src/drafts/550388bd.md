On July 24, 2026, 25 companies launched [*Open Weights and American AI Leadership*](https://www.microsoft.com/en-us/corporate-responsibility/topics/open-weight/), and Anthropic's name was missing.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The letter had passed 270 signatories by August 3, while Anthropic and Apple remained absent. Anthropic now sits where Microsoft once sat. AI safety gives the closed side a stronger case than Linux-era FUD ever had.</p></div>

Nvidia, Microsoft and Meta signed at launch. [OpenAI had joined by July 27](https://www.cnbc.com/2026/07/27/anthropic-ceo-dario-amodei-isnt-advocating-open-weight-model-ban.html). Anthropic and Apple were still missing after the official list passed 270 on August 3.

I think Anthropic's absence is a structural signal without proving bad faith. The company built its public identity around AI safety and sells Claude through controlled access.

## Microsoft documented the commercial fear

An internal Microsoft memo from August 1998 is unusually honest about what Linux threatened.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Microsoft privately wrote that open source could match commercial quality and threaten revenue. Ballmer attacked Linux anyway. Today Microsoft maintains Azure Linux and hosts the open-weights letter.</p></div>

In [Halloween Document I](https://web.archive.org/web/20210125034937/http://www.catb.org/~esr/halloween/halloween1.html), program manager Vinod Valloppillil called open source a "direct, short-term revenue and platform threat." It said open projects could exceed commercial quality and conceded that "FUD tactics can not be used to combat it." Eric S. Raymond published the memo in October 1998.

Steve Ballmer called Linux ["a cancer"](https://www.theregister.com/2001/06/02/ballmer_linux_is_a_cancer/) in 2001 while arguing about the GNU GPL. [Every TOP500 supercomputer has run Linux since November 2017](https://www.top500.org/statistics/sublist/). Microsoft now maintains [Azure Linux](https://learn.microsoft.com/en-us/azure/azure-linux/) and hosts the 2026 letter.

The private memo understood Linux. The public argument still protected Microsoft. I think that is why the open-weights fight smells like 1999.

## Anthropic's warning has earned a hearing

Anthropic's safety position predates the July letter by almost three years.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Anthropic's safety work predates the current fight. It wants capability tests for open and closed models. Controlled access also fits Claude's business.</p></div>

Anthropic published its first [Responsible Scaling Policy](https://www.anthropic.com/news/anthropics-responsible-scaling-policy) in September 2023. In its [July 27 response](https://www.anthropic.com/news/position-open-weights-models), Dario Amodei rejected a blanket ban, called non-dangerous open models a public good, and supported tests for sufficiently capable models, open and closed.

That is more careful than Microsoft's Linux campaign. Amodei argues that broad access may help attackers faster than defenders, especially in biology. His proposed chip controls and efforts to stop industrial-scale model copying add a state-security dimension that the Linux analogy cannot explain. That concern is real.

Downloadable models can reduce API dependence, which gives Anthropic a plausible commercial reason to prefer controlled access. The other signatories have skin in the game too. Nvidia sells chips. Microsoft sells cloud infrastructure. OpenAI's signature still makes the incumbent story less tidy.

I think Anthropic's warning deserves a hearing. Its preferred market deserves scrutiny too.

## A released weight changes who can intervene

Open weights give the operator a copy that the original developer may never control again.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Weights are less than source code, and released copies move the control point. A provider can update future hosted calls. Old downloaded weights may keep running.</p></div>

Weights are learned parameters that operators can download and run. The [OSI definition](https://opensource.org/ai/open-source-ai-definition) asks for more: data information plus complete training and runtime source code. It does not require every underlying training-data record.

Imagine a factory assistant that reads private sensor logs and equipment manuals. A local model can keep that work onsite. If testing later shows it can generate attacks against industrial control systems, the developer may publish safer weights. The factory still decides whether to install them.

Distributed software can remain unpatched too. A hosted provider can change future calls, while a developer cannot force every released copy to accept an update. The [reversibility problem](/posts/reversibility-is-the-new-correctness/) now includes capability control.

*Terminator 2* ends with the T-800's processor lowered into molten steel after Cyberdyne's lab has already burned. The lab is gone. The capability still exists in one more machine.

Heartbleed keeps the open side honest. The vulnerable code [entered OpenSSL on December 31, 2011](https://github.com/openssl/openssl/commit/4817504d069b4c5082161b02a22116ad75f822b1), shipped in 2012, and [became public in April 2014](https://openssl-library.org/news/secadv/20140407.txt). Inspection was possible, yet discovery was slow.

I don't know whether open models favor attackers or defenders overall. The available evidence does not settle it.

## Use one evidence bar for every model

A short release record gives procurement and security teams something firmer than vendor claims.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Run the factory test against both models. The release record must name the update owner and expire on a date. Local control makes the factory responsible for patching. Claude faces the same danger threshold.</p></div>

For the factory assistant, limit the job to reading logs and drafting recommendations, with control-system access blocked in code. Replay the same saved cases and hostile requests against both models. Then record the update owner, licence, data location, cost, review date and stop condition.

The model can change while [the tools and authorization around the agent](/posts/who-owns-the-agent-layer/) stay put.

I think the open candidate wins this job if it passes the tests and its maintenance owner can keep up. Sensitive logs stay local. A dangerous capability finding would push the decision back toward hosted access. So would repeated update failure.

I think bounded work will move toward open weights. Frontier releases are harder because every copied weight can outlive a developer's change of course. That gives Anthropic's warning real weight. Claude should still face the same threshold.
