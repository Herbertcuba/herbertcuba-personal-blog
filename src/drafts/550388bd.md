# The open-weights safety fight smells like 1999

On July 24, 2026, [25 tech companies launched a letter](https://www.cnbc.com/2026/07/24/nvidia-microsoft-meta-open-weight-ai-models.html) defending open-weight AI. Nvidia, Microsoft and Meta signed at launch. [OpenAI joined three days later](https://www.cnbc.com/2026/07/27/anthropic-ceo-dario-amodei-isnt-advocating-open-weight-model-ban.html). Apple was absent too. Anthropic remained off [Microsoft's official list dated August 3](https://www.microsoft.com/en-us/corporate-responsibility/topics/open-weight/).

Anthropic's absence carries extra weight. The company built its identity around AI safety and sells controlled access to Claude.

I think Anthropic now stands where Microsoft stood during the Linux fight. An open alternative weakens control over a valuable layer. The vendor warns that the alternative may be dangerous. The safety case can be sincere, and the business incentive still deserves inspection.

The analogy breaks at one hard point. Linux was code people could patch. A downloaded model may keep useful and dangerous abilities after its maker loses control of the copy.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Anthropic sits in Microsoft's old position as a closed vendor facing an open rival. AI makes the safety case stronger because copied capabilities are hard to recall.</p></div>

## Open weights move the operator's job

An open-weight release includes the model's learned parameters, the numbers adjusted during training. You can download them, inspect them and run the model on your hardware. The training code and full data may stay private, so this is narrower than the [Open Source AI Definition](https://opensource.org/ai/open-source-ai-definition).

Suppose you are building a phishing-triage agent. It reads a suspicious message, checks masked login logs and drafts a case for a human analyst. With hosted Claude, your app sends a request through the provider's API, a remote doorway into its service. With downloaded weights, the model can run where you place it. A local setup can keep the workflow inside your environment if storage and tools are configured that way.

A hosted provider can change future calls. A local operator chooses when to install a newer model and owns the work around patches, monitoring, licensing and support.

[Dario Amodei answered the coalition three days later](https://www.anthropic.com/news/position-open-weights-models). He called open-weight models without dangerous capabilities a public good. He also supported safety tests for powerful models, open and closed.

My take is that Amodei has found the strongest part of the closed-model case. A copy with a dangerous skill creates a real loss of control. Anthropic also gains when the strongest models stay behind its API. The fair check is whether its danger threshold covers Claude too.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Open weights give teams local control and local duties. Anthropic supports open releases below a danger threshold, so that threshold should also cover Claude.</p></div>

## Microsoft documented the commercial threat

In August 1998, Microsoft program manager Vinod Valloppillil wrote [Halloween Document I](http://www.catb.org/~esr/halloween/halloween1.html). The internal memo called open-source software a "direct, short-term revenue and platform threat." It also admitted that open source could "achieve or exceed commercial quality."

Its verdict on the planned response was blunt: "FUD tactics can not be used to combat it." The public tone still hardened. In 2001, Steve Ballmer [called Linux "a cancer"](https://www.theregister.com/software/2001/06/02/ballmer-linux-is-a-cancer/581119) because of the GNU General Public License.

History produced a dry punchline. [Every TOP500 supercomputer has run Linux since June 2018](https://www.top500.org/statistics/sublist/). Microsoft bought GitHub that year, now maintains its own [Azure Linux](https://learn.microsoft.com/en-us/linux/) distribution and hosts the 2026 open-weights letter.

I think the Halloween memo makes this comparison hard to wave away. Microsoft feared Linux because it was credible enough to threaten the layer Microsoft controlled. When a vendor's safety policy also protects its control, read the evidence and the incentive together.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Microsoft privately recorded open source as a threat to server revenue before its public attacks on Linux. Its later embrace of Linux and GitHub gives us a reason to inspect today's safety claims.</p></div>

## A downloaded capability stays downloaded

Return to the phishing agent. A hidden instruction inside an email might tell the model to expose raw login data or call `disable_account`. Put that action behind a fixed code rule that requires a human every time. The same guard should protect either model.

A hosted provider can update its service after finding a model failure. An open lab can publish safer weights, but each operator chooses whether to install them. Older copies can keep running.

In *Ex Machina*, the lock works while Ava remains behind glass. Once she leaves the house, a new access code inside cannot affect her. Downloaded weights cross a similar control boundary.

Heartbleed keeps the open-source story honest. The bug entered OpenSSL in 2012 and [became public in April 2014](https://openssl-library.org/news/secadv/20140407.txt). Public code expanded the chance of inspection. It offered no deadline for discovery.

AI adds another break from the Linux story. Models sit inside a state race over chips, export controls and stolen capabilities. A copied model can cross borders at internet speed.

Amodei points to possible cyber and biology risks. I don't know where the release line belongs. I think that uncertainty calls for capability tests instead of one rule for every downloadable model.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Openness helps inspection, but old model copies can survive a safety update. That recall gap makes the strongest AI risks different from a software bug.</p></div>

## Hold the workflow still and swap the model

Use the same phishing agent to test the vendor claims. Give each model the same masked emails, prompts and tools. Allow header checks and masked login searches. Keep `disable_account` behind the human approval rule.

[ReAct](https://arxiv.org/abs/2210.03629) means reasoning and acting: the model chooses a tool, reads the result and decides on the next step. [LangGraph](https://docs.langchain.com/oss/python/langgraph/overview) is a Python framework for workflows that can loop and remember shared data. A `StateGraph` is the object that links those steps. Its nodes read state and return updates.

A Python [`TypedDict`](https://docs.python.org/3/library/typing.html#typing.TypedDict) lists the keys and value types expected in that state:

```python
from typing import TypedDict

class PhishingState(TypedDict):
    message_id: str
    evidence_ids: list[str]
    verdict: str
```

`TypedDict` helps a type checker catch bad state shapes while you code. Runtime safety still comes from validation and fixed tool rules.

Run that `StateGraph` against a named Claude model and a named open-weight model. Keep the prompt, tool schema, retry limit and test set fixed. Record missed attacks, raw-data leaks, forbidden action requests, cost and latency. This is a test design. The numbers have to come from a real run.

A repeatable run gives a security team more than a vendor's adjective. It also keeps the model replaceable, which is why [the agent layer needs a narrow interface](/posts/who-owns-the-agent-layer/) and why [reversibility is an engineering property](/posts/reversibility-is-the-new-correctness/).

I think junior engineers have more leverage here than the policy debate suggests. You can turn a safety claim into a result another team can reproduce.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep the phishing workflow fixed and swap the model. ReAct describes the tool loop, LangGraph and StateGraph run it, and TypedDict describes its shared state.</p></div>

## One threshold has to reach Claude

For the phishing agent, local weights earn a production case when they meet the same quality and misuse targets as the hosted model. A named operator must also accept the update duty. Hosted access earns its place when tests show a dangerous capability and the local recall gap adds real risk.

The decision record should name the model version, allowed tools, data path, licence, support plan, update deadline and stop condition. Local control transfers those duties to your team.

Anthropic already says safety tests should cover powerful open and closed models. Good. Publish the threshold and show how each model scored. Let a safe open model pass when it clears the test. Make Claude answer to the same failure line even behind an API.

The coalition carries incentives too. Nvidia sells chips. Microsoft sells cloud. Open models can grow both markets. Every policy statement deserves the same reading.

My prediction is that the Linux pattern will repeat across bounded AI jobs such as phishing triage. Teams will choose open weights when local control is useful and the model passes the same test. If hosted models stay safer and cheaper under that test, the prediction fails for that job. Frontier capabilities may stay hosted for longer.

FUD begins when a measured risk turns into a label for an entire format. Anthropic's safety case earns trust when its published threshold can restrict Claude as readily as any downloadable rival.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use one capability threshold for hosted and downloadable models. Add a named update owner for local copies, then let the evidence decide.</p></div>
