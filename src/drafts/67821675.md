# The 105 minutes after the graph

“Which node in your graph has never met an input you did not write yourself?” [Jey asks](https://x.com/0xJeyx/status/2081364222856831271). A node is one step in the workflow, and his 15/105 framing assigns fifteen minutes to drawing the graph and the remaining 105 to repeated evaluation. The [official recording](https://www.youtube.com/watch?v=ib-wTAvCZqg) lasts about 2 hours 22 minutes, so the ratio is diagnostic rather than a measured agenda. Testing and evaluation enter around [15:36](https://www.youtube.com/watch?v=ib-wTAvCZqg&t=935s), and the Q&A returns to evaluation datasets around [1:42:00](https://www.youtube.com/watch?v=ib-wTAvCZqg&t=6120s).

The source trail separates the workshop from later hype. The [2024 conference schedule](https://www.ai.engineer/worldsfair/2024/schedule) lists Martin with LangChain. A [post by Movez](https://x.com/0xMovez/status/2081011657807925604) attributes a 70% adoption figure, a three to six month forecast, and “No more prompting” to an Anthropic engineer in a separate 30-minute lecture. The 2024 recording does not support that attribution. [Martin later clarified](https://x.com/RLanceMartin/status/2081408482344149047) that the graph talk came from AIE 2024, before his Anthropic role.

I think the useful signal survives the correction. The graph is the control plane, meaning the rules and routes that decide which step may run next. Typed state is a structured case record shared across steps, while a held-back eval set holds reserved cases outside design and tuning. Together they form the trust plane, the evidence and release-decision layer that tells an accountable owner whether a version may ship. Jey’s sharper line captures the gap: “A graph without an eval set is a diagram with opinions.”

## The graph decides where work can go

[Martin describes context engineering](https://rlancemartin.github.io/2025/06/23/context_engineering/) as giving each model step the right information for its next step. In LangGraph’s vocabulary, nodes perform work, edges define allowed handoffs, and a transition is the edge selected during a run.

Consider this hypothetical refund case, where one route can move money and apply customer policy:

```yaml
order_id: "8841"
payment_state: "pending"
policy_version: "2026-08-01"
proposed_action: "refund"
review_required: true
expected_next_node: "payment_review"
```

A route guard is a code rule that allows or blocks a transition. Under this fictional policy, the assertions are plain:

```python
assert route(case) == "payment_review"
assert route(case) != "refund_approval"
```

A pending payment that requires review must reach `payment_review`, so direct refund approval fails before money moves. If one model call proposes and approves the refund, HAL 9000 controls the ship and certifies its own flight log. I think typed state earns its place at this boundary because it turns a vague instruction into a condition that code can test.

Focused nodes may reduce irrelevant context, although extra calls can raise token use. Track total run tokens alongside route accuracy, the percentage of held-back cases that reach the next node recorded before testing.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The control plane earns its shape when typed state exposes each money-moving handoff to a prewritten assertion.</p></div>

## The eval set becomes release evidence

A versioned held-back eval set repeats an assertion across reserved cases. Once a case influences a workflow change, move it into the development set and add a reviewed replacement. That discipline preserves the test’s contact with unfamiliar inputs.

A grader is the logic that scores a run. [Anthropic recommends](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) starting with 20 to 50 simple tasks drawn from real failures. For the refund graph, code checks the route and ledger state, while a model grader uses a written scoring guide. Before testing, the policy owner records the expected route and acceptance threshold. The release approver blocks deployment when a critical assertion fails or route accuracy falls below that threshold.

Start with one money-moving journey and a small weekly batch of reviewed failures from support. The policy owner resolves disputed outcomes before cases enter the dataset. Engineering owns the harness; a dataset maintainer controls writes and freezes the held-back set for each release. A low-risk internal assistant may combine roles, but the record still names an accountable approver and explicit block condition. For money movement, keep policy judgment and release authority separate.

The release record binds the model version, policy version, frozen dataset ID, grader settings, results, and approver. A reviewer can rerun order 8841 against the recorded policy, reproduce the expected route and assertion result, and identify who approved that release. If a later model or policy change breaks the route assertion, the team can roll back to the recorded version or send affected cases to human review. I think this evidence and release layer earns the name trust plane because it can change the release decision.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A held-back set becomes release evidence when cases are versioned, expected routes are written before testing, and one named approver has authority to block deployment.</p></div>

## The work starts after the diagram

[Graph frameworks](https://docs.langchain.com/oss/python/langgraph/durable-execution) can supply routing, persistence, and recovery after failure. Representative cases still come from your operation. I think graph APIs will converge over the next year, while teams with versioned, failure-derived held-back sets will show fewer route regressions after model or policy changes. Count previously correct cases that reach the wrong next node after each release; if both groups show the same rate, the prediction fails.

The phrase “No more prompting” echoes every “no more code” promise. Prompts remain inside the nodes; the surrounding system adds state schemas, route guards, graders, dataset controls, and release decisions. Even a verified 70% internal adoption figure would signal what tooling may assume in twelve months. A production decision this quarter still depends on failure cost and the evidence available today.

I don’t know which graph framework will dominate. My take is to begin with the smallest graph that improves one route involving money, policy, or material user harm. Give that route a held-back case, a deterministic assertion wherever possible, and a named release owner. Drawing the graph is an afternoon; proving it survives inputs you did not choose is the job.
