Imagine a supplier-review agent assessing a contract, a security questionnaire and privacy terms. One design sends the entire packet, every tool result and the full conversation into every model call. A better design lets the contract step see clauses, the security step see controls, and the final reviewer see their structured findings.

A token is a small unit of text processed by a language model. A context window is the input and generated output available during one call, as [Anthropic, the AI company behind the Claude language model, explains](https://docs.anthropic.com/en/docs/build-with-claude/context-windows). Context engineering is the work of choosing what belongs in that window. The goal is not the fewest tokens at any cost. It is the smallest context that still supports a reliable decision.

<span class="chapter-tldr__label">In short</span>
<p>Token optimization begins by separating the supplier-review job and giving each step only the evidence it can use.</p>

## From prompts to a working graph

In an [August 2026 video about graph engineering](https://youtu.be/JWhICz1QR8M), technology entrepreneur Greg Isenberg separates three layers. Prompt engineering shapes the instruction inside one call. Context engineering selects its information. Graph engineering designs how work moves between calls, tools and people. His practical point is that better instructions cannot compensate for a badly arranged job.

A [July 2026 post on the social platform X by the Movez account](https://x.com/0xMovez/status/2081011657807925604) packaged the shift as “No more prompting.” That is a slogan rather than an engineering description: every node still needs instructions, while the graph changes what the node sees and what happens next.

A knowledge graph represents relationships among entities, such as a supplier, its service providers and the systems they can access. An agent graph represents the workflow itself. Its **nodes** are bounded steps; **edges** are allowed connections; and a **transition** is the actual move along an edge. **Shared state** is the structured record they update, while **conditional routing** chooses the next node from that state.

```text
                         ┌─ contract scan ─┐
intake ─ parallel split ─┤                 ├─ merge ─ draft ─ checker ─ skeptic
                         └─ security scan ─┘
```

The two scans use parallel fan-out because neither depends on the other. Their results then rejoin before sequential review, a split-and-rejoin shape called a **diamond topology**. If the merged state marks sensitive-data access, a condition can route the case to a privacy specialist. Otherwise it follows the standard path.

Start with the smallest useful graph. Split work where the required evidence changes, a different tool is needed, or an independent judgment matters. Turning every tiny action into a node only creates more handoffs to tune.

<span class="chapter-tldr__label">In short</span>
<p>The graph controls sequence, parallel work and exceptions; its boundaries also prevent irrelevant material from entering every model call.</p>
</div>

## Tune the handoffs

Isenberg proposes a sensible maturity ladder: run the workflow manually, make stable handoffs explicit as file artefacts, then orchestrate it with software. For the supplier review, the first version can be a person running separate prompts. The next writes contract findings and security findings to small JSON data files or readable Markdown text files. Automation comes after the team understands those outputs, not before.

| Node | Context in | State out |
|---|---|---|
| Contract scan | Relevant clauses and review policy | Obligations and exceptions |
| Security scan | Questionnaire and control requirements | Confirmed controls and gaps |
| Merge | Both structured findings | One risk brief |
| Checker | Risk brief and acceptance rules | Pass or requested repair |

Shared state lasts through this review. **Persistent memory** survives into later runs, so it should hold durable facts such as an approved supplier identity or a confirmed service provider, rather than every intermediate exchange. Each node can receive a filtered view of either store.

A **checker node** tests the brief against stated requirements. A separate **skeptic node** looks for contradictions, missing evidence and unjustified confidence. That separation is the practical value of the reflection phase in [APEX, an operating model for agentic production](/posts/2026-04-05-apex-framework/). A **human gate**, meaning required approval before the next transition, should follow the consequence: routine low-risk cases may continue, while a case involving sensitive data or a consequential exception waits for an accountable person.

This is where graph engineering becomes difficult. Drawing arrows is quick; tuning what every node sees, writes, remembers and may authorize is the real work.

<span class="chapter-tldr__label">In short</span>
<p>Manual runs reveal the workflow, file artefacts stabilize its contracts, and orchestration should preserve selective state, independent reflection and risk-based human authority.</p>
</div>

## Let held-back cases set the budget

Isenberg's video makes the practitioner case for designing work around AI, but it does not discuss evals. That bridge needs a separate source. Lance Martin, then at the AI tooling company LangChain and now an Anthropic engineer, taught *Architecting and Testing Controllable Agents* at the 2024 AI Engineer World's Fair, an industry conference for AI builders. [Jey's July 2026 analysis](https://x.com/0xJeyx/status/2081364222856831271) distilled its shape as 15 minutes on the graph and 105 on evaluation; the workshop transcript introduces evaluation around minute 23 and keeps returning to tests and dataset construction.

A checker reviews one supplier packet once. An **eval set**, a collection of held-back test cases, runs the workflow across packets and edge cases the builders did not choose. [Anthropic's guide to evaluating agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends grounding that set in real tasks and failures rather than polished demonstrations.

Now token optimization becomes testable. Hold the eval set fixed, remove or summarize a context field, and compare both token use and outcomes. Keep the saving only if routing, findings and final decisions still hold on unfamiliar cases. The graph decides where work moves; the eval set tells you whether the tuned handoffs deserve trust.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>A checker challenges one run; a held-back eval set proves whether the whole graph remains reliable after its context has been reduced.</p>
</div>
