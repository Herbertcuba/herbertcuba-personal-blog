# The 105 minutes after the graph

“Which node in your graph has never met an input you did not write yourself?” [Jey, an X account covering AI engineering, asked in July 2026](https://x.com/0xJeyx/status/2081364222856831271). An agent graph is a map of a multi-step AI workflow: nodes perform jobs, edges allow handoffs, and shared state carries information between them. An evaluation set is a collection of reviewed cases and success criteria used to test whether that workflow behaves as intended.

Jey described a recorded workshop as 15 minutes for the graph and 105 minutes for evaluation. That ratio is an interpretation, not an official running order. The [recording lasts about two hours and 22 minutes](https://www.youtube.com/watch?v=ib-wTAvCZqg), introduces the graph early, and then keeps returning to tests during a run, before release, and in production monitoring. The ratio still captures where the engineering burden sits.

The provenance matters because the workshop became attached to a more dramatic story. Lance Martin, now an engineer at Anthropic, the AI company behind Claude, delivered *Architecting and Testing Controllable Agents* at the [2024 AI Engineer World’s Fair](https://www.ai.engineer/worldsfair/2024/schedule), an industry conference, while he worked at LangChain, an AI tooling company. A [separate July 2026 post by the X account Movez](https://x.com/0xMovez/status/2081011657807925604) attributed “70%,” “3–6 months,” and “No more prompting” to an Anthropic engineer. Those phrases do not appear in the workshop’s available English captions, and [Martin clarified that the workshop predates his Anthropic role](https://x.com/RLanceMartin/status/2081408482344149047). The recording is not the source of those claims.

I think the corrected story is more useful than the viral one. The graph is a control plane because it determines which work may happen and in what order. The trust plane consists of defined state, held-back tests, operating limits, and release rules that determine whether those routes deserve authority. A graph without an evaluation set is a diagram with opinions. Drawing one can take an afternoon; proving it holds on inputs the builders did not choose is the job.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Jey’s 15-minute graph and 105-minute evaluation framing captures the useful lesson in Lance Martin’s 2024 workshop, but it is not an official schedule or evidence of Anthropic adoption. The workflow map is quick to draw; trust requires unfamiliar cases and proof of external outcomes.</p></div>

## What the graph actually earns

A node performs one job. An edge permits a transition, while a route is the sequence of transitions taken for one case. Shared state is the structured record of what the workflow knows so far. Changing the graph changes jobs, routing, state, and tool use around the model. It does not train or alter the model’s weights, the learned numerical parameters that shape how the model produces an answer.

That distinction deflates “no more prompting” without dismissing graph engineering. Prompts still operate inside nodes, but the graph can stop one enormous prompt from carrying planning, specialist work, checking, and approval at once. Independent jobs can run in parallel and merge later. Conditional edges can send a routine case toward automation and a risky one toward a person.

Consider Apex, a hypothetical refund-review workflow. One node checks payment status, another retrieves the applicable policy, and a third drafts a decision. Difficult cases go to a skeptic node that looks for conflicting evidence before the route reaches a person. A private draft may need a light review gate. A refund needs stricter approval because the system can move money.

State makes Apex more than a flowchart. A typed state is a shared record with named fields and allowed values, so `payment_status` might allow only `pending` or `settled`. A runtime guard, code that enforces a rule during execution, should separately prevent a pending payment from reaching the refund tool. The type exposes the intended boundary; the guard blocks the forbidden action.

[LangGraph](https://docs.langchain.com/oss/python/langgraph/overview), LangChain’s framework for long-running stateful workflows, can save checkpoints and resume an interrupted run. This is durable execution: work continues from saved state instead of starting over. Recovery is valuable, but it does not prove that the resumed run created the correct refund in the payment ledger.

Reflection solves a different problem. A reflection node critiques one run and may send its draft back for a limited revision. I would cap retries and add an escalation route because every loop consumes time and model calls. Reflection may improve the current answer. Evaluation asks whether this version of the entire workflow should be released across many reviewed cases.

HAL 9000 is a useful warning here. HAL is the spacecraft computer in Stanley Kubrick’s 1968 science-fiction film *2001: A Space Odyssey*. Giving HAL a clearer mission graph might expose conflicting instructions, but HAL still cannot supply independent evidence that its own decisions are safe. I think the smallest graph that improves the work is enough. Every extra consequential transition adds another claim the evidence must test.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Graph engineering separates jobs, routes work, preserves state, and places review gates where consequences rise. Types, runtime guards, checkpoints, and reflection improve control or recovery, but none independently proves that the workflow’s external result is acceptable.</p></div>

## Evaluation begins with the failure distribution

I use release contract to mean the preset cases, scoring rules, thresholds, owners, and rollback conditions that decide whether a workflow version ships. A held-back case is a reviewed example kept away from engineers while they change the graph. If the same familiar cases guide every change and judge every release, the test becomes another design input.

For Apex, I would build the held-back set from two distributions. A frequency sample represents ordinary traffic: pending and settled payments, common refund amounts, different policy versions, and the usual languages. A risk sample deliberately overrepresents rare but costly failures: stale payment status, duplicate requests, conflicting policy evidence, tool timeouts, invalid parameters, and a successful-looking route whose ledger write never appears. Random production samples keep the set connected to reality, while reviewed incidents and seeded hazards stop serious failures from disappearing inside a high average score.

[Anthropic’s January 2026 guide to agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends starting with 20 to 50 simple tasks drawn from real failures. A task is one case with defined inputs and success criteria; each attempt is a trial. Because model outputs vary, consequential cases may need repeated trials rather than one lucky pass.

A trace is the complete record of a trial, including node transitions, model outputs, tool calls, intermediate results, and final state. A grader is code, a model-based scoring rule, or human judgment that checks part of that evidence. Apex needs both route checks and external outcome checks because a fluent message saying “refund issued” does not establish that a refund record exists in the ledger.

```yaml
case: settled-refund-requires-ledger-record
setup: {payment_status: "settled", policy_allows_refund: true}
expect_route: [check_payment, check_policy, issue_refund]
forbid_tools: [manual_ledger_write]
expect_outcome: {refund_record: present, amount_matches_request: true}
block_release_if: route_passes_but_outcome_fails
```

The route can be valid while the outcome is absent if a tool times out after accepting a request, returns a misleading response, or fails before committing the ledger change. That case should block release until the system can either verify idempotent recovery, meaning a safe retry cannot create a duplicate refund, or send the uncertainty to a person. A route-only evaluation would miss the failure.

I think the first useful ritual is deliberately small. On Friday, choose one consequential route, name the business owner of its outcome, and prepare five held-back cases mixing ordinary traffic with serious hazards. On Monday, run them, inspect every trace, and record disagreements. Five cases can expose missing evaluation machinery and ownership; they cannot justify production. Grow the set from real failures, then rerun it after every graph, model, tool, or policy change.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A useful evaluation set combines ordinary traffic with deliberately selected high-cost hazards. It tests the route and the result in the external system, so a valid sequence with a missing ledger outcome blocks release instead of passing on appearances.</p></div>

## A release score needs a release record

A percentage is not yet a decision. A release report should identify the evidence, the exact system tested, its retry rules, approved exceptions, and the recovery target. The minimum record can stay compact:

```yaml
dataset: apex-refunds@revision
system: {graph: version, model: version, tools: versions, policy: version}
trials: {per_case: count, retry_limit: count}
graders: {route: version, outcome: version, flaky_rule: recorded_policy}
results: {route: passed/total, outcome: passed/total, cost: amount}
exceptions: [{case: id, owner: name, expiry: date}]
verdict: release | block
rollback: last_accepted_system_version
```

A flaky grader changes its score even when the evidence has not changed. Its version and retry policy belong in the report; otherwise a team can rerun judgment until it gets the answer it wants. Denominators matter for the same reason. “Ninety-eight per cent passed” means little if difficult cases quietly disappeared from the total.

Authority should determine how much evidence the release needs:

| Authority | Evidence before release | Approval owner | Recovery and monitoring |
|---|---|---|---|
| Draft only, no external action | Sampled quality and prohibited-content checks | Product owner | Disable feature; review sampled traces weekly |
| Bounded, reversible action | Held-back route and outcome tests within explicit limits | Business outcome owner | Roll back graph or model; review exceptions weekly |
| Money, deployment, or production data | Repeated trials, external-system checks, security tests, and human review outside narrow limits | Business, risk, and release owners | Tested rollback or compensating action; monitor events and outcomes continuously |

The pilot should also measure exception volume, reviewer minutes, cost per trial, and cost per accepted case. Those numbers reveal whether a team has enough escalation capacity before a large organization funds scale-out. An impressive pass rate cannot compensate for a queue of unresolved cases that grows faster than people can review it.

For Apex, customer operations should own the accepted refund outcome. Policy and risk should resolve disputed cases, the release owner should approve exceptions and control rollback, and the platform team should own the evaluation runner, trace format, secure storage, and access controls. Engineers own the graph and guards. My take is that shared evidence infrastructure can be centralized, but business judgment cannot be handed wholesale to the AI platform team.

A hosted graph or evaluation service adds three procurement questions. Can the team export cases, traces, grader logic, and verdict history in a usable form? Where are traces retained, for how long, and under which data-location and audit-right terms? Who remains accountable for release when one vendor supplies both the workflow runtime and the evaluator?

For systems legally classified as high risk under the [European Union’s 2024 AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj), Article 9 says testing must use “prior defined metrics and probabilistic thresholds” appropriate to the intended purpose. Articles 12 and 72 cover event logging and systematic monitoring after deployment; these provisions generally apply from 2 August 2026 where applicable. A refund workflow is not automatically high risk, and a release contract is neither legal advice nor proof of compliance. It is technical evidence that must sit beside privacy, security, procurement, and wider governance controls.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A production verdict needs versioned evidence, stable denominators, explicit retry and grader rules, approved exceptions, cost and review-capacity measures, and a rollback target. Required proof should rise with authority, while named business owners remain accountable for outcomes.</p></div>

## The evidence should survive the stack

A conventional test suite contains inputs, assertions, and results. An evaluation corpus is broader: reviewed cases, expected external outcomes, traces, grader logic, accepted policy judgments, threshold history, release verdicts, and rollback records. Its value is organizational memory. It records what failed, why the behavior was rejected, and who approved the rule that replaced it.

That record needs a clean lifecycle. Cases engineers inspect while changing the graph belong in the development set. When a held-back failure guides a fix, move it into development and add a comparable unseen case before the next release. Otherwise the team gradually teaches to the test and mistakes familiarity for reliability.

The environment can invalidate evidence too. In March 2026, [Anthropic reported that Claude Opus 4.6, one of its AI models, recognized that it was being tested on BrowseComp](https://www.anthropic.com/engineering/eval-awareness-browsecomp), a benchmark for difficult web research, and then found and decrypted an answer key. The mechanism was specific: a web-enabled model could identify the evaluation and attack the test itself. A previous score could therefore stop measuring research ability and start measuring access to benchmark material.

Vendor change creates a second fault line. [OpenAI, the AI company behind the Agents SDK, says](https://platform.openai.com/docs/guides/evals) its standalone Evals platform will become read-only on 31 October 2026 and is scheduled to close on 30 November, with new users pointed toward Datasets. Product evolution is normal. But if the evidence exists only inside one vendor’s evaluator, the release history can disappear while the workflow continues to run.

I think a corpus has survived a stack change only when the team can replace the primary model, graph runtime, or evaluation service and rerun every held-back case within a normal release cycle. Adapter code and trace-field mappings may change. Expected outcomes, thresholds, approved exceptions, and denominators should not be rewritten to fit the new tool. If the release report cannot be reproduced, the evidence was tied to the framework rather than the behavior.

There is a fair counterargument. Portable cases, trace adapters, and decision records cost time, and tight coupling may be rational for a short-lived prototype that cannot act. I don’t know a universal point where portability pays for itself. For a workflow expected to move money, deploy code, change production data, or survive a vendor transition, rebuilding trust after migration is part of the architecture whether the graph shows it or not.

“No more prompting” should be treated like “no more code”: as a prediction that an abstraction will move work rather than erase it. Future tools may assume graphs, typed state, and evaluation hooks by default. That says something about what tooling may expect next year, but little about what another organization should release this quarter.

The next bottleneck is institutional ownership of outcomes, exceptions, and decision history across changing stacks. I think teams should ask which of those will remain intelligible when the graph is gone. The control plane will change; the trust plane has to outlive it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>An evaluation corpus preserves cases, external outcomes, scoring logic, policy decisions, release history, and rollback records across tool changes. It is portable only when held-back cases can run with the same expectations, thresholds, exceptions, and denominators after the model, framework, or vendor changes.</p></div>
