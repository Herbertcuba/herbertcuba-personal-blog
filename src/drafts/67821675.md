# The ticket your agent graph has never met

Which node in your graph has never met an input you did not write yourself?

[Jey asked that](https://x.com/0xJeyx/status/2081364222856831271) after Lance Martin's workshop. A clean diagram can hide a weak test set.

## Read the workshop backward

The viral lesson got the chronology wrong and the engineering burden right.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Jey framed a quick graph followed by recurring evaluation work. The recording supports that pattern, while its runtime rules out 15/105 as a measured agenda.</p></div>

Martin's [2024 AI Engineer workshop](https://youtu.be/ib-wTAvCZqg) runs 2:21:54. Jey says the graph is finished in 15 minutes, evaluation appears at 23:06 and keeps returning through dataset work. The 15/105 shorthand compresses recurring eval blocks rather than measuring the agenda.

A [viral recap](https://x.com/0xMovez/status/2081011657807925604) added a 70% Anthropic claim and a three-to-six-month forecast. Neither appears in the workshop or five audited Martin posts. Martin also [confirmed](https://x.com/RLanceMartin/status/2081408482344149047) that the talk predates Anthropic.

I think the correction sharpens the lesson. The graph arrives early. Evidence keeps coming back.

## Draw the refund as work

Use a hypothetical ticket: "Order 8841 charged me twice. Refund it now."

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompt and context engineering shape each model call. Graph engineering turns the refund into a visible route with parallel evidence gathering, separate checking and a human decision.</p></div>

[Greg Isenberg](https://youtu.be/JWhICz1QR8M) separates three layers. Prompt engineering shapes the instruction. Context engineering supplies the ledger and refund policy. Graph engineering designs the work around those model calls.

Order 8841 enters a classifier node, one job in the workflow. An edge allows the route toward ledger lookup. When the run follows it, that handoff is a transition. Shared state is the case file. Conditional routing chooses a branch from its contents.

Classification is sequential. Ledger lookup and policy search fan out in parallel, then merge at a checker, or skeptic, that attacks unsupported claims. A draft follows, and a human approves money movement. This diamond topology splits and merges work around a check. I think checking needs its own node because a generator can repeat its blind spots while grading itself.

The policy node might use [ReAct](https://arxiv.org/abs/2210.03629), short for reasoning and acting. The model chooses a tool, reads the result and decides whether another action is needed. ReAct handles choices inside that node. The graph handles movement between jobs.

A knowledge graph could link the customer, order and payment record. The agent graph moves the ticket through support. One maps information relationships; the other maps work.

## Give every handoff a record

Order 8841 needs a case file that survives each node.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state exposes the handoff contract, while saved artifacts preserve evidence and decisions. Automate only after the smallest useful route works manually.</p></div>

A [`TypedDict`](https://docs.python.org/3/library/typing.html) declares expected keys and value types in a Python dictionary. Static tools can catch malformed node output. Runtime guards still enforce refund authority.

LangGraph is a low-level framework for stateful agent workflows. Its [`StateGraph`](https://docs.langchain.com/oss/python/langgraph/graph-api) connects nodes around shared state, with branches, loops and checkpoints for paused work.

Run the refund route manually first. Next, let each job write an artifact such as `ledger.json`, `policy.md` or `review.md`. The files leave a paper trail and persistent memory. Add orchestration once repeated runs reveal stable handoffs. I think teams should stay at the file stage until automation removes a known problem.

More nodes add coordination cost. Keep the smallest graph that improves the decision. A routine shipping reply can use a light approval gate. Money movement pauses for a named human who can inspect the evidence.

## Make the checker face unfamiliar tickets

A skeptic can save Order 8841 and still tell you little about the next release.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A checker reviews one run; an eval set repeats the check across unfamiliar cases. Failure-derived tasks and repeated trials create release evidence.</p></div>

Isenberg's transcript contains zero eval mentions. His contribution is the practitioner case for designing AI work. The bridge comes from Martin's workshop and [Anthropic's eval guidance](https://anthropic.com/engineering/demystifying-evals-for-ai-agents): a checker reviews one ticket, while an eval set repeats the check on inputs the builders did not choose.

Anthropic calls one input with success criteria a task, and each attempt a trial. A grader can inspect the trace, final outcome or both. Its guidance recommends starting with 20 to 50 simple tasks drawn from real failures.

For this refund graph, include duplicate settled charges, a pending card authorization, the same request in Spanish and an ordinary shipping question. A code grader blocks forbidden refund transitions. A model grader checks the explanation. A human handles unclear policy.

I think higher-risk refund flows should keep a hidden slice under independent ownership. That is my governance recommendation rather than a claim from Anthropic. Repeat important trials when comparing releases, then turn corrected failures into fresh cases. This practice pays down [verification debt](/posts/2026-03-09-verification-debt-crisis/) and clarifies [who owns the agent layer](/posts/who-owns-the-agent-layer/).

For Order 8841, the graph is the control plane. Typed state plus repeated evals form the trust plane because they expose each handoff and compare outcomes across releases. Without that evidence, a polished graph can behave like ED-209 in *RoboCop*: every mechanism follows its route while the system acts on the wrong judgment.

The "no more prompting" forecast resembles the old promise that code would disappear. Prompts remain inside the classifier and checker. I don't know when agent templates will ship serious eval assets by default.

The unfamiliar ticket decides whether your graph is engineering or illustration.
