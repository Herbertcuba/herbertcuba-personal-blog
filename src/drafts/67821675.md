A checkout release starts rejecting valid payments. An incident agent receives the log archive, deployment diff, runbooks, team chat, and every tool result on each call. By its fourth hypothesis, the same background has been processed several times and the useful evidence is harder to find.

A token is a small unit of text processed by a model. A [context window](https://docs.anthropic.com/en/docs/build-with-claude/context-windows) is the finite space for input and output. Context engineering decides what belongs there for this step, at this moment.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Give each agent step the evidence it needs instead of making it inherit the whole incident.</p></div>

## Start with the decision, not the diagram

In [an August 2026 video](https://youtu.be/JWhICz1QR8M), technology entrepreneur Greg Isenberg presents graph engineering as designing work around AI instead of keeping it inside one large chat. That contains three questions:

- **Prompt engineering:** What should this model call do?
- **Context engineering:** What evidence should it receive?
- **Graph engineering:** What runs before, after, or instead?

A viral July 2026 paraphrase called this “no more prompting.” It overshoots. Every model node still needs instructions; the graph makes them local and controls their handoffs.

A knowledge graph records entities and relationships, such as which services depend on the payment gateway. An agent graph routes jobs. Start from the risky decision, a production rollback, then work backward to its evidence and review.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts direct calls, context supplies evidence, and the graph works backward from the consequential decision.</p></div>

## Give the incident its smallest useful shape

```text
                         ┌─ inspect logs ─────┐
alert → frame incident ──┤                    ├─ merge → propose cause
                         └─ inspect change ───┘             │
                                                   checker + skeptic
                                                           │
                                           diagnose ── or ── human rollback
```

A node performs one job. An edge is an allowed connection; a transition is one actual move along it. The inspections fan out in parallel and merge into a diamond topology. Framing and proposing remain sequential because the second needs the first’s result.

Shared state is the common record passed between nodes. Conditional routing reads it and chooses the next edge: gather evidence, report a diagnosis, or request rollback approval. A checker verifies that the proposed cause follows from the evidence. A skeptic searches for the strongest rival explanation, such as an unrelated gateway outage.

Keep the graph this small until evidence demands another boundary. Every new node adds a prompt, context choice, failure mode, and result to inspect. Complexity is easy to draw and expensive to tune.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Parallelize independent evidence, keep real dependencies sequential, and add nodes only when separation improves control.</p></div>

## Shrink the handoff, preserve the work

Isenberg’s maturity ladder begins with manual work, turns stable handoffs into file artifacts, and adds orchestration last. For this incident, the artifacts are a timeline, bounded log extract, change summary, and rollback packet. If a handoff cannot be made explicit, automation hides the confusion.

A typed state is a shared record with named fields and allowed values. The log node may receive `service`, `symptom`, and `time_window`, while the change node gets `deploy_sha` and relevant files. Selective retrieval saves tokens because irrelevant material never enters either call.

Persistent state preserves the current incident across pauses and retries. Memory carries selected facts across incidents. [LangGraph](https://docs.langchain.com/oss/python/langgraph/persistence), an open-source agent-orchestration framework, implements this distinction with checkpoints and longer-lived stores. Neither requires every transcript.

Stable runbooks and tool definitions may use [prompt caching](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching), where supported. It can lower repeated processing cost and latency, but cached text still occupies the context window. The larger gain comes from asking for less. Read-only investigation may run automatically; a production rollback needs a human gate because its consequence is higher.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Explicit handoffs and selective retrieval save tokens; saved state and human review preserve continuity and control.</p></div>

## Reflection is where the graph gets tuned

The sources separate here. Isenberg makes the practitioner case for graph design, but his video contains no evaluation discussion. Evaluation is central to *Architecting and Testing Controllable Agents*, a roughly two-hour 2024 AI Engineer World’s Fair workshop by Lance Martin, then at LangChain and now at AI company Anthropic.

[A July 2026 X post by Jey](https://x.com/0xJeyx/status/2081364222856831271) compresses the workshop into 15 minutes for the graph and 105 for evaluation. The primary transcript enters sustained evaluation closer to minute 23, so the ratio is framing, not stopwatch timing. Drawing routes is the short part.

A checker reviews one incident run. An eval set repeats that separation across representative inputs held back from development. [Anthropic’s evaluation guidance](https://docs.anthropic.com/en/docs/test-and-evaluate/develop-tests) recommends starting with 20 to 50 tasks drawn from real failures. Here that means deployment faults, third-party outages, misleading logs, tool failures, expected outcomes, and a release rule.

This is the purpose of reflection in [APEX, the Agentic Production Execution operating framework](/posts/2026-04-05-apex-framework/). Evidence from repeated runs should change node boundaries, context fields, routing thresholds, and human gates. Ask during review: which node has never faced an input its builders did not write?

The graph controls the work. Typed state limits what nodes may exchange, while evaluations test whether those limits remain reliable. The complexity lives in fine-tuning what the graph sees, remembers, does, and proves.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Checkers challenge individual runs; held-back evaluations and reflection turn repeated evidence into a safer, leaner graph.</p></div>
