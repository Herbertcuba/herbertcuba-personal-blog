# The subtle art of graph engineering starts after the diagram

> "Which node in your graph has never met an input you did not write yourself?"

[Jey asked that](https://x.com/0xJeyx/status/2081364222856831271) after watching Lance Martin's [AI Engineer World's Fair workshop](https://youtu.be/ib-wTAvCZqg). His post frames fifteen minutes of graph drawing against 105 minutes of evaluation. The 2:21:53 recording makes that ratio a lens rather than a literal agenda. Testing appears around 15:35, while evaluation-dataset work returns around 1:42:00.

Graph screenshots travel well. Held-back cases and release records rarely do. I think that imbalance explains where agent engineering becomes expensive: a team can draw the route quickly, while evidence has to survive inputs selected by someone outside the build.

A hypothetical customer says order 8841 was charged twice and asks for a refund today. The diagram will look convincing long before the workflow deserves authority over the money.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The 15/105 ratio is Jey's interpretive framing, supported by a workshop that keeps returning to testing. A graph becomes serious when unfamiliar cases can challenge its routes.</p></div>

## Design the work around the model

[Greg Isenberg's graph-engineering explainer](https://youtu.be/JWhICz1QR8M) puts the graph one level above the model call. For order 8841, the prompt shapes the classifier's instruction and context brings in the ledger and refund policy. The graph decides which job follows, under which conditions.

Order 8841 uses a classifier node before separate ledger and policy nodes. Each node owns a job. An edge permits a next job; a transition is the route taken. Shared state carries the case forward. Its contract might contain `order_id`, `payment_status`, `policy_version`, `route`, `proposed_action` and `approver`.

Conditional routing may send a settled duplicate charge toward refund review. A pending authorization blocks the `pending_payment -> refund_approval` transition and sends the case toward an explanation. A shipping question leaves the refund branch entirely.

A knowledge graph connects the customer, order and payment. An agent graph moves their case through work. I think the practical shift is from asking one model for a confident answer to designing a path that can refuse a weak one.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts shape model calls, context supplies evidence, and the graph controls handoffs. Typed shared state makes each permitted route inspectable before money moves.</p></div>

## Build the smallest useful diamond

Classification is sequential. After it finishes, ledger verification and policy lookup can fan out in parallel. Their evidence merges into a checker or skeptic node, which challenges unsupported claims before a proposed action reaches a human. That split, fan-out and merge form the diamond topology Isenberg describes.

I think checking deserves separate criteria and context because a generator can carry its own blind spot into self-review. The human gate should then scale with risk. A delivery update can pass with light review. A refund needs a named approver, and policy ambiguity should go to the support and policy owners before anyone labels the outcome correct.

Run the workflow manually on a whiteboard, then let each job leave a file such as `ledger.json`, `policy.md` or `review.md`. Those artifacts become useful memory when later runs retrieve them. After several stable runs, [LangGraph](https://docs.langchain.com/oss/python/langgraph/overview) or another orchestrator can add persistence, checkpoints and paused approvals.

Extra nodes create handoffs and failure surfaces. The smallest useful graph may need one classifier, two parallel checks, one skeptic and a human gate. Automation should wait until the team understands why each transition exists.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The useful refund graph is a small diamond with independent evidence checks and a risk-proportional human gate. Manual lanes reveal the work, file artifacts preserve it, and orchestration follows once the route is stable.</p></div>

## A checker reviews one run; an eval set governs a release

Isenberg's video makes the practitioner case for workflow design and contains zero eval discussion. The eval bridge comes separately from Martin's workshop, Jey's framing and [Anthropic's agent-eval guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). A checker can reject one weak refund. An eval set repeats that separation across cases the builders did not choose.

Martin recorded the workshop in 2024 while at LangChain and [later clarified that it predates Anthropic](https://x.com/RLanceMartin/status/2081408482344149047). A [viral post](https://x.com/0xMovez/status/2081011657807925604) attached a 70% adoption figure, a three-to-six-month forecast and "No more prompting" to it. The workshop transcript contains zero instances of those claims. I think this is the new "no more code," worth taking seriously as a change in abstraction. Prompts remain inside every classifier and checker.

Anthropic recommends beginning with 20 to 50 simple tasks drawn from real failures. For this refund graph, include a settled duplicate charge, a pending authorization, a Spanish request and a shipping question misrouted into refunds. Conventional state-machine tests should cover deterministic transitions. A code grader can reject the illegal pending-payment route, a model grader can inspect the policy-grounded explanation, and a human can adjudicate unclear policy.

The support owner adds corrected production failures after incidents. The policy owner approves disputed labels after a rule changes. An independent eval owner holds back cases, and the release owner signs a one-page record tied to the model and policy versions under the existing retention schedule. Any illegal money-moving transition blocks release.

Every consequential agent release needs an accountable owner, held-back evidence and a named approver for residual risk. I think this creates an evidence-ownership gap: graph topology will commoditize faster than an organization's failure distribution and the work required to maintain it. The graph is the control plane. Traceable typed state and evals form the trust plane.

In *Edge of Tomorrow*, progress comes from carrying failure into the next run. An eval suite gives order 8841 the same memory, fortunately without the aliens. I don't know which framework will make this discipline a default. The diagram becomes engineering when someone is willing to sign the evidence behind it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A checker challenges one refund, while a held-back eval set challenges the release across unfamiliar cases. The durable work lives in the failure distribution, its owners and the evidence attached to each version.</p></div>
