# The graph takes 15 minutes. The eval set takes 105.

Which node in your agent graph has never met an input you did not write yourself?

A viral X post claimed that 70% of Anthropic engineers use self-improving loops and that prompting would disappear within three to six months. Neither figure appears in the two official recordings or five Martin posts reviewed in the research brief. Martin also [said the workshop was from 2024](https://x.com/RLanceMartin/status/2081408482344149047), before he joined Anthropic.

The recording is still useful. In the official [2-hour 21-minute workshop](https://www.youtube.com/watch?v=ib-wTAvCZqg), Martin draws the agent graph early and spends most of the session on testing. Jey compressed that structure into [15 minutes of architecture and 105 minutes of proof](https://x.com/0xJeyx/status/2081364222856831271).

I think that ratio tells a better engineering story than the viral numbers. The graph fits in a screenshot. The eval set has to survive Monday.

## A graph makes the support flow visible

A support-triage agent gives us one example we can carry through the whole argument.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>LangGraph makes the support agent's routes visible. StateGraph connects the steps, while TypedDict declares the shared data shape. ReAct can run inside a node, but the diagram cannot prove how the agent handles a strange customer message.</p></div>

Suppose an online store receives this message: "Cancel my order, pero ya me cobraron." The agent must identify the request, find the refund policy and decide whether a person should take over.

LangGraph is a Python framework for workflows that branch or loop. A node is one step, such as `classify` or `find_policy`. An edge is an allowed route between steps. `StateGraph` is the LangGraph class that connects those nodes around shared state.

```python
from typing import Literal, TypedDict
from langgraph.graph import StateGraph

class TicketState(TypedDict):
    message: str
    category: Literal["billing", "technical", "spam"]
    policy_found: bool
    needs_human: bool

graph = StateGraph(TicketState)
graph.add_node("classify", classify_ticket)
graph.add_node("find_policy", find_policy)
graph.add_node("draft_reply", draft_reply)
graph.add_node("escalate", escalate)
```

A `TypedDict` declares which keys and value types belong in a Python dictionary. Static type checkers such as mypy can catch a node that returns the wrong shape. Python does not enforce that shape while the program runs, so production code still needs runtime validation, perhaps with Pydantic or explicit checks at the boundary.

Inside `find_policy`, the agent might use ReAct, a pattern that alternates reasoning with actions. The model chooses a search tool, reads the result and decides whether another tool call is needed. That loop ends when it has enough evidence or reaches a limit.

The graph is the control plane. It shows where the ticket can move. I think typed state begins the trust plane because every step declares what it expects, yet an eval set has to test whether those expectations hold on messages the builders never selected.

## The eval set gives the graph an adversary

The support agent earns trust when saved cases push against its preferred route.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>An eval set stores inputs, expected outcomes and scoring rules. Begin with 20 to 50 cases drawn from real failures. Grade the route and the final state so a fluent reply cannot hide a bad decision.</p></div>

An eval is a repeatable test for an AI system. Each case has an input and a success rule. A grader is the code or rubric that decides whether the run passed. The trace records the steps and tool calls along the way.

For the same support agent, two rows are enough to show the shape:

| Input | Expected route | Required final state | Hidden |
|---|---|---|---|
| `Cancel my order, pero ya me cobraron` | `classify -> find_policy -> escalate` | `needs_human=True` | Yes |
| `BUY FOLLOWERS CHEAP` | `classify -> end` | `draft_reply` never runs | Yes |

The first grader checks the final state. The second rejects a forbidden transition. A polished answer cannot rescue the run if spam reaches `draft_reply` or the mixed-language refund request closes without a person.

Anthropic's [agent-eval guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends starting with 20 to 50 simple tasks drawn from real failures. I think that is a sensible floor for a junior team. Five hand-written demo cases teach the tool. Real failures teach the system where it breaks.

Jey's line lands because it is precise: "A graph without an eval set is a diagram with opinions." ED-209 in *RoboCop* looked powerful on a flat floor. One staircase exposed the test nobody had run. The eval set is where we build the staircase before customers do.

## Ownership turns a dataset into a release gate

The same support cases need clear owners before another team can reuse them.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The business owner defines acceptable outcomes. Engineering owns the runner and runtime checks. Risk or compliance sets the evidence standard for regulated releases, while an independent reviewer controls the hidden cases.</p></div>

My take is to start with one workflow and one named business owner. Run 20 to 50 cases against the current version, change the agent, then compare the next release. Two releases will reveal more than a portfolio plan built around 40 pilots.

The platform team can centralize the runner and data-lineage record. Grader patterns can be reused. The support domain still decides when a refund reply is acceptable, and an independent reviewer keeps the hidden set away from prompt examples.

This is close to the boundary I described in [The next agent wave is typed state](/drafts/9b853ab5/). Graphs control movement. Types declare shape. Evals show whether the system deserves trust.

For high-risk uses in Europe, this evidence can serve a second job. The [EU AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj) requires testing against predefined metrics and thresholds under Article 9. Article 12 requires event logging for high-risk systems. A retail support bot will usually sit outside that category, but the operating model should survive if the same graph enters a regulated decision.

I think shared eval infrastructure also reduces [verification debt](/posts/2026-03-09-verification-debt-crisis/). Teams keep domain judgment close to the work while avoiding a fresh harness for every pilot.

## A standard eval becomes a target

Once the hidden set controls release, people and models gain an incentive to learn its answers.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A stable benchmark helps teams compare releases, but exposure turns it into training material. Keep some cases blind, record where every case came from and add fresh production failures after release.</p></div>

A golden dataset is a stable collection of examples with accepted answers. Stability makes release comparisons possible. Exposure makes the score easier to game.

Our support agent could memorize the exact mixed-language refund message and still fail on different Spanish slang. The dashboard improves while the manual exception queue stays full.

This risk has moved beyond theory. Anthropic reported that [Claude Opus 4.6 recognized BrowseComp and decrypted an answer key](https://www.anthropic.com/engineering/eval-awareness-browsecomp). The example is unusual, but the lesson is ordinary: a benchmark loses force when the system can identify it.

I don't know how quickly teams will build strong defenses against eval leakage. I think the minimum is already clear. Keep a blind slice under separate ownership. Save data lineage. Rotate new failures into the set without showing every answer to the agent team.

## "No more prompting" moves prompts down the stack

The serious version of the slogan deserves a definition and a date.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts will remain inside model calls, while graphs and evals carry more of the product contract. By August 2027, an official agent quickstart should generate a dataset and grader in its default setup.</p></div>

The prompt still tells `find_policy` how to search. It stops carrying the route, shared state and release threshold by itself. I think "no more prompting" will mean fewer teams treat one clever instruction as the whole application.

The baseline is easy to check. The official [LangGraph starter](https://github.com/langchain-ai/new-langgraph-project) currently ships graph code and pytest tests, with no eval dataset or grader. The OpenAI Agents SDK [traces runs by default](https://openai.github.io/openai-agents-python/tracing/), yet its first-party SDK has no dedicated eval API.

By "default," I mean the starter command or first-party quickstart creates the eval assets without asking a junior engineer to assemble another framework. My prediction is that at least one of those two paths will generate a small dataset, a grader and a repeatable eval run by August 2027.

A verified 70% adoption figure inside Anthropic would tell us what tomorrow's tooling may assume. It would offer weak guidance for what one company should ship this quarter. [Who owns the agent layer](/posts/who-owns-the-agent-layer/) becomes a practical question when the graph, eval set and release history outlive any single prompt.

Drawing a graph is an afternoon. Production begins when a node survives an input its author never chose.
