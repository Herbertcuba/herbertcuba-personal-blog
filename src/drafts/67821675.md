A production incident arrives with logs, account history, a runbook and policy. The easy agent design sends the whole bundle to every model call. Each step looks informed, but each one rereads the same material, so token cost rises while the useful signal gets harder to find.

A context window is the finite input-and-output budget of one model call, measured in tokens, the small text units a model processes. Context engineering selects the instructions, evidence, tools and prior state that enter that window. When calls cooperate, the subtle part is what each step sees, passes on and leaves behind.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>In multi-step AI, token efficiency comes from controlling what each call sees and passes, not only from shortening its prompt.</p>
</div>

## Separate instruction, evidence and movement

A [July 2026 X post by Movez](https://x.com/0xMovez/status/2081011657807925604) reduced the shift to “No more prompting.” Catchy, but a graph, meaning a map of jobs and allowed handoffs, does not remove prompts. Prompt engineering shapes an instruction; context engineering supplies its evidence; graph engineering decides how work and evidence move between calls.

| Layer | Question | Incident example |
|---|---|---|
| Prompt | What should this call do? | Classify the failure |
| Context | What must it know now? | Recent logs and service ownership |
| Graph | What runs next? | Route an access failure to identity analysis |

In an [August 2026 graph-engineering video](https://youtu.be/JWhICz1QR8M), technology entrepreneur and podcast host Greg Isenberg describes a practical route:

1. **Manual work:** Perform each job separately and observe the handoffs.
2. **File artifacts:** Save compact outputs such as `intake.json`, `evidence.md` and `plan.md`.
3. **Orchestration:** Automate only the boundaries that have become stable.

Start with the smallest useful graph, perhaps intake, diagnosis and review. Each extra node creates another context boundary, so it needs a distinct job or permission.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Prompts direct calls, context supplies evidence, and a graph controls handoffs; make those handoffs visible before automating them.</p>
</div>

## Draw the smallest useful graph

An agent graph maps bounded jobs and their allowed handoffs. A **node** performs one job, an **edge** is a permitted connection, and a **transition** is the edge chosen in one run. **Shared state** is the incident record built along the way. **Conditional routing** selects the next node from that state, sending an access failure to identity analysis while bypassing billing work.

```text
intake -> [log analysis || policy lookup] -> merge -> plan
plan   -> [checker || skeptic]            -> human gate
```

The brackets show parallel **fan-out**: independent jobs run together, then their compact findings **merge**. This split-and-rejoin shape is a **diamond topology**. Sequential nodes run one after another because the next job needs the previous output. Parallel work may reduce latency while increasing total tokens, so every branch needs an informational reason.

The checker tests the plan against explicit rules; the skeptic seeks evidence that could overturn the diagnosis. A **human gate** makes approval proportional to risk: a read-only recommendation may proceed, while a production change pauses. A **knowledge graph**, by contrast, stores relationships among entities such as service, owner and policy. The agent graph routes work and may query it.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Use separate nodes when jobs need different evidence, then exchange compact findings through explicit routes and risk-based gates.</p>
</div>

## Tune the context at every edge

The hard work lives at transitions. Log analysis needs recent logs and a service map, not the whole policy library. Policy lookup needs the proposed action and service class, not raw stack traces. The merge should receive structured findings and source references rather than both branch transcripts. Conditional routes avoid work that cannot change the decision.

[Persistent state](https://docs.langchain.com/oss/python/langgraph/persistence) saves current artifacts across pauses and retries, so a resumed incident need not replay its history. **Memory** lasts across incidents, but should hold selected facts such as a service owner or approved exception. Saving every transcript as memory merely delays the token bill. [Prompt caching](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching) reduces repeated processing of an unchanged beginning, but cannot make irrelevant context useful.

The fine-tuning here is architectural, not model training. Low-risk, reversible suggestions may pass automated checks; state-changing remediation gets a named approver. This is why [APEX](/posts/2026-04-05-apex-framework/), the Agentic Production Execution operating model for governing agent work, includes a reflection phase: it creates an explicit pause before production authority.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Reduce tokens by narrowing handoffs, persisting compact state and routing selectively; use caching only after the context itself is relevant.</p>
</div>

## Make the graph meet unfamiliar inputs

Isenberg’s video makes the practitioner case for designing work around AI, but it does not discuss evaluation. That bridge comes from separate sources. Lance Martin, now an engineer at Anthropic, an AI company, taught a roughly two-hour 2024 AI Engineer World’s Fair workshop called *Architecting and Testing Controllable Agents*. A [July 2026 X post by Jey](https://x.com/0xJeyx/status/2081364222856831271) described its balance as 15 minutes to draw the graph and 105 minutes returning to evaluation. The ratio is a framing rather than a verified stopwatch audit, but it captures the engineering asymmetry.

A checker reviews one incident using the context selected for that run. An **eval set** is a reusable collection of cases and expected outcomes; held-back cases test inputs the builders did not choose while tuning the system. For this graph, include missing logs, conflicting policies, stale ownership data and tool timeouts. [Anthropic’s guidance on agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends starting with 20 to 50 tasks drawn from real failures, enough to expose weak boundaries before building a huge benchmark.

Measure tokens per case that still passes, not tokens per run in isolation. A cheaper route that misses a policy conflict is no optimization. Drawing the graph is the quick part; proving its context boundaries hold on unfamiliar inputs is the job.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>A checker judges one run; an eval set tests whether lower token use still produces acceptable outcomes on cases the builders did not select.</p>
</div>
