# The 105 minutes after the graph

“Which node in your graph has never met an input you did not write yourself?” [Jey, an X account commenting on AI engineering, asked in July 2026](https://x.com/0xJeyx/status/2081364222856831271). An agent graph is a map of a multi-step AI workflow: nodes perform jobs, edges permit handoffs, and shared state carries information between them. An evaluation set is its necessary counterpart, a collection of reviewed inputs and success criteria used to test whether the workflow behaves as intended.

Jey described a recorded workshop as 15 minutes for drawing the graph and 105 minutes for returning to evaluation. That ratio is an interpretation, not the workshop’s official running order. The [recording lasts two hours and 21 minutes](https://www.youtube.com/watch?v=ib-wTAvCZqg), but the diagram does arrive early, and the official description promises testing during a run, before release, and in production monitoring.

The provenance matters because the workshop became attached to a much bigger story. Lance Martin, now an engineer at the AI company Anthropic, delivered *Architecting and Testing Controllable Agents* at the [2024 AI Engineer World’s Fair](https://www.ai.engineer/worldsfair/2024/schedule), a developer conference, while he worked at LangChain. A [separate viral post by the X account Movez](https://x.com/0xMovez/status/2081011657807925604) attributed “70%,” “3–6 months,” and “No more prompting” to an Anthropic engineer. Those phrases do not appear in the workshop’s available English captions, and [Martin clarified that the talk predates his Anthropic role](https://x.com/RLanceMartin/status/2081408482344149047).

I think the correction strengthens the useful lesson. The graph is a control plane because it determines which work may happen and in what order. The trust plane consists of defined state, tests, operating limits, and release rules that tell us whether those routes deserve authority. A graph without an evaluation set is a diagram with opinions. Drawing one can take an afternoon; proving it holds on inputs the builders did not choose is the job.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The 15/105 split is a social-media reading of a 2024 workshop, not an Anthropic adoption statistic or an official agenda. It still captures the production problem: routes are quick to draw, while trust requires evidence from cases the builders did not select.</p></div>

## The graph controls routes, not outcomes

By refining a graph, I mean changing its state fields, routes, retry limits, reflection criteria, and human approval gates as failures appear. I do not mean training the model’s weights. An edge is one permitted handoff, while a route is the sequence of handoffs taken for a particular case. Real inputs turn those simple definitions into engineering work.

Consider Apex, a hypothetical refund-review agent. It checks whether a payment is pending or settled, reads the relevant refund policy, drafts a decision, and sends consequential cases to a person. Its typed state, a shared record with named fields and allowed values, might permit `payment_status` to be only `pending` or `settled`. A separate runtime guard would enforce the business rule that a pending payment can never reach the refund tool. The type exposes the intended boundary; the guard blocks the forbidden action.

Apex might also use reflection, a critique step that checks a draft against named conditions before the workflow proceeds. For this workflow, I would cap revisions and add an escalation route. Repeated self-critique consumes more time and model calls, and a fixed cap gives the team a clear failure point to inspect instead of letting the workflow decide indefinitely when it has done enough.

The graph is a little like the operating plan entrusted to HAL 9000, the spacecraft computer in Stanley Kubrick’s 1968 science-fiction film *2001: A Space Odyssey*. It can make the allowed sequence explicit, but it cannot provide an independent verdict on itself. The engineering team still needs an external test harness to introduce sensor errors, conflicting instructions, and other cases the workflow did not choose. Otherwise the same system writes the mission, flies it, and grades the report.

Existing tools already cover important parts of this problem. [Pydantic](https://docs.pydantic.dev/latest/), a Python data-validation library, can check state against declared fields and values. [LangGraph’s durable execution](https://docs.langchain.com/oss/python/langgraph/durable-execution) can save workflow state so an interrupted run resumes, while [LangSmith](https://docs.smith.langchain.com/evaluation/tutorials/agents), LangChain’s testing and monitoring service, can evaluate a final response, a route of tool calls, or one step in isolation. I think the missing layer is narrower: these mechanisms do not decide which external outcome the business will accept, who may change that judgment, or what independent evidence must pass before release.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Types expose state boundaries, runtime guards block forbidden actions, durable execution preserves a run, and evaluation tools inspect behavior. None of them removes the need to define acceptable external outcomes and assign release authority.</p></div>

## Release evidence has to leave the graph

A release contract is the preset collection of cases, scoring rules, thresholds, and owners that decides whether a graph version ships or rolls back. A held-back case is a reviewed example kept away from graph changes until that decision. Each case should inspect the route, the tool results, and the outcome in the external system, because a fluent message saying “refund issued” is not proof that a valid refund record exists.

Apex’s simplest forbidden transition can fit in a small test fixture:

```yaml
case: pending-payment-blocks-refund
input: {payment_id: "p_41", request: "refund"}
setup: {payment_status: "pending"}
expect_route: [check_payment, explain_pending]
forbid_tools: [refund_tool]
expect_outcome: {refund_record: absent}
release_assertion: forbidden_tool_calls == 0
```

A trace is the complete record of nodes, tool calls, intermediate results, and outcomes for one run. A grader is code, a model-based rubric, or human judgment that scores part of that record. This fixture needs a code grader for the forbidden call and an outcome check against the payment system. If policy evidence conflicts and no single automated answer is defensible, a named human reviewer should choose the expected route and record the reason. The disputed judgment then becomes versioned release evidence instead of disappearing into a prompt or meeting note.

[Anthropic’s January 2026 guide to agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends starting with 20 to 50 simple tasks drawn from real failures. I think that is a sensible first-quarter boundary: choose one consequential workflow, review failures weekly, and rerun the held-back set after every graph or model change. Record route and outcome pass rates, unauthorized tool calls, weekly exception volume, elapsed human-review time, and cost per accepted review. Compared with the previous process at the same volume, those measures can reveal whether automation is reducing work or merely moving it into an expensive exception queue.

The burden of proof should rise with the system’s authority. A drafting assistant that cannot act may need sampled quality checks and a kill switch. A refund agent that can move money needs narrow amount and policy limits, repeated trials, ledger checks, human approval outside those limits, and a tested rollback to the last accepted version. I don’t know a universal threshold that makes every workflow safe. What matters is that the threshold is explicit, owned, and tested before the tool call has consequences.

Imagine a Swedish retailer using Apex. Customer operations owns the accepted refund outcome, while policy and risk resolves disputed cases and approves changes to consequential thresholds. The product release owner signs any exception and can roll back the release. The central AI platform team owns the evaluation runner, trace format, secure storage, and data-residency controls; engineers implement the graph and its guards. This split lets the company reuse evidence infrastructure without pretending that a central platform team can make every local business judgment.

For high-risk systems to which the [European Union’s 2024 AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj) applies, Article 9(8) requires testing against previously defined metrics and probabilistic thresholds appropriate to the system’s intended purpose. Articles 12 and 72 cover event logging and systematic monitoring after deployment. Those high-risk-system requirements generally apply from 2 August 2026 where applicable, while Article 6(1) and corresponding obligations for high-risk AI used as a safety component of regulated products apply from 2 August 2027. A refund workflow is not automatically high-risk, and this is neither legal advice nor proof of compliance. It does show why named owners, retained traces, human oversight, and reversible releases are becoming ordinary engineering concerns in Europe.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A release contract connects unfamiliar inputs to routes, external outcomes, limits, and owners. Start with one consequential workflow and 20 to 50 failure-derived cases, then compare technical results and human exception work with a defined baseline.</p></div>

## The evaluation corpus should outlive the framework

A test suite usually contains inputs, assertions, and results. My take is that the more durable asset is an evaluation corpus: reviewed cases, expected external outcomes, traces, grader logic, accepted policy judgments, threshold history, release verdicts, and rollback records. That extra context matters because a test can show what failed, while the corpus also records why the organization rejected the behavior and who approved the rule that replaced it.

The record needs a clean lifecycle. Cases engineers inspect while changing the graph belong in the development set. If a held-back failure guides a fix, move it into development and add a fresh held-back analogue before the next release. Otherwise the team gradually teaches to the test and mistakes familiarity for reliability.

I think portability gives this claim a fair test. Twelve months from publication, take every held-back case from one accepted release and change the primary model or graph runtime. Within one normal release cycle, rerun all cases without rewriting expected outcomes or thresholds. Adapter code and trace-field mappings may change. The report should identify dataset and system versions, show passed cases over total cases for routes and outcomes, list thresholds and approved exceptions, state the release verdict, and name the rollback target. If expected outcomes must be translated into the old framework’s concepts, or the full report cannot be produced within that cycle, the corpus did not outlive the stack.

There is a real counterargument. Stable outcome definitions, trace adapters, and dispute records can add work before a release. Tight framework coupling may be rational for a short-lived, low-impact prototype when disposal is cheaper than migration. For a consequential workflow expected to survive model and vendor changes, however, policy encoded only inside one framework can become migration debt precisely when the team needs independent evidence.

“No more prompting” should be treated like “no more code”: as a claim that an abstraction will move work, not erase it. Prompts still operate inside nodes, while graphs make state and routing visible. Even if a credible internal adoption rate were published, it would tell us something about the defaults future tools may assume, not what another organization should deploy this quarter.

I think teams should stop asking whether their graph looks sophisticated and ask what evidence survives when the graph is replaced. The diagram records intended control. A production release deserves trust only when every consequential route meets unfamiliar evidence, an accountable verdict, and a tested way back.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The durable asset is broader than a test suite because it preserves outcomes, policy judgments, release history, and rollback decisions. Framework portability is worth its cost when the workflow is consequential and expected to survive changes in models, vendors, or runtimes.</p></div>
