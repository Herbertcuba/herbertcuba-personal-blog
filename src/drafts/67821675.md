# The 105 minutes after the graph

“Which node in your graph has never met an input you did not write yourself?” [Jey, an X account that comments on AI engineering, asked in July 2026](https://x.com/0xJeyx/status/2081364222856831271). An agent graph maps a multi-step AI workflow: nodes perform jobs, edges permit handoffs, and shared state carries information between them. An evaluation set is its necessary counterpart, a collection of reviewed inputs and success criteria used to test whether the workflow behaves as intended.

Jey framed a recorded workshop as 15 minutes for drawing the graph and 105 minutes for returning to evaluation. That ratio is an interpretation, not the official running order. The [recording lasts about two hours and 22 minutes](https://www.youtube.com/watch?v=ib-wTAvCZqg), the diagram appears early, and its official description promises testing during a run, before release, and in production monitoring.

The provenance matters because the workshop became attached to a much larger claim. Lance Martin, now an engineer at Anthropic, an AI company, delivered *Architecting and Testing Controllable Agents* at the [2024 AI Engineer World’s Fair](https://www.ai.engineer/worldsfair/2024/schedule), a developer conference, while working at LangChain, an AI tooling company. A [separate post by the X account Movez](https://x.com/0xMovez/status/2081011657807925604) attributed “70%,” “3–6 months,” and “No more prompting” to an Anthropic engineer. Those phrases do not appear in the workshop’s available English captions, and [Martin clarified that the talk predates his Anthropic role](https://x.com/RLanceMartin/status/2081408482344149047). The recording is not a source for those claims.

I think the correction makes the real lesson more useful. The graph is a control plane because it determines which work may happen and in what order. The trust plane consists of defined state, tests, operating limits, and release rules that tell us whether those routes deserve authority. A graph without an evaluation set is a diagram with opinions. Drawing one can take an afternoon; proving it holds on inputs the builders did not choose is the job.

It still captures the production problem: the workflow map is quick to draw, while trust requires evidence from cases the builders did not select.</p></div>

## The graph controls routes, not outcomes

By refining a graph, I mean changing its state fields, routes, retry limits, review steps, and human approval gates as failures appear. I do not mean training the model’s weights, the numerical parameters learned during model training. An edge is one permitted handoff, while a route is the sequence of handoffs taken for a particular case. Real inputs turn those simple definitions into engineering work.

Consider Apex, a hypothetical refund-review agent. It checks whether a payment is pending or settled, reads the relevant refund policy, drafts a decision, and sends consequential cases to a person. Its typed state, a shared record with named fields and allowed values, might permit `payment_status` to be only `pending` or `settled`. A separate runtime guard, code that checks a rule while the workflow is running, would enforce the business rule that a pending payment can never reach the refund tool. The type exposes the intended boundary; the guard blocks the forbidden action.

Apex might also use reflection, an in-run critique step that checks a draft against named conditions before proceeding. For this workflow, I would cap revisions and add an escalation route because every repeat consumes more time and model calls, while a fixed cap creates a failure point the team can inspect. Reflection can improve one run. Evaluation asks a different question across many reviewed cases: should this version of the whole system be released?

The graph is a little like the operating plan entrusted to HAL 9000, the spacecraft computer in Stanley Kubrick’s 1968 science-fiction film *2001: A Space Odyssey*. It can make the allowed sequence explicit, but it cannot provide an independent verdict on itself. The engineering team still needs an external test harness to introduce sensor errors, conflicting instructions, and other cases the workflow did not choose. Otherwise the same system writes the mission, flies it, and grades the report.

Existing tools already solve important parts of this problem. [Pydantic](https://docs.pydantic.dev/latest/), a Python data-validation library, checks state against declared fields and values. [LangGraph](https://docs.langchain.com/oss/python/langgraph/persistence), LangChain’s framework for graph-based workflows, can persist state so interrupted work can resume. [LangSmith](https://docs.smith.langchain.com/evaluation/tutorials/agents), LangChain’s testing and monitoring service, can evaluate a final response, a route of tool calls, or one step in isolation. I think the unresolved layer is narrower: these mechanisms do not decide which result in an external business system is acceptable, who may change that judgment, or what independent evidence must pass before release.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Declared state fields expose allowed values, runtime checks block forbidden actions, saved state lets interrupted work resume, and testing tools inspect behavior. Those mechanisms still need reviewed cases and accountable people to decide whether a result outside the workflow is acceptable.</p></div>

## Release evidence has to leave the graph

I use release contract to mean the preset cases, scoring rules, thresholds, and owners that decide whether a graph version ships or rolls back. A held-back case is a reviewed example kept away from graph changes until that decision. Each case should inspect the route, tool results, and outcome in the external system, because a fluent message saying “refund issued” is not proof that a valid refund record exists.

Apex’s simplest forbidden transition can fit in a small test fixture:

```yaml
case: pending-payment-blocks-refund
input: {payment_id: "p_41", request: "refund"}
setup: {payment_status: "pending"}
expect_route: [check_payment, explain_pending]
forbid_tools: [refund_tool]
expect_outcome: {refund_record: absent}
release_assertion: forbidden_tool_calls == 0
```

A trace is the complete record of nodes, tool calls, intermediate results, and outcomes for one run. A grader is code, a model-based scoring rule, or human judgment that checks part of that record. This fixture needs a code grader for the forbidden call and an outcome check against the payment system. If policy evidence conflicts and no single automated answer is defensible, a named human reviewer should choose the expected route and record the reason. The disputed judgment then becomes versioned release evidence instead of disappearing into a prompt or meeting note.

[Anthropic’s January 2026 guide to agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends starting with 20 to 50 simple tasks drawn from real failures. I think that is a sensible first-quarter boundary: choose one consequential workflow, review failures weekly, and rerun the held-back set after every graph or model change. Record route and outcome pass rates, unauthorized tool calls, weekly exception volume, elapsed human-review time, and cost per accepted review. Compared with the previous process at the same volume, those measures can reveal whether automation is reducing work or merely moving it into an expensive exception queue.

The burden of proof should rise with the system’s authority. A drafting assistant that cannot act may need sampled quality checks and a kill switch. A refund agent that can move money needs narrow amount and policy limits, repeated trials, ledger checks, human approval outside those limits, and a tested rollback to the last accepted version. I don’t know a universal threshold that makes every workflow safe. What matters is that the threshold is explicit, owned, and tested before the tool call has consequences.

Imagine a Swedish retailer using Apex. Customer operations owns the accepted refund outcome, while policy and risk resolves disputed cases and approves changes to consequential thresholds. The product release owner signs any exception and can roll back the release. The central AI platform team owns the evaluation runner, trace format, secure storage, and controls over where data may be stored; engineers implement the graph and its guards. This split lets the company reuse evidence infrastructure without pretending that a central platform team can make every local business judgment.

For systems legally classified as high risk under the [European Union’s 2024 AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj), Article 9(8) requires testing against previously defined metrics and probabilistic thresholds appropriate to the system’s intended purpose. Articles 12 and 72 address event logging and systematic monitoring after deployment. Those cited requirements generally apply from 2 August 2026 where applicable. Article 6(1) and corresponding obligations for high-risk AI used as a safety component of regulated products apply from 2 August 2027.

A refund workflow is not automatically high risk, and this is not legal advice or proof of compliance. Within the law’s limited scope, the practical connection is still clear: testing, logging, monitoring, and documented accountability have to become engineering work for applicable high-risk systems. The Act does not prescribe the release contract described here, nor does it turn rollback into a universal legal requirement.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A release contract is the preset set of cases, scoring rules, thresholds, and owners used to decide whether a workflow ships or rolls back. It should connect unfamiliar inputs to the path taken, the result in the external system, the cost of human exceptions, and a named decision owner.</p></div>

## The evidence should survive the framework

A conventional test suite contains inputs, assertions, and results. My take is that the more durable asset is an evaluation corpus: reviewed cases, expected external outcomes, traces, grader logic, accepted policy judgments, threshold history, release verdicts, and rollback records. The difference is organizational memory. A test can show what failed, while the corpus also records why the behavior was rejected and who approved the rule that replaced it.

That record needs a clean lifecycle. Cases engineers inspect while changing the graph belong in the development set. If a held-back failure guides a fix, move it into development and add a fresh held-back analogue before the next release. Otherwise the team gradually teaches to the test and mistakes familiarity for reliability.

I think portability gives this claim a fair test. Twelve months from publication, take every held-back case from one accepted release and change the primary model or graph runtime. Within one normal release cycle, rerun all of those cases without rewriting their expected outcomes or thresholds. Adapter code and trace-field mappings may change.

The resulting report should separate evidence, decision, and recovery. Evidence identifies the dataset and system versions and gives passed cases over total cases for both routes and external outcomes. The decision records thresholds, approved exceptions, and the release verdict; recovery names the rollback target. If the team must translate expected outcomes into the old framework’s concepts, omit cases from the denominator, or cannot produce the complete report within that cycle, the corpus did not outlive the stack.

There is a real counterargument. Stable outcome definitions, trace adapters, and dispute records add work before release. Tight framework coupling may be rational for a short-lived, low-impact prototype when disposal is cheaper than migration. For a consequential workflow expected to survive model and vendor changes, however, policy encoded only inside one framework can become migration debt precisely when the team needs independent evidence.

“No more prompting” should be treated like “no more code”: as a claim that an abstraction will move work, not erase it. Prompts still operate inside nodes, while graphs make state and routing visible. Even if a credible internal adoption rate were published, it would tell us something about the defaults future tools may assume, not what another organization should deploy this quarter.

I think teams should stop asking whether their graph looks sophisticated and ask what evidence survives when the graph is replaced. A production release deserves trust only when every consequential route meets unfamiliar evidence, an accountable verdict, and a tested way back.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>An evaluation corpus preserves reviewed cases, expected results in external systems, scoring logic, policy decisions, release history, and rollback records. It has survived a model or graph-framework change only if every held-back case can be rerun, with the same expected outcomes and thresholds, in a complete release report.</p></div>
