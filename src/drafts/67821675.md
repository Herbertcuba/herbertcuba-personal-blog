# The 105 minutes after the graph

“Which node in your graph has never met an input you did not write yourself?” [Jey, a developer account commenting on a workshop recording, asked on X in July 2026](https://x.com/0xJeyx/status/2081364222856831271). An agent graph is a multi-step AI workflow. Each node performs one job, while an evaluation set contains reviewed inputs and the results the system should produce.

Jey frames the workshop as 15 minutes for the graph and 105 minutes for evaluation. That is an interpretive ratio, not the official running order, but it captures the engineering lesson. The graph appears early, evaluation starts around minute 23, and a scan of the [English caption track](https://www.youtube.com/watch?v=ib-wTAvCZqg) finds the word “eval” 101 times.

The source needs correcting too. Lance Martin, an AI engineer who now works at Anthropic, delivered *Architecting and Testing Controllable Agents* at the [2024 AI Engineer World’s Fair](https://www.ai.engineer/worldsfair/2024/schedule), a developer conference, while he was at LangChain, the company behind LangGraph. [Movez’s viral July 2026 post](https://x.com/0xMovez/status/2081011657807925604) attributed “70%,” “3–6 months,” and “No more prompting” to an Anthropic engineer. Those phrases are absent from the workshop captions, and [Martin clarified that the talk predates his Anthropic role](https://x.com/RLanceMartin/status/2081408482344149047).

I think the correction makes the ratio more useful. The graph is the control plane: its nodes and connections determine what the workflow can do next. The trust plane is the typed state, a shared record whose fields accept only defined values, plus the evaluations and release rules that constrain the graph. One is easy to screenshot. The other determines whether the screenshot deserves authority.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The 15/105 ratio is a lens rather than a stopwatch reading: graph structure is quick to see, while unfamiliar cases reveal whether its routes and limits can survive production.</p></div>

## The complexity lives in fine-tuning the graph

An edge is an allowed handoff between two nodes, and a route is the sequence of handoffs chosen for one case. Complexity arrives when messy inputs meet those clean arrows.

Consider Apex, a hypothetical refund-review agent:

```text
customer request
       ↓
check payment ── pending ──→ explain pending status
       │
    settled
       ↓
check policy ── unclear ──→ human policy review
       │
     clear
       ↓
draft decision → reflection → human approval
                    │
             revise once / escalate
```

Apex needs the reflection phase because a fluent draft can still contradict the payment record, misread the policy evidence, or claim authority the graph never granted. Reflection is a separate critique node that checks those named conditions, allows one revision, and escalates if the revised answer still fails. Putting the check in its own node makes the result visible in the execution record and gives the loop an exit; asking the drafting node to “double-check” itself does neither.

This separation also keeps judgment from silently becoming authorization. HAL 9000, the shipboard AI in Stanley Kubrick’s 1968 film *2001: A Space Odyssey*, is a useful warning here: combining observation, judgment, and control inside one opaque system makes failure hard to challenge. Apex may use a model to critique a draft, but code checks and human approval keep consequential authority outside that loop.

“Fine-tuning the graph” does not mean training the model’s weights. It means changing state fields, routes, retry limits, reflection criteria, and human gates as failures expose weak handoffs. A route invariant is a rule that must always hold:

| State field | Allowed values | Release-blocking invariant |
|---|---|---|
| `payment_status` | `pending`, `settled` | `pending` can never reach refund approval |
| `policy_status` | `clear`, `unclear` | `unclear` must reach human policy review |
| `reflection_result` | `pass`, `revise`, `escalate` | `revise` may loop once; `pass` still requires human approval |

I think this is where the 105 minutes live. Each failure forces a precise decision about what Apex may know, where it may go, how often it may try, and who may stop it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Apex has reflection because drafting and checking are different jobs. Bounded critique improves one candidate answer, while typed state, route invariants, and human gates prevent that loop from granting itself authority.</p></div>

## Turn two routes into release evidence

A held-back case is a reviewed example reserved from graph changes until release evaluation. When Apex runs that case, a trace records the nodes, tool calls, and results. A grader, which may be code, a model rubric, or human judgment, compares the trace and final outcome with expectations written before the run.

| Held-back input | Expected route | Observed failure | What the grader checks |
|---|---|---|---|
| Payment pending; customer asks for a refund | payment check → pending-status reply | draft decision → refund approval | forbidden transition, final action, tool result |
| Payment settled; policy evidence is contradictory | policy check → human policy review | draft decision → reflection pass | route, cited evidence, escalation reason |

The second case matters because a correct-looking next node is not enough. Route accuracy, the share of cases sent to their expected next node, can hide a bad tool result, an unsupported decision, excessive latency, or repeated retries. I think release evidence should test the path, the outcome, and the resources consumed. Cost per successful task makes the last part concrete: divide total model and tool cost by the number of cases that pass every required check.

[Anthropic’s January 2026 guide to agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends starting with 20–50 tasks drawn from real failures. That is enough for a first release contract, provided ownership is explicit:

| Owner | First-release responsibility |
|---|---|
| Product or policy owner | writes expected outcomes and resolves disputed cases |
| Engineering | maintains the runner, trace format, graders, and cost records |
| Release owner | applies preset thresholds and orders rollback when a forbidden route appears |

A shared platform can standardize trace storage, evaluation runners, and regression checks after a model or vendor change. The workflow owner must still define what a correct refund decision means. Thresholds should follow risk: an internal drafting assistant can tolerate errors that a money-moving workflow cannot.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A route becomes release evidence when held-back cases test its path, outcome, evidence, and cost against prior expectations, with named owners for policy, engineering, approval, and rollback.</p></div>

## Let failures redraw the graph

Reflection and evaluation work at different scales. Reflection may revise one candidate run. Evaluation tests the frozen system across reviewed cases and decides whether that version can ship.

```text
real failure → reviewed expectation → development set → graph change
                                              ↓
                                         freeze version
                                              ↓
fresh held-back cases → release evaluation → ship or rollback
```

The development set contains cases engineers use while changing the graph. If a held-back failure changes Apex, move that case into the development set and add a fresh held-back case for release. Otherwise the evaluation set slowly becomes another prompt written to flatter the system.

Durable execution, a framework’s ability to save workflow state and resume after interruption, solves a different problem. Recovery preserves where Apex was. Evaluation decides whether the recovered route and result were correct enough to release. The first cannot substitute for the second.

I don’t know which graph framework will dominate. “No more prompting” is catchy in the same way “no more code” is catchy: the new layer does not remove the old one. Prompts remain inside nodes; graphs add state and routing. An unsupported 70% figure should not decide what an organization builds this quarter.

My take is that the durable asset will be the evaluation corpus, meaning the accumulated reviewed cases, policy decisions, traces, and release history. Frameworks can be replaced; rebuilding those expectations is harder because they contain the arguments an organization has already settled. I think that is the deeper lesson in the 15/105 ratio: the graph shows how an agent might work, while the evaluation set proves where it may be trusted.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Reflection improves a candidate run, durable execution preserves it, and held-back evaluation governs the system. The lasting value sits in reviewed cases and release history that can redraw the graph and stop it.</p></div>
