# The subtle art of context engineering

Which token earns its place in the next step? That question becomes urgent when a long context window tempts us to pour an entire chat, document library and tool history into every model call. More input raises cost, yet the deeper problem is attention: useful evidence must compete with everything else in the window.

[Lance Martin defines context engineering](https://rlancemartin.github.io/2025/06/23/context_engineering/) as filling that window with the right information at each step. I think the phrase “at each step” carries the argument. Token optimization becomes a workflow decision about selection, timing and retention.

This is where graph engineering helps. [Greg Isenberg distinguishes](https://youtu.be/JWhICz1QR8M?t=84) the prompt, the supplied context and the work designed around the model. A graph gives every step a smaller working set and a clear handoff. Evaluation then tells us whether that economy survives unfamiliar cases.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Context engineering allocates attention step by step. A graph makes those allocations explicit, and evaluation checks whether the missing tokens were truly expendable.</p></div>

## Give each step a smaller working set

Consider a fictional support case, order 8841. The customer requests a refund, while the ledger records a pending authorization. The first node classifies the request. A second retrieves payment facts, and another fetches the relevant policy. Each receives the order ID and its own required evidence rather than the full support history.

The shared state, meaning the compact case file carried between steps, might hold `order_id`, `payment_state`, `policy_version`, `proposed_action` and `review_required`. An edge permits movement to another job; a transition is the route this case actually takes. Conditional routing can enforce `assert route("pending") != "refund_approval"` in this proposed design.

I think typed state is a token budget with rules. It preserves fields the next decision needs while leaving incidental dialogue behind. A knowledge graph could connect the customer, order and policy as information; this agent graph controls how the case moves through work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Order 8841 carries a small, typed case file. Its payment state selects the next job, so context arrives through an enforceable route instead of a growing transcript.</p></div>

## Build the smallest useful diamond

Some work must stay sequential because classification determines which policy applies. Account verification and policy retrieval can then fan out in parallel, since neither depends on the other. Their findings merge only after a checker, acting as a skeptic, challenges the proposed refund against both sources. A human approves any action that moves money.

That diamond separates generation from review. I think asking one model call to produce an answer and certify it resembles asking HAL 9000 to audit the airlock while controlling it. The checker needs its own criteria, limited context and permission to stop the transition, even when both jobs use the same underlying model.

My take is to stop at the smallest graph that improves the decision. A private FAQ answer may need a light gate. A refund deserves stricter approval because the error is harder to reverse.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The diamond gives independent checks room to disagree before a merge. Separate review and risk-based approval improve control without filling the graph with decorative agents.</p></div>

## Persist evidence before adding orchestration

Isenberg recommends drawing and running the workflow manually first. The next level lets each job write an artifact: `ledger.json`, `policy.md`, `review.md` and a final decision record. Those files create persistent state and usable memory, meaning evidence and decisions survive the run and can be retrieved later.

I think this stage teaches the best token discipline. Pass a short finding plus a source reference across the boundary, while keeping the raw evidence available on demand. The next node receives a focused packet instead of every intermediate exchange.

Frameworks earn their place after those boundaries work. [LangGraph documents](https://docs.langchain.com/oss/python/langgraph/overview) durable execution, persistence and human review for stateful workflows. Those capabilities handle recovery and handoffs. Representative failure cases remain an engineering responsibility.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Manual runs expose weak boundaries, files preserve a reusable paper trail, and orchestration automates a route the team already understands. Compact handoffs reduce tokens without deleting evidence.</p></div>

## Test the context route on cases you did not choose

Isenberg’s video establishes the workflow case and leaves evals outside its scope. The evaluation bridge comes from Lance Martin’s [2024 AI Engineer World’s Fair workshop](https://youtu.be/ib-wTAvCZqg), [Jey’s post](https://x.com/0xJeyx/status/2081364222856831271) and [Anthropic’s agent-eval guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). Jey’s fifteen-minute graph versus 105-minute evaluation ratio is a diagnostic metaphor, since the recording runs 2:21:54. The lesson survives: diagrams photograph well, while evidence takes upkeep.

A checker reviews one run. A held-back eval set repeats that separation across inputs the builders did not select for development. Anthropic suggests beginning with 20 to 50 simple tasks drawn from real failures and combining code, model and human graders as needed. For order 8841, a deterministic grader can reject the illegal transition while a human resolves ambiguous policy language.

For one consequential customer journey, I would version the examples and freeze the held-back slice during each release cycle. Support can nominate corrected failures, the policy owner can settle disputed labels, engineering can maintain the harness, and an accountable approver can sign the model and policy record. A low-risk workflow can combine those roles. I would block a release when the money-moving guard fails.

The viral retelling claimed 70 percent adoption inside Anthropic, a three-to-six-month horizon and “No more prompting.” Those lines are absent from the workshop, which [Martin clarified predates his Anthropic role](https://x.com/RLanceMartin/status/2081408482344149047). Prompts still live inside nodes. Context still determines what they can see.

I don’t know which graph framework will dominate. I think the testable prediction is simpler: graph shapes will converge, while teams with versioned failure sets will show steadier quality across model and policy changes. A production-ready graph can name the evidence, the version, the decision it may block and the person who owns that record.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Held-back failures reveal whether lean context survives unfamiliar cases. Stable releases require a versioned set, explicit ownership and a recorded gate beside the graph.</p></div>
