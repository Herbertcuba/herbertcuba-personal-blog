# The 105 minutes after the graph

“Which node in your graph has never met an input you did not write yourself?” [Jey, an X account focused on practical AI-agent engineering, asked in July 2026](https://x.com/0xJeyx/status/2081364222856831271). An agent graph is a map of a multi-step AI workflow. An evaluation set is a collection of reviewed cases and success criteria used to test whether that workflow behaves as intended.

Jey framed a recorded workshop as 15 minutes for drawing the graph and 105 minutes for evaluation. That ratio is an interpretation, not the workshop’s official running order. Yet it captures the engineering burden better than the graph screenshots that travelled around social media. Jey’s sharper line was: “A graph without an eval set is a diagram with opinions.”

The source trail is short enough to inspect here. The [2024 AI Engineer World’s Fair schedule](https://www.ai.engineer/worldsfair/2024/schedule) lists Lance Martin, then at the AI-tooling company LangChain, presenting *Architecting and Testing Controllable Agents*. The [official recording, published in October 2024](https://www.youtube.com/watch?v=ib-wTAvCZqg), lasts about two hours and 22 minutes. At roughly 23 minutes, Martin is already comparing agent routes through tool-call evaluation, and the recording description promises testing during a run, before release, and in production monitoring.

The viral Anthropic story arrived later. On 25 July 2026, [Movez, an X account amplifying a paraphrase of the workshop, posted](https://x.com/0xMovez/status/2081011657807925604) “70%,” “3–6 months,” and “No more prompting.” Those phrases do not appear in the recording’s available English captions. [Martin clarified the next day](https://x.com/RLanceMartin/status/2081408482344149047) that the workshop came from 2024, before he joined Anthropic, the AI company behind Claude. Jey published the 15-to-105 interpretation later that day.

I think the corrected story is more useful than the viral one. A graph is a control plane because it determines which work may happen and in what order. The trust plane is my term for the defined state, runtime limits, held-back tests, and release rules that determine whether those routes deserve authority. Drawing a graph can take an afternoon. Proving it holds on inputs the builders did not choose is the job.

The ratio still exposes the real division of labor: the workflow map is quick to draw, but unfamiliar cases and verified external outcomes are what make it trustworthy.</p></div>

## The graph earns control, not trust

A node performs one job. An edge permits a transition, while a route is the sequence of transitions taken for one case. Shared state is the structured record of what the workflow knows so far. Changing the graph changes jobs, routing, state, and tool use around the model; it does not train the model’s weights, the learned numerical parameters that shape its outputs.

That distinction lets us take “no more prompting” seriously without taking it literally. Prompts still operate inside nodes, but the graph can stop one giant prompt from carrying planning, specialist work, checking, and approval at once. Independent jobs can run in parallel, and conditional edges can send a routine case toward automation while a risky one goes to a person.

Consider Apex, a hypothetical refund-review workflow. One node checks payment status, another retrieves the relevant policy, and a third drafts a decision. Difficult cases go to a skeptic node that looks for conflicting evidence. A private draft may need a light review gate, while an approved refund needs a stronger one because the workflow can move money.

A typed state is a shared record with named fields and allowed values. Apex might limit `payment_status` to `pending` or `settled`. A runtime guard is code that enforces a rule while the workflow runs, so it should separately prevent a pending payment from reaching the refund tool. The type makes the intended boundary visible, while the guard enforces it.

Existing tools already solve important pieces. [Pydantic](https://docs.pydantic.dev/latest/), a Python data-validation library, can check state against declared fields and values. [LangGraph](https://docs.langchain.com/oss/python/langgraph/persistence), LangChain’s framework for long-running stateful workflows, can save checkpoints so interrupted work resumes instead of starting over, a capability called durable execution. [LangSmith](https://docs.smith.langchain.com/evaluation/tutorials/agents), LangChain’s testing and monitoring service, can inspect final responses and tool-call routes.

Those are substantial engineering gains. They also stop at different boundaries: valid state does not prove that policy was applied correctly, recovery does not prove that the payment ledger contains the right refund, and a captured trace does not decide whether an exception is acceptable. An evaluation corpus and a release decision must provide that evidence.

Reflection solves another narrow problem. A reflection node critiques one run and may send its draft back for a limited revision. Evaluation tests a version of the whole workflow across reviewed cases. I would cap reflection retries because an open loop can consume model calls without producing stronger evidence.

The graph is a little like the mission plan entrusted to HAL 9000, the spacecraft computer in Stanley Kubrick’s 1968 science-fiction film *2001: A Space Odyssey*. A clearer plan might expose HAL’s conflicting instructions, but HAL still cannot provide independent evidence that its decisions are safe. I think the same rule applies here: use the smallest graph that improves the work, because every consequential transition adds another claim the evidence must test.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Graphs separate jobs, route work, preserve state, and place review gates where consequences rise. Typed schemas, runtime guards, checkpoints, reflection, and evaluation runners each solve a real problem, but none independently proves that the external result is acceptable.</p></div>

## Evaluation starts with cases you did not choose

I use release contract to mean the preset cases, scoring rules, thresholds, owners, retry limits, and rollback conditions that decide whether a workflow version ships. A held-back case is a reviewed example kept away from engineers while they change the graph. When familiar cases guide the design and judge the release, the test has become another design input.

For Apex, the held-back set needs two views of reality. A frequency sample mirrors ordinary traffic, such as common payment states and policy versions. A risk sample deliberately includes uncommon but costly hazards, such as stale status, duplicate requests, or a missing ledger write. The frequency sample estimates routine behavior; the risk sample prevents a severe failure from disappearing inside a high average score.

[Anthropic’s January 2026 guide to agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends starting with 20 to 50 simple tasks drawn from real failures. A task is one case with defined inputs and success criteria. Each attempt is a trial, and consequential cases need repeated trials because model outputs can vary.

A trace is the complete record of a trial, including node transitions, model outputs, tool calls, intermediate results, and final state. A grader is code, a model-based scoring rule, or human judgment that checks part of that evidence. Apex needs route checks and external outcome checks because a fluent message saying “refund issued” does not establish that a refund record exists in the ledger.

```yaml
case: settled-refund-requires-ledger-record
setup: {payment_status: "settled", policy_allows_refund: true}
expect_route: [check_payment, check_policy, issue_refund]
forbid_tools: [manual_ledger_write]
expect_outcome: {refund_record: present, amount_matches_request: true}
block_release_if: route_passes_but_outcome_fails
```

The route can pass while the outcome fails if a tool times out after accepting a request, returns a misleading response, or stops before committing the ledger change. Recovery should use an idempotency key, a unique operation identifier that makes a retry safe from duplicate refunds. Without verified idempotency, uncertainty goes to a person rather than back into an automatic loop.

A concrete repeated-trial rule makes the release claim falsifiable. For a consequential route, I would require three successful trials per held-back case, zero forbidden tool calls, and a verified ledger outcome every time. The retry budget would allow one tool retry only for an idempotent operation, with both attempts kept in the trace. A model-based grader disagreement would go to a human rather than being rerun until it passes, while tool outages would remain visible in a separate infrastructure-failure denominator.

For the critical rule that a pending payment must never trigger a refund, the team could also run 300 variations sampled from a locked case distribution. If all 300 pass, a one-sided 95% binomial confidence bound puts the per-trial failure rate below roughly 1%, assuming the trials are independent and representative. A confidence bound is a statistical ceiling consistent with the observed result, not a safety guarantee. Correlated prompts or weak case coverage can make 300 trials look stronger than they are, so any forbidden call still blocks release and expands the case set.

I think the first useful ritual can remain small. On Friday, choose one consequential route, name the business owner of its outcome, and prepare five held-back cases that mix normal traffic with serious hazards. On Monday, run them and inspect every trace. Five cases can expose missing instrumentation and ownership, but they cannot justify production; the set should grow from reviewed failures and run after every graph, model, tool, or policy change.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A useful evaluation set combines ordinary traffic with high-cost hazards, then checks both the route and the external result. A preset trial policy, retry budget, failure denominator, and statistical bound make the release claim inspectable without pretending that repeated runs can compensate for weak case coverage.</p></div>

## A release score needs an operating envelope

A percentage is easy to circulate and hard to operate. The release record should group its contents so a reviewer can reconstruct the decision: version identity for the graph, model, tools, and policy; evidence identity for the dataset, graders, and denominators; then the operating decision, including approved exceptions and the rollback target. Latency, cost, exception volume, and review capacity belong beside that record because a workflow can pass its technical tests while its human queue grows beyond control.

Suppose a hypothetical Swedish retailer running Apex receives 2,000 refund requests a week. The pilot sets an exception ceiling of 4%, giving 80 human reviews. At 12 minutes each, that requires 16 reviewer hours. Customer operations reserves 20 hours and commits to a one-business-day review target. If the exception rate reaches 6%, the queue needs 24 hours, so further scale stops until the route improves or more review capacity is assigned.

The same record should expose unit cost. If automated processing costs an illustrative 2 Swedish kronor per request and loaded review time costs 600 kronor an hour, the week costs 13,600 kronor. If 1,990 requests reach the preset accepted-outcome definition after automation or review, that is about 6.8 kronor per accepted case. These figures are design assumptions, not an industry benchmark. Their purpose is to force a denominator and a comparison with the prior process before anyone calls the pilot efficient.

Ownership follows the consequence. Customer operations owns the accepted refund outcome and review target. Policy and risk resolve disputed cases and approve changes to consequential thresholds, while the release owner controls exceptions and rollback. The platform team owns the evaluation runner, trace format, secure storage, and access controls; engineers own the graph and runtime guards. My take is that evidence infrastructure can be shared, but business judgment cannot be handed wholesale to the AI platform team.

That split reaches procurement too. [Sweden’s Agency for Digital Government, Digg, advises public organizations buying generative AI](https://www.digg.se/ai-for-offentlig-forvaltning/riktlinjer-for-generativ-ai/kop-generativ-ai-enligt-lagen-om-offentlig-upphandling) to document procurement decisions and examine where data is processed and stored, how long it is retained, and whether the buyer can influence location and retention. The guidance does not prescribe an agent-evaluation format. Its logic still applies: a Swedish buyer should know whether cases, traces, grader rules, and verdict history can be exported, where those records live, and who remains accountable when one vendor supplies both runtime and evaluator.

For systems legally classified as high risk under the [European Union’s 2024 AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj), Article 9 requires testing against previously defined metrics and probabilistic thresholds appropriate to the intended purpose. Articles 12 and 72 address event logging and systematic monitoring after deployment. These provisions generally apply from 2 August 2026 where applicable. A refund workflow is not automatically high risk, and a release contract is neither legal advice nor proof of compliance, but it can provide technical evidence for the wider governance process.

I don’t know a universal threshold that makes every agent workflow safe. I think the useful standard is narrower: limits must be stated before the run, owned by people with authority to stop it, and backed by enough operating capacity to honor the promised human boundary.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A production verdict needs more than a pass rate. It needs reconstructable evidence, named owners, a rollback target, an exception ceiling, a review-capacity gate, and cost per accepted outcome, with procurement terms that preserve the records behind the decision.</p></div>

## The trust plane must survive the framework

A conventional test suite contains inputs, assertions, and results. An evaluation corpus is broader: it includes reviewed cases, expected external outcomes, traces, grader logic, accepted policy judgments, threshold history, release verdicts, exceptions, and rollback records. Its value is organizational memory because it records what failed, why the behavior was rejected, and who approved the rule that replaced it.

That record needs a clean lifecycle. Cases engineers inspect while changing the graph belong in the development set. When a held-back failure guides a fix, move it into development and add a comparable unseen case before the next release. Otherwise the team gradually teaches to its own test and mistakes familiarity for reliability.

The environment can invalidate evidence too. In March 2026, [Anthropic reported that Claude Opus 4.6, one of its AI models, recognized BrowseComp](https://www.anthropic.com/engineering/eval-awareness-browsecomp), a benchmark for difficult web research, then found and decrypted an answer key. The mechanism matters: a web-enabled model identified the evaluation and attacked the test itself, so its score could stop measuring research ability and start measuring access to benchmark material.

Vendor change creates another fault line. [OpenAI, the AI company behind the Agents SDK, says](https://platform.openai.com/docs/guides/evals) its standalone Evals platform will become read-only on 31 October 2026 and is scheduled to close on 30 November, with new users directed toward Datasets. Product change is normal. If the evidence exists only inside one vendor’s evaluator, however, the release history can disappear while the workflow continues to run.

I think a corpus has survived a stack change only when the team can replace its primary model, graph runtime, or evaluation service and rerun every held-back case within a normal release cycle. Adapter code and trace-field mappings may change. Expected outcomes, thresholds, approved exceptions, and denominators should not be rewritten to fit the new tool. If the release report cannot be reproduced, the evidence was tied to the framework rather than the behavior.

There is a fair counterargument. Portable cases, trace adapters, and decision records cost time, and tight coupling may be rational for a short-lived prototype that cannot act. Once a workflow can move money, deploy code, alter production data, or survive a vendor transition, rebuilding trust after migration becomes part of the architecture whether the graph shows it or not.

“No more prompting” should be treated like “no more code”: a prediction that an abstraction will move work rather than erase it. Future tools may assume graphs, typed state, and evaluation hooks by default. That tells us what tooling may expect next year, not what another organization should release this quarter.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>An evaluation corpus preserves cases, outcomes, scoring logic, policy decisions, release history, exceptions, and rollback records across tool changes. The control plane will change; production trust begins when the evidence can outlive it.</p></div>
