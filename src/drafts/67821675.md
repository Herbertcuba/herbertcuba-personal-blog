# The 105 minutes after the graph

“Which node in your graph has never met an input you did not write yourself?” [Jey asks](https://x.com/0xJeyx/status/2081364222856831271). His post turns a rounded two-hour workshop into a 15/105 split: fifteen minutes for the diagram, then 105 minutes of recurring evaluation. The ratio diagnoses the gap between drawing routes and testing them on cases the designer did not select.

The [official recording](https://www.youtube.com/watch?v=ib-wTAvCZqg) lasts about 2 hours 22 minutes; the [2024 conference schedule](https://www.ai.engineer/worldsfair/2024/schedule) lists Martin with LangChain. YouTube’s English auto-generated captions introduce testing around 15:36 and later return to evaluation datasets. A [Movez post](https://x.com/0xMovez/status/2081011657807925604) attributes a 70% adoption figure, a three-to-six-month forecast, and “No more prompting” to an Anthropic engineer. A scan of those captions found no matches, and [Martin clarified](https://x.com/RLanceMartin/status/2081408482344149047) that the graph talk predates his Anthropic role.

The correction narrows the claim to how engineering work divides between graph design and evaluation, which I think makes it stronger. The graph is the control plane, the routes that decide which step may run next. The trust plane combines typed records with eval cases, graders, thresholds, ownership, and a release record. Jey’s sharper line survives intact: “A graph without an eval set is a diagram with opinions.”

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The 15/105 split puts the burden of proof after the diagram, where unfamiliar cases and release controls decide whether routes deserve production authority.</p></div>

## Make each risky transition testable

In [LangGraph’s Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api), a node performs one step, an edge permits a handoff, and state is the shared record used across steps. A transition is the edge chosen during a run, while typed state gives each field a defined shape that code can check.

Consider a hypothetical refund workflow. Its policy sends an order with a pending payment and required review to `payment_review`; a direct handoff to `refund_approval` is forbidden. A reserved evaluation case can state the input and expected route plainly:

```yaml
case_id: "refund-8841"
input:
  order_id: "8841"
  payment_state: "pending"
  review_required: true
  policy_version: "2026-08-01"
expected_next_node: "payment_review"
```

A route guard is code that allows or rejects a transition. These assertions test the stated rule for this case:

```python
next_node = route(case["input"])
assert next_node == case["expected_next_node"]
assert next_node != "refund_approval"
```

The test grades the handoff before money moves. If one model proposes a refund and approves its own route, HAL 9000 is both flying the ship and certifying the flight log. I think typed state earns its cost at this boundary because a policy sentence becomes a condition that code can enforce.

A focused node receives only the facts and tools needed for one decision, so `payment_review` can exclude marketing history and unrelated support conversation. Extra calls may raise token use and latency across the complete run. Route accuracy is the share of cases sent to the expected next node. Keep the split only when held-back cases meet its predeclared threshold within the run budget.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state makes a consequential handoff enforceable, while held-back cases show whether a narrower node improves accuracy within the run budget.</p></div>

## Let the eval set block release

A held-back eval set contains reserved cases kept outside graph design and tuning. Every case carries an expected route or outcome written before the run, and the test harness applies the relevant check. Once a case helps engineers change the graph, it moves into the development set and a reviewed replacement preserves the held-back partition.

[Anthropic recommends](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) starting with 20 to 50 simple tasks drawn from real failures. Begin with one consequential customer journey. Support can submit up to five reviewed failures for a weekly 45-minute triage, where the policy owner settles disputed outcomes. A dataset maintainer freezes the release set, engineering owns the harness, and an accountable approver signs or blocks the release. Keep policy judgment and release approval with different people when money moves.

A release record turns those roles into an audit trail. It connects one evaluated model and prompt to the applicable policy, frozen dataset, grader settings, threshold result, and approver. A reviewer can then reproduce order 8841, trace why the version shipped, and trigger rollback or human review after a regression. I think this is the smallest credible trust plane for a consequential graph.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Release readiness requires reserved cases, controlled dataset changes, a threshold, and an approval record connecting one evaluated version to one decision.</p></div>

## Tooling will converge before evidence does

[Graph frameworks](https://docs.langchain.com/oss/python/langgraph/durable-execution) can already provide routing, persistent state, and recovery after an interrupted run. I think those mechanics will become easier to copy over the next year. Failure-derived eval sets will remain specific to the workflow, its policy, and the harm caused by a wrong route.

Test that prediction by comparing two groups running workflows of similar risk on the same independent audit set after each model or policy change. One group gates releases on versioned, failure-derived cases; the other relies on examples written by the graph’s developers. The route-regression rate is the share of formerly correct cases now sent to the wrong node. A lower quarterly rate for the held-back-gate group would support the prediction; an equal or higher rate would falsify it.

The phrase “No more prompting” echoes the old promise of no more code. Prompts remain inside the nodes, while graphs add state, route guards, and release decisions around them. A verified internal adoption figure could forecast defaults in next year’s tools. This quarter’s release still depends on failure cost and available evidence.

I don’t know which graph framework will dominate. My take is to start with the smallest graph for one consequential journey, then give its risky transitions reserved cases and a named release owner. When a model or policy changes, those cases must run against the recorded threshold before a fresh approval can expose the new route to customers.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>After a model or policy change, versioned cases and a threshold let the approver defend or block the release before customers meet the new route.</p></div>
