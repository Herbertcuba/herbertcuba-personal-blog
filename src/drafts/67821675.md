Last week a clip from a two-year-old workshop went viral. Lance Martin, now at Anthropic, teaching agent graphs at the AI Engineer World's Fair 2024, a talk from before he joined the company. Half a million views. The takeaway spreading across my feed: 70% of Anthropic engineers already run self-improving loops, and within a few months we'll all build graphs instead of writing prompts. No more prompting.

I tried to find that number in the actual workshop material before writing this. I couldn't. No transcript, no slide, no post from Lance contains it. It is a paraphrase of a paraphrase. Lance himself replied to the thread, laughing that the talk is from 2024.

So I set the 70% aside and looked at what the workshop actually does. That is where the real story lives.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The viral number cannot be verified, and I stopped trying. The workshop itself tells the better story: the graph diagram takes 15 minutes, evaluation takes the other 105. Drawing the graph is an afternoon. Proving it survives inputs you did not choose is the job.</p></div>

## The claim worth arguing with

Forget the clip farm for a moment, because the strong version of the claim deserves a real answer. Prompting as an interface really is shrinking. Two years ago the prompt was the whole artifact. Today it is one field inside a node, and the node is one box inside a graph. The center of gravity moved from wording to wiring.

That part I think is true. The leap I don't believe is "no more." Software has made this promise at every abstraction layer, and the layer below always survived. We still write SQL decades after the tools that were going to kill it.

So here is my version of the prediction, dated 2 August 2026, so you can hold me to it. Within twelve months, at least one major agent framework ships a starter template where the eval folder is generated next to the graph, the same way Rails once generated a test directory for you. Watch the LangGraph release notes. If I am wrong, I will write about that too.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The serious claim is that prompting is shrinking into one field of a larger spec, and that part holds. The checkable prediction: within a year, a major framework scaffolds your eval set the day it scaffolds your graph.</p></div>

## What a graph actually is

If you have never built one of these, the whole thing fits in one picture. Imagine a support inbox agent that reads an email, classifies it, retrieves the right help docs, drafts a reply, and hands anything weird to a human:

```
             ┌───────────┐
 email in ─▶ │ classify  │
             └─────┬─────┘
                   ▼
             ┌───────────┐
             │ retrieve  │
             └─────┬─────┘
                   ▼
             ┌───────────┐     confidence low?
             │  draft    │ ──────────────┐
             └─────┬─────┘               ▼
                   ▼              ┌────────────┐
              send reply          │ escalate   │
                                  └────────────┘
```

Each box is a node, one step of the job. The arrows are edges, the allowed transitions. In LangGraph, the Python library Lance helped build at LangChain, you start with a StateGraph: a container that holds your nodes and edges. All nodes share one state, defined as a TypedDict, a plain Python dict where you declare the fields and their types up front:

```python
class InboxState(TypedDict):
    subject: str
    body: str
    category: str
    docs: list[str]
    draft: str
```

The classify node reads `subject` and `body`, writes `category`. The retrieve node reads `category`, writes `docs`. Every node sees the same typed state, so nothing travels as a mystery string.

Inside each node, the model usually runs a ReAct loop, from the 2022 paper of that name: the model reasons, calls a tool, looks at the result, reasons again. The graph is the outer structure. ReAct is what happens inside one box.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A graph is your agent's workflow made explicit: nodes are steps, edges are allowed moves, and a typed state object carries the data between them. You can draw one in an afternoon, which is exactly the point of the next section.</p></div>

## Fifteen minutes of drawing, 105 minutes of proof

Another attendee, an engineer named Jey, posted a different summary of the same workshop, and it barely spread. His observation: the diagram is finished in the first fifteen minutes. Evaluation shows up at 23:06 and keeps coming back, until the closing section is literally building eval datasets for the graph you drew in the first quarter of an hour.

```
 0 min          15 min                                          120 min
 |██████████████|****************************************************|
 [ draw the graph ] [ evaluation, evaluation, then build the eval set ]
```

Everyone screenshots the graph. Almost nobody ships the eval set.

That ratio is the whole story about where agent engineering actually lives. Half a million people will look at your graph. A few thousand will ever look at your golden dataset. Yet the second artifact is the one that decides whether the first one survives contact with real users.

Jey's phrase for it, and the best line to come out of the whole thread: a graph without an eval set is a diagram with opinions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The workshop's own time budget is the argument: 15 minutes of architecture, 105 minutes of evaluation. Drawing is the demo. The eval set is the job.</p></div>

## What an eval set looks like up close

An eval set (or golden dataset) is a folder of real inputs paired with the outcomes you expect, plus a way to score what the agent actually did. For the support inbox agent, a starter version looks like this:

```
evals/
├── 01_billing_angry.yaml      → expect: escalate
├── 02_password_reset.yaml     → expect: draft from doc KB-114
├── 03_spanish_refund.yaml     → expect: retrieve ES docs
├── 04_vague_question.yaml     → expect: escalate
└── 05_legal_threat.yaml       → expect: escalate, flag legal
```

Run the graph against all five and grade the outcomes. Here is the part that matters: my example set catches a failure the demo never shows. Case 03 classifies perfectly. Then retrieval silently returns nothing, because the help docs only exist in English, and the draft node writes a generic reply in Spanish about a refund policy it never actually read. Four of five pass. The fifth fails in a way no trace of the demo would ever surface, because the demo only ever met inputs its author picked.

One honest caveat: five cases is a workshop exercise, not a production gate. Real sets start at dozens and grow from whatever broke last week. Anthropic's own guidance points at 20 to 50 tasks drawn from real failures, and Hamel Husain's trace-review workflow is the practice of reading actual runs to find those cases. Chip Huyen and Anthropic's engineering blog have been writing versions of this sermon since 2024. None of this is new. Most teams still skip it.

I don't know how to make evals cheap. I think nobody does yet. The workable answer is that they start small and grow from production failures, one embarrassing case at a time.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>An eval set is real inputs, expected outcomes, and a scorer. It exists to catch the failure your demo never met, like the Spanish email that retrieves nothing and drafts anyway. Start with dozens of cases pulled from real failures, then keep growing it.</p></div>

## The trust plane is also the compliance plane

In the typed-state article I argued that graphs are the control plane and types with evals are the trust plane. The control plane is where the demos live, and the trust plane is where the renewals live. Procurement never asks to see your graph. They ask what happens when it fails.

There is now a harder reason to care, and the date of this post is not a coincidence. Today, 2 August 2026, the EU AI Act's obligations for high-risk systems start applying. Articles 9, 15, and 17 ask for risk management, accuracy and robustness testing, and a quality management system with records. An eval set with dated scoring runs is almost exactly the evidence trail those articles describe. The 105 minutes are also your conformity file.

And because "budget the 105" is a slogan until it has a number, here is a directional envelope from what I have seen: collecting and labeling 30 to 50 real cases takes one to two person-days. Re-running and reviewing the set costs about half a day per release. Call it three to five person-days per agent per quarter. Priced against one production incident in a regulated environment, that is the cheapest insurance on the roadmap.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The eval set is engineering hygiene, customer evidence, and as of today, regulatory evidence under the EU AI Act. Budget it like a line item: a few person-days per agent per quarter, against the cost of the incident it prevents.</p></div>

## What breaks when everyone ships eval sets

Now the part I think almost nobody is pricing in. Suppose evals-first wins, and I hope it does. The moment every team ships a golden set, the golden set becomes the target. Goodhart's law walks in: when a measure becomes a target, it stops being a good measure.

The failure modes are already visible if you look for them. Eval cases leak into training corpora, so the model has quietly seen your test. Vendors start selling eval-gaming the way they once sold SEO, tuning your agent to ace your set while real-world behavior drifts. Curated sets go stale while your users change. The score climbs. The product doesn't.

```
 golden set leaks or gets gamed
              ▼
 agent learns the test
              ▼
 eval score climbs, real behavior doesn't
              ▼
 the number you trusted now lies to you
```

My prediction for the tooling that emerges against this: held-out sets nobody on the team can see, canary cases rotated every release, provenance tracking so each case carries an auditable history, scoring runs stored as signed artifacts. Eval defense becomes a category the way test infrastructure did.

In The Matrix, Tank and Dozer sit at the monitors watching the code rain down. The crew trusts them because they read the screens. An eval set is your operator at the monitors. The day the operator starts reading a feed the enemy controls, you are inside someone else's test.

Which brings me back to Jey's question, the one I have been turning over since: which node in your graph has never met an input you didn't write yourself? My take: answer it this week, build the set that fixes it, then defend that set like it is production code. A graph without an eval set is a diagram with opinions. An eval set nobody defends is an opinion with a score.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>When evals-first becomes orthodoxy, the golden set becomes the target: leakage, gaming, staleness. The next tooling wave is eval defense. Build the set, then defend the set.</p></div>
