Context engineering starts with an unglamorous fact: every model call has a budget. A token is a small unit of text, and a context window is the amount a language model can consider in one call. Give the model everything and you pay for repetition while making the important evidence harder to find.

The useful move is to design what each step can see. Prompt engineering shapes an instruction. Context engineering selects the evidence, tools, rules, and prior decisions available to that instruction. Graph engineering controls when those steps run and what they pass forward.

That hierarchy matters. A clever prompt cannot rescue a workflow that reloads forty interview transcripts at every step or forgets the approved facts between steps.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Optimize token use by controlling what enters each model call, then use a graph to preserve only what the next step needs.</p></div>

## Start with the work, not the graph

In a [2026 graph-engineering walkthrough](https://youtu.be/JWhICz1QR8M), host Greg Isenberg makes the practitioner case for designing work around AI instead of stretching one chat across an entire job. The multiplier promised by the video's title is marketing, not a measured result. The useful idea is much more grounded: make the workflow visible before automating it.

Suppose the job is to prepare a launch briefing from forty customer interviews, a pricing sheet, and a product memo. First perform the workflow manually and notice the real steps: find evidence, compare it, form a recommendation, challenge it, and approve it. Next, make each handoff a file artifact, such as a table of claims with source pointers. Only then should orchestration software connect those artifacts into a repeatable flow.

This manual work → file artifacts → orchestration ladder saves tokens because later steps can read compact findings instead of the full conversation that produced them. It also exposes where information is being lost.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Turn a proven manual workflow into explicit files before automating it; artifacts make both context cost and missing information visible.</p></div>

## Draw the smallest useful graph

An agent graph maps work, while a knowledge graph maps entities and relationships in information. In the agent graph, a **node** performs a bounded task, an **edge** permits movement to another node, and a **transition** hands an output across that edge. **Shared state** is the structured record that nodes can read or update; **conditional routing** chooses the next edge from what that record says.

For the launch briefing, an interview-analysis node and a pricing-analysis node can run in parallel. Their compact outputs merge into a drafting node, forming the familiar diamond topology: fan out, do independent work, then merge. A sequential path is better when one step genuinely depends on the previous result.

| Graph move | Briefing example | Context rule |
|---|---|---|
| Parallel fan-out | Analyse interviews and pricing separately | Give each node only its own sources |
| Merge | Build one evidence table | Pass findings and source pointers, not raw chats |
| Conditional route | Send weak claims back for retrieval | Load only the missing evidence |
| Checker | Challenge the finished recommendation | Keep its instructions separate from the drafter's |

That last separation matters. A checker or skeptic node can catch unsupported claims because it receives a different job and a cleaner context. The diagram remains small, but the hard work moves into tuning the boundaries, return paths, and conditions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The best graph is not the busiest one. Use sequence, parallel diamonds, routing, and skepticism only where each changes the result.</p></div>

## Keep memory smaller than history

Persistent state means useful information survives beyond one model call. It should not mean replaying the full chat forever. For the briefing, retain approved claims, source locations, unresolved questions, and the current artifact version. Retrieve raw interview passages only when a node needs to inspect them again.

Human gates should follow risk. An internal draft may proceed automatically, while a public price claim or legal statement should stop for named approval. This is why the [APEX framework for Agentic Production Execution](/posts/2026-04-05-apex-framework/) includes a reflection phase: production needs a deliberate place to inspect the artifact, decide what failed, and feed that learning back into the workflow.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Durable memory stores decisions and evidence pointers, while human review appears where the cost of a wrong transition becomes material.</p></div>

## A checker is one run; an eval set is evidence

Isenberg's video contains no discussion of evals, so the attribution boundary should stay clear. His material explains how to organise work around AI. The proof layer comes from separate sources.

Lance Martin, then an engineer at LangChain, the company behind a toolkit for language-model workflows, and now at the AI company Anthropic, taught *Architecting and Testing Controllable Agents* at the 2024 AI Engineer World's Fair conference. A [July 2026 audit by Jey](https://x.com/0xJeyx/status/2081364222856831271) compressed the workshop into a useful ratio: roughly 15 minutes to draw the graph and 105 minutes around evaluation. A transcript check puts the first eval discussion closer to minute 23, but the emphasis is still unmistakable.

A checker reviews one launch briefing. An **eval set** repeats that separation across representative test cases and scores the behavior, especially on inputs the builders did not choose. Anthropic's agent-evaluation guidance recommends beginning with 20 to 50 tasks drawn from real failures. Those cases reveal whether routing, memory, context limits, and human gates keep working after the demo.

Which node in your graph has never met an input you did not write yourself? That is probably where the next hour belongs.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Fine-tuning a graph means testing its context and routes repeatedly; one successful checker pass cannot establish that the system is reliable.</p></div>
