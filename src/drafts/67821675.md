# The subtle art of context engineering

“Which node in your graph has never met an input you did not write yourself?” [Jey asked](https://x.com/0xJeyx/status/2081364222856831271) after framing Lance Martin’s 2024 AI Engineer World’s Fair workshop as fifteen minutes of graph drawing and 105 minutes of evaluation. The recording lasts 2:21:54, so 15/105 is Jey’s diagnostic framing. It still captures the production problem: routes are quick to draw; unfamiliar cases demand sustained proof.

That ratio reframes token optimization. [Martin defines context engineering](https://rlancemartin.github.io/2025/06/23/context_engineering/) as filling the context window with the right information at each step. [Greg Isenberg adds the workflow layer](https://youtu.be/JWhICz1QR8M?t=84): a prompt shapes the request, context supplies the information, and a graph designs the work around model calls. I think a useful token serves a specific step and remains accountable in evaluation.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The 15/105 framing points to the difficult work in agent engineering: context becomes useful through an explicit route, and that route earns trust on unfamiliar cases.</p></div>

## Turn the context window into a routed case file

Take fictional order 8841. A customer requests a refund while the ledger shows `payment_state: pending`. Under this example policy, that state goes to payment review. The classifier gets the request and order ID; the payment job gets the ledger record; the policy job gets the issue type and current policy.

In Isenberg’s plain-language model, each job is a node and each allowed connection is an edge. A transition is the connection one case actually follows. Shared state is the compact case file carried across those jobs, while conditional routing reads a named field and selects the next edge. Here, `payment_state` sends `pending` to review and allows `captured` to continue toward refund approval.

A schema can restrict the handoff to `order_id`, `payment_state`, `policy_version`, `proposed_action`, and `review_required`. It limits the payload crossing an edge; the token budget is the finite context available to the next model call. I think this distinction is essential: typed state controls what travels, while evaluation checks whether those fields support the decision.

A knowledge graph models relationships among the customer, order, payment, and policy. An agent graph controls the execution path through those records, deciding which job receives evidence and when. Every handoff and branch becomes a testable claim.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A typed case file gives each node a focused working set. Named fields drive conditional routes, making token use, handoffs, and branch decisions visible to evaluation.</p></div>

## Build the smallest workflow you can inspect

Some steps depend on earlier results, so they stay sequential. Once order 8841 is classified, account verification and policy retrieval fan out, meaning they run in parallel, then merge into one proposed action. This split-and-join shape is the diamond topology.

The proposal then reaches a checker, or skeptic, with its own criteria and authority to stop the route. Isenberg gives generation and checking separate jobs. I think that gives the graph a second console. One reasoning system doing both resembles the computer in *2001: A Space Odyssey*, steering the mission and certifying its own choices.

The human gate should follow the cost of error. A low-risk internal summary can use sampled review; every refund in this example requires approval before execution. My take is to keep the smallest graph that improves the decision, since each extra node consumes tokens and creates another handoff that can fail.

Isenberg’s maturity ladder starts with a manual run. Next, each job writes an artifact such as `ledger.json`, `policy.md`, `review.md`, or a decision record. A later node gets a short finding and source reference, then retrieves stored evidence when needed. Those artifacts become workflow memory because later runs can retrieve the evidence and decision.

Automation comes after those boundaries are clear. [LangGraph documents](https://docs.langchain.com/oss/python/langgraph/overview) checkpoints, durable execution, and pauses for human review. I think those features can preserve and recover workflow state. Choosing representative failures remains the team’s job.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The smallest useful graph separates independent work from checking, stores retrievable evidence, and earns automation through risk-based human approval.</p></div>

## Make the eval set the release boundary

Isenberg provides the practitioner case for graph design and leaves eval sets outside his scope. A separate evidence chain supplies the bridge: [Martin’s workshop](https://youtu.be/ib-wTAvCZqg) repeatedly covers testing, Jey turns that emphasis into the 15/105 framing, and [Anthropic’s guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) explains agent evaluations.

A checker reviews one run. A held-back eval set repeats the challenge across cases kept outside development, testing handoff fields, branch rules, reviewer separation, and artifact retrieval. Anthropic recommends starting with 20 to 50 simple tasks drawn from real failures. For order 8841, a code grader can reject a `pending` payment reaching refund approval. A model grader can assess the policy explanation; a human resolves disputed labels.

For one consequential route, I would freeze the held-back partition for each release and version it with the model and policy. In that model, support submits corrected failures before the next release, and the policy owner resolves disputes. Engineering maintains the harness and controls dataset changes; an accountable approver signs the record naming the release and the decision it may block. A low-risk workflow can combine roles.

The viral retelling attached a 70 percent adoption claim, a three-to-six-month forecast, and the disappearance of prompting to Martin’s talk. Those claims are absent from the workshop, and [Martin clarified](https://x.com/RLanceMartin/status/2081408482344149047) that it predates his Anthropic role. I don’t know which graph framework will dominate. I think graph primitives will converge, while teams with versioned failure sets will show steadier quality through model and policy changes.

A graph is the control plane for how work moves. The trust plane combines typed state with evidence stored for evaluation, making each route auditable and reversible. Context engineering becomes serious when every consequential route has a test and every failed test has an owner.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>I would require a versioned held-back set, controlled updates, explicit ownership, and a recorded blocking decision before release. The graph routes the work; the evidence proves the route deserves authority.</p></div>
