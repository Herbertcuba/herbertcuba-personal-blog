Context engineering is easy to mistake for prompt editing. Shorten the instructions, remove duplicate examples, watch the token counter. Useful, but incomplete. The larger saving comes from deciding which step needs which information, when it needs it, and what it should leave behind.

That is where graph engineering becomes practical. In [Greg Isenberg’s 2026 video on graph engineering](https://youtu.be/JWhICz1QR8M), the entrepreneur and podcast host spends about two hours and 22 minutes exploring how to design work around coding agents such as Anthropic’s Claude and OpenAI’s Codex. His useful idea is structural: stop making one model call carry the whole job.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Token optimization becomes architectural when each step receives only the context required for its part of the work.</p></div>

## Three kinds of engineering

Consider a weekly executive briefing assembled from company reports and market news. Three related disciplines shape it:

| Discipline | The decision |
|---|---|
| Prompt engineering | What instruction should the model follow? |
| Context engineering | What evidence, rules, examples, and prior decisions should it see? |
| Graph engineering | Which step runs next, and what context moves between steps? |

The maturity path is equally concrete. First, a person performs the workflow manually. Then each stage produces a file artifact, such as `sources.md`, `draft.md`, or `review.md`, so useful context can move without dragging the full chat history along. Only then is orchestration worth adding: software coordinates the stages, retries, and approvals.

This changes the token question. Instead of squeezing the entire briefing into one context window, ask whether the drafting step needs raw search logs, or whether a compact source file with citations is enough. Usually, the artifact is both cheaper and easier to inspect.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts direct a step, context supplies its working material, and graphs control how that material moves through the workflow.</p></div>

## Build the smallest useful graph

A graph has **nodes**, which perform work, and **edges**, which connect them. Moving along an edge is a **transition**. The nodes read and update **shared state**, the structured record carried through the run, while **conditional routing** chooses the next edge from the current result.

Our briefing can begin sequentially: research → source file → draft. After drafting, it can use parallel **fan-out**, where two nodes work at once, followed by a **merge** that combines their findings:

```text
                         ┌→ Fact checker ─┐
Research → Draft → split ┤                ├→ Reflection → Human gate
                         └→ Skeptic ──────┘
```

This split-and-merge shape is often called a **diamond topology**. The checker tests claims against sources. The skeptic looks for weak reasoning, missing counterevidence, and unjustified confidence. Keeping those jobs separate reduces the chance that the same model simply approves its own draft.

An agent graph should not be confused with a **knowledge graph**, a network that stores entities and their relationships. A knowledge graph might record that a claim cites a particular report. The agent graph decides that the claim must visit the checker before publication.

Start with the smallest graph that exposes a real failure boundary. Add **persistent state**, or memory retained across runs, only for durable facts such as approved terminology, prior corrections, and source decisions. Add a **human gate**, an explicit approval point, in proportion to risk: routine formatting can flow through, while a disputed financial claim should stop.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A useful graph separates jobs, passes structured state, runs independent checks in parallel, and reserves human attention for consequential uncertainty.</p></div>

## A checker is not an eval set

Isenberg’s video provides the practitioner case for designing work around AI, but it contains no discussion of evals. The reliability bridge comes from a different source: Lance Martin, now an Anthropic engineer and formerly at LangChain, taught a 2024 AI Engineer World’s Fair workshop called *Architecting and Testing Controllable Agents*.

A [July 2026 post by Jey](https://x.com/0xJeyx/status/2081364222856831271) captured its imbalance as roughly 15 minutes drawing the graph and 105 minutes returning to evaluation. A transcript audit makes the point less tidy but stronger: evaluation begins around minute 23, and “eval” appears 101 times. The viral claims that 70% of Anthropic engineers use these loops and that everyone will follow within three to six months do not appear in the primary workshop material.

A checker node reviews one briefing run. An **eval set** repeats that separation across many defined tasks, including inputs the builders did not choose. [Anthropic’s guidance for evaluating AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends starting with 20–50 tasks drawn from real failures. Measure answer quality alongside tokens, latency, checker disagreements, and human escalations. Otherwise, a cheaper graph may only be hiding weaker work.

A graph without an eval set is still a diagram with opinions. The diagram gets the screenshot; the eval set earns the right to simplify it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A checker catches defects in one run; an eval set reveals whether the whole graph stays reliable and economical across unfamiliar cases.</p></div>

## Fine-tune the graph

The [APEX framework](/posts/2026-04-05-apex-framework/), an Agentic Production Execution operating model, includes a reflection phase for exactly this reason. Reflection turns checker and skeptic findings into a revised result or a different route, rather than leaving them as comments beside the output.

This is the subtle part of context engineering. Give the researcher broad source access, the drafter a compact evidence packet, the checker the claims and original sources, and the reflection node only the disagreements it must resolve. Preserve decisions, not conversational debris. Escalate risk, not every run.

Then tune one edge at a time against the eval set. If more context improves unfamiliar cases enough to justify its cost, keep it. If it merely makes the graph look sophisticated, remove it. Complexity belongs where the evidence earns it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Fine-tuning a graph means allocating context by job, feeding review back into routing, and keeping complexity only when repeated evaluation proves its value.</p></div>
