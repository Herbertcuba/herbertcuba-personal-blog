The most expensive incident agent may be the most well-read. Give triage the alert, full log stream, service map, runbook and chat history. Then give the same bundle to diagnosis, risk review and remediation. Every job appears informed, yet the system keeps buying the same reading time.

A context window is the finite input-and-output budget of one model call. It is measured in tokens, the pieces of text and data the model processes. Context engineering decides which evidence enters that window, what stays outside, and what leaves as a useful handoff. The goal is enough context for the decision, not the fewest possible tokens.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Better token use begins when every job receives a deliberate evidence pack instead of the complete incident record.</p></div>

## Start with the artifact

In an [August 2026 video on graph engineering](https://youtu.be/JWhICz1QR8M), technology entrepreneur and podcast host Greg Isenberg describes a useful path from human practice to automation:

| Maturity | Incident workflow |
|---|---|
| Manual | Run triage, diagnosis and review separately |
| File artifact | Each job writes a compact, inspectable result |
| Orchestrated | Software routes those results between jobs |

The middle step matters. Triage can write an incident brief containing the affected service, observed symptoms, evidence links, uncertainty and next question. Diagnosis consumes that brief and retrieves raw logs only when necessary. The team learns what a good handoff contains before a runtime makes the handoff automatic.

This is also the smallest-useful-graph discipline. Automate the first stable boundary that saves repeated context, then stop. Another node is worthwhile only when its separate instructions, evidence or review responsibility justify another model call and another place to fail.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Compact file artifacts reveal the real context boundaries before orchestration turns them into infrastructure.</p></div>

## Let the graph explain the work

An **agent graph** maps jobs and allowed handoffs. A **node** performs one job; an **edge** allows movement to another; and a **transition** is the edge taken in a particular run. **Shared state** contains the current incident facts and artifacts, while **conditional routing** chooses what happens next from that state.

```text
alert → triage ─┬→ log analysis ─────┬→ merge → skeptic → remediate
                └→ dependency check ┘             └→ human gate
```

Alert intake followed by triage is sequential work. Log analysis and dependency checking then **fan out** in parallel and **merge**. That split-and-rejoin shape is a **diamond topology**. The skeptic is a checker node with an intentionally different role: look for missing evidence, conflicting findings and unsafe remediation. Conditional routing can send a low-risk diagnostic action forward while reserving a traffic shift or data repair for a human gate.

A **knowledge graph** records relationships, such as which services depend on which databases. An agent graph moves the investigation among jobs. The first may supply evidence to the second, but they are not interchangeable.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The graph makes context ownership visible: who reads what, what they produce, and which condition permits the next move.</p></div>

## Give every transition a budget

Isenberg separates prompt, context and graph engineering. Prompt engineering shapes the instruction inside one node. Context engineering selects that node’s evidence. Graph engineering defines the handoffs among nodes. A viral July 2026 [X post by Movez](https://x.com/0xMovez/status/2081011657807925604) reduced the shift to “No more prompting,” but narrower prompts remain part of every useful graph.

Token tuning now becomes local and measurable:

| Move | Incident example |
|---|---|
| Retrieve late | Fetch the relevant log interval after triage narrows the time window |
| Compress once | Pass the incident brief, not the triage transcript |
| Cache the stable prefix | Reuse an unchanged runbook and tool description |
| Exclude by default | Keep unrelated services and old incidents outside the node |

[Prompt caching](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching) reduces repeated processing for an unchanged prompt beginning. Persistent state serves another purpose: it keeps the current incident’s artifacts across pauses and retries. Memory persists information across incidents or sessions. Treating them as one store can let yesterday’s workaround quietly shape today’s diagnosis.

Human review should increase with the consequence of the transition. Read-only inspection may continue automatically; a destructive repair should stop for approval. [APEX, an operating model for agentic production execution](/posts/2026-04-05-apex-framework/), includes a reflection phase for the same reason: a separate pass compares the proposed result with the goal and constraints before release. The subtle work is tuning these boundaries without recreating one enormous context window.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Budget context per transition, preserve current-case state deliberately, and make human gates stricter as an action becomes harder to reverse.</p></div>

## Test the budget, not only the route

Isenberg’s video explains graph design but contains no discussion of evaluations. The evidence for that next step comes separately. Lance Martin, now an Anthropic engineer and then at LangChain, taught *Architecting and Testing Controllable Agents* at the 2024 AI Engineer World’s Fair. A transcript audit places evaluation around minute 23 and counts 101 uses of “eval.” A July 2026 [post by Jey](https://x.com/0xJeyx/status/2081364222856831271) captured the emphasis as roughly 15 minutes drawing the graph and 105 returning to evaluation. That ratio is a framing, not a precise timestamp.

A checker node questions one diagnosis during one run. An **eval set** repeats that separation across cases, expected outcomes and grading rules, including held-back incidents the builders did not choose. [Anthropic’s guidance for agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends starting with 20 to 50 tasks drawn from real failures, then adding cases as new failures appear.

Measure input and output tokens per node beside diagnosis accuracy, unsafe-action rate and human-review load. Shorten an artifact, remove a log source or change a route, then rerun the held-back cases. The context improved only when resource use falls and those outcomes hold.

A graph controls where evidence travels. The eval set tells you whether each boundary still deserves trust.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A checker challenges one run; an eval set proves whether a leaner context design survives incidents its builders did not select.</p></div>
