Imagine an incident-response agent handling a failed payment service. Every step gets the alert, logs, service map, runbooks, policies, tool results, and the conversation so far. It looks informed and rereads a small novel.

A context window is the finite input-and-output space of one model call. Tokens are the pieces of text a model processes within it. Context engineering decides what enters, when it arrives, and what stays out. The useful target is the smallest view that supports the decision.

Agent graphs can give each step a different context budget. The design matters only if those boundaries survive unfamiliar cases.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>More context can raise cost while burying evidence. A graph helps when it limits each step’s view without limiting what the workflow can establish.</p>
</div>

## Three different engineering levers

A July 2026 [post by Movez](https://x.com/0xMovez/status/2081011657807925604) compressed the graph-engineering shift into “No more prompting.” The phrase travels well, but prompting remains one of three distinct levers:

| Lever | Question | Incident example |
|---|---|---|
| Prompt engineering | How should this step be instructed? | Find a probable cause and cite log lines. |
| Context engineering | What evidence should it receive? | Supply recent logs and the relevant service map. |
| Graph engineering | How should work move between calls? | Send a proposed fix through policy review. |

Greg Isenberg’s August 2026 [video about graph engineering](https://youtu.be/JWhICz1QR8M) describes the third lever as designing work around AI. A knowledge graph records relationships among entities; an agent graph routes work. Here, one identifies services connected to the payment ledger, while the other decides what investigates them.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Prompts shape instructions, context supplies evidence, and graphs control movement. Better token economics treats them as separate decisions.</p>
</div>

## Build the smallest useful graph

Isenberg offers a practical maturity ladder: perform the workflow manually, expose handoffs as file artifacts, then orchestrate stable parts. For our incident, `triage.md`, `policy-review.md`, and `action-plan.md` reveal what each step needs before automation hides the boundaries.

A node performs one job. An edge is an allowed connection; a transition is the edge selected during one run. Shared state holds current artifacts, and conditional routing chooses the next transition from that state.

```text
intake → triage ─┬→ log analysis ──┬→ checker → act
                 └→ policy review ─┘
                         ↘ human gate when impact is high
```

Intake and triage run sequentially. Triage uses parallel fan-out for two independent jobs, then a merge reunites their artifacts. This split-and-rejoin pattern is a diamond topology. A checker, or skeptic node, reviews the action plan without the draft’s whole conversation.

Add a node only for a distinct instruction, context, tool, or approval rule. Read-only diagnosis may continue automatically; production changes or possible customer-data exposure should stop at a human gate. Risk determines the gate.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Move from manual decisions to visible artifacts and then orchestration. The smallest useful graph exposes boundaries, parallel work, independent review, and human authority.</p>
</div>

## Tune the boundaries

Most token savings come from a few literal adjustments:

- **Retrieve locally.** Log analysis gets recent logs and a service map. Policy review gets the proposed action and relevant policy sections.
- **Pass artifacts, not transcripts.** A triage record carries the incident ID, suspected service, evidence links, confidence, and open questions.
- **Persist deliberately.** Persistent state saves artifacts across pauses and retries. Memory carries selected facts across incidents, rather than every old exchange.
- **Cache stable prefixes.** Prompt caching reduces repeated processing and cost for an unchanged beginning, but cannot make irrelevant context useful.
- **Measure by node.** Record input tokens, output tokens, route, latency, and review result. A cheap branch can hide an expensive merge.

Parallel fan-out creates more calls. It earns its place when narrower contexts, lower latency, or independent checks outweigh that work. Much of graph engineering’s complexity lives in these boundaries.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Local retrieval, compact handoffs, deliberate persistence, caching, and per-node measurement reduce waste. Every branch needs an economic or reliability reason.</p>
</div>

## A checker cannot prove the graph

Isenberg’s video makes the practitioner case for workflow design, but its transcript never discusses evaluation. That argument comes from separate evidence. Lance Martin, now at Anthropic and formerly at LangChain, taught *Architecting and Testing Controllable Agents* at the 2024 AI Engineer World’s Fair, a conference for AI engineers. A transcript audit found 101 uses of “eval,” starting around minute 23.

A July 2026 [post by Jey](https://x.com/0xJeyx/status/2081364222856831271) framed the workshop as 15 minutes drawing the graph and 105 minutes returning to evaluation. It captures the emphasis rather than a stopwatch audit.

A checker reviews one run. The [APEX framework](/posts/2026-04-05-apex-framework/), an Agentic Production Execution operating model, includes a reflection phase so a separate pass can challenge that run. An eval set repeats the test across held-out inputs the builders did not choose. [Anthropic’s agent-evaluation guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends starting with 20 to 50 tasks drawn from real failures.

For the payment incident, include stale runbooks, misleading logs, conflicting policies, and ambiguous ownership. Grade the route, answer, token budget, and escalation decision. A cheaper path that misses a policy conflict is no optimization.

The graph controls movement. Typed artifacts and evals make it testable. Before release, ask which node receives everything, then which node has never met an input you did not write yourself.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>A checker challenges one output; an eval set tests held-out cases. Context savings count only when route quality, risk handling, and useful outcomes survive.</p>
</div>
