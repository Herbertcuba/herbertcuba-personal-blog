How many steps in your AI workflow have only seen the tidy examples their builders wrote?

That question gets to the subtle part of context engineering. A context window is the model’s limited input space, measured in tokens, the pieces of text it processes. Filling that window is easy. Deciding which step needs which evidence, what it should save, and what it can safely forget is the engineering work.

The promise of “no more prompting” therefore misses the point. Prompts still instruct individual model calls. Context determines what those calls can know, while a graph controls how their work moves. The hard part is refining that arrangement without paying for the same information at every step.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Context engineering is information allocation: give each step enough evidence to do its job, then prove that removing the rest does not weaken the result.</p></div>

## Prompt, context, and graph answer different questions

In an August 2026 [video about graph engineering](https://youtu.be/JWhICz1QR8M), entrepreneur and podcast host Greg Isenberg spends about 26 minutes making a practical case for designing workflows around AI instead of treating an agent as one enormous chat.

| Discipline | Design question | Customer-risk briefing example |
|---|---|---|
| Prompt engineering | What should this call do? | “Summarize renewal risk.” |
| Context engineering | What should this call see and leave behind? | Supply verified account facts; return claims with sources. |
| Graph engineering | What runs next? | Research, check, revise, approve, or release. |

In an agent graph, a **node** performs a bounded job and an **edge** connects it to another node. A **transition** is the move along that edge. **Shared state** is the structured record they update, while **conditional routing** chooses the next edge from the current result. These controls make token use a design choice instead of an accident.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A prompt directs one call, context supplies its working material, and a graph coordinates calls through explicit state and routes.</p></div>

## Turn the workflow into artifacts first

Isenberg’s useful maturity ladder begins before orchestration:

1. **Manual workflow:** run the customer briefing step by step and observe where judgment changes the route.
2. **File artifacts:** save stable handoffs such as `evidence.json`, `brief.md`, and `decision.json`.
3. **Orchestration:** connect only the handoffs that are understood well enough to automate.

The resulting flow might look like this:

`intake → [account history ∥ product usage] → merge → skeptic → route`

Intake followed by research is sequential. The two research nodes then **fan out**, meaning they run in parallel, before a **merge** recombines their outputs. That split-and-merge shape is called a **diamond topology**. A checker or skeptic node reviews the merged claims independently instead of helping to write them.

This is an agent graph because it moves work. A **knowledge graph** instead stores entities such as customers and products, plus their relationships. One may supply facts to the other, but they are not interchangeable. Start with the smallest useful agent graph and add the diamond only when parallel research improves measured results.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Make the handoffs visible as files before automating them, then use sequential and parallel routes only where they improve the workflow.</p></div>

## Spend tokens where they change the decision

Persistent state is the saved record that survives node boundaries or a stopped run. Memory is the subset intentionally reused in later runs. Neither should contain every chat transcript. For the briefing, state might retain the account ID, sourced facts, unresolved conflicts, approval status, and final decision.

Each node can then receive a narrow slice. The history node gets recent account notes; the usage node gets product records and metric definitions; the merge gets their evidence; the skeptic gets the draft and its source map. This reduces repeated tokens and makes missing evidence easier to see.

The skeptic’s result drives conditional routing. Unsupported claims return to research. A low-risk internal summary can proceed, while a recommendation that could change a customer commitment goes to a human. That is a **risk-proportional human gate**: review depends on the consequence, not simply on the presence of AI. Reflection in [APEX, the Agentic Production Execution framework](/posts/2026-04-05-apex-framework/), belongs here because findings must be able to change the state, route, or context on the next run.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Save durable facts and decisions in state, pass each node a focused slice, and reserve human approval for routes with material consequences.</p></div>

## A checker reviews one run; an eval set tests the design

Isenberg’s video provides the practitioner case for graph engineering, but its transcript does not discuss evaluations. The evidence bridge comes from elsewhere. Lance Martin, then at agent-tooling company LangChain and now an engineer at AI company Anthropic, taught [“Architecting and Testing Controllable Agents”](https://www.youtube.com/watch?v=ib-wTAvCZqg), a 2024 AI Engineer World’s Fair conference workshop lasting about two hours and 22 minutes.

A [July 2026 post by the X account Jey](https://x.com/0xJeyx/status/2081364222856831271) offered a secondary reading of that recording: the graph appears within the first 15 minutes, evaluation arrives around 23:06, and the workshop keeps returning to it through the closing eval-dataset exercise. That describes the emphasis; it is not a minute-by-minute runtime audit.

A checker examines the current briefing with the context it received. An **eval set** repeats the full workflow across defined cases, expected outcomes, and scoring rules, including inputs the builders did not choose. [Anthropic’s guidance on agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends starting with 20 to 50 tasks drawn from real failures. Those cases reveal whether a shorter context lost a critical fact, whether the parallel branch helped, and how often the human-review queue will grow.

That is where context optimization becomes credible. The graph is the control plane because it routes work; the eval set is the trust plane because it supplies repeatable evidence. Refine the graph by removing context that does not improve reserved cases, adding branches only when they do, and raising a human gate when the remaining uncertainty carries real cost.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A skeptic can catch a bad briefing today; an eval set shows whether the graph, context budget, and approval rules keep working beyond the examples used to build them.</p></div>
