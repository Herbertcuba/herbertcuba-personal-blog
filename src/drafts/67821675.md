# The 105 minutes after the graph

“Which node in your graph has never met an input you did not write yourself?” [Jey asks](https://x.com/0xJeyx/status/2081364222856831271). His post frames a Lance Martin workshop as 15 minutes drawing an agent graph and 105 minutes returning to evaluation. Jey rounds the recording to two hours, making 105 minutes the remainder. The ratio illustrates where work accumulates; the [official AI Engineer recording](https://www.youtube.com/watch?v=ib-wTAvCZqg) runs 2:21:53, testing enters around [15:35](https://www.youtube.com/watch?v=ib-wTAvCZqg&t=935s), and evaluation datasets come up in the Q&A around [1:42:00](https://www.youtube.com/watch?v=ib-wTAvCZqg&t=6120s).

The source trail separates the workshop from the later hype. The [2024 conference schedule](https://www.ai.engineer/worldsfair/2024/schedule) lists Martin with LangChain. A [separate post by Movez](https://x.com/0xMovez/status/2081011657807925604) describes a 30-minute lecture and attributes a 70% adoption figure, a three-to-six-month forecast, and “No more prompting” to an Anthropic engineer. Those phrases appear in Movez’s post and produce zero matches in YouTube’s English auto-generated captions for the 2024 recording. [Martin clarified](https://x.com/RLanceMartin/status/2081408482344149047) that this workshop predates his Anthropic role.

I think the useful signal survives that correction. Graph-shaped workflows may become common, but Jey’s sharper line is that “a graph without an eval set is a diagram with opinions.” A demo-ready graph shows a route. A production-ready graph carries evidence that can stop it.

## The graph is the control plane

[Martin defines context engineering](https://rlancemartin.github.io/2025/06/23/context_engineering/) as giving each model call the right information for its next step. A graph turns that idea into a control plane, the part that decides what may run next. A node performs one job, an edge allows a handoff, and a transition is the edge selected during a run. Typed state is the structured case record those jobs share.

Consider this hypothetical refund case:

```yaml
order_id: "8841"
payment_state: "pending"
policy_version: "2026-08-01"
proposed_action: "refund"
review_required: true
expected_next_node: "payment_review"
```

A route guard can enforce the recorded expectation with `assert route(case) == case.expected_next_node`. Under this fictional policy, a direct transition from `pending` to `refund_approval` fails. If one model call can propose and approve the refund, the design gives HAL 9000 both the flight controls and the accident review.

Focused nodes can reduce irrelevant context, yet extra calls and repeated retrieval can raise total token use. Measure tokens across the complete run alongside route accuracy, the share of cases that reach the next node specified before testing. The policy owner sets those expected routes and the acceptable false-escalation rate. I think context optimization begins at this boundary: spend tokens where a distinct decision needs distinct evidence, then verify the route that follows.

## The eval set is the trust plane

A checker examines one run. A held-back eval set repeats that examination across reserved cases kept outside graph design and tuning. When a case informs a workflow change, it moves into the development set and needs a fresh held-back replacement. Otherwise, the team is rehearsing the test it claims to pass.

[Anthropic recommends](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) starting with 20 to 50 simple tasks drawn from real failures. For the refund graph, code checks the route and final ledger state, while a model grader compares the explanation with a written rubric. Before testing, the policy owner records the expected outcome and threshold for each eval case. Deployment is blocked when a critical assertion disagrees with that pre-recorded outcome or route accuracy falls below its threshold; escalation to human review can pass when it is the expected outcome.

Start with one consequential customer journey. Each week, support submits a small batch of reviewed incidents, the policy owner resolves disputed labels, engineering owns the test harness, and an accountable approver signs the release record. A dataset maintainer versions the examples and keeps the held-back partition unchanged during the release cycle. Lower-risk workflows may combine roles, while money movement deserves separation.

The release record binds the model and policy versions to the frozen dataset, grader settings, results, and approver. A reviewer can rerun order 8841 against that case and policy version, reproduce the route decision, and see who accepted it. That makes the boundary auditable and gives the team a clear point for reversal when a model or policy change breaks it. I think typed state and held-back evaluations form the trust plane because they make release decisions reproducible.

## The work starts after the diagram

Frameworks can supply graph primitives, persistent state, and recovery after failure. Representative failure cases still come from your own operation. I think teams with versioned held-back sets will see fewer route regressions, where a formerly correct case reaches the wrong next node, after a model or policy change. Comparing that rate across releases makes the prediction testable.

The phrase “No more prompting” repeats the old “no more code” fantasy. Prompts remain inside the nodes, while engineering expands into state schemas, route guards, graders, dataset control, and release decisions. The work moves into a larger system.

I don’t know which graph framework will dominate. My take is to begin with one consequential journey and the smallest graph that improves it. Give each critical route a held-back case and a deterministic assertion where possible, then bind the result to an accountable release record. Drawing a graph is an afternoon; proving it holds on inputs you did not choose is the job.
