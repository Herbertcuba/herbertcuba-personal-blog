How much of your agent’s context does its next step actually need?

If the answer is “the entire conversation,” you probably have an allocation problem. A context window is a model’s finite combined input-and-output token budget; tokens are the pieces of text and data the model processes. Copying the same giant packet into every call spends that budget repeatedly and makes every step sort through material it cannot use.

Context engineering decides which instructions, evidence, and saved state belong in each call. The goal is the smallest sufficient context, with enough room left for a useful answer. Graph engineering makes that allocation visible.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Token optimization starts by deciding what each step needs to know, what it should produce, and what it can safely forget.</p></div>

## Separate the three design problems

In an [August 2026 video](https://youtu.be/JWhICz1QR8M), entrepreneur and podcast host Greg Isenberg makes a practical case for designing work around AI instead of running one enormous chat. His distinction is useful:

| Discipline | Question | Supplier-review example |
|---|---|---|
| Prompt engineering | How should this step behave? | “List unresolved security risks.” |
| Context engineering | What should it know now? | Give it the security questionnaire, not the pricing appendix. |
| Graph engineering | What happens before and after? | Route unresolved risks to independent review. |

Imagine an agent assessing a software supplier. The intake step needs the request and policy. A security reviewer needs technical evidence. A financial reviewer needs accounts and pricing. Giving every step every document is easy, but it is not careful engineering.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts shape one step, context supplies its working evidence, and a graph controls the handoffs between steps.</p></div>

## Draw the smallest useful graph

A node is one job. An edge connects jobs, while a transition moves the work along that edge. Shared state is the structured record all relevant nodes can read or update; conditional routing chooses the next node from what that record says.

```text
                 ┌→ security research ─┐
intake → scope ──┤                     ├→ synthesis → skeptic → approval
                 └→ financial research ┘
```

Intake and scope are sequential because one depends on the other. The two research jobs can fan out, meaning they run in parallel, then merge into one synthesis. That split-and-merge shape is a diamond topology. The skeptic is a checker node with a separate role: challenge unsupported claims rather than defend the draft it just wrote.

Do not confuse this with a knowledge graph, which stores entities and relationships such as suppliers, owners, controls, and incidents. An agent graph moves work among jobs. They can cooperate, but they solve different problems.

Start with the smallest graph that creates a meaningful separation of context or responsibility. Another node is justified when it needs different evidence, can run independently, or should challenge another step. Otherwise, you have converted one overloaded prompt into an overloaded diagram.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A useful graph separates work only where context, sequence, parallelism, or independent judgment genuinely differs.</p></div>

## Let artifacts carry the memory

Isenberg’s practical build order starts before orchestration software:

| Stage | What to do |
|---|---|
| Manual workflow | Run each job by hand and inspect the handoffs. |
| File artifacts | Make every job write a scoped output, such as `security-findings.md`. |
| Orchestration | Automate the route once those handoffs are stable. |

Artifacts stop the full conversation from becoming the only memory. Persistent state is the saved record that survives node boundaries or a stopped run. Memory is the subset deliberately reused in later runs. In the supplier graph, that might be the approved policy version and prior decision, not every discarded draft.

The human gate should match the risk. A low-risk renewal may continue automatically when every check passes; access to sensitive customer data should require a named approver. This is also why [APEX, the Agentic Production Execution framework](/posts/2026-04-05-apex-framework/), includes reflection: the hard work is refining what each node sees, saves, and hands over.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Manual runs reveal the workflow, artifacts reveal the context boundaries, and automation should preserve both evidence and risk-based human control.</p></div>

## A checker is not an eval set

Narrower context still needs a test beyond the graph itself. Isenberg’s video makes the practitioner case for graph design, but it does not discuss evaluations; that part of the argument comes from elsewhere.

At the AI Engineer World’s Fair in 2024, an industry conference, Lance Martin presented *Architecting and Testing Controllable Agents*, a workshop lasting about two hours and 22 minutes. Martin, now an engineer at Anthropic, the AI company behind the Claude language-model family, was then at agent-tooling company LangChain. A transcript audit finds that the workshop turns to evaluation around minute 23 and keeps returning to it. [Jey, an X writer discussing the session in July 2026](https://x.com/0xJeyx/status/2081364222856831271), sharpened the imbalance into a memorable 15 minutes on the graph and 105 on evaluation; the exact split is commentary, but the emphasis is real.

A skeptic checks one supplier report. An eval set repeats that separation across held-out cases: examples reserved from design so the builders did not choose or tune against them. Anthropic’s [guide to agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends starting with 20–50 tasks drawn from real failures. Include bad documents, conflicting evidence, cheap renewals, and sensitive-data cases, then measure whether the right route, decision, and human gate fire.

A graph without an eval set is a diagram with opinions. Refine the context or add a branch only when reserved cases show that the change improves the workflow.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A checker reviews one run; a held-out eval set tests whether the whole graph keeps its judgment when the inputs stop being friendly.</p></div>
