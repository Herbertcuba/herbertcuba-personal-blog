# The subtle art of context engineering

“Which node in your graph has never met an input you did not write yourself?” [Jey asks](https://x.com/0xJeyx/status/2081364222856831271). He describes Lance Martin’s workshop as 15 minutes of graph drawing followed by 105 minutes of evaluation. The ratio is Jey’s interpretation, but it captures the production problem: a consequential route has to survive cases the builders never selected before it can trigger a refund without human approval.

The [official 2024 recording](https://www.youtube.com/watch?v=ib-wTAvCZqg) introduces testing around [15:35](https://www.youtube.com/watch?v=ib-wTAvCZqg&t=935s) and discusses eval datasets during the Q&A around [1:42:00](https://www.youtube.com/watch?v=ib-wTAvCZqg&t=6120s). A [viral retelling](https://x.com/0xMovez/status/2081011657807925604) attached “70% of Anthropic engineers,” a three-to-six-month forecast, and “No more prompting” to that session. A search of YouTube’s English auto-generated caption track finds none of those phrases, and [Martin clarified](https://x.com/RLanceMartin/status/2081408482344149047) that the workshop predates his Anthropic role. I think the correction sharpens the useful lesson: drawing routes is quick; controlling their context and proving their behavior is the engineering work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The graph allocates work, while focused context and unfamiliar test cases determine whether a consequential route may act.</p></div>

## Budget context at the boundary

[Martin defines context engineering](https://rlancemartin.github.io/2025/06/23/context_engineering/) as filling each step’s limited context window with the right information. Token efficiency begins between jobs: each step receives decision evidence, while larger documents stay outside until a node retrieves them.

An agent graph makes those boundaries visible. A node is one job, an edge is an allowed next job, and a transition is the edge selected during a run. Shared state is the compact case record passed between jobs; conditional routing reads fields in that record to select the next node.

Consider a hypothetical refund workflow:

```yaml
order_id: "8841"
run_id: "8841-07"
intent: "refund"
payment_state: "pending"
policy_version: "2026-08-01"
proposed_action: "refund"
review_required: true
```

The classifier receives the ticket and account ID. For a refund, the payment checker retrieves a ledger excerpt while the policy node receives the exact clause for version `2026-08-01`. Both write their findings to shared state before approval.

For this fictional policy, every pending payment with a proposed refund must route to `payment_review`. A route test supplies the state above and asserts `next_node == "payment_review"`. The agent graph controls how the case moves through work; a knowledge graph would map relationships among the customer, order, and policy.

Smaller contexts can still cost more when the graph adds calls, retries, or duplicate retrieval. Measure tokens across the complete run, then compare the saving with route accuracy and approval errors. I think token optimization succeeds only when lower usage preserves or improves the decision.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Compact shared state and late retrieval give each job focused evidence, while full-run measurement shows whether the workflow actually saves tokens.</p></div>

## Build the smallest inspectable graph

With explicit state, the graph’s shape follows information dependencies. Classification runs first. Ledger and policy lookups can fan out, meaning they run independently in parallel, before a merge combines their results for the checker. A conditional edge then sends the proposed refund to human review when the recorded state crosses the policy threshold.

Letting one model propose a refund and approve its own result concentrates authority in one call. That resembles giving HAL 9000 the pilot’s controls and the incident review from the same console. A separate checker needs permission to reject or escalate the proposal, and a money-moving route should keep human approval as its final transition.

[Greg Isenberg recommends](https://youtu.be/JWhICz1QR8M?t=807) running the workflow manually and using files as persistent state before adding orchestration software. For order `8841`, `run_id` identifies one execution within that order. Storing both identifiers with every artifact lets an investigator retrieve the complete run; versioned artifacts provide the audit trail.

I think of the graph as the control plane because it decides which job runs and where the case goes. Typed state and the eval set form the trust plane: one constrains each handoff, while the other tests the resulting decisions. My take is to automate the smallest graph that improves a consequential decision, because every extra node creates another boundary to maintain.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The smallest useful graph separates generation from review, preserves every handoff, and keeps human approval proportional to the cost of error.</p></div>

## Let held-back failures block release

A checker judges one run. A held-back eval set applies the same scrutiny across cases excluded from building and tuning the workflow. Once a held-back case guides a change, it moves into the development set and needs a fresh replacement, since reusing it would make the next release result overly optimistic.

[Anthropic recommends](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) starting with 20 to 50 simple tasks drawn from real failures. In the refund workflow, code can assert that the pending-payment case reaches `payment_review`. A separate model can judge the explanation against a written rubric, which is a model grader, while a human resolves disputed labels and every high-impact judgment. Repeated trials reveal routes that behave inconsistently across runs.

Start with one consequential customer journey and fit the upkeep to its risk and volume. Support contributes corrected failures weekly, the policy owner settles expected outcomes, engineering maintains the harness, and an accountable approver signs a release record with the model, policy, and dataset versions. A low-risk flow may combine roles, but the record still names who supplied cases, resolved labels, and accepted the release. A designated maintainer controls held-back changes during each cycle to limit leakage.

I don’t know which graph framework will dominate. I think replaying versioned failures after each model or policy change will catch route drift before deployment, because the new system must face the same consequential decisions again. A successful demo shows routes on cases its builders selected; it cannot show whether those routes hold on unfamiliar cases.

A consequential graph becomes production-ready only after its named held-back set passes under recorded versions and an accountable owner accepts the decision. A graph earns authority when unfamiliar inputs have tried to break every consequential route.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Held-back failures turn context and routing choices into versioned release evidence that a named owner can use to block deployment.</p></div>
