# The subtle art of context engineering

“Which node in your graph has never met an input you did not write yourself?” [Jey asked](https://x.com/0xJeyx/status/2081364222856831271). He framed Lance Martin’s workshop as 15 minutes of graph drawing followed by 105 minutes of evaluation. The split is a diagnostic rather than a measured agenda. The 2024 recording raises testing early and returns to eval datasets; drawing a route is quick, while proving it across failures takes sustained work.

The viral retelling added claims about 70 percent adoption inside Anthropic, a three-to-six-month horizon, and “No more prompting.” Those phrases are absent from the captions, and [Martin clarified](https://x.com/RLanceMartin/status/2081408482344149047) that the recording predates his Anthropic role. I think the correction sharpens the lesson: unfamiliar inputs reveal whether a graph deserves production authority.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The ratio is diagnostic: graph drawing is quick, while unfamiliar failures expose the work needed for release.</p></div>

## Give each step a smaller case file

[Martin defines context engineering](https://rlancemartin.github.io/2025/06/23/context_engineering/) as filling each step’s limited context window with the right information. [Greg Isenberg adds the workflow layer](https://youtu.be/JWhICz1QR8M?t=84): prompts shape requests, context supplies information, and graphs design how work moves. A node is one job, an edge is an allowed handoff, and a transition is the handoff taken during a run. Shared state is the compact case file those jobs update.

Consider a hypothetical refund request for order 8841. A classifier receives the ticket and order ID. Regular code retrieves the ledger and policy into a typed state record, which restricts the fields and allowed values passed between jobs:

```text
order_id: string
payment_state: pending | captured
policy_version: string
proposed_action: review | refund
review_required: true | false
```

A conditional route reads those fields and chooses the next job. Under this example’s policy, I would assert that `pending` plus `refund` leads to `payment_review`, giving named input state an expected next state. A knowledge graph maps relationships among the customer, order, and policy; this agent graph controls movement through the work.

The reviewer receives a ledger excerpt and one policy clause instead of the whole conversation, reducing irrelevant tokens. Several narrow calls may still cost more than one broad call, so measure the full run. I think token optimization is useful when smaller contexts also improve routing accuracy or reduce unsafe behavior.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Explicit state narrows each job’s context and makes route tests precise; extra nodes can erase the token savings.</p></div>

## Keep the graph small enough to inspect

Some jobs depend on earlier results, while independent jobs can run together. Classification comes first; ledger and policy lookup can then happen in parallel. Sending work down both branches is fan-out, and combining their outputs is a merge. This creates Isenberg’s simple diamond graph shape.

A separate checker should have permission to reject the proposal. A model approving its own answer can carry one blind spot through both jobs. That resembles asking HAL 9000 to steer Discovery One and audit the flight log. The graph exposes this concentration of authority.

Separate jobs need durable handoffs. Isenberg therefore moves from a manual run to files and then orchestration software. Evidence under an `order_id/run_id` lets the checker inspect what it received and gives later runs policy history. Orchestration software carries state, selects branches, resumes failures, and pauses for approval. Frameworks can provide persistence and recovery; representative failures remain the team’s responsibility.

Light review may fit a private memo, while a refund should pause before money moves. I think the smallest useful graph removes irrelevant context, separates a meaningful check, and puts a human beside a costly decision. Automate after the manual workflow improves the result.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Preserve evidence for an independent checker, then automate; approval strictness should follow the cost of error.</p></div>

## Make unfamiliar failures the release boundary

Named state and routes create a repeatable test: given this case file, which transition follows? A checker answers once. A held-back eval set repeats the challenge across cases excluded from building or tuning the workflow. Using one for tuning makes it a development case that needs replacement.

Isenberg establishes the graph mechanics. The testing argument comes from Martin’s workshop and [Anthropic’s agent-eval guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), which recommends 20 to 50 simple tasks drawn from real failures. Code checks can grade the route, a model grader can assess the explanation, and a human can settle an ambiguous label. Repeated trials test consistency.

My take is that release pressure must never change the exam. One owner may curate cases and approve a low-risk internal workflow. For a money-moving workflow, support proposes corrected failures, the policy owner decides expected outcomes, engineering runs the harness, and a maintainer versions the held-back set after the release cycle. The approver records the model, policy, and eval versions with the deployment decision, creating audit evidence and a path to reversal.

The graph is the control plane because it moves work. Typed state and held-back tests form the trust plane because they record allowed behavior and test it. I don’t know which framework will dominate. I think nodes, branches, checkpoints, and human pauses will become ordinary features. My testable prediction is that teams with versioned failure sets will see fewer regressions after model or policy changes than teams relying on successful demos. Release a consequential workflow only when its named held-back set passes under the recorded versions and an accountable owner signs the decision.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Held-back cases turn routes into release evidence that can block deployment and support reversal.</p></div>
