# The graph takes 15 minutes. The eval set takes 105.

I tried to verify a viral story about agent graphs. The famous numbers fell apart, but one ratio survived.

A post on X claimed that 70% of Anthropic engineers use self-improving loops and that prompting would disappear within three to six months. I searched [Lance Martin's 2026 talk](https://www.youtube.com/watch?v=9QebvrrY3KY), the older workshop, and his own writing. I could not find either claim.

Lance later [said the workshop was from 2024](https://x.com/RLanceMartin/status/2081408482344149047), before he joined Anthropic. The correction is useful. The workshop is better.

Jey watched it and [pulled out the ratio](https://x.com/0xJeyx/status/2081364222856831271): roughly 15 minutes to draw the graph, then the rest of the session keeps returning to evaluation. His compressed version is 15 minutes of architecture and 105 minutes of proof.

I think that ratio says more about agent engineering than the viral numbers ever could.

<div class="article-tldr"><span class="article-tldr__label">Article TL;DR</span><p>The viral Anthropic numbers are unverified. Jey's 15/105 ratio survives: graphs make control visible, while eval sets test unseen inputs. Graph-plus-eval projects will become the framework default. Teams will learn to game the evals.</p></div>

## The graph is the easy part

A support-triage agent makes the split between control and trust easy to see.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>LangGraph gives the support agent visible routes. StateGraph holds the route, TypedDict shapes the data, and ReAct can run inside a node. The diagram still cannot tell us how the agent handles a strange message.</p></div>

Suppose we build an agent for an online store. It classifies a support message, finds the right policy, drafts a reply, and sends risky cases to a person.

LangGraph is a Python framework for building this kind of stateful workflow as a graph. Each node is a step. Each edge is an allowed route between steps. `StateGraph` is the LangGraph class that connects those nodes around shared state.

```python
from typing import Literal, TypedDict

class TicketState(TypedDict):
    message: str
    language: str
    category: Literal["billing", "technical", "spam"]
    policy_found: bool
    needs_human: bool

graph = StateGraph(TicketState)
graph.add_node("classify", classify_ticket)
graph.add_node("find_policy", find_policy)
graph.add_node("draft_reply", draft_reply)
graph.add_node("escalate", escalate)
```

A `TypedDict` is a Python dictionary with declared keys and value types. It gives every node the same contract.

Inside `find_policy`, the agent might use ReAct, short for Reason plus Act. The model picks a search tool, reads the result, then decides whether to search again. The loop ends when it has enough evidence or gives up.

We can point to every route. We still have no idea what happens when a customer pastes a spreadsheet into the message box.

## The 105 minutes become a dataset

The support agent earns trust by meeting messages its builders did not prepare for the demo.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>An eval set saves inputs with expected outcomes and scoring rules. Start with 20 to 50 cases from real failures. Treat 15/105 as a budget floor rather than a cost formula.</p></div>

Jey's line is hard to improve: "A graph without an eval set is a diagram with opinions."

For our support agent, a five-case workshop set might include a pasted spreadsheet, a message saying "it's broken," a cancellation request in Spanish, spam written like a sales lead, and a normal refund request.

Each case needs an expected outcome. The Spanish message gets the right language. Spam never reaches sales. A missing policy forces escalation. We grade the chosen route and final state.

Five cases teach the method. Production needs more. Anthropic's [agent-eval guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends 20 to 50 simple tasks drawn from real failures. Hamel Husain's [2024 guide](https://hamel.dev/blog/posts/evals/) starts from the same place: inspect traces and turn failures into tests.

I think the 15/105 ratio is a useful planning floor. I would reserve four person-days for two engineers to collect failures, define outcomes, build graders, and review the first run. Across 40 pilots, that costs 160 person-days if every team starts alone. A shared eval harness cuts repeated setup, while domain experts still define a correct refund or escalation.

ED-209 in *RoboCop* looked capable on a flat floor. One staircase exposed the missing test. Your eval set is the staircase you build before production finds one for you.

## The trust plane is also the compliance plane

The same support agent produces two kinds of engineering evidence.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Graphs and typed state form the control plane. Evals form the trust plane by giving repeatable evidence of reliability. For high-risk uses in Europe, the same artifacts can support compliance.</p></div>

The graph tells us where the ticket may go. The `TypedDict` tells us what each node may carry. I explored that layer in [The next agent wave is typed state](/drafts/9b853ab5/).

Evals answer a different question: does the route hold when the input changes? That is the trust plane. It turns a claim about reliability into a result another engineer can rerun.

For high-risk AI systems, the [EU AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj) requires testing against defined metrics and pass thresholds under Article 9. Article 17 requires documented test and validation procedures. Article 12 covers event logging. Much of that regime began applying on 2 August 2026, with some exceptions on a different timetable.

A support bot for an online store will not automatically fall into a high-risk category. If the same pattern enters a regulated decision system, the eval set and run history become part of the evidence trail.

I think this changes the budget conversation. The eval set supports releases, gives risk teams evidence, and reduces [verification debt](/posts/2026-03-09-verification-debt-crisis/) before every exception becomes a manual review queue.

## The next failure is eval gaming

With standard evals, teams and models will learn to target the test.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Golden datasets attract leakage, overfitting, and selective reporting. Blind cases, rotating tests, data-lineage records, and separate graders belong in normal infrastructure. High scores mean little after the model sees the answer key.</p></div>

A golden dataset is a stable set of examples with accepted answers. Stability helps us compare releases. It also creates a target.

Imagine that our five support cases appear in prompt examples or fine-tuning data. The agent learns those shapes. Its score rises while a Spanish message with different slang still fails, which rewards the benchmark and leaves the job unchanged.

This failure is already visible. Anthropic reported that [Claude Opus 4.6 identified BrowseComp and decrypted its answer key](https://www.anthropic.com/engineering/eval-awareness-browsecomp). The report also found leaked answers online. Research on [Chatbot Arena](https://arxiv.org/abs/2504.20879) found selective private testing, including 27 private Llama 4 variants before release.

I think eval defense needs its own engineering layer. Keep blind cases, rotate in production failures, and record where each test came from. For high-stakes systems, separate the agent team from the final release grader.

The support agent must keep meeting messages it has never seen. Otherwise the trust plane becomes another screenshot.

## Prompting shrinks into the implementation

The serious version of "no more prompting" deserves a dated prediction.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts remain inside model calls, while fewer teams use a clever prompt as the product interface. By August 2027, I expect official starters to include eval datasets and runners beside graph code and tracing.</p></div>

The strongest case for the slogan is already visible. Routes move into graphs. State moves into typed schemas. Quality rules move into graders. The prompt survives inside a node, but it stops carrying the whole system.

Today, the official [LangGraph starter](https://github.com/langchain-ai/new-langgraph-project) ships graph code, tests, and tracing hooks. It has no eval dataset or grader. The OpenAI Agents SDK [traces runs by default](https://openai.github.io/openai-agents-python/tracing/), but has no dedicated eval API.

I don't know whether both teams will use the word "eval." My prediction is specific: by August 2027, at least one official LangGraph starter and the main OpenAI agent workflow will offer a generated dataset, grader, and repeatable eval run in the default path.

I think 70% adoption inside a frontier lab, if somebody eventually verifies it, would tell us what tools may assume next year. It would say very little about what one company should ship this quarter.

For the support agent, the Monday test stays simple. Show the graph and the 20 to 50 failure cases. Name the owner of the hidden set. Then ask which node has never met an input the team did not write.

Your graph earns production one unseen input at a time.
