# The 105 minutes after the graph

“Which node in your graph has never met an input you did not write yourself?” [Jey asks in a July 26, 2026 X workshop summary](https://x.com/0xJeyx/status/2081364222856831271). An agent graph is a multi-step AI workflow; a node is one job, while an evaluation set pairs reviewed inputs with expected results.

Jey frames it as 15 minutes on the graph and 105 on evaluation. The timing is not literal, but the engineering reality holds: the graph fits in a screenshot; the evidence rarely does.

The source needs correcting. AI engineer Lance Martin delivered *Architecting and Testing Controllable Agents* at the 2024 AI Engineer World’s Fair while at LangChain, developer of LangGraph. He now works at Anthropic, maker of Claude. [Movez’s viral July 25, 2026 post](https://x.com/0xMovez/status/2081011657807925604) attributed “70%,” “3–6 months,” and “No more prompting” to an Anthropic engineer. Those phrases do not appear in the [workshop’s English captions](https://www.youtube.com/watch?v=ib-wTAvCZqg), and [Martin clarified](https://x.com/RLanceMartin/status/2081408482344149047) that the talk predates his Anthropic role.

I think the correction sharpens the lesson. The graph is the control plane, determining what can happen next. The trust plane combines typed state, a shared record of defined fields, with evaluations and release rules that constrain it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The 15/105 ratio is a lens, not a stopwatch reading: the workflow is quick to draw, while unfamiliar cases decide whether it deserves authority.</p></div>

## The complexity lives in the arrows

An edge is an allowed handoff between nodes; a route is the chosen edge for one case. Complexity appears when a messy request meets those arrows.

Consider Apex, a hypothetical refund-review agent:

```text
request → payment check ─ pending ─→ pending-payment reply
                    └─ settled ─→ policy check ─ unclear ─→ human review
                                           └─ clear ─→ draft decision
                                                          ↓
                                                   reflection check
                                             revise once / pass / escalate
                                                          ↓
                                                     human approval
```

A fluent draft can contradict payment records or policy. Apex’s reflection node therefore checks named criteria, requests one revision, or escalates. I think it earns its place only with visible criteria and an exit.

Without those limits, Apex resembles HAL 9000, the shipboard AI in Stanley Kubrick’s 1968 film *2001: A Space Odyssey*. One system would draft, judge, and authorize its answer. Models can grade, but code checks and human approval should keep authority outside the loop.

“Fine-tuning the graph” does not mean training model weights here. It means refining state, routes, limits, reflection, and human gates as failures expose weak handoffs:

| State field | Allowed values | Route invariant |
|---|---|---|
| `payment_status` | `pending`, `settled` | `pending` can never reach refund approval |
| `policy_status` | `clear`, `unclear` | `unclear` must reach human review |
| `reflection_result` | `pass`, `revise`, `escalate` | `revise` may loop once; `pass` still needs human approval |

I think the complexity lives here: every row can become a release-blocking test.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Reflection is a bounded critique step. Graph refinement turns failures into tighter state, routes, limits, and decision rights.</p></div>

## Turn one route into release evidence

A held-back case did not shape Apex. A trace records its nodes, tool calls, and results. A grader, using code, a model rubric, or human judgment, compares them with a prior expectation.

| Test record | Value |
|---|---|
| Input | Payment pending; customer requests a refund |
| Expected route | payment check → pending-payment reply |
| Observed trace | payment check → draft decision → refund approval |
| Grader result | fail: forbidden transition reached |
| Retry budget | one; preserve the first failed trace |
| Cost and latency | compare both with limits set before the run |
| Release outcome | block, fix the route, rerun the full set |

Route accuracy is the share of cases sent to their expected next node. It can hide tool failure, excessive cost, or a wrong result. I think release evidence must test path and outcome.

[Anthropic’s January 2026 guide to agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends starting with 20–50 tasks from real failures. For Apex, the policy owner writes expected results and resolves disputes, engineering maintains the runner, and a release owner applies preset thresholds. Recorded reasons stop engineers from relabelling cases merely to pass.

The first contract can require no pending-payment approvals, one retry, cost and latency limits, and rollback after a forbidden transition. Money-moving workflows need stronger evidence than internal drafting because wrong routes have real consequences.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A route becomes release evidence when held-back cases test its path and outcome against prior rules, with named owners for expectations, disputes, thresholds, and rollback.</p></div>

## Let failures redraw the graph

Reflection may revise one candidate run. An evaluation set works at system level, testing reviewed cases before the graph can ship.

```text
real failure → reviewed expectation → graph change → development test
             → frozen graph → held-back evaluation → release or rollback
```

The development set contains cases used while changing the graph. When a held-back case causes a change, move it there and add a fresh release case. Otherwise Apex learns to impress its authors.

Durable execution lets an interrupted workflow resume, while transition tests check its routes. Neither decides the right outcome when policy is ambiguous. That requires reviewed failures, accountable expectations, and someone who can stop the release.

“No more prompting” is the new “no more code.” Prompts remain inside nodes; graphs add state and routing. I don’t know which framework will dominate, and I think an unsupported 70% figure should decide nothing this quarter. My take is that tooling will converge before evidence does. A graph without an evaluation set is a diagram with opinions. Proving it holds on inputs you did not choose is the job.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Reflection improves a candidate run; held-back evaluation improves the system and controls release. Trust begins when evidence can redraw the graph and stop it.</p></div>
