# The first fifteen minutes are the graph

Jey gave the graph fifteen minutes. Evaluation kept returning.

That is the useful tension in [Jey's reading](https://x.com/0xJeyx/status/2081364222856831271) of Lance Martin's workshop. The [recording](https://youtu.be/ib-wTAvCZqg) runs longer than two hours, which makes 15/105 a framing rather than a timed agenda. The order still captures the engineering burden.

A hypothetical duplicate-charge request can fill a neat diagram quickly. Pending card authorizations, multilingual requests and tickets routed into the wrong branch expose a harder system. I think agent engineering begins when those cases enter the room. Jey puts it more sharply: "Which node in your graph has never met an input you did not write yourself?"

## A refund is larger than one model call

Put one case on the board: a customer says order 8841 was charged twice and wants a refund today.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompt engineering shapes the instruction, context engineering supplies the evidence, and graph engineering designs how the refund moves between jobs.</p></div>

[Greg Isenberg](https://youtu.be/JWhICz1QR8M) separates those three layers. The prompt tells a classifier what to decide. Context supplies the ledger and refund policy. The graph designs the work around those model calls so the case can leave one large chat.

Each node owns a job. An edge permits the next job; a transition occurs when the run takes it. Shared state is the case file carrying the order ID, payment status, cited policy and current recommendation. Conditional routing can send a shipping question away from the refund path.

A knowledge graph could map the relationships among the customer, order and payment. The agent graph moves order 8841 through work. One describes connected information. The other controls handoffs.

## The useful shape is a diamond

Order 8841 contains work that must wait and work that can happen together.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Classify first, verify evidence in parallel, challenge weak claims, then merge the result for a risk-proportional human decision.</p></div>

Classification is sequential. Ledger verification and policy lookup can fan out in parallel, then feed a skeptic that challenges unsupported claims. The surviving evidence merges into a proposed action before a human approves money movement. This is the diamond topology Isenberg describes.

I think the checker needs its own context and criteria. A generator reviewing its own answer can preserve the same blind spot in cleaner language. Separating review gives the graph a place to reject weak evidence before the recommendation reaches a person.

Approval should follow risk. A delivery-status reply can use a light gate. A refund pauses for a named person who can inspect the ledger, policy evidence and proposed amount.

## Let the artifacts survive the run

The first version of this refund route can run without an orchestration framework.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Run the workflow manually, preserve each handoff as a file, then automate stable work. Keep the graph small and retain the evidence behind every costly transition.</p></div>

Isenberg's maturity ladder starts with people moving the case through separate lanes. Each job can then write an artifact such as `ledger.json`, `policy.md` or `review.md`. When later runs retrieve those files, they become a paper trail and a practical form of memory.

Once the handoffs stabilize, a framework such as [LangGraph](https://docs.langchain.com/oss/python/langgraph/overview) can orchestrate branches, checkpoints and paused human review. I think automation earns its place when it removes a known delay from a workflow the team understands. Extra nodes add coordination cost, so the target is the smallest graph that improves the refund decision.

My suggested enterprise split is simple. The support owner defines acceptable outcomes. A platform engineer owns route and state. An independent eval owner controls held-back cases, while a release owner decides whether the version advances.

## A checker cannot certify a release

Saving order 8841 proves one run and leaves the next version largely untested.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A checker reviews one refund. An eval set repeats that separation across unfamiliar cases and turns corrected failures into release evidence.</p></div>

The source correction comes first. Martin recorded the workshop at LangChain and later [said it predated Anthropic](https://x.com/RLanceMartin/status/2081408482344149047). A separate [viral post](https://x.com/0xMovez/status/2081011657807925604) supplied the 70% Anthropic claim, the three-to-six-month forecast and "No more prompting." Searches of the workshop and five audited Martin posts found neither claim.

I think the hype points toward a real shift while offering no adoption benchmark. Prompts remain inside classifiers and checkers. Graphs place them inside an explicit workflow. That may shape next year's tools without setting this quarter's roadmap.

Isenberg makes the practitioner case for workflow design and leaves eval sets outside his video. The bridge comes from Martin's workshop, Jey's framing and [Anthropic's eval guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

Anthropic calls one input with success criteria a task, and each attempt a trial. A grader inspects the trace, the outcome or both. Its guidance recommends beginning with 20 to 50 simple tasks drawn from real failures.

For this refund route, include a duplicate settled charge, a pending authorization, a Spanish request and a shipping question routed into refunds. A code grader should fail a trial where a pending payment reaches refund approval. A model grader can check whether the explanation cites policy and gives the customer a next step. A human decides ambiguous policy.

My recommendation for higher-risk flows is a held-back slice under independent ownership. Repeat key trials between releases, then add corrected production failures. A one-page release record can retain the version, held-back results, unresolved failures and signer. This makes [verification debt](/posts/2026-03-09-verification-debt-crisis/) visible and gives [agent-layer ownership](/posts/who-owns-the-agent-layer/) a concrete decision.

I think of the graph as a control plane for order 8841. Typed state records each edge crossing, while evals test those movements across releases. Without that evidence, the control room resembles *Jurassic Park*: orderly routes meet conditions the designers never rehearsed.

I don't know how quickly agent frameworks will ship serious eval assets by default. Until they do, the team owns that work. Before a version can move money, someone should be able to show which unfamiliar refund cases it passed.
