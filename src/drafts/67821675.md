Imagine an invoice arriving 18% above its purchase order. One AI workflow receives the invoice, contract, delivery record, policy manual, email history and every previous conversation in a single prompt. The model sees everything, including plenty it does not need.

A token is a small unit of text processed by a language model, and the context window is the limited space available during one call. [Lance Martin, an Anthropic engineer who previously worked at LangChain](https://rlancemartin.github.io/2025/06/23/context_engineering/), describes context engineering as filling that window with the right information at each step. The goal is not the fewest tokens. It is the highest useful evidence per token.

That is why the viral July 2026 slogan [“No more prompting”](https://x.com/0xMovez/status/2081011657807925604) misses the interesting part. Prompts remain. The engineering shifts to deciding which one runs, what it sees and what follows.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Token efficiency comes from selecting relevant evidence for each decision, not squeezing an entire workflow into one shorter prompt.</p></div>

## Three layers, three different jobs

In an August 2026 [video about graph engineering](https://youtu.be/JWhICz1QR8M), Late Checkout chief executive Greg Isenberg separates three design problems:

| Layer | Decision being engineered |
|---|---|
| Prompt engineering | How one instruction asks for one result |
| Context engineering | Which evidence, history and tool results one call receives |
| Graph engineering | Which bounded job runs next, with what working data and authority |

For the invoice, context engineering gives a field-extraction call the invoice, not the contract archive. Graph engineering sends its result to the appropriate next job. An agent graph is this executable map of jobs and possible paths, making context selection a property of the workflow rather than a heroic prompt.

A knowledge graph maps relationships among entities, such as supplier, contract and purchase order. An agent graph maps movement among jobs. The first can supply facts to the second; it does not decide the workflow.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts shape a call, context supplies its evidence, and an agent graph controls how bounded calls work together.</p></div>

## Give every arrow a reason

A node is one bounded job. An edge is a possible path, while a transition is the actual move when a condition is met. Shared state is the common working record; conditional routing chooses the next edge from it.

```text
intake → classify
             ├→ match purchase order ─┐
             └→ confirm delivery ─────┤→ merge → checker → human gate?
```

Intake and classification are sequential because one depends on the other. The two checks then fan out in parallel and merge into one recommendation, forming a diamond topology. A checker tests that recommendation against explicit rules. On a riskier route, a skeptic separately searches for missing evidence or a reason the conclusion could be wrong.

Isenberg's practical maturity ladder is simple: run the workflow manually, save each handoff as a file artifact, then automate stable boundaries. Keep the graph small until a separate context, decision or authority justifies another node. Every extra box creates a call, transition and failure surface. Fine-tuning the graph means finding boundaries that earn that cost.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use sequential steps for dependencies, parallel branches for independent work, and add nodes only when a real boundary earns another call.</p></div>

## State needs a lifespan

Shared state should hold compact facts and references: invoice ID, amount, evidence locations, route and review status. Each node receives only the slice it needs. Persistent state survives an interruption so that run can resume; memory carries selected information across separate runs. Turning either into an endless transcript quietly recreates the swollen prompt.

Every field therefore needs a lifespan. Keep raw evidence outside the prompt and retrieve detail when needed. Route clean matches past unnecessary calls. Send conflicting evidence or high-value payments to a human gate, with human control rising alongside the consequence of a mistake.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Compact state, selective retrieval and conditional routes save tokens; explicit retention and human authority keep those savings safe.</p></div>

## Reflection has to leave the graph

Isenberg makes the practitioner case for designing work around AI, but his video contains no discussion of evaluations. The bridge comes from Lance Martin's 2024 AI Engineer World's Fair workshop, *Architecting and Testing Controllable Agents*. [Jey's July 2026 reading](https://x.com/0xJeyx/status/2081364222856831271) compresses the roughly two-hour workshop into 15 minutes for the graph and 105 for evaluation. That ratio is commentary, not the official agenda, but a transcript audit supports its point: evaluation appears from around minute 23 and returns throughout.

A checker reviews one invoice run. An evaluation set repeats that separation across held-back cases: inputs reserved from day-to-day design and paired with expected outcomes. Here those cases might include a disguised duplicate, missing delivery evidence and a supplier email telling the model to ignore policy. [Anthropic's guidance on agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends beginning with 20 to 50 tasks from real failures, then expanding with new failures.

This is why [APEX, the Agentic Production Execution framework](/posts/2026-04-05-apex-framework/), includes a reflection phase. The graph is the control plane: it decides where work goes. The evaluation set is the trust plane: it shows whether those decisions hold beyond the examples used to build them. Reflection should change the graph when context is noisy, a route is fragile or a human gate fires too late.

The diagram gets the screenshot. The evaluation set deserves the release decision because it contains disagreement, surprise and repetition. Which consequential node in your graph has met an input you did not write yourself?

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A checker can challenge one run; held-back evaluation cases reveal whether the graph's context, routes and gates survive unfamiliar inputs.</p></div>
