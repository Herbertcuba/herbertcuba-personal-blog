# The 105 minutes after the graph

“Which node in your graph has never met an input you did not write yourself?” [Jey asks on X](https://x.com/0xJeyx/status/2081364222856831271). A node is one job in an agent graph, a workflow that routes AI through several steps. Jey reads Lance Martin’s workshop as a 15/105 split: 15 minutes to draw the graph, then 105 minutes returning to evaluation. That ratio is his interpretation, not the workshop schedule.

Martin, then an engineer at the AI software company LangChain and now at Anthropic, the company behind Claude, gave the workshop at the 2024 AI Engineer World’s Fair conference. The [official recording](https://www.youtube.com/watch?v=ib-wTAvCZqg) runs 2:21:53. Its captions introduce testing around 15:37 and return to evaluation datasets around 1:42:00, so the broad lesson holds even though the clock is more complicated.

[Another X account, Movez](https://x.com/0xMovez/status/2081011657807925604), attributed “70%,” “3-6 months,” and “No more prompting” to “an Anthropic engineer.” Those phrases do not appear in the recording’s English captions, and [Martin clarified](https://x.com/RLanceMartin/status/2081408482344149047) that the workshop predates his Anthropic role. I think the correction makes the useful story clearer. The graph is the control plane: it chooses what happens next. The trust plane is the evidence and approval decision that determine whether those choices reach users.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The 15/105 ratio is a lens, not a timetable: the workflow is quick to draw, while evidence decides whether it deserves to run.</p></div>

## The complexity is in the arrows

An edge is an allowed handoff between nodes, while a route is the edge selected for one case. State is the shared record that nodes update. Typed state fixes its fields and allowed values so software can check policy.

Call the running example Apex: a hypothetical agent that reviews refund requests.

```text
request ──┬── payment check ──┐
          └── policy check ───┴── draft decision
                                      ↓
                               reflection node
                                ↙            ↘
                         revise once       human gate
```

The reflection node checks a draft against stated criteria. If it sends the draft back through the revise edge, that return route creates a reflection loop. The human gate is the final step where a person approves a risky decision. That is why Apex has a reflection phase: the first plausible answer is a candidate, not a release decision.

The checker may use code, another model, or a person. [Anthropic’s 2026 evaluation guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) describes evaluations that combine all three kinds of checker. Giving one model every quality-control role would be the HAL 9000 version of governance: in Stanley Kubrick’s 1968 film *2001: A Space Odyssey*, the fictional shipboard AI is both operator and authority. The point is separation of duties, not a ban on model graders.

I think “fine-tuning the graph” is useful if we define it. Here it means changing state fields, routes, stop rules, retries, reflection criteria, and human gates when failures reveal a weak handoff. It does not mean retraining the model’s weights.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A reflection node checks one attempt; a return edge turns that check into a loop. Graph engineering is the measured refinement of those routes and limits.</p></div>

## Turn one route into a test

Apex can make its refund policy concrete with a small state table:

| Field | Allowed values | Release meaning |
|---|---|---|
| `payment_status` | `pending`, `settled` | A pending payment cannot enter refund approval. |
| `policy_status` | `clear`, `unclear` | An unclear policy requires human review. |
| `decision` | `draft`, `approved`, `rejected` | Only the human gate may set `approved`. |

The rule is simple: `pending payment → refund approval` is blocked. Now challenge it with a held-back case, an example the builders did not use while designing the graph. A trace records the nodes, tool calls, and results from one run; a grader checks that trace or its outcome against a pre-written expectation.

| Test record | Value |
|---|---|
| Expected route | payment check → policy check → human gate |
| Observed route | payment check → refund approval |
| Outcome | no refund issued |
| Retry budget | one, recorded without erasing the first failure |
| Release | blocked until the route is fixed and the set is rerun |

Route accuracy is the share of cases sent to their specified next node. A correct route can still end with a failed tool call, excessive cost, slow response, or wrong customer outcome. I think the release record needs both route and outcome checks.

Anthropic recommends starting with 20–50 simple tasks drawn from real failures. For Apex, a policy owner settles disputed expected outcomes, engineering maintains the test runner, and a release owner applies thresholds set before the run. A first contract might require zero blocked money-moving transitions, a route-accuracy floor, a cost and latency ceiling for the reflection loop, and immediate rollback after any forbidden transition.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A route becomes releasable when unfamiliar cases test its path and outcome against fixed rules. Named owners then apply cost limits and a reversal plan.</p></div>

## Let failures redraw the graph

A reflection loop improves one run. An evaluation set tests the system across many reviewed cases, so the two work at different scales.

```text
failure → reviewed expectation → graph change → development tests
        → frozen graph → held-back tests → release or rollback
```

Once a held-back case influences a graph change, it belongs in the development set, the cases used to tune the graph. A reviewed replacement keeps the release check unfamiliar. I think this is where agent engineering becomes organizational work, because somebody must own the labels, the test runner, and the authority to stop shipping.

“No more prompting” is the new “no more code.” Prompts still operate inside relevant nodes; graphs add state and routing around them. I don’t know which framework will dominate, but the unsupported 70% figure should not decide anyone’s quarter. My take is simpler: drawing a graph may take an afternoon, while proving that its routes hold on inputs you did not choose is the job. Without an evaluation set, the graph remains a diagram with opinions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Reflection revises a candidate; held-back evaluation evidence improves the system and controls release. That trust work is where the graph earns production authority.</p></div>
