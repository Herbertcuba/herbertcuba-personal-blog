# The 105 minutes after the graph

“Which node in your graph has never met an input you did not write yourself?” [Jey asks in a July 26, 2026 X post](https://x.com/0xJeyx/status/2081364222856831271). A node is one job in an agent graph, a workflow that routes AI through several steps. An evaluation set is a reviewed collection of cases and expected outcomes used to check that workflow.

Jey reads a workshop by AI engineer Lance Martin as a 15/105 split: 15 minutes to draw the graph, then 105 minutes returning to evaluation. The ratio is an interpretation, not a literal agenda. Martin gave the workshop at the 2024 AI Engineer World’s Fair while at the AI software company LangChain; he now works at Anthropic, which makes Claude. The [official recording](https://www.youtube.com/watch?v=ib-wTAvCZqg) runs for more than two hours, with testing introduced around 15:37 and evaluation datasets returning around 1:42:00.

A July 2026 post by [Movez](https://x.com/0xMovez/status/2081011657807925604) attributed “70%,” “3–6 months,” and “No more prompting” to an Anthropic engineer. Those phrases do not appear in the recording’s English captions, and [Martin clarified](https://x.com/RLanceMartin/status/2081408482344149047) that it predates his Anthropic role. I think the correction sharpens the lesson: the graph is the control plane because it chooses what happens next; typed state and evaluation are the trust plane because they constrain those choices and support release.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The 15/105 ratio is a lens: the workflow is quick to draw, while unfamiliar cases decide whether it should run.</p></div>

## The complexity is in the arrows

An edge is an allowed handoff between nodes, while a route is the edge selected for one case. State is the shared record that nodes update. Typed state fixes its fields and allowed values so software can reject impossible or forbidden transitions.

Call the running example Apex, a hypothetical agent that reviews refund requests:

```text
request → payment check → policy check → draft decision
                                             ↓
                                      reflection check
                                      ↙              ↘
                                revise once       human gate
```

Apex needs reflection because a fluent draft can still conflict with payment status or policy. The reflection node checks explicit criteria, then routes the draft to one revision or to a person when the case is risky or unclear. Sound criteria and feedback can improve the run, but the loop guarantees nothing.

If the same model drafts, judges, and authorizes every outcome, it resembles HAL 9000, the shipboard AI in Stanley Kubrick’s 1968 film *2001: A Space Odyssey*: one system occupies every control role. Model graders remain useful, but code checks and human approval keep release authority separate.

I think “fine-tuning the graph” should mean changing fields, routes, stop rules, retry limits, reflection criteria, and human gates after failures expose a weak handoff. It is not model-weight training.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Reflection makes critique explicit and bounded. Graph engineering refines routes, limits, and decision rights rather than trusting a loop to correct itself.</p></div>

## Turn one route into a test

Apex can make its policy visible in a small state table:

| Field | Allowed values | Route rule |
|---|---|---|
| `payment_status` | `pending`, `settled` | `pending` can never reach refund approval. |
| `policy_status` | `clear`, `unclear` | `unclear` must reach a human. |
| `review_result` | `pass`, `revise`, `escalate` | Only `revise` may use the return edge. |

Now challenge the first rule with a held-back case, meaning one the builders did not use while designing Apex. A trace records the nodes, tool calls, and results from one run. A grader compares that trace or its outcome with an expectation written before the run.

| Test record | Value |
|---|---|
| Input | Payment is pending; customer asks for a refund. |
| Expected route | payment check → pending-payment response |
| Observed trace | payment check → draft decision → refund approval |
| Grader result | fail: forbidden transition reached |
| Retry budget | one; keep the original failed trace |
| Release outcome | blocked until the route is fixed and the set is rerun |

Route accuracy is the share of cases sent to their pre-specified next node. A correct route can still hide tool failure, excess cost, delay, or a wrong outcome. I think release records need path and outcome checks.

[Anthropic’s 2026 guide to evaluating AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends 20–50 simple tasks from real failures. For Apex, policy settles disputed expectations, engineering maintains the runner, and a release owner applies pre-set thresholds. The contract could require zero pending payments reaching refund approval, reflection limits, and rollback after a forbidden transition.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A route becomes releasable when held-back cases test its path and outcome against rules set in advance, with named owners for labels, evidence, and rollback.</p></div>

## Let failures redraw the graph

Reflection evaluates and may revise one run. An evaluation set tests the system across many reviewed cases, so the two operate at different scales:

```text
failure → reviewed expectation → graph change → development tests
        → graph configuration frozen before release evaluation
        → held-back tests → release or rollback
```

Once a held-back case influences a graph change, move it into the development set and add a reviewed replacement. Otherwise the release check becomes another rehearsal. I think this is where agent engineering becomes organizational work: someone must own the labels, runner, and stop decision.

“No more prompting” is the new “no more code.” Prompts remain inside nodes; graphs add state and routing. I don’t know which framework will dominate, but the unsupported 70% figure should not decide anyone’s quarter. My take: tooling will converge before evidence does. Drawing a graph may take an afternoon; proving its routes on unfamiliar inputs is the job. Without an evaluation set, it remains a diagram with opinions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Reflection checks a candidate, while held-back evaluations improve the system and control release. That trust work is where a graph earns production authority.</p></div>
