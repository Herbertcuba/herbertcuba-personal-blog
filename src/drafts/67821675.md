Every overstuffed AI request begins with a reasonable fear: if we leave something out, the model may miss it. So we paste in the policy, customer history, conversation and every tool result. The model gets more context, while the system gets less design.

Imagine a retailer handling refunds. Its first assistant receives the full policy manual, order record, payment history and support chat. Then the policy checker, risk reviewer and response writer each receive the same bundle. Every specialist rereads material it cannot use.

A [context window](https://docs.anthropic.com/en/docs/build-with-claude/context-windows) is the finite input-and-output space available to one model call; tokens are the pieces of text processed inside it. Context engineering decides what belongs there. I think the useful target is not minimum context. It is minimum sufficient context for each decision.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Token waste is usually a boundary problem: several steps repeatedly receive evidence that only one can use.</p></div>

## Context has three jobs

Prompt, context and graph engineering solve different problems. A prompt instructs one model call, context supplies its evidence, and a graph directs work across calls.

| Practice | Governing question | Refund example |
|---|---|---|
| Prompt engineering | What should this step do? | Check eligibility |
| Context engineering | What must it see? | Order facts and the matching policy clause |
| Graph engineering | What happens next? | Approve, challenge or escalate |

[Greg Isenberg](https://youtu.be/JWhICz1QR8M), a technology entrepreneur explaining graph engineering in an August 2026 video, describes that last layer as designing work around AI. He separates an agent graph, which routes jobs and handoffs, from a knowledge graph, which records entities and relationships. The retailer’s knowledge graph might connect customers, orders and products; its agent graph moves one refund through a process.

This is why “no more prompting” is too neat. Every node still needs instructions and selected evidence. The graph limits their scope and decides whether another call is worth paying for.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts direct a decision, context supports it, and graphs connect bounded decisions into a workflow.</p></div>

## Build the route before tuning the words

Start with the smallest useful refund graph. A node performs one job, an edge is an allowed connection, and a transition is the actual move along it. Shared state is the structured case record passed between nodes. Conditional routing reads that state and chooses the next edge.

```text
intake -> [policy check || risk check] -> merge -> decision -> checker
                                                    |-> refund
                                                    |-> human review
```

Intake runs first because both checks need a clean request. Policy and risk can then fan out in parallel and merge, forming the split-and-rejoin diamond topology. Parallel work may reduce elapsed time, but both calls consume tokens. If risk checking is unnecessary after a policy rejection, a sequential route may be cheaper.

The checker node acts as a skeptic: it receives the proposed decision and compact evidence, then looks for contradictions. A low-risk case can continue; an ambiguous or high-impact case pauses at a human gate. Human review should rise with the consequence of being wrong.

Token control now becomes concrete:

- Retrieve the relevant policy clause inside the policy node, rather than sending the full manual everywhere.
- Pass small file artifacts such as `policy-findings.json`, rather than replaying the conversation.
- Keep stable instruction prefixes unchanged so [prompt caching](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching), where supported, can reuse them.
- Persist current case state across pauses and retries; reserve memory for selected facts needed across cases.

Isenberg’s practical ladder is to perform the workflow manually, expose its handoffs as file artifacts, then orchestrate the stable parts. Every extra node adds a call, context boundary and failure route. This is also why [APEX, the Agentic Production Execution operating model](/posts/2026-04-05-apex-framework/), includes reflection: execution produces a candidate; reflection challenges it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The difficult work is tuning boundaries: what each node sees, when parallel work earns its token cost, and where skepticism or human judgment enters.</p></div>

## The 15/105 lesson

Isenberg’s video supports the workflow-design case, but it does not discuss evaluations. That argument comes separately from Lance Martin’s workshop and Anthropic’s evaluation guidance.

In 2024, Martin, then at LangChain, a company building agent-workflow tools, and now at Anthropic, the developer of Claude, taught the roughly two-hour workshop [*Architecting and Testing Controllable Agents*](https://www.youtube.com/@aiDotEngineer/search?query=Architecting%20and%20Testing%20Controllable%20Agents) at AI Engineer World’s Fair. [Jey, an AI engineering commentator on X](https://x.com/0xJeyx/status/2081364222856831271), compressed its shape into a memorable ratio: about 15 minutes for the graph and 105 for evaluation. That is framing rather than a literal chapter split; the transcript reaches explicit evaluation around minute 23. The ratio still captures where the work accumulates.

The viral 70% adoption and three-to-six-month forecasts do not appear in Martin’s workshop transcript or related posts. They are not an engineering roadmap.

A checker inspects one refund run. An eval set repeats that separation across representative and difficult cases, including real failures and cases held back from graph tuning. [Anthropic’s guide to agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends beginning with 20 to 50 tasks drawn from real failures. The results do not prove reliability, but they show whether cheaper context boundaries preserve the outcomes that matter.

So ask Jey’s useful question: which node has never met an input you did not write yourself? Start there. Build a small held-back set, compare outcomes and token use, then refine the route. Drawing the graph is quick. Learning where it breaks is graph engineering.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A checker challenges one run; an eval set tests the graph’s context and routing choices across cases that did not shape them.</p></div>
