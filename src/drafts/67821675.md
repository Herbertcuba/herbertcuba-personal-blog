A security questionnaire arrives with 180 questions and a stack of manuals, policies, previous answers and legal guidance. Putting everything into one giant prompt can feel responsible. It is usually expensive confusion.

A token is a small unit of text processed by a language model. Every model call has a limited context window, the working space for instructions, evidence, tool results and history. Context engineering decides what deserves that space at each moment instead of assuming a larger prompt is better.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Token optimization starts with selection: each step should receive enough evidence to do its job, but no unrelated material.</p>
</div>

## Engineer the context before the graph

[Lance Martin](https://rlancemartin.github.io/2025/06/23/context_engineering/), an engineer at AI company Anthropic and a former early team member at LangChain, the company behind tools for language-model applications, describes context engineering as supplying the right information at each step of an agent's path. That makes it broader than prompt wording and narrower than designing the whole workflow.

| Layer | The question it answers | Questionnaire example |
|---|---|---|
| Prompt engineering | How should one model call behave? | Answer only from cited evidence. |
| Context engineering | What should that call see? | One question, relevant policy passages and product facts. |
| Graph engineering | Which job runs next, and what can it receive? | Retrieve, draft, challenge and approve. |

Technology entrepreneur [Greg Isenberg](https://youtu.be/JWhICz1QR8M) uses this three-layer distinction in an August 2026 video about graph engineering. An X account called [Movez](https://x.com/0xMovez/status/2081011657807925604) compressed the surrounding excitement into “No more prompting,” but prompts have not disappeared. They now sit inside a larger system of context choices and handoffs.

For the questionnaire, retrieve evidence only when a question needs it. Pass short excerpts with stable source references, keep full documents as file artifacts, and reset temporary context between jobs. That cuts repeated tokens without losing the path back to evidence. Removing necessary evidence is not an optimization.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Prompts shape one call, context engineering selects its inputs, and graph engineering coordinates the calls without giving every step the entire dossier.</p>
</div>

## Make every node earn its place

A knowledge graph represents entities and their relationships, such as which product uses which encryption standard. An agent graph represents work. Its **nodes** are bounded jobs, its **edges** are permitted routes, and a **transition** is an actual move along a route. **Shared state** is the structured record passed between nodes; **conditional routing** chooses the next edge from that state.

```text
                         ┌─ policy evidence ─┐
question → classify → fan-out                ├→ merge → draft → checker → skeptic
                         └─ product facts ───┘                         │
                                                      low risk → release
                                                legal uncertainty → human
```

Some work must be sequential because one result depends on another. Independent retrieval can run as a parallel **fan-out**, then **merge** into one evidence packet. That split-and-join shape is a diamond topology. The checker compares a draft with its cited evidence, while the skeptic actively searches for unsupported claims or a reason the proposed answer could be wrong. A human gate belongs on routes where the possible harm justifies review, not automatically after every node.

Isenberg's practical maturity ladder is useful here:

1. **Run it manually.** Perform the jobs in order and watch where context changes.
2. **Save file artifacts.** Preserve the evidence packet, draft and challenge report at each handoff.
3. **Orchestrate stable boundaries.** Automate only after the handoffs are clear enough to inspect.

Build the smallest useful graph. Split a node when jobs need different context, can run independently or require a real separation of duties. Every extra node adds token use, latency and another place to fail. Persistent state lets one questionnaire resume after interruption; memory carries selected information across separate runs. Neither requires replaying the full transcript.

<span class="chapter-tldr__label">In short</span>
<p>The useful graph exposes context boundaries, parallel work and independent challenge while keeping human approval proportional to risk.</p>
</div>

## The hard work starts after the diagram

In July 2026, [Jey](https://x.com/0xJeyx/status/2081364222856831271), who summarized Martin's workshop on X, described 15 minutes of graph drawing followed by 105 minutes centred on evaluation. The underlying session was Martin's two-hour **Architecting and Testing Controllable Agents** workshop at the 2024 AI Engineer World's Fair, a developer conference, rather than a new 2026 graph workshop. The ratio is commentary, but a transcript audit supports its direction: evaluation dominates after the early architecture.

Isenberg's video makes the practitioner case for redesigning work around AI, but it does not discuss evaluations. The proof layer comes from separate material: Martin's workshop and [Anthropic's guidance on agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). A checker reviews one questionnaire answer in one run. An **evaluation set** runs the workflow across held-back questions with expected outcomes, including cases the builders did not choose while adjusting the graph.

Those cases reveal whether retrieval supplied the right policy, the merge dropped a source, conditional routing skipped legal review, or the checker accepted a polished invention. Anthropic recommends beginning with 20–50 tasks drawn from real failures, which makes the first evaluation set concrete without pretending it is complete.

This is why [APEX, the Agentic Production Execution framework](/posts/2026-04-05-apex-framework/), includes reflection: observed failures should change the next version of the workflow. Fine-tuning the graph here does not mean training model weights. It means adjusting node boundaries, context packets, routes, state and gates, then rerunning the held-back cases.

The graph is the control plane for how work moves. The evaluation set is the trust plane for whether those choices hold beyond the examples used to build them. So before adding another node, ask the less glamorous question: which node in this graph has never met an input its builders did not write?

<span class="chapter-tldr__label">In short</span>
<p>A checker can improve one run; only held-back evaluations show whether the graph's context choices and routes survive unfamiliar inputs.</p>
</div>
