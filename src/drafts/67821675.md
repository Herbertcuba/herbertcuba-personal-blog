# The refund request your graph has never seen

Imagine order 8841. A customer says, "I was charged twice. Refund me today." The ledger shows one settled payment and one pending authorization. A careless route treats both as captured money and sends the case toward refund approval.

[Jey asks](https://x.com/0xJeyx/status/2081364222856831271): "Which node in your graph has never met an input you did not write yourself?" Using Lance Martin's [2024 AI Engineer World's Fair workshop](https://youtu.be/ib-wTAvCZqg), he framed fifteen minutes of graph drawing against 105 minutes of evaluation. At 2:21:53, the ratio is an interpretation. Testing appears around 15:35, and eval-dataset work returns around 1:42:00.

I think the ratio describes the effort despite that caveat. Drawing the refund route is quick. Finding cases that embarrass it takes longer, and they need an owner after the diagram stops changing.

## Follow the case file through the graph

[Greg Isenberg's explainer](https://youtu.be/JWhICz1QR8M?t=84) separates three layers of the work. For order 8841, the prompt guides the classifier while context supplies the ledger and refund policy. Graph engineering begins when we design the work around that call.

Classification is a node. An edge permits the next job, while a transition is the route taken. Shared state is the case file. It holds the order ID and payment status. The policy version travels with it, followed by the proposed action and approver.

Conditional routing turns those fields into constraints. A settled duplicate charge may continue toward refund review. The system rejects `pending_payment -> refund_approval` and sends that customer an explanation. A shipping question leaves the refund branch.

A knowledge graph connects the customer with the order and payment. The agent graph moves that case through work. I think following the case file reveals the difference without a graph-theory lecture.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A node performs a job, and an edge permits movement. Shared state carries order 8841 while its payment status controls the route.</p></div>

## Use a diamond when the work can disagree

Classification happens first. Ledger verification and policy lookup can then fan out in parallel because they do not depend on each other. Their findings meet a checker or skeptic, which can challenge a claim before the merge step writes a proposed action. A human sees that proposal before money moves.

I think the checker needs separate criteria and permission to stop the route. A generator reviewing its own confident answer feels too much like asking HAL 9000 to investigate HAL 9000. The separation helps even when both jobs use one model.

Approval should scale with the cost of error. A delivery update can use light review, while a refund needs a named approver. Extra nodes create handoffs, so I would stop with the smallest diamond that improves the decision and preserves its trace.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The refund diamond lets independent checks disagree before their evidence is merged. Human review becomes stricter when the proposed action can move money.</p></div>

## Run the graph on files before a framework

Run the first version manually. Once the route survives a few cases, let ledger verification write `ledger.json` and the checker add `review.md`. Give the policy job its own file. Later runs can retrieve these artifacts.

Only then would I reach for orchestration. [LangGraph](https://docs.langchain.com/oss/python/langgraph/overview), for example, supports persisted state and paused human review. I think the framework earns its place after the team understands why each transition exists. If the route is unclear by hand, orchestration repeats that confusion faster.

Order 8841 now leaves evidence for the next refund review, provided the workflow retrieves it and the policy owner keeps it current.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Manual runs reveal whether the route works. File artifacts create a paper trail before orchestration turns that route into a persistent workflow.</p></div>

## Test the release with failures you did not choose

Isenberg's video makes the practitioner case for designing work around AI, and it contains no eval discussion. The evaluation argument comes from Martin's workshop and [Anthropic's agent-eval guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

A checker may save order 8841 and tell us little about the next twenty refunds. The held-back set needs a settled duplicate charge, a pending authorization, a Spanish request and a misrouted shipping issue. State-machine tests cover fixed transitions. A code grader rejects the illegal route. A model grader inspects the explanation, while a human settles ambiguous policy.

Anthropic recommends starting with 20 to 50 simple tasks drawn from real failures. Each week, the support owner adds corrected production failures. Policy disputes return to the person who owns the rule. A separate maintainer controls the held-back slice. The release record names who accepted the current model and policy versions. An illegal money-moving transition blocks release.

The viral retelling attached a 70% Anthropic adoption figure to Martin's workshop. It also forecast three to six months and declared "No more prompting." Those claims do not appear in the recording, which [Martin clarified predates his time at Anthropic](https://x.com/RLanceMartin/status/2081408482344149047). I think the hype sees the move toward designed workflows and skips the upkeep. Prompts remain inside the classifier and checker.

For this refund, the graph is the control plane because it chooses the route. The typed case file and eval history form a trust plane by showing what crossed each edge and how the route behaves on held-back cases. I expect graph shapes to become easy to copy. The failure set will still carry an organization's policy history and operational scars.

I don't know when agent frameworks will ship serious held-back eval assets by default. For now, I would put a maintainer and review cadence beside every consequential graph, because production starts changing the evidence as soon as the release goes out.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Release quality comes from held-back failures that keep testing the route as the model and policy change. Maintaining those cases belongs inside engineering ownership.</p></div>
