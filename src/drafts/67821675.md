# The 105 minutes after the graph

“Which node in your graph has never met an input you did not write yourself?” [the X account Jey asked in July 2026](https://x.com/0xJeyx/status/2081364222856831271). An agent graph is a map of a multi-step AI workflow: nodes perform jobs, edges allow handoffs, and shared state carries information between them. An evaluation set is the harder counterpart, a collection of reviewed inputs and success criteria used to test whether that workflow behaves as intended.

Jey framed a recorded workshop as 15 minutes for the graph and 105 minutes for evaluation. That ratio is an interpretation, not an official running order. The [recording runs for about two hours and 21 minutes](https://www.youtube.com/watch?v=ib-wTAvCZqg), and its description promises three testing loops: during a run, before release, and in production monitoring. The diagram arrives early; questions about behavior keep returning.

The source needs the same scrutiny as the system. Lance Martin, an AI engineer now at the AI company Anthropic, delivered *Architecting and Testing Controllable Agents* at the [2024 AI Engineer World’s Fair](https://www.ai.engineer/worldsfair/2024/schedule), a developer conference, while he worked at LangChain. LangChain makes LangGraph, a framework for stateful agent workflows, and LangSmith, its testing and monitoring service. A [viral 2026 post by Movez](https://x.com/0xMovez/status/2081011657807925604) attributed “70%,” “3–6 months,” and “No more prompting” to an Anthropic engineer. Those phrases do not appear in the workshop’s English captions, and [Martin clarified that the talk predates his Anthropic role](https://x.com/RLanceMartin/status/2081408482344149047).

I think the correction makes the ratio more useful. The graph is the control plane because it determines which work can happen and in what order. The trust plane consists of typed state, meaning a shared record with named fields and allowed values, plus evaluations and release rules that test and constrain each route. A graph without an evaluation set is a diagram with opinions. The engineering begins when unfamiliar cases push against its arrows.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The 15/105 split is a reading of a 2024 workshop, not a timestamped agenda or an Anthropic adoption claim. It still captures the central problem: workflow structure is quick to draw, while trust depends on evidence from cases the builders did not select.</p></div>

## The graph controls routes, not truth

By refining a graph, I mean changing its state fields, routes, retry limits, reflection criteria, and human approval gates as failures appear. I do not mean training the model’s weights. An edge is one allowed handoff; a route is the sequence of handoffs taken for a particular case. Messy inputs turn those simple definitions into engineering work.

Consider Apex, a hypothetical refund-review agent. It checks whether a payment is pending or settled, checks the relevant refund policy, drafts a decision, and sends consequential cases to a person. Its typed state might allow `payment_status` to be only `pending` or `settled`, while a runtime guard enforces the rule that `pending` can never reach the refund tool. The type makes the intended boundary visible; the guard stops the forbidden action.

Apex may also use reflection, a separate critique step that checks a draft against named conditions before the workflow proceeds. One revision can be useful. An open-ended loop is harder to inspect, more expensive to run, and capable of turning a bad judgment into a repeated one, so a retry cap and an escalation route belong in the graph.

The graph is like the route plotted by the ship computer in Stanley Kubrick’s 1968 science-fiction film *2001: A Space Odyssey*. The route matters, but the simulator has to inject sensor errors, conflicting orders, and failures the crew did not choreograph. If the same opaque component observes the problem, judges its own answer, and authorizes the action, the diagram has hidden the riskiest handoff rather than controlled it.

Existing tools already solve substantial parts of this. Pydantic, a Python data-validation library, can check state against declared fields and values. [LangGraph’s durable execution](https://docs.langchain.com/oss/python/langgraph/durable-execution) saves workflow state so an interrupted run can resume, while [LangSmith evaluations](https://docs.smith.langchain.com/evaluation/tutorials/agents) can score a final response, the route of tool calls, or one step in isolation. I think the unresolved layer is more specific: none of those mechanisms decides which external outcome the business accepts, who may change that judgment, or which held-back evidence must pass before release.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state, runtime guards, bounded reflection, durable execution, and evaluation runners each solve a real problem. Together they make routes inspectable, but acceptable outcomes and release authority still have to be defined by accountable people.</p></div>

## Release evidence has to leave the graph

A release contract is the preset collection of cases, graders, thresholds, and owners that decides whether a graph version ships or rolls back. A held-back case is a reviewed example kept away from graph changes until that decision. Each case should inspect the route, tool results, and outcome in the external system because a fluent answer saying “refund issued” is not proof that a valid refund exists.

Apex’s most basic forbidden transition can fit in a small fixture:

```yaml
case: pending-payment-blocks-refund
input: {payment_id: "p_41", request: "refund"}
setup: {payment_status: "pending"}
expect_route: [check_payment, explain_pending]
forbid_tools: [refund_tool]
expect_outcome: {refund_record: absent}
release_assertion: forbidden_tool_calls == 0
```

A trace is the complete record of nodes, tool calls, intermediate results, and outcomes for one run. A grader is code, a model rubric, or human judgment that scores some part of that record. The fixture needs a code grader for the forbidden tool call and an outcome check against the payment system. When policy evidence conflicts and there is no single correct automated answer, a named human reviewer should decide the expected route and record the reason. That decision then becomes versioned release evidence instead of disappearing into a prompt or meeting note.

[Anthropic’s January 2026 guide to agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends starting with 20 to 50 simple tasks drawn from real failures. I think that is a sensible first-quarter boundary: choose one consequential workflow, review failures weekly, and run the held-back set for every graph or model change. Track route and outcome pass rates, unauthorized tool calls, weekly exceptions, elapsed human-review time, and cost per accepted review. The last three measures show whether the system is reducing work or merely moving it into an expensive exception queue.

Authority should determine the burden of proof. A drafting assistant that cannot act may ship with sampled quality checks and a kill switch. A refund agent that can move money needs narrow amount and policy limits, repeated trials, external ledger checks, human approval outside those limits, and a tested rollback to the last accepted version. I do not know a universal threshold that makes every workflow safe. The important point is that the threshold is explicit, owned, and tested before the tool call matters.

Consider a hypothetical Swedish retailer using Apex. Customer operations owns the accepted refund outcome; the policy and risk function resolves disputed cases and approves changes to consequential thresholds; the central AI platform team owns the evaluation runner, trace format, secure storage, and data-residency controls, which determine where records may be stored; the product release owner signs exceptions and can roll back; engineers implement the graph and guards. That division lets the platform reuse evidence machinery without pretending that a central team can define every business judgment.

For high-risk systems covered on 2 August 2026 by the [European Union’s 2024 AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj), the applicable rules include testing before use against predefined metrics and probabilistic thresholds, which state in advance how performance and uncertainty will be judged. They also require event logging and post-market monitoring, meaning systematic performance checks after deployment. Some product-related provisions apply later. This does not make every refund workflow high-risk, and the operating model is not legal advice or proof of compliance. It does show why named owners, retained traces, human oversight, and reversible release decisions are becoming ordinary engineering concerns in Europe.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A release contract connects held-back inputs to routes, external outcomes, operating limits, and named owners. Start with one workflow and 20 to 50 failure-derived cases, then measure both system behavior and the human work left in its exception path.</p></div>

## The evaluation corpus should outlive the framework

A mature test suite is necessary, but it is not the whole asset. My take is that the durable asset will be the evaluation corpus: reviewed cases, expected external outcomes, traces, grader logic, accepted policy decisions, threshold history, release verdicts, and rollback records. The extra material matters because a test can say what failed while the corpus also records why the organization considered that behavior unacceptable and who approved the replacement rule.

That record needs a clean lifecycle. Cases engineers inspect while changing the graph belong in the development set. If a held-back failure guides a fix, move it into development and add a fresh held-back analogue before the next release. Otherwise the team gradually teaches to the test and mistakes familiarity for reliability.

I think portability gives this claim a fair test. Twelve months from publication, take the complete held-back set for one accepted release and change the primary model or graph runtime. Within one normal release cycle, the team should rerun every case without rewriting expected outcomes or thresholds. Adapter code and trace-field mappings may change. The resulting report must identify the dataset and system versions, show passed cases over total cases for routes and outcomes, list thresholds and approved exceptions, state the release verdict, and name the rollback target. If the expected outcomes must be rewritten in framework terms, or the full report cannot be produced inside that cycle, the corpus was coupled to the old stack.

Portability is not free. Stable outcome definitions, trace adapters, and dispute records slow the fastest possible iteration. Coupling can be rational for a short-lived, low-impact prototype whose disposal is cheaper than migration. For a consequential workflow expected to survive model and vendor changes, however, speed gained by hiding policy inside one framework becomes migration debt at the precise moment the team needs independent evidence.

I do not know which graph runtime will dominate. “No more prompting” should be taken seriously as an abstraction claim, not an erasure claim: prompts still operate inside nodes, while graphs make state and routing explicit. Even a verified internal adoption rate would tell us something about future tooling defaults, not what another organization should deploy this quarter.

The graph records intended control. The evaluation corpus records what happened when that intent met unfamiliar inputs, disputed outcomes, and real authority. I think a team is ready to ship only when every consequential route can be traced to held-back evidence, an accountable verdict, and a tested rollback decision.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Reflection can improve one run and durable execution can preserve it, but release evaluation governs behavior across versions. The graph may change; the team is ready to ship only when every consequential route has held-back evidence, an accountable verdict, and a tested way back.</p></div>
