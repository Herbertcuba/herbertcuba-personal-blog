# The 105 minutes after the graph

“Which node in your graph has never met an input you did not write yourself?” [Jey asks in a July 26, 2026 X post](https://x.com/0xJeyx/status/2081364222856831271). A node is one job in an agent graph, a multi-step AI workflow. An evaluation set is a reviewed collection of cases and expected results used to test that workflow.

Jey describes a 15/105 split: 15 minutes to draw the graph, then 105 minutes returning to evaluation. The ratio is his reading, not the workshop’s literal timetable, but it captures the important part. The diagram is visible. The evidence takes time.

The source needs a correction. AI engineer Lance Martin delivered the workshop at the 2024 AI Engineer World’s Fair while at LangChain, maker of the LangGraph workflow library. He now works at Anthropic, which makes Claude. A later viral post attributed “70%,” “3–6 months,” and “No more prompting” to an Anthropic engineer, but those phrases do not appear in the [recording’s English captions](https://www.youtube.com/watch?v=ib-wTAvCZqg), and [Martin clarified](https://x.com/RLanceMartin/status/2081408482344149047) that the talk predates his Anthropic role.

I think the corrected record makes the lesson stronger. The graph is the control plane: it chooses what can happen next. The trust plane consists of typed state, meaning a shared record with defined fields and permitted values, plus the evaluations and release rules that constrain those choices.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The 15/105 ratio is a useful lens once the source is corrected: the workflow is quick to draw, while unfamiliar cases decide whether it deserves authority.</p></div>

## The complexity lives in the arrows

An edge is an allowed handoff between nodes. A route is the edge chosen for one case. Those definitions sound simple until a real condition has to decide which arrow is legal.

Consider Apex, a hypothetical agent for reviewing refund requests:

```text
request → payment check → policy check → draft decision
                                             ↓
                                      reflection check
                                      ↙              ↘
                                revise once       human review
```

Apex needs reflection because a polished answer can still conflict with payment status or policy. The node checks named criteria, then sends the draft to one revision or to a person when the case is risky or unclear. I think reflection is useful when the criteria are visible, the retry count is fixed, and the loop has an exit.

Otherwise the design starts to resemble HAL 9000, the shipboard AI in Stanley Kubrick’s 1968 film *2001: A Space Odyssey*. One system drafts, judges, and authorizes its own work. A model can help grade a response, but code checks and human approval should keep consequential release authority outside that loop.

“Fine-tuning the graph” does not mean training model weights here. It means changing state fields, routes, stop conditions, retry limits, reflection criteria, and human gates as failures reveal weak handoffs. I think that is where most of the complexity hides.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Reflection adds a bounded critique step, while graph refinement changes the routes, limits, and decision rights exposed by failure.</p></div>

## Turn a route into evidence

Apex can make one consequential policy visible in a compact route table:

| State field | Allowed values | Enforced route rule |
|---|---|---|
| `payment_status` | `pending`, `settled` | `pending` cannot reach refund approval |
| `policy_status` | `clear`, `unclear` | `unclear` must reach human review |
| `review_result` | `pass`, `revise`, `escalate` | only `revise` may use the return edge |

Now test the first rule with a held-back case, one the builders did not use to shape Apex. A trace records a run’s nodes, tool calls, and results. A grader is code, a model rubric, or human judgment that compares the trace or outcome with an expectation written beforehand.

| Test record | Value |
|---|---|
| Input | Payment is pending; customer asks for a refund |
| Expected route | payment check → pending-payment response |
| Observed trace | payment check → draft decision → refund approval |
| Grader result | fail: forbidden transition reached |
| Retry budget | one; preserve the first failed trace |
| Release outcome | blocked until the route is fixed and the set reruns |

Route accuracy is the share of cases sent to their pre-specified next node. It can hide a failed tool call, excess delay or cost, or a correct route that produces the wrong outcome. I think a release record needs checks for path and outcome.

[Anthropic’s 2026 guide to agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends starting with 20–50 simple tasks drawn from real failures. For Apex, a policy owner settles disputed results, engineering maintains the runner, and a release owner applies thresholds set in advance. The contract could require zero pending payments reaching approval, one reflection retry at most, and rollback after a forbidden transition.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A route becomes release evidence when held-back cases test its path and outcome against prior rules, with named owners for expectations, thresholds, and rollback.</p></div>

## Let failures redraw the graph

Reflection and evaluation work at different scales. Reflection checks and may revise one run; an evaluation set tests the system across many reviewed cases.

```text
real failure → reviewed expectation → graph change → development test
             → frozen graph → held-back evaluation → release or rollback
```

Once a held-back case causes a graph change, move it into the development set and replace it with a fresh reviewed case. Otherwise the release check becomes another rehearsal, and the graph only learns to impress its authors.

“No more prompting” is the new “no more code.” Prompts still live inside nodes; graphs add shared state and routing around them. I don’t know which graph framework will dominate, and the unsupported 70% figure should not decide anyone’s quarter. My take is that tooling will converge before evidence does. Drawing the graph may take an afternoon. Proving it holds on inputs you did not choose is the job.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Reflection improves a candidate run; held-back evaluation improves the system and controls release. Without that trust work, a graph remains a diagram with opinions.</p></div>
