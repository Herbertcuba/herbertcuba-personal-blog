A supplier-review agent does not need the complete supplier record at every step. A security check needs the security questionnaire and relevant contract clauses; a finance check needs accounts and payment terms. Sending both steps everything costs more and gives each model more irrelevant material to work through.

A **token** is a small unit of text processed by a language model. The **context window** is the limited space available for the instructions, retrieved evidence, tool results, prior messages, and generated answer in one call. Context engineering is the work of choosing that material. The subtle part is removing tokens without removing the evidence that changes the decision.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Token optimization starts by deciding what each step needs to know, not by shortening one giant prompt.</p></div>

## Context is a routing decision

In an [August 2026 video](https://youtu.be/JWhICz1QR8M), Greg Isenberg, chief executive of product studio Late Checkout, separates three layers that are easy to blur:

| Layer | What it controls | Supplier-review example |
|---|---|---|
| Prompt engineering | How one model is instructed | “Extract termination clauses with citations.” |
| Context engineering | What that model receives | Contract pages, policy rules, and the required result format |
| Graph engineering | How work moves around models | Extract, split the checks, combine findings, then approve or escalate |

The July 2026 slogan “[No more prompting](https://x.com/0xMovez/status/2081011657807925604)” therefore overreaches. Prompts remain inside the steps. The graph makes their boundaries explicit, and those boundaries let you tune context step by step.

This is an **agent graph**, a map of work between AI, software, and human steps. It differs from a **knowledge graph**, which maps relationships between entities such as a supplier, its owners, and its contracts. One describes the workflow; the other describes connected facts the workflow may consult.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompt engineering shapes a call, context engineering supplies it, and graph engineering decides when that call happens and what it passes on.</p></div>

## Build the smallest graph that changes the evidence

A **node** performs one job. An **edge** connects jobs, a **transition** moves a run along that edge, and **shared state** holds outputs that later nodes may need. **Conditional routing** chooses the next edge from the current result, such as sending a high-risk supplier to human review.

```text
              ┌→ legal ─────┐
extract ──────├→ security ──┼→ merge → checker → skeptic? → human?
              └→ finance ───┘
```

Extraction is sequential because the specialist checks depend on it. Legal, security, and finance then use **parallel fan-out**, meaning they run independently, before a **merge** combines their findings. That split-and-rejoin shape is a **diamond topology**. It saves tokens because each specialist receives a narrow evidence pack and writes back compact findings with source-page citations, rather than copying the full record into shared state.

A **checker node** tests whether one run followed its rules. A **skeptic node** independently challenges an approval when the evidence conflicts or the cost of error is high. A **human gate** is an explicit approval point, and its position should match the risk: a missing field can loop back automatically, while access to sensitive data or authority to accept contractual risk deserves a named person.

Start with the smallest graph that creates a useful separation. Isenberg’s practical maturity ladder is sensible: run the steps manually first, preserve stable handoffs as saved outputs, then add orchestration software to run the route automatically once it is understood. **Persistent state** saves the current review so it can resume after interruption; longer-lived **memory** carries selected facts across reviews. Memory should be a deliberate write policy, not a growing transcript.

This is also why [APEX, the Agentic Production Execution operating model](/posts/2026-04-05-apex-framework/), includes a Reflection phase. Fine-tuning the graph means reviewing where context was missing, duplicated, stale, or allowed to trigger too much authority, then changing the next run.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The useful graph is the smallest one that separates evidence, judgment, and authority while preserving enough state to inspect and improve each handoff.</p></div>

## Make every saved token prove itself

Isenberg’s video makes a practitioner case for designing work around AI, but it does not discuss evaluations. The bridge needs a separate source. In 2024, Lance Martin, now an engineer at AI company Anthropic and then at agent-software company LangChain, taught *Architecting and Testing Controllable Agents* at the AI Engineer World’s Fair, an industry conference. A [July 2026 post by the account Jey](https://x.com/0xJeyx/status/2081364222856831271) frames the workshop as roughly 15 minutes drawing the graph and 105 minutes returning to evaluation. Treat that ratio as a useful reading of the workshop, not a measured product claim.

A checker reviews one supplier run. An **eval set** extends that independent review across stored cases and scoring rules, including held-back inputs drawn from real failures rather than composed for the graph. Anthropic’s [guidance on evaluating AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends beginning with 20–50 such tasks, which is enough to make the first context cuts answerable rather than intuitive.

For every node, record input tokens, route taken, cited evidence, checker result, and final human decision. Then remove or compress context and rerun the same held-back cases. If cost falls while required evidence, route accuracy, and risk decisions hold, the optimization earned its place. If they do not, the smaller context was merely cheaper.

Drawing a graph is quick. Proving that its tuned boundaries hold on unfamiliar inputs is the job.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A one-run checker improves a path; a held-back eval set proves whether that path remains trustworthy after its context budget changes.</p></div>
