# The 105 minutes after the graph

“Which node in your graph has never met an input you did not write yourself?” [Jey asks](https://x.com/0xJeyx/status/2081364222856831271). His post frames a Lance Martin workshop as 15 minutes drawing an agent graph and 105 minutes returning to evaluation. That ratio is a diagnostic metaphor, since the [official AI Engineer recording](https://www.youtube.com/watch?v=ib-wTAvCZqg) runs 2:21:54. Testing enters around [15:35](https://www.youtube.com/watch?v=ib-wTAvCZqg&t=935s), and evaluation datasets come up in the Q&A around [1:42:00](https://www.youtube.com/watch?v=ib-wTAvCZqg&t=6120s).

The provenance correction strengthens the point. The recording comes from the 2024 World’s Fair, when Martin worked at LangChain. A [separate viral post by Movez](https://x.com/0xMovez/status/2081011657807925604) describes a 30-minute lecture and attributes a 70% adoption figure, a three-to-six-month forecast, and “No more prompting” to an Anthropic engineer. Those phrases appear in Movez’s post; YouTube’s English auto-generated caption track for the 2024 recording contains none of them. [Martin later clarified](https://x.com/RLanceMartin/status/2081408482344149047) that the graph workshop predates his Anthropic role.

I think the useful signal survives the correction. Graph-shaped workflows may become common. Jey’s sharper line is that “a graph without an eval set is a diagram with opinions.” Production evidence accumulates in the cases that challenge its routes.

## The graph is the control plane

[Martin defines context engineering](https://rlancemartin.github.io/2025/06/23/context_engineering/) as giving each model call the right information for its next step. A graph turns that idea into a control plane. A node performs one job, an edge allows a handoff, and a transition is the edge selected during a run. Typed state is the structured case record shared between those jobs.

Consider this hypothetical refund case:

```yaml
order_id: "8841"
payment_state: "pending"
policy_version: "2026-08-01"
proposed_action: "refund"
review_required: true
```

An intake node classifies the request. Ledger and policy checks can then run in parallel before a checker combines their results. Under this fictional policy, `payment_state: pending` must produce `next_node == "payment_review"`; a direct route to `refund_approval` fails the test. If one model call can propose and approve the refund, the design gives HAL 9000 both the flight controls and the accident review.

Focused nodes can reduce irrelevant context, yet extra calls and repeated retrieval can raise total token use. Measure tokens across the complete run alongside route accuracy, the share of cases that reach the next node specified before testing. The policy owner sets those expected routes and the acceptable false-escalation rate. I think context optimization begins with this boundary: spend tokens where a distinct decision needs distinct evidence, then verify the route that follows.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The graph controls the work and its permissions; typed state makes each consequential handoff visible enough to test.</p></div>

## The eval set is the trust plane

A checker examines one run. A held-back eval set repeats that examination across reserved cases that stayed outside graph design and tuning. When a case informs a workflow change, it moves into the development set and needs a fresh held-back replacement. Otherwise, the team is rehearsing the test it claims to pass.

[Anthropic recommends](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) starting with 20 to 50 simple tasks drawn from real failures. For the refund graph, code checks the chosen route and final ledger state. A model grader can assess the explanation against a written rubric. Before any trial, the policy owner records the expected outcome and threshold; a human resolves disputed or borderline labels, while a separate approver retains authority over live money movement.

A consequential graph reaches production only when its held-back evidence, policy version, and accountable owner are recorded. Every critical transition assertion must pass every trial. An unsafe approval blocks deployment, and an unresolved label remains a failure until the policy owner resolves it.

Each week, support submits reviewed production incidents as candidate cases, and the policy owner assigns the expected outcome. A dataset maintainer versions the examples and freezes the held-back partition for that release cycle; engineering owns the test harness, and the accountable approver signs the release record. Lower-risk workflows may combine roles, while a refund route deserves separation.

That record links the model and policy versions to the frozen dataset, grader configuration, results, and approver. An investigator can trace a deployed transition back to the evidence used and identify who accepted it. I think typed state and held-back evaluations form the trust plane because they give workflow boundaries reproducible consequences.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A versioned, failure-derived eval set becomes a trust plane when its owners define expected outcomes in advance and its results can block release.</p></div>

## The work starts after the diagram

Frameworks can supply graph primitives, persistent state, and recovery after failure. Representative failure cases still come from your own operation. I think platforms will converge on similar graph shapes, while teams with versioned held-back sets will show more stable release quality when policies or models change. Regression rates across those changes will make that prediction testable.

The phrase “No more prompting” repeats the old “no more code” fantasy. Prompts remain inside the nodes, and engineering expands into state schemas, route guards, graders, dataset control, and release decisions. This shifts where the work happens.

I don’t know which graph framework will dominate. My take is to begin with one consequential journey and the smallest graph that improves it. Give every critical route a held-back case, a deterministic assertion where possible, and a release record with an accountable owner. The decisive artifact is the evidence that can stop the graph from shipping.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Graph tooling will become easier to copy; production reliability will depend on the owned evidence that survives model and policy changes.</p></div>
