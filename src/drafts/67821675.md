# The graph takes 15 minutes

“Which node in your graph has never met an input you did not write yourself?” [Jey asks](https://x.com/0xJeyx/status/2081364222856831271). His post frames Lance Martin’s workshop as 15 minutes drawing the graph and 105 minutes returning to evaluation. The ratio is an interpretation, yet it captures the production divide: drawing a route is quick; showing it holds on cases its builders never selected is the job.

The [official AI Engineer recording](https://www.youtube.com/watch?v=ib-wTAvCZqg) is a 2:21:54 workshop from 2024, when Martin was at LangChain. Testing appears around [15:35](https://www.youtube.com/watch?v=ib-wTAvCZqg&t=935s), and evaluation datasets come up during the Q&A around [1:42:00](https://www.youtube.com/watch?v=ib-wTAvCZqg&t=6120s). The recording supports the structural point without making the split a literal schedule.

In a [separate viral post](https://x.com/0xMovez/status/2081011657807925604), Movez described a 30-minute lecture and attributed “70% of our engineers,” a three-to-six-month forecast, and “No more prompting” to an Anthropic engineer. The located primary sources do not establish those claims. [Martin clarified](https://x.com/RLanceMartin/status/2081408482344149047) that the graph workshop predates his Anthropic role. I think the correction sharpens the useful signal: graph-shaped workflows are spreading, while evidence remains the slower work. Even a verified 70% figure would indicate what tools may assume next year more than what another organization should deploy this quarter.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The viral forecast is unverified, while the 2024 workshop supports a firmer lesson: graph design moves quickly and evaluation carries the production burden.</p></div>

## The graph controls the work

[Martin defines context engineering](https://rlancemartin.github.io/2025/06/23/context_engineering/) as filling each model call’s limited context window with the right information for its next step. An agent graph makes that rule explicit. A node performs one job, an edge permits a next job, and a transition is the edge chosen during a run. Shared state is the typed case record passed between nodes, and conditional routing reads that record to choose the next job.

Consider a hypothetical refund workflow:

```yaml
order_id: "8841"
payment_state: "pending"
policy_version: "2026-08-01"
proposed_action: "refund"
review_required: true
```

The classifier receives the ticket and account ID. Ledger and policy nodes then run in parallel with only the fields and retrieved material each needs, before a checker merges their findings. Under this fictional policy, `payment_state: pending` must route to `payment_review`; the test asserts that next node and rejects a direct transition to `refund_approval`.

An agent graph represents how work moves; a knowledge graph represents relationships among information. Separating jobs with different evidence and permissions prevents one model call from proposing a refund and approving its own proposal. Combining those powers would resemble giving HAL 9000 the flight controls and the incident review console.

Smaller contexts can still raise total cost through extra calls or repeated retrieval. Measure tokens across the run alongside expected-node accuracy, unsafe approvals, and unnecessary escalations. I think savings count as progress only when route accuracy holds, unsafe approvals stay at zero, and false escalations remain within an agreed limit.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The graph is a control plane for jobs and permissions; typed state gives each node focused evidence and makes consequential transitions testable.</p></div>

## The eval set controls trust

A checker reviews one run. A held-back eval set repeats that scrutiny across a reserved group of cases kept outside workflow building and tuning. Once a case influences a change, it joins the development set and needs a fresh held-back replacement, since continued reuse would make later results overly optimistic.

[Anthropic recommends](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) beginning with 20 to 50 simple tasks drawn from real failures. In the refund example, code checks the expected transition and the final ledger state. A model grader may score the explanation against a written rubric. When its score conflicts with the expected label or falls near the threshold, a human adjudicates the label; a separate human approver retains authority over the live money-moving action.

Write the release condition before evaluation begins. Every deterministic transition assertion must pass in every trial, any critical approval error blocks release, and a disputed model-grader label remains a failure until a human resolves it. Softer measures, such as explanation quality, can use a stated minimum. I think typed state and evals form the trust plane because they turn workflow boundaries into reproducible release evidence.

A designated maintainer controls changes to the held-back set. The release record names the model, policy, grader, and dataset versions, plus the threshold and approver. An investigator can then recover the evidence, decision, and owner behind a deployed route.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A reserved set of real failures tests the trust plane, and predetermined pass conditions give that evidence the power to stop a release.</p></div>

## Ship the evidence loop

Separation also needs a recoverable run record. [Greg Isenberg recommends](https://youtu.be/JWhICz1QR8M?t=807) running the workflow manually, then using files as persistent state before adding orchestration software. Each run can preserve its inputs, state changes, retrieved evidence, grader outputs, and approval decision.

Start with one consequential customer journey. Support submits corrected failures weekly, and the policy owner resolves expected outcomes and disputed labels. Engineering maintains the harness and dataset versions. The accountable approver signs the release record; a low-risk flow may combine roles, while a refund route deserves separation.

The “No more prompting” forecast sounds like the old “no more code” forecast. Graphs move effort from individual prompts into state schemas, route guards, graders, and release records. I think this is a shift in where engineering happens, rather than its disappearance.

I don’t know which graph framework will dominate. My take is to automate the smallest graph that improves a consequential decision and make its evidence loop part of every release. A graph earns authority when unfamiliar inputs have tried to break every consequential route.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Production graph engineering is a maintained evidence loop with recoverable runs, named owners, and release authority tied to unfamiliar cases.</p></div>
