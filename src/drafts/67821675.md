Imagine an AI agent, a system that lets a language model use tools across several steps, reviewing a customer's refund request. It needs the order, the applicable policy and perhaps the payment status. Yet many systems send every call the whole conversation, a policy library, tool results and earlier reasoning, then hope the model finds the important parts.

A token is a small unit of text processed by a model. Its context window is the limited space holding the input and generated output for one call. Context engineering is the work of choosing what enters that space. The subtle part is omission: spend fewer tokens without hiding the one fact that changes the decision.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Good context engineering gives each decision enough evidence, not every piece of information the system can retrieve.</p></div>

## The prompt is only one layer

In an [August 2026 video](https://youtu.be/JWhICz1QR8M), technology entrepreneur Greg Isenberg describes three layers of work around AI. Prompt engineering shapes the instructions for one model call, meaning one request-and-response cycle. Context engineering selects its tools, examples, documents and prior results. Graph engineering divides a larger job into nodes, meaning bounded pieces of work, and controls how results move between them.

That distinction deflates the July 2026 viral paraphrase [“no more prompting”](https://x.com/0xMovez/status/2081011657807925604). Prompts remain, but they become local contracts inside a workflow rather than one heroic request. It also separates two graphs that are often confused: a knowledge graph records entities and relationships, such as customer → order → payment; an agent graph routes jobs that inspect or change those records.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts direct individual calls, context supplies their evidence, and an agent graph coordinates the calls.</p></div>

## Draw the smallest useful graph

Isenberg's practical maturity ladder starts with doing the workflow manually, then saving explicit file artifacts at stable handoffs, and only then adding orchestration. An artifact is a durable output such as a structured refund assessment, not a loose chat summary. This sequence exposes the real work before software hardens the wrong process.

For the refund example, the smallest useful graph might look like this:

```text
                     ┌─> [Read order facts] ───┐
[Classify request] ──┤                         ├─> [Draft] -> [Checker] -> [Skeptic] -> {Act or human}
                     └─> [Read policy facts] ──┘
```

The boxes are nodes. The arrows are edges, and moving along one is a transition. The fork is parallel fan-out: both research nodes run at once, then their results merge into a diamond topology before the sequential review steps. Shared state carries the request ID, cited facts, draft decision and status between them. Conditional routing sends only high-value, ambiguous or low-confidence refunds through a human gate; the level of human control should rise with the consequence of a mistake.

The checker confirms that the draft follows the policy and cites required evidence. The skeptic has a different job: search for a reason the proposed decision could be wrong. Add another node only when it needs different context, tools, ownership or risk controls. Otherwise the graph gains another boundary to tune and another place to fail.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Orchestrate a proven manual workflow, split only where information or risk changes, and make human review proportional to consequence.</p></div>

## Tune what crosses each edge

Token optimization happens at the handoff. Keep full records in their source systems and retrieve the smallest relevant slice for each node; pass source references alongside compact facts so a later step can verify them. At each node, ask which evidence can change its decision. Everything else must justify the tokens it consumes.

| Node | Receives | Leaves out |
|---|---|---|
| Classifier | Request and order ID | Policy library |
| Order reader | Order ID and order tool | Customer chat history |
| Policy reader | Product, market and purchase date | Unrelated policies |
| Checker | Draft, cited facts and rubric | Raw retrieval traces |

Persistent state is the durable record of this particular run, allowing a workflow to pause, retry and recover. Memory is selected information reused across runs, such as a customer's approved preference. Mixing them makes every future call inherit old material it may not need. In [APEX, an operating model for agentic production](/posts/2026-04-05-apex-framework/), the checker and skeptic belong to the reflection phase: a deliberate second pass, with a narrower context and a different objective.

This is where graph engineering becomes difficult. Drawing arrows is quick; deciding what every node sees, saves, forgets and may do requires repeated tuning.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Save compact, traceable artifacts in workflow state, retrieve details when needed, and keep long-term memory out of calls that do not use it.</p></div>

## The missing context needs a trial

Isenberg's video makes a practitioner case for arranging work around AI, but its transcript does not discuss evaluations. The bridge comes from a separate record: Lance Martin, now an AI engineer at Anthropic and then at LangChain, taught the 2024 AI Engineer World's Fair workshop “Architecting and Testing Controllable Agents.” A transcript audit finds evaluation throughout the workshop. [Jey's later 15-versus-105-minute framing](https://x.com/0xJeyx/status/2081364222856831271) is not a literal stopwatch reading, but it captures the lesson: the graph appears early; proving it occupies most of the work.

A checker reviews one run. An eval set repeats that separation against inputs the builders did not choose. [Anthropic's guidance on agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends starting with 20 to 50 tasks drawn from real failures. For each refund case, record the scenario, expected route, observable outcome and release rule. Include missing orders, conflicting policies and misleading customer claims, then hold cases back from graph tuning.

A graph controls where work goes. Its state and evaluations establish whether that control deserves trust. The useful token budget is therefore not the smallest one; it is the smallest one that still passes unfamiliar cases for the right reasons.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A checker can improve one decision; a held-back eval set shows whether reduced context still works beyond the examples used to design the graph.</p></div>
