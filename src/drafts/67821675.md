Token waste begins when an application sends the same instructions, history, documents, and tool results into every call, whether that step needs them or not.

Consider an agent reviewing supplier invoices. Extraction needs the invoice; a delivery check needs the purchase order and receipt; a payment decision needs the findings, not three complete transcripts. A token is a piece of text the model processes. Its context window is the finite space for input and output, so context engineering decides what earns space for each decision.

The target is minimum sufficient context: enough evidence for a reliable decision, with anything else available by reference. A graph exposes those choices; evaluation tests them.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Token optimization starts by budgeting evidence per decision, then testing whether the smaller context preserves the outcome.</p></div>

## Separate the three engineering jobs

In an [August 2026 video](https://youtu.be/JWhICz1QR8M), technology entrepreneur Greg Isenberg presents graph engineering as designing work around AI rather than stretching one conversation across a process. It separates three decisions often buried in one giant prompt.

| Discipline | What it decides | Invoice example |
|---|---|---|
| Prompt engineering | How one model call is instructed | Extract line items into fixed fields |
| Context engineering | Which evidence that call can see | Send the invoice, not the payment history |
| Graph engineering | Which job runs next and under what condition | Route mismatches to review |

Isenberg also separates a knowledge graph, which records entities and relationships, from an agent graph, which routes jobs. A map linking supplier, contract, purchase order, and bank account can inform the invoice process; it cannot perform it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts shape a call, context supplies its evidence, and graphs coordinate calls; improving one does not remove the other two.</p></div>

## Draw the smallest useful graph

A node performs one job. An edge is an allowed connection; a transition is the move along it. Shared state is the compact record passed between nodes, here invoice ID, amount, status, and evidence references. Conditional routing chooses the next edge from that state.

```text
intake → extract ─┬→ purchase-order check ─┐
                  └→ delivery check ───────┤→ merge → skeptic → route
                                           ├→ approve
                                           └→ human review
```

Intake and extraction are sequential because the second needs the first output. The checks can fan out in parallel and then merge. That split-and-rejoin shape is a diamond topology: narrow contexts do independent work before their structured results meet.

A checker node confirms that amounts and identifiers agree. A separate skeptic node looks for reasons the proposed approval is wrong. Low-risk matches may continue, while a high-value invoice or bank-detail change reaches a human gate because review should rise with the cost of a mistake. Start with this smallest useful graph, not every imaginable exception.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The graph earns its complexity when it separates decisions, narrows their evidence, and increases human control with risk.</p></div>

## Cut tokens at the handoff

Isenberg's practical maturity ladder begins with people running the workflow manually. Next, each handoff becomes a file artifact such as `invoice.json` or `delivery_check.json`. Orchestration comes last, once those boundaries are stable enough to automate.

That sequence reveals direct savings:

- Put fields and source references in shared state instead of copying full prose.
- Retrieve a document only for the node that needs it, then merge conclusions rather than transcripts.
- Keep stable instructions first so [prompt caching](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching) can reuse unchanged prefixes where supported.

Persistent state preserves the current invoice across pauses and retries. Memory carries selected facts across invoices, such as an approved supplier identifier; it should not become an unfiltered archive of earlier conversations. Both reduce repetition when retention is deliberate.

This is the real fine-tuning of a graph: adjusting boundaries, routes, context packets, and gates, not training model weights. [APEX, Herbert's operating framework for agentic production work](/posts/2026-04-05-apex-framework/), includes a reflection phase for this reason. Run evidence should change the graph when a node repeatedly receives too much, too little, or the wrong material.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Map the human process, make handoffs explicit, automate stable boundaries, and use reflection to keep each context packet lean.</p></div>

## Prove every deletion

The sources separate here. Isenberg makes the practitioner case for workflow design, but his video does not discuss evaluation. Lance Martin, now at Anthropic, the AI company, taught a roughly two-hour 2024 workshop called *Architecting and Testing Controllable Agents* at AI Engineer World's Fair, a developer conference. Its transcript turns to evals around minute 23 and ends with an eval dataset. [An X post by Jey in July 2026](https://x.com/0xJeyx/status/2081364222856831271) captured the emphasis as 15 minutes on the graph and 105 on evaluation.

A checker reviews one invoice run. An eval set repeats that separation across representative and difficult inputs the builders did not choose. It reveals whether removing a receipt, shortening a policy, or changing a route saves tokens while increasing wrong approvals or human-review load.

[Anthropic's guidance on agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) suggests beginning with 20 to 50 tasks drawn from real failures. For this graph, record the expected route, forbidden actions, required evidence, token use, and final outcome. Remove one context field, then rerun the same set.

[A viral July 2026 paraphrase by the X account Movez](https://x.com/0xMovez/status/2081011657807925604) declared “No more prompting.” Prompts still live inside nodes; graph and context engineering decide where they run and what they see. The graph is the control plane. Typed state and evals form the trust plane. Keep a token saving only when held-back invoices say you can.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A lean context is a hypothesis until held-back cases show that lower token use preserves routing, safety, reviewer load, and outcomes.</p></div>
