# The subtle art of context engineering

“Which node in your graph has never met an input you did not write yourself?” [Jey asks](https://x.com/0xJeyx/status/2081364222856831271). He frames Lance Martin’s workshop as 15 minutes of graph drawing followed by 105 minutes of evaluation. That ratio is Jey’s interpretation. The official 2024 recording has no formal 15/105 agenda. Martin raises [testing and evaluation around 15:35](https://www.youtube.com/watch?v=ib-wTAvCZqg&t=935s) and returns to [building eval datasets around 1:42:00](https://www.youtube.com/watch?v=ib-wTAvCZqg&t=6120s).

A viral retelling attached “70% of Anthropic engineers,” a three-to-six-month forecast, and “No more prompting” to the session. Those phrases are absent from the official captions, and [Martin clarified](https://x.com/RLanceMartin/status/2081408482344149047) that the workshop predates his Anthropic role. I think the correction sharpens the useful lesson: graphs reveal where work moves, while unfamiliar inputs reveal whether those routes deserve production authority.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The 15/105 ratio is an interpretation of a real workshop whose recurring concern is how agent routes behave under testing.</p></div>

## Give each call a smaller case file

[Martin defines context engineering](https://rlancemartin.github.io/2025/06/23/context_engineering/) as filling each step’s limited context window with the right information. [Greg Isenberg adds the workflow layer](https://youtu.be/JWhICz1QR8M?t=84): prompts shape the request, context supplies evidence, and a graph designs the work around the model. This makes token optimization a routing problem as well as a model-call problem.

In Isenberg’s plain-language account, a node is one job and an edge connects it to an allowed next job. A transition is the edge chosen during a run. Shared state is the compact case file moving through the workflow, while conditional routing uses fields in that file to choose the next step.

Consider a hypothetical refund request:

```text
order_id: "8841"
intent: "refund"
payment_state: "pending"
policy_version: "2026-08-01"
proposed_action: "refund"
review_required: true
```

For this fictional workflow, the policy sends every case with `payment_state: pending` and `proposed_action: refund` to `payment_review`. A route test supplies the complete state above and expects that transition. A knowledge graph would represent relationships among the order, customer, and policy; this agent graph controls how the case moves through work.

The classifier needs the ticket and account ID. The reviewer needs a ledger excerpt and the exact policy clause. Each call receives focused evidence, and the typed state keeps handoffs explicit. Extra calls can still increase total usage, so measure tokens across the full run. I think optimization earns its name when smaller contexts also improve route accuracy or reduce unsafe behavior.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Explicit state gives each job focused context and turns a vague handoff into a route that code can test.</p></div>

## Keep the graph small enough to inspect

Classification precedes ledger and policy lookups, which fan out in parallel before a merge combines them. A conditional edge sends the proposed refund either to a checker or to human review.

The checker needs permission to reject the proposal. Asking one model to generate and approve a money-moving action resembles putting HAL 9000 in charge of both the mission and the incident review. Separating those jobs makes the concentration of authority visible, and a human gate can become stricter as the cost of error rises.

[Isenberg recommends starting with a manual workflow](https://youtu.be/JWhICz1QR8M?t=807), then using files as persistent state before adding orchestration software. For order 8841, one run directory could store the input state, policy version, model output, checker verdict, and human decision. The `order_id/run_id` joins those artifacts; retained versions create the history. A framework can later carry state, resume failures, and pause for approval.

I think the smallest useful graph removes irrelevant context, separates a consequential check, and preserves evidence someone can inspect. A private memo may need a light review. A refund should pause before money moves.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Run the workflow visibly, preserve its evidence, and automate only the smallest graph that improves the decision.</p></div>

## Make unfamiliar failures the release boundary

A checker evaluates one run and returns a verdict on its route or result. A held-back eval set extends that check across cases excluded from building and tuning the workflow. Once a held-back case guides a change, it joins the development set and needs a fresh replacement for the next release decision.

[Anthropic’s agent-eval guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends starting with 20 to 50 simple tasks drawn from real failures. For the refund graph, I would include proposed refunds with pending payments, captured payments, conflicting policy versions, and ambiguous customer intent. Code can grade the transition, a model grader can assess the explanation, and a human can resolve disputed labels. Repeated trials expose inconsistent behavior.

My take is a proportionate operating model. Support submits corrected failures on a regular cadence, the policy owner settles expected outcomes, engineering owns the test harness, and an accountable approver signs a release record containing the model, policy, and dataset versions. A separate maintainer can lock the held-back slice during tuning and version its replacement after the release cycle.

I don’t know which graph framework will dominate. I think replaying versioned failure cases after each model or policy change will catch route drift before deployment, because the same consequential transitions face the new system again. A successful demo covers chosen paths and provides a narrower signal.

A consequential graph is ready for production only when its named held-back set passes under recorded versions and an accountable owner accepts the decision. A graph earns authority when unfamiliar inputs have tried to break every consequential route.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Held-back failures turn graph routes into versioned release evidence with a named owner and the power to block deployment.</p></div>
