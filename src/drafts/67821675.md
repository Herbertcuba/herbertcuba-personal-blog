Context engineering is often described as feeding a model better material. That is only half the job. A [context window](https://ai.google.dev/gemini-api/docs/tokens) is a language model's finite combined input-and-output token budget; tokens are the pieces of text and data it processes. Send the same large supplier packet into five calls and you pay for the same reading repeatedly.

A better design starts with the work. A security analyst does not need the pricing appendix, and a commercial analyst does not need every security test report. Give each AI job the evidence, current decision record and output shape it needs. An **agent graph**, a workflow map of jobs and allowed handoffs, makes those allocations visible; evaluation tells you whether the savings removed something important.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Context engineering spends tokens where they can change a decision instead of sending the whole workspace into every model call.</p></div>

## Prompt, context and graph engineering

In an [August 2026 video on graph engineering](https://youtu.be/JWhICz1QR8M), entrepreneur and podcast host Greg Isenberg offers a useful separation. Prompt engineering shapes what one call must do. Context engineering decides what information it can use. Graph engineering designs how several jobs pass work among one another.

A [viral retelling](https://x.com/0xMovez/status/2081011657807925604) called this “no more prompting.” It gets the mechanism backwards: more bounded jobs create more boundaries to specify, so prompts become narrower rather than irrelevant.

| Discipline | Design question | Supplier-review move |
|---|---|---|
| Prompt | What should this call produce? | Extract security obligations into fixed fields. |
| Context | What must it see? | Retrieve the relevant clauses and evidence. |
| Graph | What runs next? | Return gaps; send high risk to a person. |

Large windows remain useful, but capacity is not permission to fill them. Store sources once, retrieve the smallest relevant slices, carry compact decisions forward, and pass changed fields rather than transcripts. A reference saves nothing unless that job can retrieve the evidence when needed.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts define a job, context supplies its evidence, and a graph determines how that job participates in the wider decision.</p></div>

## Draw the smallest useful graph

A **node** performs one job. An **edge** is an allowed path between jobs; a **transition** is the actual move along it. **Shared state** is the structured record they exchange, such as supplier ID, missing evidence, risk flags and links to saved outputs. **Conditional routing** chooses the next node from that record.

Dependent jobs run **sequentially**. Independent jobs can **fan out**, meaning they run in parallel with different context, then **merge** into one result. That split-and-rejoin shape is a **diamond topology**. A separate checker, or skeptic node, looks for unsupported claims. A **human gate** is a checkpoint where a named person can approve, redirect or stop the run.

```text
                         ┌→ security analysis ──┐
intake → plan → fan-out ─┤                      ├→ merge → skeptic
                         └→ commercial analysis ┘             ├→ revise
                                                              ├→ recommend
                                                              └→ human gate
```

Here, intake and planning run in sequence, the analyses form the diamond, and the skeptic can return weak work. Start there. Extra nodes add prompts, transitions, tokens and failure surfaces. Tuning the graph means refining job boundaries, context slices, routes and thresholds, not retraining the model.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Begin with the fewest nodes that create a real separation of work or judgment; the useful complexity lies in their boundaries and routes.</p></div>

## Build the paper trail before the platform

A **knowledge graph** records relationships among things, such as which supplier serves which system under which contract. An agent graph moves work among jobs. They can work together, but they solve different problems.

Isenberg's practical build order is refreshingly plain. A **file artifact** is one step's saved output, available for inspection or selective retrieval later.

| Stage | What to prove |
|---|---|
| Manual workflow | The jobs and handoffs are distinct. |
| File artifacts | Each step leaves structured data or plain text. |
| Orchestration | Software manages routes, retries, pauses and saved state. |

Files expose bloated context before orchestration software hides it. **Persistent state** is workflow data that survives a pause or restart. **Memory** is selected information deliberately reused in later runs. Both need a defined scope and expiry, or an old assumption can quietly become current evidence.

The skeptic provides reflection: deliberate self-review that checks the recommendation against its sources and returns gaps for revision. That is why [APEX, the Agentic Production Execution framework](/posts/2026-04-05-apex-framework/), includes reflection. Human gates should become stricter as the financial, security or legal consequences grow.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prove the workflow by hand, preserve its artifacts, and automate only after its state, reflection and risk-based authority are clear.</p></div>

## A checker is not an eval set

Isenberg makes the practitioner case for designing work around AI, but his video does not discuss formal evaluations, usually shortened to evals. The bridge comes from separate evidence. Lance Martin, now at AI company Anthropic and then at AI tooling company LangChain, taught “Architecting and Testing Controllable Agents” at the 2024 AI Engineer World's Fair, a developer conference. A word search of the official recording's transcript finds 101 uses of “eval”; evaluation enters around minute 23.

The X account Jey later [compressed that emphasis](https://x.com/0xJeyx/status/2081364222856831271) into 15 minutes for the graph and 105 for evaluation. The ratio is commentary rather than the recording's exact timeline, but it catches the engineering truth. A checker reviews one supplier run. An **eval set** repeats that separation across cases held back from design, so the builders did not choose or tune against them.

[Anthropic's guidance for evaluating AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) recommends starting with 20 to 50 tasks drawn from real failures. Here, those cases should test missing evidence, contradictory clauses, wrong routes, escaped human gates and token use alongside answer quality. A cheaper run may simply be a less informed run.

A graph without an eval set is a diagram with opinions. Before shrinking a node's context, ask which held-out supplier cases prove the new boundary still holds. Drawing the arrows is an afternoon; earning confidence in them is the job.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A checker challenges one execution. Held-out evals challenge the graph itself, proving whether its context savings, routes and gates survive inputs the builders did not select.</p></div>
