I tried to build an agent last month that could research a topic, write a summary, and post it to our internal wiki. The model was fine. The prompt was fine. The thing kept forgetting what it had already done. It would search the same term twice, lose the thread of its own argument, and occasionally claim it had already posted when it hadn't. I spent three days prompt-tuning before I realized the problem wasn't the model. It was that I had no idea what the agent knew at any given moment.

I think most people building agents right now are making the same mistake. They're treating the model as the product and the state as an implementation detail. That gets it backwards. The model is becoming commodity. The state is where the engineering lives.

## The model is not the bottleneck

Anthropic shipped Claude Opus 5 on July 24th. The Hacker News thread hit 1,756 points and 1,297 comments. The top-line claim from Anthropic's announcement: "During pre-deployment testing, our automated behavioral audit found Opus 5 to be our most aligned model to date. It adheres to Claude's Constitution better than Opus 4.8, Sonnet 5, or Fable 5; exhibits the lowest rates of deceptive behavior; and is the least susceptible to being tricked into misuse."

That's genuinely impressive. Alignment at that level means you can trust the model with more autonomy. But here's what I noticed reading the thread: nobody was talking about alignment. They were talking about cost. About how Fable 5 is twice the price. About how Opus 5 is "good enough" for most tasks. About how the real constraint isn't capability anymore.

I think that's the tell. When the community's first reaction to a major model release is "how much does it cost?" rather than "what can it do?", the capability curve has flattened enough that the bottleneck has moved somewhere else.

The somewhere else is state.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Opus 5's alignment is a real achievement. The community's reaction to it, cost and routing rather than capability, signals that the model layer is no longer the binding constraint.</p></div>

## The convergence nobody announced

Three frameworks I've been watching have independently arrived at the same architectural conclusion.

LangGraph, the most widely deployed agent framework in Python, treats every workflow as a typed state machine. Nodes read and write a shared state object with a declared schema. The graph routes based on state values rather than prompt outputs. You can inspect the state at any point, serialize it, resume from it, test it.

Inngest's AgentKit does the same thing in TypeScript. Their description is explicit: "State combines conversation history with a fully typed state machine, used in routing." The router inspects state to decide which agent runs next. Handoff between agents is a state transition rather than a prompt handoff.

Contentful's Skill-kit, which showed up on HN in May, describes itself as "TypeScript SDK for building agent skills as typed state machines." Same pattern. Same conclusion.

Three teams. Different languages, different domains, different funding models. All converging on typed state as the load-bearing structure.

I think the analogy that works here is HAL 9000. HAL doesn't lie. HAL is genuinely trying to help. But HAL optimizes for one objective (mission success), and when that objective gets quietly misaligned with what the humans actually need, HAL keeps performing confidently because no part of the system knows to question the frame. A single LLM in production is a little bit like that. It is helpful, it is fluent, and it is structurally unable to notice when the frame itself is wrong. Typed state is the mission board that lets the crew see what the ship actually knows.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>LangGraph, Inngest AgentKit, and Contentful Skill-kit all use typed state machines as their core abstraction. Three independent teams, same conclusion: the state contract is the product.</p></div>

## Why typed state beats prompt engineering

Prompt engineering asks the model to remember. Typed state tells the system to remember. The difference matters.

When you prompt-engineer memory into an agent, you're relying on the model's context window to carry the thread. The model sees the whole conversation and (hopefully) doesn't repeat itself. This works until it doesn't. Long conversations hit context limits. Complex workflows branch in ways the prompt can't anticipate. The model's attention degrades. You end up with an agent that knows a lot but can't reliably act on what it knows.

Typed state moves the memory out of the prompt and into a data structure. The agent's knowledge becomes inspectable. You can log it. You can test it. You can assert that the state at step 3 contains the sources gathered at step 2. You can serialize the whole thing, restart the process, and resume exactly where you left off.

This is what I mean when I say the state is where the engineering lives. The model is a function that takes state and returns an action. The state is the system.

I wrote about this in [The Real Leap in Agents Was Never Smarter Models. It Was Types](/drafts/9fd60cf4/) last week. The four layers of an agent workflow are prompt, loop, graph, and typed state. Most teams stop at prompt. The teams shipping reliable agents have climbed all four.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompt engineering asks the model to remember. Typed state tells the system to remember. One is a request. The other is a contract.</p></div>

## The verification debt connection

This connects directly to something I wrote about in March: [The Verification Debt Crisis](/posts/2026-03-09-verification-debt-crisis/). The core problem there was that AI-generated code is cheap to produce but expensive to verify. The same dynamic applies to agent workflows.

An agent that produces 10x more output than a human is only useful if you can verify what it did. Typed state is the verification infrastructure. When every step reads and writes a declared schema, you can audit the run. You can see where it went wrong. You can build dashboards that show which transitions are failing and why.

Without typed state, you're doing what I called "approving PRs based on vibes." The agent says it searched. The agent says it found sources. The agent says it wrote a summary. You have no way to check any of that without reading the entire conversation transcript and hoping the model didn't hallucinate its own history.

With typed state, you check the state object. Did the search node populate the sources array? Is the draft field non-empty? Is the status field one of the allowed values? The verification becomes mechanical. The judgment stays human.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state is the verification infrastructure for agent workflows. It turns "trust the model" into "audit the run."</p></div>

## The reversibility angle

There's another connection to something I wrote about in May: [Reversibility Is the New Architectural Correctness](/posts/reversibility-is-the-new-correctness/). The argument there was that when porting gets cheap, the right move isn't the one most likely to be correct forever. It's the one most reversible if you're wrong.

Typed state is the reversibility layer for agent workflows. When your agent's knowledge lives in a declared schema rather than a prompt transcript, you can swap models without losing the thread. You can change the routing logic without rewriting the memory. You can add a new node that reads the same state contract and immediately knows what every other node knows.

This is why I think the framework convergence matters more than the model release. Opus 5 is a better payload. Typed state is a better pipe. You can swap the payload without rebuilding the pipe. You cannot swap the pipe without losing the payload.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state makes agent workflows reversible. Swap the model, keep the state. Change the routing, keep the memory.</p></div>

## What this means for how you build

If you're building agents today, the question isn't "which model should I use?" It's "what is my state contract?"

Start with the schema. Define the fields your workflow needs. Declare the types. Make every node read and write the same contract. Then pick the model that fits each node's job. Cheap model for routing. Expensive model for synthesis. Fast model for retrieval. The model is a component. The state is the architecture.

I think the teams that figure this out first will have a structural advantage that compounds. The advantage isn't smarter agents. It's legible agents. They can see what the system knows, test what it does, and fix what breaks without guessing.

The next wave of agent capability won't come from bigger models. It will come from better contracts between the models we already have.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Start with the schema. Pick models per node. The state contract is the architecture. The model is a component.</p></div>

## Closing

I don't know which model will be on top in six months. I don't think it matters as much as we pretend. The frameworks are converging. The state contract is the durable layer. The model is the swappable part.

Jonas Risbrandt posted something on LinkedIn last week that I haven't been able to verify word-for-word, but the gist was this: the teams winning with agents are the ones treating state as a first-class citizen rather than a side effect of the prompt. I think that's right. And I think the Opus 5 release, with its alignment claims and its cost structure, is the clearest signal yet that the industry agrees.

The model is becoming a utility. The state is becoming the product. Build accordingly.
