A [2026 paper in *Management Science*](https://doi.org/10.1287/mnsc.2025.00535), a peer-reviewed journal about business and operations, covered field experiments with 4,867 developers at three large companies. Access to an AI coding assistant, software that suggests or generates code, increased completed tasks by about 26% in those settings. Yet [METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/), a nonprofit that studies advanced AI systems, found that 16 experienced developers working on public software repositories took 19% longer on 246 issues when they used early-2025 AI tools.

These findings do not produce a universal law about developer productivity. They show that AI can have a large effect on implementation speed, while the result still depends on the task, the tools, and the surrounding system. I think the more important economic question is what happens when enough implementation becomes cheap enough to make software that was once too expensive worth building.

AI can make some software dramatically cheaper and faster to build, but that does not eliminate the need for engineers. It changes where valuable engineering work happens. As implementation becomes increasingly automated, the bottleneck moves toward understanding messy real-world problems, deciding what should be built, fitting it into an organization, testing it against reality, and improving it after launch.

  <span class="chapter-tldr__label">In short</span>
  <p>AI-assisted coding already produces large gains in some settings and losses in others. The strategic signal is that implementation capacity is changing, so understanding the right problem becomes more valuable.</p>
</div>

## Cheap code expands the problem frontier

The usual conclusion is that cheaper coding means fewer engineers for the same backlog. I think that frame is too narrow. Lower implementation cost can also expand the backlog by making small, specialized systems practical: a tool for one claims team, one factory process, or one unusual customer journey that could never justify six months of conventional development.

This creates a useful paradox. Companies can build more software, so software reaches deeper into narrow workflows. Those workflows contain more local rules, undocumented exceptions, and human judgment, which means the work requires closer contact with the people who understand them.

This is a forecast, not an established economic law. Its possibility still matters because it changes the question from how much coding capacity a company needs to how many valuable problems it can now afford to solve.

<div class="chapter-tldr">
  <span class="chapter-tldr__label">In short</span>
  <p>Cheaper implementation may reduce effort per system while increasing the number of systems worth creating. As software reaches more specialized work, local context becomes part of the engineering problem.</p>
</div>

## The FDE owns the messy middle

A Forward-Deployed Engineer, or FDE, is an engineer who works directly with a customer's domain team from discovering the problem through putting the system into live use, rather than waiting for a finished specification. [Palantir](https://jobs.lever.co/palantir/1bb19522-3936-4adc-9ced-c3df8b5900b9), a US software company founded in 2003, says it pioneered this position by embedding engineers with customers. Its [2020 public filing](https://www.sec.gov/Archives/edgar/data/1321655/000119312520230013/d904406ds1.htm) also said that time in the field helped improve its software platforms.

The title has since spread. [OpenAI](https://jobs.ashbyhq.com/openai/305a4b22-7ff9-4fa5-9229-c6a22c9aa64f), the AI company behind the ChatGPT assistant, currently describes its FDEs as owning discovery, defining the project's scope, system design, building, and live rollout with customer engineering and domain teams. I think the title matters less than this operating pattern: the engineer stays close enough to learn what the specification left out.

That proximity has a repeatable loop: **Observe → Understand → Build → Evaluate → Learn → Improve.** Evaluation means checking the system against real examples, rules, and outcomes, not merely seeing whether the software runs. This fits [RAND's 2024 research](https://www.rand.org/pubs/research_reports/RRA2680-1.html): after interviewing 65 experienced data scientists and engineers, the US nonprofit research organization found that AI projects often struggled because teams chose the wrong problem or measure, missed the business workflow, lacked suitable data, or could not support deployment.

<div class="chapter-tldr">
  <span class="chapter-tldr__label">In short</span>
  <p>The FDE joins discovery, building, rollout, and learning in one role close to the customer. Its value comes from shortening the distance between a real workflow and the evidence that the resulting system works.</p>
</div>

## A two-date rule changes the system

Consider an illustrative insurance scenario, not a reported client case. An insurer wants to automate part of claims handling, so an FDE sits beside an experienced claims handler. The AI recommends approving a claim, but the handler rejects it because the damage happened before the policy renewal, a rule that requires comparing two dates and was never properly documented.

This is [**tacit knowledge**](https://doi.org/10.3386/w20485): know-how used in real work that has not been fully written down. The valuable engineering work begins with the expert's correction. The FDE adds the date check to the workflow so that this condition blocks automatic approval, routes the claim for review, and records the reason.

The failed claim then becomes an **evaluation case**, a saved example used to test later versions of the system. A representative test set should include similar date-boundary cases, while the claims owner, meaning the accountable business person, sets the acceptable false-approval level and can stop release. The team should also track handling time and cost per correctly handled claim, because faster output is worthless if it produces the wrong business decision.

A short operating charter makes the arrangement durable. It names the sponsor and budget, the domain owner and baseline, the acceptance threshold and review rhythm, the person with stop authority, and the production owner who receives the workflow. It also funds maintenance after the FDE leaves and brings in legal, risk, procurement, or workforce representatives when the change touches their responsibilities.

<div class="chapter-tldr">
  <span class="chapter-tldr__label">In short</span>
  <p>The decisive step is turning an expert's unwritten exception into a workflow rule, a test case, and a measurable control. Named owners, stop authority, and funded maintenance keep that learning alive after the first build.</p>
</div>

## The working unit has three parts

The claims handler is a **domain expert**, someone whose judgment comes from working inside the process. I think domain experts become more important as implementation gets cheaper because they know what good looks like, which exceptions matter, and when a plausible answer is still wrong.

The working unit is **Domain Expert ↔ FDE ↔ AI**. AI supplies implementation capacity. The FDE translates observations into systems and tests. The domain expert supplies the context and judgment that keep the system tied to reality.

The [US National Institute of Standards and Technology](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.100-1.pdf), the Commerce Department agency for measurement and technical standards, calls AI systems **socio-technical** because their results depend on technology, people, organizations, and the setting where they operate. Its risk framework calls for domain input, tests that reflect real deployment, human oversight, user feedback, and continued monitoring. That is close to the FDE loop because building and learning remain connected.

The engineer's contract changes with it. Yesterday it was, “Tell me what to build and I'll code it.” Today it is, “Tell me the problem and I'll build it.” Tomorrow it may become, “Show me how your business works and I'll help figure out what we should build.”

<div class="chapter-tldr">
  <span class="chapter-tldr__label">In short</span>
  <p>AI provides capacity, the domain expert provides grounded judgment, and the FDE turns both into a system that can improve. Engineering moves closer to the business because context is now part of implementation.</p>
</div>

## One engineer can direct more capacity

An **AI agent** here means software that can carry out a sequence of tool-using steps under a person's direction. One FDE may increasingly direct agents for coding, research, data analysis, and testing as an invisible engineering team. The potential is large, but every added agent also creates another place where bad data, weak instructions, or unchecked actions can cause failure.

The useful measure is therefore not how many agents are running. Teams should compare quality, elapsed time, and cost per accepted business outcome, keep a record of important actions, and limit what each agent is allowed to change. A payment or customer message cannot always be reversed after it leaves the system, so actions that move money or affect customers need approval or a safe holding point before they happen.

If AI keeps lowering implementation cost, the consultancy offer changes too. Selling implementation hours becomes less distinctive when clients can access more capacity; the stronger proposition is entering an organization, learning how it works, and leaving behind a functioning system with evidence, controls, an owner, and a maintenance budget. Most public evidence cited here comes from US companies and institutions, so Nordic and European organizations still need to prove the model locally with their own rules, workforce arrangements, data boundaries, and supplier risks built into the design.

By 2029, the forecast should be visible in role descriptions, budgets, and results. FDE-style teams should beat the old handoff model on cycle time, cost per correct outcome, and production error rates; domain-expert time should be funded as delivery work; and ownership should survive the embedded engineer's departure. If those changes do not appear, or if proximity adds cost without improving outcomes, the forecast weakens.

I think the FDE is one of the clearest previews of software engineering's future because the role treats code as capacity rather than the final product. The scarce resource becomes the person who can understand a messy human problem and turn it into a functioning AI system.

<div class="chapter-tldr">
  <span class="chapter-tldr__label">In short</span>
  <p>The FDE can direct much more implementation capacity, but that capacity only creates value when outcomes, controls, ownership, and handoff are explicit. The sharper question is no longer only how many developers we need when AI writes more code, but what engineers can do when writing code is no longer the limiting factor.</p>
</div>
