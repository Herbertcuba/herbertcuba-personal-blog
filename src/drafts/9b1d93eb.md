A Swedish engineer named Jonas Risbrandt posted something on LinkedIn last week that I haven't been able to verify word-for-word. The gist was a four-step sequence. One prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state.

I tried to skip the last step myself. I built an agent last month that could research a topic, write a summary, and post it to an internal wiki. The model was fine. The prompt was fine. The thing kept forgetting what it had already done. It searched the same term twice, lost the thread of its own argument, and occasionally claimed it had already posted when it hadn't. I spent three days prompt-tuning before I realized the problem was not the model. I had no idea what the agent knew at any given moment.

That is the gap typed state closes.

## The model release that nobody talked about

Anthropic shipped Claude Opus 5 on July 24th. The Hacker News thread hit 1,762 points and 1,311 comments. The top-line claim from Anthropic's announcement was that Opus 5 is "our most aligned model to date." The quote continues: "It adheres to Claude's Constitution better than Opus 4.8, Sonnet 5, or Fable 5; exhibits the lowest rates of deceptive behavior; and is the least susceptible to being tricked into misuse."

That should have been the conversation. Instead, the thread was about cost. Fable 5 is twice the price. Opus 5 is good enough for most tasks. The real constraint is no longer capability.

I think that reaction is the signal. When a major model release gets treated as a routing decision rather than a leap, the bottleneck has moved. The somewhere else is state. I think that is why Jonas Risbrandt's four-step sequence feels right in retrospect. It is not a marketing ladder. It is a damage report.

## The four waves, explained as a forcing function

A prompt is a request. You describe what you want, the model answers, and the program checks whether the answer is usable. This works for one-shot tasks. It fails the moment the task needs memory, because the only memory the agent has lives inside the prompt or the conversation transcript.

A loop adds repetition. The model calls tools, observes the results, and tries again. The loop gives you multiple actions, but the memory is still the message list. A confused agent can spend the night buying API calls, and the only way to stop it is a step limit you bolt on from the outside.

A graph adds branching. Some paths retry a failed search. Some paths rewrite a rejected draft. Some paths pause for human approval. The graph makes the routes visible, but the state still lives inside the messages that pass between nodes. The structure is clear. The data is not.

Typed state moves the memory out of the messages and into a declared schema. Every node reads and writes the same contract. You can inspect the run, serialize it, resume it, and test it. The model becomes one function among many. The state becomes the system.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts handle one call. Loops handle repetition. Graphs handle branching. Typed state makes the shared memory inspectable and enforceable.</p></div>

## Why typed state is the engineering win

Prompt engineering asks the model to remember. Typed state tells the system to remember. The difference is whether you can verify what the agent knew when it made a decision.

I think this is the same craft move that made Rails possible in 2005. Before Rails, web teams stitched together raw SQL, CGI scripts, and templating languages. Rails did not invent databases or HTML. It gave the web a convention: models, views, and controllers with a schema and predictable state. The revolution was not a faster language. It was a shared contract that let teams reason about a running system without reading every line.

Typed state is doing the same thing for agents. It does not make the model smarter. It makes the system around the model legible.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state is the Rails moment for agents: not a faster engine, but a shared contract that lets teams reason about a running system.</p></div>

## What breaks without it

The failure mode is not dramatic. It is incremental and hard to audit.

First, the prompt wears a toolbelt. The model is asked to remember, plan, verify, and summarize at the same time. Then loops hide state corruption, because the message list grows and the model's attention degrades. Then graphs hide the loops, because the branches look organized while the underlying data is still a conversation transcript. You end up with a stateful mess that nobody can audit without reading the entire run.

This connects directly to something I wrote about in March, [The Verification Debt Crisis](/posts/2026-03-09-verification-debt-crisis/). AI-generated code is cheap to produce and expensive to verify. Agent workflows multiply that problem. An agent that produces ten times more output than a human is only useful if you can verify what it did.

Without typed state, you are approving work based on vibes. The agent says it searched, says it found sources, says it wrote a summary. You have no way to check any of that without reading the whole transcript and hoping the model did not hallucinate its own history.

With typed state, you check the state object. Did the search node populate the sources array? Is the status field one of the allowed values? The verification becomes mechanical. The judgment stays human.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Without typed state, agents hide corruption inside growing transcripts. Verification debt becomes the real bottleneck.</p></div>

## The reversibility angle

There is another connection to something I wrote in May, [Reversibility Is the New Architectural Correctness](/posts/reversibility-is-the-new-correctness/). The argument there was that when porting gets cheap, the right move is the one most reversible when you are wrong, rather than the one most likely to be correct forever.

Typed state is the reversibility layer for agent workflows. When the agent's knowledge lives in a declared schema rather than a prompt transcript, you can swap models without losing the thread, change routing without rewriting the memory, and add a new node that reads the same contract and immediately knows what every other node knows.

HAL 9000 is the useful reference here. HAL does not lie. HAL is trying to help. But HAL optimizes for one objective, mission success, and when that objective quietly misaligns with what the humans need, HAL keeps performing confidently because no part of the system knows to question the frame. A single large language model in production is a little like that. It is helpful, fluent, and structurally unable to notice when the frame itself is wrong. Typed state is the mission board that lets the crew see what the ship actually knows.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state makes agent workflows reversible and inspectable. It is the mission board that lets humans question the agent's frame.</p></div>

## What to do Monday morning

If you are building agents today, the question has moved from "which model should I use?" to "what is my state contract?"

Start with the schema. Define the fields your workflow needs. Declare the types. Make every node read and write the same contract. Then pick the model that fits each node's job. Cheap model for routing. Expensive model for synthesis. Fast model for retrieval. The model is a component. The state is the architecture.

I think the teams that figure this out first will have a structural advantage that compounds. The advantage is legibility over raw capability: agents whose state you can inspect, test, and repair without guessing.

I don't know which model will be on top in six months. I don't think it matters as much as we pretend. The frameworks are converging. LangGraph, Inngest's AgentKit, and Contentful's Skill-kit have all landed on typed state machines as the core abstraction. Three independent teams, same conclusion.

The model is becoming a utility. The state is becoming the product. Build accordingly.
