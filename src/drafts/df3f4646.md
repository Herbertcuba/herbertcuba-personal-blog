# Every edge is a claim about waiting

Every edge in a workflow claims that one job must wait. A straight pipeline is the simplest graph: one directed path. A directed acyclic graph, or DAG, can branch and merge but cannot loop; a conditional graph chooses an edge from runtime state, while a cyclic graph can return to earlier work. A hybrid puts bounded branches or cycles inside a linear backbone.

I think the hierarchy is backwards. Production needs only the topology the work justifies. In [a July 2026 article on graph engineering](https://x.com/AnatoliKopadze/status/2080668775796314331), author Anatoli Kopadze wrote, “A graph buys breadth. It does not buy better judgment.” He also asks whether two jobs need an edge. His test starts with data flow; this article adds shared-resource waits.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose the minimum topology for every real wait, including those hidden in shared resources.</p></div>

## Map the waits before drawing the graph

A data dependency means one job consumes another’s result. A resource dependency means separate jobs can change the same mutable resource, such as a file, database row, approval record, or account. A read-only snapshot removes the write conflict, but not a common API quota.

Ingest request → validate schema → apply policy → persist result belongs in a pipeline because each stage needs an earlier output or authorization. I think schema checks, counts, duplicate detection, and fixed routing belong in deterministic code; models belong where judgment is needed.

Remove an edge only when B neither consumes A’s output nor conflicts with A over a shared write or capacity. [PostgreSQL, a relational database, documents one updater waiting on an earlier transaction](https://www.postgresql.org/docs/current/transaction-iso.html). [Stripe, a payment platform, separates request-rate limits from simultaneous-request limits](https://docs.stripe.com/rate-limits). Across teams, research may share one search quota and legal queue. If parallel runs spend the saved time on locks, queues, or rate limits, the wait merely moved.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Remove an edge only when neither data nor shared resources require the wait.</p></div>

## Design the join before the fan-out

Fan-out starts independent branches; fan-in merges their results. Five market-angle searches may run together before one report merges the verified findings. Parallelism can remove artificial serial waiting, but the critical path remains the longest required chain. An all-required merge waits for its slowest branch. I think the merge is the real decision because it exposes the coordination tax: the cost of tracking branches, joins, partial failures, and recovery.

Persist the branch and join contract:

```yaml
branch:
  run: R42
  id: angle-3
  attempt: 2
  required: true
  status: succeeded
  input_ref: request-v7
  output_ref: finding-91
  idempotency_key: R42/angle-3
  deadline: 2026-08-15T14:30:00Z
  provenance: sources-and-tool-v4
join:
  expected: [angle-1, angle-2, angle-3]
  required: [angle-1, angle-3]
  revision: 1
```

Reject `succeeded → running` within one attempt; a retry creates another attempt. [Idempotency](https://docs.stripe.com/api/idempotent_requests) means retrying the same logical write does not repeat its intended effect. If required `angle-1` misses its deadline, publishing stops; an absent optional branch gets a reason. A late result creates revision 2 instead of silently changing revision 1.

The workflow owner owns the partial join and chooses retry or escalation; the release owner rolls back; the budget owner funds human handling. [AWS Step Functions, Amazon’s state-machine service, can run and wait for parallel branches](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), with [configured retry and error handling](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html). It supplies mechanics; your team decides required evidence and acceptable degraded output.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Define branch identity, join completeness, failure policy, ownership, and safe retries before fan-out.</p></div>

## Let state and measurement earn the rest

Use a conditional edge when state changes the route, and a cycle when state sends work back. A cycle needs a stop rule and a hard step or cost cap. I think a fixed two-pass review should remain a DAG; only a runtime result that decides whether to refine, stop, or escalate earns a return edge. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) covers loop language and exit conditions.

Recovery terms differ: a retry reattempts one logical job; a resume continues an interrupted execution from stored state; a rerun starts a new execution from chosen inputs; history replay rebuilds state from recorded events. [Temporal, a durable workflow engine, documents that last mechanism](https://docs.temporal.io/workflow-execution). Isolate branches with ownership, partitioned keys, transactions, locks, immutable inputs, or separate workspaces. The runtime supplies mechanics, not the topology decision.

My take is to test one independent branch for one release window behind a feature flag, a switch that can disable it. The architecture owner sets the bar first: perhaps 20 percent lower p95 elapsed time, meaning 95 percent of runs finish within it, at most 10 percent more cost per successful task, 99.5 percent complete required joins, and no extra operator time. The release owner reverts on a miss. I don’t know whether the branch earns its place until runs clear that bar.

Ask four questions: What consumes an earlier result? What can overlap without a mutable-resource conflict? Can state change the route or stop condition? Can a partial failure be detected, explained, and replayed? I think the answers often yield a hybrid: a linear spine with short research or verification branches. [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, structured state, and trust controls after selection. Complexity belongs only where measured work demands it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Benchmark the linear baseline, promote one bottleneck at a time, and keep the smallest truthful topology.</p></div>
