AI builders often treat a graph as the grown-up architecture and a pipeline as something to escape. I think that reverses the decision.

Topology is simply the shape of nodes and routes. A linear pipeline is one ordered path, so it is already a graph topology. A directed acyclic graph, or DAG, has directed dependencies and no path that loops back to an earlier node; it may be straight or branched.

The useful question is smaller: what is the minimum topology that expresses the workflow's real waits, safe independence, and runtime decisions? Start there, then make every extra edge earn its operational cost.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Pipeline versus graph is a false choice. Choose the smallest graph that tells the truth about the work.</p></div>

## Find what truly has to wait

For every job, record what it reads, produces, and can change. A data dependency is clear: policy application waits for schema validation because it consumes a validated request. I think that required handoff justifies the edge.

A mutable resource is a file, database record, or workspace a job can change. Two jobs may exchange no output yet collide on a shared write; [PostgreSQL, the open-source relational database, documents](https://www.postgresql.org/docs/current/transaction-iso.html) how one updater can wait for another. Scarce capacity is different: an approval gate, API quota, or concurrency cap can serialize otherwise independent work. [Stripe, a payment API provider, documents](https://docs.stripe.com/rate-limits) rate and concurrency limits as separate controls. Shared read-only input creates no write conflict.

Now apply the fake-edge test. If B does not consume A's result, neither job changes the same resource, and they do not compete for constrained capacity, the A → B edge may be artificial.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Map data handoffs, shared writes, and scarce capacity before deciding that two jobs are independent.</p></div>

## Match the topology to the route

Keep a straight pipeline when the route is known and sequence is real: ingest request → validate schema → apply policy → persist result. Each stage needs the prior result or authorization. A visible path can make ownership and recovery easier to trace. Replay, meaning rerunning recorded input after failure, can follow the same known route. I think that clarity is a production strength, not a primitive limitation.

Use a branched DAG when the work is genuinely wide and bounded. Fan-out starts independent branches; fan-in merges their results. Five market angles can be researched separately, verified, and then combined. [AWS Step Functions, Amazon's managed workflow service, specifies](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html) that its parallel state runs branches concurrently when possible and waits for all before continuing. That illustrates the critical-path limit: the longest required chain, including the slowest required branch, controls completion time.

Use a conditional graph when current state selects the next route, and a cyclic graph when a route can revisit earlier work. A temporary error can select a retry route; refinement can return to an earlier step until a defined score is reached. Every cycle needs a stop rule and a hard budget. I think fixed predicates, counters, schema checks, and duplicate detection belong in ordinary code; model calls belong where judgment is actually required. No topology improves that judgment by itself.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use sequence for real prerequisites, branches for bounded independence, and cycles only for state-driven return paths.</p></div>

## Make the coordination tax earn itself

The merge carries the fan-out's obligation. It must know the expected and required branches, each output shape, and the policy when one times out. A partial failure means some branches finish while others fail or disappear. I think the merge is the real architecture decision because topology supplies no failure policy.

Retries sharpen that decision. Idempotency means the same logical request can be retried without repeating its effect; [Stripe's official API documentation](https://docs.stripe.com/api/idempotent_requests) shows one concrete design. Branch isolation means separating concurrent state or workspaces so one branch cannot overwrite another. Quota handling, branch traces, provenance, and replay make the coordination tax visible.

This is why a hybrid is often practical: a linear control backbone with a short fan-out/fan-in or conditional section inside it. It contains wider behavior to the stage that needs it. I don't know whether a branch pays for itself until branch duration, throttling, retry rate, merge completeness, and recovery are measured.

Before widening the design, ask four questions:

1. What must wait because it consumes an earlier result?
2. What can run independently without changing the same resource or exhausting shared capacity?
3. Can runtime state change the next route or stopping condition?
4. Can the system detect, explain, and replay a partial failure?

These questions choose the topology. Two related articles take over after that decision: [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) covers feedback-loop terms and exit conditions; [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, typed workflow state, and operational trust.
