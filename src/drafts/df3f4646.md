Architecture should describe where work must wait. When one stage needs another stage’s result or authorization, the dependency is real. When two stages can proceed without exchanging results or fighting over shared state, serial execution needs a reason.

I think the strongest default is the smallest workflow shape that tells this truth. A wider graph can increase coverage or remove serial waiting, but it cannot improve model judgment by itself. That takes evidence, validation, alternate paths, and explicit controls.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Start from the work’s real waits and conflicts, then add only the branches or return paths they require.</p>
</div>

## Draw the dependencies the diagram hides

A data dependency exists when one job consumes another’s output. A resource dependency exists when jobs share something scarce or writable, even if their outputs never meet. A mutable resource is anything a job can change, such as a file, database row, workspace, or approval record; a shared read-only snapshot creates no write conflict.

The distinction is operational, not academic. [PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html), an open-source relational database, documents how one updater may wait for another transaction touching the same row. [Stripe](https://docs.stripe.com/rate-limits), a payment API provider, separately documents limits on request rate and simultaneous requests. Both can create a dependency that the data-flow diagram misses.

Apply the fake-edge test to each dependency arrow, or edge. If B consumes no result from A, and the jobs neither change the same state nor compete for constrained capacity, A → B may be artificially serial. I think an edge should survive only when the team can name what must wait.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Map consumed outputs and hidden resource conflicts before deciding that two jobs can run together.</p>
</div>

## Choose the route that state requires

Keep one ordered path when the route is known and every stage needs the previous result. Ingest request → validate its shape → apply policy → save the result is a pipeline because each step enables the next. Replay means running recorded work again after failure; the obvious predecessor chain makes that route easier to inspect. I think fixed validation, counting, duplicate detection, and routing rules belong in deterministic code, where the same input follows the same rule.

Use a branched DAG when the work is genuinely wide. Fan-out starts independent branches; fan-in merges their results. Five market questions can be researched separately and then combined into one report, but the critical path, meaning the longest required chain of work, still includes the slowest required branch. [AWS Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), Amazon’s managed workflow service, documents this concrete join behavior: its parallel state waits for every branch to terminate before continuing. I think the rules for merging matter more than the number of branches.

A conditional graph chooses the next step from runtime state, the current outputs and status the system can inspect. A cyclic graph can revisit an earlier step. If weak evidence routes to verification, a retryable error returns to a tool call, or a failed check escalates to a person, state has changed the route. [LangGraph](https://docs.langchain.com/oss/python/langgraph/graph-api), a framework for stateful agent workflows, documents conditional edges, loops, and execution limits. I think a cycle earns its place only with a reason to return, a stop rule, and a hard budget.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Use one path for real sequence, a branched DAG for independent breadth, and a condition or cycle only when current state changes what happens next.</p>
</div>

## Make coordination pay for itself

The coordination tax arrives at the join. A partial failure means some branches finish while others fail or time out, so the merge needs expected branch identifiers, an expected output structure, a deadline, provenance, meaning the source and history of each result, and a missing-result policy. Retried side effects need [idempotency](https://docs.stripe.com/api/idempotent_requests), meaning the same logical request can run again without repeating its intended effect. Branch isolation means separate writable workspaces. You also need rate-limit controls, per-branch records for debugging, and a budget for duplicated model context.

My take is to localize that tax. Keep intake, validation, policy, approval, and saving on a linear backbone; let bounded research or verification fan out and converge inside it. That is the useful hybrid. I don’t know whether a branch pays for itself until branch duration, rate-limit delays, retry rate, merge completeness, and replay success are measured.

Before changing the shape, ask:

1. What must wait because it consumes an earlier result?
2. What can run independently without changing the same resource?
3. Can runtime state change the next route or stop rule?
4. Can the system detect, explain, and replay a partial failure?

For the deeper mechanics after this choice, [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) examines loop language and stop conditions, while [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, how workflow state should be structured, and the controls that make a chosen workflow trustworthy.

<p>Choose the smallest workflow shape that makes every real wait, branch, and return path honest, and make every extra edge earn its recovery cost.</p>
