# Choose the smallest workflow topology that tells the truth

I think “pipeline or graph?” hides the real architecture decision. A pipeline is already a graph with one directed path. A directed acyclic graph (DAG) may branch and merge but has no route back to an earlier node; a cyclic graph can return.

Before drawing edges, separate three concerns: precedence says what must happen before what; route selection says whether runtime state chooses the next step; admission control limits ready work when capacity or a shared resource is scarce. Width can increase coverage, but it does not improve model judgment by itself.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose precedence, runtime routing, and resource admission separately, then use the smallest topology that expresses the work.</p></div>

## Draw precedence before adding width

Precedence starts with consumed outputs. In ingest request → validate schema → apply policy → persist result, every stage needs the preceding result or authorization. I think that visible order is a production strength because ownership and replay remain obvious.

Now apply the fake-edge test. If two market-angle jobs read the same unchanging request and write to separate workspaces, neither consumes the other’s result, so they remain sibling nodes. A provider quota may still cap concurrency, but a semaphore, a counter that limits simultaneous work, enforces that quota without inventing `angle-1 → angle-2`, as [Python’s standard-library documentation explains](https://docs.python.org/3/library/asyncio-sync.html#asyncio.Semaphore). For a shared customer-row write, use a database transaction or per-customer queue; that controls access without creating a data edge.

This distinction prevents needless serialization and unsafe concurrency. Keep schema validation, duplicate removal, counting, and fixed routing in deterministic code; reserve model calls for judgment.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Edges express required order; quotas and shared writes need their own controls rather than artificial A-to-B dependencies.</p></div>

## Design the join before the fan-out

Fan-out starts independent branches; fan-in merges their results. Five jobs can research separate market angles from one read-only snapshot, then feed one report merge. [AWS Step Functions, Amazon’s managed workflow state-machine service, documents a Parallel state that waits for every branch to terminate](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html). An all-required merge therefore finishes after its last required branch.

I think the join is the real architecture decision. Start with branch identities, required and optional results, output schema, and provenance, meaning the inputs, sources, models, and tools behind each result. Recovery covers deadlines, retries, cancellation, and idempotency, which means a retry does not repeat the intended external effect. The completion rule says when the merge becomes final and what happens to late results.

```text
required=[angle-1, angle-2] optional=[angle-3]
31s angle-1#1 completes
32s duplicate angle-1#1 -> ignore
60s angle-2#1 times out -> retry; request angle-3 cancellation
78s angle-2#2 completes
79s revision=1 inputs=[angle-1, angle-2] missing_optional=[angle-3] degraded=true
82s angle-3 arrives late -> audit only; revision=1 remains final
```

This is a custom tolerant merge, not the AWS Parallel state’s default. In the 2013 peer-reviewed article [“The Tail at Scale”](https://www.barroso.org/publications/TheTailAtScale.pdf), Google researchers Jeffrey Dean and Luiz André Barroso explain why delays become more visible when one request waits across many components. Measure branch times instead of promising a fixed parallel speedup.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Parallelize only independent work, and specify the exact result of timeout, retry, duplicate completion, cancellation, and late arrival before execution.</p></div>

## Let state earn conditions and cycles

Conditional routing means recorded runtime state selects the next edge, but it can remain acyclic. A risk result may route a request to automatic approval or human review without returning. A cycle is different: it revisits earlier work, as in verify → revise → verify. If two review passes are known in advance, two DAG stages tell the truth more clearly.

I think a return edge earns its place only when changed state can alter the next attempt. Give it a meaningful stop rule and a hard step or cost limit. [LangGraph, an open-source framework for stateful workflows, documents state-selected edges and a recursion limit for looping graphs](https://docs.langchain.com/oss/python/langgraph/graph-api). [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper on loop terminology and exit conditions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A condition selects a route; a cycle adds a return path, and every return needs both changed state and a bounded stop.</p></div>

## Promote a hybrid with a test card

I think a hybrid is often the strongest production default: a linear path for intake, policy, approval, and persistence, with a bounded research or verification burst. That burst must pay for join state, safe retries, separate workspaces, quotas, traces, model tokens, and operator time. Track p95 elapsed time, the threshold within which 95 percent of runs finish, and make the promotion auditable and reversible:

```yaml
baseline: linear/current-release
candidate: hybrid/research-fan-out
cohort: {size: predeclared, mix: production-routes, window: one-release}
inject: [required-timeout, duplicate-completion, optional-late-arrival]
measure: [p95-elapsed, setup-hours, cost-per-success, completeness, operator-minutes, replay-success]
owner: release-owner
approver: architecture-owner
disable_switch: research-fan-out
accept: predeclared-service-recovery-and-budget-bars-pass
rollback: any-guardrail-miss
```

No sample size or acceptance bar is defensible for every system; lock yours before results and cover the production routes and input sizes that matter. I don’t know whether a branch earns its place until this record beats its baseline without weakening completeness, cost, or recovery.

Ask four questions: What must wait for an earlier result or authorization? Which jobs can be siblings, and what admission controls protect their shared resources? Can state choose another edge or send work back? Can the system detect, explain, and replay a partial failure? Once topology is chosen, [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, typed state, and the trust controls that follow.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use a linear spine with bounded graph-shaped sections, and keep each promotion only when measured benefit pays every coordination bill.</p></div>
