AI builders often mistake graph complexity for progress. Yet a pipeline is a graph with one ordered route. Choose the minimum topology that expresses the work. Extra edges should represent independent work that merges, a state-selected route, or a return after state changes. Each brings partial-failure risk: one branch may fail after others run.

Think of a launch sequence and a fleet engagement. The launch stays ordered because each stage enables the next; the fleet needs independent units and convergence. Giving the launch a fleet topology adds mission-control software. Anatoli Kopadze, author of a [2026 X article about graph engineering](https://x.com/AnatoliKopadze/status/2080668775796314331), wrote: “A graph buys breadth. It does not buy better judgment.” I don't know whether a branch deserves production until its independence and benefit are visible.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A pipeline is the minimum graph. Add an edge only for real breadth, state-dependent routing, or a controlled return.</p></div>

## Dependencies reveal the honest shape

Map data and resources. B depends on A's data when it consumes A's result. A resource dependency exists when jobs can change the same mutable resource, shared state such as a file, database row, or workspace, or compete for an approval or API quota. [PostgreSQL, the open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), shows why: a writer can wait while another transaction updates or locks the same row. The jobs exchange no output, yet the shared write forces coordination.

Apply the fake-edge test: if B consumes no output from A and the jobs share no writable state or quota, their edge may be artificial. A read-only snapshot creates no write conflict because neither branch changes it. By contrast, ingest request → validate schema → apply policy → persist result is a pipeline because each stage needs the prior result. Its critical path, the longest required chain, remains obvious; replay reruns recorded inputs and state. I think that visibility is a production strength when sequence is real. Use deterministic code for counting, schema checks, deduplication, and routing; call a language model only for ambiguous evidence.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Map consumed outputs and shared resources before changing the topology. Real sequence belongs in a pipeline.</p></div>

## A DAG must earn its merge

A DAG, a directed acyclic graph, may branch but cannot loop back. Fan-out starts independent branches; fan-in merges them. Five market searches can fan out when inputs and writable resources are separate. [AWS Step Functions, Amazon's managed state-machine service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), shows the catch: an all-required parallel step waits for every branch, so the slowest limits the merge.

I think the merge is the real architecture decision. A join policy turns branch outcomes into one run outcome: require all, tolerate failures, or involve a person.

A run ID identifies one execution, while branch IDs expose missing work. Mutable-resource keys reveal shared writes, and source provenance records each result's origin. A deadline, retry budget, and stop condition bound waiting and repetition. The owner is accountable; the side-effect boundary marks where writes may occur; replay evidence shows what can be reconstructed. Record it:

```yaml
run_id: market-report-42
owner: research-platform
expected_branch_ids: [market, regulation, customer, competitor, technology]
mutable_resource_keys: []
join_policy: all_required
failure_deadline: 10m
retry_budget: 2
stop_condition: all_received_or_fail_at_deadline
side_effect_boundary: merge_only
replay_evidence: event_log
source_provenance: per_branch
```

A retried write needs idempotency, so repeated attempts produce one logical effect; [Stripe's payments API documentation](https://docs.stripe.com/api/idempotent_requests) documents this with idempotency keys. Reject fan-out when two branches can write the same database record without separate writable state or deliberate serialization. A branch without resource independence and a measured latency or coverage gain should fail review.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A DAG earns its place when independent work has a defined merge, visible missing results, bounded retries, and safe replay.</p></div>

## Runtime state justifies the rest

A conditional graph chooses its next edge from recorded state; a cyclic graph can return to an earlier node. They fit retryable errors, escalation, or refinement with an unknown next step. I think a return earns its place only if a state change alters the next action. It needs a stop rule and a hard time, step, or cost limit; a known pass count fits a fixed DAG. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](/posts/everyone-discovered-loops/) covers feedback terms and exit conditions.

Graph APIs make edges easy, but durability is separate. [Temporal, an open-source durable workflow engine](https://docs.temporal.io/workflow-definition), shows the state-machine alternative: recorded history supports replay while model judgment stays bounded. When replay and duplicate-effect control dominate, I think that substrate matters more than a graph API.

My take is a hybrid: a linear spine with short graph-shaped bursts. Keep gates, checks that block the next stage, and writes that must survive a restart on the linear spine. Fan out bounded research or verification, then return one accepted result. This contains the coordination tax, the extra join, retry, workspace separation, and monitoring caused by branches, while the wider system receives one output.

Four questions guide the design review:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can recorded state change the next route or stop rule?
4. Can the system detect, explain, and replay a partial failure?

Measure before and after: critical-path latency, the share of required results received, duplicate effects, and cost per successful run. Approve the change only when the owner names its gain, failure deadline, write boundary, and replay evidence. Graph tooling makes coordination cheap to draw but expensive to run. [“The 105 minutes after the graph”](/drafts/67821675/) covers evaluation and trust after selection.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use a linear spine and approve extra topology only when an owner can prove a real dependency or state transition, govern partial failure, and show a measured gain.</p></div>
