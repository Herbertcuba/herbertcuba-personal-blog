# When your AI workflow actually needs a graph

Workflow topology is how stages connect. A pipeline is its simplest graph: one ordered path.

A sci-fi launch sequence stays ordered because every stage enables the next; a fleet engagement needs independent units, changing routes, and convergence. Turning the launch into a fleet graph adds mission-control software without changing the work. In a 2026 article on X, formerly Twitter, writer Anatoli Kopadze captured the limit: “A graph buys breadth. It does not buy better judgment.” I think production needs the smallest topology that tells the truth.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Add topology only for independence or a changing run condition.</p></div>

## Start with the dependency map

A data dependency means B needs A’s output. A resource dependency means jobs can change or exhaust the same mutable resource, such as a file, database row, workspace, approval gate, or API quota. [PostgreSQL, a relational database, documents](https://www.postgresql.org/docs/current/transaction-iso.html) one writer waiting behind another on the same row. Separate prompts do not make jobs independent.

If B needs none of A’s result and shares no write, lock, or quota, the A-to-B edge may be fake. A shared read-only snapshot is safe when it cannot change and no other limit is shared. I think teams should map data and resources before counting agents.

Keep a pipeline when sequence is real: ingest a request, validate its schema or expected data shape, apply policy, then persist the result. Replay reruns work from recorded execution history. Idempotency prevents a retry from repeating its effect; [Stripe, a payment-processing company, documents this for API requests](https://docs.stripe.com/api/idempotent_requests). Use ordinary code for validation, counting, deduplication, and fixed routing, leaving models for judgment.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep sequence linear; remove only false data or resource edges.</p></div>

## Use a DAG for genuine width

A DAG, or directed acyclic graph, can branch but cannot return to an earlier stage. Fan-out starts independent jobs; fan-in merges them. Five market-angle searches fit only when they share neither findings nor a mutable resource.

Parallel work can remove serial waiting, but an all-required merge waits for its slowest branch. [AWS Step Functions, Amazon’s managed workflow service, documents](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html) this behavior. The critical path is the longest chain that must finish. I think the merge defines what counts as complete.

Identify the run, expected branches, shared-resource keys, and output shape. Provenance records source and decision history. The join policy sets whether missing work triggers a retry, partial merge, or failure. Record the owner, deadline, retry budget (maximum retries), stop rule, and evidence needed to reproduce the run:

```yaml
run_id: unique-run-id
expected_branch_ids: [angle_1, angle_2, angle_3, angle_4, angle_5]
mutable_resource_keys: []
output_schema: finding-v1
provenance_required: true
join_policy: all_required
owner: research-platform
failure_deadline: 10m
retry_budget: 1
stop_condition: expected_results_received
replay_evidence: required
```

A partial failure leaves some branches complete and others missing. This contract exposes the gap and records what replay must reproduce. Reject fan-out if two branches can write the same database record without isolation or one ordered writer.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A DAG needs independent branches, missing-result rules, safe retries, and measured benefit.</p></div>

## Add routes and cycles when state changes

Runtime state is the stored record of a run’s current condition. A conditional graph chooses the next stage from that record; a cyclic graph can return to an earlier stage. Low evidence might trigger another source check, while two planned reviews remain acyclic. I think a cycle belongs only where changed state changes the next action.

Every return needs a stop rule and a hard limit on attempts, time, or cost. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](/posts/everyone-discovered-loops/) goes deeper on feedback terms, ownership, and exits. When replay and safe database or API writes dominate, consider Temporal, a durable workflow platform that stores event history and replays fixed workflow code, rather than agent-framework control flow alone. Neither foundation removes idempotency.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A cycle needs changed state, a stop rule, and a hard budget.</p></div>

## Keep the graph-shaped part bounded

Converging branches may need partial-failure rules, isolated workspaces, quota control, retries, and input-output records. Only branches that invoke a model raise model-call costs. My take is a linear spine with short graph bursts for research or verification.

Measure critical-path latency, completion coverage meaning the share of expected results returned, duplicate effects, and cost per successful run before and after a change. I don’t know a universal branch limit. I think a branch or cycle should fail review without independent work, an owner, a deadline, replay evidence, and a measurable target.

Ask what must wait, what can run without touching the same mutable resource, whether state can change the route or stop rule, and whether partial failure can be detected, explained, and replayed. After choosing, [“The 105 minutes after the graph”](/drafts/67821675/) covers evaluation, validated state, and trust controls. Graph tooling makes coordination cheap to draw but expensive to govern. The advanced choice is the smallest graph that survives those questions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Approve graph bursts only when benefit exceeds operational cost.</p></div>
