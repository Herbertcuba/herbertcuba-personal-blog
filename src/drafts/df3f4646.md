# Every edge is a claim about waiting

Every workflow edge says one job must wait. A pipeline is the simplest graph: one directed path. A directed acyclic graph (DAG) branches and merges but cannot loop. A conditional graph chooses its next edge from runtime state, the run data; a cyclic graph can revisit work. A hybrid puts bounded branches or cycles inside a linear backbone.

I think production needs only the topology the work justifies. In [a July 2026 article on graph engineering](https://x.com/AnatoliKopadze/status/2080668775796314331), author Anatoli Kopadze wrote, “A graph buys breadth. It does not buy better judgment,” and asked whether two jobs need an edge. His data-flow test inspires my extension: a shared-resource conflict can turn an artificial-looking edge into a real wait.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose the minimum topology that represents every real wait, including shared-resource waits.</p></div>

## Map the waits before drawing the graph

A data dependency means one job consumes another’s result. A resource dependency means two jobs can change the same mutable resource, such as a file, database row, or approval record. A read-only snapshot may remove a write conflict, but not a shared API quota.

Ingest request → validate schema → apply policy → persist result belongs in a pipeline because each stage needs the result before it. I think deterministic code should handle schema checks, counts, duplicate detection, and fixed routing; models should handle judgment. The ordered route keeps ownership and recovery visible.

Remove an edge only when B neither consumes A’s output nor competes with A for a shared write or capacity limit, such as an API quota. [PostgreSQL, a relational database, documents one updater waiting on an earlier transaction](https://www.postgresql.org/docs/current/transaction-iso.html). [Stripe, a payment platform, separates request-rate limits from simultaneous-request limits](https://docs.stripe.com/rate-limits). Teams may share a search quota and approval queue. If locks, queues, or throttling erase the time saved, resource contention is the bottleneck.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>An edge is removable only when neither data nor shared resources require the wait.</p></div>

## Design the join before the fan-out

Fan-out starts independent branches; fan-in merges their results. Five market-angle searches can run together before one report combines them. Parallel work can remove artificial waiting, but the critical path is the longest required chain; an all-required merge waits for its slowest branch. I think the merge is the decision because it exposes the coordination tax: tracking branches, failures, joins, and recovery.

Persist a branch and join contract:

```yaml
branch:
  run: R42
  id: angle-3
  attempt: 2
  required: true
  status: succeeded
  input_ref: request-v7
  output_ref: finding-91
  idempotency_key: R42/angle-3
  deadline: 2026-08-15T14:30:00Z
  provenance: sources-and-tool-v4
join:
  expected: [angle-1, angle-2, angle-3]
  required: [angle-1, angle-3]
  revision: 1
```

Reject `succeeded → running` within one attempt; a retry creates another attempt. [Idempotency](https://docs.stripe.com/api/idempotent_requests) means retrying the same logical write does not repeat its intended effect. Missing required `angle-1` stops publishing and cancels obsolete work; an optional miss gets a reason. Keep a caught failure visible, and create revision 2 for a late result rather than changing revision 1. Provenance is the source and tool trail.

The workflow owner owns the partial join; the release owner controls rollback; the budget owner funds human handling. [AWS Step Functions, Amazon’s workflow state-machine service, can run and wait for parallel branches](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html) with [configured retry and error handling](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html). The runtime supplies mechanics; the team decides required evidence and acceptable degraded completion.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Define branch identity, join completeness, failure policy, ownership, and safe retries before fan-out.</p></div>

## Let state and measurement earn the rest

Use a conditional edge when state changes the route, and a cycle when state sends work back. Every cycle needs a stop rule and a hard step or cost cap. I think a fixed two-pass review belongs in a DAG; only a runtime choice among refinement, completion, or escalation earns a return edge. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) covers loop terms and exit conditions.

A retry reattempts one logical job; a resume continues from stored state; a rerun starts a new execution from chosen inputs; history replay rebuilds state from recorded events. [Temporal, a durable workflow engine, documents replay against stored event history](https://docs.temporal.io/workflow-execution). Durable runtimes provide persistence, retries, and traces, but not topology choice. Isolate branches with separate owners, record keys, transactions, locks, immutable inputs, or workspaces.

My take is to benchmark the linear stage for one release window, then put one independent job behind a feature flag that can disable it. Set the bar: perhaps 20 percent lower p95 elapsed time, meaning 95 percent of runs finish within it; at most 10 percent higher cost per successful task; 99.5 percent of joins containing every required branch; and no added operator time. The release owner reverts on any miss. I don’t know whether the branch earns its place until runs clear the bar.

Ask four questions: What consumes an earlier result? What can overlap without a resource conflict? Can state change the route or stop condition? Can a partial failure be detected, explained, and replayed? I think the answers often produce a hybrid: a linear spine with short research or verification branches. [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, structured state, and trust controls after selection. Choose the smallest topology that tells the truth about every wait.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Benchmark the linear baseline, promote one bottleneck, and keep only complexity that improves results without hiding failure.</p></div>
