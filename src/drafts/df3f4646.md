Agent boxes and arrows can hide the real question: why must one job wait?

Workflow topology is the arrangement of stages and routes. I think design should start with waits: a pipeline is the narrowest graph. Extra paths should describe work, not ambition.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose topology from real waits and changing routes, not visual complexity.</p></div>

## Trace every reason to wait

Record why each edge exists. A data dependency means one job consumes another's output. A resource dependency exists when jobs share a mutable resource, a thing either can change or write to, or compete for the same approval or service capacity.

[PostgreSQL, an open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), documents a writer waiting on a locked record. [Stripe, a payments platform](https://docs.stripe.com/rate-limits), limits request rate and simultaneous requests. So jobs without data handoff can still block.

I think the fake-edge test is simple. If B needs none of A's result, both read an unchanging snapshot, and measured capacity permits concurrency, their edge may be artificial. Shared input is not a conflict; shared writes often are.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Remove an edge only after ruling out data flow and mutable-resource conflict.</p></div>

## Match the route to the work

Keep a linear pipeline when every stage needs the prior result and the route is known: ingest, validate the input shape, apply policy, persist. One predecessor keeps recovery and ownership clear. Replay may mean rerunning recorded input in a basic system; [Temporal, a durable workflow engine](https://docs.temporal.io/workflow-execution), instead re-executes control logic from stored history without automatically repeating completed external work.

A directed acyclic graph branches without a route back. Fan-out starts independent branches; fan-in merges them. Five market-angle investigations can feed one report if worker and downstream capacity support concurrency. The critical path, the longest-duration required chain, still includes the slowest required branch at an all-results join. [AWS Step Functions, a managed workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), makes that wait explicit.

A conditional graph chooses its next node from values available during the run; a cyclic graph can revisit prior work. Use either for bounded retry or refinement when new state changes the route. [LangGraph, a library for stateful agent workflows](https://docs.langchain.com/oss/python/langgraph/graph-api), documents state-based edges and loop limits. I think ordinary code should handle fixed routing, counts, data-shape checks, and duplicate detection; model calls belong where judgment is required.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use a pipeline for sequence, a DAG for independent work, and conditions or cycles when current state changes the route.</p></div>

Scarif maps to a branched graph: independent units act before a necessary merge. A launch sequence maps to a pipeline because each stage enables the next. Treating it as a fleet engagement adds control traffic, not useful independence.

## Design the merge before the branches

Parallelism creates partial failure: what happens when four branches finish and one does not? I think the merge is the real architecture decision. It needs expected and required results, output shapes, source trails, and a policy for retry, exclusion, or escalation.

Retried branches that may repeat side effects need idempotency: the same logical request should not repeat its intended external effect. [Stripe's idempotency-key design](https://docs.stripe.com/api/idempotent_requests) is one implementation, not a universal guarantee that every effect happens once. Branches changing the same resource need isolation, conflict control, or one-at-a-time updates; calls to services with documented limits need concurrency control, queueing, or delayed retries. Parallel model calls can duplicate context and raise token or tool spending, so measure the actual system.

Those obligations are the coordination tax; arrows supply none of them. Any reliability gain depends on explicit failure policy, safe retries, validation, and observable branch records.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A branch belongs in production only with an explicit merge, failure policy, retry safety, and resource limits.</p></div>

## Let evidence promote the topology

A hybrid is a linear control path with a bounded graph-shaped section. I think it is a strong production default: intake, policy, approval, and persistence stay ordered around a brief research or verification fan-out.

Instrument before widening. I don't know whether parallelism wins until branch duration, queueing, throttling, retries, merge completeness, and recovery are visible. My take is to ask:

- What must wait because it consumes an earlier result?
- What can run independently without changing or exhausting the same resource?
- Can current state alter the next route or the stop decision?
- Can operators detect, explain, and replay a partial failure?

Keep fixed passes acyclic; add a bounded cycle only when current results select a return path. The cubagarcia.com article [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) covers loop terms and exit conditions. The cubagarcia.com article [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, typed state (workflow data with enforced shapes), and post-selection trust.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Start with the smallest truthful path; make every branch or cycle prove its value.</p></div>
