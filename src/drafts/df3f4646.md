AI builders often treat an agent graph as advanced and a pipeline as primitive. Yet workflow topology simply means how stages and routes are arranged, and a linear pipeline is already a graph: one ordered path. [Apache Beam, an open-source data-processing system](https://beam.apache.org/documentation/programming-guide/), models pipelines as directed acyclic graphs and calls a sequential example a linear pipeline.

I think production architecture should use only the routes that tell the truth about the work. Parallel branches can remove serial waiting or widen a search, but more arrows do not create judgment, retry safety, or ownership.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose a workflow shape from real dependencies and recovery needs, not from how sophisticated its diagram looks.</p></div>

## Draw dependencies before topology

Start with what must wait. A data dependency exists when one job consumes another's result. A resource dependency exists when jobs alter the same mutable resource, such as a shared file, record, or workspace, or compete for one quota or approval. [PostgreSQL, an open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), documents a writer waiting on a changed or locked record; [Stripe, a payments platform](https://docs.stripe.com/rate-limits), separates concurrency from request-rate limits.

Apply the fake-edge test. If B consumes nothing from A and running them together creates no shared write, exclusive gate, capacity conflict, or duplicate external effect, their edge may be artificial. Jobs can safely read the same read-only snapshot. I think teams will mistake concurrent model calls for independent work, then find the hidden dependency during incident recovery.

Keep the route linear when sequence is real: ingest a request, validate its schema, apply policy, then persist the result. Replay means rebuilding a run from recorded history under the same control rules; external effects still need duplicate protection. Use code for validation, counting, deduplication, and routing, reserving models for judgment.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Remove an edge only after checking consumed outputs, shared writes, capacity, gates, and external effects.</p></div>

## Make the merge operational

A directed acyclic graph, or DAG, has directed dependencies but no route back to earlier work. Fan-out starts independent branches; fan-in joins their outputs. It fits wide work: research five market angles, verify sources, then merge accepted results.

The merge makes the architecture operational. A join policy says which results are required and when the merge may proceed. The critical path is the longest-duration chain of required dependent work, which sets the earliest possible completion time. An all-required join therefore waits for its slowest branch. [AWS Step Functions, a managed workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), waits until every Parallel branch finishes. I think the join policy matters more than the fan-out.

Make that policy reviewable:

```text
run_id: research-042
allowed_status: [pending, running, complete, failed, timed_out]
branches:
  market:     {required: true,  status: complete}
  regulation: {required: true,  status: running}
  competitor: {required: false, status: timed_out}
join_policy: all_required_terminal
retry_budget: 2
stop_condition: deadline_or_budget
owner: research-service
rollback: disable_parallel_stage
```

Accepting this merge is illegal because the required `regulation` branch is still running. The operator should see `join_rejected: required branch regulation is running` and retain branch identities, inputs, errors, retries, and the merge decision. A branch that writes, sends, or charges also needs idempotency: repeating the same logical request must preserve one intended external effect. [Stripe's API documentation](https://docs.stripe.com/api/idempotent_requests) shows one implementation using a request key.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A production join needs expected branches, legal transitions, a missing-result policy, retry safety, source records, and a recovery owner.</p></div>

## Let runtime state earn new routes

A conditional graph selects its next route from current state, the data available to that run. A cyclic graph can return to earlier work. [LangGraph, an open-source framework for stateful agent workflows](https://docs.langchain.com/oss/python/langgraph/graph-api), documents both state-based routing and a configurable loop limit. I think a cycle earns its place only when changed state can change the next action, and it still needs a stop rule plus a hard attempt, time, or cost limit.

Topology is framework-independent. A workflow engine that saves progress, queue workers, state-machine code, or an agent-graph library can implement the same dependencies. I think production often favors a hybrid: keep the main route on a linear backbone, and bound the research fan-out before approval.

Four questions are enough for its design review:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can runtime state change the next route or stopping condition?
4. Can the system detect, explain, and replay a partial failure?

Name the service owner, baseline the linear route, then compare the bounded alternative on latency, accepted findings with their sources, duplicate effects, incomplete joins, recovery time, and cost per successful run. Approve it only with a retry policy, deadline, and rollback condition. I don't know which shape wins before measurement; the framework cannot answer for the team.

[“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) examines loop terminology and exit conditions. [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, declared state, and evidence after topology is chosen.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The smallest truthful topology keeps coordination and recovery work proportional to the value each branch or cycle delivers.</p></div>
