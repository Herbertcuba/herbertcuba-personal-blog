Graph diagrams can make an AI workflow look advanced before they make it useful. I think that reverses the question. Topology, the arrangement of stages and edges, should describe dependencies, not agent count.

Here, a pipeline is a single directed graph path. A DAG, or directed acyclic graph, can branch and merge but never return. A conditional graph chooses its next edge from current state; a cyclic graph can revisit work. Choose the minimum topology that expresses those facts without inventing coordination.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A pipeline is already a graph; earn each branch, condition, and return edge from the work.</p></div>

## Map dependencies before agents

Start with data dependencies: one job waits for another's result. Then map resources. A mutable resource is anything a job can change: a file, database row, approval record, or workspace. A shared API quota can also couple jobs, while a common immutable input is safe to read in parallel.

[PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html), the open-source relational database, documents one writer waiting on another's row change. [Stripe](https://docs.stripe.com/rate-limits), the payments platform, sets separate rate and concurrency limits. I think the fake-edge test is simple: if B consumes no output from A and both can run without a shared write, lock, approval, or scarce capacity, their ordering edge may be artificial. Keep counting, validation, deduplication, and fixed routing in code.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Separate output dependencies from mutable-resource and capacity conflicts before removing an edge.</p></div>

## Keep real sequence linear

Consider a request moving through schema validation, policy, and persistence. Each stage supplies or authorizes the next, so parallelism cannot remove the wait. A straight pipeline keeps its predecessors, replay points, and owners visible.

[Temporal](https://docs.temporal.io/workflow-execution), a durable workflow platform, persists state and replays event history after failure. That recovery comes from the runtime, not the topology. I think an ordered pipeline is often the strongest production artifact when sequence is real.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Do not replace necessary sequence with decorative orchestration; durability and topology are separate choices.</p></div>

## Design the merge before the fan-out

Fan-out starts independent branches; fan-in joins their results. [AWS Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), Amazon's managed workflow service, runs Parallel branches as concurrently as possible and waits for all of them. The critical path is the longest required chain, so an all-results merge inherits its slowest branch.

Five market-angle branches read one frozen brief. The merge expects IDs A through E; each output has a fixed schema, provenance (its source record), input version, and attempt ID. Set a 90-second deadline and one retry. Four outputs can proceed under the degraded policy; fewer fail closed. Reject duplicate and late results. Product owns completeness; platform owns isolation and the join; operations owns recovery and fallback; risk approves degraded output. I think the merge is the architecture decision.

An illustrative review runs 100 frozen briefs over two weeks, capped at five engineer-days. Promotion requires 30 percent lower 95th-percentile latency, the limit met by 95 percent of runs; 99 five-of-five merges; exact replay; ten-minute recovery; and accepted-report cost no more than 15 percent above the serial baseline, including models, runtime, and operator time. Suppose the candidate returns 34 percent, 99 merges, exact replay, eight minutes, and 12 percent. Every bar passes, so promote. This is a decision example, not enterprise evidence; otherwise stay linear. I don't know whether width has earned its place without such a record.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Parallelize breadth only after branch identity, completeness, cost, failure, ownership, and fallback rules are testable.</p></div>

## Route on state and cap the return

Use a conditional graph when current state changes the next route, and a cycle when state sends work back after a retryable tool error, failed evidence check, or refinement decision. If the passes are known beforehand, keep the route acyclic.

Every return needs a reason, stop condition, hard step or cost limit, and escalation. [LangGraph](https://docs.langchain.com/oss/python/langgraph/graph-api), an open-source framework for stateful agent workflows, documents state-based edges and a hard execution limit. I think a cycle without both a state change and a stop rule is an unbounded bill. The related article [Everyone Discovered Loops. Nobody Agrees What the Word Means.](https://www.cubagarcia.com/posts/everyone-discovered-loops/) covers feedback-loop terms, ownership, and exit conditions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Add a condition or cycle only when state explains the next move and stop.</p></div>

The mapping is practical: a launch sequence needs a pipeline because each stage enables the next, while a fleet engagement needs branches, changing routes, and convergence. Turning the launch into a fleet graph only adds mission-control software that can fail.

## Prefer a bounded hybrid

My take is to keep intake, validation, policy, approval, and persistence on a linear spine, while research or verification uses isolated branches with local retries. This confines partial failures, joins, quotas, tracing, and multiplied model use to where width creates measured value. Idempotency means a retry cannot repeat the same external effect.

Close with four questions: What waits for an earlier result? What can run without touching the same mutable resource? Can state change the route or stop? Can the system detect, explain, and replay partial failure? Once topology is chosen, the related article [The 105 minutes after the graph](https://www.cubagarcia.com/drafts/67821675/) addresses evaluation, explicit state, and production trust controls.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose the smallest truthful topology; widen only when measured gain repays its coordination tax.</p></div>
