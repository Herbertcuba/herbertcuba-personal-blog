Graph tools make sophisticated workflows easy to draw. They do not make the work independent, recoverable, or wise. I think that gap explains much of the architecture theatre around AI agents: coordination looks free on the canvas and becomes expensive during an incident.

A pipeline is already a graph, just one directed path. Topology means the layout of stages and connections. The decision is therefore simple to state: choose the minimum topology that tells the truth about the work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Pipeline versus graph is a false choice. Start with the smallest truthful layout, then make evidence earn every branch, merge, condition, and return route.</p></div>

## Draw the edges before the agents

A data dependency exists when one job consumes another job’s result. A resource dependency exists when otherwise separate jobs can change or exhaust the same mutable resource, such as a file, database record, approval gate, workspace, or API quota. [PostgreSQL, an open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), documents conflicting updates waiting on each other. [Stripe, a payments platform](https://docs.stripe.com/rate-limits), separately documents request-rate and active-request limits.

That gives us the fake-edge test. If B consumes nothing from A, and both can run without conflicting writes, approvals, quotas, or external effects, the A → B edge may be artificial. A shared read-only snapshot does not by itself require ordering. I think parallelism should fail review, however, when its supposed branches still collide through an ungoverned shared resource.

## Let behavior choose the shape

Keep a linear pipeline when every stage needs the previous result, as in ingest request → validate schema → apply policy → persist result. Replay means rerunning recorded work while controlling repeated external effects. I think an obvious sequence is often the strongest production artifact when validation, counting, and routing remain deterministic code.

A directed acyclic graph, or DAG, has no route back to an earlier stage. Fan-out starts independent branches and fan-in merges them. This can shorten the critical path, the required chain that controls completion time, but an all-required merge still waits for its slowest branch. [AWS Step Functions, a cloud workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), makes that wait explicit. I think the merge is the real design decision because it needs expected branch IDs, a deadline, result provenance, meaning which inputs and branch produced each result, and a rule for missing work.

A conditional graph selects the next stage from recorded runtime state; a cyclic graph can return to an earlier stage. A cycle earns its arrow only when changed state can change what happens next, and it needs both a stop rule and a hard budget. A hybrid keeps a linear control spine around one bounded branch or return. The Content Engine, Herbert’s article-production workflow, follows an ordered route with quality gates and sends failed work back for revision. That is a state-driven return, not a claim that its research currently runs as a parallel merge. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) examines loop terminology and exit conditions in more depth.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use a pipeline for real sequence, a DAG for independent breadth, a conditional or cyclic graph for state-driven routes, and a hybrid when only one bounded section needs added topology.</p></div>

## Make extra topology earn production

Every branch or cycle adds a coordination tax: partial failures, deadlines, retries, join rules, shared-resource controls, execution records, and cost. A join policy says which results a merge requires and what happens when one is late or fails. Retried side effects need idempotency, a key or rule that prevents one logical action from taking effect twice. Shared writes need a proven control such as separate workspaces, serialization, locks, version checks, or database isolation, which constrains what concurrent work can observe and change.

The same contract can run in a workflow engine, queue workers that pull jobs from a queue, or state-machine code that permits only declared transitions. The drawing does not select the runtime. I don’t know which topology wins before measurement. I think a team should baseline the linear route, test the bounded alternative, then compare critical-path latency, completion coverage, duplicate effects, and cost per successful run.

[“The 105 minutes after the graph”](/drafts/67821675/) covers evaluation and typed state, a schema with declared field types, after this architecture choice. The next fault line is already visible: teams will mistake concurrent model calls for independent work, then discover coordination debt when recovery has no clear owner. Unearned topology is an unowned failure path.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Approve added topology only with a real dependency case, a complete join and recovery policy, one accountable owner, and measured value over the simpler route.</p></div>
