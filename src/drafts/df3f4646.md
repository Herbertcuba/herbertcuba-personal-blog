# When your AI workflow actually needs a graph

Workflow topology is how stages connect and how execution can move between them. A pipeline is already a graph: one ordered path. The decision is how much more topology the work justifies.

A sci-fi launch sequence stays ordered because each stage enables the next; a fleet engagement needs independent units, changing routes, and convergence. In a 2026 article on X, the social platform formerly called Twitter, author Anatoli Kopadze framed the distinction: “A graph buys breadth. It does not buy better judgment.” Used as inspiration rather than evidence, the line separates wider work from better judgment. I think production architecture should use the smallest topology that tells the truth about the work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The minimum topology preserves real sequence, adds branches for genuine width, and uses recorded state only when the route can change.</p></div>

## Begin with the dependencies

A data dependency exists when B consumes A’s output. A resource dependency appears when jobs can change or exhaust the same mutable resource, such as a file, database row, workspace, approval, or API quota. [PostgreSQL, an open-source relational database, documents](https://www.postgresql.org/docs/current/transaction-iso.html) one updater waiting on another for the same row. A shared immutable snapshot is safe only if no write, lock, quota, or external effect competes.

If B consumes none of A’s output and both jobs run without resource conflict, the A-to-B edge may be fake. Separate prompts do not prove independence. I think the map should describe data and resources before it counts agents.

Keep real sequence linear: ingest a request, validate its schema, apply policy, then persist. Replay reruns failed work from a recorded stage. Idempotency lets the same operation retry without duplicating an effect; [Stripe, a payment-processing company, documents this for API requests](https://docs.stripe.com/api/idempotent_requests). Validation, counting, deduplication, and routing belong in ordinary code, with models reserved for judgment.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Sequence belongs in a pipeline; remove an edge only when no data or mutable-resource dependency requires it.</p></div>

## Use a DAG when the work is genuinely wide

A DAG is a directed acyclic graph: its edges point forward, never back to an earlier stage. Fan-out starts independent jobs; fan-in merges their results. Five market-angle searches fit if branches share neither findings nor a writable resource.

Parallel fan-out helps only when it removes serial waiting. If the merge needs every result, the slowest branch bounds that part of the critical path, the longest required chain. [AWS Step Functions, Amazon’s managed workflow service, waits](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html) for every parallel branch before continuing. I think the merge is the real decision because it defines which results count and what absence means.

A partial failure leaves some branches complete and others missing. Record the contract for each execution: a unique `run_id`, expected branch IDs, mutable-resource keys, output schema and provenance, the join policy for missing work, deadline, owner, retry budget, stop condition, and replay or rollback evidence. A validator should reject `fan_out` when two branches can write the same transactional record without isolation or one ordered writer.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A DAG earns its merge when branches are independent, missing results are governed, retries are safe, and latency improves.</p></div>

## Add cycles only when state changes the route

Runtime state records a run’s condition. A conditional graph chooses the next stage from that state; a cyclic graph can return to an earlier stage. Low evidence might trigger another source check, while a retryable error might return work until its budget expires. Two planned reviews remain acyclic. I think a cycle earns its place only when changed state changes the next action.

Every return needs a stop rule and a cap on attempts, time, or cost. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](/posts/everyone-discovered-loops/) covers feedback terms, ownership, and exits. An external effect is a change outside the run, such as a database write. A durable workflow engine persists state and event history so work can resume after failure; an agent framework mainly coordinates model-driven steps. When recovery around external effects dominates, the durable engine may be the better foundation. Neither removes idempotency.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Conditional routes need recorded state. A cycle also needs a reason to return, a stop rule, and a hard budget.</p></div>

## Keep the graph-shaped part bounded

Every branch adds partial-failure handling, merge rules, workspace isolation, quota control, retries, and execution traces, the records of its inputs, outputs, and transitions. It also adds model calls and cost. A branch improves reliability only when alternate paths, validation, and recovery controls are deliberate. My take is that production often favors a linear spine for intake, policy, approval, and persistence, plus a short research or verification fan-out.

Measure critical-path latency, completion coverage, duplicate effects, and cost per successful run before and after the change. Ask four questions: what must wait; what can run without resource conflict; can state change the route or stop; can partial failure be detected, explained, and replayed? I don’t know a universal branch limit. I think a new branch or cycle should fail review without independent work, a measurable target, an owner, and recovery evidence.

After topology is chosen, [“The 105 minutes after the graph”](/drafts/67821675/) covers evaluation, schema-constrained state, and trust controls. Frameworks make coordination cheap to draw but expensive to govern; the smallest topology that survives these tests is the advanced choice.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A linear spine keeps recovery visible; bounded graph bursts must earn their place through independence, measured benefit, and replay evidence.</p></div>
