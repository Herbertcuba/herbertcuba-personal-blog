Every extra edge promises that the runtime can explain why one job waits and recover when work fails. Fragility begins when an operator cannot replay that decision.

A pipeline is a directed path through stages, so it is already a graph. A directed acyclic graph (DAG) can split and merge but cannot return to an earlier node. Conditional graphs choose edges from runtime state; cyclic graphs can revisit work. I think the question is how little topology expresses the workflow without hiding obligations.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose among a pipeline, DAG, cycle, or hybrid by matching the workflow’s real dependencies and runtime decisions.</p></div>

## Prove the dependencies first

Start by recording what each job consumes and what it can change. A data dependency exists when one job needs another job’s output. A resource dependency exists when both touch the same mutable resource, meaning a file, database row, workspace, approval slot, or service capacity that a run can change or occupy. Two jobs may share a read-only snapshot safely because neither rewrites it.

Apply the fake-edge test: if job B does not use job A’s result and they share neither mutable state nor a constrained service, their edge may be artificial. The documentation for [PostgreSQL, an open-source database](https://www.postgresql.org/docs/current/transaction-iso.html), explains why a second updater can wait when two transactions touch the same row. [Stripe, a payments API provider](https://docs.stripe.com/rate-limits), documents separate request-rate and active-request limits. I think independence has to survive both the data test and the resource test.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Remove an edge only when jobs share neither required outputs nor mutable or limited resources.</p></div>

## Separate sequence from breadth

Keep a straight pipeline when sequence is real: ingest a request, validate its schema, apply policy, then persist. Each step requires the previous output or approval, keeping recovery and ownership visible. Put deterministic validation, counting, deduplication, and fixed routing in ordinary code. I think a visible sequence is a strong production design when every wait has a reason.

Use a fan-out/fan-in DAG when the work is genuinely wide. Fan-out starts independent branches; fan-in combines them. A research stage might examine five market angles in parallel, verify each result, and merge the survivors. [AWS Step Functions, Amazon’s managed workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), documents a parallel state that waits for every branch. An all-required merge therefore cannot finish before its slowest required branch.

I think the merge matters more than the fan-out. It must know which branches were expected, expose missing or failed results, enforce a deadline, and preserve provenance, the record of where each result came from and how it was produced. If a retry performs an external write, it also needs idempotency, meaning the same logical attempt can be repeated without duplicating the intended effect.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Parallel breadth earns its place only when branches are independent and the merge can govern incomplete or retried work.</p></div>

## Let runtime state earn the return edge

Use a conditional graph when recorded state changes what runs next, such as weak evidence going to verification. Use a cyclic graph when changed state sends work back. A fixed two-pass review stays acyclic; a runtime choice to refine, finish, or escalate earns a conditional or return edge.

[LangGraph, an open-source framework for stateful agent workflows](https://docs.langchain.com/oss/python/langgraph/graph-api), documents conditional edges, loops, and an execution limit. Those features make a route possible, not wise. I think every return edge needs a named state change, a clear stop rule, and a hard step, time, or cost cap. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper on loop terminology, ownership, and exit conditions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Add a condition or cycle only when runtime state can change the route, and bound every possible return.</p></div>

## Make the coordination tax pay

Wider topology creates more partial failures, isolation needs, quota pressure, duplicated context, and traces to interpret. A framework may help manage them, but drawing edges does not remove them. A merge still needs a policy: fail, retry, accept named survivors, or escalate. It must remain replayable without silently repeating external effects.

That is why I prefer a hybrid for many production systems: a linear control spine with short graph-shaped bursts for research, verification, or parallel analysis. Four questions are enough to inspect the fit:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can runtime state change the next route or stopping condition?
4. Can the system detect, explain, and replay a partial failure?

I don’t know whether a wider section pays until latency, completeness, cost, and recovery are measured. Start with the smallest truthful shape, unless independent work already makes a branch the honest starting point. Instrument it, then promote one proven need at a time. [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, typed state, and trust controls after this choice. My take is simple: every extra edge must earn the right to exist.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use a linear spine, localize graph-shaped work, and keep only the complexity whose measured gain exceeds its coordination cost.</p></div>
