# Every workflow edge is a claim about waiting

In a workflow, every dependency edge claims that one job must wait. I think treating more arrows as maturity is backwards. A linear pipeline is both a graph and a [directed acyclic graph (DAG)](https://networkx.org/documentation/stable/reference/algorithms/dag.html): one directed path with no cycle. A DAG may branch and merge but cannot contain a directed cycle. A conditional graph chooses its next edge from runtime state; a cyclic graph can revisit earlier work. A hybrid puts bounded graph sections inside a pipeline.

[Anatoli Kopadze, author of a July 2026 graph-engineering article](https://x.com/AnatoliKopadze/status/2080668775796314331), argues that graphs add width rather than judgment and asks whether each step needs its predecessor’s result. His fake-edge question is useful, but production adds hidden waits: a data-flow edge can protect shared state or capacity.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose the minimum topology that represents every real wait, including the hidden ones.</p></div>

## Map the waits before drawing the graph

A data dependency exists when one job consumes another’s result. A resource dependency exists when jobs change the same mutable resource, such as a file, database row, or approval record. Branches can read one immutable snapshot yet compete for an API quota.

Ingest request → validate schema → apply policy → persist result belongs in a pipeline because every stage needs the previous output. I think deterministic code should handle schema checks, counts, duplicate detection, and fixed routes; models should handle judgment.

Kopadze’s test is two-part: B neither consumes A’s output nor conflicts over a shared write or capacity limit. Only then is their edge suspect. [PostgreSQL, a relational database, documents an updater waiting on another transaction](https://www.postgresql.org/docs/current/transaction-iso.html); [Stripe, a payment platform, separates request-rate limits from simultaneous-request limits](https://docs.stripe.com/rate-limits). If lock, queue, or throttle time then dominates the critical path, meaning the longest required chain, the bottleneck moved rather than disappeared.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Remove an edge only when neither data nor a shared resource requires the wait.</p></div>

## Design the join before the fan-out

Fan-out starts independent branches; fan-in merges their results. Five market-angle searches can run together before one report combines them, but an all-required merge still waits for its slowest required branch. [AWS Step Functions, Amazon’s workflow state-machine service, runs parallel branches and waits for them to finish](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html). Parallel work removes artificial waiting; it does not promise an N-times speedup.

I think the merge exposes the coordination tax: tracking branches, failures, joins, and recovery. Persist this record:

```yaml
run: R42
branch: {id: angle-3, attempt: 2, status: succeeded}
refs: {input: request-v7, output: finding-91}
controls: {idempotency_key: R42/angle-3, deadline: 2026-08-15T14:30:00Z, provenance: sources/tool-v4}
join: {required: [angle-1, angle-3], optional: [angle-2], received: [angle-2, angle-3], revision: 1, status: blocked}
```

Required `angle-1` is missing; publishing stays blocked. An optional absence may yield a degraded result; a late result creates immutable revision 2. Within attempt 2, `succeeded → running` is illegal. A retry creates attempt 3; idempotency means repeating the same logical write does not repeat its intended effect. Obsolete branches are cancelled; caught failures remain visible as failed or degraded. Provenance records the source-and-tool trail.

The workflow owner handles partial joins; the release owner approves, stops, or rolls back; the budget owner funds human handling. Mature orchestrators provide branch execution, retries, and error handling. The team still decides required evidence, acceptable degraded completion, and whether the coordination tax is worth paying.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Define branch identity, merge rules, failure policy, ownership, and safe retries before parallel work.</p></div>

## Let state and measurement earn the rest

Use a conditional route when state changes what runs next, and a cycle when it sends work back. Every cycle needs a stop rule and a hard step or cost cap. I think a fixed two-pass review remains a DAG; a runtime choice among refinement, completion, or escalation earns a return edge. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper on loop terms and exit conditions.

A retry reattempts one job; a resume continues the same stored execution; a rerun starts a new execution; deterministic history replay reconstructs state from recorded events. [Temporal, a durable workflow engine, persists event history and uses replay to resume execution](https://docs.temporal.io/workflow-execution). Such runtimes support durability, but do not choose topology. Isolate branches through owned records, partitions, transactions, locks, immutable snapshots, or separate workspaces.

For one release, benchmark the linear stage, then test one proven-independent branch behind a disable switch. An example promotion bar: p95 elapsed time, the duration at or below which 95 percent of runs finish, falls 20 percent from that baseline; cost per success rises at most 10 percent; required-branch completeness reaches 99.5 percent; operator time does not rise. The release owner reverts on any miss. I don’t know whether the branch earns its place until local runs clear the bar.

Ask four questions: What consumes an earlier result? What can overlap without a mutable-resource conflict? Can state change the route or stop condition? Can the system detect, explain, and replay a partial failure? I think the answers often produce a hybrid: a linear intake, policy, approval, and persistence spine with a bounded research burst. Across teams, supplier quotas and approval queues remain governed dependencies. [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, structured state, and trust controls after selection. Choose the smallest graph that tells the truth about every wait.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Promote one measured bottleneck and keep only complexity whose gain covers its coordination tax.</p></div>
