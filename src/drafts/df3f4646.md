Graph tools make sophisticated workflows easy to draw. They do not make the work independent or recoverable. I think that gap explains much of the architecture theatre around AI agents: coordination looks cheap on the canvas and becomes expensive in production.

A pipeline is already a graph: one directed path. Topology means the layout of stages and connections. The useful question is what minimum topology expresses the work’s real dependencies without inventing failure paths and merge logic.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A pipeline and a graph are not competing categories. Choose the simplest layout that matches the work, then make evidence earn every added branch or return route.</p></div>

## Draw dependencies before agents

A data dependency exists when one job consumes another’s result. Jobs can also depend on a mutable resource, meaning a file, database record, workspace, approval, or service capacity that either can change or exhaust. [PostgreSQL, an open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), documents one update waiting on a conflicting update. [Stripe, a payments platform](https://docs.stripe.com/rate-limits), documents active-request limits separately from request-rate limits.

Use the fake-edge test in both directions. If B consumes no result from A and concurrent execution creates no conflict over writes, approvals, quotas, or side effects, the A → B edge may be artificial. A shared read-only snapshot is different because neither branch changes it. I think fan-out should fail review when two branches can update the same transactional record without isolation, enforced ordering, or another proven control.

## Let runtime behavior choose the shape

Keep a linear pipeline when every stage needs the previous result, as in ingest request → validate schema → apply policy → persist result. Replay means rerunning recorded work through that route while controlling duplicate external effects. I think visible sequence is a production advantage when sequence is real, especially when validation and routing remain deterministic code.

Use a directed acyclic graph, or DAG, when work is wide and no route returns to an earlier stage. Fan-out starts independent branches; fan-in merges their results. Parallel work can shorten the critical path, the longest required chain controlling completion time, but an all-required merge still waits for its slowest branch. [AWS Step Functions, a cloud workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), makes that wait explicit. I think the merge is the real decision because it needs expected branch IDs, a deadline, result provenance, and a rule for missing or failed work.

A conditional graph selects its next stage from recorded runtime state. A cyclic graph can return to an earlier stage, so it needs a state change, a stop condition, and a hard attempt or cost limit. If every run makes two passes, draw two stages instead. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper into feedback-loop terminology and exit conditions.

A hybrid keeps a linear backbone around one bounded graph-shaped section. The current Content Engine, Herbert’s article-production workflow, offers a simple example: most work follows an ordered route, while a failed quality gate can return an article for revision. That is a state-driven return, not a parallel research-and-verification merge.

I think simultaneous activity is not the same as independence. Preserve every prerequisite edge the final objective consumes.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Parallel activity can contain hard prerequisites. Draw independent units where they exist, but keep every gate that the outcome genuinely depends on.</p></div>

## Make extra topology earn approval

Additional branches, cycles, retries, or concurrent side effects create a coordination tax. A join policy states which results a merge requires and what happens when one is late or fails. Retried external actions need idempotency, a key or rule that prevents one logical action from taking effect twice. Concurrent writes need isolation or serialization. Execution traces must preserve what each branch received, produced, and retried. Any extra model or tool work is a measured cost, not an automatic property of a graph.

When recovery dominates, test documented execution guarantees rather than assuming an agent-graph library supplies them. [Temporal, a durable workflow platform](https://docs.temporal.io/workflow-definition), requires deterministic workflow code for replay and places external calls outside that replay path. That is one execution model, not a universal comparison or a topology decision.

I don’t know which shape wins before measurement. I think a branch or cycle should survive review only when it represents independent work or a necessary state transition, has an owner and bounded failure, and improves the linear baseline. Measure critical-path latency, completion coverage, the share of required outputs delivered, duplicate effects, and cost per successful run before and after the change.

Ask four questions: What must wait for an earlier result? What can run without a mutable-resource conflict? Can runtime state change the route or stop condition? Can the system detect, explain, and replay a partial failure? [“The 105 minutes after the graph”](/drafts/67821675/) takes up evaluation and typed state, a state schema with declared field types, after topology is chosen.

Operate the smallest graph that tells the truth about the work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Approve a branch or cycle only with a real dependency case, explicit resource and failure rules, an owner, recovery evidence, and measured value over the simpler path.</p></div>
