AI builders often treat an agent graph as advanced and a pipeline as primitive. Yet workflow topology just means how stages and routes are arranged, and a linear pipeline is already a graph: one ordered path. [Apache Beam, an open-source data-processing system](https://beam.apache.org/documentation/programming-guide/), models pipelines as directed acyclic graphs and calls a sequential example a linear pipeline.

Anatoli Kopadze, whose recent X post on graph engineering inspired this article, puts the consequence plainly: "A graph buys breadth. It does not buy better judgment." I think production architecture should use only the routes that tell the truth about the work. Parallel branches can remove serial waiting, but more arrows do not create judgment, retry safety, or ownership.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose a workflow shape from real dependencies and recovery needs, not from how sophisticated its diagram looks.</p></div>

## Draw dependencies before topology

Start with what must wait. A data dependency exists when one job consumes another's result. A resource dependency exists when jobs alter the same mutable resource, such as a shared file or record, or compete for one quota or approval. [PostgreSQL, an open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), documents a writer waiting on a changed or locked record, and [Stripe, a payments platform](https://docs.stripe.com/rate-limits), separates concurrency from request-rate limits. Jobs can exchange no data at all and still be coupled.

Apply the fake-edge test. If B consumes nothing from A and running them together creates no shared write, exclusive gate, capacity conflict, or duplicate external effect, their edge may be artificial. Jobs can still safely read the same read-only snapshot. I think teams will keep mistaking concurrent model calls for independent work and discovering the hidden dependency during an incident.

Keep the route linear when sequence is real: ingest a request, validate its schema, apply policy, then persist the result. Replay, rebuilding a run from recorded history under the same control rules, stays simple because every stage's expected predecessor is obvious. That same record doubles as audit evidence, because explaining a run to a reviewer stops being archaeology when the route is one path. Keep validation, counting, deduplication, and routing in ordinary code, and reserve models for judgment.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Remove an edge only after checking consumed outputs, shared writes, capacity, gates, and external effects.</p></div>

## The join is the hard part

A directed acyclic graph, or DAG, has directed dependencies but no route back to earlier work. Fan-out starts independent branches; fan-in joins their outputs. It fits wide work: research five market angles, verify sources, then merge accepted results.

The fan-out is the easy half; I think the join policy matters more. A join policy makes the merge operational by saying which results are required and when the merge may proceed. The critical path, the longest-duration chain of required dependent work, is a lower bound on completion rather than a promise, because real runs also pay for queueing, limited workers, and retries. [AWS Step Functions, a managed workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), waits until every Parallel branch finishes.

Make that policy reviewable:

```text
run_id: research-042
allowed_status: [pending, running, complete, failed, timed_out]
branches:
  market:     {required: true,  status: complete}
  regulation: {required: true,  status: running}
  competitor: {required: false, status: timed_out}
join_policy: all_required_terminal
retry_budget: 2
stop_condition: deadline_or_budget
owner: research-service
rollback: disable_parallel_stage
```

The system must reject this merge while the required `regulation` branch runs, and the operator should see the rejection together with branch identities, inputs, errors, retries, and the merge decision. A retriable branch with an uncertain external effect, such as a write or charge, needs idempotency: repeating the same logical request must preserve one intended external effect. [Stripe's API documentation](https://docs.stripe.com/api/idempotent_requests) shows one implementation using a request key.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A production join needs expected branches, allowed transitions, a missing-result policy, retry safety, source records, and a recovery owner.</p></div>

## When state earns a new route

A conditional graph selects its next route from current state, the data available to that run. A cyclic graph can return to earlier work. [LangGraph, an open-source framework for stateful agent workflows](https://docs.langchain.com/oss/python/langgraph/graph-api), documents both state-based routing and a configurable loop limit. I think a cycle earns its place only when changed state can change the next action, and it still needs a stop rule plus a hard attempt, time, or cost limit.

I think production often favors a hybrid, keeping the main route on a linear backbone and bounding the research fan-out before approval, whichever framework implements it. The runtime choice is separate from the topology choice. [Temporal, an open-source durable execution platform](https://temporal.io/), records workflow history so interrupted work can resume, and a managed orchestrator can expose retries and traces, but neither decides which edges the work actually needs. The topology decision also needs one named owner, because an unowned join policy decays the first time the research team and the platform team disagree.

Run four questions in the next design review:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can runtime state change the next route or stopping condition?
4. Can the system detect, explain, and replay a partial failure?

Then measure. A linear baseline is usually visible within a sprint or two of real traffic, and an unbounded fan-out multiplies model calls per request, so compare the bounded alternative against that baseline on latency, duplicate effects, incomplete joins, recovery time, and cost per successful run rather than per request started. Approve the change only with a retry policy, a deadline, and a rollback condition. I don't know which shape wins before measurement, and the framework cannot answer that.

["Everyone Discovered Loops. Nobody Agrees What the Word Means."](https://www.cubagarcia.com/posts/everyone-discovered-loops/) examines loop terminology and exit conditions, and ["The 105 minutes after the graph"](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, declared state, and evidence after the topology is chosen. Until the measurement exists, earn every extra edge from the work and choose the smallest graph that tells the truth.
