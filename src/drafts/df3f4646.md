Graph diagrams can make AI workflows look advanced too soon. Topology, the arrangement of stages and edges, should describe work, not agent count.

A pipeline is one ordered path. A DAG, or directed acyclic graph, can branch and merge but cannot return. Conditional graphs choose the next edge from current state; cyclic graphs revisit work. I think the right choice is the smallest topology that tells the truth.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A pipeline is already a graph; earn every branch, route, and return.</p></div>

## Map dependencies before topology

Start with data: a job waits when it consumes an earlier result. Then map mutable resources, shared things it can change. [PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html), an open-source relational database, documents one writer waiting on another's row; [Stripe](https://docs.stripe.com/rate-limits), a payments platform, separates rate and concurrency limits. Files, approvals, workspaces, and scarce capacity create similar hidden edges.

Apply the fake-edge test. If B consumes no A output and they share no write, lock, approval, or quota, the edge may be artificial. Put temporary API caps in queue settings, or today's limit may harden into permanent workflow, ownership, and cost.

Keep real sequence linear: ingest request, validate schema, apply policy, persist result. Each stage authorizes the next, so I think visible order is often strongest in production. If required calls are independent and serial execution misses its latency target, bounded fan-out is the more truthful start.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Remove fake order, preserve real dependencies, and keep temporary capacity limits out of permanent architecture.</p></div>

## Design the merge before the fan-out

A DAG earns its place when work is wide. Fan-out starts independent branches; fan-in joins them. [AWS Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), Amazon's managed workflow service, runs parallel branches and waits for all. An all-required join cannot complete before its slowest required branch. The critical path, the longest required chain, includes work before and after the join.

For a five-angle report, I think the merge is the architecture decision:

```text
JoinKey = workflow_id + input_version
BranchResult = branch_id + attempt + status + evidence_refs + output_hash + idempotency_key
MergeState = OPEN | SEALED | FAILED
```

Declare expected branch IDs and the current authorized attempt. An atomic update accepts one terminal result per branch only while the merge is open. `SEALED + stale, duplicate, or unknown branch → REJECTED_ARRIVAL`. Each branch reads immutable input and uses an isolated workspace. An idempotency key identifies one logical external action so retries have the equivalent intended effect or resulting state.

A 90-second branch-attempt limit excludes queueing, retry, merge, and review. At deadline, missing required IDs seal the merge as failed; request cancellation, reject late arrivals, and retain inputs, attempts, evidence, hashes, errors, and the decision for replay.

Test width against the serial baseline. For frozen briefs in a hypothetical market report that gates investment review, promotion requires lower end-to-end 95th-percentile latency, no drop in human acceptance against a written evidence rubric, replay of sampled failures, and full cost per accepted report including retries, rejections, runtime, and review. Inspect every failure and a fixed sample of successes. I don't know whether width has earned its place until that record exists.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Parallelize only when the join contract, accepted quality, full cost, late arrivals, cancellation, and replay are enforceable.</p></div>

## Route only when state changes

Use a conditional graph when state changes the route, and a cycle when state can send work back. Two known review passes belong in a DAG; a failed evidence check that selects a new path at runtime earns a return edge.

Every cycle needs changed state, a stop rule, a hard cap, and escalation. [LangGraph](https://docs.langchain.com/oss/python/langgraph/graph-api), an open-source framework for stateful agent workflows, documents state-based edges and execution limits. I think a cycle without reasons to return and stop is an unbounded bill. The article [Everyone Discovered Loops. Nobody Agrees What the Word Means.](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper into terminology, ownership, and exit conditions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Add a conditional route or cycle only when runtime state explains both the next move and the stopping condition.</p></div>

The mapping is practical: a launch sequence needs a pipeline because each stage enables the next; a fleet engagement needs branches, changing routes, and convergence. Turning launch into a fleet graph only adds mission-control software that can fail.

## Keep the graph local

My take is a linear spine for intake, policy, approval, and persistence, with bounded research or verification graphs. This confines joins, partial failures, quotas, and model work. A mature workflow runtime may expose retries and traces clearly; the obligations remain.

Before release, record data boundaries, isolation, quotas, and human approval. Name the sponsor funding the test, architecture lead signing promotion, risk reviewer accepting degraded mode, and operations lead owning rollback. I think the review then closes with four questions:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can runtime state change the route or stopping condition?
4. Can the system detect, explain, and replay a partial failure?

If the last answer is no, do not widen. The article [The 105 minutes after the graph](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, explicit state, and controls after selection. Complexity should follow measured need, never the ease of drawing another edge.
