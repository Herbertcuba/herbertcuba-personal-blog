# Choose the smallest workflow topology that tells the truth

I think “pipeline or graph?” asks the wrong architecture question. A pipeline is a graph with one directed path. A directed acyclic graph (DAG) may branch and merge but cannot return; a cyclic graph can.

Three decisions matter. Precedence topology says what must happen before what; route selection says whether runtime state chooses the next step; admission control caps ready work using a scarce resource. More arrows widen the work, but they do not improve judgment.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose precedence, runtime routing, and resource admission separately, then use the smallest topology that expresses the real work.</p></div>

## Draw precedence before adding width

Start with the outputs each job consumes. In ingest request → validate schema → apply policy → persist result, every stage needs the preceding result or authorization. That sequence is real, and I think its visible replay path, cost, and owner are a production strength.

Now apply the fake-edge test. If two market-angle jobs read the same immutable request and write isolated results, neither needs the other’s output. A provider quota may still allow only two calls at once. A semaphore is a counter that caps simultaneous work; it can enforce the quota without inventing `angle-1 → angle-2`, as [Python’s standard-library documentation describes](https://docs.python.org/3/library/asyncio-sync.html#asyncio.Semaphore). If both jobs update the same customer record, coordinate the write with isolation or a per-customer queue. Add a precedence edge only when business order matters.

I think this prevents serializing independent work or calling unsafe concurrency a DAG. Keep schema checks, duplicate removal, counts, and fixed routing in deterministic code, and reserve model calls for decisions that require judgment.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>An edge should represent required order; quotas and shared writes need explicit controls, but they do not automatically create an A-to-B dependency.</p></div>

## Design the join before the fan-out

Fan-out starts independent branches; fan-in merges them. Five research jobs can examine separate market angles from one immutable input before a report merge. [AWS Step Functions, Amazon’s workflow state-machine service, documents a Parallel state that waits for every branch to terminate](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), so an all-required merge waits for its last required branch.

I think the join is the real architecture decision. Declare branch identities, required and optional results, output schema, deadline, cancellation, retries, finalization, and late-result policy. Idempotency means a retried operation does not repeat its intended external effect; provenance records the inputs, sources, models, and tools behind an output.

```text
required=[angle-1, angle-2] optional=[angle-3]
31s angle-1#1 succeeds
32s duplicate completion for angle-1#1 -> ignore
60s angle-2#1 times out -> retry; request cancellation of angle-3
78s angle-2#2 succeeds
79s finalize revision 1 from [angle-1, angle-2], degraded=true
82s angle-3 arrives late -> audit only; revision 1 stays unchanged
```

That trace defines a tolerant merge; the topology does not. In Step Functions, an unhandled branch error fails the Parallel state, while retries and catches must be configured. [Google Cloud Workflows, Google’s managed workflow service, warns that parallel branches can increase elapsed time for non-blocking work](https://docs.cloud.google.com/workflows/docs/execute-parallel-steps).

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prove branch independence, then specify the exact merge result for timeout, retry, duplicate completion, cancellation, and late arrival.</p></div>

## Let state earn conditions and cycles

Conditional routing is separate from cyclic topology. A risk result can select automatic approval or human review without returning, so the graph stays acyclic. A cycle lets execution revisit earlier work, as in verify → revise → verify; two review passes known in advance can be two DAG stages.

I think a return edge earns its place only when recorded state can change the next attempt. Give it a state-based stop rule, such as every required claim having accepted evidence, plus a hard step or cost limit. [LangGraph, an open-source framework for stateful workflows, documents state-selected edges and a recursion limit for looping graphs](https://docs.langchain.com/oss/python/langgraph/graph-api). [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) explores loop terminology and exit conditions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A condition selects a route; a cycle adds a return path, and every return needs both a meaningful state change and a bounded stop.</p></div>

## Promote a hybrid with evidence

I think the strongest production default is often a hybrid: a linear control path for intake, policy, approval, and persistence, with a bounded graph-shaped section for research or verification. The graph section must pay for partial-failure handling, join state, safe retries, isolated outputs, quotas, traces, model tokens, and operator time. Record the promotion so another team can rerun or reverse it:

```yaml
baseline: linear / current release
candidate: hybrid / research fan-out / max_in_flight=2
measured_bottleneck: research_elapsed_time
expected_gain: lower_p95_without_lower_completeness
cohort: {size: "n locked before results", mix: "representative routes and input sizes", window: "one release"}
inject: [required_timeout, duplicate_completion, optional_late_result]
measure: [p95_elapsed, setup_hours, cost_per_success, required_completeness, operator_minutes, replay_success]
owner: release-owner
disable_switch: research_fanout
accept: all_predeclared_service_and_budget_bars_pass
rollback: any_guardrail_miss
```

P95 elapsed time is the point under which 95 percent of runs finish. I don’t know whether a branch earns its place until a locked, representative workload and injected failures beat the baseline without breaking the cost or recovery bars.

Ask four questions. What must wait for an earlier result or authorization? Which jobs can be siblings, and what admission controls protect shared resources? Can state select another edge or send work back? Can a partial failure be detected, explained, and replayed? After topology is chosen, [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, typed state, and later trust controls. The right architecture is the smallest graph whose measured benefit pays for every coordination obligation.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use a linear control path with bounded graph-shaped sections, and keep each promotion only when a replayable test proves that its gain exceeds its coordination cost.</p></div>
