Graphs often look advanced. The real question is: what is the smallest topology, the arrangement of stages and connections, that tells the truth about the work? A pipeline is the simplest graph: one ordered path. A directed acyclic graph (DAG) may branch but cannot loop back. Conditional and cyclic graphs route or revisit work from runtime state; a hybrid puts short graph sections inside a linear spine. I think edges need reasons.

Think of a launch sequence and a fleet engagement. The launch stays ordered because each stage enables the next; the fleet needs independent units, changing decisions, and convergence. Turning the launch into a fleet adds failure-prone coordination. Anatoli Kopadze, author of a [2026 X essay on graph engineering](https://x.com/AnatoliKopadze/status/2080668775796314331), wrote: “A graph buys breadth. It does not buy better judgment.” I don't know whether a branch belongs until its independence and benefit are visible.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A pipeline is the minimum graph. Add branches or returns only when the work requires them.</p></div>

## Start with the dependencies

Map each stage's inputs and changes. B has a data dependency if it needs A's result. A hidden resource dependency appears when both change the same mutable resource, shared state a task can alter, such as a file, database record, or workspace, or compete for one approval gate or API quota. [PostgreSQL, an open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), shows the mechanism. A transaction is one unit of database work; a row lock makes a second writer wait until the first commits or rolls back. No output is exchanged, but the shared write forces coordination.

Apply the fake-edge test. If B does not consume A's output and the jobs share no writable state, lock, quota, or external side effect, the edge may be artificial; both may read one immutable snapshot. By contrast, ingest request → validate schema → apply policy → persist result is a pipeline because every stage needs the prior result. Its critical path, the longest required chain, stays clear; replay reruns recorded inputs and state. I think that visibility helps recovery and ownership.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Map consumed outputs and mutable resources. Keep real sequence; test apparent sequence for fake edges.</p></div>

## Make the merge governable

A branched DAG fits independent jobs that fan out, meaning start concurrently, and fan in, meaning combine their results. Five market searches can do this with separate inputs and writable resources. [AWS Step Functions, Amazon's managed workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), documents the catch: an all-required parallel step waits for every branch. The slowest required branch holds the merge; a partial failure means some finish while another does not.

I think the merge is the real architecture decision. Suppose it expects five results, but customer is missing at the ten-minute deadline. It compares expected and received branch IDs, then applies its join policy, the rule that turns branch outcomes into one run outcome. With `all_required`, it names the gap and fails instead of publishing four-fifths of a report. The log preserves completed work, so only the missing branch is replayed. Each result carries its input version and evidence source, keeping the merge traceable.

A small contract:

```yaml
run_id: market-report-42
expected_branch_ids: [market, regulation, customer, competitor, technology]
mutable_resource_keys: []
join_policy: all_required
failure_deadline: 10m
retry_budget: 1
stop_condition: complete_or_fail_at_deadline
owner: research-platform
side_effect_boundary: merge_only
replay_evidence: event_log
branch_output_fields: [result, input_version, evidence_source]
```

The side-effect boundary confines publishing to the merge. A retried write needs idempotency, protection that makes repeated attempts produce one logical effect; [Stripe's payment API documentation](https://docs.stripe.com/api/idempotent_requests) shows this with idempotency keys. Fan-out is invalid when two branches can update one database record without separate writable state or deliberate serialization.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A DAG needs independent branches and a merge that exposes missing work, bounds failure, preserves replay, and prevents duplicates.</p></div>

## Let state and evidence add complexity

A conditional route fits when runtime state changes the next step. A cycle sends work back when a verifier finds missing evidence and requests targeted research. I think that return is justified when new state changes the action, with a meaningful stop rule and a hard step, time, or cost limit. If two passes are known in advance, use a fixed DAG. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](/posts/everyone-discovered-loops/) goes deeper on feedback terminology and exit conditions.

Graph control flow and durable execution are separate choices. [Temporal, an open-source durable workflow engine](https://docs.temporal.io/workflow-definition), records history so control logic can rebuild the same route after interruption. When replay and duplicate-effect control dominate, that substrate may matter more than an agent framework's graph API. This points to the hybrid: keep durable gates and writes ordered, while independent research uses a bounded branch-and-merge segment. My take is that this contains the coordination tax of partial failures, separate workspaces, rate limits, extra model calls, and tracing.

Four questions are enough for the design review:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can runtime state change the next route or stop rule?
4. Can the system detect, explain, and replay a partial failure?

Begin linear unless required work is independent and the latency target rules out serial execution. Measure critical-path latency, completion coverage (the share of required results received), duplicate effects, and cost per successful run. That change needs an owner, failure deadline, write boundary, replay evidence, and measured gain. [“The 105 minutes after the graph”](/drafts/67821675/) covers post-selection evaluation and controls for trustworthy state and output. Choose the minimum topology that represents real dependencies without inventing coordination work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose the smallest truthful shape, measure it, and require every branch, route, or return to prove benefit and recoverability.</p></div>
