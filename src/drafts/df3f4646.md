# Choose the smallest workflow topology that tells the truth

I think the pipeline-versus-graph debate uses the wrong categories. A linear pipeline is a graph with one path. A directed acyclic graph (DAG) can branch and merge but cannot return; a cyclic graph has a return edge. Conditional routing is separate: runtime state chooses the next edge in either topology.

[Anatoli Kopadze’s July 2026 essay on graph engineering](https://x.com/AnatoliKopadze/status/2080668775796314331) offers a useful line: “A graph buys breadth. It does not buy better judgment.” The production question is which waits belong in the topology, which routes depend on state, and which ready jobs merely need controlled access to a scarce resource.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose topology, route selection, and resource admission separately; complexity should express real work rather than framework fashion.</p></div>

## Separate the three decisions

Topology describes required order and return paths. Routing chooses the next edge, either fixed or from current state. Admission control decides which ready jobs may run under worker, quota, lock, and shared-write limits. Mixing these layers creates fake edges.

Suppose five market-angle jobs read the same immutable request. They remain siblings even if a provider allows only two calls: a semaphore, a counter limiting simultaneous work, admits two without inventing `angle-1 → angle-2`. If jobs mutate the same customer record, queue them by customer or isolate their outputs. [GitHub Actions, GitHub’s continuous-integration workflow service, uses named concurrency groups](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) to enforce the same separation.

By contrast, ingest request → validate schema → apply policy → persist result is a genuine pipeline because each stage needs the previous result or authorization. I think visible order is often strongest: replay and ownership stay obvious, ordinary code handles checks, counts, duplicate removal, and fixed routes, while models handle judgment.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A shared limit can restrict concurrency without creating an A-to-B dependency; draw an edge only when order changes the result or permission to proceed.</p></div>

## Design the join before the fan-out

Fan-out starts independent branches; fan-in merges their results. The five research jobs qualify with immutable inputs and isolated outputs, but an all-required merge waits for its slowest required branch. [AWS Step Functions, Amazon’s workflow state-machine service, documents this barrier for its Parallel state](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html). In their 2013 peer-reviewed paper [“The Tail at Scale,” Google researchers Jeffrey Dean and Luiz André Barroso](https://www.barroso.org/publications/TheTailAtScale.pdf) explain why component latency variation becomes more visible when a service waits across many components.

I think the merge is the real architecture decision. Declare expected branch identities, required and optional results, deadlines, cancellation, retry, finalization, and late-result policy. Idempotency means a retry does not repeat the intended external effect; provenance records which inputs, sources, models, and tools produced the result. Then make failure replayable:

```text
policy: required=[angle-1, angle-2], optional=[angle-3]
        dedupe=(run, branch, attempt), effect_key=(run, branch)
31s  angle-1#1 succeeded
32s  angle-1#1 duplicate completion -> ignored
60s  angle-2#1 timed out -> retry #2; cancel optional angle-3
78s  angle-2#2 succeeded
79s  finalize revision=1 inputs=[angle-1, angle-2] degraded=true
82s  angle-3#1 late completion -> audit only; revision unchanged
```

That is a designed tolerant merge, not a generic DAG property. In Step Functions specifically, an unhandled branch failure makes the Parallel state fail and stops its branches; a different policy needs different supported control logic. Width alone supplies neither reliability nor better judgment.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Specify the exact merge result for timeout, retry, duplicate, cancellation, finalization, and late completion before parallel work enters production.</p></div>

## Let state earn conditions and cycles

Conditional routing lets state select the next edge and can remain acyclic: a risk result may send a request to automatic approval or human review. A cycle exists only when execution can revisit earlier work, such as verify → revise → verify; a fixed two-pass review can be unrolled as a DAG.

I think a return edge earns its place only when a recorded state change can alter the next attempt. Give it a semantic stop rule and a hard step or cost ceiling. [LangGraph, an open-source framework for stateful agent workflows, documents state-based edges and an execution limit for looping graphs](https://docs.langchain.com/oss/python/langgraph/graph-api). [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper on loop terminology and exit conditions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A condition chooses among edges; a cycle adds a return edge, and every return needs both a reason and a bounded stop.</p></div>

## Promote with a replayable test

I think the production default is often a hybrid: a linear intake, policy, approval, and persistence spine with a bounded research or verification DAG. Its coordination tax includes partial failures, join state, safe retries, isolation, quotas, traces, model tokens, and operator time. Record the trade before enabling it:

```yaml
decision: parallelize-research
baseline: linear / previous release
candidate: hybrid / max_in_flight=2
sample: {size: "n locked before results", mix: "same routes and input sizes", window: "one release"}
budgets: {setup_hours: "preapproved", cost_per_success: "preapproved", operator_minutes: "preapproved"}
inject: [required_timeout, duplicate_completion, optional_late_completion]
accept: [p95_elapsed, required_completeness, replay_success, cost_per_success, operator_minutes]
owner: release-owner
disable_switch: research_fanout
rollback: any_predeclared_guardrail_miss
```

Set `n` and acceptance bars from service objectives and budgets before results. P95 elapsed time is the threshold within which 95 percent of runs finish. I don’t know whether a branch earns its place until evidence from representative pre-production runs or production traffic, including injected failures, beats the linear baseline.

Four questions choose the architecture: What must wait for an earlier result or authorization? Which jobs can be siblings, and what admission controls protect shared resources? Can state choose another edge or send work back? Can a partial failure be detected, explained, and replayed?

```text
shape = [linear_path]
if independent_ready_jobs >= 2: shape += [fan_out_fan_in]
if state_can_return: shape += [bounded_cycle]
routing = conditional if state_selects_edge else fixed
admission = limit_by(resource_key, quota, worker_pool)
if not partial_failure_replayable: reject_promotion
architecture = hybrid if graph_burst_inside_linear_spine else shape
```

Once topology is selected, [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, typed state, and the trust controls that follow.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The strongest production graph is the smallest one whose measured gain pays for every branch, return edge, and recovery obligation.</p></div>
