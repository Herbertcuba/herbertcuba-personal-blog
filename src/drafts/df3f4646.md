# Choose the smallest workflow topology that tells the truth

I think “pipeline or graph?” is the wrong architecture question. A pipeline is already a graph with one directed path. A directed acyclic graph (DAG) can branch and merge without returning to an earlier node, while a cyclic graph contains a return path.

The usual menu mixes three decisions: precedence says what waits, route selection decides whether state chooses the next step, and admission control limits ready work against constrained resources. In [an X article about graph engineering](https://x.com/AnatoliKopadze/status/2080668775796314331), Anatoli Kopadze puts the restraint well: “A graph buys breadth. It does not buy better judgment.”

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose required order, runtime routes, and capacity controls separately; extra arrows do not improve judgment.</p></div>

## Separate order from admission

Consider ingest request → validate schema → apply policy → persist result. Each stage consumes the previous output or authorization, so a straight pipeline keeps order, ownership, retries, and reruns easy to inspect.

Two jobs can research different market angles from the same read-only request. Neither needs the other’s result, so no A → B edge exists. A shared API quota still needs admission control, such as a queue or [semaphore, a counter that limits simultaneous work](https://docs.python.org/3/library/asyncio-sync.html#asyncio.Semaphore). If both update one customer record, that mutable resource is shared state either can change; partitioned ownership or a [database transaction and row lock](https://www.postgresql.org/docs/current/transaction-iso.html) can coordinate the writes.

I think the fake-edge test needs two passes: first remove order that no output requires, then add the resource control that safe concurrency requires. Encoding a quota as precedence merely hides a scheduling decision in the graph.

```text
if B consumes A: draw A -> B
otherwise: keep them topologically independent
if they share capacity: queue or limit concurrency
if they share mutable state: partition, lock, or serialize that write
```

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>An edge expresses required order; queues, limits, partitions, and locks govern independent work that shares capacity or mutable state.</p></div>

## Design the join before the fan-out

Fan-out starts independent branches; fan-in merges their results. Five jobs can research separate market angles, verify the findings, and send the surviving evidence into one report. [AWS Step Functions, Amazon’s managed workflow service, documents a Parallel state](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html) that waits for every branch to terminate before continuing. That is one all-required join policy, not a universal default.

I think the merge is the real production decision. Persist the expected branch identities, mark results required or optional, and define deadlines, cancellation, duplicates, and late arrivals. Record provenance, the inputs, sources, models, and tools behind an output. Any retried external effect also needs idempotency: repeating the logical request should not repeat its intended effect.

```text
required=[angle-1, angle-2] optional=[angle-3]
angle-1 complete; duplicate angle-1 completion -> reject
angle-2 timeout -> retry; request angle-3 cancellation
angle-2 retry complete -> finalize revision 1 from [angle-1, angle-2]
angle-3 late -> audit only; revision 1 remains final
```

The trace is an illustrative tolerant merge, not AWS Parallel behavior. In the 2013 peer-reviewed article [“The Tail at Scale”](https://www.barroso.org/publications/TheTailAtScale.pdf), Google researchers Jeffrey Dean and Luiz André Barroso show how fan-out amplifies slow responses at an all-required join. It is not an AI-workflow benchmark; the relevant mechanism is that the merge cannot beat its slowest required branch.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Fan out only after the expected results, timeout, retry, cancellation, finalization, and late-result rules are explicit.</p></div>

## Let state earn conditions and cycles

Conditional routing means current state selects the next edge, but the resulting graph can still be acyclic. A risk result might route a request to automatic approval or human review without ever returning. A fixed two-pass review can also be drawn as two DAG stages.

A cycle is different because execution can return to earlier work. I think that return edge earns its place only when changed state can alter the next attempt. Give it a meaningful stop rule and a hard step or cost cap. [LangGraph, a framework for stateful workflows, documents state-selected edges and a recursion limit](https://docs.langchain.com/oss/python/langgraph/graph-api); [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper on loop language and exits.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A condition chooses a route; a cycle adds a return path and therefore needs changed state, a stop rule, and a hard budget.</p></div>

## Promote a bounded hybrid with evidence

A hybrid keeps a linear control spine while allowing short graph-shaped bursts. I think it is often the strongest production shape: intake, policy, approval, and persistence stay ordered while research or verification fans out. The burst still adds join state, partial failures, retries, resource controls, traces, model cost, and operator work.

Predeclare one decision record before promotion:

```yaml
candidate: research-fan-out
cohort: {source: frozen-representative-set, sample-size: predeclared}
window: one-release
compare: [linear-baseline, hybrid-candidate]
inject: [required-timeout, duplicate-completion, optional-late-result]
measure: [elapsed-time-distribution, cost-per-success, completeness, operator-minutes]
recovery: [branch-retry, full-rerun-from-recorded-inputs]
budget: {setup-hours: capped, review-hours: capped, operating-cost: capped}
owner: named
acceptance-bars: predeclared
disable-switch: research-fan-out
rollback: any-bar-fails
```

Run every frozen case through both versions, inject the failures, and retain the branch only if every agreed bar passes. A branch retry repeats failed work; a full rerun starts the recorded case again. Name and test resume or durable-history replay separately. I don’t know whether width pays until the candidate beats the baseline without weakening completeness or recovery.

Four questions choose the architecture: What must wait? What can run independently under separate resource controls? Can runtime state choose another route or return? Can the system explain and rerun a partial failure? Once topology is chosen, [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, typed state, and trust controls. Choose the smallest graph that tells the truth, and make complexity earn its place in measured work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep a linear spine and retain each bounded graph burst only when a predeclared, failure-injected comparison shows that its gain beats its coordination tax.</p></div>
