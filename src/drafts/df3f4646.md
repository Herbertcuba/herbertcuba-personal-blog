# Choose the smallest graph that tells the truth

A pipeline is already a graph: one ordered path through a set of nodes. I think the useful question is smaller and harder: which topology expresses the work’s true dependencies with the least coordination overhead?

Think of a launch sequence beside a fleet engagement. The launch stays ordered because each stage enables the next. A fleet needs units that can move independently, react, and converge. Turning the launch into a fleet graph creates mission-control software while the work stays sequential. As [Anatoli Kopadze](https://x.com/AnatoliKopadze/status/2080668775796314331) puts it, “A graph buys breadth. It does not buy better judgment.”

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Topology should describe the work. Every extra branch, join, or return edge needs an operational reason.</p></div>

## Draw dependencies before agents

Start by mapping what each job consumes and changes. A data dependency is obvious when B needs A’s result. A resource dependency is easier to miss: two jobs can conflict through the same writable file, database row, approval gate, mutable workspace, or API quota. A mutable resource is simply a shared thing that a task can change. [PostgreSQL’s isolation documentation](https://www.postgresql.org/docs/current/transaction-iso.html) shows the underlying issue clearly: concurrent writers may have to wait or resolve conflicts.

Then apply the fake-edge test. If B consumes none of A’s output, and both can run together without a shared write, lock, or quota conflict, the A-to-B edge may be artificial. Shared read-only input is usually safe. I think this test finds more useful parallelism than counting agents ever will.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Map data flow and shared resources first. A real dependency earns each edge; the diagram records it.</p></div>

## Keep real sequence linear

A pipeline is one ordered path, and it remains the strongest shape when each stage consumes or authorizes the next. Consider ingest request → validate schema → apply policy → persist result. The route is known, replay is easy to reason about, and ownership of a failed stage stays visible.

Keep schema checks, counters, deduplication, and fixed routing in ordinary code. Models earn their cost where judgment is required. I think a visibly ordered path is a strong production artifact when sequence is real, especially when auditability and predictable recovery carry more value than parallel speed.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use a pipeline when the work must wait in order. Clear sequence makes recovery, replay, and ownership easier to govern.</p></div>

## Use a DAG for genuine width

A DAG, or directed acyclic graph, allows branches while preventing any route from returning to an earlier node. Fan-out starts independent jobs; fan-in merges their results. Researching five market angles can fan out, each result can face separate verification, and the surviving evidence can converge into one report.

The merge carries the difficult contract. [AWS Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html) waits for every required parallel branch to finish, so completion time inherits the slowest required branch. The merge should know which branches were expected, expose missing results, preserve provenance, and apply a declared failure policy. Retries that create side effects also need idempotency, meaning the same logical attempt can run again without repeating the effect. [Stripe documents that contract](https://docs.stripe.com/api/idempotent_requests) for its API. I think the merge is the product decision; fan-out is merely the opening move.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Parallel breadth pays only when branches are independent and the merge can explain missing, late, retried, and rejected results.</p></div>

## Add cycles when state changes the route

A conditional graph chooses the next edge from current state. A cyclic graph can revisit earlier work. Both earn their place when an evidence score selects a verification route, a retryable error returns to a bounded attempt, or a weak result triggers escalation.

Each return needs a state change, a stop rule, and a hard budget. A fixed number of known passes can stay acyclic. I think a cycle becomes honest only when runtime evidence determines whether the system returns or exits. The deeper distinctions around feedback and ownership belong in [Everyone Discovered Loops. Nobody Agrees What the Word Means.](/posts/everyone-discovered-loops/).

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use conditional routes and cycles for state-dependent decisions, with an explicit reason to return and a bounded way to stop.</p></div>

## Make the graph pay its tax

Branches bring partial failures, shared-workspace hazards, rate limits, extra traces, and more model calls. Safe replay requires branch identity and idempotent writes. A join needs a policy for timeouts and missing work. Shared quotas can also turn apparent independence into queueing, as [Stripe’s separate rate and concurrency limits](https://docs.stripe.com/rate-limits) illustrate.

I think the practical production default is a hybrid: a linear control spine with bounded graph-shaped bursts for research, verification, or parallel analysis. Start with the smallest truthful shape, instrument the critical path (the longest required chain of work), and promote measured independent work into branches. I don’t know where your bottleneck sits, but four questions will expose it:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can runtime state change the next route or stopping condition?
4. Can the system detect, explain, and replay a partial failure?

Once topology is chosen, [The 105 minutes after the graph](/drafts/67821675/) takes up evaluation, typed state, and the trust layer around it. The architecture decision comes first: choose the smallest graph that tells the truth.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A hybrid contains coordination where it earns a measurable gain. The smallest truthful graph is usually the strongest system.</p></div>
