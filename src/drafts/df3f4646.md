# Every edge is a claim about waiting

Each edge says a job must wait. A pipeline is a graph with one directed path. A directed acyclic graph, or DAG, can branch and merge but cannot loop. A conditional graph chooses its next edge from runtime state; a cyclic graph can revisit work. A hybrid keeps a linear backbone around bounded branches or cycles.

In [a July 2026 article on graph engineering](https://x.com/AnatoliKopadze/status/2080668775796314331), author Anatoli Kopadze wrote, “A graph buys breadth. It does not buy better judgment.” His no-edge question helps, but I think production hides waits outside data flow: a seemingly artificial edge may still represent shared-resource contention.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose topology by finding every real wait, including those the diagram hides.</p></div>

## Find the reason for every wait

A data dependency exists when one job consumes another’s result. A resource dependency appears when jobs can change the same file, database row, approval record, or account: a mutable resource. Shared read-only input avoids write conflict, although capacity may still limit concurrency.

Ingest request → validate schema → apply policy → persist result fits a pipeline because each stage needs prior output or authorization. I think schema checks, counts, duplicate detection, and fixed routes should remain deterministic code; model calls are for judgment.

Kopadze’s no-edge heuristic needs a resource clause. [PostgreSQL, an open-source relational database, documents an updater waiting on an earlier transaction](https://www.postgresql.org/docs/current/transaction-iso.html), while [Stripe, a payment platform, separates request-rate from simultaneous-request limits](https://docs.stripe.com/rate-limits). Across teams, independent research may still share a search quota and legal approval queue. If removing an edge moves trace time into locks, queues, or throttling, shared capacity is the next bottleneck.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Remove an edge only when neither data nor a shared resource requires the wait.</p></div>

## Design the join before the fan-out

Fan-out sends independent jobs into separate branches; fan-in merges them. Five market-angle searches can branch and then merge verified findings. Parallel execution can reduce elapsed time by removing artificial serial waits, but in a fixed workflow the critical path remains its longest required chain. An all-required merge still waits for its slowest branch. I think the merge exposes the coordination tax better than the fan-out.

An illustrative persisted branch record makes the contract visible:

```yaml
run: R42
branch: angle-3
attempt: 2
required: true
status: succeeded
input_ref: request-v7
output_ref: finding-91
idempotency_key: R42/angle-3
deadline: 2026-08-15T14:30:00Z
provenance: sources-and-tool-v4
```

Valid states might include pending, running, succeeded, failed, and cancelled. Reject `succeeded → running` within one attempt; a retry creates another attempt. [Idempotency](https://docs.stripe.com/api/idempotent_requests) means retrying the same logical write does not repeat its intended effect.

The merge lists expected and required branches. A strict policy blocks publishing if a required result is late, allows missing optional results, records cancellations and handled errors, and writes late output to a new immutable revision so completed output never changes silently. The workflow owner chooses retry or stop; the release owner can roll back; the budget owner accepts human-handling costs. [AWS Step Functions, Amazon’s state-machine service, documents parallel branches](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html) plus [retry and error-handling mechanics](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html), but policy remains local.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Define branch identity, merge completeness, failure policy, ownership, and safe retries before fan-out.</p></div>

## Promote topology through a bounded test

Current state earns a conditional edge when it changes the route. A cycle needs a runtime-driven return, a stop rule, and a hard step or cost cap. I think a predetermined two-pass review should stay acyclic; use a cycle when runtime evidence decides whether to repeat. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper into loop language and exit conditions.

Keep recovery terms separate. A retry reattempts one logical job; resume continues the interrupted execution from durable state; rerun starts a new execution from selected inputs. History replay rebuilds state from recorded events. [Temporal, a durable workflow engine, documents that mechanism](https://docs.temporal.io/workflow-execution). Isolation controls who may write what through ownership, partitioning, transactions, locks, immutable inputs, or separate workspaces. A runtime can provide these mechanics without choosing the topology.

My take is to keep production gates linear and test one independent branch for one release window behind a feature flag. Compare the linear baseline on 95th-percentile elapsed time, the point below which 95 percent of runs finish, plus cost per successful task, join completeness, lock or throttle time, replay success, and operator minutes. An illustrative rule could require 20 percent lower elapsed time, at most 10 percent higher cost, 99.5 percent complete required joins, and no extra manual handling. The architecture owner sets the bar; the release owner reverts on a miss. I don’t know whether a branch earns its place until runs clear that bar.

Ask four questions: What consumes an earlier result? What can overlap without touching the same mutable resource? Can runtime state change the route or stop condition? Can a partial failure be detected, explained, and replayed? I think those answers should choose the topology. Often that means a hybrid: a linear spine with short research or verification branches. [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, structured state, and trust controls after that choice. Complexity earns its place when measured work demands it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Promote one measured bottleneck at a time, with thresholds, named owners, and a path back.</p></div>
