Graph-shaped agent systems look capable because their diagrams branch and return. I think that confuses expressive power with production quality. A pipeline is already a graph: one directed path. A directed acyclic graph (DAG) may branch and merge but cannot return; conditional and cyclic graphs use runtime state to choose or revisit work.

Choose the least topology that represents real waiting and changing routes. Extra edges create scheduling, recovery, and replay duties; they do not improve model judgment.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose topology from real waiting, safe concurrency, and state-dependent routes.</p></div>

## Separate precedence from resource admission

A precedence edge means B waits for A’s result. Resource admission controls concurrent access to a shared write target, workspace, approval slot, or limited service. Use isolation, a lock, a queue, or a concurrency limit unless true sequence is required.

[PostgreSQL, an open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), shows how a second updater can wait on the same row. [Stripe, a payments API provider](https://docs.stripe.com/rate-limits), distinguishes request-rate from active-request limits. I think that contrast sharpens the fake-edge test: if B uses none of A’s output and concurrent jobs neither mutate the same state nor exceed a shared limit, their serial edge is probably artificial. An immutable snapshot creates no write conflict.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use edges for real precedence; govern shared writes and limited capacity with isolation or admission controls.</p></div>

## Match the shape to the route

Keep a pipeline when the route is known: ingest a request, validate its schema, apply policy, then persist the result. Keep validation, counting, deduplication, and fixed routing deterministic. I think visible order helps when each failed run needs an obvious replay path.

Use fan-out, which starts independent branches, and fan-in, which merges them, for wide work. Five market-angle research jobs may run separately before becoming one report. [AWS Step Functions, Amazon’s managed workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), runs branches as concurrently as possible and waits for all required branches to terminate. The critical path, the longest required chain setting completion time, still includes the slowest result. Measure against the linear baseline before assuming a gain.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep real sequence linear; widen only independent work whose completion rule and measured benefit are clear.</p></div>

The mapping is architectural. A launch needs ordered gates because each stage enables the next; a fleet engagement needs independent units, branching decisions, and convergence. Modeling the launch as a fleet adds mission-control failure points.

## Add a return edge only for changed state

A conditional graph uses current state to choose the next route. A cyclic graph can return execution, as when a retryable failure triggers one bounded retry or weak evidence triggers human review. Two passes known in advance still fit a fixed DAG.

[LangGraph, an open-source framework for stateful agent workflows](https://docs.langchain.com/oss/python/langgraph/graph-api), documents conditional edges, loops, and an execution limit. I think a production cycle needs a named state change, a stop rule, and a hard step, time, or cost cap. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper on ownership and exit conditions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Let state select a branch or return path, and make every cycle explain both why it repeats and why it stops.</p></div>

## Define the merge before the branch

Define the merge before fan-out. It needs expected and required branch identities, late and duplicate rules, and recovery authority. A compact state contract can look like this:

```text
run_id: RunId
expected: Set<BranchId>
required: Set<BranchId>
results: Map<BranchId, {status: pending | running | succeeded | failed, output_ref, provenance}>
merge_policy: all_required | threshold | survivors
deadline: Timestamp
idempotency_key: RunId + BranchId + Effect
run_status: open | merged | failed
owner: ServiceTeam
```

Provenance records a result’s origin and production. Idempotency means retrying the same logical attempt cannot duplicate its intended external effect; [Stripe’s API documentation](https://docs.stripe.com/api/idempotent_requests) demonstrates this control with stable keys.

Inject a failure: `pricing` times out, so the merge records failure and blocks an all-required merge. Its retry keeps the same effect key. Any duplicate or late result after `merged` is rejected and logged as an illegal terminal transition. I think that trace reveals more than another arrow.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A production merge identifies missing work, retries safely, rejects invalid transitions, and names its owner.</p></div>

## Earn the hybrid in production

A hybrid keeps a linear spine with a bounded research or verification burst. Its decision record names the dependency, resource control, merge and replay policy, service owner, recovery and rollback authority, and acceptance measure. Compare 95th-percentile latency, the time under which 95% of runs finish, with cost per accepted result, merge completeness, and operator minutes.

I don’t know whether wider topology pays until that comparison exists. Ask: What consumes an earlier result? What can run together after resource controls? Can state change the route or stop rule? Can an operator explain and replay a partial failure? Keep the linear path reversible until the candidate clears its bar. [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, typed state, and trust controls after this choice.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>My take: promote the smallest measured change that improves the workflow while keeping failure ownership and reversal explicit. Complexity is justified only by work that requires it.</p></div>
