AI builders often treat graphs as advanced and pipelines as primitive. That hides the real choice. Workflow topology is the arrangement of stages and routes, and a linear pipeline is its simplest graph shape: one ordered path.

I think the production question is how little topology can represent the work truthfully. More routes widen the work without improving judgment, yet create scheduling and recovery decisions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose the arrangement of work from real dependencies, not from how sophisticated its diagram looks.</p></div>

## Draw the edges before choosing the shape

Start with two dependencies. A data dependency exists when one job consumes another's result. A resource dependency exists when jobs conflict over a mutable resource: a shared file, record, workspace, approval, quota, or external system that can change or exhaust. [PostgreSQL, an open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), documents writers waiting on the same record; [Stripe, a payments platform](https://docs.stripe.com/rate-limits), documents separate rate and concurrency limits.

Apply the fake-edge test. If B consumes nothing from A and the jobs share no conflicting write, lock, approval, quota, or external effect, the A → B edge may be artificial. Both may read the same immutable snapshot. I think concurrent model calls prove neither independence nor safe concurrency.

Keep a linear pipeline when sequence is real: ingest → validate schema → apply policy → persist. Use deterministic code for checks, counts, deduplication, routing, and merge completeness. Replay depends on the runtime. In [Temporal, a workflow platform that stores event history](https://docs.temporal.io/workflow-definition), replay rebuilds workflow state from that history; retried external Activities may execute again, so their side effects need separate controls.

Use a directed acyclic graph, or DAG, when independent work can fan out concurrently and fan in at a merge, with no route back to an earlier stage. Its critical path is the longest required chain. When every result is required, it includes the slowest branch, so parallel work offers no fixed speedup. [AWS Step Functions, a managed workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), documents this wait.

A conditional graph selects the next route from current state. A cyclic graph can return to earlier work, so it needs a meaningful stop rule and a hard attempt, time, or cost limit. A hybrid keeps a linear spine around a bounded branch or cycle. I think that is the strongest production shape. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) covers loop terminology and exit conditions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use one path for real sequence, a DAG for independent breadth, and state-driven routes only when runtime evidence changes what happens next.</p></div>

## Make the merge operational

The coordination tax appears where branches converge: partial failures, workspace conflicts, service limits, extra calls, and harder recovery. A join policy says which results are required and what happens when one is missing. I think this contract matters more than the fan-out.

Consider a framework-neutral research stage:

```text
run_id: r42
status: pending | running | complete | failed | timed_out
branches:
  market:      {required: true,  status: complete, retries: 0}
  regulation:  {required: true,  status: running,  retries: 1}
  competitors: {required: false, status: timed_out, retries: 2}
join_policy: all_required
retry_budget: 2
stop_condition: deadline_or_budget
owner: research-service
guard: required_branches_must_be_terminal
```

The guard rejects this merge because `regulation` is required but still running. For this workflow, an operator trace records one run: each branch ID, an immutable input reference, its output or error, retry count, and the merge decision. Before release, the service owner should approve the deadline, evidence acceptance rule, recovery rule, and rollback condition.

Retries that can repeat a charge, message, or write need idempotency: repeated attempts of the same logical request retain one intended external effect. [Stripe's idempotency guidance](https://docs.stripe.com/api/idempotent_requests) shows one implementation. After an uncertain outcome, compare the workflow record with the external system before acting again.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Before parallel work enters production, define branch identities, required results, retry safety, stop rules, rejected state changes, recovery, and ownership.</p></div>

## Promote topology with evidence

Topology is framework-independent. The same shape can run on a durable workflow engine, which persists state so work can resume after failure, or through queue workers and state-machine code. An agent-graph library is one implementation choice.

Ask four questions in the design review:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can current state change the next route or stopping condition?
4. Can the runtime detect and explain a partial failure, then repeat work according to its documented replay and retry rules?

Baseline the linear route, test one bounded alternative, then compare critical-path latency, fulfilled evidence requirements, duplicate effects, incomplete merges, recovery, and cost per successful run. I don't know which shape wins before measurement. I think a change is earned when its owner can show that the gain beats the coordination tax and reverse it when the agreed limit is breached.

Once the shape is chosen, [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) examines evaluation, declared state, and evidence for trusting a production run. My take is simple: if nobody owns an added failure path, the topology was never earned.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Measure the straight path first, add only routes that improve a declared outcome, and require an owner who can explain, recover, and reverse every added failure path.</p></div>
