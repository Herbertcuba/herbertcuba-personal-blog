I think the useful production question is not whether to use a pipeline or a graph. A pipeline is already a graph: one directed path in which each required stage follows the previous one. Topology simply means the arrangement of stages and connections, so the real decision is how little topology can express the work honestly.

Every extra edge creates another route to schedule, observe, retry, and recover. It does not improve model judgment by itself.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A pipeline is the smallest graph. Add routes only when the work requires them.</p></div>

## Start with real dependencies

A data dependency exists when one job consumes another job’s result. A resource dependency exists when jobs interfere through a mutable resource, meaning a shared file, database record, workspace, approval, or service quota they can change or exhaust. [PostgreSQL, an open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), documents concurrent writers waiting on one record; [Stripe, a payments platform](https://docs.stripe.com/rate-limits), documents separate rate and concurrency limits.

Apply the fake-edge test. If B consumes nothing from A, and running both creates no conflicting write, lock, approval, quota, or external effect, the A → B edge may be artificial. Both jobs can read the same immutable input because neither changes it, although they may still share a quota. I think separate prompts prove neither independence nor safe concurrency.

Keep schema checks, counters, deduplication, routing rules, and merge-completeness checks in deterministic code when possible. Use models where judgment is actually required.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Map consumed outputs and possible interference before counting agents or drawing edges.</p></div>

## Choose the shape the work requires

Keep a linear pipeline when sequence is real: ingest a request → validate its schema → apply policy → persist the result. Replay means rerunning known work after failure while controlling repeated external effects. I think this ordered path is often the strongest production artifact when predictable recovery matters more than parallel speed.

Use a directed acyclic graph, or DAG, when independent work can branch and no route returns to an earlier stage. Fan-out starts branches; fan-in merges them. If the merge requires every result, its critical path, the longest required chain of work, still includes the slowest required branch. [AWS Step Functions, a managed workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), documents this all-branch wait in its Parallel state. Parallel work can remove serial waiting, but it promises no universal speedup.

A conditional graph selects its next route from current workflow state. A cyclic graph can return to earlier work, so it needs a meaningful stop rule plus a hard attempt, time, or cost limit. A hybrid keeps a linear backbone around a bounded branch or return. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper into loop terminology and exit conditions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use a pipeline for sequence, a DAG for independent breadth, a conditional or cyclic graph for state-driven routing, and a hybrid for a bounded mix.</p></div>

## Write the merge contract first

The fan-out is easy to draw. The merge is the production decision. A join policy states which branch results are required before work may continue. Result provenance records which branch and input produced each output; isolated writes stop branches from overwriting one another; traces record how a run moved through the workflow.

Retries also need idempotency: repeating one logical action must retain the same intended effect rather than create a duplicate charge, message, or write. [AWS documents explicit retry and error-handling behavior](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html), while [Stripe documents idempotency keys for safe API retries](https://docs.stripe.com/api/idempotent_requests). These protections do not appear merely because the workflow has more edges.

A hybrid research stage might use this merge record:

```text
run_id: R42
market:      required, complete, attempts 1
regulation:  required, running,  attempts 1
competitors: optional, timed_out, attempts 2
join_policy: ALL_REQUIRED
retry_budget: 2
stop_when: deadline_reached OR retry_budget_exhausted
owner: research-service
merge -> REJECT REQUIRED_BRANCH_PENDING(regulation)
```

Accepting the merge while the regulation branch remains active is an illegal transition. The error tells an operator what blocks progress, and replay retains the run and branch identities. Before production, the product owner defines acceptable evidence, the platform owner verifies the controls, and the named service owner approves deadlines, recovery, and rollback. I think that contract matters more than another agent node.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Declare branch identities, requirements, retries, stop rules, illegal transitions, replay behavior, and one accountable owner.</p></div>

## Measure before promotion

Topology is independent of framework. The same shape can run on a durable workflow service, queue workers, or state-machine code. An agent-graph library is an implementation option, not the architecture decision.

Ask four questions in the design review:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can current state change the next route or stopping condition?
4. Can the system detect, explain, and replay a partial failure?

Baseline the linear route, test one bounded alternative, then compare critical-path latency, evidence that met the declared acceptance policy, duplicate external effects, incomplete merges, recovery success, and cost per successful run. I don’t know which shape wins before measurement. Approve a change only when a named owner can show that its gain beats the coordination tax and can state the rollback condition.

After topology selection, [“The 105 minutes after the graph”](/drafts/67821675/) covers evaluation, declared state, and the evidence needed to trust a production run. I think the rule here is simpler: every branch, join, condition, and cycle must earn its place from the work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Measure before promotion, govern partial failure, and choose the smallest graph that tells the truth about the work.</p></div>
