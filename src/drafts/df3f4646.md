Graph tools make coordination look free. On a canvas, another agent is one box and arrow. In production, that arrow carries state, retries, cost, and ownership. I think a sophisticated drawing can therefore be mistaken for a stronger system.

A pipeline is already a graph: one directed path. Topology is simply the layout of stages and connections. The real choice is the minimum topology that tells the truth about the work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Pipeline versus graph is a false choice. Make every extra route earn its place through a real dependency.</p></div>

## Draw the edges before the agents

A data dependency exists when one job consumes another’s result. Separate jobs still have a resource dependency when they change or exhaust the same file, database record, approval gate, workspace, or API quota. [PostgreSQL, an open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), documents concurrent-update waiting; [Stripe, a payments platform](https://docs.stripe.com/rate-limits), documents distinct request-rate and active-request limits.

Apply the fake-edge test: if B consumes nothing from A, and both run without conflicting writes, approvals, quotas, or external effects, A → B may be artificial. One immutable input does not require ordering. I think separate prompts prove nothing about operational independence.

## Let behavior choose the shape

Keep a linear pipeline when every stage needs the previous result: ingest request → validate schema → apply policy → persist result. Replay means rerunning known work while controlling repeated external effects. I think this is often the safest production architecture.

Use a directed acyclic graph, or DAG, when independent work can branch and no route returns to an earlier stage. Fan-out starts branches; fan-in merges them. Parallel work can remove serial waiting, but the critical path, the longest required chain controlling completion, still includes the slowest required branch. [AWS Step Functions, a cloud workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), documents one all-required design. I think the merge is decisive: what was expected, what arrived, and what happens when work is late?

Use a conditional graph when current workflow state selects the next route, and a cyclic graph when it can return to earlier work. A cycle needs a stop rule and hard attempt or cost limit. A hybrid keeps a linear backbone around one bounded branch or return. I think that is usually honest when only part of the workflow needs breadth or feedback. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) examines loop terminology and exit conditions.

## Make extra topology earn production

Branches and cycles impose a coordination tax. A join policy says which results are required and handles failure or delay. Retried side effects need idempotency: one logical action keeps the same intended effect when repeated. Branches also need write controls, quota-aware concurrency, result provenance, and visible failure records. More arrows provide none of these automatically. [AWS documents retry and catch behavior](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html), while [Stripe documents idempotency keys](https://docs.stripe.com/api/idempotent_requests).

The Content Engine is Herbert’s article-production workflow. Its current route is ordered, with gates that can return failed work for revision. Consider a candidate change, not today’s system: one research step fans out before the next gate.

This contract could run in a workflow engine, queue workers, or explicit state-machine code. The drawing does not select the runtime. I don’t know which shape wins before measurement. Baseline the linear route, test the bounded alternative, then compare critical-path latency, successful-completion rate, duplicate effects, and cost per successful run.

I think the likely next mistake is treating concurrent model calls as independent work, then finding the hidden edge during recovery. [“The 105 minutes after the graph”](/drafts/67821675/) covers evaluation and declared state after topology selection. Complexity is earned when the wider system works better and one owner can explain why.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Approve added topology only with a real dependency case, a complete join and recovery policy, one accountable owner, and measured value over the simpler route.</p></div>
