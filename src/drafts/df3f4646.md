# Make every workflow edge earn its place

Graph tools make workflows cheap to draw and expensive to govern. A pipeline is already a graph: one ordered path. Choose the minimum topology that tells the truth about the work.

Think of a science-fiction launch sequence and a fleet engagement. Each launch stage enables the next; a fleet needs independent units, changing routes, and convergence. I think making the launch fleet-shaped adds mission-control software that can fail.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Start with the smallest truthful topology. Every extra edge needs evidence and operating controls.</p></div>

## Draw the dependencies before the diagram

A data dependency exists when one job consumes another’s output. A resource dependency exists when jobs share a mutable resource: a file, database row, workspace, approval gate, or API capacity they can change or exhaust.

Apply the fake-edge test: if B does not consume A’s result and both can run without conflicting over a write, lock, or quota, the edge may be artificial. Branches may share an immutable read-only snapshot. [PostgreSQL, the open-source database, documents](https://www.postgresql.org/docs/current/transaction-iso.html) one writer waiting on another’s locked row. Jobs can look independent while their resources are not.

Keep a pipeline when sequence is real: ingest a request, validate its schema, apply policy, then persist the result. Each stage has a known predecessor, so replay from recorded state is easier to inspect. I think visible order is often the strongest production artifact. Use deterministic code, where the same input yields the same output, for validation, counting, deduplication, and fixed routing.

Use a DAG, or directed acyclic graph, when work is wide. No directed route returns to an earlier stage. Fan-out starts independent jobs; fan-in merges their results. Five market-research branches fit this shape, although an all-required merge still waits for its slowest branch. That branch bounds the join; the critical path is the longest required chain. [AWS Step Functions, Amazon’s workflow service, specifies](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html) this all-branch wait. I think the merge is the product decision because it defines which results count and what absence means.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep real sequence in a pipeline. Add DAG branches only when jobs are independent in data and shared resources, then design the merge first.</p></div>

## Let recorded state change the route

Runtime state records the condition of a run. A conditional graph chooses its next stage from state; a cyclic graph can revisit an earlier stage. Use either when the route or stop cannot be fixed beforehand.

Low evidence might trigger another source check. A retryable error might return work until its retry budget expires, then escalate to a human. I think a cycle earns its place only when a recorded change affects the next action, with a stop condition and a hard cap on attempts, time, or cost. Two planned review passes should remain ordered stages.

[“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](/posts/everyone-discovered-loops/) covers feedback-loop terminology, ownership, and exits. Here, state must provide a reason to return and evidence for when to stop.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use routes and cycles for state-driven decisions. A return edge needs a recorded reason, a stop condition, and a hard budget.</p></div>

## Turn topology into an operating contract

Every branch creates a coordination obligation. A partial failure leaves some branches complete and others missing. A side effect is an external change, such as a write or charge; idempotency lets the same request be retried without repeating that effect. [Stripe, a payments platform, documents](https://docs.stripe.com/api/idempotent_requests) this protection for API requests.

Use a compact decision record:

```yaml
run_id: <unique execution>
topology: pipeline | dag | conditional | cyclic | hybrid
expected_branch_ids: [...]
mutable_resource_keys: [...]
join_policy: <required results; missing-result action>
retry_budget: <attempts; time; cost>
stop_condition: <recorded exit state>
owner: <accountable owner>
failure_deadline: <escalation time>
idempotency_key: <side-effect identity>
replay_or_rollback_evidence: <trace or reversal proof>
```

Reject this transition: two branches cannot fan out if they can write the same transactional record without isolation or a serialization rule. The merge must preserve branch identity and source provenance, show missing results, and apply its declared deadline.

I don’t know whether a branch pays for itself without a baseline. Measure critical-path latency, completion coverage, duplicate effects, and cost per successful run before and after. Coverage is the share of expected branches returning usable results. I think a branch without resource independence and a measured latency, coverage, or resilience benefit should fail review.

When replay and side effects dominate, use a durable workflow engine: a state-machine runtime that persists execution state so retries follow explicit rules. An agent graph can remain a bounded decision layer inside it. My take is that production usually fits a hybrid, with intake, policy, approval, and persistence on a linear spine while research or verification fans out briefly and converges before the next gate.

Ask four questions. What must wait for an earlier result? What can run without touching the same mutable resource? Can state change the route or stop? Can the system detect, explain, and replay partial failure? [“The 105 minutes after the graph”](/drafts/67821675/) covers evaluation, typed state, and trust controls after selection.

Approve a branch or cycle only with a named owner, an independence or state-change case, a measurable target, a failure deadline, and replay evidence. The smallest graph that tells the truth is the advanced architecture.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Extra topology needs an owner, branch and resource identities, a join policy, bounded retries, replay evidence, and measured benefit. If those fields stay blank, remove the edge.</p></div>
