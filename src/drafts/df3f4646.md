AI builders often call graphs advanced and pipelines primitive. That confuses topology with capability. Workflow topology is how stages and routes are arranged; a pipeline is its simplest graph, an ordered path.

I think production calls for the minimum truthful topology. Extra routes expand coverage or parallelism, but not judgment, retry safety, or ownership. They add scheduling and recovery work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The useful architecture matches the work's real dependencies and failure paths.</p></div>

## Draw dependencies before topology

Start with what must wait. A data dependency means one job consumes another's result. A resource dependency means jobs share something mutable or exhaustible, such as a file, database record, approval, quota, or service. [PostgreSQL, an open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), documents writers waiting on a locked record; [Stripe, a payments platform](https://docs.stripe.com/rate-limits), separates rate from concurrency limits.

Apply the fake-edge test. If B consumes nothing from A and the jobs share no write, lock, approval, quota, or external effect, their edge may be artificial. A shared immutable input creates no write conflict. I think teams will mistake concurrent model calls for independent work, then find the hidden dependency during recovery.

Keep a linear pipeline when sequence is real: ingest → validate → apply policy → persist. Code should handle validation, deduplication, routing, counting, and merge completeness; models belong where judgment is required.

Replay means reconstructing workflow state from recorded history, but its mechanics depend on the runtime. [Temporal, a durable workflow platform](https://docs.temporal.io/workflow-definition), runs deterministic Workflow control logic against Event History without re-executing Activities, its external-work units. [An Activity may still run again under its retry policy](https://docs.temporal.io/activity-execution), so writes and messages need duplicate-effect protection.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Sequence is an asset when each stage consumes the prior result; remove an edge only after checking shared data and resources.</p></div>

## Make the merge operational

A directed acyclic graph, or DAG, has directed dependencies but no route back. Use it when work fans out into independent branches and fans in at a merge: research five market angles concurrently, verify each, then merge accepted evidence.

The coordination tax arrives at the merge: partial failures, shared limits, extra calls, and recovery. A join policy says which results are required and what happens when one is missing. The critical path is the longest required chain, so an all-required merge waits for its slowest branch. [AWS Step Functions, a managed workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), waits for every Parallel branch. I think the merge contract matters more than fan-out.

This pseudocode is a design contract, not engine configuration:

```text
run_id: research-042
branches:
  market:      {required: true,  status: complete,  mutable_resource_keys: []}
  regulation:  {required: true,  status: running,   mutable_resource_keys: [regulatory-cache]}
  competitors: {required: false, status: timed_out, mutable_resource_keys: []}
join_policy: all_required
retry_budget: 2
stop_condition: deadline_or_budget
owner: research-service
guard: required_branches_must_be_terminal
```

Here, accepting the merge while `regulation` is running is illegal. An implementing runtime should return a visible error: `join_rejected: required branch regulation is running`. The run record should preserve branch IDs, input versions, results or errors, retry counts, and the merge decision. These are requirements, not automatic graph features.

A retried charge, message, or write needs idempotency, meaning repeats of the same request preserve one intended external effect. [Stripe's API documentation](https://docs.stripe.com/api/idempotent_requests) shows one implementation using a key.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A production merge needs required branches, a missing-result policy, retry safety, legal transitions, evidence, and a recovery owner.</p></div>

## Add routes only when state earns them

A conditional graph selects its next route from current state, the run's recorded facts. A cyclic graph can return to earlier work, so it needs a reason, a stop rule, and an attempt, time, or cost limit. [LangGraph, an open-source framework for stateful agent workflows](https://docs.langchain.com/oss/python/langgraph/graph-api), documents state-based routing and a loop limit. I think a cycle earns its place only when state alters the next action.

Topology is framework-independent. A durable engine, queue workers, state-machine code, or an agent-graph library can implement it. A hybrid makes this visible: intake and policy stay linear while research fans out into two required branches and one optional branch, then converges before approval.

Use four questions in the design review:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can runtime state change the next route or stopping condition?
4. Can the system detect, explain, and recover from a partial failure?

Baseline the linear route, run the bounded alternative, then compare latency, evidence, duplicate effects, incomplete merges, recovery time, and cost per successful run. Before release, the service owner should approve retries, the failure deadline, and rollback. If independence and useful gain are proven, with join and recovery rules explicit, a DAG has earned its place. I don't know which shape wins before measurement. I think a team claiming otherwise is drawing ahead of the evidence.

[“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper on loop terminology and exit conditions. [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, declared state, and evidence after topology selection.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The advanced architecture is the smallest graph that tells the truth, because every unearned edge becomes an unowned failure path.</p></div>
