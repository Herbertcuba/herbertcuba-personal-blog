I think graph tools make coordination cheap to draw and easy to underestimate. More nodes can look advanced even when the work remains sequential.

A pipeline is already a graph: one directed path. Topology is the layout of stages and connections. Choose the minimum that expresses real dependencies without inventing joins and failure paths. Start there, measure it, then let evidence earn each branch or return edge.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A pipeline and a graph are not opposites. Choose the simplest graph that matches the work.</p></div>

## Draw the dependencies before the graph

A data dependency exists when one job consumes another job’s result. A resource dependency is less visible: two jobs may share no output yet still contend for a writable file, database record, mutable workspace, approval gate, or API capacity.

This distinction matters in production. [PostgreSQL, an open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), documents a would-be updater waiting on a conflicting row update or lock. [Stripe, a payments platform](https://docs.stripe.com/rate-limits), documents concurrency limits separately from request-rate limits. Independent prompts do not make independent jobs.

Apply the fake-edge test: if B consumes no output from A and creates no shared-write, approval, quota, or side-effect conflict when run concurrently, the A → B edge may be artificial. Immutable read-only snapshots can be shared under appropriate controls. Shared writes are not independent by default; they need isolation, enforced ordering, or another proven control. I think fan-out should be rejected when two branches can write the same transactional record without one.

## Let runtime behavior choose the shape

Keep a linear pipeline when every stage needs the previous result, as in request intake → schema validation → policy check → persistence. The route is known, deterministic checks remain ordinary code, and replay means rerunning recorded work through that known route while preventing duplicate effects. I think visible sequence is a production strength when sequence is real.

Use a directed acyclic graph, or DAG, when work is genuinely wide and no route returns to an earlier stage. Fan-out starts independent branches; fan-in merges their results. Parallel work can shorten the critical path, the longest required chain that determines completion time, but an all-required merge still waits for its slowest branch. [AWS Step Functions, a cloud workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), makes that all-branch wait explicit. I think the merge is the design decision: it needs expected branch IDs, a deadline, provenance, and a policy for missing or failed results.

A conditional graph chooses the next stage from recorded state. A cyclic graph can revisit an earlier stage, so it also needs a meaningful state change, a stop rule, and a hard budget. If every run always makes two passes, draw two stages instead. The article [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) covers feedback-loop terminology and exit conditions in more depth.

The current Content Engine, Herbert’s content-production workflow, offers a hybrid example: a mostly linear backbone with a short state-driven return route. It moves from research through drafting and quality gates toward publication, while a failed gate can return the article to drafting. It has no parallel research-and-verification merge today. A future research fan-out would need independent questions, isolated workspaces, and a measured latency benefit.

## Price the coordination tax

Topology alone supplies no reliability. A merge must expose missing branches, preserve provenance, and apply a declared join policy. Retried side effects need idempotency: a key or rule that stops one logical action from taking effect twice. Operators also need an owner, a failure deadline, controlled writes, and enough recorded state to replay one branch without guessing.

When recovery dominates, choose an execution layer with durable history, explicit transitions, deterministic replay, retry policy, and idempotency controls. An agent framework can sit above it; topology and execution guarantees are separate decisions. Compare the proposal with its linear baseline on critical-path latency, completion coverage, duplicate effects, and cost per successful run.

I don’t know which shape wins before measurement. I think a branch or cycle should survive review only with independent work, bounded failure, an owner, and measured benefit. Ask four questions: What must wait? What can run without a mutable-resource conflict? Can state change the route or stop rule? Can partial failure be explained and replayed? [“The 105 minutes after the graph”](/drafts/67821675/) covers the next layer: evaluation and typed state, meaning run records with declared fields and allowed values.

Operate the smallest graph that tells the truth about the work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Approve extra topology only with explicit resources, failure rules, ownership, recovery evidence, and measured value over the simpler path.</p></div>
