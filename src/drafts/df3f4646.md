AI workflow diagrams can make branches look mature and straight lines primitive. A linear pipeline is already a graph: one directed path through required stages. A directed acyclic graph (DAG) can branch and merge but cannot return to an earlier node. A conditional graph chooses its route from current state; a cyclic graph revisits prior work; and a hybrid is a linear backbone with a bounded graph-shaped section.

I think the useful question is which minimum topology matches the work. Anatoli Kopadze’s [2026 essay about graph engineering](https://x.com/AnatoliKopadze/status/2080668775796314331) puts it well: “A graph buys breadth. It does not buy better judgment.” Arrows describe coordination, not evidence or validation.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A pipeline is already a graph; add complexity only when the work’s dependencies require it.</p></div>

## Draw dependencies before topology

Every edge should answer what must wait. A data dependency exists when one job consumes another’s output. A mutable resource is a shared thing a job can change, such as a file, database row, approval record, or workspace. Jobs that write to the same resource may need isolation or sequencing even when they exchange no output.

An API quota sets a scheduling or concurrency limit, not a data edge. Shared input does not create a write conflict when every branch reads the same immutable version. Apply the fake-edge test: if B does not consume A’s result, neither changes the same resource, and shared capacity allows both, the A-to-B edge is probably artificial. If no pair passes, do not branch.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Map outputs, shared writes, approvals, and capacity before calling two jobs independent.</p></div>

## Choose sequence or breadth

A pipeline fits ingest request → validate schema → apply policy → persist result. Each stage needs the previous result or authorization, the route is known, and the replay point is obvious. Keep schema checks, counting, duplicate removal, and fixed routing in deterministic code. I think an ordered design is strongest when real sequence keeps cost, recovery, and ownership visible.

Use a branched DAG for genuinely wide work. Fan-out starts independent jobs; fan-in merges their results. For example, research five market angles, verify against evidence, then merge acceptable findings. [Amazon Web Services’ Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), a managed workflow service, makes one join rule concrete: its Parallel state waits for every branch. The slowest required branch therefore sets the earliest merge time. I think the merge policy matters more than the fan-out: declare required results, missing-result handling, and a deadline.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep real sequence linear; branch only independent work whose merge and missing-result policy you can define.</p></div>

## Let runtime state earn the return path

Conditional routing is justified when current run state changes what happens next. Evidence scores may trigger verification; policy exceptions may escalate to a person. A cyclic graph is warranted when state can send work back for retry or refinement.

If the number of passes is known in advance, keep them in a DAG. I think a cycle earns its place only when state determines whether to return, and it still needs a stop rule plus a hard step or cost cap. [LangGraph](https://docs.langchain.com/oss/python/langgraph/graph-api), a framework for stateful agent workflows, documents state-based edges and a loop execution limit. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper on loop terminology, ownership, and exit conditions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use conditions for state-driven choices and cycles for bounded return paths, never for decorative complexity.</p></div>

## Price the coordination tax

Partial failure means one branch fails after its peers produce outputs, leaving an incomplete merge. The join must know the expected branch identifiers, expose missing results, and preserve provenance, the record of which branch and source produced each result. Retried side effects need [idempotency](https://docs.stripe.com/api/idempotent_requests), meaning the same logical request cannot repeat its effect. Isolated workspaces, quota-aware scheduling, branch logs, and replayable inputs complete the bill.

I don’t know whether wider execution will repay that price in your system. Measure duration, throttling, retries, join completeness, and replay success. I think the strongest production default is often a hybrid: keep intake, policy, approval, and persistence linear, then allow a short fan-out/fan-in burst for research or verification. Once topology is chosen, [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, schema-checked workflow state, and the controls needed to trust execution.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A hybrid confines branching to the work that benefits from it while keeping the main control path easy to operate.</p></div>

## Ask four questions, then stop

Before adding an edge, ask:

1. What must wait because it consumes an earlier result?
2. What can run independently without changing the same mutable resource?
3. Can runtime state change the next route or stopping condition?
4. Can the system detect, explain, and replay a partial failure?

Start with the smallest truthful topology and instrument it. If independent calls dominate latency, begin with a DAG. Otherwise, let measured bottlenecks earn branches and state changes earn return paths. My take: every edge needs a production reason.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose the minimum topology that expresses the work, then require every added edge to justify its operational cost.</p></div>
