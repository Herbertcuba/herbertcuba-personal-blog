Graph diagrams can make an AI workflow look advanced before it becomes useful. I think topology, the arrangement of stages and edges, should describe work, not agent count.

A pipeline is an ordered graph path. A DAG, or directed acyclic graph, can branch and merge but not return. A conditional graph routes from state; a cyclic graph revisits work. Choose the minimum topology that expresses the work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A pipeline is already a graph; earn every branch, route, and return.</p></div>

## Map dependencies before topology

Map data first: a job waits when it consumes another's result. Then map mutable resources it can change: files, rows, approvals, or workspaces. Shared quotas couple jobs; local immutable snapshots create no shared write.

[PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html), an open-source relational database, documents a writer waiting on another's row; [Stripe](https://docs.stripe.com/rate-limits), a payments platform, separates rate and concurrency limits. I think an A-to-B edge may be fake if B consumes no output from A and the jobs share no write, lock, approval, or scarce capacity. A temporary cap belongs in queue settings, not a permanent edge.

Schema validation, policy, and persistence stay sequential because each stage authorizes the next. [Temporal](https://docs.temporal.io/workflow-execution), a durable workflow platform, persists state and reconstructs execution from event history after failure. Those are runtime guarantees. I think a visible pipeline is strongest for a known route.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Remove fake order, preserve dependencies, and separate runtime guarantees from topology.</p></div>

## Design the merge before the fan-out

Fan-out starts independent branches; fan-in joins them. [AWS Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), Amazon's managed workflow service, runs Parallel branches concurrently and waits for all. The critical path, the longest required chain, therefore ends at the slowest branch.

For five market angles, the merge expects IDs A through E, each with a brief version, findings, provenance (where the result came from), model and tool versions, attempt ID, and finish time. With a 90-second deadline and one retry, five satisfy completeness, four stay internal for risk review or rerun, and three or fewer fail closed. Code rejects C1 if it arrives after accepted C2, just as it rejects a duplicate.

Product decides completeness, promotion, and rollback; data owns inputs; platform owns isolation, capacity, and the join; operations can stop fan-out and invoke the serial fallback; risk controls degraded results. I think the merge is the architecture decision.

Test 100 frozen briefs over two weeks with the same model, tools, and sources, capped at five engineer-days. The serial baseline is 150-second p95 latency and $1.00 per accepted report, including model, runtime, and operator work. Set the bars before testing:

| Measure | Promotion bar | Candidate |
|---|---:|---:|
| End-to-end p95 latency, 30% below baseline | ≤105 seconds | 98 seconds |
| Complete five-branch merges | ≥99/100 | 99/100 |
| Replay of recorded IDs and merge decision | 100/100 | 100/100 |
| Full cost per accepted report | ≤$1.15 | $1.12 |
| Recovery to serial fallback | ≤10 minutes | 8 minutes |

All bars pass, though one four-branch run stays internal, so promote the bounded fan-out while retaining the serial fallback. This is illustrative, not enterprise evidence. I don't know whether width has earned its place without such a record.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Parallelize only when identity, completeness, cost, failure, authority, and fallback are testable.</p></div>

## Route only when state changes

Use a conditional graph when state changes the route, and a cycle when a tool error, failed evidence check, or refinement decision sends work back. If the pass count is known, keep the route acyclic.

Every return needs a reason, stop rule, budget, and escalation. [LangGraph](https://docs.langchain.com/oss/python/langgraph/graph-api), an open-source framework for stateful agent workflows, documents state-based edges and maximum execution steps. I think a cycle without a state change and stop rule is an unbounded bill. [Everyone Discovered Loops. Nobody Agrees What the Word Means.](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper on ownership and exit conditions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Add routes or cycles only when state explains the next move and stop.</p></div>

The mapping is practical: a launch sequence needs a pipeline because each stage enables the next, while a fleet engagement needs branches, changing routes, and convergence. Turning the launch into a fleet graph only adds mission-control software that can fail.

## Keep the graph local

My take is a linear spine for intake, policy, approval, and persistence, with graph bursts for research or verification. This contains partial failures, joins, quotas, and model use. Idempotency means a retry does not repeat an external effect; it is a coordination cost, not a benefit.

I think an architecture review can close with four questions:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can runtime state change the route or stopping condition?
4. Can the system detect, explain, and replay a partial failure?

If the last answer is no, do not widen. [The 105 minutes after the graph](https://www.cubagarcia.com/drafts/67821675/) covers what follows: evaluation, explicit state, and production controls. Complexity should follow measured need, never the ease of drawing another edge.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose the smallest truthful topology; widen only when measured gain repays coordination.</p></div>
