Graph frameworks make coordination cheap to draw and expensive to operate. A linear pipeline is already a graph topology, the arrangement of stages and connections: one ordered path. Add branches only for independent work, and conditions or cycles only when runtime state changes the next step. I think architecture should describe those facts before it displays sophistication.

A launch sequence stays ordered because each stage enables the next; a fleet engagement needs independent units, branching decisions, and convergence. Turning one into the other adds mission-control software without changing the work. Anatoli Kopadze, author of a [January 2026 essay on graph engineering](https://x.com/AnatoliKopadze/status/2080668775796314331), wrote: “A graph buys breadth. It does not buy better judgment.” I don't know whether a branch belongs until its independence is visible.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose topology from dependencies and runtime decisions, then make each edge justify its operating cost.</p></div>

## Draw both kinds of dependency

Start with data dependencies: B must wait when it consumes A's result. A hidden resource dependency arises through mutable state a task can change: a file, database row, workspace, approval gate, or external side effect. [PostgreSQL, an open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), documents one mechanism: a second writer may wait when the first transaction updates or locks a row. No output is exchanged, but the shared write still forces coordination. A shared API quota can throttle both.

Apply the fake-edge test. If B does not consume A's output and the jobs share no mutable resource, lock, quota, or side effect, their edge may be artificial. A read-only snapshot is safe to share; writable branch state must be isolated. I think five market-research jobs qualify only with independent angles and either isolated workspaces or no writes.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Map consumed outputs and hidden resource conflicts; separate prompts do not make jobs independent.</p></div>

## Keep sequence linear and widen only real work

Consider ingest request → validate schema → apply policy → persist result. Every stage needs the previous result or authorization, so the linear route exposes its owner, retry point, and replay path. Replay means rerunning from recorded inputs and state. I think deterministic code should handle validation, counting, deduplication, and routing; reserve model calls for judgment.

A directed acyclic graph, or DAG, allows branches but no directed route back. Fan-out starts independent branches; fan-in merges them. Parallel work can shorten the critical path, the longest required chain, by removing serial waiting, but speedup is not automatic. [AWS Step Functions, Amazon's managed workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), waits for every branch in an all-required parallel step, so the slowest required result still holds the merge.

I think the merge is harder. If five IDs are expected but the `customer` branch result is missing at the deadline, the join policy decides whether the run fails, retries, accepts survivors, or escalates. Selective replay requires durable per-branch input and output records, stable IDs, and an executor that reruns work without duplicating external effects. [Stripe, a payment processor](https://docs.stripe.com/api/idempotent_requests), accepts client-supplied idempotency keys so retries produce one logical effect. Reject fan-out when two branches can update the same transactional record without isolation or deliberate serialization.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep real sequence linear. Use a DAG only when branches are isolated and the merge defines failure and replay.</p></div>

## Let runtime state justify a return

A conditional graph selects its next edge from recorded runtime state; a cyclic graph can revisit an earlier node. Use them when evidence, errors, or approvals change the route. For example, a verifier may send a missing-source request back to research. I think a return is justified only when state changes the next action; it also needs a stop rule and a hard step, time, or cost limit. If two passes are known in advance, use a fixed DAG. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](/posts/everyone-discovered-loops/) explains feedback terms and exit conditions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use conditions or cycles when state changes the route; give every return a stop rule and budget.</p></div>

## Make complexity pass an operating test

Durable execution handles interruption and replay regardless of topology. [Temporal, an open-source durable workflow engine](https://docs.temporal.io/workflow-definition), records workflow history to reconstruct control state. That separation enables a hybrid: intake, policy, approval, and persistence stay on a linear spine while bounded research fans out and converges. My take is that this limits the coordination tax to the section that needs it: partial-failure handling, workspace isolation, quota pressure, extra model calls, and tracing.

Before approval, create a small operating contract: stable run and branch IDs, writable resource keys, join policy and deadline, retry budget, stop rule, owner, write boundary, and replay evidence. This makes illegal fan-out checkable rather than debatable.

```yaml
run_id: market-report-42
topology: fan_out_fan_in
expected_branch_ids: [market, regulation, customer, competitor, technology]
mutable_resource_keys: []
join: {policy: all_required, deadline: 10m}
retry: {budget_per_branch: 1, side_effect_boundary: merge_only}
stop_condition: complete_or_fail
owner: research-platform
replay_evidence: durable_branch_input_and_output
```

Use four questions in the review:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can runtime state change the next route or stopping condition?
4. Can the system detect, explain, and replay a partial failure?

Compare the linear baseline with the proposed topology on critical-path latency, completion coverage, duplicate effects, and cost per successful run. Approve the move only when its owner can show write isolation, a failure deadline, replay evidence, and a measured gain. Once topology is chosen, [“The 105 minutes after the graph”](/drafts/67821675/) covers evaluation, typed state, and trust controls. Frameworks make graphs easy to draw; production has to make every edge worth operating.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prefer a linear spine with bounded graph sections, approved through explicit controls and measured benefit.</p></div>
