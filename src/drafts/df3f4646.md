# Choose the smallest graph that fits the work

Workflow topology is the shape of stages and connections. Graph tooling represents stages as nodes and dependencies as edges. A pipeline is already a graph: one ordered path.

I think teams invert this decision when they treat graphs as advanced and draw coordination the work never required. Picture a sci-fi launch beside a fleet engagement. Launch stages enable one another; fleet units move independently and converge as conditions change. Turning the launch into a fleet adds mission-control software without changing the work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose the minimum workflow shape that expresses real dependencies. More arrows do not create better judgment.</p></div>

## Map the work before the arrows

Map each job’s inputs and changes. Job B has a data dependency when it needs A’s result. A mutable resource is a shared file, database row, approval gate, workspace, or API quota a job can change or exhaust.

Jobs can conflict without exchanging results. [PostgreSQL, an open-source relational database, documents](https://www.postgresql.org/docs/current/transaction-iso.html) one writer waiting behind another on the same row. An immutable snapshot is a fixed copy neither job can alter; it creates no shared-write conflict. Apply the fake-edge test: if B consumes none of A’s output and the jobs share no write, lock, quota, or side effect, their edge may be artificial.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Map data flow and shared resources before choosing tools. Separate prompts do not make work independent.</p></div>

## Keep sequence linear and branch for width

Keep a pipeline for real sequence: ingest a request, validate its schema, apply policy, then persist the result. Put validation, counting, deduplication, and routing in deterministic code, which returns the same result for the same input. I think visible order is strong because ownership, recovery, and replay stay easy to trace.

Use a DAG, or directed acyclic graph, for real width: work may branch, but no directed path returns to an earlier stage. Fan-out starts independent branches; fan-in merges them. This can shorten the critical path, the longest required chain, but an all-required merge still waits for its slowest branch. [AWS Step Functions, Amazon’s managed workflow service, specifies](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html) that behavior for its parallel step.

For five independent market angles, I think the merge is the real decision. It needs five expected branch IDs, a deadline, a missing-result policy, and provenance, meaning each result’s source and execution trail. Parallel work pays when that contract is governable.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Preserve real sequence. Branch only work whose merge can account for delay, absence, and evidence.</p></div>

## Let recorded state change the route

Sometimes the next step is unknown in advance. Runtime state is the current recorded result or condition. A conditional graph uses it to choose a route; a cyclic graph can return to earlier work.

A weak evidence score may trigger another check; a retryable failure may send work back or escalate it. If two review passes are known beforehand, keep them as ordered DAG stages. I think a cycle earns its place only when changed state alters the next action, and it needs a stop condition plus a hard limit. Breadth alone does not improve judgment; evidence and validation do that work.

[Everyone Discovered Loops. Nobody Agrees What the Word Means.](/posts/everyone-discovered-loops/) goes deeper on feedback-loop terms, ownership, and exits.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Add a route or return only when current state changes the next action. Every cycle needs a reason to return and stop.</p></div>

## Make the coordination tax executable

Every branch adds failure choices, quota pressure, repeated calls, write conflicts, and replay work. Idempotency means a retry cannot repeat an external effect; [Stripe, a payments platform, documents](https://docs.stripe.com/api/idempotent_requests) one key-based design. Isolation prevents branch writes from overwriting each other. When replay dominates, a durable state-machine runtime that persists steps, timers, retries, and results is often a better base than an agent graph API alone.

Record the decision as a production contract:

| Decision question | Evidence to record |
| --- | --- |
| What must wait for an earlier result? | Required inputs, outputs, and ordered edges. |
| What can run without touching the same mutable resource? | `expected_branch_ids` and `mutable_resource_keys`. |
| Can state change the route or stopping point? | Route condition, `retry_budget`, `stop_condition`, and hard cap. |
| Can partial failure be detected, explained, and replayed? | `run_id`, `join_policy`, owner, `failure_deadline`, idempotency key, and replay or rollback evidence. |

Reject fan-out if two branches can write the same database record without isolation. Start linear and measure it; I don’t know whether a branch pays without a baseline. Compare critical-path latency, completion coverage, duplicate effects, and cost per successful run before and after. I think a branch lacking independent work and a measured critical-path benefit should fail review.

My take: default to a hybrid, a linear control spine with short graph sections for research or verification. [The 105 minutes after the graph](/drafts/67821675/) covers evaluation and trust after selection. Frameworks make coordination cheap to draw; operating it remains expensive.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Approve the smallest topology whose owner can show independent work or a state-driven route, measured benefit, and replayable failure controls.</p></div>
