Graph tooling makes coordination cheap to draw and expensive to govern.

A pipeline is already a graph: one ordered path through dependent jobs. A launch sequence must remain ordered because each stage enables the next; a fleet engagement needs independent units and routes that later converge. Giving the launch a fleet topology adds mission-control software without changing the work.

[A 2026 graph-engineering explainer on X, the social platform formerly called Twitter](https://x.com/AnatoliKopadze/status/2080668775796314331), puts it well: “A graph buys breadth. It does not buy better judgment.” I think that is right. I don't know which framework fits until work reveals its topology.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A pipeline is the minimum graph. Add only branches or returns the work requires.</p></div>

## Dependencies come before topology

Job B has a data dependency when it needs job A's result. A resource dependency appears when both change the same file, database row, approval record, or workspace, or share an API quota, a provider's limit on requests or concurrent calls. [Database transaction rules](https://www.postgresql.org/docs/current/transaction-iso.html) show that one writer can wait behind another without consuming its output.

The fake-edge test is simple: if B consumes no result from A and they neither change the same mutable resource, meaning shared state, nor exhaust a quota, the edge may be artificial. Shared fixed input is fine; shared writes require coordination.

Keep the pipeline when sequence is real: ingest, validate schema, apply policy, persist. Its critical path, the longest required chain, and replay, a rerun from recorded inputs and state, stay visible. I think this clarity is a production advantage. Keep validation, routing, counting, and deduplication, removing repeats, in ordinary code; use models for judgment.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Check data and resources before removing an edge. Real sequence belongs in a pipeline.</p></div>

## Where a branched DAG earns its place

A DAG, or directed acyclic graph, can branch but cannot return along a directed route. Fan-out starts independent jobs; fan-in merges them. Five market-angle searches can fan out before their evidence is combined. [AWS Step Functions, a managed state-machine service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), waits for every required parallel branch, so the slowest one still bounds the merge.

The merge needs expected branch IDs to distinguish missing from unfinished work. That sets its join policy: wait for all, accept a threshold, retry, or escalate. External writes also need idempotency, meaning a repeated logical request has one effect; [Stripe's payments API documents](https://docs.stripe.com/api/idempotent_requests) this with retry keys. Record branch sources and processing history. I think the merge is the real product decision.

Record the contract:

```yaml
run_id: market-report-42
topology: fan_out_fan_in
expected_branch_ids: [market, regulation, customer, competitor, technology]
mutable_resource_keys: []
join_policy: all_required
retry_budget: 2
stop_condition: all_received_or_10m
owner: research-platform
failure_deadline: 10m
side_effect_boundary: merge_only
replay_evidence: event_log
provenance: per_branch_sources
```

Reject fan-out when branches share a writable resource key without isolation, meaning separate writable state or coordinated shared writes.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A DAG pays off when independent jobs meet a merge contract covering results, failures, writes, and replay.</p></div>

## Cycles are for state-dependent routes

A conditional graph chooses its next edge from runtime state, the recorded facts of this run. A cyclic graph can revisit an earlier node. Both fit score-based verification, bounded retries, or refinement until a stated condition. When the pass count is known, a fixed DAG is clearer.

Every return needs a reason, stop rule, and hard limit. I think a cycle earns its place only when state changes what happens next. The companion article [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](/posts/everyone-discovered-loops/) explains feedback terms, ownership, and exit conditions.

When replay and duplicate-effect control dominate, [a durable workflow system](https://docs.temporal.io/workflow-definition), which records history and replays deterministic control code, may be the better substrate. Agent judgment can still run inside a step, while external writes keep idempotency controls.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use a cycle only when state changes the next action. Every return needs a stop rule and hard limit.</p></div>

## The production default is usually hybrid

A hybrid keeps intake, policy, approval, and persistence on a linear spine while a bounded research or verification stage fans out. A model or external-service branch creates a possible failure the merge must detect and may consume tokens, quota, and time; a deterministic local branch may do neither.

Measure critical-path latency, completion coverage or the share of required results received, duplicate external effects, and cost per successful run on both versions. Approve complexity only when a named owner provides the resource boundary, expected gain, failure deadline, side-effect boundary, and rollback or replay evidence.

Use four questions:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can runtime state change the next route or stop rule?
4. Can the system detect, explain, and replay a partial failure?

The companion article [“The 105 minutes after the graph”](/drafts/67821675/) covers evaluation, validated state, and trust after topology selection. My take is that complexity should follow a measured bottleneck, independent branch, then state-dependent route. I think branches lacking resource independence and measured latency or coverage gains should fail review. Choose the smallest graph that tells the truth, because every extra edge becomes somebody's production problem.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep a linear spine. Approve graph sections only when measured gains and controls exceed their coordination tax.</p></div>
