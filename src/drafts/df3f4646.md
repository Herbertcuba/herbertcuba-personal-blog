I think graph tools make coordination cheap to draw and expensive to govern. A canvas full of nodes can look advanced even when the work remains sequential, while every extra connection creates another route that operators must explain and recover.

A pipeline is already a graph: one directed path. Topology simply means the layout of stages and their connections. The real architecture decision is the minimum topology that expresses the workflow’s dependencies without inventing merge points and failure paths. Start with the truthful shape, measure it, then let evidence earn each branch or return edge.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A pipeline and a graph are not opposites. Choose the simplest topology that matches the work, then require evidence before adding another route.</p></div>

## Draw dependencies before agents

A data dependency exists when one job consumes another job’s result. A resource dependency is less visible: jobs may exchange no output yet still contend for a mutable resource, meaning a file, database record, workspace, approval, or service limit that either job can change or exhaust. [PostgreSQL, an open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), documents conflicting updates waiting on one another. [Stripe, a payments platform](https://docs.stripe.com/rate-limits), documents active-request limits separately from request-rate limits.

Apply the fake-edge test in both directions. If B consumes no result from A and the jobs can run together without conflicting writes, approvals, quotas, or side effects, the A → B edge may be artificial. A shared immutable snapshot is usually different because neither branch changes it. I think a proposed parallel split should fail review if two branches can update the same transactional record without isolation, enforced ordering, or another proven control.

## Let runtime behavior choose the shape

Keep a linear pipeline when every required stage needs the previous result, as in ingest request → validate schema → apply policy → persist result. The route is known, deterministic checks stay in ordinary code, and replay means rerunning recorded work through that route while controlling duplicate external effects. I think visible sequence is a production strength when sequence is real.

Use a directed acyclic graph, or DAG, when work is genuinely wide and no route returns to an earlier stage. Fan-out starts independent branches, while fan-in merges their results. Parallel work can shorten the critical path, the longest required chain that controls completion time, but a merge that requires every branch still waits for the slowest one. [AWS Step Functions, a cloud workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), makes that wait explicit. I think the merge is the real design decision: it needs expected branch IDs, a deadline, provenance, meaning a record of which branch produced each result, and a rule for late, missing, or failed results.

A conditional graph selects the next stage from recorded runtime state. A cyclic graph can return to an earlier stage, so it also needs a meaningful state change, a stop condition, and a hard attempt or cost limit. If every run always makes two passes, draw two stages instead. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper into feedback-loop terminology and exit conditions.

A hybrid is a linear backbone with one bounded branched or state-driven section. The current Content Engine, Herbert’s content-production workflow, is a useful simplified example: most article production follows an ordered route, while a failed quality gate can return the article for revision before the route continues. It does not currently use a parallel research-and-verification merge. The point is to describe the control flow that exists, without drawing imaginary concurrency into it.

## Meanwhile in sci-fi

<p>In this 1983 science-fiction film, the Rebel ground operation and fleet action proceed in parallel, but the fleet’s final strike depends on the ground team disabling the shield. That maps to a branched workflow with a real dependency gate, rather than two fully independent branches. A launch sequence is more strictly ordered because each stage enables the next. The architecture lesson is to draw independent units where they exist while preserving every prerequisite edge that the final objective consumes.</p>
</div>

I think this distinction matters because a fleet-shaped picture can still contain launch-sequence dependencies. The arrows must describe what can actually proceed, not what makes the diagram exciting.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Parallel activity can still contain hard prerequisites. Preserve those gates instead of mistaking simultaneous work for independence.</p></div>

## Make extra topology earn approval

A graph adds a coordination tax: partial failures, merge rules, isolated writes, service limits, traces, and more model or tool calls. The merge rule, often called a join policy, states which branch results are required and what happens when one is late, missing, or fails. Retried side effects also need idempotency, a key or rule that prevents one logical action from taking effect twice.

When recovery dominates, choose an execution layer with a durable history, meaning a persisted record of transitions, plus explicit retry rules, deterministic replay, and idempotency controls. An agent framework can sit above it; topology and execution guarantees are separate decisions. Compare every proposal with its linear baseline using critical-path latency, completion coverage or the share of required outputs delivered, duplicate effects, and cost per successful run.

I don’t know which shape wins before measurement. I think a branch or cycle should survive review only when it has independent work or a necessary state transition, an accountable owner, bounded failure, and measured value. Ask what must wait, what can run without a mutable-resource conflict, whether state can change the route or stopping point, and whether a partial failure can be detected, explained, and replayed. [“The 105 minutes after the graph”](/drafts/67821675/) takes up evaluation and typed state, a state schema whose fields have declared types or allowed values, after the topology is chosen.

Operate the smallest graph that tells the truth about the work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Approve a branch or cycle only with a real dependency case, explicit resources and failure rules, an owner, recovery evidence, and measured value over the simpler path.</p></div>
