# Every edge is a claim about waiting

Every edge claims one job must wait. A linear pipeline is both a graph and a directed acyclic graph (DAG): one ordered path with no directed cycle. A branched DAG can fan out and merge. A conditional graph selects its next edge from current run data; a cyclic graph can return to earlier work. A hybrid keeps a linear backbone with bounded branches or cycles.

These are workflow shapes, not maturity levels. In [a July 2026 article on graph engineering](https://x.com/AnatoliKopadze/status/2080668775796314331), author Anatoli Kopadze argues that graphs add width rather than judgment and asks whether each step needs its predecessor’s result. I think his test needs one production extension: independent jobs may still need an edge when they compete for shared state or capacity.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose the minimum topology that represents every wait, including hidden resource waits.</p></div>

## Map the waits before drawing the graph

A data dependency exists when one job consumes another’s result. A resource dependency exists when jobs can change the same mutable resource, such as a file, database row, or approval record. An immutable snapshot may remove a write conflict, but not an API quota.

Ingest request → validate schema → apply policy → persist result belongs in a pipeline because each stage needs the previous output. I think deterministic code should handle schema checks, counts, deduplication, and fixed routes; reserve models for judgment.

Apply Kopadze’s fake-edge question: if B neither consumes A’s output nor competes with A for a shared write or capacity limit, their edge may be artificial. [PostgreSQL, a relational database, documents one updater waiting on another transaction](https://www.postgresql.org/docs/current/transaction-iso.html); [Stripe, a payment platform, separates rate from concurrency limits](https://docs.stripe.com/rate-limits). If removing an edge replaces model waiting with lock, queue, or throttle waiting, the shared resource is the bottleneck.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Remove an edge only when neither data nor a shared resource requires the wait.</p></div>

## Design the join before the fan-out

Fan-out starts independent branches; fan-in merges their results. Five market-angle searches can run together before one report combines them. The critical path is the longest required chain, so an all-required merge still waits for its slowest branch. [AWS Step Functions, Amazon’s workflow state-machine service, runs parallel branches and waits for them to finish](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html). Parallel work removes artificial waiting; it does not promise an N-times speedup.

I think the merge is the real design decision because it exposes the coordination tax: the extra work of tracking branches, failures, joins, and recovery. Persist an inspectable contract:

```yaml
branch: {run: R42, id: angle-3, attempt: 2, status: succeeded}
refs: {input: request-v7, output: finding-91}
controls: {idempotency_key: R42/angle-3, deadline: 2026-08-15T14:30:00Z, provenance: sources/tool-v4}
join: {required: [angle-1, angle-3], optional: [angle-2], received: [angle-2, angle-3], revision: 1, status: blocked}
```

Required `angle-1` is missing, so publishing stays blocked. Record a handled error as failed or degraded, explain an optional absence, and cancel obsolete work. A late result creates revision 2 instead of changing revision 1. Reject `succeeded → running` within one attempt; a retry creates attempt 3. Idempotency means repeating the same logical write does not repeat its intended effect. Provenance records the source-and-tool trail.

The workflow owner handles partial joins; the release owner can stop or roll back; the budget owner funds human handling. Step Functions supplies retry and error mechanics; the team defines required evidence and acceptable degraded completion.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Define branch identity, merge rules, failure policy, ownership, and safe retries before parallel work.</p></div>

## Let state and measurement earn the rest

Use a conditional edge when state changes the next route, and a cycle when state sends work back. Every cycle needs a stop rule and a hard step or cost cap. I think a fixed two-pass review remains a DAG; only a runtime choice among refinement, completion, or escalation earns a return edge. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper on loop terminology and exit conditions.

A retry reattempts one job; a resume continues stored execution; a rerun starts a new execution; history replay reconstructs state from recorded events. [Temporal, a durable workflow engine, supplies persisted event history and replay](https://docs.temporal.io/workflow-execution), not topology choice. Isolate branches through owned records, partitions, transactions, locks, immutable snapshots, or separate workspaces.

My take: benchmark the linear stage for one release, then test one independent branch that can be disabled. One example bar: p95 duration at least 20 percent below the linear baseline, where 95 percent of runs finish at or below that duration; cost per successful task no more than 10 percent higher; 99.5 percent of joins containing every required branch; and no added operator time. With several teams, include supplier throttling and approval queueing. The release owner reverts on any miss. I don’t know whether the branch is worthwhile until runs clear the bar.

Ask four questions. What consumes an earlier result? What can overlap without a mutable-resource conflict? Can state change the route or stop condition? Can the system detect, explain, and replay a partial failure? I think the answers often produce a hybrid: a linear spine with short research or verification bursts. [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, structured state, and trust controls after selection. Choose the smallest graph that tells the truth about every wait.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Benchmark the linear baseline, promote one bottleneck, and keep only complexity whose measured gain covers its coordination tax.</p></div>
