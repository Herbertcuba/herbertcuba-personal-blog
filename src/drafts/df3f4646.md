AI builders often rank graphs above pipelines. Workflow topology is the arrangement of stages and routes; a linear pipeline is already its smallest graph shape: one ordered path.

I think production asks for the least topology that represents the work truthfully. Every added route brings a scheduling and recovery decision.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose the arrangement of work from real dependencies, not from how sophisticated its diagram looks.</p></div>

## Draw dependencies before topology

Begin with two dependencies. A data dependency means one job consumes another's result. A resource dependency exists when jobs share a mutable resource such as a file, record, workspace, approval, quota, or external system either can change or exhaust. [PostgreSQL, an open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), documents writers waiting on the same record; [Stripe, a payments platform](https://docs.stripe.com/rate-limits), documents separate rate and concurrency limits.

Apply the fake-edge test. If B consumes nothing from A and the jobs share no conflicting write, lock, approval, quota, or external effect, the edge may be artificial even if both read one immutable input. I think teams will mistake concurrent model calls for independent work and discover the dependency during recovery.

Keep a pipeline when sequence is real: ingest → validate schema → apply policy → persist. Use deterministic code for checks, deduplication, routing, and merge completeness. [Temporal, a durable workflow platform](https://docs.temporal.io/workflow-definition), calls reconstructing its Workflow state from event history replay. A retried Activity, the platform's unit of external work, may run again, so side effects need separate controls.

Use a directed acyclic graph, or DAG, when independent jobs fan out concurrently and fan in at a merge, with no route back. A conditional graph chooses its next route from current state. A cyclic graph returns to earlier work, so it needs a stop rule and hard attempt, time, or cost limit. A hybrid wraps a linear backbone around one bounded branch or cycle.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep real sequence linear, branch only independent work, and introduce state-driven routes only when runtime evidence changes what happens next.</p></div>

## Make the merge operational

Branches tax convergence through partial failures, workspace conflicts, service limits, extra calls, and recovery. A join policy states which results are required and what a missing one triggers. I think this contract matters more than fan-out. The critical path is the longest required chain; an all-required merge includes its slowest branch, so concurrency has no fixed speedup. [AWS Step Functions, a managed workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), waits for every branch in a Parallel state before continuing.

A compact state contract makes the decision testable:

```text
run_id: r42
branches:
  market:      {required: true,  status: complete,  retries: 0}
  regulation:  {required: true,  status: running,   retries: 1}
  competitors: {required: false, status: timed_out, retries: 2}
join_policy: all_required
retry_budget: 2
stop_condition: deadline_or_budget
owner: research-service
guard: required_branches_must_be_terminal
```

The guard rejects the merge with `JOIN_REJECTED: required branch regulation is running`. Require an operator-visible run record with every branch ID, immutable input reference, result or error, retry count, and merge decision. Before release, the service owner approves evidence, deadline, recovery, and rollback rules.

Retries that can repeat a charge, message, or write need idempotency: the same logical request retains one intended external effect. [Stripe's API documentation](https://docs.stripe.com/api/idempotent_requests) shows one implementation. For high-risk systems covered by the [European Union's 2024 Artificial Intelligence Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj/eng), Article 12 requires automatic event logging throughout operation. Weak run records are therefore a compliance risk for systems in scope.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Before parallel work enters production, define required results, retry safety, stop rules, rejected state changes, recovery evidence, and one accountable owner.</p></div>

## Earn the hybrid with evidence

Topology is framework-independent. The same shape can run on a durable workflow engine that saves progress, queue workers, or state-machine code. An agent-graph library is one implementation choice.

Ask four questions in the design review:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can current state change the next route or stopping condition?
4. Can the runtime detect and explain a partial failure, then repeat work according to its documented recovery rules?

I think the strongest common production shape is a hybrid: intake and policy stay linear; research fans out into required market and regulation branches plus an optional competitor branch; required results merge before approval. Compare that branch with the linear baseline on latency, accepted evidence, duplicate effects, incomplete merges, recovery time, and cost per successful run.

If independence and a latency need are already proven, the honest starting shape may be a DAG. I don't know which wins before measurement. I think a change is earned when its owner proves the gain beats the tax and can restore the simpler route when a limit is breached.

[“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) covers loop terminology and exit conditions. [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, declared state, and evidence after topology selection. My take: the smallest graph that tells the truth is the advanced architecture.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Measure the straight path, add only routes that improve a declared outcome, and require an owner who can explain, recover, and reverse every added failure path.</p></div>
