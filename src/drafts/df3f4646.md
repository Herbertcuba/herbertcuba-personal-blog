Take the first failed production run and work backward. Which task can be retried alone, what state does it need, and how can the final stage prove nothing is missing? I think those questions reveal the architecture faster than counting agents.

Topology describes how tasks and routes are arranged. A linear pipeline is one ordered path, so it is already a graph. In a July 2026 X article, [graph-engineering writer Anatoli Kopadze](https://x.com/AnatoliKopadze/status/2080668775796314331) captures its limit: “A graph buys breadth. It does not buy better judgment.” The choice is how much breadth the work justifies.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose topology from dependencies and recovery, not from agent count. More routes are useful only when the system can explain and replay the failures they create.</p></div>

## Draw the reasons for waiting

For each task, record its inputs and everything it changes. Consuming an earlier result creates a data dependency. Changing the same mutable resource, such as a file, database row, workspace, or external account, creates a resource dependency even without direct data flow.

The second kind hides easily. [PostgreSQL, an open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), documents a writer waiting on another writer’s record lock. [Stripe, a payments API provider](https://docs.stripe.com/rate-limits), separately limits request rate and simultaneous requests. Apparent parallelism can become contention or queueing.

Apply the fake-edge test: if B does not need A’s result, and both can run without competing over mutable state or a limiting quota, their edge may be artificial. Otherwise, preserve the order. I think a pipeline is strongest when sequence is real because ownership stays visible and replay, rerunning recorded work from a known stage, remains simple. Keep fixed checks and routing in code; use models for judgment.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>An edge can carry data or protect a shared resource. Remove it only when concurrent execution is logically independent and operationally safe.</p></div>

## Make the join a contract

A directed acyclic graph, or DAG, permits branches but no return to an earlier task. Fan-out starts independent work; fan-in merges it. Separate branches might inspect one immutable build for security, licensing, or API compatibility before a release decision.

The merge determines whether that width is governable. [AWS Step Functions, a managed cloud workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), waits for every Parallel branch before continuing. The slowest required branch therefore sits on the critical path, the chain that sets the earliest finish. Jeffrey Dean and Luiz André Barroso’s 2013 systems paper [“The Tail at Scale”](https://www.barroso.org/publications/TheTailAtScale.pdf) explains how waiting across components magnifies latency variation; it is not an agent benchmark.

I think every join needs expected branch identities, a deadline, and a policy for failed or absent results. Retried writes need idempotency, meaning one logical request preserves one intended effect; [Stripe documents a key-based implementation](https://docs.stripe.com/api/idempotent_requests). Preserve provenance so an operator can replay one branch without presenting an incomplete merge as complete. A graph supplies no reliability by itself.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use a DAG when independent work can finish under a clear merge contract. The gain in latency or coverage must beat slow branches and the burden of missing results, retries, quotas, or isolation.</p></div>

## Bend the route only when state changes

A conditional graph chooses the next route from current runtime state. A cyclic graph can revisit an earlier task. They fit a retryable tool error, an evidence score that triggers another check, or an unresolved case that must escalate. If the passes are known before execution, a fixed DAG is clearer.

[LangGraph, an open-source framework for stateful agent workflows](https://docs.langchain.com/oss/python/langgraph/graph-api), documents state-based edges and a configurable limit on looping execution. I think a useful cycle also needs a meaningful stop rule: the system must record what changed, why another pass could help, and what budget ends the attempt.

This is where a hybrid often wins: a linear control backbone containing a short graph-shaped burst. A release flow can validate its request, fan out independent reviews, merge them, then return to ordered approval and persistence. The harder observability and partial-failure logic stays within one boundary.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Conditions and cycles belong where recorded state can change the next action or stopping decision. A bounded graph inside a linear backbone often captures the benefit without spreading coordination everywhere.</p></div>

## Let each extra edge prove its value

Ask four questions in the design review:

1. What must wait because it consumes an earlier result?
2. What can run independently without changing the same mutable resource?
3. Can runtime state change the next route or stopping condition?
4. Can the system identify a partial failure, explain it, and replay the affected work?

I don’t know which topology wins until those answers meet measurements. Track branch duration, throttling, retries, merge completeness, and replay success. I think the progression should be a truthful path, then a proven branch, then dynamic routing only when observed state demands it.

After topology comes the trust problem. [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, declared state, and execution evidence. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper on feedback-loop terminology and exit conditions. Here the rule is narrower: choose the fewest edges that make the work honest.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Start with the real reasons for waiting, widen only after measurement, and add dynamic routes only for real state changes. The right topology is the smallest one that can tell the truth about its work and its failures.</p></div>
