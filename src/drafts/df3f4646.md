Graph tooling makes coordination cheap to draw, but production pays for every arrow through shared state, retries, cost, and ownership.

Workflow topology is the layout of stages and connections. A pipeline is already a graph: one ordered path. Think of a launch sequence versus a fleet engagement: ignition must precede separation, while independent ships can scout, change course, and converge. Turning the launch sequence into a fleet graph only adds mission-control software that can fail.

In [“Graph Engineering explained,”](https://x.com/AnatoliKopadze/status/2080668775796314331) Anatoli Kopadze writes: “A graph buys breadth. It does not buy better judgment.” My take: choose the minimum honest shape and make every added branch or return path prove its value.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose the smallest shape that matches real dependencies; approve branches or loops only when measured benefit exceeds operating cost.</p></div>

## Start with what must wait

Begin with dependencies, not agent count. A data dependency exists when one job consumes another job’s result. Hidden dependencies live in mutable resources, shared state a job can change: a writable file, database record, workspace, service quota, or approval gate. [PostgreSQL, an open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), documents one writer waiting behind another; [Stripe, a payments platform](https://docs.stripe.com/rate-limits), separates request-rate limits from simultaneous-work limits.

Apply the fake-edge test. If B consumes no result from A and they share no mutable resource, their edge may be artificial. Read-only snapshots avoid write conflicts; shared writes do not. I think a design review should reject parallel branching when two branches can both write `customer:42` without isolation, which gives each branch separate state, or serialization, which forces those writes to happen one at a time.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Map consumed outputs and shared resources before selecting a framework; apparent independence disappears when branches contend for the same write, quota, or approval.</p></div>

## Let the route choose the shape

Keep the pipeline when sequence is real: ingest a request, validate its schema (declared data shape), apply policy, then persist the result. Each stage needs the previous result. Replay means rerunning work from recorded inputs, and I think this ordered path is strongest when reconstruction matters. Schema checks, counting, duplicate removal, and fixed routes belong in ordinary code that returns the same result for the same input, not model calls.

Use a directed acyclic graph for genuinely wide work. “Directed” means dependencies point forward; “acyclic” means no route returns to an earlier stage. Fan-out starts independent branches, and fan-in merges them. Five market-angle research branches can run independently before their checked findings merge into one report. Parallel execution can shorten the critical path, the longest required chain of work, but an all-required merge still waits for its slowest branch, as [Amazon Web Services (AWS) Step Functions, a cloud workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), makes explicit.

I think the merge is the real product decision. Its join policy, the rule governing that merge, must name expected branch IDs, required outputs, a deadline, retry limit, the treatment of missing results, and each result’s provenance: its source and history. It may fail the run, retry a missing required branch, or accept results only from branches explicitly marked optional, while recording every absent required branch and its final error. Retried external writes also need [idempotency](https://docs.stripe.com/api/idempotent_requests), a key or rule that prevents one logical attempt from taking effect twice.

A conditional graph chooses the next stage from recorded runtime state, meaning the facts stored for the current run. A cyclic graph can revisit an earlier stage. I think either earns its place only when a state change alters the route or stop rule; if every run always uses two passes, draw two fixed stages instead. For a deeper treatment of returns and exit conditions, see [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/).

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep real sequence linear, use branches for independent breadth, and add a condition or cycle only when current state can change what happens next.</p></div>

## Make complexity prove its value

Before approving a wider shape, record a `run_id`, expected branch IDs, keys naming mutable resources, join policy, retry budget (the attempt cap), stop condition, accountable owner, and failure deadline. Mark the side-effect boundary, the external writes a branch may perform, and require rollback or replay evidence that they will not be duplicated. Compare it with the linear baseline on critical-path latency, completion coverage, the share of runs with every required result, duplicate effects, and cost per successful run.

When recovery dominates, compare foundations rather than drawing more edges. A [durable workflow engine](https://docs.temporal.io/workflow-definition) records execution history so interrupted work can resume; a [state-machine engine](https://states-language.net/spec.html) moves through declared states and transitions; an agent framework coordinates model and tool calls. Prefer the first two when replay, retries, and external writes are harder than model judgment.

I don’t know which shape will win before the measurements exist. I think the usual production default is a hybrid: a linear spine with a bounded research or verification graph. Ask what must wait, what can run without a shared mutable resource, whether state changes the route or stop rule, and whether the system can detect and explain a partial failure, then replay the branch. Once the shape is chosen, [“The 105 minutes after the graph”](/drafts/67821675/) covers evaluation and typed state, a workflow record with declared field types.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep a linear spine and admit only branches or cycles with proven independence, an owner, replay evidence, and measured benefit. The smallest truthful graph is the strongest production default.</p></div>
