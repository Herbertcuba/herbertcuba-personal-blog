# Choose the smallest graph that fits the work

Workflow topology is the shape of stages and their connections. A pipeline is already a graph, one ordered path. Treating graphs as advanced and pipelines as primitive reverses the architecture decision.

Think of a science-fiction launch beside a fleet engagement. The launch stays ordered because each stage enables the next. The fleet needs independent units, state-driven decisions, and convergence. I think making the launch fleet-shaped adds mission-control software that can fail. Choose the smallest topology that tells the truth about the work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Architecture begins with dependencies, not agent count or visible arrows.</p></div>

## Let dependencies choose the shape

Map what each job consumes and changes. B has a data dependency when it needs A’s result. A mutable resource is something jobs can change or exhaust, such as a file, database row, workspace, approval gate, or API quota.

Mutable resources reveal hidden edges. [PostgreSQL, the open-source relational database, documents](https://www.postgresql.org/docs/current/transaction-iso.html) one writer waiting behind another on the same row. Jobs can collide without exchanging outputs, although they may read the same immutable snapshot, a fixed copy neither can change, when no quota or side effect couples them.

Apply the fake-edge test: if B consumes none of A’s output and the jobs share no mutable resource, lock, quota, or side effect, their edge may be artificial. Use deterministic code, which gives the same result for the same input, for validation, counting, deduplication, and fixed routing. I think a pipeline is strongest when the route is known: ingest, validate, apply policy, persist. Its predecessors make ownership and replay easy to trace.

Use a DAG, or directed acyclic graph, for wide work. Its branches cannot return to an earlier stage. Fan-out starts independent jobs; fan-in merges them. Parallel work can shorten the critical path, the longest required chain, but an all-required merge still waits for its slowest branch. [AWS Step Functions, Amazon’s managed state-machine service, specifies](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html) that behavior.

For five independent market angles, I think the merge is the product decision: which results were expected, which arrived, and whether an absence blocks the report. Topology expands coverage; evidence and validation improve judgment.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Sequence belongs in a pipeline. A DAG earns its branches when jobs are independent and every result is accounted for.</p></div>

## Change the route only when state changes

Runtime state is the recorded condition during a run. A conditional graph selects a route from it; a cyclic graph can return to earlier work.

A low evidence score might trigger another source check; a retryable failure might return or escalate. If two passes are known beforehand, model them as ordered DAG stages. I think a cycle earns its place only when state changes the next action, and it needs a stop condition plus a hard limit on attempts, time, or cost.

[“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](/posts/everyone-discovered-loops/) is the deeper piece on feedback-loop terminology, ownership, and exit conditions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Routes and cycles represent decisions that emerge during a run. Planned sequence stays acyclic.</p></div>

## Write down the coordination cost

A graph adds obligations, not automatic reliability. Branches can fail separately, exhaust a shared rate limit, repeat paid calls, or overwrite state. Idempotency means a retry cannot repeat its effect; [Stripe, a payments platform, documents](https://docs.stripe.com/api/idempotent_requests) a key-based API design. Isolation means separate workspaces or coordinated writes prevent collisions.

When replay and side effects dominate, consider a durable state-machine runtime. It persists state, timers, retries, and results so recovery is part of execution. An agent-graph library can route calls, but its edges do not supply durable recovery.

Record the decision in four questions:

| Decision question | What the record must contain |
| --- | --- |
| What must wait? | Consumed inputs, produced outputs, and ordered edges. |
| What can run independently? | Expected branch IDs; mutable-resource keys, the names of shared writes, locks, or quotas; and the expected critical-path gain. |
| Can state change the route or stop? | Route condition; retry budget, the allowed attempts or cost; stop condition; and hard cap. |
| Can partial failure be handled? | Run ID, owner, deadline, and idempotency key. Define the join policy: wait for all, accept a named subset, or fail and escalate. Add replay or rollback evidence, proof that rerunning is safe or an effect is reversible. |

Reject fan-out when two branches can write the same database row without isolation. Start with the smallest truthful topology, usually a pipeline, and measure it. I don’t know whether a branch pays without a baseline. Compare critical-path latency; completion coverage, the share of expected branches returning usable results; duplicate side effects after retries; and cost per successful run. I think a branch without resource independence or measured benefit should fail review.

My take: a hybrid often becomes the production shape after a bottleneck exposes bounded independent work. A linear spine keeps gates visible while research or verification briefly fans out and converges. If required independent calls already break the latency target when serialized, a DAG may be the truthful starting point. [“The 105 minutes after the graph”](/drafts/67821675/) covers evaluation, typed state, and trust after selection.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A branch or cycle needs an owner, real independence or state-driven routing, measured benefit, and replayable failure policy. Graph tooling is cheap to draw; the work must earn its cost.</p></div>
