Teams often choose agents, then make the workflow fit a graph diagram. I think topology should come from what must wait, what may overlap, and what can change route at runtime.

A pipeline is already a graph: one ordered path. A DAG, or directed acyclic graph, can branch and merge but never return to an earlier node. A conditional graph chooses its next edge from current state; a cyclic graph can revisit work. A hybrid puts bounded branches or cycles inside a linear backbone.

In a July 2026 X article on graph engineering, Anatoli Kopadze wrote, “A graph buys breadth. It does not buy better judgment.” I think the correction is useful: wider graphs cover more work, but judgment still needs evidence, validation, and acceptance criteria.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A graph is not an upgrade. It claims which work can overlap or change direction.</p></div>

## First find the real waits

A data dependency exists when one job consumes another’s result. A hidden resource dependency appears when jobs edit one file, update one database row, share an API quota, or await one approval. A mutable resource is anything a job can change. [PostgreSQL, the open-source relational database, shows a concurrent updater waiting on an earlier transaction](https://www.postgresql.org/docs/current/transaction-iso.html). [Stripe, a payment API provider, separates request-rate limits from simultaneous-request limits](https://docs.stripe.com/rate-limits). Shared read-only input creates no write conflict, although capacity may still be constrained.

Kopadze’s second heuristic asks whether two jobs can exist with no edge. In production, B must not consume A’s output, and both must overlap safely without a shared write, lock, quota, or gate. Then the edge may be artificial.

Keep `ingest → validate → apply policy → persist` linear because each stage enables the next. Five independent market-angle searches can fan out, then fan in by merging results. Parallel work shortens only the critical path, the longest required chain; a merge still waits for its slowest required branch. I think schema checks, counts, deduplication, and fixed routes belong in deterministic code, not model calls.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Remove an ordering edge only after ruling out both data dependence and hidden contention.</p></div>

## Make state and failure explicit

The merge turns width into an operating contract. [AWS Step Functions, Amazon’s managed state-machine service, can run branches concurrently and waits for all before continuing](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html). Partial failure means some branches finish while others fail or disappear. Name required and optional branches, deadlines, cancellation, and caught failures. Required branches must succeed; optional ones may be marked absent after their deadline. A late result creates a new immutable merge revision.

Persist `run_id`, `branch_id`, attempt, status, input and output references, idempotency key, deadline, and provenance. Idempotency means retrying the same logical operation cannot repeat its external effect. Permit `pending → running → succeeded | failed | cancelled`; after success, require a new attempt. I think the join deserves more design attention than the fan-out.

A condition belongs where state selects the next route; a cycle belongs where state sends work back. Weak evidence might route to verification, while a recoverable error may return to a bounded retry. [LangGraph, a framework for stateful agent workflows, supports state-based edges and configurable recursion limits](https://docs.langchain.com/oss/python/langgraph/graph-api). Every loop needs a meaningful stop rule and a hard budget.

Mature runtimes can clarify recovery. A retry repeats one failed unit; a resume continues a saved execution; a rerun starts a new execution; and [history replay in Temporal, a durable workflow platform, reconstructs state from recorded events](https://docs.temporal.io/workflow-execution). Topology alone supplies none of these policies.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Branches, joins, conditions, and cycles need persisted state, legal transitions, explicit failure policy, and bounded recovery.</p></div>

## Promote one edge at a time

My take is that many production systems should be hybrids: intake, policy, approval, and persistence stay linear, while research or verification fans out briefly. Isolation means ownership or partitioning for every writable resource, not necessarily a separate workspace; shared quotas still need concurrency control.

Benchmark the linear stage, parallelize one proven-independent job, then compare critical-path latency, cost per successful run, rate-limit responses, required-branch completeness, retries, and replay. I don’t know whether a branch is worth keeping until those measures are visible. Set the rule first: beat the agreed latency or coverage target, stay within budget, and revert if outputs or recovery deteriorate.

A workflow owner approves the change and can roll it back. A merge owner decides whether degraded completion is allowed and budgets human handling for a missing required result. Then ask:

1. What must wait because it consumes an earlier result?
2. What can overlap without touching the same mutable resource?
3. Can runtime state change the route or stopping condition?
4. Can the system detect, explain, and replay a partial failure?

I think those answers should choose the topology, not a framework demo. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) covers loop language and exits. [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, structured state, and trust after topology is chosen.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Start from measured dependencies, promote one bounded section, and keep it only when its operational gain pays for every new edge.</p></div>
