Because a pipeline is already a graph, one ordered path, every extra arrow must explain independence and partial failure. The question is how much topology the work needs.

A launch sequence stays ordered because each stage enables the next; a fleet engagement needs independent units and convergence. Giving the launch a fleet topology only adds mission-control software.

Anatoli Kopadze, author of [“Graph Engineering explained: what it is, when to use it and when not to”](https://x.com/AnatoliKopadze/status/2080668775796314331), a 2026 article on the social platform X, wrote: “A graph buys breadth. It does not buy better judgment.” I think that is right. I don't know whether a branch is worthwhile until its independence and benefit are demonstrated.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A pipeline is the minimum graph. Add topology only for breadth or a state-dependent route.</p></div>

## Start with the dependency map

Map two dependencies before counting agents. A data dependency exists when job B consumes job A's result. A resource dependency exists when jobs can change the same mutable resource, meaning shared state such as a file, database row, or workspace, or share an API quota, a service's request or concurrency cap.

[PostgreSQL, the open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), shows why the hidden kind matters: one transaction waits while another updates or locks the same row. Neither job consumes the other's output, yet the shared write still forces coordination. Branches may safely read one fixed snapshot, but mutation, locks, quotas, and external effects can make apparent parallel work serial.

Apply the fake-edge test: if B consumes no output from A and the jobs share no mutable resource or quota, the edge may be artificial. In ingest request → validate schema → apply policy → persist result, sequence is real. The critical path, the longest required chain, stays obvious, as does replay, a rerun from recorded inputs and state. I think visibility matters in production. Keep validation, counting, deduplication, and routing in code; use models for judgment.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Check data flow and shared resources before removing an edge. Real sequence belongs in a pipeline.</p></div>

## Let breadth earn a branched DAG

A DAG, or directed acyclic graph, can branch but has no directed route back to an earlier node. Fan-out starts independent jobs; fan-in merges them. Five market-angle searches can fan out if inputs and writable state are separate.

The merge makes the architecture real. [AWS Step Functions, Amazon's managed state-machine service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), waits for every required `Parallel` branch before continuing. An all-required join is bounded by its slowest branch, and missing work cannot silently count as complete. The join policy must name expected results and say whether the run fails, retries a branch, or keeps survivors.

Make that contract inspectable by reviewers and code:

```yaml
run_id: market-report-42
expected_branch_ids: [market, regulation, customer, competitor, technology]
mutable_resource_keys: []
join_policy: all_required
retry_budget: 2
stop_condition: all_received_or_10m
owner: research-platform
failure_deadline: 10m
side_effect_boundary: merge_only
replay_evidence: event_log
provenance: per_branch_sources
```

The run ID identifies one execution; branch IDs expose missing work; resource keys expose write conflicts. The join policy and deadline define completion, while retry and stop fields bound repeated work. The owner, write boundary, event log, and sources support recovery and replay.

A retried write needs idempotency, meaning one logical request cannot repeat its effect; [Stripe's payments API documentation](https://docs.stripe.com/api/idempotent_requests) documents this with retry keys. Reject fan-out when two branches can write the same database record without separate writable state or deliberate serialization.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A DAG earns its place when independent work has a governable merge, explicit failure rules, and safe replay.</p></div>

## Add a return only when state changes the route

A conditional graph chooses its next edge from recorded runtime state; a cyclic graph can return to an earlier node. These shapes fit score-based verification, a retryable tool error, or human escalation.

A cycle needs a reason to return, a stop rule, and a hard budget. If the pass count is known in advance, a fixed DAG is clearer. I think a loop earns its place only when state changes what happens next. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](/posts/everyone-discovered-loops/) goes deeper on feedback terms, ownership, and exit conditions.

When replay and duplicate-effect control dominate, [Temporal, an open-source durable workflow engine](https://docs.temporal.io/workflow-definition), shows the stronger foundation: recorded history and replayable control code, with model judgment inside a bounded step.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use a conditional route or cycle only when recorded state changes the next action. Every return needs a reason and a limit.</p></div>

## Keep the control spine visible

My take is to use a hybrid: keep gates and persistence linear, then fan out only bounded research or verification. That localizes the coordination tax: partial failures, resource conflicts, quota pressure, token cost, and debugging.

Measure critical-path latency, required-result coverage, meaning the share of required results received, duplicate effects, and cost per successful run before and after the change. Approve a branch or cycle only when a named owner states its expected gain, resource boundary, failure deadline, side-effect boundary, and replay evidence. I think that threshold is defensible.

Four questions choose the shape:

1. What consumes prior output?
2. What is independent in data and mutable resources?
3. Does state change the route or stop rule?
4. Can partial failure be detected, explained, and replayed?

Start with the smallest truthful topology. Measure the bottleneck, prove resource independence before branching, then add state-dependent routing only when runtime evidence requires it. [“The 105 minutes after the graph”](/drafts/67821675/) covers evaluation, validated state, and trust after selection. In production, every unnecessary edge becomes somebody's responsibility.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep a linear spine and approve extra topology only when measured gains, explicit ownership, and failure controls exceed the coordination tax.</p></div>
