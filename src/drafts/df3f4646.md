A pipeline is already a graph: one directed path through required stages. A directed acyclic graph (DAG) may branch and merge but cannot return to an earlier node. A conditional graph selects its next edge from runtime state; a cyclic graph can revisit earlier work. A hybrid keeps a linear backbone and inserts wider shapes only where needed.

I think the question is: what is the smallest topology that tells the truth about the work? Begin with an ordered path and add branches or returns when evidence demands them.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose topology from the work’s dependencies, not from how sophisticated its diagram appears.</p></div>

## Find the dependencies hidden behind the arrows

List each job’s inputs, outputs, reads, and writes before counting agents. A data dependency exists when one job needs another’s output. A resource dependency exists when jobs share something mutable, such as a file, database row, workspace, approval gate, or limited external service.

[PostgreSQL, an open-source database, documents](https://www.postgresql.org/docs/current/transaction-iso.html) one writer waiting for another, while [Stripe, a payments API provider, separates](https://docs.stripe.com/rate-limits) request-rate limits from active-request limits. A shared immutable snapshot creates no such conflict because neither job changes it.

Apply the fake-edge test in both directions. If B does not consume A’s result and they share no write, lock, quota, or approval, the A-to-B edge may be invented. I think an edge without a concrete dependency is usually serial waiting disguised as architecture.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Map data flow and shared resources before deciding which work can run at the same time.</p></div>

## Use a chain for dependence and branches for breadth

A pipeline fits this flow: ingest a request → validate its schema → apply policy → persist the result. Each stage enables the next, so route, owner, retry, and replay remain visible. Keep schema checks, counts, duplicate removal, and fixed routing in deterministic code; reserve AI models for judgments that need interpretation. I think an ordered path is strongest when sequence is part of correctness.

When work is genuinely wide, fan-out starts independent jobs and fan-in merges their outputs. Five market-angle jobs can run concurrently, then merge verified findings into one report. [AWS Step Functions, Amazon’s managed workflow service, documents](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html) parallel branches that run concurrently, while an all-required merge waits for every branch. The slowest required branch therefore sets the earliest merge time.

Parallelism pays only if it shortens the critical path, the longest required chain before output is ready. The merge needs branch IDs, schema, deadline, failure policy, and provenance, the record of each result’s source and process. A retried external effect also needs [idempotency](https://docs.stripe.com/api/idempotent_requests), so the same logical attempt does not duplicate it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use a DAG for independent breadth only when the merge and its failures have an explicit contract.</p></div>

## Add a return path when state redirects the work

Runtime state records outputs, errors, scores, and approvals. Use a conditional route when that record chooses the next node, such as sending a failed policy check to a human. Use a cycle when changed state sends work back after a retryable error or failed acceptance test.

A known number of passes belongs in a fixed DAG. [LangGraph, an open-source framework for stateful agent workflows, documents](https://docs.langchain.com/oss/python/langgraph/graph-api) conditional edges, loops, and an execution limit, but availability is not justification. I think a cycle earns its place only when changed state explains the return, while a stop rule and hard cap explain the exit.

The companion essay [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper into loop terminology, ownership, and exit conditions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Add conditions or cycles only when runtime state can change the route or the stopping point.</p></div>

## Price the coordination before widening the workflow

Every branch adds failure policy, safe retries, isolated writes, quota-aware scheduling, logs, and repeated model context or tool calls. In a partial failure, some branches finish while another does not. The merge must expose that gap, and provenance must show what survived and why.

I don’t know whether wider execution will repay that bill in a particular system. Measure the serial bottleneck, branch durations, throttling, retries, merge completeness, and replay success. I think production often favors a hybrid: keep intake, policy, approval, and persistence on a linear backbone, then contain research or verification inside a bounded fan-out/fan-in section.

Before adding another edge, ask:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can runtime state change the next route or stopping condition?
4. Can the system detect, explain, and replay a partial failure?

My take: keep the pipeline when sequence dominates; branch when independent work shortens the measured critical path and missing results are governable; add a condition or bounded cycle when state changes the route. [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, typed state, and trust controls after topology is chosen. The strongest architecture is the smallest topology that tells the truth.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Let measured breadth and changing state earn complexity; keep everything else on the clearest path.</p></div>
