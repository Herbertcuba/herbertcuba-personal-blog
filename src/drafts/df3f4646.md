# When your AI workflow actually needs a graph

Workflow topology is the arrangement of stages and connections. A pipeline is already a graph: the simplest topology, one ordered path. Each extra arrow becomes a production dependency and replay path.

Picture a science-fiction launch beside a fleet engagement. Launch stages stay ordered because each enables the next; a fleet needs independent units, changing routes, and convergence. I think maturity means matching topology to work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose one ordered path unless dependencies require independent branches or state-driven returns.</p></div>

## Start with data and resource dependencies

A data dependency means consuming another job’s output. A mutable resource is shared state a job can change or exhaust: a file, database row, workspace, approval gate, or API quota. Jobs may share no output yet collide. [PostgreSQL, a relational database, documents](https://www.postgresql.org/docs/current/transaction-iso.html) one writer waiting on another over the same row.

B passes the fake-edge test when it consumes none of A’s result and shares no writable resource or quota. The edge may be artificial. A read-only snapshot creates no write conflict. I think separate prompts do not prove operational independence.

A pipeline fits real sequence: ingest, validate schema, apply policy, persist. Its known route makes targeted replay easier to inspect. I think visible order is a production strength. Validation, counting, deduplication, and fixed routing belong in deterministic code, where equal inputs produce equal outputs; models are for judgment.

A DAG, or directed acyclic graph, fits wide work because it can branch without returning to an earlier stage. Fan-out starts independent jobs; fan-in merges them. Five market angles fit, but an all-required merge waits for the slowest branch. It can bound the critical path, the longest required chain. [AWS Step Functions, Amazon’s managed workflow service, specifies](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html) this wait. I think the merge defines which results count and what absence means.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A pipeline preserves sequence. DAG branches need data and resource independence plus a defined merge.</p></div>

## Let runtime state change the route

Runtime state records a run’s condition. A conditional graph chooses the next stage from it; a cyclic graph can revisit an earlier stage. Both fit when the route or stopping point cannot be fixed beforehand.

Low evidence might trigger another source check; a retryable error might return work until its budget expires, then escalate. I think a cycle earns its place only when changed state affects the next action, with a meaningful stop condition and hard cap on attempts, time, or cost. Two preplanned reviews remain ordered stages.

[“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](/posts/everyone-discovered-loops/) goes deeper into loop terminology, ownership, and exits. Here, a return edge needs a state-based reason and evidence for when to stop.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>State-driven decisions justify conditional routes and cycles. Every return edge needs a reason, a stop condition, and a hard budget.</p></div>

## Make the coordination tax explicit

More edges alone do not create resilience. A partial failure leaves some branches complete and others missing. A side effect is an external change, such as a write or charge; idempotency lets a retry avoid repeating it. [Stripe, a payments platform, documents](https://docs.stripe.com/api/idempotent_requests) one implementation using idempotency keys.

A decision record turns the diagram into an operating contract:

```yaml
run_id: <unique execution>
topology: pipeline | dag | conditional | cyclic | hybrid
expected_branch_ids: [...]
mutable_resource_keys: [...]
join_policy: <required branches; missing-result action>
retry_budget: <attempts; time; cost>
stop_condition: <recorded exit state>
owner: <accountable owner>
failure_deadline: <time before escalation>
idempotency_key: <side-effect identity>
replay_or_rollback_evidence: <trace or reversal proof>
```

Resource keys identify shared writable objects; the join policy defines required branches and missing-result handling. Fan-out fails review when two branches can write the same database record unless each uses an isolated copy that prevents races, or every write passes through one ordered writer.

The merge retains branch identity and source provenance: which branch and evidence support each result. I don’t know if a branch pays without a baseline. The review compares critical-path latency, completion coverage, duplicate effects, and cost per successful run before and after topology changes; coverage is the share of expected branches returning usable results.

When replay and side effects dominate, a durable workflow engine fits better: it persists execution state and resumes explicit transitions after failure. My take is that production usually needs a hybrid: a linear spine for intake, policy, approval, and persistence, with bounded research or verification fan-out and convergence.

Four questions close the review. What must wait for an earlier result? What can run without touching the same mutable resource? Can state change the route or stop? Can the system detect, explain, and replay partial failure? [“The 105 minutes after the graph”](/drafts/67821675/) covers evaluation, typed state constrained by a declared schema, and trust controls.

A branch or cycle passes review only with a named owner, a real independence or state-change case, a measurable target, a failure deadline, and replay evidence. Otherwise it adds unnecessary coordination.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Extra topology needs an owner, resource identities, join rules, bounded retries, replay evidence, and measured benefit. Blank fields disqualify the edge.</p></div>
