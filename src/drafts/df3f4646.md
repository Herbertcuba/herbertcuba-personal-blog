A launch sequence and a fleet engagement need different shapes. Ignition, stage separation, and orbital insertion stay ordered because each enables the next. Fleet units can move independently, respond to conditions, and converge. Turning a launch into a fleet graph adds mission-control complexity.

A pipeline is a graph topology: one ordered path through connected stages. I think the question is the minimum topology that matches the work. In a [January 2026 graph-engineering essay](https://x.com/AnatoliKopadze/status/2080668775796314331), software builder Anatoli Kopadze wrote: “A graph buys breadth. It does not buy better judgment.” I don't know if a branch belongs until its operational independence is clear.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose topology from real dependencies, independent work, and runtime decisions.</p></div>

## Map the dependencies before choosing the shape

Begin with data dependencies: B waits when it consumes A's result. Then map resource conflicts. A mutable resource is shared state a task can change: a file, database row, writable workspace, approval gate, or external account. Jobs may exchange no output yet conflict. [PostgreSQL, an open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), shows one writer waiting when another locks or updates the same row.

Isolation gives each branch its own writable copy or unique resource key. Otherwise, serialization makes shared writes take turns in a declared order. Read-only input can be safe, but an API quota or external write can still couple jobs.

Apply the fake-edge test. If B does not consume A's output and both can run without sharing a mutable resource, lock, quota, or external write, their edge may be artificial. I think this beats counting agents: it exposes false sequence and unsafe parallelism.

Keep a linear pipeline when sequence is real. Ingest request → validate schema → apply policy → persist result forms one path because each stage needs prior output. The known path clarifies ownership; replay reruns work from recorded inputs and state. Use deterministic code for validation, counting, deduplication, and routing; reserve models for judgment.

A directed acyclic graph, or DAG, permits branches but no path back to an earlier node. Fan-out starts independent branches; fan-in merges them. This can shorten the critical path, the longest required chain, but promises no fixed speedup. [AWS Step Functions, Amazon's managed workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), waits for every branch in an all-required parallel step, so the slowest branch holds the merge.

Suppose the expected branches are `market`, `regulation`, `customer`, `competitor`, and `technology`. If `customer` is missing at the deadline, the join policy, the rule governing the merge, must fail the run, retry that branch, accept named survivors, or escalate. I think the merge is the real architecture decision. For retried writes, idempotency means repeat requests do not duplicate the effect; [Stripe, a payment processor](https://docs.stripe.com/api/idempotent_requests), documents keys for that purpose.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep real sequence linear; branch only when work and writable resources are independent and the merge handles missing results.</p></div>

## Add routes and returns only when state changes

A conditional graph chooses its next edge from recorded runtime state: the current run's facts. A cyclic graph can revisit an earlier node. Use either when evidence, errors, or approvals change the next action: an unsupported claim returns to research, while a retryable tool error triggers a bounded retry.

I think a return needs a relevant state change and a stop rule capped by steps, time, or cost. If every run uses two passes, draw two DAG stages. The companion article [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](/posts/everyone-discovered-loops/) explores feedback-loop terminology, ownership, and exit conditions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use conditions and cycles only for state-dependent routes, with a reason to return and a firm stop rule.</p></div>

## Put the operating contract before the graph

Graphs introduce partial failures, merge rules, quotas, extra model calls, and harder replay; topology alone adds no reliability. If recovery and safe write retries dominate, a durable workflow or state-machine engine may be a better foundation than an agent framework. [Temporal, an open-source durable workflow engine](https://docs.temporal.io/workflow-definition), records workflow history so control state can be rebuilt after interruption.

I think the production default is a hybrid: a linear control spine for intake, policy, approval, and persistence, with a bounded fan-out or state-based section for research and verification. Review it with four questions: What must wait for an earlier result? What can run without a shared mutable resource? Can state change the next route or stop condition? Can a partial failure be detected, explained, and replayed? Record the answers in an operating contract:

```yaml
run_id: market-report-42
expected_branch_ids: [market, regulation, customer, competitor, technology]
mutable_resource_keys: []
join: {policy: all_required, failure_deadline: 10m}
retry_budget_per_branch: 1
stop_condition: complete_or_fail
owner: research-platform
side_effect_boundary: merge_only
replay_evidence: durable_branch_inputs_and_outputs
```

The side-effect boundary marks allowed external writes. If two branches can both write `customer:42`, reject fan-out until they get separate keys or their writes are serialized. Compare the linear baseline with the proposal on critical-path latency, completion coverage (the share of runs that finish with every required result), duplicate external effects, and cost per successful run. Approve a branch or cycle only when its named owner can show independence, a failure deadline, replay evidence, and a measured benefit.

Once the topology is chosen, the companion article [“The 105 minutes after the graph”](/drafts/67821675/) covers evaluation, typed state (workflow state whose fields have declared data types), and trust controls. Every extra route needs an owner and evidence that it deserves to stay.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prefer a linear spine with bounded graph sections whose owner can prove failure controls, replay, and measured benefit.</p></div>
