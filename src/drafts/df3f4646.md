# Choose the smallest workflow topology that tells the truth

I think “pipeline or graph?” hides the real decision. A pipeline is already a graph with one directed path. A directed acyclic graph (DAG) can branch and merge but cannot return; a cyclic graph can revisit earlier work.

In [“Graph Engineering explained”](https://x.com/AnatoliKopadze/status/2080668775796314331), an X article on graph-shaped workflows, Anatoli Kopadze writes: “A graph buys breadth. It does not buy better judgment.” For production, separate precedence, meaning what must wait, from runtime route selection and admission control, which limits ready work when capacity is scarce.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose precedence, runtime routing, and resource admission separately, then use the smallest topology that expresses the work.</p></div>

## Draw precedence before adding width

Precedence begins with consumed outputs or authorizations. In ingest request → validate schema → apply policy → persist result, each stage needs the preceding result. I think visible order is a production strength because ownership, retries, and replay stay easy to inspect.

Kopadze’s second prompt is the fake-edge test: “If you cannot find two jobs with no edge between them, there is no graph to build.” Two market-angle jobs can read one immutable request and write separately. Since neither consumes the other’s result, there is no fixed A → B edge.

Shared resources still need controls. A provider quota can use a [semaphore, a counter that limits simultaneous work](https://docs.python.org/3/library/asyncio-sync.html#asyncio.Semaphore), without inventing an edge. If both jobs update one customer row, a transaction with the appropriate row lock or isolation level, or a per-customer queue, can coordinate writes. Resource control may restrict concurrency without changing the logical graph.

Keep schema checks, duplicate removal, counting, and fixed routing deterministic. Use models only for judgment.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Edges express required order; quotas and shared writes need separate controls rather than artificial A-to-B dependencies.</p></div>

## Design the join before the fan-out

Fan-out starts independent branches; fan-in merges their results. Five jobs can research market angles from one read-only snapshot, then feed a report merge. [AWS Step Functions, Amazon’s managed workflow service, documents a Parallel state that waits for every branch to terminate](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html). An all-required merge finishes after its last required branch.

I think the join is the real architecture decision. Record branch identities, required and optional results, output schema, and provenance: the inputs, sources, models, and tools behind each output. Define deadlines, cancellation, and idempotency, meaning a retry does not repeat its intended external effect. Then declare finalization and late-result policy.

```text
required=[angle-1, angle-2] optional=[angle-3]
31s angle-1#1 completes
32s duplicate angle-1#1 -> reject complete-to-complete transition
60s angle-2#1 times out -> retry; request angle-3 cancellation
78s angle-2#2 completes
79s merge revision=1 final inputs=[angle-1, angle-2] missing=[angle-3] degraded=true
82s angle-3 arrives late -> audit only; revision=1 remains final
```

This trace is illustrative and uses a custom tolerant merge, not the AWS Parallel state’s default. In the 2013 peer-reviewed article [“The Tail at Scale”](https://www.barroso.org/publications/TheTailAtScale.pdf), Google researchers Jeffrey Dean and Luiz André Barroso show how one request waiting across many components magnifies delays. This warns against generic speed promises; it is not an AI-workflow benchmark.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Parallelize only independent work, and define the result of timeout, retry, duplicate completion, cancellation, and late arrival beforehand.</p></div>

## Let state earn conditions and cycles

Conditional routing means runtime state selects the next edge, but the graph can remain acyclic. A risk result may send a request to automatic approval or human review without returning. A cycle revisits earlier work, as in verify → revise → verify. If two passes are fixed in advance, two DAG stages describe them more clearly.

I think a return edge earns its place only when changed state can alter the next attempt. Give it a stop rule and a hard step or cost limit. [LangGraph, a framework for stateful workflows, documents state-selected edges and a recursion limit](https://docs.langchain.com/oss/python/langgraph/graph-api). [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper on loop terminology and exit conditions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A condition selects a route; a cycle adds a return path, and every return needs both changed state and a bounded stop.</p></div>

## Promote the hybrid with evidence

A hybrid keeps a linear control spine with short graph-shaped bursts. I think that is often the strongest production default: intake, policy, approval, and persistence stay ordered while research or verification fans out. The burst must still pay for join state, retries, write isolation, quotas, traces, model tokens, and operator time.

Run one representative workload through the linear baseline and candidate, then inject the failures the join promises to handle. Replace every placeholder before the test begins and save the decision beside the workflow:

```yaml
baseline: linear/current-release
candidate: hybrid/research-fan-out
cohort: {runs: set-before-test, routes: representative, window: fixed-dates}
budget: {setup-hours: set-before-test, operating-cost-cap: set-before-test}
inject: [required-timeout, duplicate-completion, optional-late-arrival]
measure: [p95-elapsed, cost-per-success, completeness, operator-minutes, replay-success]
owner: named-release-owner
approver: named-architecture-owner
disable-switch: research-fan-out
accept-if: all-predeclared-thresholds-pass
rollback-if: any-threshold-fails
```

P95 elapsed time is the point under which 95 percent of runs finish. No framework can choose your sample or acceptance thresholds; lock them before results. I don’t know whether a branch earns its place until this record beats its baseline without weakening completeness or recovery.

Ask four questions: What must wait for an earlier result? Which jobs can run independently as separate branches, and what controls protect shared resources? Can runtime state choose another edge or return? Can the system detect, explain, and replay a partial failure? After topology is chosen, [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, typed state, and the trust controls that follow.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep the linear spine, bound each graph-shaped burst, and retain complexity only when measured benefit pays the coordination cost.</p></div>
