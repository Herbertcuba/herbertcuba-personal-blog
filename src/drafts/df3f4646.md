# Choose the smallest graph that fits the work

Agent-workflow tools make complex diagrams easy. Workflow topology is the shape of stages and dependencies, and a pipeline is already a graph: one ordered path. Which shape fits the work?

Think of a science-fiction launch beside a fleet engagement. Each launch stage enables the next, while the fleet needs independent units, changing routes, and a rendezvous. I think making the launch fleet-shaped adds mission-control software without widening the work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Start with the minimum topology, then demand evidence for every added branch, route, or cycle.</p></div>

## Let dependencies choose the shape

Map what each job consumes and changes. A data dependency means one job needs another’s output. A mutable resource is shared state or capacity: a file, database row, approval gate, or API quota that jobs can alter, occupy, or exhaust. A side effect is an external change, such as a database write or paid call; a lock prevents concurrent changes.

An edge connects dependent jobs. If B does not need A’s output and they share no mutable resource or side effect, the edge may be artificial. Both may read an immutable snapshot, a fixed copy neither changes. [PostgreSQL, an open-source database, documents](https://www.postgresql.org/docs/current/transaction-iso.html) one writer waiting when another changes or locks the same row.

Keep a pipeline when sequence is real: ingest, validate, apply policy, then persist. Each stage has a known prior stage and owner. Replay means rerunning a recorded workflow from a known state, so inputs and the recovery point remain easy to inspect. Put validation, counting, deduplication, and fixed routing in deterministic code, which gives the same result for a given input. I think visible order is often stronger in production.

Use a DAG, or directed acyclic graph, for wide work. It can branch, but no directed route returns to an earlier stage. Fan-out starts independent jobs; fan-in merges their results. Parallel work can shorten the critical path, the longest required chain, but an all-required merge still waits for its slowest branch. [AWS Step Functions, Amazon’s workflow service, specifies](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html) that wait. For five market angles, I think the merge decides what must arrive and what absence means.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep sequence in a pipeline. Add DAG branches only when jobs neither consume each other’s output nor conflict over mutable resources; make the merge account for every result.</p></div>

## Let recorded state change the route

Runtime state is the recorded condition of a run. A conditional graph chooses its next stage from that state; a cyclic graph can return to an earlier stage. Use them when neither route nor stopping point can be fixed beforehand.

Low evidence can trigger another source check. A retryable error can send work to a named earlier stage until its retry budget, the allowed attempts, is exhausted, then to a human owner. Two planned passes remain ordered DAG stages. I think a cycle belongs only when a recorded change affects the next action, with a stop condition that says when to exit and a hard cap on attempts, time, or cost.

[“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](/posts/everyone-discovered-loops/) explains feedback-loop terminology, ownership, and exits.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Runtime decisions earn routes or cycles. Return paths need destinations, retry budgets, and bounded stop rules.</p></div>

## Make coordination earn its place

A partial failure means some branches finish while others fail. Safe retry needs idempotency: a stable key marks the same intended effect, avoiding a second write or charge. [Stripe, a payments platform, documents](https://docs.stripe.com/api/idempotent_requests) this pattern. When replay and external writes dominate, use a durable workflow engine, a state-machine runtime that stores state so an interrupted run can resume. An agent-graph library can choose the next model or tool call, but arrows alone do not preserve recovery state.

Record: `run_id` identifies one execution; `expected_branch_ids` lists expected branches; `mutable_resource_keys` names shared writes, locks, or quotas; and `join_policy` says whether to wait for all, accept a named subset, or fail. Add the accountable `owner`; `failure_deadline`, when unresolved work escalates; allowed `retry_budget`; cycle `stop_condition`; stable `idempotency_key`; and `replay_or_rollback_evidence` proving safe repetition or reversal.

Refuse fan-out when two branches can write the same database record without isolation, meaning separate state or coordination that prevents collision. I don’t know whether a branch pays without a baseline. Measure before and after: critical-path latency, completion coverage (the share of expected branches with usable results), duplicate effects, and cost per successful run. I think a branch without resource independence or measured benefit should fail architecture review.

My take: production often fits a hybrid, with a linear spine and bounded graph bursts for research or verification. Ask what must wait, what can run without touching the same mutable resource, whether runtime state changes the route or stop rule, and whether a partial failure can be detected, explained, and replayed. [“The 105 minutes after the graph”](/drafts/67821675/) covers evaluation and trust controls after selection.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Approve branches or cycles only with an owner, real independence or state change, a measurable target, and replay evidence. The work must earn every edge.</p></div>
