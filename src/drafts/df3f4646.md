# Choose the smallest workflow topology that tells the truth

I think “pipeline or graph?” hides the architecture decision. A pipeline is already a graph with one directed path. A directed acyclic graph (DAG) may branch and merge but has no return path, while a cyclic graph can revisit earlier work.

Anatoli Kopadze’s [“Graph Engineering explained”](https://x.com/AnatoliKopadze/status/2080668775796314331), an X article on graph workflows, says: “A graph buys breadth. It does not buy better judgment.” Production design has three layers: precedence says what waits, route selection lets state choose the next step, and admission control limits ready work when capacity is scarce. Choose them separately.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A pipeline is a graph. Choose required order, runtime routes, and capacity controls separately.</p></div>

## Draw required order first

In ingest request → validate schema → apply policy → persist result, every stage consumes the prior result or authorization. A straight pipeline keeps ownership, retries, cost, and replay easy to inspect.

Kopadze’s fake-edge prompt is: “If you cannot find two jobs with no edge between them, there is no graph to build.” Two market-angle jobs can read the same immutable request and write separately. Neither consumes the other’s result, so there is no A → B edge.

Capacity is a separate concern. A [semaphore, a counter that limits simultaneous work](https://docs.python.org/3/library/asyncio-sync.html#asyncio.Semaphore), can enforce a provider’s concurrency limit. If both jobs update one customer record, they share a mutable resource: state either can change. A [transaction that locks the row](https://www.postgresql.org/docs/current/transaction-iso.html) or a per-customer queue can coordinate access. The runtime may serialize access without creating A → B precedence.

I think the test must remain two-part: Does B need A’s result? If not, can the runtime admit both safely? Encoding every quota as an edge serializes independent work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Edges express required order; admission controls govern safe access to shared capacity and state.</p></div>

## Design the join before the fan-out

Fan-out starts independent branches; fan-in merges their results. Five jobs can research separate market angles from one read-only snapshot and feed one report. [AWS Step Functions, Amazon’s managed workflow service, documents a Parallel state that waits for every branch to terminate](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html). That is an all-required join.

I think the join is the production decision. Persist branch identities, required and optional results, schemas, and provenance, meaning the inputs, sources, models, and tools behind each output. Define deadlines, cancellation, and idempotency, meaning a retry has the same intended external effect.

```text
required=[angle-1, angle-2] optional=[angle-3]
31s angle-1#1 complete
32s duplicate angle-1#1 -> reject
60s angle-2#1 timeout -> retry; request angle-3 cancellation
78s angle-2#2 complete
79s merge revision=1 inputs=[angle-1, angle-2] missing=[angle-3] degraded=true
82s angle-3 late -> audit only; revision=1 stays final
```

This tolerant merge is illustrative, not the AWS Parallel state’s default. In the 2013 peer-reviewed article [“The Tail at Scale”](https://www.barroso.org/publications/TheTailAtScale.pdf), Google researchers Jeffrey Dean and Luiz André Barroso model 100 parallel components, each with a one-percent chance of exceeding one second; 63 percent of requests that wait for all 100 then exceed one second. It is not an AI-workflow benchmark, but it shows why a full join inherits its slowest required branch.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Parallelize only after timeout, retry, cancellation, missing-result, finalization, and late-result behavior are explicit.</p></div>

## Let runtime state earn conditions and cycles

Conditional routing lets current state select the next edge and can remain acyclic. A risk result may choose automatic approval or human review. A cycle adds a return path, such as verify → revise → verify; two fixed reviews fit two DAG stages.

I think a return edge earns its place only when changed state can alter the next attempt. Give every cycle a stop rule and a hard step or cost limit. [LangGraph, a stateful-workflow framework, documents state-selected edges and a recursion limit](https://docs.langchain.com/oss/python/langgraph/graph-api). [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper on loop terms and exits.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A condition chooses a route; a cycle returns and needs changed state, a stop rule, and a budget.</p></div>

## Promote the hybrid with a replayable test

A hybrid is a linear control spine with short graph-shaped bursts. I think it is often the strongest production shape: intake, policy, approval, and persistence stay ordered while research or verification fans out. The burst still pays for failures, join state, safe retries, separate writes, quotas, traces, tokens, and operator time. Workflow engines can provide retries and error handling, but cannot choose the missing-branch policy.

Use one release decision record, filled before the test:

```yaml
decision: hybrid/research-fan-out
workload: {cases: frozen-representative-set, size: predeclared, dates: fixed}
run: "each case through linear baseline and hybrid candidate; repeat with injections"
budget: {setup-hours: predeclared, review-hours: predeclared, cost-cap: predeclared}
inject: [required-timeout, duplicate-completion, optional-late-result]
measure: [p95-elapsed, cost-per-success, completeness, operator-minutes, replay-success]
owners: {release: named, merge-policy: named, budget: named}
accept-if: all-predeclared-bars-pass
rollback-if: any-bar-fails
disable-switch: research-fan-out
```

Lock the record before testing and retain the candidate only if every bar passes. Separate a branch retry from replaying the frozen case end to end. P95 elapsed time is the point under which 95 percent of runs finish. I don’t know whether width earns its place until the candidate beats the baseline without weakening completeness or recovery.

Four questions choose the shape: What must wait? What can run independently with separate resource controls? Can runtime state choose another route or return? Can the system detect, explain, and replay a partial failure? Afterward, [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, typed state, and trust controls. Choose the smallest graph that tells the truth, then make every extra edge prove why it exists.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep a linear spine and retain each bounded burst only when a predeclared test shows its benefit exceeds the coordination tax.</p></div>
