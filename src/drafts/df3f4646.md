AI builders often treat a graph as advanced and a pipeline as primitive. That is a false choice. A straight pipeline is already the simplest graph topology: one ordered path through stages and connections.

I think the production question is how little topology can express the work honestly. Every additional route must be scheduled, observed, retried, and recovered, while adding no model judgment by itself.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose topology by the work’s dependencies, not by how advanced the diagram looks.</p></div>

## Start with real dependencies

A data dependency exists when one job consumes another job’s result. A resource dependency exists when jobs can conflict through a mutable resource, meaning a shared file, database record, workspace, approval, or service quota that either job can change or exhaust. [PostgreSQL, an open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), documents concurrent writers waiting on the same record; [Stripe, a payments platform](https://docs.stripe.com/rate-limits), documents separate rate and concurrency limits.

Apply the fake-edge test. If B consumes nothing from A, and the jobs share no conflicting write, lock, approval, quota, or external effect, the A → B edge may be artificial. Both can read the same immutable input because neither changes it. I think separate model calls prove neither independence nor safe concurrency.

Use deterministic code for schema checks, counting, deduplication, routing rules, and merge-completeness checks. Reserve models for judgment.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Map consumed outputs and shared mutable resources before counting agents or drawing edges.</p></div>

## Choose the minimum truthful shape

Keep a straight pipeline when sequence is real: ingest a request → validate its schema → apply policy → persist the result. Replay means reconstructing workflow state from recorded history, which differs from retrying an external action. [Temporal, a durable workflow platform](https://docs.temporal.io/workflow-definition), documents that distinction. If a retry may repeat a write, use idempotency, which gives the same logical request the same intended effect, or reconciliation, a check against the external system after an uncertain action.

Use a directed acyclic graph, or DAG, when independent work can fan out into concurrent branches and later fan in at a merge, with no route back to an earlier stage. When every result is required, the critical path, or longest required chain, includes the slowest branch. [AWS Step Functions, a managed workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), documents this all-branch wait. I think breadth can earn a DAG, but speed does not arrive automatically.

A conditional graph selects the next route from current workflow state. A cyclic graph can return to earlier work, so it needs a meaningful stop rule and a hard attempt, time, or cost limit. A hybrid keeps a straight control spine around one bounded branch or cycle. I think that is usually the strongest production shape.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use a straight path for real sequence, a DAG for independent breadth, and state-driven routes only when runtime evidence changes the next move.</p></div>

## Write the merge contract first

The coordination tax appears as partial failures, workspace conflicts, quotas, extra model calls, and harder recovery. A join policy states which branch results a merge requires. A trace is a per-run record of each branch’s path, inputs, outputs, errors, and retries. I think this contract matters more than the fan-out.

Consider a hybrid flow: intake and policy gates remain linear, while research branches into market, regulation, and competitor checks. Market and regulation are required; the competitor branch is optional. The following is framework-neutral pseudocode, not a vendor format:

```text
run: r42
branches:
  market:      {required: true,  status: complete, retries: 0}
  regulation:  {required: true,  status: running,  retries: 1}
  competitors: {required: false, status: timed_out, retries: 2}
join_policy: all_required
retry_budget: 2
stop_condition: deadline_or_budget
owner: research-service
guard: reject_merge_if_required_branch_is_not_terminal
```

The guard rejects this merge because regulation is still running, and the trace should show that reason to an operator. Before production, the service owner must approve the deadline, retry and recovery rules, required evidence, and rollback to the previous straight route.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Define branch identities, required results, retries, stop rules, illegal transitions, and ownership before fan-out enters production.</p></div>

## Promote topology with evidence

Topology is framework-independent. The same shape can run on a durable workflow engine, queue workers, or state-machine code; an agent-graph library is one implementation choice.

Ask four questions in the design review:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can current state change the next route or stopping condition?
4. Can the system detect, explain, and replay a partial failure?

Baseline the straight route, test one bounded alternative, then compare critical-path latency, accepted evidence, duplicate effects, incomplete merges, recovery success, and cost per successful run. I don’t know which shape wins before measurement. I think a change is earned only when its named owner can show that the gain beats the coordination tax and can explain how to roll it back.

For deeper treatment of cycles, [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) explains loop terminology and exit conditions. Once topology is chosen, [“The 105 minutes after the graph”](/drafts/67821675/) examines evaluation, declared state, and the evidence needed to trust a run. Teams that mistake concurrent model calls for independent work will discover the difference during incident recovery, when every unearned edge becomes an unowned failure path.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Measure before promotion, govern partial failure, and choose the smallest graph that tells the truth about the work.</p></div>
