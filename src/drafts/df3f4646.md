Calling a pipeline primitive confuses visual complexity with architectural maturity. A pipeline is itself a graph: tasks, called nodes, connected by directed edges along one ordered path. The production question is how many branches, joins, conditions, and return edges the work actually needs.

I think topology should follow dependencies, not agent count. More arrows create more execution states; they do not improve model judgment by themselves.

```text
Pipeline       A → B → C
Branched DAG   A → {B, C} → D
Cycle          A → B → A, until a stop rule is met
Hybrid         A → {B, C} → D → E
```

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose the smallest shape that represents the work honestly.</p></div>

## Draw the real edges

A data dependency is obvious: B waits because it consumes A’s result. A resource dependency is easier to miss. Two tasks with separate inputs may still collide through a mutable resource, meaning a shared file, database row, workspace, approval gate, or quota that either task can change or exhaust.

The official [PostgreSQL transaction documentation](https://www.postgresql.org/docs/current/transaction-iso.html) explains that a second database update can wait when another transaction has changed or locked the same row. [Stripe’s payment API documentation](https://docs.stripe.com/rate-limits) distinguishes request-rate limits from concurrent-request limits. Prompt independence is not operational independence.

I think the useful test is simple: if B does not consume A’s output, and A and B share no mutable resource or constrained service, the edge may be fake. Reading the same immutable snapshot does not create a conflict.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Check both data flow and hidden conflicts over writes, workspaces, approvals, and service limits.</p></div>

## Let the route choose the shape

Keep a pipeline when every stage enables the next. Ingest request → validate schema → apply policy → persist result is honestly linear. I think this ordered route is strong in production because replay, cost, and ownership remain easy to inspect.

Use a branched DAG, a directed graph with no route back to an earlier node, when work is genuinely wide. Fan-out starts independent branches; fan-in merges them. Five market-angle research jobs can run separately, but the merge still needs their identified outputs. [AWS Step Functions, a cloud workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), specifies that its parallel state waits for every branch to finish. Parallel work can remove serial waiting, yet a full join still inherits its slowest required branch and any queueing.

Choose a conditional graph when current state selects the next route, and a cyclic graph when a route may revisit earlier work. A retry, refinement, or escalation cycle needs a meaningful stop condition and a hard budget. [LangGraph’s official framework documentation](https://docs.langchain.com/oss/python/langgraph/graph-api) makes state-based edges and execution limits explicit.

At a high level, a Content Engine shows the hybrid shape:

```text
brief → [bounded evidence branches] → production path → gate → publish
                                          ↑            │
                                          └── revise ───┘
```

The backbone stays linear, evidence work can converge, and runtime feedback can trigger a bounded return without turning every stage into a free-moving graph.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use sequence for a pipeline, independent breadth for a DAG, state-dependent returns for cycles, and localized combinations for a hybrid.</p></div>

## Make the branch contract explicit

A branch is justified only when its gain beats the coordination tax. I think the merge is the real architecture decision: it must know which branches were expected, expose missing results, preserve source provenance, and declare whether failure means retry, accept survivors, cancel, or escalate.

| Concern | Contract to define |
|---|---|
| Retry | Idempotency: repeating one logical attempt adds no second effect |
| Isolation | Separate workspaces or controlled shared writes |
| Limits | Queues, backoff, and maximum concurrency |
| Replay | Branch identity, input version, result, and merge decision |

[Stripe’s idempotency documentation](https://docs.stripe.com/api/idempotent_requests) shows the retry mechanism: a key identifies the same logical request so it can be repeated without performing the operation twice. Graph topology supplies none of this automatically. A fresh model context does not guarantee independent verification either; branches can share weak sources and blind spots. Keep schema checks, deduplication, counting, and routing in deterministic code, and reserve models for judgment that requires them.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Parallelism pays only when joins, partial failures, retries, isolation, limits, provenance, and replay have explicit behavior.</p></div>

The mapping is architectural: a launch sequence needs an ordered pipeline because each stage enables the next, while a fleet engagement needs branches and state-based decisions. Modeling the launch as a fleet merely adds mission-control machinery that can fail.

## Decide with four answers

Before drawing the workflow, ask:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can runtime state change the next route or stopping condition?
4. Can the system detect, explain, and replay a partial failure?

“Start linear” should mean start with the smallest truthful topology, not serialize obviously independent work. Measure branch duration, throttling, retries, join completeness, and replay, then promote only the work that earns a wider route. I think a hybrid is often the practical destination because it keeps the control spine obvious and contains complexity where it pays.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Measure first, then add only the branch, condition, or cycle that represents proven work and can be recovered when it fails.</p></div>
