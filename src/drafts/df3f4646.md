AI builders often treat an agent graph as advanced and a pipeline as primitive. That reverses the decision. Workflow topology is the arrangement of stages and routes, and a linear pipeline is already a graph: one ordered path.

I think production architecture should use the fewest routes the work needs. Branches can cut serial waiting or widen a search, but they do not create judgment, retry safety, or ownership.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose topology from real dependencies and failure paths, not from how sophisticated the diagram looks.</p></div>

## Draw dependencies before topology

Begin with what must wait. A data dependency exists when one job consumes another's result. A resource dependency exists when jobs may change the same file or record, compete for limited service capacity, or wait on one approval gate. [PostgreSQL, an open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), documents writers waiting on a locked record. [Stripe, a payments platform](https://docs.stripe.com/rate-limits), separates concurrency limits from request-rate limits.

Apply the fake-edge test. If B consumes nothing from A, and running both creates no shared write, exclusive gate, capacity conflict, or duplicate external effect, their edge may be artificial. A shared immutable input creates no write conflict. I think teams will mistake simultaneous model calls for independent work, then discover the hidden dependency during recovery.

Keep a straight pipeline when sequence is real: ingest request, validate schema, apply policy, persist result. Each stage needs the preceding output or authorization. Ordinary deterministic code should handle validation, deduplication, counting, routing, and merge checks; models belong where the task requires judgment.

Replay means rebuilding workflow state from recorded history under runtime rules. [Temporal, a durable workflow platform](https://docs.temporal.io/workflow-definition), replays deterministic control code against event history without rerunning completed activities, its units of external work. Activities can still retry. I think an ordered path is often strongest when the work itself is ordered.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Remove an edge only after checking both consumed outputs and hidden conflicts over writes, capacity, gates, and external effects.</p></div>

## Make the merge operational

A directed acyclic graph, or DAG, has directed dependencies but no route back. Fan-out starts independent branches; fan-in merges their outputs. Use it for wide work, such as researching several market angles before verifying and combining accepted findings.

The architecture becomes operational at the merge. A join policy states which results are required and what happens when one is missing. The critical path is the longest required chain, so an all-required merge waits for its slowest branch. [AWS Step Functions, a managed workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), waits for every Parallel branch to terminate. I think the merge contract matters more than fan-out.

This pseudocode is a design contract, not engine configuration:

```text
run_id: research-042
statuses: [pending, running, complete, failed, timed_out]
branches:
  market:      {required: true,  status: complete}
  regulation:  {required: true,  status: running}
  competitors: {required: false, status: timed_out}
join_policy: all_required_terminal
retry_budget: 2
stop_condition: deadline_or_budget
owner: research-service
rollback_condition: disable_parallel_stage
```

Accepting the merge while `regulation` is running is an illegal transition. The runtime should surface `join_rejected: required branch regulation is running` and preserve branch IDs, input versions, results or errors, retry counts, and the merge decision. These are design requirements, not automatic graph features.

That distinction matters when a branch writes, sends, or charges. Idempotency means repeating one logical request preserves one intended external effect; [Stripe's API documentation](https://docs.stripe.com/api/idempotent_requests) shows an implementation based on a key. Without it, a retry can repeat the effect it should recover.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A production merge needs expected branches, a missing-result policy, legal transitions, retry safety, provenance, and a recovery owner.</p></div>

## Add routes only when state changes

A conditional graph selects its next route from current state, the data available to the run; that state is recorded only if the runtime persists it. A cyclic graph can return to earlier work, so it needs a reason for another pass, a stop rule, and a hard attempt, time, or cost limit. [LangGraph, an open-source framework for stateful agent workflows](https://docs.langchain.com/oss/python/langgraph/graph-api), documents state-based routing and a configurable loop limit. I think a cycle belongs only where current data changes what happens next.

Topology is framework-independent. A durable workflow engine, queue workers, state-machine code, or an agent-graph library can implement the same dependencies. A hybrid combines a linear backbone with a bounded branched or conditional section: intake and policy stay ordered, research splits into two required branches and an optional branch, then accepted results converge before approval.

Four questions are enough for the design review:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can runtime state change the next route or stopping condition?
4. Can the system detect, explain, and replay a partial failure?

Baseline the linear route, run the bounded alternative, then compare latency, accepted findings with source provenance, duplicate effects, incomplete merges, recovery time, and cost per successful run. Before release, the service owner should approve the retry budget, deadline, partial-failure rule, and rollback condition. I don't know which shape wins before measurement; the framework cannot answer for the team.

[“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper on loop terminology and exit conditions. [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, declared state, and evidence after the topology is chosen.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose by dependency, route-changing state, and recoverability; every unearned edge becomes an unowned failure path.</p></div>
