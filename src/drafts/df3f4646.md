Agent architecture is often presented as a maturity ladder: pipelines first, graphs later. I think that rewards arrows rather than engineering. A pipeline is already a graph: one directed path.

A pipeline moves work through a known sequence. A directed acyclic graph, or DAG, can branch and merge but cannot return to an earlier node. A conditional graph chooses the next edge from current state, while a cyclic graph can revisit work. A hybrid keeps a linear backbone with bounded graph-shaped sections. Choose the minimum topology that expresses the real dependencies and runtime decisions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Select topology by the work's shape, not the diagram's apparent sophistication.</p></div>

## Draw dependencies before agents

Map each stage's inputs, outputs, writes, approvals, and limits. A data dependency means one stage consumes another's result. A resource dependency appears when separate jobs change the same file, database row, or workspace, or compete for limited API capacity. Shared read-only input creates no write conflict.

Apply the fake-edge test: if B consumes none of A's output and the jobs share neither mutable state nor constrained capacity, the edge may be artificial. A real conflict need not serialize the workflow. Resource admission controls scarce capacity with a queue, lock, or concurrency limit. [PostgreSQL, an open-source database, documents a second updater waiting on the same row](https://www.postgresql.org/docs/current/transaction-iso.html), while [Stripe, a payments API, separates active-request from request-rate limits](https://docs.stripe.com/rate-limits). I think prompt independence without resource independence creates fake edges.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Justify an edge with consumed data or a real coordination constraint.</p></div>

## Keep real sequence linear

Keep the chain when each stage needs what came before it: ingest a request, validate its schema, apply policy, then persist the result. The known route keeps retries, ownership, and replay boundaries visible. Put schema checks, counts, deduplication, and fixed routing in code; use a model for judgment.

A pipeline does not create reliability. A durable workflow runtime may persist state, retry work, and expose traces, but those are runtime capabilities rather than benefits of branching. I think an obvious predecessor helps operators explain a run and resume from a known boundary.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep real sequence linear so execution and recovery remain inspectable.</p></div>

## Define the merge before the branch

Fan-out starts independent branches; fan-in merges them. Use this shape for genuinely wide work, such as checking five market angles separately before one report. [AWS Step Functions, Amazon's managed workflow service, runs parallel branches as concurrently as possible and waits for them to finish](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html). Parallelism can remove serial waiting, but an all-results merge still follows its slowest required branch on the critical path, the longest required chain setting completion time.

Before launch, specify expected branch identities, output schema, provenance showing where each result came from, deadline, and missing-work policy. A retried external write needs idempotency: the same logical attempt cannot repeat its intended effect. [Stripe documents one implementation using stable keys](https://docs.stripe.com/api/idempotent_requests). I think the merge is the architecture decision. Breadth alone supplies neither judgment nor reliability.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Fan out independent work only when the merge and its failures are governable.</p></div>

## Add routes only when state changes

Conditional routing lets runtime state select the next step; a cycle can send work back. An evidence score might trigger deeper verification, a retryable error might repeat one operation, or a weak result might return for bounded refinement. [LangGraph, a framework for stateful agent workflows, documents state-based edges and looping execution](https://docs.langchain.com/oss/python/langgraph/graph-api).

I think a cycle earns its place only when a recorded change alters the next action. Give it a stop rule and a hard step, time, or cost limit. If the route and pass count are known beforehand, keep them acyclic. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper on ownership and exit conditions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A return edge needs a reason to repeat and an enforceable reason to stop.</p></div>

## Let the hybrid earn promotion

Many production systems need a linear spine for intake, policy, approval, persistence, and publishing, with a bounded research or verification burst. This hybrid contains the coordination tax: partial failures, safe retries, workspace isolation, quotas, branch traces, and model cost. Topology supplies none of those controls.

I don't know whether a wider candidate is better until it beats the linear baseline. Record latency, cost per accepted result, merge completeness, replay success after an injected branch failure, and operator recovery time. Name the budget owner, service owner, promotion approver, rollback trigger, and tested linear fallback.

Four questions are enough for the architecture review:

1. What must wait because it consumes an earlier result?
2. What can run independently without changing the same resource or exhausting shared capacity?
3. Can runtime state change the next route or stopping condition?
4. Can the system detect, explain, and replay a partial failure?

My take: add only the branch, condition, or return edge those answers require. Once chosen, [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, typed state, and production trust controls.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose the smallest measured topology whose gain exceeds its coordination tax.</p></div>
