Most agent workflow diagrams start one decision too late. They show model roles, tools, and arrows before anyone establishes which pieces of work must wait for which others.

A pipeline is already a graph: its nodes form one directed path. I think the useful production question is therefore simpler than “pipeline or graph?” Choose the minimum topology, meaning the shape of nodes and edges, that represents the workflow’s real dependencies without inventing coordination work.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Graph complexity should follow the work’s dependency structure, not the number of agents or the features exposed by an orchestration framework.</p>
</div>

## Map the edges you cannot remove

Start with data dependencies. If policy enforcement needs validated input, or persistence needs an approved result, those edges are real. Then map resource dependencies: shared files, database rows, mutable workspaces, approval gates, and API quotas. Two tasks can ignore each other’s output and still be unsafe or slower when run together.

The fake-edge test has two parts. If B does not consume A’s result and both can run concurrently without competing for a mutable resource, meaning a shared thing either task can change, the A → B edge may be artificial. A shared read-only snapshot does not create that conflict. The [PostgreSQL transaction-isolation documentation](https://www.postgresql.org/docs/current/transaction-iso.html) for the open-source relational database shows the opposite case: concurrent updates to the same row may force one writer to wait. I think agent count is irrelevant until this map exists.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Remove an edge only after checking both data flow and hidden contention around shared state, quotas, and approvals.</p>
</div>

## Match the shape to the work

A linear pipeline is one ordered path. A DAG, or directed acyclic graph, can branch but never returns to an earlier node. A conditional graph selects its next edge from current state, while a cyclic graph can revisit work. A hybrid keeps a linear control spine and contains short graph-shaped sections.

**Topology sketch**

```text
Pipeline       A → B → C
Branched DAG   A → {B | C | D} → E
Conditional    A → B or C, selected from state
Cyclic         A → B → C ↺ B, until a stop rule
Hybrid         A → {B | C} → D → E
```

Keep ingest request → validate schema → apply policy → persist result linear because each stage needs the previous result or authorization. Use a branched DAG when five independent market angles can be researched concurrently and then merged. Use ordinary code for schema checks, counting, deduplication, and routing conditions; models belong where judgment is actually required. I think a cycle earns its place only when runtime state can justify both the return and the stop. If the number of passes is known beforehand, an acyclic route remains clearer.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Sequence supports a pipeline, genuine breadth supports a DAG, and state-dependent routing or stopping supports conditions and cycles.</p>
</div>

## The merge carries the coordination bill

Fan-out/fan-in means starting independent branches and later merging their results. [AWS Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), Amazon Web Services’ managed workflow service, documents the important mechanic: parallel branches run as concurrently as possible, but a full join waits for all of them. The critical path, the longest required chain of work, therefore includes the slowest required branch. The 2013 systems paper [“The Tail at Scale”](https://www.barroso.org/publications/TheTailAtScale.pdf) explains why latency variation becomes more visible as a request waits on many components.

I think the merge is the real architecture decision. It must know which branch IDs were expected, expose missing results and provenance, the source history attached to each result, and decide whether to fail, retry, accept survivors, or escalate. Retried writes also need idempotency, meaning the same logical attempt does not repeat its external effect; the payment platform [Stripe documents this pattern](https://docs.stripe.com/api/idempotent_requests) for safe API retries. Add isolated workspaces, rate-limit handling, traceable state, and replay, then compare that bill with the latency or coverage gained. More arrows supply none of those controls automatically.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Parallel work pays off only when the system can govern the slowest branch, partial failure, duplicate effects, shared resources, and replay.</p>
</div>

## Meanwhile in sci-fi

<span class="scifi__label">Meanwhile in sci-fi</span>
<p class="scifi__film">Battlestar Galactica (2004)</p>
<p>The science-fiction television series offers two useful command shapes. A launch sequence follows ordered checks because each stage enables the next. A fleet engagement distributes decisions across units that can move independently and later converge around a shared objective.</p>
</div>

The mapping is precise: a pipeline fits the launch sequence, while branching and state-dependent routes fit the fleet engagement. Recasting the ordered sequence as a fleet merely creates more mission-control software that can fail.

## Keep graph-shaped work bounded

Consider the Content Engine behind this article at a deliberately high level. Its useful production shape is hybrid: a controlled path governs movement, while a bounded research burst can explore independent evidence angles and converge before the next gate. The exact stages are less important than keeping the branching local.

**Content Engine, simplified**

```text
control gate → fan-out ┬→ evidence angle A ┐
                       ├→ evidence angle B ├→ checked merge → next gate → delivery
                       └→ evidence angle C ┘
```

If a check consumes a completed draft, it stays after drafting rather than becoming a decorative parallel branch. I think the hybrid is often the strongest production answer because it preserves obvious recovery along the spine and spends coordination only where breadth is useful.

Before adding topology, ask:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can runtime state change the next route or stopping condition?
4. Can the system detect, explain, and replay a partial failure?

Start with the smallest truthful shape, measure it, and promote only proven independence or state-dependent behavior. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](/posts/everyone-discovered-loops/) goes deeper on loop terminology and exit conditions. “The 105 minutes after the graph” takes up evaluation, typed state, and trust once this topology choice has been made.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>A linear backbone with bounded branching keeps production understandable; every added edge should correspond to a measured dependency, useful concurrency, or a real state change.</p>
</div>
