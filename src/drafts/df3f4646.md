# Let the work choose the graph

A pipeline is already a graph, one ordered path. I think the question is which topology matches the work with the least coordination overhead.

Picture a launch sequence beside a fleet engagement. Launch stages enable one another, while fleet units move independently and converge. Turning the launch into a fleet graph adds mission-control software although the work stays sequential. As [Anatoli Kopadze](https://x.com/AnatoliKopadze/status/2080668775796314331) puts it, “A graph buys breadth. It does not buy better judgment.”

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose topology from dependencies and runtime decisions. Every extra edge needs an operational reason.</p></div>

## Draw dependencies before agents

Map what each job consumes and changes. B depends on A’s result. Hidden resource edges can appear when jobs share a writable file, database row, approval gate, workspace, or API quota. A mutable resource is shared state a task can change. [PostgreSQL documents](https://www.postgresql.org/docs/current/transaction-iso.html) how one concurrent writer may wait behind another.

Apply the fake-edge test. If B consumes none of A’s output and shares no write, lock, quota, or changing external state with A, their edge may be artificial. Shared input is safe in parallel only as an immutable or consistent snapshot, without contention for a quota, lock, or external side effect. I think this test reveals more parallelism than agent count ever will.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Map data flow and shared resources first. Contention can turn apparent independence into a real edge.</p></div>

## Keep real sequence linear

A pipeline fits when each stage consumes or authorizes the next: ingest request → validate schema → apply policy → persist result. Its known route gives each failure an obvious predecessor, which simplifies targeted replay.

Keep validation, counters, deduplication, and fixed routing in ordinary code, then use models where judgment is required. I think an ordered path is often stronger in production when auditability and predictable recovery carry more value than parallel speed. Measure the critical path, meaning the longest required chain of work, before adding breadth.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use a pipeline when sequence reflects the work. Clear predecessors simplify inspection and recovery.</p></div>

## Use a DAG for genuine width

A DAG, or directed acyclic graph, allows branches but contains no route back to an earlier node. Fan-out starts independent jobs, and fan-in merges their results. Five market angles can fan out for separate research and verification, then converge into one report.

The merge makes the operational decisions. In [AWS Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), a Parallel state waits for every branch to terminate before moving on, so an all-required join waits for its slowest required branch. The merge should know expected branch identities, expose missing results, preserve provenance, and enforce a deadline and failure policy. Side-effecting retries also need a duplicate-effect defense, such as the [idempotency keys Stripe documents](https://docs.stripe.com/api/idempotent_requests). I think the merge deserves more design attention than the fan-out.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Parallel breadth helps when branches are independent and the merge can account for incomplete or retried work.</p></div>

## Add cycles when state changes the route

A conditional graph selects the next edge from current state. A cyclic graph can revisit earlier work. Use them when an evidence score selects verification, a failure triggers escalation, or a retry sends a job back to verification with capped attempts.

Each return needs a state change, a stop rule, and a hard budget. Known passes can stay acyclic. I think a cycle is justified when runtime evidence determines whether the system returns, exits, or escalates. For deeper treatment of feedback and ownership, read [Everyone Discovered Loops. Nobody Agrees What the Word Means.](/posts/everyone-discovered-loops/).

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use cycles for state-dependent returns. Name the destination, changed state, stopping condition, and hard limit.</p></div>

## Contain the coordination tax

Branches can add partial-failure handling, workspace conflicts, rate constraints, and tracing. Model-calling branches can also multiply model calls. Safe replay of side-effecting work needs a durable execution identity plus idempotency, deduplication, transactional writes, or an equivalent duplicate-effect defense.

A production hybrid often works well: a linear control spine with a bounded graph burst for research or verification. It keeps policy, approval, and persistence visible while localizing joins and failure policies. Start linear unless required work is independent and the latency target rules out serial execution.

I don’t know where your bottleneck sits before measurement, and a diagram cannot settle it. Use four questions to form a hypothesis, then test it with traces:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can runtime state change the next route or stopping condition?
4. Can the system detect, explain, and replay a partial failure?

Afterward, [The 105 minutes after the graph](/drafts/67821675/) covers evaluation, typed state, and the trust layer. If removing an edge changes neither data correctness, resource safety, routing, nor recovery, delete it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A hybrid localizes branching. Keep an extra edge only when it protects a dependency, resource, route, or recovery path.</p></div>
