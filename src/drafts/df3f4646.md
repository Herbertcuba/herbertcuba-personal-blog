# Choose the smallest workflow topology that tells the truth

I think treating graphs as advanced and pipelines as primitive reverses the decision. A linear pipeline is already a graph: one directed path with no cycle. A [directed acyclic graph (DAG)](https://networkx.org/documentation/stable/reference/algorithms/dag.html) may branch and merge but cannot return; a conditional graph follows runtime state; a cyclic graph revisits earlier work. A hybrid places bounded graph sections inside a linear backbone.

[Anatoli Kopadze, author of a July 2026 article on graph engineering](https://x.com/AnatoliKopadze/status/2080668775796314331), argues that graphs add width rather than judgment. His test asks whether two jobs need an edge. I extend it to resource waits and seek the minimum truthful topology.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose topology by representing every real wait, including hidden resource conflicts.</p></div>

## Map dependencies before topology

A data dependency means one job consumes another’s result. A resource dependency exists when jobs can change or lock the same mutable file, database row, approval record, or workspace, or exhaust the same API quota. Branches may read one immutable snapshot safely.

An edge is removable only when neither job consumes the other’s output nor shares a conflicting write, lock, approval, or capacity limit. [PostgreSQL, a relational database, documents one updater waiting](https://www.postgresql.org/docs/current/transaction-iso.html); [Stripe, a payment platform, separates request-rate limits from simultaneous-request limits](https://docs.stripe.com/rate-limits). Branching can move the wait into a queue.

Ingest request → validate schema → apply policy → persist result belongs in a pipeline because each stage requires the previous result or authorization. I think deterministic code should handle checks, counts, duplicate removal, and fixed routes; models should handle judgment. If locking or throttling dominates the critical path, the required chain that sets minimum completion time, branching only moves the bottleneck.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep sequence visible; remove an edge only after checking data flow and shared resources.</p></div>

## Design the join before the fan-out

Fan-out starts independent branches; fan-in merges their results. Five market-angle searches can run together, but an all-required merge still waits for its slowest required branch. [AWS Step Functions, Amazon’s workflow state-machine service, documents this barrier](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html). Parallel work removes artificial waiting; it promises no fixed speedup.

I think the merge is the real architecture decision. This illustrative record makes its obligations inspectable:

```yaml
run: R42
branch: {id: angle-3, attempt: 2, status: succeeded}
refs: {input: request-v7, output: finding-91}
controls: {idempotency_key: R42/angle-3, deadline: T+90s, provenance: sources/tool-v4}
join: {required: [angle-1, angle-3], optional: [angle-2], received: [angle-2, angle-3], revision: 1, status: blocked}
```

Required `angle-1` is missing, so publishing stays blocked. An optional absence may yield a degraded result; a late result creates immutable merge revision 2. Within attempt 2, `succeeded → running` is illegal, while a retry creates attempt 3. [Idempotency](https://docs.stripe.com/api/idempotent_requests) means repeating the same logical write does not repeat its intended effect. Provenance records source and tool versions. [The Amazon States Language, Step Functions’ JSON-based specification, makes branch failure and tolerated failure explicit](https://states-language.net/spec.html).

The workflow owner handles a partial join; the release owner approves, stops, or rolls back; the budget owner funds human handling. A durable runtime can store state, but the team decides required evidence and acceptable degradation.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Define branch identity, merge rules, failure policy, safe retries, and owners before widening.</p></div>

## Let runtime state earn the return edge

Use conditional routing when state changes the next job, and a cycle when it sends work back. I think a fixed two-pass review remains a DAG because both passes are known; a runtime choice among refinement, completion, or escalation earns a return edge. Every cycle needs a stop rule and a hard step or cost cap. [LangGraph, an open-source framework for stateful agent workflows, documents state-based edges and bounded loops](https://docs.langchain.com/oss/python/langgraph/graph-api). [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper on loop terms and exit conditions.

Recovery terms differ. A retry reattempts a job; a resume continues stored execution; a rerun starts a new execution; deterministic history replay rebuilds progress from recorded events. [Temporal, a durable workflow engine, stores event history and replays it to resume execution](https://docs.temporal.io/workflow-execution). The runtime provides machinery; topology remains your decision. Isolate branches through owned records, partitions, immutable snapshots, or separate workspaces.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Add conditions or cycles only when state changes the route; keep every return bounded and recoverable.</p></div>

## Promote one measured bottleneck

For one release, benchmark the linear stage and test one independent branch behind a disable switch. Example bar: p95 elapsed time, meaning 95 percent of runs finish within it, falls 20 percent; cost per success rises at most 10 percent; completeness of required branches reaches 99.5 percent; operator time stays flat. The release owner reverts on a miss. I don’t know whether the branch earns its place until local runs clear that bar.

Ask four questions: What must wait because it consumes an earlier result? What can overlap without a mutable-resource conflict? Can runtime state change the route or stop condition? Can the system detect, explain, and replay a partial failure?

I think the answers often produce a hybrid: a linear intake, policy, approval, and persistence spine with a bounded research burst. Across teams, a shared supplier quota or approval queue remains a dependency. Once topology is chosen, [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, structured state, and trust controls.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Start with the smallest truthful topology, promote one measured bottleneck, and keep complexity whose gain covers its coordination cost.</p></div>
