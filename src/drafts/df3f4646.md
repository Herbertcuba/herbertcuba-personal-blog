Graph diagrams can make an AI workflow look sophisticated before they make it useful. I think the better question is: which topology, meaning the arrangement of stages and edges, tells the truth about the work?

A pipeline is one ordered graph path. A DAG, or directed acyclic graph, may branch and merge but cannot return to an earlier stage. A conditional graph selects the next edge from current state; a cyclic graph can revisit work. A hybrid keeps a linear backbone with bounded graph-shaped sections.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose topology from dependencies and state changes, using the fewest edges that express them.</p></div>

## Map the edges the work actually has

Start with data dependencies: one stage waits because it consumes another's result. Then map resource dependencies. A mutable resource is anything a job can change, such as a file, database row, approval record, or workspace; API limits can also couple jobs.

[PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html), the open-source relational database, shows how concurrent writers can block on the same row. [Stripe](https://docs.stripe.com/rate-limits), the payments platform, separately limits request rate and simultaneous requests. If B consumes nothing from A and they share neither mutable state nor scarce capacity, the A-to-B edge may be fake. A shared read-only input alone creates no conflict. I think queues, locks, or concurrency limits should control shared capacity without inventing a data dependency.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Separate output dependencies from shared-resource conflicts before deciding which work can run independently.</p></div>

## Keep a line when sequence is real

Consider ingesting a request, validating its schema, applying policy, and persisting the result. Each stage supplies or authorizes what follows, so branching cannot remove the wait. Keep schema checks, counters, deduplication, and fixed routing in deterministic code; use models where judgment is required.

A linear path makes each predecessor, replay point, and owner visible. A durable workflow runtime can persist state and retry either a line or a graph, so runtime and topology are separate decisions. I think a pipeline is often the strongest production shape when the order is real.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep genuine sequence visible; branching cannot help work that must proceed in order.</p></div>

## Branch only when the merge is designed

Fan-out starts independent branches; fan-in joins their results. Five market angles can read the same immutable brief and write isolated outputs. A DAG fits. Its merge must know which branches were expected, which arrived, where claims came from, and how to handle failure or delay.

[AWS Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), Amazon's managed workflow service, runs branches as concurrently as possible and waits for every Parallel branch to finish. The critical path is the longest required chain, so an all-results merge still inherits its slowest required branch. I think the merge is the architecture decision: set its output schema, timeout, missing-result policy, and provenance, a record of where each result came from. Idempotency means retrying cannot repeat the same external effect.

Compare both versions on the same workload, including an injected branch failure, and measure latency, cost, completeness, and replay behavior. I don't know whether branching has earned its place until it beats that baseline without hiding missing results.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Parallelize breadth only after join, failure, and replay rules are explicit.</p></div>

## Route on state, and cap the return

A conditional graph is justified when state changes the next route. A cycle is justified when state can send work back after a retryable tool error or evidence check. If the passes are known, use a DAG.

Every cycle needs a return reason, a meaningful stop condition, a hard step or cost limit, and an escalation path. [LangGraph](https://docs.langchain.com/oss/python/langgraph/graph-api), an open-source framework for stateful agent workflows, documents state-based edges and a hard execution limit. I think a return edge without a stop rule is an unbounded bill. The related article [Everyone Discovered Loops. Nobody Agrees What the Word Means.](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper on ownership and exit conditions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Add a route or cycle only when runtime state can explain both the next move and when the work stops.</p></div>

The mapping is practical: a launch sequence needs a pipeline because each stage enables the next, while a fleet engagement needs branches, changing routes, and convergence. Turning the launch sequence into a fleet graph only creates more mission-control software that can fail.

## Make the hybrid prove itself

Many production workflows can keep intake, validation, approval, and persistence linear while a bounded research or verification stage fans out. My take is that this hybrid localizes the coordination tax: partial failure, isolation, idempotent writes, quotas, tracing, and multiplied model use stay where width can create measurable value.

Ask four questions:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can runtime state change the next route or stopping condition?
4. Can the system detect, explain, and replay a partial failure?

Name the people who approve promotion, own shared capacity, and command recovery to the linear fallback. Instrument the current path, then widen only a measured bottleneck. The related article [The 105 minutes after the graph](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, explicit state schemas, and production controls after topology is chosen.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Earn every branch and return edge with measured value; the strongest production graph is the smallest one that tells the truth.</p></div>
