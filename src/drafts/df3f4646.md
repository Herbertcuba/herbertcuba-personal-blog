Graph tooling makes coordination cheap to draw and expensive to govern. Every edge promises order, failure, ownership, and replay. A pipeline is already a graph: one path. I think architecture gets clearer once we stop calling it primitive.

Choose the minimum topology, the layout of stages and connections, that describes the work honestly. Keep sequence linear, branch only independent work, and add a return path only when runtime state changes what follows.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose topology from dependencies and runtime state, then make every extra edge justify its operating cost.</p></div>

## Draw the dependencies first

Begin with dependencies, not agent count. A data dependency means one job consumes another’s result. A mutable resource is state a job can change: a file, database record, workspace, approval, or API quota. Jobs can exchange no data and still conflict.

Use the fake-edge test. If B consumes no output from A and shares no mutable resource, A → B may be artificial. Read-only snapshots can be safe; shared writes are not. [PostgreSQL, an open-source relational database](https://www.postgresql.org/docs/current/transaction-iso.html), documents writers waiting; [Stripe, a payments platform](https://docs.stripe.com/rate-limits), documents separate rate and concurrency limits.

I think fan-out should be rejected when branches can write the same transactional record without isolation or enforced ordering. Their prompts may look independent; the system is not.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Remove an edge only when jobs share neither required output nor a mutable resource, quota, or approval.</p></div>

## Let the route choose the shape

A linear pipeline fits when each stage needs the previous result: ingest → validate schema → apply policy → persist. Its route is known, deterministic checks stay in ordinary code, and replay follows the same path.

Use a directed acyclic graph, or DAG, for wide work. Its edges point forward, with no route returning to an earlier stage. Fan-out starts independent jobs; fan-in merges them. Five market angles can be researched separately before one report. Parallel work may shorten the critical path, the longest chain, but an all-required merge waits for its slowest branch. [AWS Step Functions, a cloud workflow service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), makes that wait explicit.

I think the merge is the real design decision. Its join policy, the rule for accepting results, must define expected branch IDs, missing results, provenance, deadline, and retries. A retried external write also needs idempotency, a key or rule that stops one logical action taking effect twice.

A conditional graph selects the next stage from recorded state. A cyclic graph may revisit an earlier stage, but changed state must justify the return and a stop rule must end it. If every run makes two passes, draw two stages. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) goes deeper into feedback loops and exit conditions.

Our Content Engine moves an article through research, drafting, and quality gates. It uses a hybrid: a linear control spine contains a bounded research or verification burst whose branches converge before the next gate.

## Make complexity prove its value

Before approving a branch or cycle, create a decision record that exposes legal routes and failure behavior instead of hiding them inside framework code.

Compare the proposal with the linear baseline on critical-path latency, completion coverage, duplicate effects, and cost per successful run. I don’t know which shape wins before measurement. I think review should admit a branch or cycle only with independent work, an owner, bounded failure, replay evidence, and measured benefit.

When replay and safe retries dominate, prefer a durable workflow engine, which records history so work can resume, or a state-machine engine, which executes declared states and transitions. Both are stronger than an agent framework when recovery matters more than model judgment. After topology comes [“The 105 minutes after the graph”](/drafts/67821675/), the separate piece on evaluation and typed state, a run record with declared field types.

Ask four questions: What needs an earlier result? What can run without touching the same mutable resource? Can runtime state change the route or stop rule? Can the system explain and replay a partial failure? Operate the smallest graph that answers truthfully.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Approve extra topology only with explicit resources, failure rules, ownership, replay proof, and a measured gain over the simpler path.</p></div>
