# When your AI workflow actually needs a graph

Workflow topology is how stages connect. A pipeline is already a graph: one ordered path. The decision is how much more topology the work justifies.

In sci-fi, a launch sequence stays ordered because each stage enables the next; a fleet engagement needs independent units, changing routes, and convergence. In [a 2026 X article on graph engineering](https://x.com/AnatoliKopadze/status/2080668775796314331), Anatoli Kopadze wrote, “A graph buys breadth. It does not buy better judgment.” I think mature architecture uses the smallest topology that tells the truth about the work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A pipeline is a graph. Add branches or returns only when dependencies require them.</p></div>

## Begin with the dependencies

A data dependency exists when B consumes A’s output. A hidden resource dependency exists when jobs touch the same mutable resource, something they can change or exhaust: a file, database row, workspace, approval, or API quota. [PostgreSQL, an open-source relational database, documents](https://www.postgresql.org/docs/current/transaction-iso.html) one updater waiting on another for the same row. Jobs may share an immutable snapshot if no write, lock, quota, or external effect competes.

If B consumes none of A’s output and both jobs run without resource conflict, the A-to-B edge may be fake. Separate prompts do not prove independence. I think the map should describe data and resources before it counts agents.

Keep a pipeline for real sequence: ingest a request, validate its schema, apply policy, then persist. Replay means rerunning failed work from a recorded stage or state. A known predecessor makes recovery easier to inspect, while [idempotency](https://docs.stripe.com/api/idempotent_requests) lets one attempt run again without duplicating a write, message, or charge. Validation, counting, deduplication, and fixed routing belong in ordinary code; models should handle judgment that code cannot settle.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Map consumed outputs and shared resources first. Real sequence belongs in a visible, replayable pipeline.</p></div>

## Use a DAG when the work is genuinely wide

A DAG is a directed acyclic graph: its edges point forward, never back to an earlier stage. Fan-out starts independent jobs; fan-in merges their results. Five market-angle searches fit if branches share neither findings nor a write or quota.

Parallel fan-out reduces elapsed time only when it replaces sequential work. If the merge requires every result, the slowest branch controls that part of the critical path, the run’s longest required chain. [AWS Step Functions, Amazon’s managed workflow service, waits](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html) for every parallel branch. I think the merge is the real decision because it defines which results count and what absence means.

A partial failure leaves some branches complete and others missing. The merge needs branch identities, deadline, output shape, evidence sources, and missing-result policy. Write retries need idempotency; the owner needs a failure deadline. Reject fan-out when two branches can write the same record without isolation or one ordered writer. Compare critical-path latency, usable-result coverage, duplicate effects, and cost per successful run before and after the change.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Parallelize independent work only after defining the merge, failure policy, safe retry, and measured benefit.</p></div>

## Add cycles only when state changes the route

Runtime state records a run’s condition. A conditional graph chooses its next stage from that state; a cyclic graph can return to an earlier stage. Low evidence might trigger another source check, while a retryable error might return work until its budget expires. I think a cycle earns its place only when changed state changes the next action.

The return needs a stop rule and a hard cap on attempts, time, or cost. Two planned reviews remain an ordered path. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](/posts/everyone-discovered-loops/) goes deeper into feedback terminology, ownership, and exits. A durable workflow engine records history and resumes transitions after failure; when recovery and external effects dominate, it may be a better foundation than an agent framework.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use state-driven routes when the next action is unknown. Every return needs a reason, stop rule, and hard budget.</p></div>

## Keep the graph-shaped part bounded

Every branch adds failure handling, merge rules, workspace isolation, rate limits, traces, retries, and model calls. None creates reliability by itself. My take is that production favors a hybrid: a linear spine for intake, policy, approval, and persistence, plus a short research or verification fan-out before the next gate.

Before adding topology, ask what must wait, what can run without resource conflict, whether state can change the route or stop, and whether partial failure can be detected, explained, and replayed safely. I don’t know a universal branch count where the tax becomes too high. I think an extra edge needs an owner, a measurable latency, coverage, or resilience target, and recovery evidence.

Once topology is chosen, [“The 105 minutes after the graph”](/drafts/67821675/) covers evaluation, schema-constrained state, and trust controls. Frameworks make coordination cheap to draw. The work must earn every edge.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use a linear spine with bounded graph bursts, and add topology only when measured gains beat its operating cost.</p></div>
