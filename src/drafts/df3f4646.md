# Let the work choose the graph

Graph tooling makes coordination cheap to draw and expensive to govern, which is why teams mistake arrows for capability. I think the hierarchy is backwards. A pipeline is already a graph: tasks are nodes, dependencies are edges, and its topology is one ordered path.

Picture a launch sequence beside a fleet engagement. Launch stages must wait; fleet units can move independently and converge. Turning the launch into a fleet graph adds mission-control software without changing the work. In [his X article on graph engineering](https://x.com/AnatoliKopadze/status/2080668775796314331), Anatoli Kopadze writes, “A graph buys breadth. It does not buy better judgment.” The decision is the minimum topology that tells the truth.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A pipeline is a graph. Add branches and returns only when dependencies or runtime state require them.</p></div>

## Draw dependencies before agents

Start with what each job consumes and changes. A data edge means B needs A’s output. A resource edge exists when jobs touch the same mutable resource, a shared thing a task can change, such as a file or database row. [PostgreSQL, an open-source relational database, documents](https://www.postgresql.org/docs/current/transaction-iso.html) how one writer may wait behind another; approval locks and API quotas can couple jobs too.

Two branches can read the same source in parallel only when each uses a defined read-only snapshot, neither competes for a quota or lock, and neither causes conflicting external effects. If B consumes none of A’s output and no conflict exists, the fake-edge test marks their edge as suspect. I think this finds honest breadth without equating separate prompts with independent work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Map both data flow and shared resources. Apparent independence disappears when branches contend or cause conflicting effects.</p></div>

## Keep real sequence linear

Use a pipeline when each stage needs the previous result or authorization. Ingest request → validate schema → apply policy → persist result is linear because every transition has a reason. Keep schema validation and routing deterministic, and deduplicate in ordinary code.

The critical path is the longest required chain. Parallelism shortens elapsed time only by removing waiting from that chain; when every stage needs its predecessor, branches do nothing. I think an ordered path is often strongest when sequence is real because recovery and ownership remain easy to trace.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep genuine sequence visible. Parallel structure cannot shorten a dependency chain that must remain ordered.</p></div>

## Branch for breadth, not prestige

A DAG, or directed acyclic graph, can branch but cannot return to an earlier node. Fan-out starts independent branches; fan-in merges them. For five market angles, create five branch IDs. Within each branch, research one angle and verify its evidence, then merge the survivors.

[AWS Step Functions, Amazon’s managed state-machine service](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), waits for every `Parallel` branch before continuing, so an all-required merge inherits the slowest one. Its contract needs expected IDs, deadline, schema, provenance, and a missing-result policy. Idempotency means a retry cannot repeat an effect; [Stripe, a payment-platform provider, documents](https://docs.stripe.com/api/idempotent_requests) keys that prevent duplicate operations. I think the merge is the real product decision, not the fan-out.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Parallelize bounded, independent work only when the merge can identify every branch, handle delays and absences, then retry safely.</p></div>

## Add a return only when state changes

A conditional graph picks its next edge from current state; a cyclic graph can revisit earlier work. Use them when evidence selects another verification route, a retryable failure returns, or a result triggers escalation.

If two review passes are known beforehand, represent them as ordered DAG nodes. Use a cycle only when runtime evidence decides whether to return, exit, or escalate; record the changed state, stop rule, and hard cap. [LangGraph, an agent-workflow framework](https://docs.langchain.com/oss/python/langgraph/graph-api), documents state-based edges and execution limits, but mechanics do not improve judgment. I think the production default is a hybrid: linear gates around a bounded research or verification burst. [Everyone Discovered Loops. Nobody Agrees What the Word Means.](/posts/everyone-discovered-loops/) goes deeper on feedback and ownership.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Let runtime state earn a route or cycle. Keep known passes acyclic and contain dynamic work inside a simple control spine.</p></div>

## Make the coordination tax executable

Before approval, ask: What consumes an earlier result? What runs without touching the same mutable resource? Can runtime state change the route or stop? Can the system explain and replay a partial failure? Record those answers beside the controls:

```yaml
run_id: stable operation ID
expected_branch_ids: []
mutable_resource_keys: []
join_policy: all | quorum | survivors | fail_fast
retry_budget: 0
stop_condition: explicit predicate
owner: accountable production owner
failure_deadline: timestamp or duration
replay_evidence: trace plus original inputs
rollback: side-effect recovery
```

The `run_id` survives retries so logs and replay identify the same work. Reject fan-out if two branches can write one transactional record without isolation. When replay and idempotency dominate, use a durable state-machine runtime; an agent graph API alone does not provide durable execution.

I don’t know whether a branch pays without a baseline. Compare critical-path latency, completion coverage, duplicate effects, and cost per successful run before and after. My take: approve a branch or cycle only when its owner can show independent work or a state-dependent route, measured benefit, and replayable failure controls. After topology selection, [The 105 minutes after the graph](/drafts/67821675/) covers evaluation, typed state, and the trust layer. An independent branch still fails review unless its benefit is measured and its failures are governed.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose the smallest topology whose owner can prove the dependency case, govern partial failure, and show that its measured gain beats its coordination tax.</p></div>
