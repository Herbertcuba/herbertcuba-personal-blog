# Every edge is a production decision

Workflow topology means the arrangement of stages and routes. A linear pipeline passes work through stages in order, making it the narrowest graph topology.

More nodes look capable, but every arrow creates an obligation. Anatoli Kopadze, writing about graph engineering on the social platform X in July 2026, put the point well: “A graph buys breadth. It does not buy better judgment.” I think the real question is which arrangement expresses the work with the least coordination.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>A pipeline and a graph are not competing categories. Choose the smallest arrangement that expresses the workflow’s real dependencies.</p>
</div>

## Waiting is the architecture

Map data and resource dependencies first. A data dependency means one job consumes another’s result. A resource dependency appears when jobs share a mutable file, database row, workspace, approval gate, or limited capacity.

That second category catches false independence. [PostgreSQL, an open-source relational database, explains](https://www.postgresql.org/docs/current/transaction-iso.html) how one writer may wait for another touching the same record. [Stripe, a payments platform, documents](https://docs.stripe.com/rate-limits) separate request-rate and concurrency limits. Jobs can exchange no output yet still block through shared capacity.

Apply the fake-edge test. If B neither needs A’s output nor races with A on mutable state or a shared limit, their arrow may be artificial. Shared read-only input is not the same conflict. I think dependencies, rather than agent count, reveal the honest shape.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>An edge is justified by consumed data or shared mutable capacity. If neither exists, serial execution needs another reason.</p>
</div>

## Give each topology one job

Keep the pipeline when sequence is real: ingest a request, validate its schema, apply policy, then persist the result. Replay means running recorded input through the stages again; the ordered route makes each predecessor obvious. I think ordinary code should handle validation, deduplication, and fixed routing, leaving model calls for judgment.

Use a DAG, a directed acyclic graph with no route back to an earlier node, when work is genuinely wide. Fan-out starts independent branches; fan-in merges them. Researching five market angles concurrently, verifying each result, and combining the survivors is one example. [AWS Step Functions, a managed workflow service, specifies](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html) that its parallel state waits for every branch to finish. The critical path, meaning the longest required chain of work, therefore includes the slowest required branch.

A conditional graph chooses the next route from runtime state; a cyclic graph may revisit earlier work. They fit a failed check that triggers a retry or refinement with a defined threshold. Every cycle needs a stop rule and a hard step or cost limit. I think a hybrid is often practical: a linear control spine with a bounded research or verification fan-out.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Use a pipeline for real sequence, a DAG for independent breadth, a conditional or cyclic graph for state-dependent routing, and a hybrid when only one stage needs wider behavior.</p>
</div>

## Make failure part of the shape

A partial failure occurs when some branches finish and another does not. Before fan-out begins, the merge should know which results are expected, which are required, what schema they use, and what happens when one is missing. It must also preserve provenance so an operator can trace a conclusion to its branch and input.

Retries add another obligation. Idempotency means repeating the same logical request preserves one intended external effect; [Stripe’s API documentation](https://docs.stripe.com/api/idempotent_requests) shows one implementation using a request key. Writing branches need isolated workspaces or serialized updates, external calls need quota-aware backoff, and traces need to expose errors and retries. Parallel model calls also duplicate context and spend. I think deterministic code should check completeness and route mechanical failures.

A graph does not create better judgment, redundancy, or reliability by having more arrows. Those outcomes require evidence, alternate paths, validation, and operating controls. Any gain in latency, coverage, or recovery must beat this coordination tax.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>The merge, retry policy, isolation, quotas, and traceability belong to the architecture. Without them, parallelism mainly widens the failure surface.</p>
</div>

## Let evidence add the next edge

Starting linear is a default, not a religion. If required external calls are independent and serial execution cannot meet the latency target, fan out immediately. Otherwise, measure stage time, throttling, retries, merge completeness, and replay success. I don’t know which topology wins until those facts are visible.

Four questions make the review concrete:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can runtime state change the next route or stopping condition?
4. Can the system detect, explain, and replay a partial failure?

For more on feedback terminology and exit conditions, read [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/). Once the topology is chosen, [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, declared state, and the evidence needed to trust the resulting system.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Begin with the smallest truthful shape, measure where it fails, and add only the branch, route, or cycle the evidence demands. Every production edge must earn its place.</p>
</div>
