Calling a workflow a pipeline can sound like admitting it is primitive. The label is misleading. A pipeline is a graph with one directed path. A DAG, or directed acyclic graph, permits branches but no route back to an earlier node. A conditional graph chooses its next edge from runtime state, while a cyclic graph can revisit prior work.

The decision is how much topology the work requires. I think the strongest production architecture is the smallest shape that represents the real dependencies and failure behavior. Every extra branch, join, condition, and return path should have a specific reason to exist.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>Pipeline versus graph is a false choice. Select the minimum graph shape that accurately represents sequence, independence, and state-dependent routing.</p>
</div>

## Read the dependencies before drawing the graph

Start by recording what each job consumes and changes. A data dependency exists when one job needs another’s output. A resource dependency exists when separate jobs touch the same mutable resource: a file, database row, approval gate, workspace, or API quota that can be changed, locked, or exhausted.

| Question | Architecture signal |
|---|---|
| What must wait for an earlier result? | Keep that path linear. |
| What can run without a shared write or quota conflict? | Consider a parallel branch. |
| Can current state change the route or stop rule? | Consider a condition or cycle. |
| Can a partial failure be detected, explained, and replayed? | Only then is wider execution governable. |

I think the most useful check is the fake-edge test. If job B does not consume job A’s result, and both can run together without contending for mutable state or a limit, the edge from A to B may be artificial. Reading the same immutable snapshot is usually safe; editing the same workspace is not. Keep schema checks, counts, deduplication, and routing rules in ordinary code when they are deterministic, rather than asking a model to exercise judgment where none is needed.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>An edge is real when output or a shared resource creates a dependency. Check both before removing artificial sequence.</p>
</div>

## Put graph-shaped work inside a simple control spine

Consider a simplified Content Engine, an article-production system that moves a brief through research, creation, quality gates, and release. This is a conceptual view, not a map of its exact stages:

```text
linear control → {independent research branches} → merge → linear control
                                                       │
                                      revise ← failed gate
```

The backbone remains ordered because downstream work consumes an approved upstream result. Inside research, independent questions can fan out as separate branches and fan in when their results merge. The merge returns one defined result to the linear path.

A failed gate adds conditional routing because current state decides whether the system proceeds or revises. It becomes a cycle only when revision returns to earlier work at runtime, and that cycle needs both a meaningful stop rule and a hard budget. I think this hybrid is a strong production default: ownership and replay stay clear, while breadth and revision are confined to the places that earn them.

<div class="chapter-tldr">
<span class="chapter-tldr__label">In short</span>
<p>A hybrid keeps the main route readable and confines parallel or cyclic behavior to the work that genuinely needs it.</p>
</div>

The mapping is architectural: ordered work belongs on an ordered path, while coordinated independent work needs a wider graph. Turning the launch sequence into a fleet engagement would add mission-control machinery without changing its dependencies.

## Make the coordination tax earn its place

Parallel work removes serial waiting only across independent paths. Its critical path, the longest chain that must finish, still includes the slowest required branch at a full join. [AWS Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), Amazon’s cloud state-machine service, makes this explicit by waiting for every parallel branch to terminate. The 2013 peer-reviewed paper [“The Tail at Scale”](https://www.barroso.org/publications/TheTailAtScale.pdf), by Google engineers Jeffrey Dean and Luiz André Barroso, explains why latency variation becomes more visible when a service waits across many components.

I think the merge is the real architecture decision. It must know which branches were expected, expose missing results, preserve source provenance, and declare whether to fail, retry, accept survivors, or escalate. Retried side effects need idempotency, meaning the same logical attempt can run again without duplicating its effect; [Stripe](https://docs.stripe.com/api/idempotent_requests), a payments platform, documents one request-key design. Branches also need isolated workspaces or coordinated writes. [PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html), an open-source relational database, documents how concurrent writers can block, while [Stripe’s rate-limit guidance](https://docs.stripe.com/rate-limits) separates throughput limits from limits on active requests.

A graph runtime may help implement these controls, but arrows alone add no reliability or better judgment. I think complexity should be promoted from evidence: measure the bottleneck, branch duration, throttling, retry rate, join completeness, and replay success, then add only the topology that improves the result. If independent, latency-sensitive calls are already required, start with a DAG rather than serializing them by ritual.

For runtime returns, see [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](/blog/everyone-discovered-loops-nobody-agrees-what-the-word-means/). Once topology is chosen, [“The 105 minutes after the graph”](/blog/the-105-minutes-after-the-graph/) covers evaluation, typed state, and the trust layer around execution. Choose the smallest graph that tells the truth about the work.

<span class="chapter-tldr__label">In short</span>
<p>Wider topology pays only when its latency, coverage, or recovery gain exceeds the cost of joins, retries, isolation, limits, observability, and replay.</p>
</div>
