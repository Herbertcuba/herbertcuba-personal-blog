# When your AI workflow actually needs a graph

Workflow topology describes how stages and dependencies connect. A pipeline is the simplest graph topology: one ordered path through the work.

A sci-fi launch sequence stays ordered because each stage enables the next. A fleet engagement needs independent units, changing routes, and convergence, a controlled merge of results. Turning the launch into a fleet graph only adds mission-control software. In a [2026 article on X, formerly Twitter](https://x.com/AnatoliKopadze/status/2080668775796314331), Anatoli Kopadze put it plainly: “A graph buys breadth. It does not buy better judgment.” I think production needs the minimum topology that expresses the work honestly.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose topology from dependencies and runtime conditions, not from how advanced the diagram looks.</p></div>

## Draw dependencies before choosing

A data dependency exists when one job consumes another’s result. A hidden resource dependency appears when jobs can change or exhaust a shared mutable resource: a file, database row, writable workspace, approval gate, or [API quota](https://docs.stripe.com/rate-limits). [PostgreSQL, an open-source relational database, documents](https://www.postgresql.org/docs/current/transaction-iso.html) one writer waiting behind another on the same row. Separate prompts do not make jobs independent.

Apply the fake-edge test: if B consumes none of A’s result and the jobs share no write, lock, quota, or side effect, their edge may be artificial. A fixed read-only snapshot creates no conflict unless its readers share another limit. I think teams should map both kinds of dependency before counting agents.

Keep work linear when sequence is real: ingest a request, validate its data shape, apply policy, persist. Replay reruns work from recorded history, and the known path keeps ownership easy to inspect. If independence is uncertain, start here and measure; if jobs are already independent and serial work misses the latency target, branch immediately. Keep validation, counting, deduplication, and fixed routing in code; use models for judgment.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep real sequence linear; remove an edge only after data and shared-resource dependencies are absent.</p></div>

## Use a DAG for genuine width

A DAG, or directed acyclic graph, has directed dependencies but no route back to an earlier stage. Fan-out starts independent branches; fan-in merges them. Five market-angle searches fit when their inputs and resources are independent.

Parallel work can remove serial waiting, but an all-required merge waits for its slowest branch. [AWS Step Functions, Amazon’s managed workflow service, documents](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html) this behavior. The critical path is the longest required chain, so there is no universal speedup. I think the merge is the real product decision.

The merge needs expected branch IDs and a join policy for handling missing results. A retry budget caps retries; a stop condition defines completion. Provenance records each branch’s sources and processing history. [Idempotency](https://docs.stripe.com/api/idempotent_requests) means repeating a write does not repeat its effect; a side-effect boundary says which stage may write. For concurrent writes, isolation gives each branch its own workspace or record; otherwise use one ordered writer.

This example machine-readable review contract makes those rules enforceable without prescribing a framework:

```yaml
topology: fan_out_fan_in
run_id: market-report-042
expected_branch_ids: [angle-1, angle-2, angle-3, angle-4, angle-5]
mutable_resource_keys: []
join_policy: all_required
retry_budget: 1
stop_condition: all_expected_valid
owner: research-platform
failure_deadline: 10m
side_effect_boundary: merge_only
replay_evidence: required
```

Review tooling should reject fan-out when branches can write the same record without isolation or an ordered writer. It should also reject any merge that cannot identify a missing branch.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A DAG earns its place through independent work, safe writes, a governed merge, and measured benefit.</p></div>

## Add routes and cycles when state changes

Runtime state is the stored record of a run’s current condition. A conditional graph chooses the next stage from it; a cyclic graph can return to an earlier stage. Low evidence might trigger another source check, while two reviews planned in advance remain acyclic. I think a cycle belongs only when changed state changes the next action.

Every return needs a stop rule and a hard limit on attempts, time, or cost. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](/posts/everyone-discovered-loops/) examines feedback terms, ownership, and exits. When replay and external side effects dominate, [Temporal, a durable workflow platform](https://docs.temporal.io/workflow-definition), records event history and replays deterministic workflow code. Neither a durable engine nor an agent-graph framework prevents a retried external write from happening twice; idempotency still belongs at the side-effect boundary.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Add a route or cycle only for a state-dependent decision, and give every return a reason to stop.</p></div>

## Keep the graph-shaped part bounded

Each branch adds a failure boundary and consumes API quota, tokens, and time. At the merge, results can arrive late, twice, or not at all. Partial-failure rules, visible branch IDs, and replay evidence therefore belong in the approval decision. Graph tooling makes coordination cheap to draw but expensive to govern.

My take is a hybrid: a linear spine with bounded graph bursts for research or verification. Measure critical-path latency, completion coverage, the share of expected results returned, duplicate effects, and cost per successful run before and after each change. I don’t know a universal branch limit. I think review should reject a branch or cycle without independent work, an owner, a failure deadline, replay evidence, and a measurable target.

Ask: What must wait for an earlier result? What can run independently without touching the same mutable resource? Can runtime state change the route or stop rule? Can the system detect, explain, and replay a partial failure? After topology is chosen, [“The 105 minutes after the graph”](/drafts/67821675/) covers evaluation, validated state, and trust controls. The production choice is the smallest topology that tells the truth and survives failure.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Approve graph complexity only when its measured production benefit exceeds the cost of governing its failures.</p></div>
