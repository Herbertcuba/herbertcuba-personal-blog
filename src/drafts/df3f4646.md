# Choose the smallest graph that fits the work

Graph tooling makes coordination cheap to draw and expensive to govern. I think the hierarchy is backwards: a pipeline is already a graph, the simplest topology, with one ordered path.

Picture a launch sequence beside a fleet engagement. Launch stages wait because each enables the next; fleet units move independently and converge as conditions change. Turning the launch into a fleet graph adds mission-control software without changing the work. Choose the minimum topology that expresses the workflow’s dependencies.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A pipeline is a graph. Add topology only when dependencies or runtime state require it.</p></div>

## Map dependencies before topology

The first design artifact, I think, should map what each job consumes and changes. A data edge means one job needs another’s output. A resource edge means jobs share a mutable resource: a file, database row, approval gate, workspace, or quota one can change or exhaust.

Jobs can conflict without exchanging results. [PostgreSQL, the open-source relational database, documents](https://www.postgresql.org/docs/current/transaction-iso.html) how one writer may wait behind another on the same row. Parallel reads can remain independent when both jobs use the same immutable snapshot, input captured and frozen at a particular time, rather than a changing source. Apply the fake-edge test: if B consumes none of A’s output and the jobs share no mutable resource, lock, quota, or side effect, their edge may be artificial.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Map data flow and shared resources first. Separate prompts do not make work independent.</p></div>

## Keep sequence linear and branch for width

A pipeline is one ordered path. Keep it when sequence is real: receive, validate schema, apply policy, persist. Put validation, routing, counting, and deduplication in deterministic code. I think visible sequence helps because ownership and recovery remain easy to trace.

A DAG, or directed acyclic graph, allows branches but no directed route back to an earlier node. Fan-out starts independent work; fan-in merges it. Parallel work saves time only when it removes waiting from the critical path, the longest required chain. An all-required merge still waits for its slowest required branch, as [AWS Step Functions, Amazon’s cloud workflow service, documents for its parallel step](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html).

Suppose market research starts `angle-1` through `angle-5`. I think the merge is the real decision. It expects all five identifiers by a deadline; if `angle-4` times out, mark it missing, retry once under the same `run_id`, a stable identifier for the logical run, then fail or escalate instead of silently merging four. Provenance is each result’s source and execution trail. Idempotency means a retry cannot repeat an external effect, as [Stripe, a payment platform, illustrates in its API documentation](https://docs.stripe.com/api/idempotent_requests).

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use a DAG only when independent work is real and the merge can govern absence, delay, and retry.</p></div>

## Let runtime state earn a return

A conditional graph selects the next edge from current state; a cyclic graph can revisit earlier work. A state machine is the runtime model that records the current step and its allowed transitions. I think a cycle earns its place only when changed state alters what happens next, such as a retryable error, weak evidence needing another check, or a result that triggers human escalation.

If two review passes are known beforehand, use ordered DAG nodes. Reserve a cycle for a runtime decision to return, exit, or escalate, with a stop condition and hard cap. A production hybrid can keep intake, policy, approval, and persistence on a linear spine while one bounded research stage branches and converges. [Everyone Discovered Loops. Nobody Agrees What the Word Means.](/posts/everyone-discovered-loops/) is the companion article on feedback terminology, ownership, and exit conditions.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Let state earn a route or return, and contain dynamic work inside a simple control spine.</p></div>

## Make the coordination tax executable

A wider topology brings partial failures, quota pressure, repeated model calls, and write conflicts. Isolation means separate transactions or workspaces that stop writes from racing or overwriting. Ask four questions: What waits on earlier output? What runs without the same mutable resource? Can state change the route or stop? Can the system detect, explain, and replay a partial failure? Record the answers:

| Contract field | Decision it records |
| --- | --- |
| `run_id`, `expected_branch_ids` | Stable run identity and every expected branch. |
| `mutable_resource_keys` | Files, records, quotas, approvals, or workspaces a branch may touch. |
| `join_policy`, `failure_deadline`, `owner` | Required results, tolerated absence, deadline, and accountability. |
| `retry_budget`, idempotency key | Maximum attempts and the identity preventing a duplicate effect. |
| `stop_condition`, hard cap | The state test ending a cycle and its absolute limit. |
| Replay evidence, rollback | Retained inputs and traces, plus side-effect recovery. |

Reject fan-out when two branches can write the same database record without isolation or sequential writes. When replay dominates, use durable orchestration: a state-machine runtime that persists steps, inputs, transitions, timers, retry history, and external results needed to resume after failure. A graph API alone does not guarantee that persistence.

I don’t know whether a branch pays without a baseline. Compare critical-path latency, completion coverage, the share of runs returning every required output, duplicate effects, and cost per successful run before and after. My take: approve a branch or cycle only when its owner can show independent work or a state-dependent route, measured benefit, and replayable failure controls within a declared deadline. [The 105 minutes after the graph](/drafts/67821675/) covers schema-checked workflow state, evaluation, and trust controls after topology is chosen.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Approve only the smallest topology whose measured gain beats its coordination tax.</p></div>
