A pipeline is already a graph: one ordered path through a set of jobs. So “pipeline or graph?” is the wrong production question. Ask how much topology the work can justify.

I think the default should be the smallest shape that expresses the real dependencies. Instrument it, then add branches or return paths only when evidence demands them.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose topology from the work’s dependencies, and make every extra branch, join, and cycle earn its cost.</p></div>

## Draw dependencies before choosing a runtime

For each job, record the output it consumes and the resources it can change. A data dependency connects a producer to a consumer. A resource dependency connects jobs that touch the same mutable resource, such as a file, database row, workspace, approval gate, or limited API quota.

```text
data edge:      A ── result ──▶ B
resource edge:  A ── write ──▶ [shared state] ◀── write ── B
no edge:        A                         B
```

The second line is easy to miss. [PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html), the open-source relational database, documents how one update may wait for another to finish. Shared API limits create similar coupling, while concurrent reads from an immutable input do not create a write conflict.

I think the fake-edge test should be simple: if B does not consume A’s result, and the jobs neither change the same resource nor compete for a constrained quota, the edge may be artificial. Remove it before adding an agent.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Map data flow and shared-resource conflicts; separate prompts alone do not make two jobs independent.</p></div>

## Match topology to the route

The useful shapes differ because the work behaves differently:

```text
Pipeline:       A → B → C → D

Branched DAG:       ┌→ B ─┐
                A ──┤     ├──→ D
                    └→ C ─┘

Cyclic graph:   A → B → C
                    ↑   │
                    └───┘
```

Keep the pipeline when each stage needs the previous result or authorization. For example, schema validation must finish before a policy check, and persistence must wait for that decision. Use ordinary code for deterministic validation, counting, deduplication, and fixed routing. I think this ordered path is a strong production artifact because replay and ownership remain obvious.

Use a DAG, a directed graph with no path back to an earlier job, when work is genuinely wide. Fan-out starts independent branches; fan-in merges them. [Amazon Web Services Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), a managed workflow service, waits for every parallel branch to terminate. Parallel work removes serial waiting, but a complete join still inherits its slowest required branch on the critical path, the longest chain that must finish.

Choose a conditional graph when current state selects the next route. Add a cycle only when state can send work back after something like a retryable error or failed refinement check. The return needs a meaningful stop rule and a hard step or cost limit. More arrows do not improve model judgment.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use a pipeline for real sequence, a DAG for independent breadth, and a conditional or cyclic graph for state-driven routing.</p></div>

## Put a contract around the complicated part

I think the merge is the real architecture decision. It must know which branches were expected, identify missing results, preserve source provenance, and apply a policy: retry, accept a threshold, collect survivors, or fail the run.

Retries need idempotency, a contract that prevents the same logical operation from repeating its effect. [Stripe’s payment API documentation](https://docs.stripe.com/api/idempotent_requests) shows one mechanism: an idempotency key permits a safe retry. Isolated workspaces, quota-aware concurrency, branch traces, replayable inputs, and measured model-call costs complete the coordination tax.

A hybrid confines that tax. At a high level, the Content Engine behind this article can be represented as a linear control spine, separate bounded checks, a convergence gate, and a return route when the result requires correction:

```text
brief → produce → ┌→ check A ─┐
                  ├→ check B ─┼→ gate → publish
                  └→ check C ─┘    │
                       ↑            │ correction needed
                       └────────────┘
```

Normal progress stays easy to explain, while parallel checks and state-driven rework remain contained. The graph-shaped section earns its place without taking over the system.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A hybrid keeps a linear control spine and contains coordination inside the stages that benefit from branching or rework.</p></div>

A launch sequence maps to a pipeline because each completed stage enables the next. A fleet engagement maps to a graph because independent units act, routes change with events, and results converge. Modeling the launch as a fleet only creates more mission-control software that can fail.

## Ask four questions, then measure

Before choosing a framework, ask:

1. What must wait because it consumes an earlier result?
2. What can run independently without touching the same mutable resource?
3. Can runtime state change the next route or stopping condition?
4. Can the system detect, explain, and replay a partial failure?

If required independent work would miss the latency target when serialized, start with bounded fan-out. Otherwise, start linear and measure branch duration, throttling, retries, join completeness, and replay success before widening it. I think complexity should follow observed work, not the ease with which a framework draws it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose the minimum truthful topology, measure its limits, and promote only proven independent work or state-driven decisions into a more complicated graph.</p></div>
