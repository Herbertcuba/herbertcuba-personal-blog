# Choose the smallest workflow topology that tells the truth

AI teams often call a graph advanced and a pipeline primitive. I think that reverses the decision. A pipeline is a graph with one directed path. A directed acyclic graph, or DAG, can branch and merge without returning, while a cyclic graph has a return path.

Anatoli Kopadze, author of an [X article on graph engineering](https://x.com/AnatoliKopadze/status/2080668775796314331), writes: “A graph buys breadth. It does not buy better judgment.” Evidence and validation do the judging.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose the minimum topology that expresses the work’s order, width, and state changes; extra arrows add coordination, not judgment.</p></div>

## Separate sequence from shared-resource control

Take a request through ingest → schema validation → policy check → persistence. Each stage consumes the previous result or authorization, so a pipeline keeps ownership, retries, and replay order obvious.

The fake-edge test has two parts. If B does not consume A’s result, their edge may be artificial. Yet they are independent only if they avoid the same mutable resource, a shared file, record, workspace, or approval gate either can change. Shared immutable reads are safe, but updates to one record need serialization or a transaction; [PostgreSQL, an open-source relational database, documents waiting on locked rows](https://www.postgresql.org/docs/current/transaction-iso.html).

A shared API quota calls for a queue or concurrency limit, not a false edge. I think confusing work order with resource admission creates graphs that hide why jobs actually wait.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Draw an edge for required order; use queues, limits, partitions, locks, or transactions for independent work that shares capacity or mutable state.</p></div>

## Design the join before the fan-out

Fan-out starts independent branches; fan-in merges them. Five jobs might research separate market angles and merge surviving evidence. [AWS Step Functions, Amazon’s managed workflow service, documents a Parallel state](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html) that waits for every branch. That is one all-required policy, not a universal default.

I think the merge is the real architecture decision. It needs stable expected branch identifiers, required and optional results, a deadline, and a timeout policy. It should preserve provenance, meaning the inputs, sources, models, and tools behind each result. The 2013 peer-reviewed article [“The Tail at Scale,” by Google researchers Jeffrey Dean and Luiz André Barroso](https://www.barroso.org/publications/TheTailAtScale.pdf), is not an agent benchmark, but it explains why an all-required merge inherits its slowest required branch.

A compact transition contract makes partial failure testable:

```text
JoinState = Open | Ready | Finalized(revision)
Event = Succeeded(branch_id, idempotency_key, output_hash) | TimedOut(branch_id)
Open + required results complete -> Ready
Finalized(v1) + late success -> Finalized(v1) + audit for possible v2
any state + unknown branch_id -> reject
```

Each stable idempotency key names one external effect, preventing a retry from repeating it. Branch replay uses recorded inputs and suppresses committed effects; a full rerun gets a new run identity but reuses effect keys unless a new effect is authorized. Counting, duplicate rejection, schema validation, routing predicates, and completeness belong in deterministic code. Models belong where judgment is required.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Fan out only after branch identity, join completeness, late-result handling, replay boundaries, and duplicate-effect protection are explicit.</p></div>

## Let runtime state earn routes and cycles

Conditional routing means current state selects the next edge. A risk score might choose automatic approval or human review while the graph remains acyclic. A cycle returns to earlier work for a retry or refinement.

I think a return edge earns its place only when changed state can change the next attempt. Give it a stop rule and a hard step, time, or cost limit. [LangGraph, a framework for stateful workflows, documents state-selected edges and a recursion limit](https://docs.langchain.com/oss/python/langgraph/graph-api), but mechanics do not prove that looping improves an answer. If two passes are known in advance, keep two DAG stages. [“Everyone Discovered Loops. Nobody Agrees What the Word Means.”](https://www.cubagarcia.com/posts/everyone-discovered-loops/) covers loop terms and exit conditions in depth.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use a condition when state chooses a route, and a cycle only when changed state justifies returning and an explicit rule can stop it.</p></div>

## Promote the smallest useful hybrid

A hybrid keeps a linear backbone with short graph-shaped bursts. I think this is often the strongest production shape: ordered intake, policy, approval, and persistence around parallel research or verification.

Starting linear is a default, not dogma. If mandatory API reads are independent, use immutable inputs, fit within quotas, and miss the latency objective in sequence, start with fan-out. Then compare against a linear baseline using predeclared, service-specific limits for elapsed time, completeness, cost, and operator minutes. Inject a required timeout, duplicate completion, and late optional result.

Name the promotion approver, service and data owners, incident owner, rollback authority, and risk tier. I don’t know whether width pays until the gain survives failure without weakening recovery. A durable workflow engine may supply state, retries, and traces, but the team owns missing-result policy and external effects.

Four questions decide the shape: What must wait for an earlier result? What can run without shared mutable resources? Can state change the route or stop rule? Can the system explain and replay partial failure? Once topology is chosen, [“The 105 minutes after the graph”](https://www.cubagarcia.com/drafts/67821675/) covers evaluation, typed state, and trust controls. Complexity should enter production only after the work proves it belongs there.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Keep a linear backbone and retain each graph burst only when benefit, recovery, and named owners justify its coordination tax.</p></div>
