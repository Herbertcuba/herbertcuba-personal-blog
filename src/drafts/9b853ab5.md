An engineer named Jonas Risbrandt posted a compact history of agentic coding [on LinkedIn](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz) on July 25.

> "First, we talked about prompting."

Two sentences later, he reached the current wave:

> "Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing."

Each wave looked like a feature. Each exposed a fault line under the previous design. I think Jonas found the pattern inside four years of agent frameworks.

A day earlier, Anthropic launched [Claude Opus 5](https://www.anthropic.com/news/claude-opus-5). The company called it its "most aligned model to date" after a pre-deployment behavioral audit. [The Hacker News thread](https://news.ycombinator.com/item?id=49038433) drew over 1,700 upvotes. Attention stayed on the model while engineering work moved into the loops and state around it.

I call this the State Contract Ladder. Every step adds a firmer contract around what an agent may know and do.

<div class="article-tldr"><span class="article-tldr__label">Article TL;DR</span><p>Prompts give instructions. Loops keep work moving, while graphs expose possible routes. ## Four waves through one article pipeline

Our running example moves an article through twelve states, from an idea inbox to publishing.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The same pipeline grows from one prompt into a loop, then a graph, and finally a typed state machine. Each version adds control, while the last one makes the agent's working record inspectable.</p></div>

### Wave one: the prompt carries the process

A prompt is the instruction sent to a language model. The first version can fit in four lines:

```text
You are a content pipeline. Take this article idea.
Research it, write it, review it, fact-check it, publish it.
Ask the human if anything is unclear.
```

This works in a demo. Production incidents soon add rules about sources and stale numbers. The prompt starts carrying workflow and memory, with little for code to inspect or enforce.

### Wave two: the loop keeps working

ReAct means Reason plus Act. The model chooses an action, calls a tool, reads the result and repeats.

```python
while done is False:
    thought = model.reason(context)
    action = model.act(thought)
    result = tools[action.name](action.args)
    context.append(result)  # the chat log carries state
```

The loop can research and revise, yet its state often lives in the message history. This article exposed the failure. Fact-check changed a stale Hacker News count to "over 1,700." A later revision pulled the old value from context.

Both values remained in the log, with no verified field to settle the conflict. I think this is where a useful loop becomes chat-log archaeology.

### Wave three: the graph exposes the route

LangGraph is a Python agent framework. Its `StateGraph` class connects work nodes with edges that define the allowed routes.

```python
graph = StateGraph(MessagesState)
graph.add_node("research", research_node)
graph.add_node("draft", draft_node)
graph.add_node("fact_check", fact_check_node)
graph.add_conditional_edges("fact_check", route_by_verdict)
```

`MessagesState` is LangGraph's container for conversation messages. The graph shows a failed fact-check returning to draft. A node may still contain a ReAct loop whose memory is a transcript. The route is visible while its values remain unclear.

[LangGraph's documentation](https://docs.langchain.com/oss/python/langgraph/graph-api) supports a shared state schema. Teams choose how strictly they enforce it, and loose dictionaries can still cross node boundaries.

### Wave four: the state gets a contract

A Python `TypedDict` is a dictionary with declared keys and value types. `Literal` narrows a field to fixed allowed values. A type checker can flag mistakes before runtime.

```python
Status = Literal[
    "research", "draft", "slop_review", "fact_check", "publish"
]

class CardState(TypedDict):
    card_id: str
    status: Status
    brief_version: int
    kickback_count: int
    sources_verified: bool
    hn_points: str  # "over 1,700"

def transition(raw: dict, to: Status) -> CardState:
    state = validate_card_state(raw)  # runtime check
    if to == "publish" and state["sources_verified"] is False:
        raise IllegalTransition("unverified sources")
    return {**state, "status": to}
```

`TypedDict` helps during static checks. Pydantic or another runtime validator inspects data from a model or database. Here, `sources_verified=False` blocks publish even when the model requests it.

The audit question now has a short answer. At review, the writer carried a known brief version, kickback count and source-verification value. An engineer can inspect those fields without replaying the conversation.

## Why typed state changes the engineering

The fourth wave changes how failure appears to the team.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state turns silent corruption into a rejected write or an illegal transition. It gives runtime validation a contract and gives operators a record they can audit.</p></div>

Types validate shape and allowed values. Source checks decide whether a claim is true. The contract catches corruption at a boundary where the system can stop.

LangGraph already supports shared schemas, so this wave grew inside the graph wave. Teams now validate state on write, persist accepted transitions and assign an owner to the schema.

[Inngest AgentKit](https://news.ycombinator.com/item?id=43426164) described a typed state machine in TypeScript in March 2025. MemState used Python validation on write in December. Turn and [Agd](https://news.ycombinator.com/item?id=47224560) arrived in Rust and Zig in March 2026. These small projects are existence proofs across four languages. Broad adoption remains an open question.

I think the craft move is familiar. Rails 1.0 made web state legible in 2005 through reviewable schemas and migrations. ML and Hindley-Milner made static type discipline practical in the 1970s. Agents now apply it to facts carried between model calls.

A legible [AI operating model](/posts/building-the-ai-operating-model/) needs the same record. Ownership becomes concrete when a named engineer can inspect the state, review its schema and trace its last transition.

## What breaks when state stays loose

Model alignment and system accountability cover different parts of an agent run.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A pre-deployment model audit covers behavior in a test. Production accountability also needs persisted tool results and validated state, especially when an agent touches money or rights.</p></div>

Anthropic's alignment claim came from pre-deployment testing. Alignment here means the model followed its maker's intended rules. A production agent later adds search results and saved memory outside that test.

I think the qualifier deserves as much attention as the headline. In *Blade Runner*, the Voight-Kampff test measures a subject in an interview room. Passing that test tells Deckard something about the subject in front of him. It says little about every record the subject will receive once the door opens.

Calling the full workflow accountable from the model audit alone is alignment theater. The model may follow its instruction perfectly while acting on a stale field.

The [EU AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj) points in this direction. Article 12 requires automatic event logging for high-risk AI systems. Article 26(5) requires deployers to keep logs under their control. The main Annex III obligations began applying on August 2, 2026. Persisted state can become evidence in a high-risk domain.

Loose state also creates ordinary operating pain. One corrupt field in a finance agent can stall month-end close and start a restatement conversation. Every field that escapes verification adds [verification debt](/posts/2026-03-09-verification-debt-crisis/).

I don't know whether typed state is the final wave. Shared memory across many agents looks like the next fault line. A team of agents will need common rules for which claims are current and who may replace them.

## What to do on Monday morning

Start with one long-running agent whose mistakes already require human review.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Write the fields your agent carries, guard one costly transition and persist each accepted change. Review the schema like any other production contract.</p></div>

A one-shot ticket classifier may carry little durable state. Choose a workflow that can publish, transfer money or update a customer record.

Write down every field carried between steps. Give each field a type and an owner. Put the schema in version control, then review changes once per sprint.

Guard the highest-cost transition. This content pipeline rejects `publish` when `sources_verified=False`. Validate state when it enters a node and again before the expensive action.

Persist accepted transitions with the actor, timestamp and schema version. An addressable history makes [reversibility](/posts/reversibility-is-the-new-correctness/) a property of the state machine. An engineer can return to a valid checkpoint and explain the change.

I think one boundary is enough for the first pull request. Diff the schema against the state your agent already carries. Missing fields and leftover prompt keys show where verification debt has been collecting.

Jonas closed with a dry summary. Agent builders had replaced code with a prompt before slowly reintroducing code around it. Monday's work is to put that code around the transition you most need to trust.
