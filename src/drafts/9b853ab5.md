On July 21, 2026, engineer [Jonas Risbrandt described the recent evolution of agentic coding](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz). Agentic coding means software in which an AI model can plan work and call tools instead of merely answering a question.

> “Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing.”

Risbrandt then asked, “Haven't we just invented... a programming language?” I think the more important point is that prompts, loops, and graphs could coordinate work without recording why one particular output had permission to affect a live system.

Three days later, Anthropic, the company that develops the Claude model family, [announced Claude Opus 5](https://www.anthropic.com/news/claude-opus-5) for long-running, multi-step work. Anthropic said a pre-deployment automated behavioral audit found it to be “our most aligned model to date.” The related [Hacker News discussion](https://news.ycombinator.com/item?id=49038433), on a software forum, drew over 1,700 points, a measure of attention rather than endorsement.

A stronger model is useful, but its evaluation cannot identify which evidence, revision, and approval authorized a later production action. I think typed state matters because it gives that authority a record software can inspect.

## Four waves, one publication card

Consider one content-production card moving from research to publication. Its draft mentions the changing Hacker News score above, so the accepted wording must remain “over 1,700 points.” Only the exact revision that passed factual review and human approval may be published.

### Prompt

A prompt is a natural-language instruction that tells a model what to do and describes the constraints in prose.

```text
Research the card, write the article, verify its sources,
and publish only the approved revision.
Use “over 1,700 points,” never an exact score.
```

This can power a demonstration, but production exceptions soon add retry rules, approval policy, recovery steps, and factual corrections. The prompt is wearing a toolbelt, while “approved revision” still points to no machine-checkable revision.

### Loop

A loop lets the model choose an action, inspect the result, and repeat until it reaches a stopping condition.

```python
while card.status not in {"done", "escalated"}:
    action = model.choose(message_history)
    result = tools.run(action)
    message_history.append(result)
```

The message history becomes informal state, meaning the facts carried between steps. This task's history records an exact Hacker News score entering through an early specification, a factual correction, and a later revision restoring the stale number. Both versions remained plausible messages, so the loop kept moving. I think this is the production danger: corrupted state can resemble progress.

### Graph

A graph represents a workflow as named nodes joined by directed edges. It makes the route and its possible branches visible.

```text
research → draft → fact_check → human_approval → publish
             ↑          |
             └─ kickback┘
```

Now the route after a failed fact check is visible, but the diagram cannot show whether the next node received the corrected source record or an older message. A node may still hide a loop carrying the same ambiguous history. The roads are visible while the load remains hard to inspect.

### Typed state

Typed state defines the fields a workflow may carry and the values those fields may hold. Persistence stores that record beyond a single model call. The following illustrative boundary uses [Pydantic, a Python library for runtime data validation](https://docs.pydantic.dev/latest/concepts/models/), and a locked database transaction:

```python
class PublishState(BaseModel):
    model_config = ConfigDict(strict=True)
    card_id: str
    version: int
    status: Literal["fact_check", "human_approval", "publish"]
    revision_id: str
    content_hash: str
    approved_revision_id: str | None
    approved_content_hash: str | None
    sources_verified: bool

with transaction():
    current = PublishState.model_validate(lock_card(request.card_id))
    require(request.expected_version == current.version)
    require(current.status == "human_approval")
    require(current.sources_verified)
    require(current.revision_id == current.approved_revision_id)
    require(current.content_hash == current.approved_content_hash)
    write_publish_intent_once(request.idempotency_key, current)
    advance_if_version(current.card_id, current.version, "publish")
```

The schema declares the expected shape, and runtime validation rejects malformed values. A content hash fingerprints the draft. The expected-version check rejects a request based on an older database row, while the transition guards decide whether the locked current row may publish. An idempotency key identifies one intended external action, so a retry can return the existing intent instead of creating a duplicate.

Those checks do not prove the article true; they ensure that the released revision is the one marked verified and approved. Replace the article with an invoice or an access request and the boundary stays recognizable: the amount or permission, evidence, approver, and action must belong to the same accepted version.

## The win is a checked boundary

Typed state does not replace graphs. [LangGraph, LangChain's framework for graph-based agent workflows](https://docs.langchain.com/oss/python/langgraph/graph-api), already supports shared state schemas. In March 2025, [Inngest's TypeScript AgentKit described routing with a “fully typed state machine”](https://news.ycombinator.com/item?id=43426164), meaning that allowed states and routes are declared in code. These are signs of architectural convergence, not proof of broad adoption.

The engineering shift is from allowing a schema to enforcing it where an agent can create an external effect. I think typed state deserves special attention among Risbrandt's list because it makes the other controls answerable. A retry needs to say which accepted state it resumes from, and observability needs named fields whose changes can be compared.

This is also where model alignment and system accountability separate. Anthropic's claim concerns behavior observed before deployment. It cannot establish that a live publish request carried the current approval. My take is that alignment theater begins when a model evaluation is treated as proof that a production action had authority.

An AI Operating Model is the ownership, evidence, decisions, and controls around an AI system. The business or system owner defines acceptable evidence and forbidden transitions; engineering makes those rules executable. Typed state gives both sides one contract to review.

## Implicit state creates verification debt

An execution trace records which steps ran. It may show `human_approval` before `publish` without showing which revision the human approved. Without that link, incident reviewers reconstruct the decision from prompts, messages, and tool traces.

I call that gap verification debt: the distance between what a workflow assumes and what its retained records can prove. In content publishing, the debt is a stale claim. In invoice approval or access provisioning, the same design can leave a business owner unable to show that the amount, identity, evidence, and approval belonged to one transaction.

The [European Union's 2024 AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj) points in the same direction without prescribing typed state. Article 12 requires high-risk AI systems to support automatic event recording, while Article 26(6) requires deployers to retain generated logs under their control. The law neither classifies this workflow as high risk nor mandates this architecture. Still, a rejection tied to a version is more useful audit evidence than a chat transcript containing the right words somewhere.

Typed state also makes reversibility concrete. Reversibility means returning to an earlier accepted state or applying a deliberate correction. Versioned records can support replay, while idempotency can prevent a retry from duplicating an action. Neither can unsend an email or reverse a completed payment, so the state machine must name the compensating action as well as the forward path.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Verification debt grows when traces show activity but cannot prove which facts and approval authorized it. Versioned state turns that missing proof into a visible engineering problem.</p></div>

## Put the contract into review

Computer scientist Robin Milner's [1978 paper on type polymorphism](https://doi.org/10.1016/0022-0000%2878%2990014-4) helped formalize reasoning about which values programs may accept. “Strong typing” has no single universal definition, but the useful craft remains: declare valid forms and reject invalid combinations early.

[Ruby on Rails 1.0, released in December 2005](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh), brought conventions and database migrations into a widely used web framework. A migration is a versioned change to stored database structure. Rails did not invent web applications; it made structural assumptions easier to see, reproduce, and review. Typed state applies that same craft to the facts an agent carries toward an external action.

On Monday morning, put one write-capable agent in a 30-minute review with the enterprise architect, engineering lead, and system owner. Pick one consequential transition. Name the current version, required evidence, approving role, retention rule, and a transition that must never succeed. Then persist both acceptance and rejection, rather than leaving either as a line in a model transcript.

Test the boundary with three cases:

```text
stale approved revision → rejection, no publish intent
current approved revision → one publish intent
retry after interruption → existing intent, no duplicate
```

Run the incident review from persisted state alone. If the team cannot explain what was accepted, which guard decided, and what followed, it has found the next verification debt. This is how a pilot earns production ownership.

I don't know which agent framework will dominate. I think the durable artifact will be the state contract because it can survive changes in models and orchestration. The next agent wave belongs to teams that can show, in software, why an uncertain model was allowed to act.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Review one consequential transition as a software contract, test its refusal paths, and demand an incident explanation from persisted state. Craft discipline is back when authority becomes executable.</p></div>
