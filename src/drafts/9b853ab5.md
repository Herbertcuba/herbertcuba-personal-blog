On July 21, engineer Jonas Risbrandt [described agentic coding's progression](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz): “Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state...” His punchline: “Haven't we just invented... a programming language?”

Three days later, Anthropic [said](https://www.anthropic.com/news/claude-opus-5) its pre-deployment behavioral audit found Opus 5 to be “our most aligned model to date.” The [Hacker News discussion](https://news.ycombinator.com/item?id=49038433) drew over 1,700 points. I think those events belong together because a model audit cannot reconstruct which production evidence authorized an action after a retry. Better models will keep arriving, while the immediate engineering gain comes from smaller loops organized around explicit state.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Model behavior can improve before deployment while production authority remains buried in an agent's history.</p></div>

## Four waves through one publishing decision

An early brief for this article used 1,723 Hacker News points. Fact-checking later approved “over 1,700 points,” yet another run restored the old number. Call the accepted article `v8` and the stale article `v7`. Only `v8` may publish.

The first wave puts the program in a prompt, the instruction sent to the model:

```text
Research, draft, fact-check, publish.
Use the fact-checker's approved wording.
```

The prompt becomes a toolbelt of policies, with no checked pointer to the approved revision.

A loop repeats model reasoning and tool calls until work is done:

```python
while card.status in ACTIVE_STATES:
    action = model.run(messages)
    messages.append(run_tool(action))
```

Both revisions can survive in `messages`. I think a larger context preserves the disagreement while leaving the next write without an authoritative value.

A graph makes the route visible:

```text
research -> draft -> fact_check -> approve -> publish
             ^           |
             +-- revise --+
```

The graph exposes the route, but each node can hide a loop with mixed history. [LangGraph](https://docs.langchain.com/oss/python/langgraph/graph-api) supports shared schemas, so enforcement remains a production choice: the publish service must reject an invalid request before writing an outbox record.

Typed state makes that choice explicit:

```python
class ArticleState(BaseModel):
    revision_id: str
    approved_revision_id: str | None
    status: Literal["draft", "approved", "publishing", "published",
                    "amendment_pending"]
    evidence_ids: list[str]
    effect_id: str | None = None

def request_publish(db, s: ArticleState):
    require(s.status == "approved")
    require(s.revision_id == s.approved_revision_id)
    require(bool(s.evidence_ids))
    key = f"publish:{s.approved_revision_id}"
    with db.transaction():
        db.states.save(s.model_copy(update={"status": "publishing"}))
        db.outbox.put_once(key, {"revision_id": s.approved_revision_id})
```

`BaseModel` validates shapes; the `require` calls enforce allowed state changes. A transaction commits the state and outbox record, a durable pending send. Its stable idempotency key identifies one publication across retries. After delivery, the worker saves the external `effect_id`.

Across four waves, the accepted revision moves from an instruction, through a transcript and route, into a checked record controlling the next effect.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The schema describes state, the validator governs transitions, and the transaction binds approved evidence to one pending external effect.</p></div>

## Why the old discipline works here

Types constrain representation; source review still judges the evidence. I think strong typing earns its place because the schema, validator, and transaction turn a stale revision into a rejected write instead of a silent publication.

A durable workflow history records where work resumes. `ArticleState` records accepted evidence and the next permitted move. Recovery needs both. A trace is insufficient when it cannot reproduce the authorized transition and evidence.

Type discipline is decades old. [Rails 1.0](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh) made database changes declarative and reviewable through migrations. Agent schemas apply that craft habit to state shape; runtime validators separately govern transitions. I don't know which framework will lead. The contract can outlast it.

In *The Martian*, an airlock relies on known pressure and a permitted transition. “Do something reasonable with the door” offers no safety boundary. Long-running agents deserve the same explicitness.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Types make state shape explicit, while validation and persistence turn that shape into recoverable production authority.</p></div>

## Audit the system as well as the model

Anthropic carefully scoped its Opus 5 claim to a pre-deployment audit. A production incident asks which accepted evidence and transition produced an effect. I think using the model audit to imply production accountability becomes alignment theater when the authority record cannot be replayed.

For agents in high-risk domains, the [EU AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj) addresses event logging in Article 12 and log retention in Article 26(5). Teams choose the implementation. Typed, persisted state lets leaders inspect evidence, effect, retention, and access directly.

A one-shot classifier with a low-risk output carries a lighter control burden. Repeated external writes require an AI Operating Model people can inspect. The gap between prompt policy and enforced state is verification debt, and every unreplayable retry adds interest.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Model audits describe pre-deployment behavior; inspectable state lets an organization review the authority behind a production effect.</p></div>

## Put one transition under contract on Monday

Start with one consequential boundary such as `approved -> publishing`. Bring a state-contract diff to review with accepted evidence, owner, retention and access rule, and illegal condition. Size the work to the current platform.

Test the stale request first: `v7` creates no state or outbox entry. Then test `v8`, which commits `publishing` and its outbox entry together. Stop before delivery, retry through another worker, and verify one effect. An explicit `published -> amendment_pending` transition preserves the original `effect_id` and makes reversibility a state-machine property.

I think this boundary test pays down more verification debt than another prompt rule. My take is that teams granting agents external write authority will standardize state contracts before their next orchestration migration. If 2027 incident reviews reconstruct authorized actions and evidence from traces alone, that prediction fails.

Jonas wrote, “We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt.” The returning code is the part that lets an agent earn authority.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A consequential agent action should begin with accepted state, survive a retry as one effect, and carry an explicit correction path.</p></div>
