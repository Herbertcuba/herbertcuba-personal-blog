On July 21, 2026, engineer [Jonas Risbrandt described the evolution of agentic coding](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz). Agentic coding lets an AI model plan work and call software tools instead of only answering a question.

> “Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing.”

Risbrandt then asked, “Haven't we just invented... a programming language?” I think he named the larger pattern correctly. Typed state adds one thing: an authority record showing which version, evidence, approval, and rule allowed model output to affect a live system.

Three days later, Anthropic, developer of the Claude family of AI models, [announced Claude Opus 5](https://www.anthropic.com/news/claude-opus-5) for long-running work. Anthropic said its pre-deployment automated behavioral audit found Opus 5 to be “our most aligned model to date.” The [Hacker News discussion](https://news.ycombinator.com/item?id=49038433), on a technology forum, drew over 1,700 points. I think the timing exposes the fault line: a model test cannot prove which facts authorized a later action.

## Four waves, one publication card

Follow one article card through drafting, fact review, approval, and publication. Fact review changed a volatile Hacker News score to “over 1,700 points,” but a later revision retrieved the older figure from stale context. Only the corrected, approved revision may publish.

### Prompt

A prompt gives a model its work and constraints in natural-language prose.

```text
Research the card, write the article, verify every source,
and publish only the approved revision.
Use “over 1,700 points,” never an exact score.
```

“Approved revision” names no machine-checkable object. As rules accumulate, the prompt serves as data contract, workflow, and runbook. Because those rules remain prose, the system cannot reliably identify which revision a human approved.

### Loop

A loop lets the model choose an action, inspect the result, and repeat until it reaches a stopping condition.

```python
while card.status not in {"done", "escalated"}:
    action = model.choose(message_history)
    result = tools.run(action)
    message_history.append(result)
```

The message history becomes informal state: facts carried between steps. Both the stale score and its correction can remain, so a later pass may retrieve the wrong one without breaking the loop. I think corruption can resemble progress until an external tool acts.

### Graph

A graph connects named workflow steps, called nodes, with directed edges that determine where work goes next.

```text
research → draft → fact_check → human_approval → publish
             ↑          |
             └─ kickback┘
```

A failed fact check now routes back to drafting. The graph cannot prove that the next node received the corrected revision, and each node can hide another prompt or loop. It exposes the route, not the authority of what moves along it.

### Typed state

Typed state declares the fields and values that a workflow may carry. Persistence stores that record beyond a single model call. This illustrative boundary uses [Pydantic, a Python library that validates data at runtime](https://docs.pydantic.dev/latest/concepts/models/), inside a locked database transaction:

```python
class PublishState(BaseModel):
    model_config = ConfigDict(strict=True)
    card_id: str
    version: int
    status: Literal["fact_check", "human_approval", "publish"]
    revision_id: str
    content_hash: str
    fact_report_id: str | None
    sources_verified: bool
    approved_revision_id: str | None
    approved_content_hash: str | None
    approved_by: str | None

with transaction():
    current = PublishState.model_validate(lock_card(request.card_id))
    require(request.expected_version == current.version)
    require(current.status == "human_approval")
    require(current.sources_verified and current.fact_report_id is not None)
    require(current.revision_id == current.approved_revision_id)
    require(current.content_hash == current.approved_content_hash)
    write_publish_intent_once(request.idempotency_key, current)
    advance_if_version(current.card_id, current.version, "publish")
```

The schema declares expected fields, while runtime validation rejects malformed values. A content hash fingerprints the draft. The expected-version check rejects an older request. The `require` statements are transition guards, which stop a well-formed record from taking an unauthorized route. These states and moves form a state machine.

`write_publish_intent_once` creates an outbox record, a durable instruction delivered after commit. Its idempotency key names one intent, so a retry can reuse the existing record. These controls do not prove the article true or make every destination safe against duplicates. They bind publication to one accepted revision, fact report, and approval.

The contract also fits invoice approval: bind one invoice version to purchase-order evidence and a budget owner's approval.

## Why typed state changes the boundary

Typed state does not replace graphs. [LangGraph, a graph-based agent library from AI tooling company LangChain](https://docs.langchain.com/oss/python/langgraph/graph-api), supports shared state schemas. In March 2025, [workflow infrastructure company Inngest said AgentKit, its TypeScript multi-agent library, used a “fully typed state machine” for routing](https://news.ycombinator.com/item?id=43426164). These cases show direction, not broad adoption.

Strong typing has no single universal definition. Here, typed state means a schema enforced at runtime and at the database boundary; Python annotations alone do not police inputs. It cannot verify a source or make a model correct, but it can turn a missing report, mismatched revision, or illegal move into a loud rejection.

I think that gives typed state more weight than another framework layer. Retries need a known starting record, observability needs stable fields, and persistence needs storage rules. The contract makes each control answerable against named facts.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The fourth wave exposes the state that earlier waves carried informally. Its bounded engineering win is that software can refuse an action whose evidence, version, or approval does not match.</p></div>

## What implicit state costs

An execution trace records which steps ran. It may show `human_approval` before `publish` while omitting which revision was approved. An incident review must then reconstruct authority from records designed for execution rather than proof.

I call that gap verification debt: the distance between what a workflow assumes and what its records can prove. Here, it appeared as a stale claim. In a 5,000-employee company, the same failure in invoice approval or access provisioning can mean audit work, a delayed close, or another pilot leadership will not scale.

This is where model alignment and system accountability separate. Anthropic's claim concerned behavior measured before deployment, not the evidence behind a later live request. My take is that alignment theater begins when model evaluation is presented as proof of production authority.

An AI Operating Model is the ownership, evidence, decisions, and controls around an AI system. It is legible when business defines a consequential transition, engineering enforces it, and reviewers inspect accepted and rejected records. The [European Union's 2024 AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj) points this way without prescribing typed state. For high-risk systems in scope, Article 12 requires automatic event recording, while Article 26(6) requires deployers to retain generated logs. Many obligations for systems listed as high risk in Annex III began applying on August 2, 2026. A publication workflow is not automatically high risk, but a rejection tied to a rule, version, and owner is stronger audit evidence than a transcript containing the right sentence somewhere.

Typed state also makes reversibility precise: returning to an accepted version or running a named correction after an external effect. Versioned records support replay, and idempotency can prevent a duplicate intent, but neither can unsend an email or reverse a payment. Those effects need explicit compensation paths. Shared agent memory needs the same rules, or verification debt returns at a larger scale.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Activity logs show what ran, while authority records show which facts and approval allowed it to run. Without that link, verification debt grows across incidents, audits, and attempts to move pilots into production.</p></div>

## Put the contract into review

Computer scientist Robin Milner's [1978 paper “A theory of type polymorphism in programming”](https://doi.org/10.1016/0022-0000%2878%2990014-4) presented a formal type discipline and a compile-time checking algorithm for polymorphic procedures. The craft move is old: declare valid forms and reject invalid combinations before action.

Web applications already existed when [Ruby on Rails 1.0, a web framework, arrived in December 2005](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh). Rails made database change easier through [migrations, reproducible instructions that move a schema between versions](https://guides.rubyonrails.org/active_record_migrations.html). Typed state applies that discipline to facts carried toward an agent action: assumptions become explicit, versioned, and reviewable.

On Monday, ask the enterprise architect and system owner to convene a 30-minute review with engineering and the business owner. Choose one write-capable agent and one consequential transition. Name its version, evidence, approver, retention rule, and one forbidden move. Business accepts the rule; engineering owns enforcement.

Give two engineers two weeks to implement that boundary, not a platform rewrite. Persist acceptance and rejection, then test refusal and recovery:

```text
stale approved revision → rejection, no publish intent
current approved revision → one publish intent
retry with the same key → existing intent, no second record
```

Run an incident review from persisted state alone. If the team cannot explain what was accepted, which guard decided, and what followed, it has found verification debt. This is how a pilot earns production ownership.

I don't know which agent framework will dominate. Risbrandt's sharper line was, “We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt.” I think the state contract will endure across changes in models and orchestration. The next agent wave begins when a team can show, in software, why an uncertain model was allowed to act.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Review one consequential transition as a software contract, test its refusal paths, and demand an incident explanation from persisted state. Craft discipline is back when authority becomes executable.</p></div>
