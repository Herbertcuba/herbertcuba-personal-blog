On July 21, 2026, engineer [Jonas Risbrandt described the evolution of agentic coding](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz). Agentic coding means software in which an AI model can plan work and call tools instead of merely answering a question.

> “Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing.”

Risbrandt then asked, “Haven't we just invented... a programming language?” I think he named the pattern correctly, but the deeper fault line is authority. None of the first three forms necessarily recorded why one output could affect a live system.

Three days later, Anthropic, the company behind Claude, [announced Claude Opus 5](https://www.anthropic.com/news/claude-opus-5) for long-running, multi-step work. It said a pre-deployment automated behavioral audit found the model to be “our most aligned model to date.” The related [Hacker News discussion](https://news.ycombinator.com/item?id=49038433), on a software forum, drew over 1,700 points, a measure of attention rather than endorsement. I think the events belong together: model behavior cannot tell us which evidence, revision, and approval authorized a later production action.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Agent frameworks are rediscovering ordinary software structure. Typed state matters because it gives the authority behind a model action a record that software can inspect.</p></div>

## Four waves, one publication card

Consider one article card moving from research to publication. Because it cites the changing Hacker News score, its accepted wording must remain “over 1,700 points.” Only the revision that passed factual review and human approval may be published. This card exposes what each wave leaves unresolved.

### Prompt

A prompt is a natural-language instruction that tells a model what to do and expresses its constraints in prose.

```text
Research the card, write the article, verify its sources,
and publish only the approved revision.
Use “over 1,700 points,” never an exact score.
```

Production soon adds retries, approval rules, recovery, and corrections, while “approved revision” still names no machine-checkable object. The prompt is wearing a toolbelt because prose is serving as schema, state machine, and runbook.

### Loop

A loop lets the model choose an action, inspect the result, and repeat until it reaches a stopping condition.

```python
while card.status not in {"done", "escalated"}:
    action = model.choose(message_history)
    result = tools.run(action)
    message_history.append(result)
```

The message history becomes informal state, meaning the facts carried between steps. This task's history held a stale score, its correction, and a later revision that restored the old figure. Both versions remained plausible messages, so the loop continued. I think corrupted state can look like progress until something reaches production.

### Graph

A graph represents a workflow as named nodes joined by directed edges. It makes the allowed route and its branches visible.

```text
research → draft → fact_check → human_approval → publish
             ↑          |
             └─ kickback┘
```

Now the route after a failed fact check is explicit. The graph still does not show whether the next node received the corrected source record or an older message, and any node can hide another prompt or loop. Visible routing does not make the state passed along that route inspectable.

### Typed state

Typed state defines the fields a workflow may carry and their allowed values. Persistence stores that record beyond one model call. This boundary uses [Pydantic, a Python library for runtime data validation](https://docs.pydantic.dev/latest/concepts/models/), inside a locked database transaction:

```python
class PublishState(BaseModel):
    model_config = ConfigDict(strict=True)
    card_id: str
    version: int
    status: Literal["fact_check", "human_approval", "publish"]
    revision_id: str
    content_hash: str
    approved_revision_id: str | None
    approved_content_hash: str | None
    sources_verified: bool

with transaction():
    current = PublishState.model_validate(lock_card(request.card_id))
    require(request.expected_version == current.version)
    require(current.status == "human_approval")
    require(current.sources_verified)
    require(current.revision_id == current.approved_revision_id)
    require(current.content_hash == current.approved_content_hash)
    write_publish_intent_once(request.idempotency_key, current)
    advance_if_version(current.card_id, current.version, "publish")
```

The schema declares the expected shape, while runtime validation rejects malformed values. A content hash fingerprints the draft. The expected-version check rejects an older database row, and transition guards decide whether the locked current row may publish. An idempotency key identifies one external action, so a matching retry can reuse its stored publish intent.

These checks do not prove the article true. They ensure that the released revision is marked verified and approved. For an invoice or access request, the amount or permission, evidence, approver, and action must likewise belong to one accepted version.

## Why the checked boundary wins

Typed state does not require abandoning graphs. [LangGraph, LangChain's graph-workflow framework](https://docs.langchain.com/oss/python/langgraph/graph-api), already supports shared state schemas. In March 2025, [Inngest's TypeScript AgentKit described routing with a “fully typed state machine”](https://news.ycombinator.com/item?id=43426164), with allowed states and routes declared in code. These are signs of convergence, not proof of broad adoption.

The gain comes from enforcing the contract where an agent can create an external effect. A type declaration cannot verify a source, and Python annotations do not police runtime data. Validation can reject a malformed record, while a transition guard can reject a well-formed record that lacks current approval. I think typed state deserves special attention among Risbrandt's additions because it makes retries, persistence, and observability answerable against named facts.

This is where model alignment and system accountability separate. Anthropic's claim concerns behavior observed before deployment; it cannot establish that a live publish request carried current approval. My take is that alignment theater begins when a model evaluation is presented as proof that a production action had authority. An AI Operating Model, meaning the ownership, evidence, decisions, and controls around an AI system, is legible only when business rules and retained state can be reviewed together.

## What implicit state costs

An execution trace records which steps ran. It may show `human_approval` before `publish` without showing which revision the human approved. When that link is missing, incident reviewers have to reconstruct the decision from prompts, messages, and tool traces.

I call that gap verification debt: the distance between what a workflow assumes and what its records can prove. In publishing, the debt is a stale claim. In invoice approval or access provisioning, one corrupted field can consume audit hours, delay a close, or keep a useful pilot from earning production ownership.

The [European Union's 2024 AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj) points in the same direction without prescribing typed state. Article 12 requires high-risk AI systems to support automatic event recording, while Article 26(6) requires deployers to retain generated logs under their control. This publishing workflow is not presented as high risk. Still, a rejection tied to a version gives an auditor stronger evidence than a transcript containing the right words somewhere.

Typed state also makes reversibility concrete: returning to an earlier accepted state or applying a deliberate correction. Versioned records can support replay, and idempotency can prevent a duplicate retry, but neither can unsend an email or reverse a completed payment. The state machine must therefore name the correction path as carefully as the forward path.

The next fault line appears when several agents share memory. If their common record has no declared owner, version, or allowed transitions, a multi-agent graph recreates the same unauditable mess at a larger scale.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Verification debt grows when traces show activity but cannot prove which facts and approval authorized it. Versioned state turns that missing proof into a visible engineering problem.</p></div>

## Put the contract into review

Type discipline is old. Computer scientist Robin Milner's [1978 paper “A theory of type polymorphism in programming”](https://doi.org/10.1016/0022-0000%2878%2990014-4) formalized valid uses of values while preserving generality. “Strong typing” has no universal definition, but the durable craft is to declare valid forms and reject invalid combinations early.

[Ruby on Rails 1.0, a web framework released in December 2005](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh), made database migrations standard application work. A [migration is a reproducible, versioned change to stored database structure](https://guides.rubyonrails.org/active_record_migrations.html). Rails made structural assumptions easier to see and review. Typed state applies that craft to the facts an agent carries toward an external action.

On Monday morning, ask the enterprise architect and system owner to convene a 30-minute review with the engineering lead. Pick one write-capable agent and one consequential transition. Name its current version, required evidence, approving role, retention rule, and one forbidden transition. Persist both acceptance and rejection instead of leaving either in a model transcript.

Test the boundary before changing the wider platform:

```text
stale approved revision → rejection, no publish intent
current approved revision → one publish intent
retry after interruption → existing intent, no duplicate
```

Give two engineers one sprint to put that contract around the agent, then run an incident review from persisted state alone. If the team cannot explain what was accepted, which guard decided, and what followed, it has found verification debt. Review later changes like any production interface: the system owner owns the rule, and engineering owns enforcement.

I don't know which agent framework will dominate. Risbrandt's sharper line was, “We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt.” I think the state contract will endure because it can survive changes in models and orchestration. The next agent wave begins when a team can show, in software, why an uncertain model was allowed to act.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Review one consequential transition as a software contract, test its refusal paths, and demand an incident explanation from persisted state. Craft discipline is back when authority becomes executable.</p></div>
