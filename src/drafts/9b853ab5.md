The field of AI engineering moves so fast that a technique can go from breakthrough to liability in about eighteen months. Watching that happen three times in a row is what makes this week's moment interesting.

A Swedish engineer named Jonas Risbrandt posted on LinkedIn that agentic coding has gone through three waves and is entering a fourth. His words: "Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state."

The same week, Anthropic shipped Opus 5 with the claim "most aligned to date," and the Hacker News thread pulled over 1,700 upvotes and 1,300 comments. Read the thread and a pattern emerges. The comments are not arguing about model quality. They are arguing about what breaks when agents run for hours against real systems.

I think those two events are the same signal. The industry has stopped betting on bigger models and started betting on smaller loops with typed state. Each wave in Jonas's list looked like a feature when it arrived. Each one hid the failure mode of the wave below it.

To see the fault lines, follow one small task through all four waves. The task: process an incoming invoice. Read a PDF, pull out the vendor, amount, and due date, check it against a purchase order, and flag mismatches.

## Wave one: prompts

The prompt is the program.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Wave one put the whole task in one prompt with tools attached. It works in demos and breaks silently in production, because nothing records what the agent believed along the way.</p></div>

In 2023, you handled the invoice with one big prompt. You pasted the PDF text in, described the task, and hoped. When tool use arrived, you bolted on functions: read_file, lookup_po, send_slack. The prompt grew a toolbelt.

```python
prompt = """
You are an invoice processor. Read this invoice.
Extract vendor, amount, due_date.
Call lookup_po(vendor) and compare.
If the amount differs, call send_slack(#finance).
Invoice text: {pdf_text}
"""
```

This works in a demo. In production it breaks in a specific way: the agent decides the PO number is INV-1042 because the vendor name is similar, calls lookup_po with a hallucinated ID, gets null, and then helpfully invents a plausible PO to compare against. Nobody finds out until the month-end close. When you try to debug it, the only evidence is a chat log. You need archaeology on a chat log to answer the simplest question: what did the agent believe when it called that tool?

A prompt wearing a toolbelt is still a prompt. The state of the task lives inside a text blob, mutated by every model call, invisible to everything outside it.

## Wave two: loops

The agent runs the loop, the loop hides the state.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Wave two wrapped the prompt in a reason-act-observe cycle (ReAct). That made agents useful, but the state still lived in a growing message history, and corruption compounded quietly across turns.</p></div>

ReAct (Yao et al., 2022) gave wave two its shape. ReAct stands for Reason + Act: the model writes a thought, takes an action, reads an observation, and repeats. Think, do, look, think again. Every framework shipped a version of it.

For the invoice, the loop looks like this:

```python
messages = [system_prompt, invoice_text]
while not done:
    response = llm(messages, tools=[read, lookup, slack])
    messages.append(response)
    if response.tool_call:
        result = run_tool(response.tool_call)
        messages.append(result)
    else:
        done = True
```

Now the agent can notice a missing PO number and go look it up. Real progress. But watch where the state lives: in `messages`, a list that only ever grows. By turn fourteen, the extracted amount sits in turn three's text, the PO lookup result sits in turn eight, and a correction the user made in chat sits in turn eleven. The model re-reads all of it every turn, and when two turns disagree, the model resolves the conflict silently, in whatever direction reads most plausible.

State corruption in wave two does not throw an error. It compounds. A bad extraction in turn three is still there in turn fourteen, quietly shaping every later decision.

## Wave three: graphs

The graph hides the loops.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Wave three drew the workflow as nodes and edges (LangGraph and its cousins). That made branching and retries visible, but the state flowing between nodes was usually still an untyped dict, so the mess got an org chart.</p></div>

Loops that branch became hard to follow, so wave three drew them as graphs. LangGraph is the best-known example. You define nodes (steps like "extract fields" or "match PO") and edges (the paths between them, including conditional branches). The runtime walks the graph. Other frameworks do the same thing with different syntax.

```python
graph = StateGraph(dict)  # state: a plain dict
graph.add_node("extract", extract_fields)
graph.add_node("match_po", match_po)
graph.add_node("flag", flag_mismatch)
graph.add_edge("extract", "match_po")
graph.add_conditional_edges("match_po",
    lambda s: "flag" if s.get("mismatch") else END)
```

This is genuinely better. Retries, branches, and parallel paths are explicit. But look at the first line: `StateGraph(dict)`. The thing flowing between nodes is a dictionary with string keys, mutated in place by each node. `extract_fields` writes `s["amount"] = 1042.0`. A refactor renames the key to `s["total"]`. `match_po` still reads `s["amount"]`, gets None, and treats the invoice as zero. No error. The graph runs green and the answer is wrong.

Wave three made the control flow legible and left the data flow opaque. That is the pattern Jonas named: the toolbelt hid the prompt's fragility, the loop hid the toolbelt's state corruption, the graph hid the loops.

## Wave four: typed state

The state gets a schema, and the schema gets enforced.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Wave four declares what the agent knows as a typed object with legal transitions. The runtime rejects illegal moves, so the failure surfaces at the moment it happens instead of at month-end.</p></div>

Wave four changes what the state is. A TypedDict (or a Pydantic model, same idea) declares the shape up front: every field, every type, every legal value. "Typed" means the runtime checks the shape, the way a compiler checks types in ordinary code.

```python
from typing import TypedDict, Literal

class InvoiceState(TypedDict):
    vendor: str | None
    amount: float | None
    po_number: str | None
    status: Literal[
        "received", "extracted",
        "matched", "flagged", "approved"
    ]
```

Now the graph declares `StateGraph(InvoiceState)`, and the runtime enforces the contract. A node that writes `state["total"] = 1042.0` fails immediately, because the schema has no `total` field. A node that tries to move `status` from `"received"` straight to `"approved"`, skipping extraction and matching, gets rejected as an illegal transition. The rename bug from wave three cannot survive wave four. The skip-a-step bug cannot survive it either.

The state is now what the agent believes, rendered as data you can inspect. You can answer "what did the agent believe when it called that tool" with a database query instead of an archaeology dig. You can checkpoint the run, roll it back, and show an auditor the exact object the agent held at every step.

## Why this wave is different

Every earlier wave added capability. This one adds accountability.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state is the Rails move from 2005 applied to agents: a schema as the enforced contract. It is also the oldest discipline in software, rediscovered exactly when we need it.</p></div>

I think the right historical comparison is Rails in 2005. Rails made web apps operable for small teams. The mechanism was the schema: a declared structure for the data, with migrations making every state change versioned and reviewable. Before Rails, most web apps were prompts wearing toolbelts too, PHP scripts with the state smeared across sessions and globals. After Rails, the database shape was a contract and breaking it was a visible event.

Typed state is the same craft move, twenty years later, applied to agent cognition. The schema is the contract. Transitions are migrations. The agent's beliefs are the database.

Two objections are worth taking seriously, because the HN thread will raise both.

The first: Temporal and the durable-execution people solved half of this years ago. Partially true. Temporal gives you durable workflows: typed inputs, replayable history, checkpoints that survive crashes. What it types is the workflow state, the orchestration bookkeeping. The new claim is about a different object: what the agent believes about the world mid-task, the extracted fields and inferred facts it reasons over. Durable execution people will recognize the mechanics instantly, and they are right to; the lineage is real. Applying it to cognition is the new part.

The second objection: plenty of agents are short-lived and do not need durable state. Also true, for throwaway tasks. But production agents increasingly run for hours against systems where mistakes cost money, and for those the schema is the cheapest accountability mechanism we have.

Type theory is older than almost everyone arguing about this on HN. I think that is the part worth sitting on for a second: the oldest craft discipline we have in software is getting rediscovered, because we built systems that can act on the world and then noticed we could not audit what they were thinking.

## What breaks without it

A stateful mess nobody can audit, wearing an alignment badge.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Without typed state you get alignment theater: a well-behaved model inside an unaccountable system. Once state is typed, the next fight is schema governance, and that fight is already starting.</p></div>

The ladder of failure is short, and I have watched it happen more than once (this is my observation, not a cited study). A prompt wearing a toolbelt ships as an "AI feature." It breaks, so the team wraps it in a loop. The loop corrupts state, so the team draws a graph. The graph hides the loops, and now the team owns a stateful mess that runs green and answers wrong. One thousand invoices a month becomes ten thousand, and the mismatch rate becomes a finance-department mystery.

Meanwhile the vendor page says "most aligned to date." That claim is about model behavior during training evaluations. Alignment at the model layer and accountability at the system layer are different problems, and the second one is yours. An aligned model inside an unauditable state machine is a slot machine with a changelog. That is alignment theater.

Once state is typed, schema governance becomes the battleground. Who owns the schema, and do you version it like an API? I do not know the answer yet. I know frameworks will fight over lock-in to their state definitions the way ORMs fought over migrations, and it is better to see that fight coming than to discover it during an audit.

## What to do Monday morning

One agent, one schema, one instrumented transition.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Pick one production agent, declare its state as a typed schema, and diff the schema against what the agent actually carries. The gap is your verification debt, rendered visible.</p></div>

This is a two-engineer, two-week instrumentation project. No platform rewrite required.

Pick one agent in production. Write down its state as a typed schema, the way you would write a database schema. Then dump what the agent actually carries at each step and diff the two documents. The gap between them is your verification debt, rendered visible for the first time. Every field the agent tracks that is not in your schema is a belief you cannot audit. Every schema field the agent ignores is a control that does not exist.

Then instrument one transition. Pick the step where a mistake costs the most (for the invoice agent, the "matched" to "approved" jump) and make the runtime reject illegal moves through it. That single enforced transition will teach you more about your agent than a month of prompt tuning.

Assign ownership while you are at it. The schema lives in the repo, changes go through pull request, and one named engineer owns it. That is the whole process. If you are running ten agents, repeat the exercise per agent; the schema diff is cheap, and it slots into the review habits your team already has.

I think we will look back on this the way we look back on migrations in Rails: the boring discipline that made everything else governable. The schema is where craft lives now.
