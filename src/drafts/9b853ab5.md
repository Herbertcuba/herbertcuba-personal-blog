On July 21, 2026, engineer [Jonas Risbrandt compressed the recent history of agentic coding into a LinkedIn post](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz). Agentic coding means software in which an AI model can plan work and call tools, rather than only answer a question.

> “Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing.”

Risbrandt asked, “Haven't we just invented... a programming language?” Three days later, Anthropic, the company behind the Claude model family, [announced Claude Opus 5](https://www.anthropic.com/news/claude-opus-5) for long-running agents. Anthropic said its pre-deployment automated behavioral audit found Opus 5 to be “our most aligned model to date.” The [Hacker News discussion](https://news.ycombinator.com/item?id=49038433), on a technology forum widely read by software builders, drew over 1,700 points, a measure of attention rather than proof.

I think these events expose the same fault line. A stronger model may behave better in an evaluation, but it still cannot tell a production system which draft, evidence, and approval earned permission for a live action. Risbrandt's joke is that code came back around the prompt. The missing object inside that code is a typed, persisted authority record.

## Four waves, one publication card

Take one content-production card, `card-42`, from research through review to publication. Its current draft must describe a changing Hacker News score as “over 1,700 points,” and only the exact revision that passed fact-checking and human approval may be published.

### Prompt

A prompt is a natural-language instruction that tells a model what to do and which constraints to follow.

```text
Research card-42, write the draft, verify every source,
and publish only the approved revision.
For the changing score, write “over 1,700 points.”
```

This can produce a good demo. Production exceptions then accumulate until the prompt is wearing a toolbelt, with source checks, retries, approvals, and recovery written as prose. It still cannot bind approval to the exact bytes that will ship.

### Loop

A loop lets the model choose an action, inspect the result, and repeat until a stopping condition is met.

```python
while card.status not in {"done", "escalated"}:
    action = model.choose(history)
    result = tools.run(action)
    history.append(result)
```

The message history now acts as informal state, meaning the facts the agent carries between steps. If one message contains the stale exact score and another contains its correction, a later pass can retrieve the stale value and continue. I think this is the dangerous part: corrupted state can look like successful progress.

### Graph

A graph represents the workflow as named nodes connected by directed edges, so teams can see where work should go next.

```text
research → draft → fact_check → human_approval → publish
             ↑          |
             └─ kickback┘
```

The graph exposes the route after a failed check, but it cannot prove which source snapshot entered `fact_check` or whether approval matches the current revision. A tidy node can still hide a loop and ambiguous history.

### Typed state

Typed state gives the card defined fields and allowed values, while persistence stores that record beyond one model call. This illustrative schema deliberately covers only the final publication boundary:

```python
class PublishState(TypedDict):
    card_id: str
    version: int
    status: Literal["human_approval", "publish", "done"]
    revision_id: str
    content_hash: str
    approved_revision_id: str | None
    approved_content_hash: str | None
    sources_verified: bool

with transaction():
    current = lock_card(request.card_id)
    validate_types(request, current)
    require(request.expected_version == current.version)
    require(current.status == "human_approval")
    require(current.revision_id == current.approved_revision_id)
    require(current.content_hash == current.approved_content_hash)
    require(current.sources_verified)
    enqueue_once(request.idempotency_key, request)
    advance_if_version(current.card_id, current.version, "publish")
```

A content hash fingerprints the draft, while an expected-version check rejects requests based on older records. Runtime validation checks structure; the transition guard checks whether the locked current record may act. An idempotency key lets a retry return the existing publish intent instead of creating a duplicate.

A type check cannot establish that a source is true. The validated record and transition guard can ensure that the revision marked as verified and approved is the one permitted to publish. That distinction turns a vague instruction into a boundary software can test.

## Why the fourth wave changes the boundary

Typed state can sit inside graphs. [LangGraph, LangChain's graph-orchestration framework](https://docs.langchain.com/oss/python/langgraph/graph-api), already supports shared-state schemas. In March 2025, [Inngest's TypeScript AgentKit described routing with a “fully typed state machine”](https://news.ycombinator.com/item?id=43426164), which restricts allowed state transitions. These are convergence signals, not adoption evidence.

The practical shift is from permitting a schema to enforcing one at consequential transitions. Prompts carry intent, loops carry repeated decisions, and graphs carry routing. The typed record adds an acceptance boundary that can refuse stale or unauthorized work and retain the rejection as evidence.

That boundary also clarifies the limit of model alignment. Anthropic's Opus 5 statement describes behavior observed before deployment; it does not identify the live revision or approval behind a later publish request. I think alignment theater begins when model-level evaluation is presented as evidence that a production action had authority. The examination never saw the revision.

An AI Operating Model is the owners, evidence, decisions, and controls around an AI system. Engineering owns enforcement; the system or business owner defines acceptable evidence and transitions. Typed state gives them one contract to review.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Graphs can support schemas, but production accountability begins when current state is persisted and checked before an external action is accepted.</p></div>

## What fails when state stays implicit

An execution trace records which steps ran. It may place `human_approval` before `publish` while omitting which revision was approved. I think that gap will become central to agent incident reviews.

Verification debt is the gap between what a workflow assumes and what its records prove. It creates transcript archaeology here; in invoice approval or access provisioning, one disputed field can mean audit hours and a business owner unable to explain the action.

Regulation points in the same direction without prescribing typed state. The [European Union's 2024 AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj) requires high-risk AI systems to support automatic event recording under Article 12 and deployers to retain controlled logs under Article 26(6). The [European Commission's timeline](https://digital-strategy.ec.europa.eu/en/policies/regulatory-framework-ai) places strict high-risk obligations on December 2, 2027. This does not classify a content pipeline as high risk; it shows why retained transitions matter in authoritative systems.

Typed state still permits a well-formed mistake. A wrong claim can fit every declared field, which means factual checks and human judgment remain necessary. Its engineering win is narrower and more useful: silent corruption becomes a loud rejection with a record of the control that fired.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Execution history cannot prove action authority unless versions, evidence, and approvals are joined in the accepted state. The resulting gap is verification debt.</p></div>

## The old craft returns on Monday

“Strong typing” has no single universal definition, but the useful discipline is old: declare which values belong where and reject invalid combinations. Computer scientist Robin Milner's [1978 paper on type polymorphism](https://doi.org/10.1016/0022-0000%2878%2990014-4) helped formalize that reasoning. Agent engineering now applies it to uncertain runtime output.

[Ruby on Rails 1.0, the web application framework released in December 2005](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh), paired conventions with database migrations, versioned steps for changing stored structure. Migrations are not strong typing, but both disciplines make structural assumptions explicit and reviewable. Rails made changing web data operable; typed state does the same for agent authority.

Reversibility means returning to an earlier accepted state or applying a deliberate correction. Version checks block stale moves, retained events support replay, and idempotency keys prevent duplicate retries. None can unsend an email or reverse a bank transfer, so external effects need a correction path. My take is that reversibility becomes credible when those limits live in the state machine.

On Monday, give an enterprise architect, engineering lead, and system owner 30 minutes with one write-capable agent. Name the evidence, owner, retention rule, and one forbidden transition. For `card-42`, forbid publication after the approved hash changes.

Time-box a pilot instead of rebuilding the platform. Test three outcomes from persisted records alone:

```text
stale revision      → rejection event, no publish intent
approved revision   → one publish intent
retry after a crash → existing intent, no duplicate
```

Then run the incident review without the chat transcript. If the team cannot explain what the agent accepted, why the guard decided, and which action followed, the missing proof is the verification debt to pay next.

A one-shot classifier may deserve a lighter record because control should follow consequence. I don't know which framework will dominate, but I think state contracts will become standard review artifacts for write-capable agents by the end of 2027. If execution traces alone support incident review and crash recovery, that forecast is wrong. The next agent wave belongs to teams that can show, in software, why an uncertain model was allowed to act.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Start with one external action, bind it to current evidence and approval, and test refusal before scale. Craft discipline returns when agent authority becomes reviewable as software.</p></div>
