A Swedish engineer named Jonas Risbrandt posted on LinkedIn last week that agentic coding has gone through three waves, and is entering a fourth:

"Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state."

Each wave looked like a feature when it arrived. Each one was a fault line.

The timing is sharp. Opus 5 shipped this month carrying the claim "most aligned to date," and the Hacker News thread on it passed 1,700 upvotes. The model's quality was barely disputed. The skepticism sat one layer up: fine, the model behaves, but what does the system around it actually do, and who can inspect it while it runs?

Jonas's four waves answer that question in order. To make it concrete, I want to carry one small system through all four: an invoice agent. It reads supplier invoices, pulls out the vendor, the amount, and the due date, and books them for payment. Six to ten fields. The kind of agent half the companies I talk to already have in production.

## Four waves, one invoice

Here is how the same task survives each wave, and what each wave quietly breaks.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts forget, loops corrupt, graphs decorate, typed state exposes. Each wave exists because the one below it hid a failure.</p></div>

### Wave one: the prompt

You write a system prompt. "You are an invoice processing assistant. Extract the vendor, the amount, and the due date," and so on, for pages. In my experience these prompts grow without bound. I have seen them pass 4,000 words, every line a scar from some past failure.

I tried to fix a misbehaving invoice agent once by editing the prompt. It worked, until the next invoice format arrived and I added another paragraph. The prompt is a goldfish. Every run starts from nothing, and a rule buried 600 words deep gets treated as a suggestion. A German invoice reading "12.400,50" came back booked as 1240050 kronor. The decimal-comma rule was in there somewhere. The model had other priorities.

### Wave two: the loop

So we gave the goldfish a memory. The standard pattern is called ReAct, short for reason and act: the model writes a thought, calls a tool, reads the result, and repeats until it decides it is done. The transcript grows with every step.

This fixed the forgetfulness, and I think it created something worse. The transcript became the state, and a transcript is a rumor about itself. When the agent misreads the amount at step three, that number sits in the log looking exactly like a fact. By step nine the agent is quoting its own error back as established truth. Finding the fault means reading the whole transcript top to bottom, like a detective.

### Wave three: the graph

So we drew the loop. Frameworks like LangGraph let you declare the agent as a graph: nodes for the steps (extract, validate, book), edges for which step runs next. Its core type is literally called StateGraph. The diagram is a genuine improvement. You can point at the box that failed.

But look at what flows along those edges. In most graph setups, the state handed between nodes is a loose dictionary, a bag of string keys that any node can write and none of them guarantees. The graph made the control flow legible and left the data underneath as mush. A diagram of a mess is still a mess.

### Wave four: typed state

The current wave gives the bag a schema. In Python that usually means a TypedDict: a dictionary where every key is declared up front with a type, and anything that violates the contract fails loudly.

```python
from typing import TypedDict, Literal

class InvoiceState(TypedDict):
    vendor: str
    amount_ore: int                      # 1240050 = 12,400.50 SEK
    currency: Literal["SEK", "EUR", "USD"]
    due_date: str                        # ISO 8601, e.g. "2026-08-15"
    needs_human_review: bool
```

Read what this does to the German invoice. The amount is stored in öre, as an integer. There is no comma left to misread. If the extraction step hands over a float or a string, validation rejects it at step three, where the error was born. The schema also makes policy executable: anything over 100,000 kronor flips needs_human_review to true, and a person sees the invoice before finance does.

One honest caveat for the junior engineers: TypedDict types are checked by your static tooling. Python itself will not enforce them at runtime, so you still call a validator after each step. That call is the whole point.

Worth naming one distinction here, because it frames everything after it. Workflow state records which step ran. Agent state is what the agent knows. The first is plumbing. The second is cognition, and cognition is what needs the schema.

## Why this wave pays down debt

The first three waves added capability. This one adds a discipline, and I think that is why it behaves differently from the hype cycles before it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state turns verification, rollback, and review from prompt-level hopes into schema-level guarantees.</p></div>

I wrote about verification debt in March: every agent output nobody checks compounds like financial debt, with interest. Typed state is a payment plan. Validation runs after every step, against a contract a human wrote, so the debt stops compounding at step three instead of surfacing at month-end close.

I wrote about reversibility earlier this year. With snapshots of a typed state, rollback becomes a feature of the state machine. You stop hoping the prompt wording will save you, because the last known-good state is a file you can restore.

There is precedent for this move. Rails made web apps buildable in 2005 through convention over configuration: declare the shape, and the framework enforces it. Typed state does the same work for agents in 2026. Strong typing is the oldest craft discipline we have in software, and we are rediscovering it in the newest system we have.

## What breaks without a schema

The failure mode of waves one to three is a system nobody can audit.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>An agent you cannot interrogate is a liability with a nice demo. Typed state is what makes it inspectable.</p></div>

Each wave hid the failure of the one below. The prompt hid the forgetfulness. The loop hid the corruption inside a growing transcript. The graph wrapped the transcript in a diagram that looked rigorous from a distance.

Which brings me back to Opus 5. "Most aligned to date" is a claim about the model. Alignment theater is what I call the confusion of that claim with system safety: the certification says the actor behaves, while the stage is on fire. Model-layer alignment and system-layer accountability are different problems, and the second one is yours. Regulators are circling the same conclusion. The EU AI Act's record-keeping duties assume you can produce logs of what an automated system decided. An untyped transcript is nobody's idea of a record. A validated state log is something you can hand to an auditor.

Any legible operating model for AI starts here: you cannot govern agent state you cannot inspect.

In 2001: A Space Odyssey, HAL ran the whole ship, and the crew could not inspect what HAL knew until it was far too late. I don't want to be paged at 3 AM by an agent I cannot interrogate, and I don't know anyone who does.

## What to do on Monday

You do not need a platform rewrite to start.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Pick one agent, write its schema first, validate after every step. Two engineers, two weeks.</p></div>

Pick one agent in production. Write its TypedDict before you touch the prompt: what fields it carries, what type each one is, what values are legal. Declare the schema, validate after each step, snapshot the state. Then diff your schema against what the agent actually carries in its transcript today. My prediction, and you can check me on it: you will find two or three times as many fields as you declared, half of them written by accident and read by hope.

The exercise costs two engineers for two weeks. What comes out of it is a line of code you can read, test, and point at when finance calls.

I think this is the wave where agent engineering becomes ordinary engineering. I don't know if it is the last wave, and honestly I doubt it. But the first three waves made agents possible. This one makes them professional.
