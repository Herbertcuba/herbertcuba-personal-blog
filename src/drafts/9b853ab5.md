In July 2026, engineer [Jonas Risbrandt](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz) compressed the recent history of agentic coding, where models choose tools and work across multiple steps, into four moves:

> First, we talked about prompting.
>
> Then we realized one prompt was not enough, so we added loops.
>
> Then loops were not enough, so we introduced graphs.
>
> Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing.

His question was sharp: "Haven't we just invented... a programming language?" Each addition had arrived as extra capability. Seen together, they reveal the failure boundary created by the previous design.

On July 24, 2026, [Anthropic](https://www.anthropic.com/news/claude-opus-5), the AI company behind Claude, released Claude Opus 5 for demanding work including long-running agents. Anthropic said its pre-deployment behavioral audit found Opus 5 to be "our most aligned model to date." The announcement received over 1,700 upvotes on [Hacker News](https://news.ycombinator.com/item?id=49038433), a technical forum where practitioners vote on and discuss software news. That attention signals interest, not independent proof of the claim.

I think these two events expose the real next step. Better model behavior matters, but a production incident usually asks a different question: what facts did the agent accept before it acted? Prompts, loops, and graphs can all leave that answer buried in prose. Typed state gives it a checked address.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Agent frameworks kept adding control around uncertain model output, yet the accepted facts often remained implicit. Typed state matters because it records those facts before they authorize a real action.</p></div>

## One article, four architectures

Consider a content engine moving one article through research, drafting, fact-checking, human approval, and publication. Its brief contains a precise Hacker News score, but that number changes over time. Research replaces it with the durable wording "over 1,700 upvotes." Publication should use the checked claim from the checked draft, even after a revision or crash.

A **prompt** is a natural-language instruction given to a model. The first architecture places the workflow and its safeguards in the same block of prose:

```text
Research the article, write it, fact-check every claim,
request human approval, and publish it.
Use "over 1,700 upvotes" for the Hacker News response.
Never publish an unverified source.
```

This can work while the task is small. Then every incident contributes another sentence, and the prompt starts carrying policy, recovery behavior, and data definitions alongside editorial intent. The model has tools, but no formal field says which draft was checked or whether an approval still applies. It is a prompt wearing a toolbelt.

A **loop** repeats model and tool calls until a stopping rule is met:

```python
while status != "done":
    action = model.choose(message_history)
    result = tools.run(action)
    message_history.append(result)
```

The loop lets the agent gather a missing source, revise a rejected draft, or retry a temporary failure. Its `message_history`, however, now acts as working memory. If an early message contains the stale score and a later fact-check replaces it, another revision can recover the older value because both remain plausible text. Finding what the writer accepted at the handoff requires reconstructing a conversation.

A **graph** names the workflow steps as nodes and the allowed routes as edges:

```text
research -> draft -> fact_check -> human_approval -> publish
              ^           |
              +-- reject -+
```

This map makes control flow visible. It still may carry the article as a free-form message bundle, while each node hides another prompt or loop. [LangGraph](https://docs.langchain.com/oss/python/langgraph/graph-api), a Python toolkit for graph-based agent workflows, already supports shared state schemas, so the honest argument is not that graphs must be untyped. The problem is treating a schema as optional plumbing rather than the authority for every transition.

**Typed state** is a persisted record with declared fields, validated values, and checked transitions. Persisted means that an accepted record survives a model call or process crash. In Python, [Pydantic](https://docs.pydantic.dev/latest/), a runtime validation library, can reject model or tool output that does not match the contract before the application stores it:

```python
class ArticleState(BaseModel):
    card_id: str
    status: Literal["research", "draft", "fact_check",
                    "human_approval", "publish", "done"]
    draft_revision: int
    checked_revision: int | None
    sources_verified: bool
    hn_claim: Literal["over 1,700 upvotes"]

def may_publish(s: ArticleState) -> bool:
    return (
        s.status == "human_approval"
        and s.sources_verified
        and s.checked_revision == s.draft_revision
    )
```

`may_publish` is a **transition guard**, a rule that must pass before the system changes state. A revision after fact-check makes the revision numbers disagree, so publication stops. An exact, drifting score fails validation. Types cannot establish whether the source itself is truthful, but they can prevent an unchecked value or expired verdict from quietly acquiring authority.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The prompt states the job, the loop keeps it moving, and the graph exposes its routes. Typed state adds the missing production record: which draft was checked, which claim was accepted, and whether publication is currently allowed.</p></div>

## State makes the rest testable

Jonas listed typed state alongside persistence, retries, error handling, observability, reusable components, and testing. I think state is the forcing function because each discipline needs a defined object: retries need a known checkpoint, tests need expected transitions, and logs need fields whose meaning survives changes in transcript wording.

**Strong typing** means different things across languages, but the craft is old: software limits operations that do not fit declared kinds of values. In 1978, computer scientist [Robin Milner](https://doi.org/10.1016/0022-0000(78)90014-4) formalized influential work on type polymorphism, which lets programs remain flexible while preserving value guarantees. Agents now need that discipline where probabilistic output enters deterministic software.

[Ruby on Rails 1.0](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh), a web framework released in December 2005, offers the useful parallel. Rails used dynamically typed Ruby; its contribution was not static typing. Database migrations made schema changes ordered, version-controlled instructions that teams could review and replay instead of applying by hand. Rails made application state operable. Typed contracts can do the same for agent state.

This direction is appearing across independent projects, although that shows convergence rather than adoption. [Inngest AgentKit](https://github.com/inngest/agent-kit), a 2025 open-source TypeScript framework, calls its router a "fully typed state machine." [MemState](https://github.com/scream4ik/MemState), a later Python project, validates agent memory on write. Both put a checked boundary before model output becomes durable state.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Retries, logs, and tests become dependable only when they refer to a stable record. Type discipline supplies that record without pretending that a schema can make an uncertain model infallible.</p></div>

## Alignment cannot audit a transaction

Anthropic's Opus 5 audit tested model behavior before deployment, including adherence to the company's constitution and resistance to misuse. That work is genuinely useful. I think alignment theater begins when a team presents the model result as evidence that the surrounding production system can explain a particular action.

After a bad publication, the incident review needs the source version, draft revision, fact-check verdict, approving person, and publisher response. A model evaluation answers none of those transaction-level questions. **Verification debt** is the investigation and rework created when a system fails to retain that evidence at the moment of decision. Chat logs and graph traces show activity; a state contract shows which activity the application accepted.

This distinction matters more when an agent approves an invoice or provisions employee access. A stale invoice revision can carry the wrong amount, while an old access approval can grant a role the manager never reviewed. The **AI Operating Model**, meaning the ownership and controls around AI-enabled work, therefore needs a named owner for each critical field, retained rejected transitions, and a clear rule for who may change the contract.

Regulation is moving toward the same demand for evidence. The [EU AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj), the European Union's 2024 AI regulation, requires automatic event logging for high-risk AI systems under Article 12 and requires deployers to retain logs under their control under Article 26(5). The main obligations for high-risk uses listed in Annex III began applying on August 2, 2026. A publishing agent is not automatically high-risk, and typed state alone does not create compliance. For covered systems, however, retained acceptances and rejections can provide evidence that a vendor's model score cannot.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A pre-deployment audit describes a model under test; it does not explain a production decision. Inspectable state pays down verification debt by preserving the evidence, authority, and rejected transitions behind consequential actions.</p></div>

## Put one consequential transition under contract

My take for Monday is narrow: choose one agent action that changes the outside world, such as publishing, paying, or granting access. In a 30-minute review, the system owner and enterprise architect should name the facts that authorize it, their sources and retention periods, and one forbidden transition.

For the article engine, the boundary sits between human approval and publication. Store the approved draft revision, the source-verification result, the approver, and the publisher's response. Give a publish request an **idempotency key**, a unique identifier that lets the publisher recognize a retry after a crash and return the first result instead of creating a duplicate.

Give two engineers two weeks to test this boundary without replacing the graph or model. A post-check revision must block publication, an unverified source must produce a retained rejection, and an accepted request repeated after a simulated crash must create only one article. The team can then restore a known record and retry safely, making reversibility a property of the state machine.

I don't know which agent framework will lead next year. Short, read-only classification may never need durable state. I think any agent allowed to publish, pay, approve, or provision should show the exact record that granted its authority.

Jonas ended with the line that should guide the architecture: "We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt." The return of explicit code around uncertain judgment is where accountable agent engineering starts.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Begin with one external action and put its authority under a persisted contract. Assign field ownership, reject stale approvals, retain the evidence, and make retries safe before expanding the pattern to the rest of the agent system.</p></div>
