On July 21, 2026, [engineer Jonas Risbrandt described the evolution of agentic coding in a LinkedIn post](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz). Agentic coding lets an AI model use tools, read results, and continue toward a goal.

> “Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing.”

Risbrandt then asked, “Haven't we just invented... a programming language?” I think he named the pattern. My addition is an authority record for the version, evidence, approval, and rule behind a live action.

Three days later, AI company Anthropic [announced its Claude Opus 5 model for long-running work](https://www.anthropic.com/news/claude-opus-5). Anthropic said its pre-deployment behavioral audit found it to be “our most aligned model to date.” In that test, alignment meant following the company's stated behavior rules better. By early August, the discussion on [Hacker News, a technology forum](https://news.ycombinator.com/item?id=49038433), had more than 1,700 points, a measure of attention rather than agreement.

I think the events belong together. Better model behavior cannot tell an incident reviewer which revision an agent used after deployment. Each wave looked like a feature. Each one exposed a fault line in the state beneath it.

## Four waves, one publication card

Consider one publication card. Research captures a changing Hacker News score, fact review replaces it with the stable phrase “more than 1,700 points,” and only that verified, human-approved revision may publish. Each wave handles it differently.

### Prompt

A prompt is a natural-language instruction supplied to a model.

```text
Research card-42, draft the article, verify every source,
and publish only the approved revision.
Use “more than 1,700 points,” never an exact score.
```

“Approved revision” names no machine-checkable object. As rules accumulate, the prompt doubles as a data contract, workflow, and runbook without enforcing any of them. This is a prompt wearing a toolbelt.

### Loop

A loop lets the model act, inspect the result, and repeat until it reaches a stopping condition.

```python
while card.status not in {"done", "escalated"}:
    action = model.choose(message_history)
    result = tools.run(action)
    message_history.append(result)
```

Message history now serves as informal state, meaning the facts carried between steps. The old score and the corrected phrase can both remain in that history, so a later drafting pass may retrieve the wrong one without breaking the loop. I think this is the dangerous part: the system can keep making visible progress after its accepted fact has become unclear.

### Graph

A graph connects workflow steps, called nodes, with directed edges that decide which step runs next.

```text
research → draft → fact_check → human_approval → publish
             ↑          |
             └─ kickback┘
```

The failed fact check now has an explicit route back to drafting. Yet the graph does not prove that the drafting node received the corrected revision, and each node may contain another prompt or loop. Routing is visible while data authority remains implicit.

Graphs are not inherently untyped. [LangGraph, a graph-based agent library from AI tooling company LangChain](https://docs.langchain.com/oss/python/langgraph/graph-api), supports shared state schemas. The narrower point: a graph shows execution routes, not which persisted facts authorize the next action.

### Typed state

Typed state declares the fields and allowed values a workflow may carry. Persistence stores that record beyond one model call. This boundary uses [Pydantic, a Python library that validates data at runtime](https://docs.pydantic.dev/latest/concepts/strict_mode/), inside a locked database transaction:

```python
class PublishState(BaseModel):
    model_config = ConfigDict(strict=True)
    card_id: str
    version: int
    status: Literal["fact_check", "human_approval", "publish"]
    revision_id: str
    content_hash: str
    fact_report_id: str | None
    sources_verified: bool
    approved_revision_id: str | None
    approved_content_hash: str | None

with transaction():
    current = PublishState.model_validate(lock_card(request.card_id))
    require(request.expected_version == current.version)
    require(current.status == "human_approval")
    require(current.sources_verified and current.fact_report_id is not None)
    require(current.revision_id == current.approved_revision_id)
    require(current.content_hash == current.approved_content_hash)
    write_publish_intent_once(request.idempotency_key, current)
    advance_if_version(current.card_id, current.version, "publish")
```

The schema declares the expected fields, and runtime validation checks incoming data against those fields and rules. A content hash fingerprints the draft. The expected-version check rejects an older record, while the `require` statements are transition guards that stop a valid record from taking an unauthorized route.

`write_publish_intent_once` represents a transactional outbox record, a durable instruction stored with the database change. Its idempotency key names one logical operation, so a retry finds the instruction instead of creating another. That boundary can bind an invoice revision to purchase-order evidence and budget-owner approval, or an access request to an employee, role, and manager.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts hold instructions, loops repeat work, and graphs expose routes. Typed, persisted state adds a checked record that can reject stale, malformed, duplicate, or unauthorized publication attempts.</p></div>

## Why this wave is different

By typed state, I mean a schema enforced at runtime and at the database boundary. Python annotations alone are insufficient. Types cannot verify a source or make a model correct, but they can refuse a missing report, changed revision, or forbidden transition.

I think that bounded refusal is the engineering win. Retries and observability depend on a known record with stable fields. Typed state names those facts, turning failure into a rejected transition instead of a search through message history.

This direction predates Risbrandt's label. In March 2025, [workflow company Inngest described its TypeScript AgentKit library as using a “fully typed state machine” for routing](https://news.ycombinator.com/item?id=43426164). Together with LangGraph's shared schemas, this shows independent teams choosing a similar boundary, not broad adoption.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The fourth wave exposes workflow state instead of burying it in instructions or history. It can refuse an action whose evidence, version, approval, or route does not match.</p></div>

## What implicit state costs

An execution trace lists which steps ran. It may show `human_approval` before `publish` without the approved revision, forcing reviewers to reconstruct authority from activity records that cannot prove it.

I call that gap verification debt: the distance between what a workflow assumes and what its records can demonstrate. In the publication card, the debt is a stale claim. In invoice approval or access provisioning, the gap can consume audit time, delay a close, or leave a pilot without a production owner.

This separates model alignment from system accountability. Anthropic measured behavior before deployment, not the evidence used by a later production action. My take is that alignment theater begins when a model evaluation is treated as evidence that the live system carried the right state.

An AI Operating Model is the ownership, evidence, decisions, and controls around an AI system. It becomes legible when the business names a consequential transition, engineering enforces it, and reviewers can inspect both accepted and rejected records. The [European Union's 2024 AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj/eng) points in this direction without prescribing typed state. For high-risk systems within its scope, Article 12 requires technical event logging. Article 26(6) requires deployers to retain automatically generated logs under their control for at least six months unless another law sets a different period.

Typed state also makes reversibility precise. Retained versions let the system return to a known record or replay a transition. Neither version history nor an idempotency key can unsend an email or reverse a payment; those effects need a named correction action. I think shared state between agents will become the next fault line if nobody can show who changed it, from which version, and under whose authority.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Activity records show what ran; authority records show which facts and approval allowed it. Without that link, verification debt grows across incidents, audits, and AI pilots moving into production.</p></div>

## Put one contract into review

Computer scientist Robin Milner's [1978 paper “A Theory of Type Polymorphism in Programming”](https://doi.org/10.1016/0022-0000%2878%2990014-4) presented a formal type discipline with a compile-time checking algorithm. The mechanism here is runtime validation, but the underlying strong-typing discipline is old software craft: declare valid forms and reject invalid combinations before action.

[Ruby on Rails 1.0, a web framework released in December 2005](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh), used [database migrations](https://github.com/rails/rails/blob/v1.0.0/activerecord/lib/active_record/migration.rb) to give teams reproducible instructions for moving a schema between versions. Those instructions made structural change easier to review and deploy. Typed, persisted state applies similar discipline to agent transitions.

On Monday, convene a 30-minute review with the enterprise architect, system owner, and business owner. Choose one write-capable agent and one consequential transition. Name its version, evidence, approver, retention rule, and one forbidden move. The business owner accepts it; a named engineer owns enforcement.

Give two engineers two weeks rather than starting a platform rewrite. Persist both acceptance and rejection, then make these tests pass:

```text
stale approved revision → rejection, no publish intent
current approved revision → one publish intent
retry after a crash with the same key → existing intent, no second record
```

Run an incident review from persisted state alone. If the team cannot explain what was accepted, which guard decided, and what followed, its verification debt is visible. A pilot earns production ownership this way.

I don't know which agent framework will dominate. I think by the end of 2027, teams running write-capable agents will treat state contracts as a standard review artifact. If execution traces alone support incident review and crash recovery, the contract adds little. I do not expect that result.

Risbrandt's sharper line was, “We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt.” The code worth keeping will be the code that records why an uncertain model was allowed to act.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Review one consequential transition as a software contract, test refusal and recovery, and demand an incident explanation from persisted state. Craft discipline is back when authority becomes executable.</p></div>
