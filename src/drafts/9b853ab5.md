Each wave looked like a feature. Each one was actually a fault line.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Agent frameworks evolved through four waves: prompts, loops, graphs, and now typed state. Each wave solved a real problem and created a new failure mode. Typed state is the first wave that makes agent systems auditable.</p></div>

## The four waves explained

Jonas's post tracks how we got here. Let me walk through each wave with the same example, so you can see what actually changed.

Say you need to process invoices. Extract the vendor, the date, the total, and match it to a purchase order. Simple enough to explain, complex enough to break.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The four waves are prompts (one big instruction), loops (iterate until done), graphs (branching workflows with shared memory), and typed state (explicit data structures that enforce what the system knows). Each wave fixed a real problem and created a new failure mode.</p></div>

**Wave 1: The prompt**

You write one big prompt. "Read this invoice. Extract vendor, date, total. Match to PO database. Flag discrepancies."

The model tries to do everything at once. Sometimes it works. Sometimes it hallucinates a PO number that looks right but doesn't exist. You can't tell which because the reasoning is a black box. The invoice goes in, an answer comes out, and you hope.

**Wave 2: The loop**

So you add a loop. The model breaks the task into steps: read invoice, extract fields, validate against PO, repeat if uncertain. This is the ReAct pattern (Reasoning + Acting). The model thinks out loud, takes an action, observes the result, thinks again.

Better. But now the model can loop forever. It keeps "checking" the same PO, burning tokens, never quite sure. You add a max_iterations guard. The state lives in the prompt history, growing longer each turn. Nobody can see what the system actually knows at any point without reading the whole transcript.

**Wave 3: The graph**

So you add a graph. LangGraph, or something like it. You define nodes: parse_invoice, extract_fields, match_po, human_review. Edges connect them based on conditions. The graph has memory. It can branch, retry, escalate.

This handles complex workflows. But the state is still implicit. It lives in the graph's internal memory, passed between nodes as context. When something breaks, you trace through logs trying to reconstruct what the system believed at step 7. The graph hides the state corruption.

**Wave 4: Typed state**

Now you define explicit state. A TypedDict in Python, or a schema in TypeScript. The invoice object has a vendor field (string), a date field (ISO format), a total field (decimal), a status field (enum: pending, matched, flagged, approved).

The graph nodes can only read and write these fields. The state is inspectable. You can pause the graph and see exactly what the system knows. You can replay it. You can audit it.

```python
class InvoiceState(TypedDict):
    vendor: str
    date: str  # ISO 8601
    total: Decimal
    po_match: Optional[str]
    status: Literal["pending", "matched", "flagged", "approved"]
    confidence: float  # 0.0 to 1.0
```

The state is the system. Everything else is just functions that transform it.

## Why typed state is the engineering win

I think this is the first wave that actually makes agent systems auditable.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state turns agent memory from a hidden transcript into an explicit data structure. You can inspect it, replay it, and audit it. This is the difference between a system you can debug and a system you can only observe.</p></div>

The earlier waves externalized different things. A prompt externalizes instructions. A loop externalizes iteration. A graph externalizes workflow. Typed state externalizes memory.

That last one is the hard part. State is where bugs hide. State is where security vulnerabilities live. State is what you need to see when the CFO asks why the system approved a duplicate payment.

I think about this like the difference between a ship's log and the ship's actual position. The log tells you where you were. The position tells you where you are. Typed state gives you the position.

The Rails comparison is useful here. In 2005, Rails made web apps possible by making the implicit explicit. Conventions, a schema, one place where the shape of your data lived. Typed state does the same thing for agent systems. It takes the shape of what the system knows and puts it in one place, in a format you can read.

## What breaks without it

Let me show you what this looks like when it fails.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Without typed state, agent systems fail in ways you can't debug. The state lives in the prompt history or graph memory. When the system makes a wrong decision, you can't see why. You can only see the output.</p></div>

Last month I talked to a team that built an invoice processing agent. It worked in demo. In production, it started approving invoices with the wrong currency. EUR became USD. The amounts looked plausible. The PO match was valid. Nobody caught it for three days.

The bug was in the state. The agent had extracted "10.000,00" from a German invoice. Somewhere in the loop, the comma became a period. The total went from ten thousand euros to ten dollars. The graph logs showed the steps. They didn't show the state transformation. The team had to add print statements to every node and rerun the failing invoices to find where the corruption happened.

With typed state, the total field is a Decimal. The currency field is an enum. The transformation from string to Decimal is explicit and testable. You can write a unit test that feeds "10.000,00" into the parser and checks the output. You can add a validation rule that flags any total under 100 when the currency is EUR.

The state was the system all along. They just couldn't see it.

## What to do Monday morning

If you're building agent systems, here's what I would do.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Start with the state schema. Define what your system knows before you write the logic. Make every field typed and every transition explicit. The schema is your contract with the future.</p></div>

First, write the state schema before you write the prompt. What does your system need to know? What are the valid values? What are the transitions? This is your contract with the future.

Second, make the state inspectable. Log it. Store it. Build a view that shows you exactly what the system knows at any step. When something breaks, you should be able to open the state and see the problem, not reconstruct it from logs.

Third, test the state transitions. Unit tests for the functions that transform state. Integration tests for the workflows. The state schema is your test boundary.

I don't know if typed state is the last wave. I doubt it. But I think it's the first wave that makes agent systems legible. The ones you can open like a book, not the ones whose agents score highest on a leaderboard.

The craft discipline is back. Strong typing, explicit state, auditability. The oldest disciplines in software, finally applied to the newest systems.
