On July 21, Jonas Risbrandt compressed the recent history of agentic coding into [one LinkedIn post](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz):

> First, we talked about prompting.
>
> Then we realized one prompt was not enough, so we added loops.
>
> Then loops were not enough, so we introduced graphs.
>
> Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing.

His punchline was sharper: "Haven't we just invented... a programming language?"

Three days later, Anthropic [announced Claude Opus 5](https://www.anthropic.com/news/claude-opus-5). The company said its automated pre-deployment behavioral audit found Opus 5 to be its "most aligned model to date." The [Hacker News thread](https://news.ycombinator.com/item?id=49038433) drew over 1,700 points.

I think the timing reveals the next engineering problem. Better models improve the reasoning inside an agent. They leave us with the working facts that accumulate around that reasoning. Each wave gave the agent more freedom while hiding a new fault line in its state.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Agent frameworks moved from prompts to loops and graphs. Longer runs need a clear record. Typed state shows what the agent knew, which evidence supported it and which move it was allowed to make.</p></div>

## Four waves, one broken fact

The same article card shows what each abstraction adds and what it leaves hidden.

### Wave 1: a prompt carries the whole job

A prompt is a plain-language instruction sent to a model. Our content pipeline could start with this:

```text
Research this article.
Write a draft.
Check every source.
Ask for approval, then publish.
```

Each incident adds another sentence. Soon the prompt carries policy, memory and recovery rules in prose. It is a prompt wearing a toolbelt, with no named field for `sources_verified` or the evidence behind a claim.

### Wave 2: a loop keeps the agent moving

ReAct means reasoning and acting. In the 2022 [ReAct paper](https://arxiv.org/abs/2210.03629), a model alternates reasoning with an action and the result of that action. A simplified loop looks like this:

```python
while card_status != "done":
    action = model.choose_next_action(messages)
    result = run_tool(action)
    messages.append(result)
    card_status = choose_next_status(messages)
```

The loop can research, draft and call a fact-checker. Its message history also becomes an informal database.

This article produced the failure in real life. The original spec carried an exact Hacker News count. Fact-check replaced it with "over 1,700," but a later revision pulled the stale number back from earlier context. Both values existed in the history. I think this is where an able loop turns into chat-log archaeology.

### Wave 3: a graph makes the route visible

[LangGraph](https://docs.langchain.com/oss/python/langgraph/graph-api) is a Python framework for agent workflows. Its `StateGraph` class builds a graph around shared state. Nodes are steps such as research or fact-check. Edges are the routes between those steps.

```python
graph = StateGraph(MessagesState)
graph.add_node("research", research_node)
graph.add_node("draft", draft_node)
graph.add_node("fact_check", fact_check_node)
graph.add_conditional_edges("fact_check", route_by_verdict)
```

`MessagesState` is LangGraph's built-in state for conversation messages. The graph now shows that fact-check may return the card to draft. Yet a clean edge can still carry the stale count because the domain facts remain inside messages.

LangGraph already supports shared typed schemas. The fault appears when a team treats the graph as the contract and leaves the important state loose. A node may contain its own loop, and that loop may contain the original toolbelt prompt.

### Wave 4: typed state names the facts

[`TypedDict`](https://docs.python.org/3/library/typing.html#typing.TypedDict) declares the keys and value types expected in a Python dictionary. `Literal` limits a value to a fixed set of choices. They let a type checker inspect the shape before the program runs.

```python
from datetime import datetime
from typing import Literal
from typing_extensions import TypedDict
from pydantic import TypeAdapter

class ClaimEvidence(TypedDict):
    value: str
    source_url: str
    checked_at: datetime
    verified: bool

class CardState(TypedDict):
    status: Literal[
        "research", "draft", "fact_check",
        "human_approval", "publish"
    ]
    draft_hash: str
    evidence: dict[str, ClaimEvidence]
    approved_by: str | None
```

Python type hints alone do not validate data during a live run. A runtime validator such as Pydantic can check the payload at each boundary. A transition guard can then use the validated fields:

```python
CARD_STATE = TypeAdapter(CardState)

def request_publish(raw_state: dict) -> CardState:
    state = CARD_STATE.validate_python(raw_state, strict=True)

    if state["status"] != "human_approval":
        raise IllegalTransition("publish requires human approval")

    hn = state["evidence"].get("opus5_hn_points")
    if hn is None or not hn["verified"]:
        raise IllegalTransition("HN claim requires verified evidence")

    save_transition(state, "publish")
    return {**state, "status": "publish"}
```

`IllegalTransition` is a custom error for a forbidden move. `save_transition` writes the accepted state to durable storage. Now the count has a value, a source URL and a check time. The bad transition fails at the boundary through a code path another engineer can test.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts describe the job, ReAct loops repeat work and StateGraph exposes possible routes. TypedDict gives the carried facts a declared shape, while runtime validation and transition guards can stop stale state before publication.</p></div>

## A type changes the failure

Typed state earns its cost by turning silent corruption into a visible rejection.

Types cannot prove that a source is true. They can prove that the system received a source record in the expected shape. Verification still decides whether the record deserves `verified: true`. The contract separates those jobs, so each can fail loudly.

I think typed state is the first wave in Jonas's sequence that exposes the failure beneath it. A prompt can ask for care. A loop can try again. A graph can route the retry. The state contract shows the exact value being retried.

This is also how typed state pays down [Verification Debt](/posts/2026-03-09-verification-debt-crisis/). Compare the fields your workflow claims to carry with the payload it actually saves. The gap becomes visible. Persist each accepted transition and [reversibility becomes an architectural property](/posts/reversibility-is-the-new-correctness/) of the state machine, backed by a previous state you can restore or compensate for.

The craft is old. Static type discipline reaches back to ML and Hindley-Milner work in the 1970s. [Rails 1.0 shipped in 2005](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh), and Rails migrations put database changes into versioned code. Rails remained dynamically typed. The shared craft move was making state changes explicit and reviewable.

I don't know whether typed state will remain the label. [AgentKit](https://github.com/inngest/agent-kit), [MemState](https://github.com/scream4ik/MemState), [GraphFlow](https://github.com/a-agmon/rs-graph-llm) and [Agd](https://github.com/frontman-ai/agd) explore related designs across four languages. They show a direction. Adoption is a separate claim.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A state contract combines a declared shape with runtime checks, legal transitions and a saved record. It cannot make a false claim true, but it can expose which claim moved through the system and reject malformed or unverified state.</p></div>

## Production alignment needs receipts

A model audit ends before a live workflow starts collecting tool output, edits and approvals.

Anthropic carefully described its Opus 5 result as a pre-deployment audit. Production begins afterward. The model may behave well in that test while an application passes old facts through a long-running loop.

Think of HAL 9000 in *2001: A Space Odyssey*. A clean test before Discovery One leaves Earth says something about HAL. The mission still needs a record of the instructions and observations HAL receives in flight. In the film, conflicting orders hidden inside the system break the mission. A graph of the route would never expose that conflict.

I think alignment theater begins when a team cites the model audit while the run remains impossible to rebuild. A legible [AI Operating Model](/posts/building-the-ai-operating-model/) needs an owner for the schema and an owner for the costly transition. Product defines which facts the agent may carry. Platform enforces validation and retention. Risk approves boundaries such as publish, payment or account closure.

Regulation is moving in the same direction. For high-risk AI systems, Article 12 of the [EU AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj) requires automatic event logging. Article 26(6) requires deployers to retain logs under their control. A persisted state transition gives an engineering team something concrete to inspect.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Pre-deployment model testing covers the model before a production run. Operational accountability also needs structured state, named owners and retained transitions that show what the deployed agent knew before it acted.</p></div>

## Guard one expensive edge

Start with the action whose reversal would hurt most.

For this article pipeline, that edge is `human_approval -> publish`. A finance agent may have `reviewed -> payment_sent`. A support agent may have `reviewed -> account_closed`. The domain changes while the engineering move stays the same.

Pick one long-running agent. Write down the fields it must carry before that action. Give each claim its value, source and verification time. Add runtime validation. Persist the state before and after the transition, including rejected attempts.

Using pytest, a Python test runner, write the test you hope never passes:

```python
def test_unverified_claim_cannot_publish():
    state = {
        "status": "human_approval",
        "draft_hash": "9b853ab5",
        "approved_by": "reviewer@example.com",
        "evidence": {
            "opus5_hn_points": {
                "value": "over 1,700",
                "source_url": "https://news.ycombinator.com/item?id=49038433",
                "checked_at": datetime(2026, 8, 5),
                "verified": False,
            }
        },
    }

    with pytest.raises(IllegalTransition):
        request_publish(state)
```

Keep the first sprint small. One workflow, one costly edge and one named engineer who owns the schema. Review changes to that schema like changes to an API or database migration.

A one-shot classifier probably does not need this machinery. A long-running agent that carries facts across tools and can trigger a costly side effect usually does. I think junior engineers can lead the first implementation. The work is familiar software craft: define the type, validate the input and test the forbidden move.

Jonas closed his post with the line that contains the whole cycle: "We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt."

The code is returning because uncertain model calls need boundaries another engineer can inspect. Once agent state becomes a contract, the team can argue about behavior in a pull request instead of discovering it in a postmortem.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose one agent with a costly side effect and guard that transition with typed, validated and persisted state. The next agent wave begins when the facts behind an action become code another engineer can review.</p></div>
