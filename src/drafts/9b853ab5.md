A Swedish engineer named Jonas Risbrandt posted this on LinkedIn this week:

"Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state."

Four sentences. I read them three times.

The same week, Anthropic shipped Opus 5. Their announcement claimed it was their "most aligned model to date." The Hacker News thread passed 1,700 upvotes in a day. Two events, one week. The first described how we build agents. The second described how we evaluate them. The connection is the thing most teams are missing.

Jonas's post is short enough to quote in full. It describes three waves of agentic coding and names the fourth. Each wave solved the problem the previous wave created. Each wave also hid a new problem underneath. The fourth wave, typed state, is the first one that makes the hidden problem visible.

I think Jonas is right. I also think most teams will get the fourth wave wrong, because they will treat it as a feature to add instead of a discipline to adopt. The difference matters more than it sounds.

## The four waves, one example

I tried to find a simple example that shows all four waves without changing the problem. Invoice processing works. Every company has it. The failure modes are concrete. Money moves or it does not.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The four waves are prompts (one big instruction), loops (iterate until done), graphs (branching workflows with shared memory), and typed state (explicit data structures that enforce what the system knows). Each wave fixed a real problem and created a new failure mode.</p></div>

You need to read a PDF invoice, extract the vendor, date, and total, match it to a purchase order, and book it to the ledger. Simple enough to explain in one sentence. Complex enough to break in production.

**Wave 1: the prompt**

You write one big prompt. "Read this invoice. Extract vendor, date, total. Match to PO. Flag discrepancies."

The model tries to do everything at once. Sometimes it works. Sometimes it invents a PO number that looks right but does not exist. You cannot tell which because the reasoning is a black box. The invoice goes in, an answer comes out, and you hope.

The prompt becomes a junk drawer. Every production incident adds another paragraph. "If the PDF has two blank pages followed by a table, skip page 3." Six months in, the prompt is doing the job of a schema, a state machine, and a runbook. It is bad at all three. Nobody can diff it. Nobody can test it. A prompt wearing a toolbelt.

**Wave 2: the loop**

So you add a loop. The model breaks the task into steps: read invoice, extract fields, validate against PO, repeat if uncertain. This is the ReAct pattern, from a 2022 paper by Yao and others. ReAct means the model reasons out loud, calls a tool, reads the result, reasons again. LangChain, AutoGen, CrewAI, and OpenAI's Assistants API all wrap this loop.

Better. But now the model can loop forever. It keeps "checking" the same PO, burning tokens, never quite sure. You add a max_iterations guard. The state lives in the prompt history, growing longer each turn. Nobody can see what the system actually knows at any point without reading the whole transcript.

State corruption is silent. The agent misreads a total. "10.000,00" from a German invoice becomes "10000.00" in the next message. The error is just another line in the chat log. The agent keeps going. You find out at month-end close.

**Wave 3: the graph**

So you add a graph. LangGraph is the most common tool for this in Python. You declare steps as nodes and transitions as edges. A StateGraph object holds the shared memory. Nodes can branch, retry, escalate. The control flow is visible on one page.

This handles complex workflows. But the state is still implicit. LangGraph's own documentation says state is "typically defined using a shared state schema." The framework permits typed state. Default practice does not enforce it. Most teams use MessagesState, a free-form dictionary mutated in place. The graph shows the roads. The plumbing is still hidden.

A node can contain a loop, which contains a prompt, which contains a toolbelt. Waves 1 and 2 are still there, with a nicer diagram. When something breaks, you trace through logs trying to reconstruct what the system believed at step 7. The graph hides the state corruption.

**Wave 4: typed state**

Now you define explicit state. A TypedDict in Python, or a schema in TypeScript. TypedDict is a Python dict where you declare every key and its type up front. The invoice object has a vendor field (string), a date field (ISO format), a total field (Decimal), a status field (one of: extracting, validating, booking, done, failed).

The graph nodes can only read and write these fields. The state is inspectable. You can pause the graph and see exactly what the system knows.

```python
class InvoiceState(TypedDict):
    vendor: str | None
    date: str | None        # ISO 8601
    total: Decimal | None
    currency: Literal["EUR", "USD", "GBP"] | None
    po_match: str | None
    status: Literal["extracting", "validating", "booking", "done", "failed"]
    error: str | None

def validate(state: InvoiceState) -> InvoiceState:
    if state["status"] != "validating":
        raise IllegalTransition(f"cannot validate from {state['status']}")
    if state["currency"] == "EUR" and state["total"] and state["total"] < 100:
        return {**state, "status": "failed", "error": "suspicious EUR total"}
    ...
```

The illegal transition is rejected at the boundary, not discovered at month-end close. The state is a database row, not a vibe in a prompt. When the auditor asks "what did the agent believe when it called the booking tool," you have a structured answer.

## Why typed state is the engineering win

I think this is the first wave that actually makes agent systems auditable.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state turns agent memory from a hidden transcript into an explicit data structure. You can inspect it, replay it, and audit it. This is the difference between a system you can debug and a system you can only observe.</p></div>

The earlier waves externalized different things. A prompt externalizes instructions. A loop externalizes iteration. A graph externalizes workflow. Typed state externalizes memory.

That last one is the hard part. State is where bugs hide. State is where security vulnerabilities live. State is what you need to see when the CFO asks why the system approved a duplicate payment.

I think about this like the difference between a ship's log and the ship's actual position. The log tells you where you were. The position tells you where you are. Typed state gives you the position.

The Rails comparison is useful here. In 2005, Rails made web apps possible for small teams by making the implicit explicit. A schema file. Migrations. One place where the shape of your data lived. Rails did not invent the database. It made the database legible. Typed state does the same thing for agent systems. It takes the shape of what the system knows and puts it in one place, in a format you can read.

I think this is why the pattern is showing up everywhere at once. Inngest shipped a typed state machine for agent routing in March 2025. A Rust team rebuilt their agent framework because they needed "type safety" they could not get in Python. A Python library called MemState validates agent memory on write: if the model tries to save a string into an integer field, the transaction fails before corruption happens. Nine independent projects across five languages in sixteen months. That is convergence, not coincidence.

The evidence is not adoption. It is direction. These are small projects, most of them. But when people keep arriving at the same architecture from different starting points, the architecture is solving a real problem.

## What breaks without it

Let me show you what this looks like when it fails.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Without typed state, agent systems fail in ways you cannot debug. The state lives in the prompt history or graph memory. When the system makes a wrong decision, you cannot see why. You can only see the output.</p></div>

Last month I talked to a team that built an invoice processing agent. It worked in demo. In production, it started approving invoices with the wrong currency. EUR became USD. The amounts looked plausible. The PO match was valid. Nobody caught it for three days.

The bug was in the state. The agent had extracted "10.000,00" from a German invoice. Somewhere in the loop, the comma became a period. The total went from ten thousand euros to ten dollars. The graph logs showed the steps. They did not show the state transformation. The team had to add print statements to every node and rerun the failing invoices to find where the corruption happened.

With typed state, the total field is a Decimal. The currency field is an enum. The transformation from string to Decimal is explicit and testable. You can write a unit test that feeds "10.000,00" into the parser and checks the output. You can add a validation rule that flags any total under 100 when the currency is EUR. The failure mode dies at the boundary.

The alignment theater problem is related. Anthropic's "most aligned to date" claim is about pre-deployment behavior. It says nothing about what an agent did in production. A model can pass every behavioral audit and still corrupt state in a loop you cannot see. Alignment at the model layer does not help if the system layer is illegible.

This is the verification debt I wrote about in March. Every unaudited agent run is debt. Typed state is how you start paying it down. The schema is your contract. The transitions are your test boundary. The state diff is your audit trail.

## What to do Monday morning

If you are building agent systems, start with the state schema.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Define what your system knows before you write the logic. Make every field typed and every transition explicit. The schema is your contract with the future.</p></div>

First, write the state schema before you write the prompt. What does your system need to know? What are the valid values? What are the transitions? This is your contract with the future.

Second, make the state inspectable. Log it. Store it. Build a view that shows you exactly what the system knows at any step. When something breaks, you should be able to open the state and see the problem, not reconstruct it from logs.

Third, test the state transitions. Unit tests for the functions that transform state. Integration tests for the workflows. The state schema is your test boundary.

I do not know if typed state is the last wave. I doubt it. But I think it is the first wave that makes agent systems legible. The ones you can open like a book and read what the system actually believed.

The craft discipline is back. Strong typing, explicit state, auditability. We have had the tools since the 1970s. We are finally applying them to the systems that need them most.
