On July 21, 2026, engineer [Jonas Risbrandt described four stages of agentic coding](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz), where language models plan and use software tools:

> “Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing.”

Risbrandt asked, “Haven't we just invented... a programming language?” His phrase “unreliable semantic functions” meant model steps that reason over meaning and may vary between runs, so production needs stable rules.

Three days later, Anthropic, Claude's developer, [announced Claude Opus 5](https://www.anthropic.com/news/claude-opus-5) for long-running agent work. The vendor said a pre-deployment automated behavioral audit found it to be “our most aligned model to date.” Its [Hacker News discussion](https://news.ycombinator.com/item?id=49038433) drew over 1,700 points, a measure of attention rather than validation.

I think the gap is production authority. Each wave solved a visible coordination problem while hiding the state underneath. Typed state adds what the others could not express: the exact version, evidence, and approval accepted before an agent acts.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Long agent runs accumulate hidden assumptions. Typed state records which facts and approval authorized one action.</p></div>

## Start with the authority to publish

This article's content-production card is a stored task record moving from research to publication. It must say “over 1,700 points,” pass fact-checking, and publish only while the approved revision remains current. The design question is which exact record earns permission to publish.

Typed state is a record with defined fields and allowed values, persisted beyond a model call and checked at runtime. A transition guard decides whether that record may advance. Here, the fields include a version, revision identifier, content hash that fingerprints the text, source-verification status, and the revision and hash a person approved.

The publish request also carries an idempotency key, a stable identifier that makes a safe retry return the existing action. This pseudocode uses [Pydantic, a Python data-validation library](https://docs.pydantic.dev/latest/concepts/models/), at the boundary:

```python
CardStatus = Literal[
    "ideas_inbox", "approved", "research", "draft", "slop_review",
    "fact_check", "persona_panel", "design", "human_approval",
    "publish", "done", "escalated",
]


class CardState(BaseModel):
    card_id: str
    version: int
    status: CardStatus
    revision_id: str
    content_hash: str
    approved_revision_id: str | None
    approved_content_hash: str | None
    sources_verified: bool


class PublishRequest(BaseModel):
    card_id: str
    expected_version: int
    revision_id: str
    content_hash: str
    idempotency_key: str


def accept_publish(raw: dict) -> Decision:
    request = PublishRequest.model_validate(raw)

    with db.transaction():
        current = CardState.model_validate(
            db.cards.for_update(request.card_id)
        )
        prior = db.outbox.get(request.idempotency_key)

        if prior:
            same_request = prior.request_hash == stable_hash(request)
            if same_request is False:
                db.events.insert("idempotency_conflict", request, current)
                return Decision.rejected("action key already used")
            return Decision.accepted(prior)

        allowed = all((
            request.expected_version == current.version,
            request.revision_id == current.revision_id,
            request.content_hash == current.content_hash,
            current.revision_id == current.approved_revision_id,
            current.content_hash == current.approved_content_hash,
            current.sources_verified,
            current.status == "human_approval",
        ))

        if allowed is False:
            db.events.insert("publish_rejected", request, current)
            return Decision.rejected("stale or unauthorized state")

        db.outbox.insert_once(
            key=request.idempotency_key,
            request_hash=stable_hash(request),
            payload=request,
        )
        db.cards.advance_if_version(
            request.card_id,
            expected_version=request.expected_version,
            status="publish",
        )
        return Decision.accepted()
```

`model_validate` performs runtime validation on the request and stored record. Inside the transaction, the current row is locked before the expected-version check and comparisons that bind revision, hash, and approval.

An outbox holds pending external actions written in the same transaction as the state change, supporting safe retries. The guard blocks a stale score claim from inheriting newer approval; a rejection event preserves why.

Typed state cannot prove that a source is true. It proves that the verified, approved revision is the one allowed to act. The same boundary applies to an invoice version or access request: approval belongs to an exact object, not a nearby conversation.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The authority record binds approved content to the current stored version. Stale requests are rejected before publication, while retries return the existing action.</p></div>

## Replay the same card through four waves

That boundary clarifies the earlier architectures. Each wave added capability, but only the fourth made accepted state explicit and enforceable.

### Prompt

A prompt is a natural-language instruction that tells a model what result to pursue and which constraints to respect.

```text
Research the article, draft it, fact-check it, and publish after approval.
For a changing Hacker News score, use “over 1,700 points.”
```

A demo can run, but incident clauses soon turn the prompt into a toolbelt. “Approved” still does not bind a reviewer to the exact bytes that will ship.

### Loop

A loop lets the model choose an action, inspect the result, and repeat until it reaches a stop condition.

```python
while card.status not in {"done", "escalated"}:
    action = model.choose(history)
    result = tools.run(action)
    history.append(result)
```

History may contain an exact score, its correction, and an approval message. It preserves sequence without declaring authority, so a later pass can retrieve the stale score and keep moving. I think corrupted state can resemble successful progress.

### Graph

A graph represents the workflow as named nodes connected by directed edges, making the route after a failed check visible.

```text
research → draft → fact_check → human_approval → publish
             ↑          |
             └─ kickback┘
```

The graph reveals where work went, but not which source snapshot reached `fact_check` or whether approval still matches the current revision. Each node can hide a prompt and a loop with ambiguous message state.

[LangGraph, LangChain's graph-orchestration framework](https://docs.langchain.com/oss/python/langgraph/graph-api), supports shared-state schemas. In March 2025, [Inngest's TypeScript multi-agent library AgentKit described “fully typed state machine” routing](https://news.ycombinator.com/item?id=43426164). These are convergence signals rather than adoption evidence. Safety depends on validation, persistence, and guards.

### Typed state

Typed state turns the same card into an accepted record that software can test at every move:

```text
candidate → validate shape → lock current record → compare authority
                                                   ├─ reject + retain event
                                                   └─ accept + write action
```

I think typed state is different because it can refuse malformed, stale, or unauthorized state. The first three waves organize model reasoning; typed state adds a deterministic boundary around the resulting facts and authority. Types cannot make an agent correct, but they can turn silent corruption into an inspectable rejection. Workflow state is the plumbing and model reasoning is the cognition, so both need contracts.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts express intent, loops repeat work, and graphs expose routing. Typed state adds the checked record that tells software which version may act.</p></div>

## Model evidence stops at the system boundary

Anthropic's Opus 5 claim comes from a pre-deployment automated audit, which cannot identify the revision or approval behind a later action. I think alignment theater begins when teams use model-level evidence as production proof. A model can pass every examination and still publish a stale revision because the examination never saw it.

The missing record belongs inside an AI Operating Model, meaning the owners, evidence, decisions, and controls around an AI system. Engineering owns the schema; the business or risk owner defines a legal transition. Without that agreement, verification debt grows through assumptions the team cannot later prove.

In a finance system, one corrupted field from an unauditable agent can force staff to reconstruct its source before closing the books, adding audit hours and delaying month-end close. A retained rejection proves that a control stopped the move before its external effect; a clean final row cannot.

Regulation points in the same direction. The [European Union's AI Act, adopted in 2024](https://eur-lex.europa.eu/eli/reg/2024/1689/oj), requires high-risk AI systems to support automatic event recording under Article 12 and deployers to retain controlled logs under Article 26(6). The Commission's [timeline](https://digital-strategy.ec.europa.eu/en/policies/regulatory-framework-ai) extends strict high-risk obligations to December 2, 2027.

Those provisions do not classify a content pipeline as high risk or prescribe typed state. They show why retained transitions matter when an agent changes an authoritative system.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Model audits describe behavior under test. Production accountability needs a separate record of the state, owner, and approval behind each live action.</p></div>

## The old craft returns at one boundary

Strong typing uses declared kinds and constraints to reject incompatible data, one of software's oldest craft disciplines. Computer scientist Robin Milner's [1978 paper on type polymorphism](https://doi.org/10.1016/0022-0000%2878%2990014-4) helped formalize which values belong where. Static checks run before code; model output arrives at runtime and needs validation.

[Ruby on Rails 1.0, released in December 2005](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh), combined web-development conventions with [database migrations](https://guides.rubyonrails.org/active_record_migrations.html), versioned steps for changing stored structure. Migrations were not strong typing. The common move made structural assumptions explicit and reviewable. Rails made web state legible; typed state does the same for agent authority.

Typed state also makes reversibility precise. An expected-version check blocks stale moves, while retained events support restoration. An idempotency key prevents duplicate action on retry but cannot unsend an email or revoke a permission, so external effects still need a correction path. My take is that reversibility becomes credible when those limits live in the state machine, the code governing allowed moves.

On Monday, choose one agent with external write access. Put its engineering lead and system owner in a 30-minute review to name evidence, ownership, retention, and one forbidden transition. For this card, it is `human_approval` to `publish` after the content hash changes.

Store the smallest contract beside the code, then give two engineers two weeks instead of starting a platform rewrite. This is how a pilot earns production ownership. Test three outcomes:

```text
stale revision      → rejection event, no publish intent
approved revision   → one publish intent
caller-crash retry  → existing intent, no duplicate intent
```

Run an incident review from persisted events alone. The team should identify what the agent accepted, why the guard decided as it did, and which action followed. If that requires a transcript, the verification debt remains unpaid.

A one-shot classifier that only labels an input may need a lighter record because control should follow consequence. I don't know which framework will dominate, but I think state contracts will become standard review artifacts for write-capable agents by the end of 2027. If execution traces alone support reliable incident review and crash recovery, that forecast is wrong.

Risbrandt wrote, “We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt.” That returning code lets uncertain models operate where authority must be earned and explained.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Put one consequential transition under a reviewed state contract and test refusal before scale. Agent authority becomes trustworthy when the exact record that permitted an action is reviewable as software.</p></div>
