On July 21, an engineer named Jonas Risbrandt posted a history of agentic coding [on LinkedIn](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz).

> "First, we talked about prompting.
>
> Then we realized one prompt was not enough, so we added loops.
>
> Then loops were not enough, so we introduced graphs.
>
> Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing."

Then he asked: "Haven't we just invented... a programming language?"

Three days later, Anthropic announced [Claude Opus 5](https://www.anthropic.com/news/claude-opus-5), calling it its "most aligned model to date" after a pre-deployment behavioral audit. [The Hacker News thread](https://news.ycombinator.com/item?id=49038433) drew over 1,700 points.

Attention stayed on the model, while Jonas's list carried the engineering signal. I think the useful name is the State Contract Ladder. Each step makes more of the agent's working record explicit.

## Four waves through one article pipeline

The content engine behind this article moves a card through twelve states, including research, draft, fact-check and publish.

### Wave one: prompts

A prompt is an instruction sent to a language model. The first version of our pipeline could fit in four lines:

```text
You are a content pipeline. Take this article idea.
Research it, write it, review it, fact-check it, publish it.
Ask the human if anything is unclear.
```

Production incidents soon add rules about sources and stale numbers. The prompt starts carrying process and memory. It becomes a prompt wearing a toolbelt that code can barely inspect.

### Wave two: loops

ReAct is short for Reason plus Act. The model chooses an action, calls a tool, observes the result and repeats.

```python
while done is False:
    thought = model.reason(context)
    action = model.act(thought)
    result = tools[action.name](action.args)
    context.append(result)  # the chat log carries state
```

The loop can revise, but old and new claims may coexist in its message history.

This article produced the failure itself. The original spec pinned the Hacker News count at 1,723. Fact-check replaced it with "over 1,700." A later revision pulled the old number from stale context. I think this is where a useful loop becomes chat-log archaeology. Finding what the agent believed means reading the transcript.

### Wave three: graphs

LangGraph is a Python framework for agent workflows. Its `StateGraph` class connects work nodes with edges that show the allowed routes.

```python
graph = StateGraph(MessagesState)
graph.add_node("research", research_node)
graph.add_node("draft", draft_node)
graph.add_node("fact_check", fact_check_node)
graph.add_conditional_edges("fact_check", route_by_verdict)
```

`MessagesState` is LangGraph's built-in container for conversation messages. The graph shows the fact-check kickback. A node may still hide a ReAct loop whose memory is a transcript.

[LangGraph supports shared state schemas](https://docs.langchain.com/oss/python/langgraph/graph-api), including schemas with runtime validation. Teams decide how strictly to enforce those boundaries. A graph can organize loose state perfectly.

### Wave four: typed state

A Python `TypedDict` declares dictionary keys and their value types. `Literal` narrows a value to a fixed set. Type checkers use both before the program runs.

```python
Status = Literal[
    "research", "draft", "slop_review", "fact_check", "publish"
]

class CardState(TypedDict):
    card_id: str
    status: Status
    brief_version: int
    kickback_count: int
    sources_verified: bool
    hn_points: str  # "over 1,700"

def transition(raw: dict, to: Status) -> CardState:
    state = validate_card_state(raw)  # runtime validation
    if to == "publish" and state["sources_verified"] is False:
        raise IllegalTransition("unverified sources")
    return {**state, "status": to}
```

`TypedDict` helps the developer and type checker. Pydantic can check live model or database data against the schema. The transition guard blocks publish when source verification is false.

This exact guard is a proposed upgrade to the current pipeline. In this example, the review record would show the brief version and verification status without replaying the conversation.

## Why typed state changes the engineering

Typed state gives failure a place to appear in ordinary code.

Typed state alone defines shape. Runtime validation and explicit transition guards can reject a bad write. A source check still decides whether a claim is true. The schema records whether that check happened.

Temporal and Restate made durable workflow state explicit years ago. LangGraph exposed shared schemas to agent developers. I think the newer move is narrower: teams are typing the facts an agent carries between model calls. Workflow state describes where the job is. Agent state describes what the system currently believes.

Several small projects show this direction. [Inngest AgentKit](https://news.ycombinator.com/item?id=43426164) described a typed state machine in TypeScript in March 2025. MemState used Python validation that December. [Agd](https://news.ycombinator.com/item?id=47224560) explored addressable state in Zig in March 2026, while GraphFlow used Rust. The work spans four languages over sixteen months. Broad adoption remains open.

The craft has old roots. Strong static type discipline has been part of software since the 1970s. [Rails 1.0](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh) used schema as a contract and migrations as reviewed changes in 2005. A legible [AI Operating Model](/posts/building-the-ai-operating-model/) needs that same ownership around agent state.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The fresh part is the state an agent believes, rather than durable workflow plumbing by itself. Types define the record, runtime checks enforce its shape, and a named team owns the contract.</p></div>

## What breaks while state stays loose

A model audit covers a model under test. Production adds tool results and stored memory after that test.

I think the qualifier in Anthropic's claim deserves as much attention as the headline. In *Blade Runner*, the Voight-Kampff test examines a subject in a controlled interview. A production agent leaves the room with tool access and a changing memory. The audit tells you about the subject in the room. Persisted state tells you what the system acted on later.

The phrase "alignment theater" fits when a model audit substitutes for production records. The model may follow its rules while reading a stale field. An operator then has a transcript instead of an answer: what did the system know when it made this decision?

For high-risk AI systems, that question has legal weight. [Article 12 of the EU AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj) requires systems to allow automatic event logging. Article 26(6) requires deployers to retain logs under their control. The main Annex III obligations began applying on August 2, 2026. A content pipeline falls outside that category by default, but an agent in a high-risk domain needs records that survive an audit.

Loose state creates operating risk too. If a finance agent carries a corrupt value, month-end close may be where the error surfaces. Every field that escapes a check adds [verification debt](/posts/2026-03-09-verification-debt-crisis/).

I don't know whether typed state is the final wave. My 2028 bet is shared memory across many agents. The agent forgets. The shared record keeps the error until a system with authority acts on it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Model alignment cannot answer which stored facts shaped a production action. Persisted, validated state gives operators an inspectable record and prepares high-risk systems for real logging duties.</p></div>

## What to change on Monday morning

Start with one long-running agent whose mistakes already require human review.

Write the fields it carries between steps. Compare that list with the live payload. Leftover prompt keys and duplicated facts show where verification debt has collected.

The product team that owns the decision should own the schema. A platform team can supply validators and storage.

Guard one costly transition. For this content pipeline, a safer design rejects `publish` when `sources_verified=False`. Persist accepted state changes with enough context to explain who changed what and under which schema version.

When a system stores sufficient snapshots and implements authorized rollback or compensation, its record can support [reversibility](/posts/reversibility-is-the-new-correctness/). External side effects may still need compensation.

I think one boundary is enough for the first pull request. Jonas ended his post with the line hiding inside the whole argument: "We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt."

For this pipeline, that code belongs around `publish`.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Pick one costly transition and make its state contract visible in code. The prompt may remain probabilistic. The transition to publish should be a contract.</p></div>
