A Swedish engineer named Jonas Risbrandt posted this week that agentic coding has gone through three waves: prompts, then loops, then graphs, and now typed state. His exact words: "Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state."

Each wave looked like a feature. Each one was actually a fault line.

The same week, Anthropic shipped Opus 5 with the claim "most aligned to date," and the Hacker News thread pulled 1,723 upvotes. I think the timing is the story. The field is converging on something quieter than bigger models: smaller loops with typed state. Teams working in Python, TypeScript, Rust, and Zig are arriving at the same architecture independently. When that happens, something structural is going on.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts, loops, graphs, typed state. Four waves, one running example, and a reason the fourth wave is the first one that makes agents auditable.</p></div>

## Wave one: prompts

The 2023 pattern. One big prompt holds everything: instructions, edge cases, tool descriptions. One call, one answer.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A prompt-only agent produces one answer you cannot inspect. It works until the input stops looking like the demo.</p></div>

Here is the example we will carry through the whole piece: an invoice agent. Its job is to read incoming invoices and return vendor, date, and total.

Wave one, you write a careful prompt. It works on the demo invoice. Then a real invoice arrives with two totals on it, net and gross. The model picks one. The output looks right. Nobody checks, because there is nothing to check against. The prompt is a black box that returns JSON.

A prompt wearing a toolbelt is still a black box. You added capability. You did not add anything you can audit.

## Wave two: loops

So the field wrapped the model in a loop. The pattern most people met first is ReAct: reason, act, observe, repeat. The model writes a thought, calls a tool, reads the result, thinks again.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Loops made agents more capable and less legible. State corruption moved into the transcript, where nobody reads it.</p></div>

```python
while not done:
    thought = model.think(transcript)
    if thought.wants_tool:
        result = run_tool(thought.tool_call)
        transcript.append(result)
    else:
        done = True
```

The invoice agent gains a calculator and a second OCR pass. Accuracy goes up. Then, on turn nine of a long run, the model "corrects" the total. The correction lives in the transcript, buried inside nine turns of reasoning text.

Reading nine turns of chain-of-thought to find one bad write is archaeology. Engineering needs something better. The state of the agent (what it currently believes about vendor, date, total) was still nowhere. It was smeared across prose.

## Wave three: graphs

So the field drew the control flow. LangGraph is the framework most teams met here. Its core idea, the StateGraph, is simple: you declare your agent as a graph. Each node is a step, like "parse invoice" or "match purchase order." Each edge is an allowed transition.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Graphs made control flow visible. The data flowing through them stayed a shapeless bag, and that is where the failures hid.</p></div>

The invoice agent becomes a clean diagram. Parse, extract, match, approve. You can point at the picture in a design review.

But here is what broke in production. The parse node wrote the total as the string "10.000,00", Swedish formatting for ten thousand kronor. The approval node read it as a number and got one million. The graph showed exactly where control flowed. It said nothing about what the data was allowed to look like. State was still a plain dictionary, and any node could write anything into it.

The graph hid the loop inside architecture diagrams. The mess moved again, somewhere harder to see.

## Wave four: typed state

The fourth wave gives the state a declared shape. In Python the tool is TypedDict: a dictionary where you declare every key and its type up front, and anything that violates the declaration fails loudly.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state makes the agent's beliefs a first-class, inspectable object. Bad writes fail at the moment they happen, with the value attached.</p></div>

```python
class InvoiceState(TypedDict):
    vendor: str
    invoice_date: date
    total_sek: Decimal
    po_number: str | None
    status: Literal["received", "parsed", "matched", "approved"]
```

Now every node reads and writes through this shape. The Swedish-formatted string from wave three never makes it in. A validator rejects it the moment the parse node tries to store it, at 09:14 on a Tuesday, with the offending value attached. The wave-two corruption has nowhere to hide, because there is no prose to hide it in. There is only the state, and the state has a type.

## Why typed state is the engineering win

Pongsak Khamdee's graph engineering essay frames the ladder well. A loop externalizes iteration and evaluation. A swarm externalizes parallel search. A graph externalizes shared facts and memory. I would add one rung: typed state externalizes the contract. The bottleneck was never the next model call. The bottleneck is everything that call is silently carrying.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Each wave externalized something the prompt could not hold. Typed state externalizes the contract itself, the same craft move Rails made in 2005.</p></div>

This is the same craft move that made Rails possible in 2005. Rails did not speed up web apps through cleverness. It made the implicit explicit: conventions, a schema, one place where the shape of your data lived outside any single request. Agent systems in 2026 need that move, and typed state is it. Strong typing is the oldest craft discipline we have in software. It took autonomous systems to make us rediscover why.

It also pays down debts I have written about before. Verification debt: every unauditable agent run is a claim you never checked, and typed state is how you start checking. Reversibility: a state machine with declared transitions can roll back by construction, instead of by hoping the prompt remembers what it did. And the AI Operating Model thesis: a legible operating model requires inspectable agent state. Typed state is what "inspectable" means in practice.

## What breaks without it

The failure cascade runs like this. Prompts wearing a toolbelt. Loops hiding state corruption. Graphs hiding loops. A stateful mess nobody can audit, running in production, approving invoices.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>An aligned model with unauditable state is HAL 9000. Alignment claims mean little if you cannot read what the system currently believes.</p></div>

Which brings me back to Opus 5 and "most aligned to date." I think claims like that are aiming at the wrong layer. In 2001: A Space Odyssey, HAL 9000 did not fail because it was stupid. It failed because its objectives lived where the crew could not see them. Dave had to pull memory modules one by one while it sang. That is what operating an agent without typed state feels like at scale: you find out what the system believed by taking it apart.

Typed state is the difference between auditing a system and lobotomizing it.

I don't know if typed state is the last wave. I doubt it. But it is the first wave that makes the mess visible by construction, rather than by forensics after the incident.

## What to do on Monday

Pick the loudest agent you run. Write down its state as a type: every field, every allowed value. Route every node through it. Put one validator on the boundary between the model and the state.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Type one agent's state this week. The validator's rejection log is the first honest picture you will have of what it actually does.</p></div>

Then read what the validator rejects for a week. That rejection log will teach you more about your agent than any alignment benchmark. My take: the teams that win the next two years will be the ones whose agents you can open like a book, not the ones whose agents score highest on a leaderboard.

Every wave was a confession. The state was the system all along.
