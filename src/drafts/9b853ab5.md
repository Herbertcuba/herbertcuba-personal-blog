On July 21, engineer Jonas Risbrandt [described agentic coding’s progression](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz): “Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing.” He then asked, “Haven’t we just invented... a programming language?”

Three days later, AI developer Anthropic [introduced Claude Opus 5](https://www.anthropic.com/news/claude-opus-5) for long-running agents. Anthropic said a pre-deployment audit found it to be “our most aligned model to date,” and the [Hacker News discussion](https://news.ycombinator.com/item?id=49038433) drew over 1,700 points. That audit evaluates pre-release behavior. It cannot identify the evidence and human decision behind a later production action.

I think Jonas’s sequence names the engineering gap. Prompts express intent and loops retain activity. Graphs expose routes. Typed state makes the accepted facts and allowed next action inspectable before an external write.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Model evaluations describe pre-release behavior; production control requires a durable record of what authorized each consequential action.</p></div>

## Follow one claim through four waves

In a publishing pipeline, a source snapshot shows a changing Hacker News score. Revision `v7` says “1,723 points”; a fact reviewer approves `v8`, “over 1,700 points,” with the source URL and check time. Both remain for audit; a later retry attempts stale `v7`.

A **prompt** is one instruction sent to a model:

```text
Research the claim, revise it, get approval, then publish.
```

A prompt can call every tool yet keeps no authoritative field binding publication to `v8`. The policy lives in prose, so the publishing tool can receive `v7`.

A **loop** repeats model reasoning and tool use. The 2022 [ReAct pattern](https://arxiv.org/abs/2210.03629), short for Reason and Act, interleaves reasoning with actions and their results:

```python
while card.open:
    result = agent.run(history)
    history.append(result)
```

History contains the snapshot, both revisions, and the approval, but no accepted-revision field. A larger context adds text without identifying the record governing the write.

A **graph** names steps and routes between them:

```text
draft -> fact_check -> approval -> publish
   ^          |
   +-- revise-+
```

The `publish` node may read the latest message and call the tool without checking the approved revision. Like the Nostromo deck plan in *Alien* (1979), visible corridors reveal little about the danger inside one room.

**Typed state** declares persisted fields and allowed values. Its transition guard controls movement:

```text
PublishState:
  status: approved | publishing
  revision_id: text
  approved_revision_id: text
  evidence_ids: text[]
  version: integer

require(state.status == "approved")
require(state.revision_id == state.approved_revision_id)
require(state.evidence_ids)
with db.transaction():
    card.move("publishing", revision="v8", evidence=state.evidence_ids,
              expected_version=state.version)
    outbox.put_once("publish:card-42:v8", revision="v8")
```

`expected_version` makes the database reject an older worker after state changes. The **outbox** is a durable pending send. Its **idempotency key**, `publish:card-42:v8`, makes retries reuse one delivery, whose receipt records the effect. Stale `v7` fails the revision guard and changes neither the card nor the outbox.

Fact review supplies evidence, and types check its shape. The guard then verifies status and approved revision. I think the engineering gain is clear: hidden corruption becomes a rejected transition with a reason.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts carry intent, loops carry history, graphs carry routes, and typed state lets only the approved revision cross the publishing boundary.</p></div>

## Bring an old craft discipline to agent state

Programming-language type systems that reject invalid states reach back to Hindley-Milner research in the 1970s. In 2005, the [Rails 1.0 web framework](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh) used migrations to make database changes reproducible and reviewable, even in dynamically typed Ruby. The shared principle is reviewable change: Rails versions schema migrations; agent types describe state, while guards and persistence preserve the accepted record.

Execution history records each node attempt and outcome. Accepted state says `v8` may advance with named evidence. The outbox records intended delivery; the publisher receipt records the result. I think traces help diagnosis; these records reproduce the authorization path.

That path pays down **verification debt**, the gap between a prompt rule and the proof a system can produce. It gives reversibility a concrete form because an amendment can retain the original state and receipt. An **AI operating model** is the ownership and control around AI work; it stays inspectable when retention and access rules attach to a named record owner.

Anthropic’s audit can inform model selection. It cannot identify `v8`, its evidence, the allowed transition, or the delivery receipt during an incident. I think presenting that audit as sufficient production control amounts to “alignment theater”: visible assurance without decisive incident evidence.

A one-shot classifier returning a temporary label can carry a lighter record. The control burden rises when an agent keeps state and receives authority to publish, refund, or update a system of record.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state complements workflow history by preserving the evidence and transition that authorized an external effect.</p></div>

## Put one boundary under contract on Monday

For `approved -> publishing`, spend 30 minutes producing a one-page state contract. Name the required evidence and owner, set retention and access rules, then encode the illegal condition: a revision mismatch leaves state and outbox unchanged.

Within two weeks, two engineers prove four tests. Stale `v7` must leave no outbox item; approved `v8` must persist its evidence and one item. After failure, a retry produces one receipt, while an amendment retains the original so reviewers can reconstruct the change.

Ask the risk owner one practical question: who can retrieve the accepted state and delivery receipt during an incident, and for how long? If the vendor cannot export that record, its operating model remains dependent on raw traces.

I don’t know which agent framework will dominate. My take: by the end of 2027, teams granting write access will review state contracts before switching orchestration frameworks. Traces that reproduce the accepted evidence, allowed transition, and single delivery after a crash would disprove that claim.

An agent earns more authority when stale `v7` fails loudly, approved `v8` ships once, and the amendment path preserves what happened.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Guard one costly transition, prove rejection and recovery, then expand the agent’s authority.</p></div>
