On July 21, 2026, [engineer Jonas Risbrandt described the evolution of agentic coding in a LinkedIn post](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz). Agentic coding lets an AI model plan, use tools, and respond to results while pursuing a goal.

> “Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing.”

Risbrandt then asked, “Haven't we just invented... a programming language?” I think he named the pattern. The engineering win is an authority record: a machine-checkable account of the version, evidence, approval, and rule behind a live action.

On July 24, AI company Anthropic [announced Claude Opus 5](https://www.anthropic.com/news/claude-opus-5), which it positioned for long-running work. Anthropic said a pre-deployment audit found it to be “our most aligned model to date.” By early August, its discussion on [Hacker News, a technology forum](https://news.ycombinator.com/item?id=49038433), had more than 1,700 points. I think the launch and post belong together because model capability does not expose stale or unauthorized production state.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Agent frameworks are rediscovering software structure. Typed state matters because it records the authority behind a model action in a form that software can inspect and enforce.</p></div>

## Four waves, one publication card

Consider an article card whose brief contains an exact Hacker News score. Fact review replaces it with “more than 1,700 points,” and only that verified, human-approved revision may publish. Each wave solves a different part of this problem.

### Prompt

A prompt is a natural-language instruction supplied to a model.

```text
Research the card, write the article, verify every source,
and publish only the approved revision.
Use “more than 1,700 points,” never an exact score.
```

“Approved revision” names no machine-checkable object. As incident rules accumulate, the prompt becomes a data contract, workflow, and runbook without proving which revision the human approved.

### Loop

A loop lets the model choose an action, inspect the result, and repeat until it reaches a stopping condition.

```python
while card.status not in {"done", "escalated"}:
    action = model.choose(message_history)
    result = tools.run(action)
    message_history.append(result)
```

Message history now acts as informal state, the facts carried between steps. Both scores can remain, so a later pass may retrieve the wrong one without breaking the loop. I think that is dangerous because visible progress can continue after state becomes corrupted.

### Graph

A graph connects workflow steps, called nodes, with directed edges that determine which step runs next.

```text
research → draft → fact_check → human_approval → publish
             ↑          |
             └─ kickback┘
```

The failed fact check has a route back to drafting. Yet the graph does not prove that the drafting node received the correction, and each node may hide another prompt or loop. Routing is explicit; data authority remains implicit.

### Typed state

Typed state declares the fields and allowed values a workflow may carry. Persistence stores that record beyond one model call. This illustrative boundary uses [Pydantic, a Python library that validates data at runtime](https://docs.pydantic.dev/latest/concepts/strict_mode/), inside a locked database transaction:

```python
class PublishState(BaseModel):
    model_config = ConfigDict(strict=True)
    card_id: str
    version: int
    status: Literal["fact_check", "human_approval", "publish"]
    revision_id: str
    content_hash: str
    fact_report_id: str | None
    sources_verified: bool
    approved_revision_id: str | None
    approved_content_hash: str | None
    approved_by: str | None

with transaction():
    current = PublishState.model_validate(lock_card(request.card_id))
    require(request.expected_version == current.version)
    require(current.status == "human_approval")
    require(current.sources_verified and current.fact_report_id is not None)
    require(current.revision_id == current.approved_revision_id)
    require(current.content_hash == current.approved_content_hash)
    write_publish_intent_once(request.idempotency_key, current)
    advance_if_version(current.card_id, current.version, "publish")
```

The schema declares fields; runtime validation checks incoming data against them. A content hash fingerprints the draft. The expected-version check rejects an older record, while the `require` statements are transition guards that stop a valid record from taking an unauthorized route.

`write_publish_intent_once` represents an outbox record, a durable instruction stored with the database change. Its idempotency key names one operation, so a retry finds the existing instruction instead of creating another. The same boundary can bind an invoice version to purchase-order evidence and budget-owner approval, or an access request to an employee, role, and manager.

## Why typed state changes the engineering boundary

Typed state does not replace graphs. [LangGraph, a graph-based agent library from AI tooling company LangChain](https://docs.langchain.com/oss/python/langgraph/graph-api), supports shared state schemas. In March 2025, [workflow company Inngest described its TypeScript AgentKit library as using a “fully typed state machine” for routing](https://news.ycombinator.com/item?id=43426164). These are signs that independent teams are arriving at a similar architecture, not evidence of broad adoption.

Strong typing has no universal definition. Here, typed state means a schema enforced at runtime and the database boundary; Python annotations alone do not police inputs. It cannot verify a source or make a model correct, but it can refuse a missing report, changed revision, or forbidden transition.

I think this makes typed state more than another layer. Retries need a known starting record, observability needs stable fields, and persistence needs storage rules. Types give those controls named facts, turning failure into a rejected transition rather than chat-history archaeology.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The fourth wave makes informal workflow state explicit. Its bounded engineering gain is the power to refuse an action whose evidence, version, approval, or route does not match.</p></div>

## What implicit state costs

An execution trace records which steps ran. It may show `human_approval` before `publish` while omitting which revision was approved. The incident review then has to reconstruct authority from activity records that were never designed to prove it.

I call that gap verification debt: the distance between what a workflow assumes and what its records can demonstrate. In the publication card, the debt is one stale claim. In invoice approval or access provisioning, the same missing link can consume audit time, delay a close, or keep a promising pilot from earning production ownership.

This is also where model alignment and system accountability separate. Anthropic's claim described behavior measured before deployment; it did not claim to prove which evidence a later production action used. My take is that alignment theater begins when a model evaluation is treated as proof that the live system carried the right state.

An AI Operating Model is the ownership, evidence, decisions, and controls around an AI system. It becomes legible when the business names a consequential transition, engineering enforces it, and reviewers inspect accepted and rejected records. The [European Union's 2024 AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj/eng) points in this direction without prescribing typed state. For high-risk systems in scope, Article 12 requires automatic event recording, while Article 26(6) requires deployers to retain generated logs under their control for at least six months unless other law says otherwise. A publication workflow is not automatically high risk, but a retained rejection tied to a version, rule, and owner gives an auditor evidence to test.

Typed state also makes reversibility precise: return to a known accepted version or run a named correction after an external effect. Versioned records support replay, and an idempotency key can prevent a duplicate instruction, but neither can unsend an email or reverse a payment. Those effects need explicit compensation paths. I think shared state between several agents will become the next fault line if nobody can show which agent changed it or why.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Activity logs show what ran, while authority records show which facts and approval allowed it to run. Without that link, verification debt grows across incidents, audits, and attempts to move pilots into production.</p></div>

## Put one contract into review

Computer scientist Robin Milner's [1978 paper “A Theory of Type Polymorphism in Programming”](https://doi.org/10.1016/0022-0000%2878%2990014-4) presented a formal type discipline with a compile-time checking algorithm. The discipline is old: declare valid forms and reject invalid combinations before action.

Web applications already existed when [Ruby on Rails 1.0, a web framework, arrived in December 2005](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh). Rails migrations gave teams reproducible instructions for moving a database schema from one version to another, which made structural change easier to review and deploy. Rails made web state legible. Typed state can do the same for agent state.

On Monday, ask the enterprise architect and system owner to convene a 30-minute review with the business owner. Choose one write-capable agent and one consequential transition. Name its version, evidence, approver, retention rule, and one forbidden move. The business owner accepts the rule; a named engineer owns its enforcement.

Time-box a two-engineer, two-week pilot instead of beginning with a platform rewrite. Persist both acceptance and rejection, then make these tests pass:

```text
stale approved revision → rejection, no publish intent
current approved revision → one publish intent
retry after a crash with the same key → existing intent, no second record
```

Run an incident review from persisted state alone. If the team cannot explain what was accepted, which guard decided, and what followed, its verification debt is visible. This is how an interesting pilot earns production ownership.

I don't know which agent framework will dominate. I think a useful prediction is that by the end of 2027, teams running write-capable agents will treat state contracts as a standard review artifact. If execution traces alone consistently support incident review and crash recovery, the extra contract adds little. I do not expect that result.

Risbrandt's sharper line was, “We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt.” The code that endures will be the code that records why an uncertain model was allowed to act.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Review one consequential transition as a software contract, test its refusal and recovery paths, and demand an incident explanation from persisted state. Craft discipline is back when authority becomes executable.</p></div>
