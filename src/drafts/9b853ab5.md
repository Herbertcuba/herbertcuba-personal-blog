An engineer named Jonas Risbrandt posted a short history of agentic coding [on LinkedIn](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz) last week. I think it is the sharpest summary of the last four years:

> "First, we talked about prompting. Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing."

Then he lands the punch: "Haven't we just invented... a programming language?"

The timing helps. The day before Jonas posted, Anthropic [shipped Claude Opus 5](https://www.anthropic.com/news/claude-opus-5) and called it its most aligned model to date after a pre-deployment behavioral audit. [The Hacker News thread](https://news.ycombinator.com/item?id=49038433) passed over 1,700 upvotes. One conversation looked up at the model. Jonas looked down at the system carrying it.

Each wave looked like a feature. Each one was a fault line. This is fault-line archaeology: every layer records the failure that forced the next one into existence.

<div class="article-tldr"><span class="article-tldr__label">Article TL;DR</span><p>Agentic coding moved through prompts, loops, and graphs before arriving at typed state. The first three waves made control easier while leaving the agent's beliefs hard to inspect. Typed state gives those beliefs a schema, rejects illegal moves at runtime, and makes auditability and reversibility part of the system.</p></div>

## Four waves, one pipeline

Use one real example throughout: a content pipeline that moves an article idea through twelve states, from inbox to publish.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The prompt became a junk drawer. The loop smuggled state into the chat log. The graph showed the routes while its nodes kept the mess hidden. Typed state gives the pipeline a contract.</p></div>

### Wave one: the prompt is the program

The first version fits in four lines:

```
You are a content pipeline. Take this article idea.
Research it, write it, review it, fact-check it, publish it.
Ask the human if anything is unclear.
```

A prompt is the instruction sent to a language model. Once tools get attached, the prompt also starts carrying rules about when to search, when to ask for help, and what counts as done. Every incident adds another paragraph. Soon the prompt is trying to be a schema and a runbook at the same time. It cannot enforce either role.

### Wave two: the loop hides the state

The next version adds ReAct, short for Reason plus Act. ReAct is a loop where the model chooses an action, calls a tool, reads the result, and repeats:

```python
while not done:
    thought = model.reason(context)
    action = model.act(thought)
    result = tools[action.name](action.args)
    context.append(result)   # state = the whole chat log
```

The pipeline can now research, revise, and retry. But its state lives in the message history. This article exposed the failure. The brief carried a stale exact Hacker News count of `1,723`. Fact-check corrected it to the safer "over 1,700." A later revision pulled the old number back from context. The error was another message in the log, with no field saying which value had passed verification.

### Wave three: the graph hides the loop

LangGraph is a Python framework for building agent workflows as graphs. A graph has nodes, the steps that do work, and edges, the allowed routes between those steps. `StateGraph` is LangGraph's class for connecting those nodes around shared state:

```python
graph = StateGraph(MessagesState)
graph.add_node("research", research_node)
graph.add_node("draft", draft_node)
graph.add_node("fact_check", fact_check_node)
graph.add_conditional_edges("fact_check", route_by_verdict)
```

The route is finally visible. A failed fact-check can return the card to draft. Yet each node may still contain a loop whose memory is a long chat transcript. [LangGraph's documentation](https://docs.langchain.com/oss/python/langgraph/graph-api) permits a shared typed schema. It does not force every payload through runtime validation, so teams can still pass loose dictionaries between nodes.

### Wave four: the schema is the contract

A `TypedDict` is a normal Python dictionary with declared keys and value types. It helps an editor or type checker catch mistakes before the code runs:

```python
class CardState(TypedDict):
    card_id: str
    status: Literal["ideas_inbox", "approved", "research", "draft",
                    "slop_review", "fact_check", "persona_panel", "design",
                    "human_approval", "publish", "done", "escalated"]
    brief: str | None
    draft: str | None
    kickback_count: int
    sources_verified: bool
    hn_points: str            # "over 1,700"

def transition(raw: dict, to: Status) -> CardState:
    state = validate_card_state(raw)  # Pydantic validation at runtime
    if to == "publish" and not state["sources_verified"]:
        raise IllegalTransition("unverified sources")
    return {**state, "status": to}
```

`TypedDict` alone only helps during type checking. The boundary still needs runtime validation, using Pydantic's `model_validate` or an equivalent validator. Otherwise the guard is decoration.

Now the pipeline can reject an illegal publish move before a stale claim ships. When the card entered review, the system can answer with a structured record: brief version four, sources unverified, one kickback. I think that answer is the engineering win.

## Why this wave changes the job

Typed state changes the question from "did the agent sound right?" to "what did the agent believe when it acted?"

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Durable workflow systems already typed the plumbing, and agent frameworks already support schemas. The newer move is typing cognition: the facts, confidence, approvals, and unresolved errors the agent carries between steps.</p></div>

There is prior art. Temporal, Restate, and DBOS gave long-running workflows durable state years ago. LangGraph's `TypedDict` patterns and Pydantic AI already made typed agent data familiar. The new pressure sits one layer deeper: teams are typing the agent's beliefs, alongside the workflow that moves them.

That line separates plumbing from cognition. Workflow state says which node runs next. Agent state says which sources were checked, whether approval exists, and which error remains unresolved. I think a legible AI operating model needs both, because ownership means little when nobody can inspect the state being owned.

The convergence is easy to date. [Inngest AgentKit](https://news.ycombinator.com/item?id=43426164) described a fully typed state machine in March 2025. [GraphFlow](https://news.ycombinator.com/item?id=44481157) cited type safety in Rust that July. [MemState](https://github.com/scream4ik/MemState) added validate-on-write memory in Python in December. [Turn](https://news.ycombinator.com/item?id=47220136) and [Agd](https://news.ycombinator.com/item?id=47224560) arrived in March 2026, using Rust and Zig. Independent teams reached the same architecture across four languages in sixteen months. That shows direction rather than adoption.

Rails made a neighboring craft move in 2005. It made web state legible through schema as contract and changes as migrations. Typed state gives agent systems the same kind of legibility. Type discipline has been available since the 1970s. I think agent engineering is rediscovering why it survived.

## What breaks without legible state

The failure starts as a debugging nuisance and ends as an accountability problem.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Model alignment cannot explain a production decision made from corrupted state. Typed, persisted state gives operators and auditors a record they can inspect, while the next fault line is forming in memory shared across many agents.</p></div>

A prompt wears a toolbelt. A loop hides a corrupted belief. A graph gives the loop a clean box and a tidy arrow. The production system still cannot answer which claim was verified before publish.

This is where alignment becomes theater. Anthropic's Opus 5 claim rests on pre-deployment testing. I think the qualifier deserves as much attention as the claim. In *Blade Runner*, the Voight-Kampff test measures a replicant in an interview room. A pre-deployment behavioral audit works in a similar frame. It tells you how the model behaved in the room. Your production system is off-world, carrying tools and state the test never saw.

The regulatory direction is already clear. [The EU AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj) requires high-risk AI systems to support automatic event logging under Article 12, while Article 26(5) requires deployers to retain logs under their control. The main high-risk obligations began applying on August 2, 2026. That was Sunday. When an agent touches a high-risk domain, "what did the system know when it made this decision?" can become a legal question.

At enterprise scale, one corrupted field in an unauditable finance agent can stall the month-end close and start a restatement conversation. The model may have behaved exactly as designed. The state it received was wrong.

I don't know whether typed state is the final wave. My bet is that the unauditable mess of 2028 will be multi-agent shared memory. One agent forgets. The shared graph remembers, including the mistake.

## What to do on Monday morning

Start with one agent whose mistakes cost enough that somebody checks its work.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Write one schema, guard one expensive transition, and assign one owner. Compare the declared fields with runtime state on every deploy so drift becomes visible before it turns into verification debt.</p></div>

A one-shot classifier that labels a support ticket and exits may never need durable state. A publishing, payment, booking, or deployment agent does.

Give two engineers two weeks. Write the fields the agent is allowed to carry and the transitions it may take. Add runtime validation at every boundary. Guard the move with the highest cost, such as publish with unverified sources.

Put the baseline schema with the platform team. Let product teams propose changes, and make one named engineer approve them like any other contract. Run a schema-versus-runtime diff on every deploy, then review drift once per sprint. The first diff will often expose scratchpad keys left behind by deleted prompts or confidence fields that never reached the dashboard.

That gap is [verification debt](/posts/2026-03-09-verification-debt-crisis/) made visible. Persist each accepted transition and [reversibility](/posts/reversibility-is-the-new-correctness/) becomes a property of the state machine. A team can inspect the old state, replay the move, and return to the last valid checkpoint.

Jonas wrote, "We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt." The model can stay probabilistic. The system around it has to become legible.
