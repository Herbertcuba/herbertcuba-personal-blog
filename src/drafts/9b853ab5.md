Fast-moving agent frameworks are returning to old software discipline. In late July, engineer Jonas Risbrandt [described the sequence](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz): “Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state...” His punchline was, “Haven't we just invented... a programming language?”

That week, Anthropic [said](https://www.anthropic.com/news/claude-opus-5) a pre-deployment audit found Opus 5 to be “our most aligned model to date.” Its [Hacker News thread](https://news.ycombinator.com/item?id=49038433) passed 1,700 points. Release attention can hide an operational gap: the audit cannot show which evidence authorized a live action after a retry. Each wave added capability and exposed another fault line. I think typed state is different because it makes production authority inspectable.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Better model behavior leaves teams needing a durable record of what an agent accepted and why it could act.</p></div>

## Four waves through one stale claim

A publishing brief stores a changing HN score as an exact number, then fact-checking approves “over 1,700 points.” A later writer run reloads the brief and restores the stale figure. Both claims remain in the transcript, with no authoritative value for the next transition to check.

**Prompt.** A prompt is an instruction given to a model.

```text
Research -> draft -> fact-check -> publish.
Use the fact-checker's approved wording.
```

The policy exists as prose. No checked field identifies the approved revision, so the prompt can act on either version.

**Loop.** A loop repeats model reasoning and tool calls until a stopping condition.

```python
while card.status != "done":
    action = model.run(messages)
    messages.append(run_tool(action))
```

The loop handles longer work, but its history carries conflicting claims. I think a larger context window preserves the conflict without deciding which claim governs the next step.

**Graph.** A graph names workflow steps and routes.

```text
research -> draft -> fact_check -> approve -> publish
             ^           |
             +--- revise -+
```

The route is visible, although each node can still read both claims from message history. [LangGraph](https://docs.langchain.com/oss/python/langgraph/graph-api) supports shared state schemas. The fourth wave begins when consequential writes must satisfy one.

**Typed state.** Typed state is a persisted record with checked fields, allowed values, and legal transitions. In this Python-style pseudocode, a transition means a permitted state change:

```python
class ArticleState(TypedDict):
    revision_id: str
    approved_revision_id: str | None
    accepted_evidence_id: str | None
    approved_by: str | None
    status: Literal["draft", "approved", "publishing", "published"]
    publish_key: str | None
    effect_id: str | None

def authorize_publish(s):
    require(s["status"] == "approved")
    require(s["revision_id"] == s["approved_revision_id"])
    require(s["accepted_evidence_id"])
    require(s["approved_by"])
    return persist(s, status="publishing",
                   publish_key=stable_key(s["revision_id"]))
```

Fact-checking binds accepted evidence to one revision. A validator checks the contract before `approved -> publishing`, and a stale revision produces no send record. Human review judges source credibility. The type contract makes that recorded decision enforceable.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts store policy, loops accumulate history, and graphs expose routes. Typed state binds accepted evidence to the publishable revision.</p></div>

## Typed state turns history into authority

Tool traces preserve service outputs, while execution history preserves worker position. Accepted state names the evidence governing the next move. An `effect_id` links that authority to the published result.

A durable workflow engine can resume execution after a crash. The state contract carries business authority. Approved state and an outbox, a durable pending send, commit in one transaction. A stable idempotency key identifies one intended effect across retries; after delivery, the pipeline saves its `effect_id`.

I think strong typing earns its place by turning a silent contradiction into a rejected write. Software has used this discipline since the 1970s. [Rails 1.0](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh) made database changes reviewable through migrations; agent schemas apply the same craft to evidence and approval. I don't know which framework will lead. The contract can outlast it.

The Opus 5 audit describes behavior before deployment; incident review needs the approved revision afterward. In *The Martian*, an airlock needs a known pressure state and a permitted transition. Reasonable-sounding instructions offer no equivalent control.

For high-risk systems, the [EU AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj) points the same way: Article 12 requires automatic event logging, and Article 26(5) requires deployers to retain logs under their control. I think a legible AI Operating Model starts with inspectable state. The gap between written policy and enforced fields is verification debt; saved versions make reversibility a state-machine property.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Logs describe activity. Typed state links approved evidence to the delivered effect that gives a production action authority.</p></div>

## Put one boundary under contract on Monday

Put `approved -> publishing` through a 30-minute review. Record accepted evidence, owner, retention and access, and the illegal condition. Give two engineers two weeks to persist and test the contract within the current platform.

Then force the recovery path. Commit the authorized state and outbox, stop the worker before send, and restart through another worker. The retry must use the saved idempotency key, create one external effect, and persist an `effect_id` tied to the approved revision. A second test presents the stale revision and confirms that no outbox record is created.

I think this small test pays down verification debt faster than another prompt rule. My take is that teams granting agents external write authority will soon review state contracts as seriously as API contracts. Jonas wrote, “We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt.” That returning code is craft discipline.
