On July 21, 2026, engineer [Jonas Risbrandt compressed the history of agentic coding into a LinkedIn post](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz):

> “Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing.”

His punchline: “Haven't we just invented... a programming language?” Three days later, Anthropic, the company behind Claude, [announced Opus 5](https://www.anthropic.com/news/claude-opus-5) as a model for long-running, multi-step agent work. Anthropic said a pre-deployment behavioral audit found it to be “our most aligned model to date,” while the [Hacker News discussion](https://news.ycombinator.com/item?id=49038433) drew over 1,700 points.

I think the timing matters. Better models make long-running agents useful, and longer runs multiply the chances of carrying an old fact or wrong approval forward. Typed state addresses that problem with a persisted record whose fields have defined meanings and whose allowed changes are checked before the system acts. Each earlier wave expanded what agents could do while exposing where informal state fails.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Long-running agents turn hidden state into a production risk. Typed state gives teams a checked, persisted record of what an agent accepted and what it may do next.</p></div>

## Four architectures, one questionnaire

Consider a hypothetical agent that completes a customer security questionnaire. It reads approved policies, drafts answers, routes uncertain claims to a reviewer, and sends the finished file. Trouble starts when policy version 8 changes an answer but the system still carries approval issued for version 7.

### Prompt

A prompt is the natural-language instruction a model interprets. The first version of this agent might be almost entirely prose:

```text
Read questionnaire Q-47.
Answer only from the approved policy folder.
Ask Security to review unsupported answers.
After approval, send the completed file to the customer.
```

The prompt combines the goal, evidence policy, review route, and permission for an external action. Each incident adds another clause about versions or revisions. The prompt starts wearing a toolbelt because prose is doing the work of data structures and transition rules, yet nothing formally binds “approved” to the answer revision the reviewer saw.

### Loop

A loop repeats model decisions, tool calls, and observations until a stop condition is reached:

```python
while not complete:
    action = model.next(messages)
    result = run_tool(action)
    messages.append(result)
```

Now the message history often becomes the working state. Q-47 can contain the version 7 answer and approval, followed by the version 8 policy and a revision. All are present; none is marked authoritative. If the model treats the old approval as permission to send the new answer, state corruption moves forward without breaking the loop. I think this is where many convincing demos become difficult production systems: the transcript remembers everything except which fact governs the action.

### Graph

A graph represents the workflow as named nodes connected by directed edges. It makes routing easier to inspect:

```text
extract → retrieve → draft → review → send
                       ↑         |
                       └─ revise ┘
```

The graph shows that rejection returns the draft for revision and approval permits sending. Yet the `review` node may contain a loop that still uses free-form messages. Passing through that node does not prove the reviewer approved the current policy version and answer hash, a fingerprint of the file's contents.

[LangGraph, LangChain's framework for graph-based agent workflows](https://docs.langchain.com/oss/python/langgraph/graph-api), already defines state as a shared application snapshot and supports a shared schema. The problem appears when teams leave that schema optional, skip runtime validation, or fail to connect accepted state to the next action. Graphs are not inherently untyped, but a visible route can still carry an ambiguous payload.

### Typed state

Typed state makes that payload an explicit contract. Pydantic, a Python data-validation library, can check model output at runtime instead of relying only on type hints seen before execution:

```python
class QuestionnaireState(BaseModel):
    questionnaire_id: str
    policy_version: str
    answer_hash: str
    reviewed_hash: str | None
    reviewed_policy_version: str | None
    review_status: Literal["pending", "approved", "rejected"]
    evidence_refs: list[str]
    version: int


def authorize_send(candidate: dict) -> None:
    s = QuestionnaireState.model_validate(candidate)
    approved = (s.answer_hash, s.policy_version) == (
        s.reviewed_hash, s.reviewed_policy_version
    )
    if s.review_status != "approved" or not approved:
        raise IllegalTransition("current answers were not approved")
```

The schema defines the record's shape. Runtime validation rejects malformed model output, while the transition guard checks whether a well-formed record may move from review to send. Database persistence keeps the accepted record beyond the model call for later inspection.

For Q-47, a version 8 revision can no longer inherit version 7 approval. The send attempt fails at the boundary and leaves a rejection to investigate. Evidence review must still establish truth, but silent ambiguity has become a testable engineering failure.

## The old discipline inside the new stack

Risbrandt's longer list matters because typed state gives persistence, retries, observability, and tests a common object to inspect. I think types are the load-bearing item: every other control needs to know which state the system accepted.

Software has used this discipline for decades. Robin Milner's [1978 paper on type polymorphism](https://doi.org/10.1016/0022-0000%2878%2990014-4) helped establish a type-system tradition still used in programming languages. Static checking catches mismatches before code runs; runtime validation checks data arriving during execution. Model output needs that second boundary.

The same craft move helped Ruby on Rails, a web framework, become practical infrastructure for teams. [Rails 1.0 arrived in December 2005](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh), and its Active Record migrations made database-schema changes reviewable code that teams could apply consistently across environments. Rails made stored structure explicit. Typed state does the same for facts and permissions carried through an agent workflow.

There is an important limit. An expected-version check, called optimistic concurrency, can reject a stale write but cannot reconstruct earlier state. That requires events that are never overwritten or saved immutable snapshots. External effects also need controls: an idempotency key lets a supporting endpoint recognize a retry and avoid repeating the operation, while an irreversible send may require a correction. Typed state supplies the contract; recovery still has to be designed.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state applies an old software discipline to uncertain model output, but it does not create history or reversibility by itself. Teams still need retained events or snapshots, stale-write protection, and explicit controls for external effects.</p></div>

## Alignment claims stop before the production action

Anthropic's pre-deployment audit is useful evidence about Opus 5 under evaluation. It cannot tell an incident reviewer whether Q-47 sent revision 6 using approval tied to revision 5. I call this the authority-record gap: evaluation describes behavior under test, while a production record shows what authorized one consequential action. Substituting the first for the second is alignment theater.

Closing that gap belongs in an AI Operating Model, meaning the owners, decisions, evidence, and controls around AI work. Engineering owns the schema; the security owner decides what makes `send` legal. Without that agreement, verification debt accumulates because every incident requires reconstructing authority from logs and chat history.

For the specified high-risk uses it covers, the [European Union's 2024 AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj) requires automatic event logging under Article 12 and deployer retention of controlled logs under Article 26(6); the main Annex III high-risk rules applied from August 2, 2026. The law does not prescribe typed state, and a security questionnaire is not automatically high risk. A retained acceptance or rejection still gives compliance teams evidence instead of reconstruction.

When the same weak boundary reaches finance, human resources, or access control, one corrupted field can create audit hours or an unexplained permission. Inspectable state becomes an operating requirement.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A model evaluation and an action-authority record answer different questions. Production accountability starts when owners can retrieve the exact state, evidence, and approval that permitted a consequential transition.</p></div>

## What to change on Monday

Pick one agent that can publish, send, approve, or update an authoritative business system. In a 30-minute review, ask the engineering owner and the business or risk owner to name the accepted fields, attached evidence, retention rule, and one forbidden transition. Store that contract beside the agent code so changes go through normal review.

Give two engineers roughly two weeks to prove one consequential boundary. Validate output before storage, reject stale writes, retain accepted and rejected events, and test a crash between committing intent and acting. Where the destination supports duplicate-safe requests, reuse one idempotency key; otherwise define the correction path before launch.

During an incident review, the team should be able to show which policy version informed Q-47, which answer hash a person approved, which guard authorized the send, and every rejected attempt. If that still requires transcript archaeology, the verification debt remains.

I don't know which agent framework will make this pattern standard. I think the durable move is smaller: make accepted state a reviewed engineering artifact, then let models remain uncertain inside that boundary. My take is that craft discipline is back because production agents have made its absence impossible to ignore.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Start with one consequential transition, two accountable owners, and a contract stored with the code. The work is successful when incident review can rely on retained state and transition evidence instead of reconstructing authority from a transcript.</p></div>
