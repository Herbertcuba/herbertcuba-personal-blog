On July 21, 2026, engineer [Jonas Risbrandt described the evolution of agentic coding](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz). Agentic coding lets an AI model plan work and call tools rather than only answer a question.

> “Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing.”

Risbrandt then asked, “Haven't we just invented... a programming language?” I think he named the larger pattern correctly, but typed state adds something specific: an authority record showing which version, evidence, approval, and rule allowed model output to affect a live system.

Three days later, Anthropic, the company behind the Claude family of AI models, [announced Claude Opus 5](https://www.anthropic.com/news/claude-opus-5) for long-running work. Anthropic said a pre-deployment automated behavioral audit found it to be “our most aligned model to date.” The related [Hacker News discussion](https://news.ycombinator.com/item?id=49038433), on a technology forum, drew over 1,700 points. I think the timing exposes the next problem: a model test cannot prove which production facts authorized a later action.

## Four waves, one publication card

Follow one article card through research, drafting, factual review, human approval, and publication. Its Hacker News citation must remain “over 1,700 points.” This task's history contained an exact score, its correction, and the stale figure's later return. Only the corrected, approved revision may publish.

### Prompt

A prompt gives a model its work and constraints in natural-language prose.

```text
Research the card, write the article, verify every source,
and publish only the approved revision.
Use “over 1,700 points,” never an exact score.
```

The instruction sounds clear, but “approved revision” names no machine-checkable object. As recovery rules accumulate, the prompt starts serving as data contract, workflow, and runbook. It is a prompt wearing a toolbelt it cannot inventory.

### Loop

A loop lets the model act, inspect a result, and repeat until a stopping condition is met.

```python
while card.status not in {"done", "escalated"}:
    action = model.choose(message_history)
    result = tools.run(action)
    message_history.append(result)
```

The message history becomes informal state, meaning the facts carried between steps. The stale score and its correction remain equally plausible, so a later pass can retrieve the wrong one without breaking the loop. I think corruption can resemble progress until an external tool acts.

### Graph

A graph connects named workflow steps, called nodes, with directed edges that decide where work goes next.

```text
research → draft → fact_check → human_approval → publish
             ↑          |
             └─ kickback┘
```

A failed fact check now has a route back to drafting. Yet the graph cannot prove whether the next node received the corrected revision, and each node can hide another prompt or loop. The roads are visible, while their cargo remains informal.

### Typed state

Typed state declares allowed fields and values. Persistence stores the record beyond one model call. This illustrative boundary uses [Pydantic, a Python library for runtime data validation](https://docs.pydantic.dev/latest/concepts/models/), inside a locked database transaction:

```python
class PublishState(BaseModel):
    model_config = ConfigDict(strict=True)
    card_id: str
    version: int
    status: Literal["fact_check", "human_approval", "publish"]
    revision_id: str
    content_hash: str
    fact_report_id: str | None
    sources_verified: bool
    approved_revision_id: str | None
    approved_content_hash: str | None
    approved_by: str | None

with transaction():
    current = PublishState.model_validate(lock_card(request.card_id))
    require(request.expected_version == current.version)
    require(current.status == "human_approval")
    require(current.sources_verified and current.fact_report_id is not None)
    require(current.revision_id == current.approved_revision_id)
    require(current.content_hash == current.approved_content_hash)
    write_publish_intent_once(request.idempotency_key, current)
    advance_if_version(current.card_id, current.version, "publish")
```

The schema declares expected fields, while runtime validation rejects malformed values. A content hash fingerprints the draft. The expected-version check rejects a request that no longer matches the locked record. The `require` statements are transition guards, which block a well-formed record from taking an unauthorized route. These states and allowed moves form a state machine.

`write_publish_intent_once` creates an outbox record, a durable instruction delivered after commit. Its idempotency key names one intent so a retry does not create another. These controls do not prove the article true or make the destination safe against duplicates. They bind publication to one accepted revision, fact report, and approval. Invoice and access-provisioning agents need the same link among value, evidence, approver, and version.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts express intent, loops repeat work, and graphs expose routes. Typed, persisted state adds a checked record that can reject stale, malformed, duplicate, or unauthorized publication attempts.</p></div>

## Why typed state changes the boundary

Typed state does not replace graphs. [LangGraph, a graph-based agent framework published by AI tooling company LangChain](https://docs.langchain.com/oss/python/langgraph/graph-api), already supports shared state schemas. In March 2025, [workflow infrastructure company Inngest described its TypeScript AgentKit as using a “fully typed state machine” for routing](https://news.ycombinator.com/item?id=43426164). These examples show direction, not broad adoption.

Strong typing has no universal definition. Here, typed state means a declared schema enforced at runtime and at the database transition boundary; Python annotations alone do not police inputs. Types cannot verify a source or make a model correct. They can turn a missing report, mismatched revision, or illegal transition into a loud rejection.

I think that gives typed state more weight than another framework layer. Retries need a known starting state, observability needs stable fields, and persistence needs storage rules. The contract makes each control answerable against named facts.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The fourth wave exposes the state that earlier waves carried informally. Its bounded engineering win is that software can refuse an action whose evidence, version, or approval does not match.</p></div>

## What implicit state costs

An execution trace records which steps ran. It may show `human_approval` before `publish` while omitting which revision was approved. An incident review must then reconstruct authority from prompts, messages, and tool traces created for execution rather than proof.

I call that gap verification debt: the distance between what a workflow assumes and what its records can prove. Here, it appears as a stale claim. In a 5,000-employee company, the same failure in invoice approval or access provisioning can mean audit hours, a delayed close, or another pilot leadership will not scale.

This is where model alignment and system accountability separate. Anthropic's claim concerned behavior measured before deployment, not the evidence behind a later live request. My take is that alignment theater begins when model evaluation is presented as proof that a production action had authority.

An AI Operating Model is the ownership, evidence, decisions, and controls around an AI system. It is legible when business defines a consequential transition, engineering enforces it, and reviewers inspect accepted and rejected records. The [European Union's 2024 AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj) points this way without prescribing typed state. For high-risk systems in scope, Article 12 requires automatic event recording, while Article 26(6) requires deployers to retain generated logs. Many Annex III obligations began applying on August 2, 2026. A publishing workflow is not automatically high risk, but a version-linked rejection is stronger audit evidence than a transcript containing the right sentence somewhere.

Typed state also makes reversibility precise: returning to an accepted version or running a named correction after an external effect. Versioned records support replay, and idempotency can stop a duplicate intent, but neither can unsend an email or reverse a payment. Such effects need explicit compensation paths. Shared memory across agents also needs an owner, a version, and allowed transitions, or verification debt returns at a larger scale.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Activity logs show what ran, while authority records show which facts and approval allowed it to run. Without that link, verification debt grows across incidents, audits, and attempts to move pilots into production.</p></div>

## Put the contract into review

Type discipline is old. Computer scientist Robin Milner's [1978 paper “A theory of type polymorphism in programming”](https://doi.org/10.1016/0022-0000%2878%2990014-4) presented a formal type discipline and a compile-time checking algorithm for polymorphic procedures. The enduring craft move is to declare valid forms and reject invalid combinations before action.

Web applications predated [Ruby on Rails 1.0, a web framework released in December 2005](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh). Rails made database state easier to operate through [migrations, reproducible changes that treat each schema change as a new version](https://guides.rubyonrails.org/active_record_migrations.html). I think typed state brings the same discipline to facts carried toward a consequential action: structural assumptions become explicit, versioned, and reviewable.

On Monday, ask the enterprise architect and system owner to convene a 30-minute review with the engineering lead. Choose one write-capable agent and one consequential transition. Name its version, evidence, approving role, retention rule, and one forbidden move. The business owner accepts the rule; engineering owns enforcement.

Time-box that boundary to two weeks instead of promising a platform rewrite. Persist acceptance and rejection, then test it before touching the wider architecture:

```text
stale approved revision → rejection, no publish intent
current approved revision → one publish intent
retry with the same key → existing intent, no second record
```

Run an incident review from persisted state alone. If the team cannot explain what was accepted, which guard decided, and what followed, it has found verification debt. This is how a promising pilot earns production ownership instead of remaining a demonstration.

I don't know which agent framework will dominate. Risbrandt's sharper line was, “We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt.” I think the state contract will endure because it can survive changes in models and orchestration. The next agent wave begins when a team can show, in software, why an uncertain model was allowed to act.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Review one consequential transition as a software contract, test its refusal paths, and demand an incident explanation from persisted state. Craft discipline is back when authority becomes executable.</p></div>
