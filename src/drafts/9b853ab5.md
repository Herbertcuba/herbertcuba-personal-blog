In July 2026, engineer [Jonas Risbrandt](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz) described four stages of agentic coding, where a language model selects tools across several steps:

> First, we talked about prompting.
>
> Then we realized one prompt was not enough, so we added loops.
>
> Then loops were not enough, so we introduced graphs.
>
> Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing.

He asked, “Haven't we just invented... a programming language?” Then he summarized the arc: “We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt.”

One day earlier, [Anthropic](https://www.anthropic.com/news/claude-opus-5), the company behind Claude, had released Claude Opus 5 for work including long-running agents. Anthropic said an automated behavioral audit during pre-deployment testing found it to be “our most aligned model to date.” The release drew over 1,700 upvotes on [Hacker News](https://news.ycombinator.com/item?id=49038433), a technical forum. That attention is not independent validation.

I think the two events point to the same engineering boundary. Better model behavior helps, but it cannot tell us which facts a production agent accepted, which approval still applies, or whether a failed tool call already changed the outside world. Typed state forces those answers out of the conversation and into software that can be inspected.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The model can improve while the surrounding agent remains impossible to audit. Typed state matters because it records what the system accepts before uncertain language becomes an authorized action.</p></div>

## Watch one claim move through the stack

Take a publishing pipeline that researches, drafts, checks, approves, and publishes an article. Its brief contains an exact Hacker News score that will age. The durable wording is “over 1,700 upvotes.” Follow that fact through each architecture.

### Prompt

A prompt is the instruction given to the model. In the first version, the whole workflow sits in prose:

```text
Research card-42, write the article, check every source,
request human approval, and publish the approved draft.
Use time-stable wording for changing engagement counts.
```

Every incident adds another instruction until the prompt must explain tools, recovery, approval, source policy, and exceptions. It now behaves like a program without fixed fields or legal transitions. The prompt is wearing a toolbelt, yet no database can show which rule governed a run.

### Loop

A loop lets the model choose and run another action until the task appears complete:

```python
done = False
while not done:
    action = model.next_action(messages)
    result = run_tool(action)
    messages.append(result)
    done = model.says_done(messages)
```

Messages now carry the state, meaning the information passed between steps. Fact checking may replace the old exact score with “over 1,700 upvotes,” while a later revision reads the earlier brief and restores stale wording. Both versions remain in the history, so the loop can finish after the accepted fact has moved backwards.

### Graph

A graph makes the allowed routes visible as nodes connected by directed edges:

```text
research -> draft -> fact_check -> human_approval -> publish
              ^           |
              +-- revise -+
```

The team can now see where a rejection returns. [LangGraph](https://docs.langchain.com/oss/python/langgraph/graph-api), LangChain's framework for graph-based agents, already supports shared state schemas, so graphs are not inherently untyped. Yet teams can leave schemas optional while nodes contain prompts, loops, and free-form history. The route is clear; the fact crossing an edge may remain ambiguous.

### Typed state

Typed state is a named record whose fields and permitted value shapes are checked before the record is accepted. Persistence saves that record outside the conversation, and a transition guard decides whether the next move is legal.

```python
class PublishState(TypedDict):
    card_id: str
    status: Literal["draft", "fact_check", "human_approval", "publish", "done"]
    hn_claim: str
    draft_revision: int
    checked_revision: int | None
    approved_revision: int | None
    publish_receipt: str | None


def ready_to_publish(state: PublishState) -> bool:
    revision = state["draft_revision"]
    return (
        state["hn_claim"] == "over 1,700 upvotes"
        and state["checked_revision"] == revision
        and state["approved_revision"] == revision
        and state["publish_receipt"] is None
    )
```

A type checker or runtime validator rejects malformed data. The guard blocks a checked claim attached to the wrong revision, while persistence records the rejection. A schema cannot prove the sentence true, but it can stop an unchecked or stale version from receiving publication authority.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A prompt describes the job, a loop repeats decisions, and a graph exposes the route. Typed state adds the missing contract: which fact was accepted, for which revision, under which approval, and whether the external action already occurred.</p></div>

## The old craft underneath the new stack

Typed state gives a new label to an old discipline. Computer scientist Robin Milner's [1978 work on type polymorphism](https://doi.org/10.1016/0022-0000(78)90014-4) helped establish how software could infer and enforce the kinds of values a program may handle. Agent systems often combine static types with validation when data is written. Both make invalid states harder to represent and easier to reject.

[Inngest AgentKit](https://github.com/inngest/agent-kit), a March 2025 TypeScript toolkit from workflow company Inngest, described a “fully typed state machine”: named states with permitted moves. LangGraph documents shared state schemas, while projects in Python, Rust, and Zig use related designs. This shows a direction of travel, not broad adoption.

My take is that typed state is more consequential than another retry setting because it makes the other controls intelligible. A retry launched from unknown state can repeat damage. Observability that stores only free-form messages records activity without establishing which evidence or approval had authority.

[Ruby on Rails 1.0](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh), the convention-driven web framework released in December 2005, offers a useful precedent. Its migrations made changes to database structure versioned and repeatable, so teams could move application state between known forms. Rails made web state legible. Typed state makes agent state legible.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Agent engineering is rediscovering a durable software discipline: put changing state under a versioned contract, then let retries, logs, and recovery operate against facts the system can name.</p></div>

## Production evidence starts after the model audit

Anthropic's Opus 5 claim is carefully scoped to pre-deployment behavioral testing. That evidence may say something useful about the model's tendency to follow policy under evaluation. It cannot answer which draft revision a production agent published, what source supported a claim, or whether approval had expired before a retry.

I think alignment theater begins when an organization treats a model audit as evidence for a production transaction. A legible AI Operating Model, meaning the ownership and rules used to deploy and govern AI, needs inspectable agent state. Otherwise a policy can name an approver while the running system cannot show which approval unlocked the action.

The regulatory direction reinforces this need. The [European Union's AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj), adopted in 2024, requires high-risk AI systems to support automatic event logging under Article 12, while Article 26 requires deployers to retain logs under their control. The main obligations for high-risk uses listed in Annex III began applying on 2 August 2026. A publishing pipeline is not automatically a high-risk system, and typed state does not create compliance by itself. When an agent enters finance, employment, or another high-risk domain, however, structured state makes retained logs far more useful than reconstructed chat history.

At a company with 5,000 employees, one unauditable agent touching invoice approval or access provisioning can turn a corrupted field into hours of reconstruction and a delayed close. I don't know which agent framework will dominate. I think the stronger bet is that production teams will demand evidence tied to state transitions, especially as several agents begin sharing memory that no single trace can explain.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Model evaluations describe tendencies before deployment. Production accountability requires a retained record linking evidence, approval, revision, and action at the exact transition where an agent changes the outside world.</p></div>

## Put one consequential transition under contract

Start Monday with the boundary that can create harm: publishing a claim, releasing a payment, or provisioning access. Put the enterprise architect, system owner, and engineering lead in a 30-minute review. Ask which record is authoritative, what evidence applies to its current revision, who may approve it, and which next move must be impossible.

Then set a narrow two-engineer, two-week pilot around that transition. Store the schema in the system of record, validate every write, and add a guard before the external action. Give each outbound request an idempotency key, a unique token that makes a retry return the original result instead of creating a duplicate. Test a stale revision, a crash after the external call, and a revoked approval.

I think this is the practical way to pay down verification debt, the gap between what a workflow claims to have checked and what its stored record can prove. Reversibility also stops depending on a sentence in the prompt. When accepted states and transitions are versioned, the team can identify the last valid state and define how to restore it.

Risbrandt's “reintroducing the code around the prompt” describes the work required to use uncertain model judgment inside accountable software. The model may propose what happens next; authority begins at the typed, persisted boundary.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Begin with one external effect rather than a platform rewrite. Put it under a typed state contract, assign its owner, test its illegal transitions, and make every retry explainable. The next agent wave becomes real where uncertain output meets checked authority.</p></div>
