The code is coming back around the prompt, and that may be the healthiest development in agent engineering this year. On July 21, 2026, [Jonas Risbrandt wrote on LinkedIn](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz):

> “First, we talked about prompting. Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing.”

His punchline was sharper: “Haven't we just invented... a programming language?” He called agent frameworks languages for coordinating “unreliable semantic functions,” meaning model calls that can be useful without being predictably correct.

On July 24, 2026, three days later, the model company [Anthropic announced Claude Opus 5](https://www.anthropic.com/news/claude-opus-5) for long-running, multi-step agentic coding. Anthropic said a pre-deployment behavioral audit found it to be “our most aligned model to date.” The launch drew [over 1,700 upvotes on Hacker News](https://news.ycombinator.com/item?id=49038433), a technical forum, yet that attention cannot show what a production agent accepted before changing an external system.

I think that question defines the next wave because each prior architecture solved coordination while pushing unresolved risk into less visible state. Better model behavior matters, while reliable operations still require a checked record of what the system knows, who approved it, and which transition is allowed.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Model evaluations describe behavior under test. Typed production state records what an agent accepted and had authority to do.</p></div>

## One publication, four architectures

Take one article moving through research, drafting, fact-checking, approval, and publication. Its brief contains a stale exact Hacker News score, while the safe wording is “over 1,700 upvotes.” Following that fact shows what each architecture leaves unresolved.

### Prompt: instructions without an accepted record

```text
Research the article, draft it, verify every source,
request approval, and publish.
Use “over 1,700 upvotes” for changing Hacker News scores.
```

A prompt tells the model what outcome to pursue. Add search, file, and publishing tools, and it soon carries rules for retries, approvals, and exceptions. The prompt becomes a toolbelt with no clear place to record which version of a claim passed verification.

### Loop: progress inside a transcript

```python
while card.status in ACTIVE_STATES:
    action = model.choose(history)
    result = run_tool(action)
    history.append(result)
```

A loop repeats model decisions, tool actions, and observations until a stopping condition is reached. It can research and revise, yet both versions of the score remain in `history`, where a later pass may select the stale one. The transcript records two values without establishing which became authoritative.

### Graph: routes without enforced contents

```text
research → draft → fact_check → approval → publish
             ↑          │
             └── revise ┘
```

A graph connects work steps as nodes with directed edges, making control flow visible. It shows a failed fact-check returning to drafting, although each node may still contain a prompt and loop. [LangGraph](https://docs.langchain.com/oss/python/langgraph/graph-api), LangChain's graph-based agent framework, supports a shared state schema, so graphs are not inherently untyped. Trouble remains when nodes can write free-form or unvalidated values: the route is visible, but accepted contents are not.

### Typed state: a checked write and a guarded transition

In Python, `TypedDict` helps a static checker find code mismatches but does not validate model output at runtime. A library such as Pydantic must inspect every write, while storage independently enforces the transition.

```python
from datetime import datetime
from typing import Literal

from pydantic import BaseModel, HttpUrl

class Claim(BaseModel):
    wording: str
    source_url: HttpUrl
    checked_at: datetime
    verified_by: str
    verdict: Literal["verified", "rejected"]

class CardState(BaseModel):
    card_id: str
    status: Literal["draft", "fact_check", "approval", "publish"]
    hn_claim: Claim
    version: int

def move_to_publish(raw: dict, expected_version: int):
    state = CardState.model_validate(raw)  # runtime validation
    return store.commit_transition(        # one database transaction
        candidate=state,
        expected_version=expected_version,
        required_status="approval",
        next_status="publish",
        required_claim_verdict="verified",
    )
```

Here, typed state is a named record with allowed fields and values, checked at the write boundary and stored beyond one model call. The validator rejects malformed records. The illustrative `commit_transition` guard checks the persisted version, current status, and verified verdict in one transaction, preventing an older draft from overwriting a newer checked record. These controls do not prove that “over 1,700” is true; fact-checking must still attach sound evidence. They prevent an unchecked or stale value from becoming accepted production state.

## The old discipline inside the new stack

The first three waves improved how an agent works. Typed state improves how the system refuses work. I think that matters because a probabilistic model can propose a change while deterministic software rejects its shape, version, evidence, or destination.

The discipline predates agent frameworks by decades. In [Robin Milner's 1978 paper on type polymorphism](https://doi.org/10.1016/0022-0000%2878%2990014-4), the computer scientist helped establish the type discipline behind ML, a family of statically typed programming languages. Agent software adds a runtime problem: model-produced data arrives after deployment, so static checks must be paired with write-time validation.

Independent projects point this way without proving broad adoption. [Inngest AgentKit](https://github.com/inngest/agent-kit), introduced in March 2025 as a TypeScript multi-agent library, describes a fully typed state machine for routing. LangGraph documents shared schemas inside graph workflows. My take is that different builders are putting deterministic contracts around uncertain calls before any framework has won.

The comparison with Ruby on Rails is narrow but useful. [Rails 1.0 arrived in December 2005](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh), and Active Record migrations gave web teams a standard way to version database-schema changes alongside code. Migrations did not manage complete application state; they made structural change explicit and reviewable. A versioned agent-state contract applies that craft move to accepted records and allowed transitions.

Reversibility also becomes concrete because a team can inspect an earlier version and reject a stale write. External effects still need a compensating action or duplicate-safe retry mechanism, but recovery no longer depends on a model reconstructing its past from a transcript.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Static checks protect agent code, runtime validators check model-produced records, and persisted guards make state changes reviewable.</p></div>

## Auditability begins after the model test

A behavioral evaluation asks how a model responds under test conditions. A production audit asks which data the running system accepted, which rule authorized its action, and what effect followed. Conflating them creates alignment theater, where confidence in model behavior substitutes for deployment evidence.

An execution trace helps, but tool calls are not accepted state. In the publishing example, the trace may show two fact-checks; retained state must show which wording passed, its source, the check time, and the version covered by approval. I think a legible AI Operating Model, the assignment of owners, decisions, evidence, and controls around AI work, depends on that distinction.

Regulation is moving in the same direction. The [European Union AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj), adopted in 2024, requires specified high-risk systems under Article 12 to support automatic event logging; Article 26(6) requires deployers to retain logs under their control. The main Annex III obligations began applying on August 2, 2026. Annex III covers specific uses, including certain employment decisions and creditworthiness assessments, rather than every publishing, finance, or human-resources agent.

The law does not prescribe this architecture, and typed state alone cannot satisfy every duty. It does show the direction: consequential systems need retained records of decisions and authority. I don't know which framework will dominate, but systems that cannot answer those questions accumulate verification debt, the gap between capability and provable control. Versioned accepted state pays it down by retaining the answer with the action.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Model testing and production accountability answer different questions. Accepted state connects actions to evidence, approval, and authority.</p></div>

## Give Monday to the boundary

Start with one consequential transition. For the publishing pipeline, use approval to publication. Ask the engineering lead and system owner to define four things together:

1. the smallest record that contains the accepted claim, its evidence, approval scope, and version;
2. the runtime validator that checks every model-produced write;
3. the storage-level guard that names an illegal transition; and
4. the retry rule for the external effect, including an [idempotency key](https://docs.stripe.com/api/idempotent_requests), a unique request value that a correctly implemented endpoint can use to recognize a retry and avoid duplicating the operation.

Test the boundary with the known failure. Reintroduce the stale score after fact-checking, attempt publication with an unverified claim, and repeat the request after a simulated timeout. The system should reject the stale write, block publication, and recognize the retry without another model judgment.

One-shot classification may not need durable state. A long-running agent that revises, seeks approval, and changes an external system does. I think consequence is the threshold: if an effect may need explanation or reversal, accepted state belongs in a contract owned like any production interface.

Risbrandt ended with the cycle in one sentence: “We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt.” Reliable agents will still contain prompts. They will stop letting prompts decide what the system remembers.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>For one consequential transition, define accepted state, validate every write, enforce the storage guard, and test stale data plus retries.</p></div>
