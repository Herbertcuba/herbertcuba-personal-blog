A Swedish engineer named Jonas Risbrandt compressed four years of agentic coding into three sentences on LinkedIn. One prompt was not enough, so we added loops. Loops were not enough, so we introduced graphs. Now we are adding typed state.

Each wave looked like a feature. Each one was actually a fault line.

He is right. I think the fault lines are the part worth reading twice.

## The four waves

I tried to build an invoice-processing agent last year. It failed in ways I did not expect, and the failure taught me what these waves actually are.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts, loops, graphs, typed state. Each wave solved a real problem and created a new one. The fourth wave is the first one that exposes the failure below it instead of hiding it.</p></div>

**Wave one: prompts.** You write a long instruction. You give the model tools. You hope it reads the invoice, finds the amount, checks the vendor, and posts the entry. The prompt grows. It becomes a system prompt wearing a toolbelt. You are no longer programming. You are negotiating with a very confident intern who has read every invoice ever written but has never worked your ledger.

**Wave two: loops.** You add a loop so the agent can retry. Read, extract, validate, retry if wrong. This is ReAct, a pattern where the model reasons about what to do, acts, observes the result, and reasons again. It works better. It also hides state corruption. The loop carries forward half-remembered context from earlier iterations. By iteration seven the agent thinks the vendor is a different company. You cannot see where the drift started.

**Wave three: graphs.** You replace the loop with a graph. LangGraph is the common framework here. You draw nodes and edges in a StateGraph, the class LangGraph gives you for wiring steps together: this node reads the PDF, that node extracts fields, this one validates, that one posts. It looks like architecture. It is still hiding state. The graph passes a black-box dictionary between nodes. Any node can write anything. The graph knows the path. It does not know the data.

**Wave four: typed state.** You define the shape of what the agent carries. In LangGraph you do this with a TypedDict, a Python class where every field has a declared type. You hand that TypedDict to the same StateGraph, and the graph now knows the data as well as the path.

```python
class InvoiceState(TypedDict):
    vendor_name: str
    amount: float
    currency: Literal["SEK", "EUR", "USD"]
    posted: bool
```

Now the state has a contract. If a node writes the wrong shape, the system fails fast, in the open, before the error reaches the ledger. A wrong currency becomes a crash at 09:14 on a Tuesday. That is a much better problem than a mystery at month-end close.

## Why typed state is the engineering win

I think typed state is the first wave that behaves like engineering instead of improvisation.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state makes the agent's memory inspectable and auditable. It turns vibe into structure. It is the same craft move that made Rails web apps possible in 2005.</p></div>

In 2005, Rails did something similar for web apps. Before Rails, every PHP project was a bespoke mess of SQL concatenated into strings. Rails said: here is a convention, here is a schema, here is a migration. The database became a typed, versioned contract. You could diff it. You could roll it back. You could audit it. Web apps stopped being crafts and started being engineering.

Typed state does the same for agents. The agent's memory stops being a vibe in a prompt and becomes a state machine. Reversibility stops being a hope and becomes a property of the system. You can diff the state before and after a node runs. You can replay it. You can point to a field and say: this is where the corruption started.

This is what pays down verification debt. Every unchecked agent action is a liability you will audit later. Typed state is the ledger.

## What breaks without it

I don't know how many production agent systems are running right now with unauditable state. I suspect the number is higher than most CTOs admit.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Without typed state, agent systems become demos that survive on habits nobody wrote down. Model-layer alignment and system-layer accountability are different problems. The second one is yours.</p></div>

Anthropic shipped Opus 5 with a claim of "most aligned to date." The [Hacker News thread](https://news.ycombinator.com/item?id=49038433) passed over 1,700 upvotes. The alignment discussion is real and necessary. It is also a distraction from a harder problem.

A model can be perfectly aligned and still corrupt your ledger because the system around it has no memory contract. Alignment theater is when you tune the model's values while the agent's state drifts into shapes nobody designed. The model says the right words. The system does the wrong thing.

Regulators are moving in the same direction. The EU AI Act's record-keeping rules for high-risk systems assume you can reconstruct what an automated system did. An agent with untyped state cannot show its work.

My take: model-layer alignment is the vendor's problem. System-layer accountability is yours. Typed state is how you own it.

## The Monday morning test

I think most teams can test this in two weeks with two engineers.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Pick one agent. Define its state as a TypedDict. Diff what the agent carries against what you think it carries. You will find two or three times the fields. That gap is your verification debt.</p></div>

Pick one agent. One. Write down what you think it carries. Then instrument it and write down what it actually carries. In my experience the agent carries two or three times the fields you designed. Some of those fields are stale. Some are wrong. Some are written by nodes you forgot existed.

That gap is your verification debt made visible. You do not need a platform rewrite. You need one schema with a named owner, plus a review process that treats state changes like database migrations.

One agent. One schema. Two engineers. Two weeks. That is the test.

## Craft discipline is back

The oldest craft discipline in software is strong typing. We are rediscovering it in agent systems because the cost of skipping it is finally visible.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state is the return of the oldest discipline we have in software. Make the contract explicit, so the failure is fast and the next engineer can read the system at 3 AM.</p></div>

In *Blade Runner*, the replicants are dangerous because they have memories they did not earn and cannot account for. Agent systems without typed state are similar. They carry context they cannot explain. They make decisions from fields nobody validated. They look competent until you ask them to prove it.

Typed state is the baseline test. It asks: do you know what you are? Can you show me?

The next wave of agent systems will be built by teams who answer yes. The rest will ship impressive systems held together by habits nobody could defend in a review. I think we are done with those.
