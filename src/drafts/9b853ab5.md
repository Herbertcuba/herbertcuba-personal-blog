An engineer named Jonas Risbrandt posted a short history of agentic coding [on LinkedIn](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz) on July 21. I think it captures the last four years. Each wave looked like a feature. Each one was a fault line.

> "First, we talked about prompting. Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing."

Then he asks, "Haven't we just invented... a programming language?"

Three days later, Anthropic shipped [Claude Opus 5](https://www.anthropic.com/news/claude-opus-5) and called it its most aligned model to date after a pre-deployment behavioral audit. [The Hacker News thread](https://news.ycombinator.com/item?id=49038433) drew over 1,700 upvotes.

I call the sequence the State Contract Ladder. Every step strengthens the contract around agent state.

<div class="article-tldr"><span class="article-tldr__label">Article TL;DR</span><p>Prompts gave agents instructions. Loops let them keep working, and graphs made the routes visible. Typed state adds an enforceable record of what the agent knows, which makes bad transitions easier to block and later decisions easier to audit.</p></div>

## Four waves through one article

One pipeline makes the waves concrete. It moves an article through twelve states, including research, draft, fact-check and publish.

### Wave one: the prompt carries the process

A prompt is the instruction sent to a language model. The first version of our pipeline could fit in four lines:

```
You are a content pipeline. Take this article idea.
Research it, write it, review it, fact-check it, publish it.
Ask the human if anything is unclear.
```

This works for a demo. Production incidents soon add rules about stale numbers and research kickbacks. The prompt starts carrying process and memory, yet code cannot stop either one from drifting.

### Wave two: the loop keeps working

ReAct is short for reasoning and acting. It is a common agent pattern where the model chooses an action, calls a tool, reads the result and repeats.

```python
while not done:
    thought = model.reason(context)
    action = model.act(thought)
    result = tools[action.name](action.args)
    context.append(result)  # the chat log holds the state
```

The loop can search and revise, but its state often lives in the whole message history. This article exposed the problem. Fact-check changed a stale exact Hacker News count to "over 1,700." A later revision pulled the old value from context. The log held both values with no verified field to settle the conflict.

### Wave three: the graph exposes the route

LangGraph is a Python framework for agent workflows. Its `StateGraph` class connects nodes, which do the work, with edges that define where execution may go next. `MessagesState` is its built-in container for conversation messages.

```python
graph = StateGraph(MessagesState)
graph.add_node("research", research_node)
graph.add_node("draft", draft_node)
graph.add_node("fact_check", fact_check_node)
graph.add_conditional_edges("fact_check", route_by_verdict)
```

Now a failed fact-check can route the article back to draft. A node may still contain a ReAct loop with a transcript as memory, so the graph cannot tell us which count the writer accepted.

[LangGraph's documentation](https://docs.langchain.com/oss/python/langgraph/graph-api) supports shared state schemas. Enforcement remains a team choice, so loose dictionaries can still cross node boundaries.

### Wave four: the state gets a contract

A `TypedDict` is a normal Python dictionary whose allowed keys and value types are declared in advance. `Literal` limits a field to named values. Type checkers can flag mistakes before runtime.

```python
Status = Literal[
    "ideas_inbox", "approved", "research", "draft",
    "slop_review", "fact_check", "persona_panel", "design",
    "human_approval", "publish", "done", "escalated",
]

class CardState(TypedDict):
    card_id: str
    status: Status
    brief_version: int
    kickback_count: int
    sources_verified: bool
    hn_points: str  # "over 1,700"

def transition(raw: dict, to: Status) -> CardState:
    state = validate_card_state(raw)  # runtime validation
    if to == "publish" and state["sources_verified"] is False:
        raise IllegalTransition("unverified sources")
    return {**state, "status": to}
```

`TypedDict` helps during type checking. Pydantic or another runtime validator must still inspect incoming data. Here, `sources_verified=False` blocks publish even if the model requests it.

The audit question now has a structured answer. At review, the writer had brief version four, unverified sources and one kickback. I think this is the win: a failed transition points to one field instead of a full chat history.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Inside a prompt or chat log, <code>sources_verified</code> can drift between values. A typed state field gives runtime validation one value to check before publish.</p></div>

## Why typed state changes the engineering

Workflow engines such as Temporal and Restate made execution state explicit years ago. LangGraph also made schemas familiar to agent developers.

The newer pressure concerns the agent's working record, including which source it trusted and which error remains open. Workflow state tells the runner where to go. Agent state tells an operator what information caused that route.

This is why typed state deserves attention. Truth still needs verification. Types turn silent corruption into a rejected write or an invalid transition. I think that smaller promise is far more useful.

[Inngest AgentKit](https://news.ycombinator.com/item?id=43426164) described a fully typed state machine in March 2025. [Agd](https://news.ycombinator.com/item?id=47224560) used Zig for addressable agent state in March 2026, while projects in Rust and Python enforced similar contracts. By July 2026, several teams had reached the same design over sixteen months. Broad adoption remains unproven.

Rails made a similar craft move for web apps in 2005. Schema became a contract, and database changes became migrations that teams could review. Typed state applies that discipline to the facts carried by an agent. Strong type discipline has been software craft since the 1970s. Agents give junior engineers a practical reason to learn it.

A legible [AI operating model](/posts/building-the-ai-operating-model/) needs this record. Ownership becomes concrete when an engineer can inspect the state and its last transition.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The useful advance is enforcement around the agent's working record. Types expose bad fields early, while validated transitions show which rule stopped the workflow and why.</p></div>

## What breaks when state stays loose

Anthropic's alignment claim describes a pre-deployment test of the model. A production agent also carries tool results and saved state that were outside that test.

I think the qualifier deserves as much attention as the headline. In *Blade Runner*, the Voight-Kampff test examines a subject in a controlled interview. A behavioral audit has the same boundary: production workflows act on records gathered after the test.

Calling that workflow accountable because the base model passed an audit is alignment theater. Model-level evidence cannot answer a system-level audit question.

[The EU AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj) requires high-risk AI systems to support automatic event logging under Article 12. Article 26(6) requires deployers to retain logs. The main Annex III obligations began applying on August 2, 2026. In a high-risk domain, agent state can become evidence.

Loose state creates ordinary operating pain. One corrupted field in a finance agent can stall month-end close. The model may follow its instruction while acting on a value that should have failed validation.

I don't know whether typed state is the final wave. I expect the next fault line to appear in shared memory across many agents. A team of agents will need common rules for which claims are current and who may replace them.

Each unchecked field adds [verification debt](/posts/2026-03-09-verification-debt-crisis/). Comparing the schema with persisted values makes that debt visible before an audit.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A decision made from corrupted state falls outside model testing. Persisted fields give operators a record they can inspect when a workflow affects money or rights.</p></div>

## What to do on Monday morning

Start with one long-running agent whose mistakes already require human review. A one-shot classifier that labels a ticket and exits may need very little durable state.

Write down every field the agent carries between steps, then put the schema under a named owner's code review.

Guard the highest-cost transition. This pipeline must reject publish when `sources_verified=False`. Run validation when state enters a node and before the expensive action.

Compare persisted state with the schema on every deploy, then review drift once per sprint. The first diff may reveal keys left by deleted prompts or fields missing from the operator's dashboard.

Persist each accepted transition. With an addressable history, [reversibility](/posts/reversibility-is-the-new-correctness/) becomes a property of the state machine. An engineer can return to a valid checkpoint and explain the state change.

I think one existing agent is enough to begin. This can fit inside a sprint by placing a contract around state the system already carries.

Jonas wrote, "We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt." That reintroduced code is where the craft lives. If `sources_verified=False` can still reach `publish`, the agent is carrying a prompt where an engineering contract should be.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Choose one costly transition and define the state required to allow it. Runtime validation should enforce the schema, while an addressable history preserves reversal.</p></div>
