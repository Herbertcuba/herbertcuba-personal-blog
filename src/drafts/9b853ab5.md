A Swedish engineer named Jonas Risbrandt posted on LinkedIn this week that agentic coding has gone through three waves (prompts, then loops, then graphs) and is entering a fourth: typed state. His words: "Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state."

The same week, Anthropic shipped Opus 5 with the claim "most aligned to date" (their own pre-deployment behavioral audit), and the Hacker News thread pulled over 1,700 upvotes and 1,300 comments. I think those two events are the same signal. This field moves fast enough that you can watch it learn in public, and right now it is converging on smaller loops with typed state. Two years ago the argument was about prompt tricks. In the last sixteen months, independent teams in Python, TypeScript, Rust, and Zig have all shipped typed state machines for agents. When people who do not talk to each other arrive at the same architecture, pay attention.

## Wave one: prompts

The prompt was the program.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Wave one put everything in the prompt: instructions, edge cases, tool descriptions. It worked for demos and broke in production, because a prompt cannot be diffed, tested, or audited.</p></div>

Take one example and keep it for the whole article: an invoice agent. It reads PDF invoices, extracts vendor, date, total, and line items, and books them to the general ledger. Every mid-size company has built one by now.

In 2023, you handled the invoice with one big prompt:

```
You are an invoice processor. Read the invoice.
Extract vendor, date, total, and line items.
Call the booking tool for each line item.
If anything is unclear, ask the human.
```

Then tool use arrived, and you bolted on functions. Then production arrived, and every incident added another paragraph to the prompt. One clause for the PDF with two blank pages before the table. One clause for the vendor that writes dates backwards. I have watched a system prompt grow past 4,000 words this way (this is my observation, not a cited study).

The prompt ends up doing the job of a schema, a state machine, and a runbook. It is bad at all three. You cannot diff it or test it. It is a prompt wearing a toolbelt.

## Wave two: loops

One pass was not enough, so the field wrapped the model in a loop.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Wave two was the reason-act loop (ReAct): the model thinks, calls a tool, reads the result, thinks again. The loop let agents iterate, but state lived in the chat history, so corruption was silent and auditing meant archaeology on a log.</p></div>

The pattern is called ReAct (Reason + Act), from a 2022 paper by Yao and colleagues. The model writes a thought, takes an action, reads an observation, and repeats until done. LangChain, AutoGen, CrewAI, and OpenAI's Assistants API all shipped a version of it:

```python
while not done:
    thought = model.reason(context)           # "The total looks wrong"
    action = model.act(thought)               # "Re-read page 2"
    result = tools[action.name](action.args)  # actual re-read
    context.append(result)                    # state = the chat log
```

Look at the last line. The agent's state is the message history, mutated in place. That is the fault line. If the invoice agent misreads a total ($1,000.00 becomes $10,000.00) and books the wrong amount, the error becomes one more message in the history, and the loop keeps going.

The auditor's question has no good answer. "What did the agent believe when it called the booking tool?" You cannot query that. You do archaeology on a chat log. The log also grows every turn, so the model pays to re-read its own history and drifts as early context falls out of the window. The loop solved iteration and hid state corruption.

## Wave three: graphs

Loops were not enough, so the field drew the control flow.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Wave three was the graph: nodes for steps, edges for transitions. Frameworks like LangGraph made the flow visible, but default practice still passed state around as a free-form dict. The graph showed the roads. It did not show the plumbing.</p></div>

LangGraph is the best-known example. You declare steps as nodes and transitions as edges, and you can finally see the control flow on one page:

```python
graph = StateGraph(dict)
graph.add_node("extract", extract_node)
graph.add_node("validate", validate_node)
graph.add_node("book", book_node)
graph.add_edge("extract", "validate")
graph.add_conditional_edges("validate", route_by_confidence)
graph.add_edge("book", END)
```

A StateGraph is exactly what it sounds like: a graph where a state object flows between nodes, and each node returns updates to it. LangGraph's own docs define state as a typed schema, so the capability is there. The failure is in default practice. Most teams write `StateGraph(dict)`: a dictionary with string keys, mutated in place.

That is where the invoice agent breaks in a new way. A node that writes `state["total"] = "1000.00"` (a string, not a number) does not fail. A node that reads `state["toatl"]` after a refactor writes to a key nobody reads. The graph renders green, the ledger is wrong, and the first person to notice works in finance. The graph hid the loops, and the loops were still hiding the state.

## Wave four: typed state

Now the field is making the state itself the contract.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Wave four declares the agent's state as a schema with typed fields and legal transitions, validated at runtime. The wave-two corruption ($1,000.00 becoming $10,000.00) now dies at the boundary, loudly, at the moment it happens.</p></div>

Typed state means the agent's working memory is declared as a structured type, the way a database table is declared. In Python, a TypedDict is a dictionary where the keys and value types are declared up front. Here is the invoice agent, wave four:

```python
class InvoiceState(TypedDict):
    vendor: str | None          # None until extracted
    date: date | None
    total: Decimal | None
    line_items: list[LineItem]
    confidence: float
    status: Literal["received", "extracting", "validating",
                    "booking", "done", "failed"]

def book(state: InvoiceState) -> InvoiceState:
    if state["status"] != "booking":
        raise IllegalTransition(f"cannot book from {state['status']}")
    if state["total"] is None or state["total"] <= 0:
        raise InvalidState("booking requires a positive total")
    ...
```

One honest technical note, because the first HN comment will make it otherwise: a plain TypedDict only checks types when you run a static checker. The runtime enforcement (the `raise` statements above, or Pydantic validation, or LangGraph reducers) is what rejects the bad write when it happens. The schema plus validation at each transition is the wave.

Watch the wave-two failure die. The extraction node reads the total as $10,000.00. The validation transition checks it against the purchase order, finds no PO within an order of magnitude, and refuses the transition. The run fails loudly at 09:14 with the full state attached. Under wave two, that same error sailed through and surfaced at month-end close as a finance-department mystery.

The state is now data you can inspect. Show an auditor the exact object the agent held at every step. Keep the state versioned (a state table per run, an event-sourced log) and reversibility becomes an engineering property: rollback is a query against the log, replay is a rerun from any checkpoint. And because the state is inspectable, the same object answers the record-keeping questions regulators are starting to ask about automated decision systems.

## Why this wave is different

Each prior wave hid the failure mode of the one below it. This one exposes it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state is the same craft move Rails made in 2005: the schema becomes the contract, and every change to it is versioned and reviewable. Strong typing is the oldest discipline we have in software, and the agent field is finally rediscovering it.</p></div>

I think the right historical comparison is Rails in 2005. Rails made web apps operable for small teams, and the mechanism was the schema: one file you could read to understand the shape of the data, with migrations making every change versioned and reviewable. Twenty years later the same move is arriving for agents. The state schema becomes the contract. Transitions become migrations.

The evidence is convergence. Inngest shipped a fully typed state machine for agent routing in March 2025. A Rust team rewrote their framework citing the lack of type safety in Python tools. Someone built MemState, which validates agent memory on write: if the model tries to save a string into an integer field, the transaction fails before corruption happens. These are small projects, but they are independent and they point the same way.

The theory is catching up too. A recent synthesis at pkhamdee.blog (July 2026) connects Karpathy's loop-and-AgentHub work with Anthropic's knowledge-graph cookbook into one claim: the next step is many agents sharing one knowledge graph as memory. Their line is "the agent forgets, the graph does not." A shared graph only works if the claims in it and their provenance are typed. Otherwise the swarm inherits a corrupted transcript and every worker rebuilds context from a poisoned record. Typed state at one agent becomes the shared graph at many. Same discipline, one level up.

This is also the oldest discipline we have. We have had type theory since the 1970s, older than almost everyone arguing about it on HN. I think we are rediscovering it now because agent systems are the first software most of us have built where the state comes from a probabilistic process. You cannot trust that state by construction. You check it at the boundary. In *Blade Runner*, the Voight-Kampff test exists because you cannot tell a replicant from the outside. Typed state is the same move for agents: stop trusting the surface behavior, inspect what the machine is carrying.

I don't know if typed state is the last wave. I doubt it. But it is the first one that exposes the failure below it instead of hiding it, and that is a different kind of progress.

## What breaks without it

The failure mode has a shape, and it compounds.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Without typed state, each wave hides the failure of the one below it, and you end up with an aligned model inside an unauditable system. Alignment at the model layer and accountability at the system layer are different problems.</p></div>

A fair objection: Temporal and the durable-execution people solved half of this years ago. Partially true. Temporal gives you durable workflows: typed inputs, replayable history, checkpoints that survive crashes. The difference is what the state describes. Workflow state says where the process is. Agent state says what the agent believes: the extracted total, the confidence, the plan it committed to. The first is plumbing. The second is cognition, and cognition is what corrupts silently. Scale turns that into an incident. One thousand invoices a month becomes ten thousand, and the mismatch rate turns into a mystery nobody can reconstruct.

This is where the Opus 5 claim fits. "Most aligned to date" is a claim about behavior during pre-deployment evaluations. It says nothing about what your agent did in production at 3 AM on a Tuesday. Auditing the model while the loop's state is illegible is alignment theater. Model-layer alignment and system-layer accountability are different problems, and the second one is yours.

## What to do Monday morning

One agent, one schema, two weeks.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Pick one agent, write down its state schema, diff it against what the agent actually carries, and instrument the most expensive transition. Two engineers, two weeks, no platform rewrite.</p></div>

Pick one agent in your system. The one that scares you the most. Write down its state schema: five to ten lines, one named engineer owns it, changes go through review like any other contract. Then diff the schema against the actual state the agent carries in production. In my experience the agent carries two or three times the fields you declared. Every field the agent tracks that is missing from your schema is a belief you cannot audit. The gap is your verification debt, rendered visible.

Then instrument the most expensive transition. For the invoice agent, that is validate-to-book. Log the state before and after, reject the illegal transitions, and see what breaks. Two engineers, two weeks. When you can checkpoint and replay the runs, the failures start to have a shape you can test against.

I think we will look back on this period the way we look back on web apps before migrations: impressive systems held together by habits nobody could defend in a review. The craft discipline was never new. We are finally applying it to the one place we skipped, and the schema is where the craft lives now.
