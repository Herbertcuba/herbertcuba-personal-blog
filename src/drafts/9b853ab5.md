On July 21, 2026, engineer [Jonas Risbrandt used a LinkedIn post to describe four stages of agentic coding](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz), where language models plan and use software tools:

> “Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing.”

Risbrandt asked, “Haven't we just invented... a programming language?” He called agent frameworks programming languages for orchestrating “unreliable semantic functions”: model steps whose outputs can vary inside otherwise deterministic software.

Three days later, Anthropic, developer of the Claude family of AI models, [announced Claude Opus 5](https://www.anthropic.com/news/claude-opus-5) for long-running agent work. The vendor said a pre-deployment automated behavioral audit found it to be “our most aligned model to date.” On [Hacker News, a technology discussion site](https://news.ycombinator.com/item?id=49038433), the announcement drew over 1,700 points, which signals attention rather than validation.

I think the missing object is production authority. Each wave coordinated more work while hiding the state underneath. Typed state can record the evidence, version, and approval that earned permission for an agent to act.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Long agent runs accumulate assumptions. Typed state records the facts and approval behind one consequential action.</p></div>

## Start with the authority to publish

Use one content-production card as the running example. It moves from research through review to publication, and its current draft must say “over 1,700 points.” Publication is allowed only after fact-checking and approval of the exact revision that remains current.

Typed state is a record with defined fields and allowed values. Persistence keeps it beyond one model call, while a transition guard decides whether it may move to another status. This record includes a version, a revision identifier, a content hash that fingerprints the text, source-verification status, and the approved revision and hash.

The publish request carries an idempotency key, a stable identifier that lets a retry return the existing action. This illustrative pseudocode uses [Pydantic, a Python runtime data-validation library](https://docs.pydantic.dev/latest/concepts/models/):

```python
from typing import Literal
from pydantic import BaseModel, ConfigDict


class StrictModel(BaseModel):
    model_config = ConfigDict(strict=True)


class CardState(StrictModel):
    card_id: str
    version: int
    status: Literal["fact_check", "human_approval", "publish"]
    revision_id: str
    content_hash: str
    approved_revision_id: str | None
    approved_content_hash: str | None
    sources_verified: bool


class PublishRequest(StrictModel):
    card_id: str
    expected_version: int
    revision_id: str
    content_hash: str
    idempotency_key: str


def accept_publish(raw: dict) -> Decision:
    request = PublishRequest.model_validate(raw)

    with db.transaction():
        current = CardState.model_validate(
            db.cards.for_update(request.card_id)
        )
        prior = db.outbox.get(request.idempotency_key)

        if prior:
            same_request = prior.request_hash == stable_hash(request)
            if same_request is False:
                db.events.insert("idempotency_conflict", request, current)
                return Decision.rejected("action key already used")
            return Decision.accepted(prior)

        allowed = all((
            request.expected_version == current.version,
            request.revision_id == current.revision_id,
            request.content_hash == current.content_hash,
            current.revision_id == current.approved_revision_id,
            current.content_hash == current.approved_content_hash,
            current.sources_verified,
            current.status == "human_approval",
        ))

        if allowed is False:
            db.events.insert("publish_rejected", request, current)
            return Decision.rejected("stale or unauthorized state")

        db.outbox.insert_once(
            key=request.idempotency_key,
            request_hash=stable_hash(request),
            payload=request,
        )
        db.cards.advance_if_version(
            request.card_id,
            expected_version=request.expected_version,
            status="publish",
        )
        return Decision.accepted()
```

Strict runtime validation checks declared field types. Inside the transaction, the current row is locked before the expected-version check binds the request to the latest revision, hash, and approval. An outbox stores the pending action with the state change, supporting safe retries and preserving conflicts as events.

Typed state cannot establish that a source is true. It establishes that the verified, approved revision is the one allowed to act. The same boundary can bind an invoice amount to its approver or an access request to its owner.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The authority record binds approval to the current version, rejecting stale requests before publication and making retries safe.</p></div>

## Replay the same card through four waves

That boundary clarifies the earlier architectures. Each wave adds capability to the same card, but only the fourth gives accepted state an enforceable shape.

### Prompt

A prompt is a natural-language instruction that tells a model what result to pursue and which constraints to respect.

```text
Research the article, draft it, verify every source, and publish only
when a person has approved the current revision.
For a changing Hacker News score, write “over 1,700 points.”
```

The demo can work. Then incidents add source checks, approval conditions, and retry rules until the prompt is wearing a toolbelt. It still cannot bind “approved” to the exact bytes that will ship.

### Loop

A loop lets the model choose an action, inspect the result, and repeat until it reaches a stop condition.

```python
while card.status not in {"done", "escalated"}:
    action = model.choose(history)
    result = tools.run(action)
    history.append(result)
```

The history may contain an exact score, its correction, and an approval. It preserves sequence without declaring authority, so a later pass can retrieve the stale score and keep moving. I think corrupted state can resemble successful progress.

### Graph

A graph represents a workflow as named nodes connected by directed edges, making the route after a failed check visible.

```text
research → draft → fact_check → human_approval → publish
             ↑          |
             └─ kickback┘
```

The graph shows where work went, but not which source snapshot reached `fact_check` or whether approval matches the current revision. A node can still hide a prompt, a loop, and ambiguous message history.

[LangGraph, LangChain's graph-orchestration framework](https://docs.langchain.com/oss/python/langgraph/graph-api), supports shared-state schemas. In March 2025, [Inngest's TypeScript agent library AgentKit described “fully typed state machine” routing](https://news.ycombinator.com/item?id=43426164). A state machine limits which stored states may follow which. These are convergence signals, not adoption evidence; applications must still validate and persist the schema, then enforce its transitions.

### Typed state

Typed state turns the same card into an accepted record that software can test at every move:

```text
candidate → validate shape → lock current record → compare authority
                                                   ├─ reject + retain event
                                                   └─ accept + write action
```

I think this wave is different because it can refuse malformed, stale, or unauthorized state. Prompts express intent, loops repeat work, and graphs expose routing; the typed record says which version may act. It cannot make model output correct, but it can turn silent corruption into an inspectable rejection.

Workflow state is the plumbing: status, version, ownership, retries, and allowed moves. Model reasoning is the uncertain work inside it. The first three waves concentrated on reasoning while the plumbing hid in transcripts and node code. Typed state makes that plumbing reviewable.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts carry intent, loops carry history, and graphs carry routes. Typed state records which facts and approval may authorize action.</p></div>

## Model evidence stops at the system boundary

Anthropic's Opus 5 claim comes from a pre-deployment automated audit. It cannot identify the revision or approval behind a later production action because it never sees that live record. I think alignment theater begins when teams present model-level evidence as proof of production authority.

The record belongs inside an AI Operating Model, meaning the owners, evidence, decisions, and controls around an AI system. Engineering owns enforcement; the business or risk owner defines allowed transitions. Without that agreement, verification debt grows through assumptions the team cannot prove.

In an enterprise, the publishing example becomes an invoice approval or account provision. One corrupted field can force staff to reconstruct its source before closing the books. A final row shows what survived; a retained rejection shows which control stopped an invalid move.

Regulation points in the same direction. The [European Union's 2024 AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj) requires high-risk AI systems to support automatic event recording under Article 12 and deployers to retain controlled logs under Article 26(6). The European Commission's [current timeline](https://digital-strategy.ec.europa.eu/en/policies/regulatory-framework-ai) starts strict high-risk obligations on December 2, 2027.

Those provisions neither classify a content pipeline as high risk nor prescribe typed state. They show why retained transitions matter when an agent changes an authoritative system.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Model audits describe test behavior. Production accountability requires the state, owner, and approval behind each live action.</p></div>

## The old craft returns at one boundary

People often call this a return to strong typing, but the term is too loose for the whole production boundary. The exact move is to declare expected fields, validate model output at runtime, and compare each transition with the current persisted record. Static checks can catch mismatches before code runs; live output still needs runtime enforcement.

Computer scientist Robin Milner's [1978 paper on type polymorphism](https://doi.org/10.1016/0022-0000%2878%2990014-4) helped formalize how languages reason about which values belong where. Agent systems are rediscovering the practical habit: make valid structure explicit before uncertain output acts.

[Ruby on Rails 1.0, a web application framework released in December 2005](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh), paired web conventions with [database migrations](https://guides.rubyonrails.org/active_record_migrations.html), versioned steps for changing stored structure. Migrations were not strong typing. Both approaches make structural assumptions explicit and reviewable: Rails for database change, typed state for agent authority.

Typed state also makes reversibility precise. An expected-version check blocks stale moves, while retained events support recovery. An idempotency key prevents duplicate action on retry but cannot unsend an email, so external effects still need a correction path. My take is that reversibility becomes credible when those limits live in the state machine.

On Monday, choose one agent with write access. Ask the enterprise architect, engineering lead, and system owner to name the evidence, owner, retention rule, and one forbidden transition. Here, that is `human_approval` to `publish` after the content hash changes.

Time-box the work to two engineers and two weeks instead of starting a platform rewrite. Store the smallest contract beside the code and test three outcomes:

```text
stale revision      → rejection event, no publish intent
approved revision   → one publish intent
caller-crash retry  → existing intent, no duplicate intent
```

Run an incident review from persisted events alone. Identify what the agent accepted, why the guard decided, and which action followed. If that requires a transcript, the gap between assumptions and proof is verification debt.

A one-shot classifier may need a lighter record because control should follow consequence. I don't know which framework will dominate, but I think state contracts will become standard review artifacts for write-capable agents by the end of 2027. If execution traces alone support incident review and crash recovery, that forecast is wrong.

Risbrandt wrote, “We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt.” That code lets uncertain models earn explainable authority.
