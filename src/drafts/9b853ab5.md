On July 21, 2026, [engineer Jonas Risbrandt summarized the evolution of agentic coding on LinkedIn](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz). Agentic coding means that an AI model can use tools, inspect their results, and keep working toward a goal. He wrote:

> “Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing.”

Risbrandt then asked, “Haven't we just invented... a programming language?” I think the fault line inside that joke is his sharper contribution: prompts, loops, and graphs organize activity without necessarily recording which version, evidence, and approval authorized an action.

Three days later, AI company Anthropic [announced Claude Opus 5](https://www.anthropic.com/news/claude-opus-5), positioning the model for long-running, multi-step work. Anthropic said its pre-deployment behavioral audit found Opus 5 to be “our most aligned model to date.” By early August, its discussion on [Hacker News, a technology forum](https://news.ycombinator.com/item?id=49038433), had more than 1,700 points, which shows attention rather than agreement.

I think the juxtaposition matters because model behavior and production authority sit at different layers. The missing object is an authority record, a machine-checkable account of why an agent could cross a consequential boundary.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Agent frameworks are rebuilding software controls around uncertain model calls. Typed state matters because it can make the facts and approval behind a production action explicit and enforceable.</p></div>

## Four waves around one publish decision

Follow `card-42`. Its draft cites a changing Hacker News score, fact review replaces an old exact figure with “more than 1,700 points,” and a human approves revision eight. Only that verified revision may be published.

### Prompt

A prompt is a natural-language instruction supplied to a model.

```text
Research card-42, draft the article, verify every source,
and publish only the human-approved revision.
Use “more than 1,700 points,” never a drifting exact score.
```

The intent is understandable, but “the human-approved revision” is not a record software can compare. Each incident adds a warning until policy, recovery instructions, and workflow status hang from the same paragraph. This is the prompt wearing a toolbelt.

### Loop

A loop lets the model act, inspect the result, and repeat until it reaches a stopping condition.

```python
while card.status not in {"done", "escalated"}:
    action = model.choose(message_history)
    result = tools.run(action)
    message_history.append(result)
```

The message history becomes informal state, the facts carried between steps. It can retain both the stale score and the correction, allowing a later draft pass to retrieve the wrong one while the loop keeps moving. I think this is where motion starts impersonating control.

### Graph

A graph connects workflow steps, called nodes, with directed edges that choose which step runs next.

```text
research → draft → fact_check → human_approval → publish
             ↑          |
             └─ kickback┘
```

The graph exposes the route back from a failed fact check. It cannot prove that the next draft used the correction, because a node can still contain a loop carrying both versions. The map is clear while the cargo remains uncertain.

[LangGraph, a graph-based agent library maintained by AI tooling company LangChain](https://docs.langchain.com/oss/python/langgraph/graph-api), supports shared state schemas, so graphs need not be untyped. The narrower problem is that visible routing alone does not enforce which persisted record has authority.

### Typed state

Typed state declares the fields and allowed values a workflow may carry. Persistence means storing that record beyond one model call. Here [Pydantic, a Python library for runtime data validation](https://docs.pydantic.dev/latest/concepts/strict_mode/), checks the stored card before the database permits publication:

```python
class PublishState(BaseModel):
    model_config = ConfigDict(strict=True)
    card_id: str
    version: int
    status: Literal["fact_check", "human_approval", "publish"]
    revision_id: str
    content_hash: str
    fact_report_id: str | None
    sources_verified: bool
    approved_revision_id: str | None
    approved_content_hash: str | None

with transaction():
    state = PublishState.model_validate(lock_current(card_id))
    require(request.expected_version == state.version)
    require(state.status == "human_approval")
    require(state.sources_verified and state.fact_report_id)
    require(state.revision_id == state.approved_revision_id)
    require(state.content_hash == state.approved_content_hash)
    write_publish_intent_once(request.idempotency_key, state)
    advance_if_version(state.card_id, state.version, "publish")
```

The schema names expected fields, and runtime validation checks stored values against it. A content hash fingerprints the draft. The expected-version check rejects an older record, while each `require` line is a transition guard that blocks an unauthorized move.

The final calls cover recovery. A publish intent is an outbox record, a durable instruction saved with the state change. Its idempotency key identifies one publish operation, so a retry finds the instruction instead of issuing a duplicate. In an invoice workflow, the same boundary would bind one invoice version to purchase-order evidence and budget-owner approval.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts express intent, loops continue work, and graphs expose routing. Typed, persisted state lets software reject a stale revision, a missing fact report, an invalid approval, or a duplicate publish attempt at the boundary.</p></div>

## The engineering win is bounded refusal

A type can carry a false claim. Its value is bounded refusal: a malformed or unauthorized transition can fail loudly before producing an external effect. I think this is the first wave that exposes the failure below it instead of giving the agent another way to continue.

There is evidence of convergence, though not broad adoption. In March 2025, workflow company Inngest [described its TypeScript AgentKit library](https://news.ycombinator.com/item?id=43426164) as combining conversation history with a “fully typed state machine” for routing. Alongside LangGraph, it points toward a shared boundary: uncertain model output inside explicit accepted state.

That boundary pays down verification debt, the gap between workflow assumptions and demonstrable evidence. It also makes an AI Operating Model concrete: the ownership, decisions, and controls around an AI system. The business owner defines the rule, engineering encodes it, and reviewers inspect accepted and rejected transitions.

Persisted versions give reversibility a hard edge. Internal state can be restored or replayed, while an external effect such as a payment needs a compensating action. Reversibility becomes a tested state-machine property rather than reassuring prompt language.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Types do not prove that model output is true. They reduce verification debt by turning evidence, ownership, and recovery rules into a contract that can reject the wrong transition and explain the accepted one.</p></div>

## What model alignment cannot tell you

Without that contract, the layers nest: the prompt accumulates tools, the loop carries damaged facts, and the graph hides the loop inside a tidy node. An execution trace may show `human_approval` before `publish` while omitting the revision and evidence the human approved. Activity is visible while authority remains ambiguous.

My take is that alignment theater begins when a model evaluation is treated as proof of production accountability. Anthropic's pre-deployment audit is useful within its scope. It cannot identify the fact report behind a live publication, confirm that approval matched its hash, or show whether a crash duplicated the side effect.

The [European Union's 2024 AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj/eng) makes the distinction operational. For high-risk AI systems within its scope, Article 12 requires automatic event recording, and Article 26(6) requires deployers to retain automatically generated logs under their control. The law does not prescribe typed state, but a retained rejection tied to a version, evidence record, and guard answers more than a model transcript.

For a publication card, the failure may be a stale sentence. In finance, HR, or access systems, the same gap can turn one corrupted field into audit work, delayed close, or a difficult access review. The mechanism stays the same as the stakes rise.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A behavioral audit evaluates the model, while an authority record explains a live action. Production accountability needs retained state that connects the exact version and evidence to the rule that allowed or rejected the effect.</p></div>

## Bring the old discipline to Monday

Computer scientist Robin Milner's [1978 paper “A Theory of Type Polymorphism in Programming”](https://doi.org/10.1016/0022-0000%2878%2990014-4) presented a formal type discipline and a compile-time checking algorithm. Pydantic and database guards work at runtime, so the mechanisms differ. The craft rule is shared: describe valid forms clearly enough to refuse invalid combinations.

[Ruby on Rails 1.0, the web framework released in December 2005](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh), made a related operating move. Its [database migrations](https://github.com/rails/rails/blob/v1.0.0/activerecord/lib/active_record/migration.rb) expressed schema changes as reproducible instructions between versions. Rails helped teams manage structural change; typed state applies that discipline to agent transitions.

Risbrandt captured the return: “We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt.” On Monday, pick one write-capable agent and one consequential transition. Ask the enterprise architect, system owner, and business owner to name the version, evidence, approver, retention rule, and one forbidden move. Give that contract to a named engineer and review changes like any other production interface.

Test the boundary. A stale approved revision should create no publish intent. The current one should create exactly one, and a retry after a simulated crash should find it. Then run an incident review from persisted records alone. Chat-log reconstruction means the verification debt remains.

I don't know which framework will dominate. I think teams with write-capable agents will treat state contracts as normal review artifacts because the alternative does not survive recovery or audit work. The craft discipline is back when the system can prove why the model was allowed to act.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Start with one consequential transition, assign its state contract to named owners, and test rejection, retry, and incident review. An agent becomes operable when its permission to act is executable evidence.</p></div>
