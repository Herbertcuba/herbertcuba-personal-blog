On July 21, Jonas Risbrandt compressed the recent history of agentic coding into [four stages on LinkedIn](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz): prompting, loops, graphs, typed state. His punchline was a question: "Haven't we just invented... a programming language?"

The joke lands because every added capability exposed a fault line beneath it.

Anthropic [announced Claude Opus 5](https://www.anthropic.com/news/claude-opus-5) on July 24, three days after the post. It attributed "most aligned model to date" to an automated audit run before deployment. The [Hacker News discussion](https://news.ycombinator.com/item?id=49038433) has over 1,700 points.

I think the next engineering problem sits around the model. A long-running agent collects facts while it calls tools and moves between steps. That working record is its state. Even an excellent model can carry a stale fact into a valid action when that state lives inside a transcript.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Agent frameworks are rebuilding software structure around uncertain model calls. Typed state makes the working record inspectable before an agent crosses a costly boundary.</p></div>

## Four waves inside one article card

This article's own Hacker News score changed while the draft moved through review, giving us a useful test case.

The original task carried an exact score. A fact check replaced it with "over 1,700 points," wording that survives normal score drift. A later revision pulled the stale integer back from older context. Follow that fact through each wave and the abstractions become concrete.

### Wave 1: the prompt carries the job

A prompt is plain-text instruction sent to a model. Our article pipeline could begin like this:

```text
You are the article pipeline.
Take one approved idea through research and drafting.
Run fact review before publication.
Use "over 1,700 points" for changing Hacker News scores.
Ask for human approval before publish.
```

This works for a small task. Each incident adds another instruction. After enough incidents, the prompt carries workflow policy alongside memory. Tone guidance sits beside source rules. A diff shows changed words while the legal transitions stay buried in prose.

The prompt is wearing a toolbelt, with workflow state stuffed into the pockets.

### Wave 2: the loop carries the history

[ReAct](https://arxiv.org/abs/2210.03629) means reasoning and acting. The 2022 paper described a pattern that alternates a model's reasoning trace with a tool action and its result. A simplified loop looks like this:

```python
while card["status"] != "done":
    thought = model.reason(context)
    action = model.choose_action(thought)
    result = run_tool(action)
    context.append(result)
```

The loop can search, write, call a fact checker and try again. Its memory is often the growing `context` list.

That is where our score regressed. The correction entered the transcript while the older value remained elsewhere in the history. Both looked like ordinary text. The loop kept moving, and the current belief existed only as an inference from the conversation. Reconstructing it meant replaying messages in order.

### Wave 3: the graph carries the routes

[LangGraph](https://docs.langchain.com/oss/python/langgraph/graph-api) is a Python framework for agent workflows. A graph represents work as nodes connected by edges. A node performs a step, while an edge selects the next step.

`StateGraph` is LangGraph's builder for that structure. `MessagesState` is its built-in schema for conversation messages.

```python
from langgraph.graph import MessagesState, StateGraph

graph = StateGraph(MessagesState)
graph.add_node("draft", draft_node)
graph.add_node("fact_check", fact_check_node)
graph.add_conditional_edges("fact_check", route_by_verdict)
```

The rewrite route is visible now. The HN wording still lives in message history, and a node can contain its own ReAct loop. I think graphs made orchestration easier to discuss. They also made a neat diagram feel more complete than the payload moving through it.

LangGraph already supports richer shared schemas, including `TypedDict` and Pydantic models. The next wave comes from treating that schema as the workflow contract.

### Wave 4: typed state carries the contract

Typed state gives the working record a declared shape. The article card can carry a claim record that stays separate from the chat transcript:

```python
from datetime import datetime
from typing import Literal, Optional
from typing_extensions import TypedDict

from pydantic import TypeAdapter


class ClaimEvidence(TypedDict):
    claim_id: str
    publish_text: str
    source_url: str
    checked_at: datetime
    verified: bool


class CardState(TypedDict):
    card_id: str
    status: Literal["draft", "fact_check", "human_approval", "publish"]
    evidence: list[ClaimEvidence]
    approved_by: Optional[str]


class IllegalTransition(Exception):
    pass


card_adapter = TypeAdapter(CardState)


def claim_text(state: CardState, claim_id: str) -> str:
    item = next(item for item in state["evidence"] if item["claim_id"] == claim_id)
    return item["publish_text"]


def move(candidate: dict[str, object], target: Literal["fact_check", "human_approval", "publish"]) -> CardState:
    state = card_adapter.validate_python(candidate, strict=True)

    if target == "publish" and state["approved_by"] is None:
        raise IllegalTransition("human approval required")

    if target == "publish" and any(item["verified"] is False for item in state["evidence"]):
        raise IllegalTransition("unverified claim")

    return {**state, "status": target}
```

In Python, [`TypedDict`](https://docs.python.org/3/library/typing.html#typing.TypedDict) describes the keys a dictionary should carry, so a type checker can catch bad access before a run. [`Literal`](https://docs.python.org/3/library/typing.html#typing.Literal) narrows `status` to the listed choices. [Pydantic's `TypeAdapter`](https://docs.pydantic.dev/latest/concepts/type_adapter/) validates the incoming payload while the program is running.

In this version, the HN sentence lives in one `ClaimEvidence` record beside its source URL. The same record has a check time and verification flag. A revision renders the sentence from that record. The publish transition rejects the card while verification is false.

That shape gives the fact checker a stable place to record whether the cited source supports the sentence.

## Why an old discipline works here

Typed state turns trust from a long prompt into a boundary in ordinary code.

A retry can start from a named snapshot. Observability and tests can work with a field instead of searching a transcript.

Strong type discipline reaches back to [ML and Hindley-Milner work in the 1970s](https://doi.org/10.1016/0022-0000%2878%2990014-4). Agent teams are rediscovering it because model calls produce uncertain values, while production systems still need explicit contracts.

Rails offers a useful parallel. [Rails 1.0 shipped in 2005](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh), and [migrations put database schema changes into versioned code](https://guides.rubyonrails.org/active_record_migrations.html). Ruby itself was dynamic. The shared craft move is explicit state: a schema an engineer can review and a change history the team can replay.

[AgentKit](https://news.ycombinator.com/item?id=43426164) explored typed routing in TypeScript, while [MemState](https://news.ycombinator.com/item?id=46138027) used Pydantic validation in Python. [GraphFlow](https://news.ycombinator.com/item?id=44481157) cited type safety in its Rust design, and [Agd](https://news.ycombinator.com/item?id=47224560) presented content-addressed state in Zig.

I think typed state earns attention because it gives failure an address: a field or a rejected transition. I don't know how long teams will use the phrase "typed state," especially when every framework wants its own vocabulary.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state gives uncertain model calls an ordinary software boundary. Its value comes from making state changes visible in code another engineer can review.</p></div>

## Alignment ends at the model boundary

A pre-deployment audit observes a model under controlled conditions. A production agent keeps changing after that test ends.

Anthropic was precise about its Opus 5 claim. The cited result came from an automated behavioral audit during pre-deployment testing. The live workflow later adds tool output and stored state. One stale claim can pass through several reasonable model calls before an action exposes it.

I think a system-level alignment claim needs one production answer: show the state that authorized the action.

Calling a model audit the control framework for an illegible workflow is alignment theater. Operational review begins with the state that entered the action.

The EU AI Act makes the operational record concrete. [Article 12](https://eur-lex.europa.eu/eli/reg/2024/1689/oj) requires high-risk AI systems to allow automatic event logging. Article 26(6) requires deployers to retain logs under their control, and the main Annex III duties began applying on August 2, 2026. For an agent in a high-risk setting, the record has legal weight alongside its engineering value.

At enterprise scale, a corrupted field in a finance workflow can become audit hours and a delayed close. This is the operational edge of my [AI Operating Model](/posts/building-the-ai-operating-model/): governance needs a retained object that owners can inspect and approve.

## Guard one transition on Monday

Start at the transition with the highest cost of reversal.

In our content pipeline, that boundary is `human_approval -> publish`. In a finance agent, the equivalent boundary might release a payment. Write the contract before redesigning the whole framework.

| Costly transition | Required state | Logged outcome |
|---|---|---|
| `human_approval -> publish` | `approved_by` is set and every evidence record is verified | accepted snapshot or rejection reason |

The product owner defines the schema. A platform engineer owns validation and retention. The person accountable for risk approves changes to the publish edge.

I would cap the first trial at two engineers and two weeks, focused on this single transition inside the current platform. Compare the fields already carried by the agent with the required state in the table. The gap is [verification debt](/posts/2026-03-09-verification-debt-crisis/) made visible.

In this article, the missing object was a claim record that keeps public wording beside its source. Once that record exists, a test can feed `verified: false` into the transition and expect an exception. Store the accepted snapshot beside the rejection record. Replay and rollback then become properties of the state machine, which is the practical form of [reversibility](/posts/reversibility-is-the-new-correctness/).

Scope matters. Long-running workflows with delegated authority deserve the contract first. A one-shot labeler can stay simple.

I think we spent the early agent years asking prompts to carry responsibilities that code handles better. Jonas named the return in one sentence: "We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt."

A production action should open only when its evidence is present in typed state.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Start with the transition whose reversal would hurt most. Put its required evidence into state and log every rejection.</p></div>
