On July 21, 2026, engineer [Jonas Risbrandt](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz) described agent engineering in four moves:

> First, we talked about prompting.
>
> Then we realized one prompt was not enough, so we added loops.
>
> Then loops were not enough, so we introduced graphs.
>
> Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing.

His punchline: "Haven't we just invented... a programming language?"

Three days later, Anthropic, the AI company behind Claude, released [Claude Opus 5](https://www.anthropic.com/news/claude-opus-5), an AI model for work that includes long-running agents. Anthropic said a pre-deployment behavioral audit found it to be "our most aligned model to date." The announcement drew over 1,700 points on [Hacker News](https://news.ycombinator.com/item?id=49038433), a forum where software practitioners vote on and discuss technical news.

I think the timing exposes the next engineering problem. A model can improve in an evaluation while a deployed agent still carries stale facts, loses an approval, or repeats an action after a crash. The missing layer is an inspectable record of what the system accepts and permits.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Model behavior is improving, but production accountability sits at the system layer. Typed state gives a deployed agent a checked record of the facts and permissions behind its next action.</p></div>

## Four waves through one return

Imagine an agent processing a customer return. It reads a receipt, checks policy, seeks approval for exceptions, and sends the refund to a payment service. The task processes documents until its final step moves money, making its carried state consequential.

A **prompt** is a natural-language instruction to a model. The first version puts nearly the entire workflow into that instruction:

```text
Read the receipt and return request.
Check the policy, ask for approval when required,
and issue the refund only when the evidence is complete.
```

The instruction has no formal place for the receipt revision, policy version, approval scope, or refund status. Each incident adds another warning. Before long, the prose is carrying policy while trying to act as both program and recovery plan.

A **loop** lets the model choose another action until it reaches a stopping condition:

```python
while not resolved:
    action = model.choose(message_history)
    result = run_tool(action)
    message_history.append(result)
```

Now the agent can request a clearer receipt or retry a failed lookup. Yet its working state sits inside `message_history`, the growing chat record. Suppose the customer uploads receipt A, then corrects the quantity in receipt B. A reviewer approves B, but a later loop recovers the old quantity and prepares the larger refund from A. Both versions are plausible text, so the corruption remains quiet.

A **graph** represents workflow steps as nodes and allowed routes as edges:

```text
extract -> policy_check -> approval -> refund
    ^             |
    +-- need_info-+
```

The graph shows that missing information returns the case to extraction, but it may not show which receipt version crosses that edge or which amount the approval covers. A node can also hide its own prompt and loop. The map is clearer while the cargo remains informal.

**Typed state** is a persisted record whose fields accept declared kinds of values and whose transitions are checked. Persistence means the record survives a model call or process crash. A type annotation states what the code expects; runtime validation checks actual model and tool output before it enters the durable record.

```typescript
type ReturnState = {
  caseId: string
  stage: "extract" | "policy_check" | "approval" | "refund"
  receiptVersion: number
  policyVersion: string
  approvedReceiptVersion: number | null
  refundCents: number
  approvedRefundCents: number | null
  approvedBy: string | null
  evidenceComplete: boolean
}

function canRefund(s: ReturnState): boolean {
  return s.stage === "approval" &&
    s.evidenceComplete &&
    s.approvedReceiptVersion === s.receiptVersion &&
    s.approvedRefundCents === s.refundCents &&
    Boolean(s.approvedBy)
}
```

`canRefund` is a **transition guard**, a condition that must pass before the state changes. If receipt B supersedes A, the old approval no longer authorizes payment. If the model produces `"forty euros"` where the boundary requires an integer number of cents, runtime validation rejects the write. Types do not prove the amount is correct, but they turn malformed values and expired authority into visible failures.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The prompt expresses intent, the loop repeats work, and the graph shows possible routes. Typed state records the exact receipt, amount, evidence status, and approval that must agree before a refund can leave the system.</p></div>

## Why state is the forcing function

Jonas listed typed state beside retries, persistence, error handling, observability, reusable components, and testing. I think state is the forcing function because each discipline depends on knowing what is being retried, stored, or tested. A retry from corrupted state repeats the wrong work. A log without defined fields records activity without establishing authority.

The term **strong typing** varies by language, but its discipline is old. In 1978, computer scientist Robin Milner published [a theory of type polymorphism](https://doi.org/10.1016/0022-0000(78)90014-4), helping formalize how programs can remain flexible while preserving guarantees about values. For agents, uncertain output should cross into durable business state through a boundary that can reject unsafe values.

A similar discipline made early web applications operable. [Ruby on Rails 1.0](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh), a web framework released in December 2005, did not make its Ruby programming language statically typed. Its database migrations put shared-schema changes into version-controlled code, so teams could review and replay how application state evolved. Typed agent state brings that visibility to facts and permissions carried between model calls.

Independent tools point this way, showing convergence rather than broad adoption. In March 2025, [Inngest AgentKit](https://github.com/inngest/agent-kit), an open-source TypeScript framework, described its routing as a "fully typed state machine." That December, [MemState](https://github.com/scream4ik/MemState), a small Python project, used Pydantic, a Python validation library, to reject invalid memory writes at runtime.

I think this wave differs from the first three because it exposes their shared weakness. The prompt, loop, and graph all improved orchestration while allowing critical business facts to remain ordinary text. Typed state gives those facts a named home and makes disagreement fail at a boundary.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>State is the forcing function because retries, persistence, logs, and tests all depend on a defined record. The engineering gain comes from checking uncertain model output before the rest of the system treats it as accepted business data.</p></div>

## Audit the system, not only the model

A pre-deployment model evaluation and a production audit answer different questions. Anthropic's claim concerns how Opus 5 behaved during testing. After an incorrect refund, an incident team needs to know which receipt and policy were active, what amount was approved, and how the payment service responded. Treating the first answer as proof of the second is alignment theater: the model has been examined while its operating trail remains incomplete.

I think that gap creates **verification debt**, the future investigation and rework caused by weak evidence at the moment a decision crossed a boundary. A chat transcript can show what was said, and a graph trace can show which nodes ran. Neither necessarily proves that the approval covered receipt B and exactly 4,000 cents. A typed record can make that question answerable without reconstructing intent from prose.

At enterprise scale, an agent touching invoices, employee access, or customer credits can turn one stale field into audit work and a delayed financial close. An **AI Operating Model**, the ownership and control structure around AI work, therefore needs inspectable state, a named system owner, and retained rejections. A reviewer should see what the agent proposed, what the boundary accepted, and why a transition failed.

Regulation points in the same direction. The [EU AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj), the European Union's 2024 AI regulation, requires high-risk systems to support automatic event logging under Article 12 and deployers to retain controlled logs under Article 26(5). Its main obligations for Annex III high-risk uses began applying on August 2, 2026. A retail return agent is not automatically high-risk, but agents in employment or access to essential services may be. There, durable transitions can supply evidence that model quality alone cannot.

Reversibility also becomes a state property rather than a hopeful sentence in a prompt. Keeping the prior accepted record gives the system a known point to restore. An **idempotency key**, a unique token attached to an external operation, lets the payment service recognize a repeated refund request after a crash and return the original result rather than pay twice. The money may not always be recoverable, but the transition can be replayed without duplicating it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Model testing can characterize behavior, but it cannot reconstruct a deployed decision. Typed records reduce verification debt by preserving why authority was granted or rejected and what happened outside the system.</p></div>

## Put one boundary under contract

My take for Monday morning is narrow. Choose one agent with permission to create an external effect, then ask the enterprise architect and system owner to review that boundary for 30 minutes. Name the state fields, who owns each one, how long the record remains available, and one transition that must be impossible.

For the return agent, bind approval to the receipt version and refund amount. Require the evidence status to be set by a validator rather than inferred later from conversation. Give each payment attempt an idempotency key and retain the payment service's response as part of the case record.

Then give two engineers two weeks to test the contract without replacing the whole platform. A changed receipt must invalidate approval. An approved return must pay exactly once. A crash after the payment request must recover the original provider response without issuing another refund. Those tests make verification debt visible before a customer or auditor does.

I don't know which agent framework will dominate, and I think that uncertainty is healthy. Short-lived classification may not need durable workflow state. An agent that can publish, pay, provision access, or approve a business decision does, because its authority must survive a model call without becoming ambiguous.

Jonas closed his post with the line that matters: "We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt." That return is not a failure of agent engineering. It is where the craft begins again.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Start with one consequential boundary rather than a platform rewrite. Give its state a named owner, bind authority to an exact record, and test invalidation plus duplicate prevention until the system can explain every action it permits.</p></div>
