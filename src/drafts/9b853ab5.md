A Swedish engineer named Jonas Risbrandt posted on LinkedIn this week that agentic coding has gone through three waves. His words: "Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state."

Each wave looked like a feature. Each one was actually a fault line.

In the same week, Anthropic shipped Opus 5 with the claim "most aligned to date," and the Hacker News thread about it collected 1,723 upvotes. The top comments were skeptical. Nobody in that thread doubted the model was good. They doubted that a better model would fix what broke their agent systems.

I think Jonas's post and that thread are the same conversation. The industry spent three years scaling the model, and the failures kept coming from somewhere else: the state the agent carries while it works. Typed state is the first wave that attacks that problem directly.

## Four waves, one invoice

To make this concrete, take one task and follow it through all four waves: an agent that reads incoming invoice PDFs, pulls out the vendor, amount, and due date, and drafts the payment entry for a human to approve.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Each wave added structure. The first three hid their failures one layer down, and typed state is the first wave that exposes them instead.</p></div>

### Wave one: the prompt

You write one careful prompt.

```text
Read the attached invoice PDF.
Extract the vendor, total amount, currency, and due date.
Draft a payment entry for review.
```

This works on the demo invoice. It keeps working until the day a Swedish supplier sends an invoice that writes the total as 12.400,50, with the period and comma swapped from the English convention. The model reads it as 12.40. The output still looks confident, formatted, and correct. The failure is invisible because a prompt has no place where a wrong number looks different from a right one.

### Wave two: the loop

One prompt is not enough, so you add a loop. The common pattern here is called ReAct, short for reasoning and acting. The model writes down a thought, picks a tool to call, reads the result, and repeats until it decides the job is done.

```python
while not done:
    thought = model.think(context)
    action = model.pick_tool(thought)
    result = run(action)
    context.append(thought, action, result)
```

This is a real improvement. The agent can now open the PDF, call a parser, and check its own work. But everything the agent knows lives in one growing list of messages. A misread at step three becomes an established fact by step twelve, and every later step reasons on top of it. When the finance team asks why the agent drafted a payment of 12.40 instead of 12,400.50, you get to scroll through forty messages and guess. I think this is where a lot of teams still live, and it is an uncomfortable place to be during an audit.

### Wave three: the graph

Loops are hard to follow, so the frameworks gave us graphs. LangGraph is the best known one. You define nodes, where each node is one step of work, and edges, which are the allowed moves between steps. The object that wires them together is called a StateGraph.

```python
graph = StateGraph(dict)
graph.add_node("extract", extract_invoice)
graph.add_node("verify", verify_amounts)
graph.add_node("draft", draft_payment)
graph.add_edge("extract", "verify")
graph.add_edge("verify", "draft")
```

Now you can draw the flow on a whiteboard. I think graphs were a real improvement, because the process finally had a shape you could point at. But look at the first line: `StateGraph(dict)`. The data passed between nodes is a plain dictionary. Any node can write any key. The verify step can quietly overwrite `amount`, or invent a new key called `ammount_final_v2`, and nothing complains. The graph gave you visible structure for the flow. The state underneath stayed fog.

### Wave four: typed state

The fourth wave gives that state a declared shape. The simplest version in Python is a TypedDict: a dictionary where you declare the keys and their types up front, before anything runs.

```python
class InvoiceState(TypedDict):
    vendor: str
    amount: Decimal
    currency: str
    due_date: date
    status: Literal["new", "extracted", "verified", "drafted"]
    errors: list[str]
```

Now the extract step fills declared fields. The verify step flips `status` from extracted to verified, and it cannot invent `ammount_final_v2`, because that field does not exist in the schema. One honest caveat: TypedDict is checked by your editor and type checker, not at runtime. If you want the shape enforced while the agent runs, you use a validation library like pydantic. Either way, the principle holds. The agent's working memory is now a document with a shape you agreed on in advance.

## Why this wave pays down debt

Typed state is different in kind from the three waves before it, and the difference is what it does to failure.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A schema turns agent memory into something you can diff, test, and roll back. That is verification debt being repaid.</p></div>

Every earlier wave pushed the problem one layer down. The prompt hid the process. The loop hid the state inside a conversation. The graph hid the state inside an untyped dictionary. Typed state inverts the pattern: when the invoice agent fails now, it fails inside a named field, with a status, at a logged step. You can reconstruct the run. I wrote earlier this year about verification debt, the pile of agent output you shipped but never actually checked. A state schema is how you start paying that pile down, because every run leaves an artifact you can inspect instead of a transcript you have to trust.

If this sounds familiar, it should. In 2005, Rails made web applications possible for ordinary teams, and the move it made was convention over configuration. Rails decided where things lived, so any developer could open an unfamiliar codebase and find their way around. Typed state is the same craft move applied to agents. The structure is declared, so a stranger, or an auditor, or future you at 09:14 on a bad morning, can read what the system holds. I think that is the part worth copying, more than any framework feature.

Here is a falsifiable version of the claim. Take an agent you run today, write the schema you believe it operates on, then diff that schema against what the agent actually carries at the end of a run. My prediction: you will find two to three times the fields you declared, half of them written once and read never.

## What breaks without it

The failure mode of skipping this wave has a name I have started using: alignment theater.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A well-aligned model inside an unauditable system is alignment theater. The failure lands in your ledger either way.</p></div>

Opus 5 may well be the most aligned model Anthropic has shipped. Alignment is a property of the model. Accountability is a property of the system the model runs inside, and those are different things that get confused constantly. In Blade Runner, the Voight-Kampff test sits a replicant down and interviews it, measuring responses to questions. The test can tell you something about the individual in the chair. It tells you nothing about what that individual did last night out in the world. That is the situation with a well-aligned model running an untyped agent loop. You interviewed the model. The system still drafted a payment of 12.40 at 03:00, and in the morning nobody can reconstruct why.

This is also where reversibility stops being a vibe. When state is typed and logged per step, rollback becomes a property of the state machine: you restore the last verified snapshot and replay from there. When state is a forty-message conversation, rollback is a hope embedded in the prompt, and hope does not survive contact with a month-end close. I think the skepticism in that Hacker News thread is healthy, because those engineers have been the human rollback mechanism for exactly this kind of system, and it is thankless work.

## Monday morning

The practical version of all this fits in a small set of moves.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Pick one agent, write its state schema before you touch its prompt, and diff what it actually carries after a week.</p></div>

Pick one agent your team runs. Write down its state schema before you change anything else: the fields it starts with, what each step may add, and what must be true before its output ships. Then let it run for a week and diff the schema against reality. You will find fields nobody declared and at least one step that writes something nobody reads. Fix the schema or fix the step, and repeat.

I don't know whether typed state is the last wave. I doubt it, because every wave so far has exposed a fault line underneath itself. But this is the first wave where the thing being added is a discipline rather than a capability, and disciplines tend to stick.

The invoice agent still misreads Swedish number formats sometimes. The difference is that it now fails inside a declared field, with a status, in a log line I can read on Monday morning. That is the whole upgrade.
