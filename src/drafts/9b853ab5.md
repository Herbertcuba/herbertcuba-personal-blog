On July 21, 2026, [Jonas Risbrandt described the evolution of agentic coding in a LinkedIn post](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz). Agentic coding lets an AI model plan work and call software tools instead of only answering a question.

> “Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing.”

Risbrandt then asked, “Haven't we just invented... a programming language?” I think he named the pattern, but the engineering win is more specific. Typed state can record which version, evidence, approval, and rule allowed uncertain model output to affect a live system.

Three days later, AI company Anthropic [announced its Claude Opus 5 model](https://www.anthropic.com/news/claude-opus-5) for long-running work. It said a pre-deployment automated behavioral audit found Opus 5 to be “our most aligned model to date.” The discussion on [Hacker News, a technology forum](https://news.ycombinator.com/item?id=49038433), drew over 1,700 points. Each wave looked like a feature but exposed a fault line: model capability never showed what the production system knew when it acted.

## Four waves, one publication card

Follow one article card from drafting to publication. Its brief contained an exact Hacker News score. Fact review replaced that volatile number with “over 1,700 points,” but a later revision recovered the old figure from stale context. Only the corrected, approved revision may publish.

### Prompt

A prompt gives the model instructions and constraints in natural-language prose.

```text
Research the card, write the article, verify every source,
and publish only the approved revision.
Use “over 1,700 points,” never an exact score.
```

“Approved revision” names no machine-checkable object. As incidents add instructions, the prompt starts serving as data contract, workflow, and runbook. The system can repeat the rule without proving which revision the human approved.

### Loop

A loop lets the model choose an action, inspect the result, and repeat until it reaches a stopping condition.

```python
while card.status not in {"done", "escalated"}:
    action = model.choose(message_history)
    result = tools.run(action)
    message_history.append(result)
```

The message history becomes informal state: facts carried between steps. Both scores can remain, so a later pass may retrieve the wrong one without breaking the loop. I think state corruption can resemble progress until an external tool acts.

### Graph

A graph connects workflow steps, called nodes, with directed edges that determine what runs next.

```text
research → draft → fact_check → human_approval → publish
             ↑          |
             └─ kickback┘
```

The failed fact check now has a visible route back to drafting. Yet the graph cannot prove that the drafting node received the correction, and every node may hide another prompt or loop. It exposes the route while leaving the authority of what moves through it implicit.

### Typed state

Typed state declares the fields and allowed values a workflow may carry. Persistence stores that record beyond one model call. This illustrative boundary uses [Pydantic, a Python library that validates data at runtime](https://docs.pydantic.dev/latest/concepts/models/), inside a locked database transaction:

```python
class PublishState(BaseModel):
    model_config = ConfigDict(strict=True)
    card_id: str
    version: int
    status: Literal["fact_check", "human_approval", "publish"]
    revision_id: str
    content_hash: str
    fact_report_id: str | None
    sources_verified: bool
    approved_revision_id: str | None
    approved_content_hash: str | None
    approved_by: str | None

with transaction():
    current = PublishState.model_validate(lock_card(request.card_id))
    require(request.expected_version == current.version)
    require(current.status == "human_approval")
    require(current.sources_verified and current.fact_report_id is not None)
    require(current.revision_id == current.approved_revision_id)
    require(current.content_hash == current.approved_content_hash)
    write_publish_intent_once(request.idempotency_key, current)
    advance_if_version(current.card_id, current.version, "publish")
```

The schema declares expected fields; runtime validation checks incoming data against those fields and rules. A content hash fingerprints the draft. The expected-version check rejects an older request, while the `require` statements are transition guards that stop a well-formed record from taking an unauthorized route. Together they form a state machine.

`write_publish_intent_once` creates an outbox record, a durable instruction stored with the database change. Its idempotency key identifies one intent, so a matching retry finds the existing record. The same contract can bind an invoice version to purchase-order evidence and budget-owner approval.

## Why typed state changes the boundary

Typed state does not replace graphs. [LangGraph, a graph-based agent library from AI tooling company LangChain](https://docs.langchain.com/oss/python/langgraph/graph-api), supports shared state schemas. In March 2025, [workflow company Inngest described its TypeScript AgentKit library as using a “fully typed state machine” for routing](https://news.ycombinator.com/item?id=43426164). These examples show direction, not broad adoption.

Strong typing has no universal definition. Here, typed state means a schema enforced at runtime and the database boundary; Python annotations alone do not police inputs. It cannot verify a source or make a model correct, but it can reject a missing report, mismatched revision, or illegal move before publication. One-shot classification may need a light record; control should scale with consequence.

I think that gives typed state more weight than another framework layer. Retries need a known starting record, observability needs stable fields, and persistence needs storage rules. Typed state lets those controls answer questions against named facts.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The fourth wave makes informal workflow state explicit. Its bounded engineering gain is the power to refuse an action whose evidence, version, approval, or route does not match.</p></div>

## What implicit state costs

An execution trace records which steps ran. It may show `human_approval` before `publish` while omitting which revision was approved. The incident review must reconstruct authority from activity records.

I call that gap verification debt: the distance between what a workflow assumes and what its records can prove. Here, it appeared as a stale claim. In a 5,000-employee company, the same failure in invoice approval or access provisioning can create audit work, a delayed close, or another pilot leadership will not scale.

This is where model alignment and system accountability separate. Anthropic's claim concerned behavior measured before deployment, not the evidence behind a later live action. My take is that alignment theater begins when a model evaluation is treated as proof that production used the right state.

An AI Operating Model is the ownership, evidence, decisions, and controls around an AI system. It becomes legible when the business defines a consequential transition, engineering enforces it, and reviewers can inspect accepted and rejected records. The [European Union's 2024 AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj) points in this direction without prescribing typed state. For high-risk systems in scope, Article 12 requires automatic event recording, and Article 26(6) requires deployers to retain generated logs under their control for at least six months. Many obligations for Annex III, the annex listing regulated high-risk use categories, began applying on August 2, 2026. A publication workflow is not automatically high risk, but a retained rejection tied to a rule, version, and owner is evidence an auditor can actually test.

Typed state also makes reversibility precise: return to an accepted version or run a named correction after an external effect. Versioned records support replay, and an idempotency key can prevent a duplicate intent, but neither can unsend an email or reverse a payment. Those effects need compensation paths. I think shared multi-agent memory will become the next fault line if its authority remains implicit.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Activity logs show what ran, while authority records show which facts and approval allowed it to run. Without that link, verification debt grows across incidents, audits, and attempts to move pilots into production.</p></div>

## Put the contract into review

Computer scientist Robin Milner's [1978 paper “A theory of type polymorphism in programming”](https://doi.org/10.1016/0022-0000%2878%2990014-4) presented a formal type discipline and compile-time checking algorithm. The craft move is old: declare valid forms and reject invalid combinations before action.

Web applications existed when [Ruby on Rails 1.0, a web framework, arrived in December 2005](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh). Rails migrations are reproducible instructions for changing a database schema between versions. They made change easier to operate and review. Rails made web state legible. Typed state makes agent state legible.

On Monday, ask the enterprise architect and system owner to convene a 30-minute review with engineering and the business owner. Choose one write-capable agent and one consequential transition. Name its version, evidence, approver, retention rule, and one forbidden move. The business accepts the rule; a named engineer owns enforcement.

Time-box the boundary to two engineers for two weeks rather than starting a platform rewrite. Persist both acceptance and rejection, then make these tests pass:

```text
stale approved revision → rejection, no publish intent
current approved revision → one publish intent
retry after a crash with the same key → existing intent, no second record
```

Run an incident review from persisted state alone. If the team cannot explain what was accepted, which guard decided, and what followed, its verification debt is visible. This is how a pilot earns production ownership.

I don't know which agent framework will dominate. My claim is falsifiable: by the end of 2027, teams running write-capable agents will treat state contracts as a standard review artifact. If traces alone consistently support incident review and crash recovery, the contract adds little. I don't expect it.

Risbrandt's sharper line was, “We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt.” I think the code that endures will be the code that records why an uncertain model was allowed to act.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Review one consequential transition as a software contract, test its refusal and recovery paths, and demand an incident explanation from persisted state. Craft discipline is back when authority becomes executable.</p></div>
