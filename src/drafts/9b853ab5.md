A Swedish engineer named Jonas Risbrandt posted on LinkedIn this week that agentic coding has gone through three waves and is entering a fourth. One prompt, then loops around the prompt, then graphs of loops, and now typed state. His post is one paragraph, and I have read it four times.

The same week, Anthropic shipped Opus 5 with the claim "most aligned to date." The Hacker News thread passed 1,700 upvotes. I read the thread top to bottom, and the interesting thing is where the skepticism sits. The model's quality was barely disputed. What people doubted was that a better model would fix what broke their agent systems. Their agents failed in the plumbing, in the state the agent carries while it works, and alignment at the model layer does not touch that.

I think Jonas's post and that thread belong in the same conversation. One describes how we got here. The other shows what the people running these systems in production have already learned the hard way.

## Four waves, one invoice agent

Take one task and follow it through all four waves: an agent that reads a supplier invoice and posts it to your accounting system. It has to pull out the vendor, the amount, and the due date, then create the booking.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>One invoice agent, four architectures. A prompt forgets the invoice between steps. A loop remembers everything in one growing transcript, so early mistakes harden into facts. A graph organizes the transcript but inherits its fog. Typed state declares the fields up front, which makes the agent inspectable for the first time.</p></div>

**Wave one: the prompt.** You write one big instruction. Read the invoice, extract the fields, call the accounting API. The invoice text goes in, a confident answer comes out. The failure shows up the moment the task needs two steps. Say the extraction tool returns the amount as "12.400,50" because the invoice is Swedish. The next step needs that number, but the model no longer sees the invoice. It only sees what it wrote down, and it wrote down twelve kronor. The prompt is a goldfish. Every step starts from whatever the last step happened to say.

**Wave two: the loop.** So you wrap the prompt in a cycle. The model proposes an action, your code runs it, the result goes back into the conversation, repeat until done. This pattern has a name, ReAct, short for reasoning and acting, from a 2022 paper by Yao and others. Most agent frameworks you have heard of started here. With the loop, the agent re-reads the invoice when it needs to, and accuracy jumps.

Then the invoice count grows. The loop's memory is the whole conversation transcript, and the transcript only grows. A vendor name misread at step three is plain text by step twelve, and every later step reasons on top of it. I think this is where a lot of teams still live: a loop that works in the demo and quietly corrupts its own memory in production, and when finance calls about a wrong booking, nobody can reconstruct what the agent believed at the moment it acted.

**Wave three: the graph.** So you give the agent a map. Nodes are steps like extract, validate, book. Edges say which step follows which, and the edges can branch on conditions. LangGraph is the best known implementation; its core object is even called a StateGraph, a graph whose nodes share one state object. With a graph you can route invoices above 100,000 kronor to a human, and the system starts looking like engineering.

I think graphs were a real improvement, and they also did something sneaky. Most implementations still passed that growing transcript around underneath the map. The graph gave you architecture. The fog underneath stayed the same, only now it had a diagram on top, and the diagram made everyone feel better.

**Wave four: typed state.** The fourth wave says the agent's memory is a declared data structure with types. In Python this often means a TypedDict, a dictionary where you declare every field and its type up front. For the invoice agent:

```python
class InvoiceState(TypedDict):
    vendor: str
    amount_ore: int          # öre, always integer
    due_date: date
    currency: str
    approved: bool
    confidence: float        # 0.0 to 1.0
```

Six fields. Each step reads some of them and writes some of them, and anything outside the schema has to fight its way in. The "12.400,50" string from wave one cannot survive here. Something has to convert it to the integer 1240050 before it enters the state, and that conversion is a line of code you can read, test, and point at when finance calls.

## Why this wave pays down debt

Typed state does a different kind of work than the three waves before it, and the difference shows up in how systems fail.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts, loops, and graphs each added capability and pushed the failure one layer down. Typed state adds a discipline: the agent's memory becomes a declared schema, which pays down verification debt and turns reversibility into a property of the system. Rails did the same move for web apps in 2005.</p></div>

Each earlier wave added capability and hid the failure one layer deeper. The prompt hid the forgetfulness. The loop hid the corruption inside a growing transcript. The graph hid the transcript inside a diagram. Typed state is the first wave that points the flashlight at the failure itself: what, exactly, is this system carrying around while it works.

I wrote in March about verification debt, the gap between what your AI systems produce and what you can actually check. Typed state pays that debt down directly. The schema is a contract. You can validate the state after every step, and when the validation fails you know which step broke the contract. I wrote last quarter about reversibility, and it changes address here. With a typed state object you can snapshot the state at each step, so a bad run means you restore the last verified snapshot and replay from there. Rollback becomes a feature of the state machine, instead of a hope baked into the prompt wording.

This is also why the Rails comparison keeps coming back to me. Rails made web apps possible for ordinary teams in 2005 with a boring craft move: convention over configuration. The framework declared the structure, and the structure made a thousand decisions stop mattering. Typed state is the same move for agents. The schema declares the structure, and the structure makes the agent's behavior legible to a reviewer, an auditor, or future you at 09:14 on a bad morning. I think that legibility is what turns an AI feature into an AI operating model, because you cannot govern what you cannot inspect.

Strong typing is the oldest craft discipline we have in software. We are rediscovering it in the newest system we have.

## What breaks without it

The failure mode of skipping this wave is worth naming plainly, because it is already running in production.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Without typed state you get alignment theater: the model is certified aligned while the system around it corrupts state in ways nobody can reconstruct. Alignment lives at the model layer. Accountability lives at the system layer. Your auditors will ask about the second one.</p></div>

Back to that Hacker News thread. Opus 5 can be the most aligned model Anthropic has ever shipped, and your invoice agent can still book twelve kronor instead of twelve thousand, because the corruption happens in the system the model runs inside. A well-behaved model inside a system whose state nobody can inspect gives you impressive demos and indefensible incidents. I think of that as alignment theater: the certification says the actor behaves, while the stage is on fire.

Regulators are starting to ask about the stage. When an automated system makes or prepares a decision, someone will eventually ask what it knew when it decided. With a transcript-based agent, the honest answer is a shrug and a log file. With typed state, the answer is a record: the fields it started with, what each step added, and what was true before its output shipped. I think the skepticism in that HN thread is healthy. It is the sound of people who have been paged at 3 AM by an agent they could not interrogate.

I don't know whether typed state is the last wave. I doubt it, since every wave so far has exposed a fault line in the layer below it. But this is the first wave where what we are adding is a discipline, and disciplines tend to stick around longer than capabilities.

## What to do on Monday

You do not need a framework migration to start. You need one agent and one honest afternoon.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Pick one agent you run. Write down the schema you believe it operates on. Diff that against what it actually carries at the end of a run. The gap is your verification debt made visible, and closing it for one agent is a two-engineer, two-week job with no platform rewrite.</p></div>

Pick one agent you run in production. Write down the schema you believe it operates on, six to ten fields like the invoice example above. Then diff that schema against what the agent actually carries at the end of a run. My prediction: you will find two or three times the fields you expected, plus values with no type at all, plus fields that mean different things at different steps. That gap is your verification debt made visible.

Closing it for one agent is a small project. Two engineers, two weeks, no platform rewrite. Declare the schema, validate it after each step, snapshot it so you can replay. One named engineer owns it, and changes to it go through review like any other contract.

The waves Jonas described will keep coming. The teams that come out ahead will be the ones who noticed that this wave asks for something older and less glamorous than the others: write down what your system knows, in a form a stranger can check. In 2001, the ship's computer in 2001: A Space Odyssey ran the whole vessel with total confidence and state nobody on board could inspect. We have spent three waves building agents that work the same way. The fourth wave is where we start reading the gauges.
