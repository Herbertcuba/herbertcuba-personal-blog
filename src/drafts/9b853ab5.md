A Swedish engineer named Jonas Risbrandt [posted something on LinkedIn](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz) this week that I read twice:

"Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state."

Four moves in three sentences. Each one looked like a feature when it shipped. Each one was actually a fault line, a place where the previous approach cracked under its own weight.

The timing is sharp. Anthropic shipped Opus 5 days ago with "most aligned to date" in the launch material, and the Hacker News thread filled up with engineers arguing about what "aligned" even means when you can't see inside the system. I think Jonas's post and that thread are the same conversation. Alignment claims are cheap when the agent's inner workings are a fog. Typed state is how the fog lifts.

I want to walk through all four waves using one example, because the evolution only makes sense when you watch the same task break four different ways.

## The task: one invoice, four waves

Say you run a small finance team. Every month, a few hundred supplier invoices land in an inbox. Someone has to pull the vendor name and the total out of each PDF and type them into the accounting system.

You want an agent to do it. Here is how that agent grows up, wave by wave.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>One boring job, extracting the vendor and total from supplier invoices, is enough to show why each wave of agentic coding cracked and forced the next one.</p></div>

## Wave one: the prompt

I tried to do this with one prompt. Everyone did.

```
Read this invoice PDF and return the vendor name and the total as JSON.
```

That works. For a while. Clean PDFs from your two biggest suppliers come back perfect, and you feel like a wizard.

Then an invoice arrives as a scanned image. Another has the total in a footnote on page three. A third is in Swedish, and the model confidently returns the invoice number as the total. The prompt has no way to say "I can't read this, ask a human." It has to answer. So it guesses, and the guess lands in your accounting system.

The deeper problem: the prompt is carrying three jobs at once. It defines the output shape, it drives the process, and it holds whatever the agent has learned so far. All inside a blob of text that nobody can diff, review, or test.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>One prompt can extract data from clean invoices, but it can't admit confusion, can't use tools, and hides all its working inside text nobody can test.</p></div>

## Wave two: the loop

The fix was a pattern called ReAct, short for Reason and Act. Instead of answering in one shot, the model writes a short "thought," picks an action (usually calling a tool), reads the result, and repeats until it thinks it is done.

```
loop:
  thought = model.think(context)
  if thought.says_done: break
  result = run_tool(thought.action)
  context += result
```

Now the agent can run the PDF through an OCR tool when text extraction fails. It can re-read page three. It can check its own arithmetic. This genuinely fixed the one-shot failures, and frameworks built on this pattern ran most of the agents you used in 2024 and 2025.

But the loop created a quieter bug. The agent's entire memory of the job lives in the conversation transcript, a growing pile of thoughts and tool results. Nothing checks that pile. If the OCR tool misreads "17,500" as "1,7500" on step four, that wrong number rides along through every later step, and the final answer carries it with full confidence. State corruption, happening silently inside what looks like a normal chat.

I think this is where a lot of teams still live. The agent works in the demo and rots in production, and nobody can say why, because the "why" is buried in a transcript nobody reads.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>ReAct loops let the agent use tools and recover from bad inputs, but all state lives in an unchecked transcript, so one wrong value on step four poisons everything after it.</p></div>

## Wave three: the graph

Loops have another weakness: they wander. The model decides what to do next at every step, which means the same invoice can take a different path on Tuesday than it did on Monday. So the next wave made the paths explicit.

LangGraph is the best known tool here. It is a Python library from the LangChain team where you stop hoping the model picks the right next step and instead draw the steps yourself. Your agent becomes a graph: nodes are chunks of work, edges are the rules for where to go next.

```
graph.add_node("extract", extract_invoice)
graph.add_node("verify", verify_totals)
graph.add_node("human_review", ask_a_human)
graph.add_edge("extract", "verify")
graph.add_conditional_edges("verify", route)
```

Now every invoice takes the same route. Extract, verify, and only escalate to a human when verification fails. Auditable, repeatable, demo-friendly. I think graphs were a real improvement, and they also smuggled the loop's core problem into a nicer box.

The problem is what flows along those edges. In most graph setups, the state passed between nodes is a plain dictionary, a bag of keys and values with no declared shape. Any node can write any key. A typo in one node (`vndr` instead of `vendor`) creates a new key instead of an error. The `verify` node reads `state["total"]`, gets `None` because `extract` happened to store it as `state["amount"]`, and silently approves the wrong thing.

The graph gave you visible structure for the flow. The state underneath stayed fog.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Graphs made the agent's path explicit and repeatable, but state still moved between nodes as a shapeless dictionary, so typos and mismatched keys passed silently from step to step.</p></div>

## Wave four: typed state

The fourth wave attacks the fog directly. Typed state means you declare, up front, exactly what the agent is allowed to know at any moment, and the framework enforces it.

In LangGraph this is done with a TypedDict, a Python construct that looks like a normal dictionary except you declare every key and the type of every value in advance:

```
class InvoiceState(TypedDict):
    raw_text: str
    vendor: str | None
    total: float | None
    approved: bool
```

Then you build the graph on top of that schema, which is what `StateGraph` means: a graph where every node reads from and writes to this declared state, and nothing else.

Now watch the earlier bugs die. The `vndr` typo fails immediately, because `vndr` is not in the schema. The `amount` versus `total` mismatch fails, because there is exactly one field for the money. A node that tries to mark an invoice `approved` without a `total` can be rejected before it runs. The state at any moment is a small, inspectable object you can print, diff, save, and hand to a colleague.

I don't know if the current frameworks are the final shape of this. The field is moving too fast for that. But the direction is clear, and it is the same direction software always moves when it grows up: from "it works on my machine" to "here is the contract, and the machine checks it."

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state declares what the agent may know, in advance, as an enforced schema. The silent bugs from waves two and three become loud errors, and the agent's condition becomes something you can inspect, diff, and test.</p></div>

## Why this wave is different

Here is the part I keep coming back to. Prompts, loops, and graphs each added capability. Typed state adds legibility. Capability makes the demo better. Legibility makes the system ownable.

This is a very old craft move. Rails did it for web apps in 2005. Rails made the average web application legible: you could open a stranger's project and know where the models lived, where the requests flowed, where the business rules sat. That legibility is what let teams of people build big things fast, and it is a large part of why web engineering became a mass profession. Typed state is the same move for agent systems. An agent built on a declared schema is an agent a second engineer can pick up.

It also pays down what I have called verification debt. Every unchecked agent decision you ship is debt, and the interest is paid in incidents nobody can reconstruct. A typed state machine gives you the ledger: at step seven, the agent knew this, believed this, and had not yet checked that. Reversibility stops being a vibe in the prompt ("please be careful") and becomes a property of the system, because state snapshots are data you can roll back.

And it makes agents testable in a way prompts never were. Unit tests for the functions that transform state. Integration tests for the workflows. The schema is the boundary where the tests attach.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state is the Rails move for agents: it makes the system legible enough to own, audit, roll back, and test, which is what turns a demo into infrastructure.</p></div>

## What breaks without it

In *2001: A Space Odyssey*, the crew of the Discovery can talk to HAL 9000 as much as they like. What they cannot do is open him up and look at what he currently believes. HAL's state is sealed. So when he drifts, the only signal anyone gets is behavior, and by the time the behavior is visible, Dave is outside the ship.

That is the failure mode of every agent running on fog state. You can prompt it, you can watch its outputs, you can even give it a toolbelt. What you cannot do is answer the question an auditor, a regulator, or your own incident review will eventually ask: what did the system know, and when did it know it.

This is also why "most aligned to date" rings hollow to so many engineers. Alignment evaluated on outputs is theater when the state that produced those outputs is uninspectable. I think the skepticism in that Hacker News thread is healthy. A system you can only interview is a system you have to trust, and trust without inspection is exactly the thing engineering exists to remove.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>An agent whose state you cannot inspect is HAL 9000: you only learn what it believes from its behavior, when it is too late. Alignment claims on uninspectable systems are marketing, because the question "what did it know, and when" has no answer.</p></div>

## What to do on Monday

Pick the one agent workflow your team actually depends on. Sit down for an hour and write its state as a schema. Not the prompt, the state: what the agent knows at the start, what each step is allowed to add, and what must be true before anything ships.

You will find keys that mean the same thing with different names. You will find a field that three steps write and nobody validates. You will find at least one place where the agent proceeds on a guess. That hour is the cheapest audit you will ever run, and it works even if your framework is a pile of prompt strings held together with hope.

Then, when you touch the system next, move one workflow onto a typed state machine. LangGraph's `StateGraph` is fine. So is rolling your own with a dataclass and discipline. The tool is secondary.

Jonas compressed three years of agentic coding into three sentences, and the compression holds because each wave fixed the last wave's crack while introducing a subtler one. Typed state breaks the pattern, because it doesn't add a new way for the agent to act. It adds a way for you to see.

Bigger models made agents plausible. Typed state makes them accountable.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Write down the state schema for the agent workflow you depend on, find the fields nobody validates, and move one workflow onto typed state. The schema is the audit, and the audit is the job now.</p></div>
