Long-running agents force hidden assumptions to become software.

On July 21, 2026, engineer [Jonas Risbrandt described the progression of agentic coding](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz):

> “Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing.”

Risbrandt asked, “Haven't we just invented... a programming language?” and called agent frameworks programming languages for orchestrating “unreliable semantic functions.” He meant model steps that reason over meaning and may vary between runs. Production still needs stable rules around that uncertainty.

Three days later, Anthropic, the company behind Claude, [announced Claude Opus 5](https://www.anthropic.com/news/claude-opus-5) for long-running, multi-step agents. The vendor said a pre-deployment automated behavioral audit found it to be “our most aligned model to date.” Its [Hacker News discussion](https://news.ycombinator.com/item?id=49038433) drew over 1,700 points, attention rather than validation.

I think the gap is production authority. A model can score well in evaluation while a workflow publishes a stale revision under an old approval. Typed state gives that action an inspectable record of the exact version, evidence, and approval accepted before execution.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Long agent runs accumulate hidden assumptions. Typed state records which facts and approval authorized one action.</p></div>

## Start with the authority to publish

Consider this article's content-production card. It must say “over 1,700 points,” pass fact-checking, receive human approval, and publish only while that revision remains current. The design question is which exact record earns permission to publish.

By typed state, I mean a record with defined fields and allowed values, persisted beyond a model call and checked while the program runs. A transition guard then decides whether that stored record may advance. Here, the record includes a version, revision identifier, content hash, which is a fingerprint of the text, source-verification status, and the revision and hash a person approved.

The publish request also carries an idempotency key, a stable identifier for one external action. This pseudocode uses [Pydantic, a Python data-validation library](https://docs.pydantic.dev/latest/concepts/models/), at the boundary:

```python
CardStatus = Literal[
    "ideas_inbox", "approved", "research", "draft", "slop_review",
    "fact_check", "persona_panel", "design", "human_approval",
    "publish", "done", "escalated",
]


class CardState(BaseModel):
    card_id: str
    version: int
    status: CardStatus
    revision_id: str
    content_hash: str
    approved_revision_id: str | None
    approved_content_hash: str | None
    sources_verified: bool


class PublishRequest(BaseModel):
    card_id: str
    expected_version: int
    revision_id: str
    content_hash: str
    idempotency_key: str


def accept_publish(raw: dict) -> Decision:
    request = PublishRequest.model_validate(raw)

    with db.transaction():
        current = CardState.model_validate(
            db.cards.for_update(request.card_id)
        )
        prior = db.outbox.get(request.idempotency_key)

        if prior:
            same_request = prior.request_hash == stable_hash(request)
            if same_request is False:
                db.events.insert("idempotency_conflict", request, current)
                return Decision.rejected("action key already used")
            return Decision.accepted(prior)

        allowed = all((
            request.expected_version == current.version,
            request.revision_id == current.revision_id,
            request.content_hash == current.content_hash,
            current.revision_id == current.approved_revision_id,
            current.content_hash == current.approved_content_hash,
            current.sources_verified,
            current.status == "human_approval",
        ))

        if allowed is False:
            db.events.insert("publish_rejected", request, current)
            return Decision.rejected("stale or unauthorized state")

        db.outbox.insert_once(
            key=request.idempotency_key,
            request_hash=stable_hash(request),
            payload=request,
        )
        db.cards.advance_if_version(
            request.card_id,
            expected_version=request.expected_version,
            status="publish",
        )
        return Decision.accepted()
```

`model_validate` checks both incoming data and stored state at runtime. The transaction locks the current row before comparing versions, revisions, and hashes. It retains rejected attempts and records pending publish work in an outbox table during the same commit. On retry, the idempotency key returns the existing action instead of creating another one.

The stale score can no longer arrive through an older revision and inherit a newer approval. Typed state cannot prove that a source is true. It proves that the verified, approved revision is the one allowed to act.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The authority record binds approved content to the current stored version. Stale requests are rejected before publication, while retries return the existing action.</p></div>

## Replay the same card through four waves

That boundary makes the earlier architectures easier to judge. Each wave gave the content card more capability, but only the fourth made its accepted state explicit and enforceable.

### Prompt

A prompt is a natural-language instruction that tells a model what result to pursue and which constraints to respect.

```text
Research the article, draft it, fact-check it, and publish after approval.
For a changing Hacker News score, use “over 1,700 points.”
```

A demo can run on this. Production incidents add clauses about sources, revisions, kickbacks, and approval. The prompt wears a toolbelt, yet “approved” does not bind a reviewer to the exact bytes that will ship.

### Loop

A loop lets the model choose an action, inspect the result, and repeat until it reaches a stop condition.

```python
while card.status not in {"done", "escalated"}:
    action = model.choose(history)
    result = tools.run(action)
    history.append(result)
```

The history may contain an exact score, its correction, a revised paragraph, and an approval message. It preserves sequence but does not declare authority. A later pass can retrieve the stale score and keep moving. I think the danger is simple: corrupted state can resemble successful progress.

### Graph

A graph represents the workflow as named nodes connected by directed edges, making the route back after a failed check visible.

```text
research → draft → fact_check → human_approval → publish
             ↑          |
             └─ kickback┘
```

The graph reveals where work went, but not which source snapshot reached `fact_check` or whether approval still matches the current revision. Each node can hide a prompt and a loop with ambiguous message state.

[LangGraph, a graph-orchestration framework from LangChain](https://docs.langchain.com/oss/python/langgraph/graph-api), supports schemas for its shared application state. [Inngest's AgentKit, a TypeScript multi-agent library, said its routing used a “fully typed state machine” in March 2025](https://news.ycombinator.com/item?id=43426164). These are convergence signals, not proof of broad adoption. A route remains unsafe when teams fail to check incoming values, store accepted state, or guard transitions against that record.

### Typed state

Typed state turns the same card into an accepted record that software can test at every move:

```text
candidate → validate shape → lock current record → compare authority
                                                   ├─ reject + retain event
                                                   └─ accept + write action
```

I think typed state is different because it can refuse stale or unauthorized state. Prompts, loops, and graphs organize work around the model; typed state places a deterministic acceptance boundary around the facts and authority that work produces.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prompts express intent, loops repeat work, and graphs expose routing. Typed state adds the checked record that tells software which version may act.</p></div>

## Model evidence stops at the system boundary

Anthropic's Opus 5 claim describes behavior during a pre-deployment automated audit. It cannot tell an incident reviewer which article revision reached production or which approval applied at that moment. I think alignment theater begins when teams present model-level evidence as proof of a production action.

The missing record belongs inside an AI Operating Model, meaning the owners, evidence, decisions, and controls around an AI system. Engineering owns the schema and transaction; the business or risk owner defines what makes `publish`, `grant_access`, or `release_payment` legal. Without that agreement, verification debt grows because the system assumes more than the team can later prove.

The direction of regulation reinforces the need for durable evidence. The [European Union's AI Act, a law adopted in 2024](https://eur-lex.europa.eu/eli/reg/2024/1689/oj), requires high-risk AI systems to support automatic event logging under Article 12 and deployers to retain controlled logs under Article 26(6). The European Commission's [current timeline](https://digital-strategy.ec.europa.eu/en/policies/regulatory-framework-ai) extends rules for the high-risk uses listed in Annex III to December 2, 2027.

Those provisions neither classify a content pipeline as high risk nor prescribe typed state. The engineering lesson is narrower: when an agent alters an authoritative system, retained transitions provide evidence a transcript cannot reliably supply.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Model audits describe behavior under test. Production accountability needs a separate record of the state, owner, and approval behind each live action.</p></div>

## The old craft returns at one boundary

Type systems have supplied reliable refusal for decades. Computer scientist Robin Milner's [1978 paper](https://doi.org/10.1016/0022-0000%2878%2990014-4) helped formalize which values belong where. Static checking catches mismatches before code runs. Model output arrives during execution, so runtime validation must meet it at the acceptance boundary.

[Ruby on Rails 1.0, released in December 2005](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh), was a web framework that used conventions and [database migrations](https://guides.rubyonrails.org/active_record_migrations.html) to make stored structure versioned and reviewable. Migrations were not strong typing. The shared craft move was making structural assumptions explicit rather than scattering them through application logic.

Typed state also makes reversibility precise. An expected-version check blocks stale moves, while retained events or immutable snapshots support restoration. An idempotency key prevents duplicate action on retry but cannot unsend an email or revoke a permission, so external effects still need a correction path. My take is that reversibility becomes credible when those limits live in the state machine.

On Monday, choose one agent with external write access. Ask its engineering lead and system owner to spend 30 minutes naming one forbidden transition. Here, it is `human_approval` to `publish` after the content hash changes.

Store the smallest contract that enforces that rule beside the code, then time-box a two-week pilot with two engineers. Its acceptance tests are concrete:

```text
stale revision     → rejection event, no publish intent
approved revision  → one publish intent
retry after crash  → existing action, no duplicate publish
```

Run an incident review from persisted events alone. The team should identify what the agent accepted, why the guard allowed or rejected the move, and which external action followed. If that requires reconstructing a transcript, the verification debt remains unpaid.

A one-shot classifier that only labels an input may need a lighter record. The control should follow the consequence. I don't know which framework will dominate, but I think state contracts will become standard review artifacts for write-capable agents by the end of 2027. If teams can pass incident review and crash recovery using step-by-step run logs alone, that forecast is wrong.

Risbrandt wrote, “We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt.” That return is the craft required to let uncertain models operate where authority must be earned and explained.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Put one consequential transition under a reviewed state contract and test refusal before scale. Agent authority becomes trustworthy when the exact record that permitted an action is reviewable as software.</p></div>
