A Swedish engineer named Jonas Risbrandt posted on LinkedIn this week that agentic coding has gone through three waves and is entering a fourth. First prompts. Then loops, when one prompt was not enough. Then graphs, when loops were not enough. Now typed state. Each wave looked like a feature. Each one was actually a fault line.

The same week, Anthropic shipped Opus 5 with the claim "most aligned to date," and the Hacker News thread pulled over 1,700 upvotes. Most of the discussion was about the model. I think the model is the least interesting part. The interesting part is what Jonas named: the frameworks are converging on smaller loops with typed state, and that convergence says more about where this industry is going than any benchmark.

I tried to write this piece as a victory lap for graph frameworks, since I have recommended them to clients. I couldn't. The more honestly I looked at the systems I have helped ship, the more Jonas's four waves read like a confession. So let me confess, using one example the whole way through: an invoice agent, the kind a mid-size company actually runs. It reads incoming invoices, matches them to purchase orders, flags exceptions, and posts the rest to the ledger.

## Four waves, one invoice

The four waves are easiest to see as the same task rebuilt four times.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>One invoice agent, rebuilt four times. The prompt wore a toolbelt. The loop hid state corruption inside a growing transcript. The graph hid the loops inside nodes. Typed state is the first version where you can see what the agent knows.</p></div>

**Wave one: the prompt.** You write a long system prompt. "You are an invoice processor. Extract the vendor, the amount, the PO number. Call the lookup tool. If the amounts match, approve." The prompt grows a toolbelt, and it works in the demo. Then a credit note arrives with a negative amount, the model approves it anyway, and you discover the failure at month-end close. The prompt had no place to put what it learned between steps, so everything lived in a growing wall of text the model skimmed. I have watched a system prompt grow past 4,000 words. Past a certain length it stops being a specification and becomes a wish.

**Wave two: the loop.** ReAct, from a 2022 research paper, gave the pattern a name: the model reasons, acts with a tool, observes the result, and repeats. Thought, action, observation, around and around until done.

```python
while not done:
    thought = model.think(transcript)
    action  = model.act(transcript)      # call lookup_po(), post_to_ledger()
    result  = run(action)
    transcript += [thought, action, result]
```

Better. But the state of the world now lives inside `transcript`, an append-only pile of prose. When the agent matched the wrong PO on invoice 41 of 200, the evidence sat somewhere in the middle of a 60,000-token transcript that nobody read. The loop hid the corruption inside history.

**Wave three: the graph.** LangGraph and its peers said: stop hoping one loop generalizes. Draw the flow as a graph of nodes, one node to extract, one to match, one to approve, with edges for the exceptions. The core class is even called `StateGraph`. This was real progress, because it forced you to name the steps. But in practice the graph hid the loops. Each node ran its own little ReAct loop, state passed between nodes as an untyped dictionary, and a typo in a field name (`po_number` versus `poNumber`) became a bug that compiled fine and failed silently at 09:14 on a Tuesday. The diagram looked like engineering. The dictionary underneath it was still a wish.

**Wave four: typed state.** The fix is almost embarrassingly old. You declare the shape of what the agent carries, in code, with a type. In Python, a `TypedDict` does this: it says a dictionary must have exactly these fields, of exactly these types.

```python
class InvoiceState(TypedDict):
    vendor: str
    amount: Decimal
    po_number: str | None
    match_confidence: float
    approved: bool
    exception_reason: str | None
```

Now the invoice agent has a skeleton. Every node reads and writes this shape. A missing field is an error you can catch. An audit means reading the state, not excavating a transcript. I should be honest about the limits: a `TypedDict` is checked by your editor and your type checker, and Python will not stop a determined model from writing garbage into it at runtime. You still validate at the boundaries. But the contract exists, and it is written down, and that changes everything about how the system fails.

## Why this wave is different

Every previous wave hid the failure below it. This one exposes it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Workflow state is plumbing. Agent state is cognition. Typed state turns the agent's working memory into something you can diff, review, and roll back, which is what makes reversibility a property of the system instead of a vibe in the prompt.</p></div>

Here is the distinction I wish someone had handed me two years ago. Workflow state is plumbing: which step are we on, what ran, what is next. Tools like Temporal have solved plumbing for years. Agent state is cognition: what does the agent currently believe about this invoice, this vendor, this exception. The first is where the system is. The second is what the system thinks. Typed state matters because it is the first wave that makes cognition legible.

That legibility pays down three debts at once. The verification debt I wrote about in March: you can finally check what the agent carried, field by field, instead of trusting a summary. Reversibility, from my Q1 post: when state is a typed snapshot, rolling back means restoring the snapshot, and reversibility becomes a property of the state machine rather than a vibe in the prompt. And the operating model question: an agent whose state you can inspect is an agent you can put a name and an owner next to.

The craft move underneath is one we have seen before. Rails made web apps possible for ordinary teams in 2005 by making structure explicit: convention over configuration, the schema in a migration file, the framework assuming the shape so you didn't have to invent it. Typed state does the same for agent systems in 2026. Strong typing is the oldest craft discipline we have in software. We are rediscovering it because we finally built systems strange enough to need it again.

It reminds me of the Voight-Kampff test in Blade Runner, the interview that tells a replicant from a human by measuring responses instead of trusting appearances. Typed state is the Voight-Kampff test for agents. The demo always looks aligned. The state is where you find out.

## What breaks without it

The failure mode is impressive systems held together by habits nobody could defend in a review.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Without typed state you get alignment theater: the model passes its evaluations while the system around it corrupts state nobody can audit. Model-layer alignment and system-layer accountability are different problems, and the second one is yours. The EU AI Act's record-keeping obligations make that concrete.</p></div>

Opus 5's "most aligned to date" claim is probably true at the model layer. I believe Anthropic means it. But alignment at the model layer and accountability at the system layer are different problems. A well-aligned model inside an untyped graph still produces a stateful mess nobody can audit, and when the invoice agent approves the wrong credit note, the model's alignment score is not evidence in your incident review. The state is.

This is where regulation stops being abstract. The EU AI Act's record-keeping obligations for high-risk systems require you to keep logs that let you reconstruct what an automated system did and why. "The transcript was 60,000 tokens and the answer is somewhere in the middle" is a reconstruction nobody can defend. A typed state transition log, this field changed from this to this at this step, is exactly the artifact a reviewer, an auditor, or a regulator asks for. In my experience the teams that will comply cheaply are the ones whose state was already legible for engineering reasons.

There is a next fault line visible here, and I will name it even though I don't know how fast it arrives. Typed state at one agent becomes shared typed state at many agents, a knowledge graph of what the fleet believes. The agent forgets between runs. The graph does not. The unauditable single agent becomes the unauditable shared memory, and the first company to corrupt that shared memory at scale will teach the rest of us why typed state was necessary and insufficient.

## What to do on Monday morning

One agent, one schema, two engineers, two weeks.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Pick one production agent. Write down its state as a typed schema. Diff the schema against what the agent actually carries at runtime. Put one named engineer on the schema and route changes through review like any other contract.</p></div>

Don't rewrite the platform. Pick the agent that scares you most, the one whose failure would reach a ledger, a customer, or a regulator. Have two engineers spend two weeks on one question: what does this agent carry? Write it down as a schema, the way I sketched `InvoiceState` above. Then instrument one production run and diff the schema against reality. In my experience the agent carries two or three times the fields you declared, plus a few you didn't know existed. That diff is your verification debt, made visible and therefore payable.

Then treat the schema the way you treat a database migration. One named engineer owns it. Changes go through review like any other contract. When someone wants to add a field, the question "does the agent need to believe this" gets asked out loud, in the open, before the field exists.

I don't know whether typed state is the last wave. I suspect it is the first honest one, and honesty in engineering tends to compound. Rails did not end web frameworks. It ended the excuse that structure was optional.

The models will keep getting better. That is their job. Making the system legible enough to trust is yours.
