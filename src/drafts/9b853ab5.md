On July 21, 2026, engineer [Jonas Risbrandt described the recent arc of agentic coding](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz) in one LinkedIn post:

> “Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state, control flow, persistence, retries, error handling, observability, reusable components, and testing.”

He then asked, “Haven't we just invented... a programming language?” My take: the joke identifies a production boundary. Prompts, loops, and graphs organize action without ensuring that a team can name the facts accepted first. Typed state gives those facts a defined place to live.

Three days later, Anthropic, the company behind Claude, [announced Claude Opus 5](https://www.anthropic.com/news/claude-opus-5) for long-running, multi-step agent work. Anthropic said a pre-deployment behavioral audit found it to be “our most aligned model to date,” while its [discussion on Hacker News, a technology forum](https://news.ycombinator.com/item?id=49038433), drew over 1,700 points. I think the timing sharpens the question: a better model test cannot tell an incident team which document revision authorized a production action.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Model behavior and production accountability sit at different layers. Typed state matters because it turns the facts and authority behind an agent action into something a system can inspect and enforce.</p></div>

## One access request through four waves

Consider `AR-842`, a contractor's request for 30 days of read access to a production analytics system. An agent reads the form, checks approval, and calls the company's identity and access management (IAM) service, the system that grants and revokes permissions. In this hypothetical, an ambiguous sentence can grant a real account access.

### Prompt: the instruction carries the rules

A prompt is a natural-language instruction that describes the intended outcome. The first version might be this:

```text
Read access request AR-842. Confirm that the data owner approved it,
then grant the requested permission. Ask for clarification if needed.
```

This works until the policy grows clauses about expiry dates, approver roles, document revisions, and forbidden permissions. The prompt starts wearing a toolbelt because prose carries the process and its exceptions. I think prompts are a good place for judgment, but a fragile place for rules that must hold every time.

### Loop: progress hides in the conversation

A loop repeats a model decision, a tool action, and an observation until a stop condition is met. It lets the agent gather missing information instead of trying to finish everything in one response:

```python
messages = [access_request]
while not finished(messages):
    action = model(messages)
    observation = run_tool(action)
    messages.extend([action, observation])
```

Suppose revision 2 requested write access and received a message saying “approved.” Revision 3 reduces the permission to read but changes the expiry date, so it needs fresh approval. Both forms and the old message remain in the conversation, with no formal link between approval and revision. A fluent model may continue with the wrong pairing, leaving the error inside the transcript.

### Graph: the route becomes visible

A graph represents work as nodes connected by directed edges. It can show the allowed route and send an incomplete request back for correction:

```text
parse form -> check policy -> obtain approval -> prepare grant -> call IAM
                       \-> request correction -/
```

Engineers can now inspect the route. Yet a node may still contain a prompt and a loop, then write `approved: true` into a free-form record. The diagram cannot show how that node decided an old approval covered the new form.

[LangGraph, LangChain's graph-orchestration framework](https://docs.langchain.com/oss/python/langgraph/graph-api), already supports shared state schemas, so graphs are not inherently untyped. The gap lies between declaring a shape and enforcing it when model output becomes stored state.

### Typed state: acceptance moves to the boundary

Typed state is a stored record with defined fields and allowed values. [Python type annotations are not enforced at runtime](https://docs.python.org/3/library/typing.html), so declaring a schema covers only part of the boundary. Here, [Pydantic, a Python library for runtime validation](https://docs.pydantic.dev/latest/concepts/models/), checks the model's proposed update before the system accepts it:

```python
class GrantCandidate(BaseModel):
    request_id: str
    form_revision: int
    approved_revision: int
    approver_role: Literal["data_owner"]
    resource: str
    permission: Literal["read"]
    expires_at: datetime


def prepare_grant(raw: dict, stored):
    candidate = GrantCandidate.model_validate(raw)
    require(stored.phase == "approved")
    require(candidate.request_id == stored.request_id)
    require(candidate.form_revision == stored.form_revision)
    require(candidate.approved_revision == stored.form_revision)
    return append_event_and_update(
        stored, "grant_pending", candidate,
        expected_version=stored.record_version,
    )
```

Runtime validation checks the candidate's shape and allowed values. Transition guards compare it with the persisted access record, meaning data kept beyond the current model call. The expected-version check rejects a stale write; `append_event_and_update` represents a transaction that retains an immutable event and updates the current snapshot. Together they reject revision 3 when its approval points to revision 2.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The prompt states intent, the loop repeats work, and the graph exposes routes. Typed state adds an enforced acceptance boundary, so an old approval cannot quietly attach itself to a new request revision.</p></div>

## Old discipline, new boundary

Risbrandt described agent frameworks as programming languages for orchestrating “unreliable semantic functions.” Here the semantic function is the model call: it works with meaning, so the same input can produce different output. Typed state places deterministic acceptance rules around that useful uncertainty.

Software has used type discipline for decades. Computer scientist Robin Milner's [1978 paper on type polymorphism](https://doi.org/10.1016/0022-0000%2878%2990014-4) helped establish ways to express and check which values belong where. Ruby on Rails, the web framework whose [version 1.0 arrived in December 2005](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh), gave database structure similar visibility through [migrations](https://guides.rubyonrails.org/active_record_migrations.html) that travel with code. Migrations are not strong typing, but both practices make structural assumptions reviewable.

[The workflow infrastructure company Inngest presented AgentKit](https://news.ycombinator.com/item?id=43426164), a TypeScript multi-agent library, with a fully typed state machine for routing in March 2025; LangGraph documents shared state schemas. These examples indicate a direction rather than broad adoption. I don't know which framework will dominate, and I think that matters less than whether its state contract survives a model call, a retry, and an incident review.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state brings a decades-old software habit to agent systems: uncertain output meets an explicit contract before it becomes accepted production data. Framework choice is secondary to whether that contract is checked and retained.</p></div>

## Alignment cannot supply the missing record

Typed state has strict limits. Runtime validation can require an expiry date and an allowed approver role. It cannot prove that the source document is true or that the permission is wise. Those questions still need evidence, identity controls, and human judgment.

Nor does typed state make an external action reversible. An expected-version check can reject stale updates; earlier-state inspection requires append-only events or immutable snapshots. For access, the state machine can encode and test a compensating revoke transition. An [idempotency key](https://docs.stripe.com/api/idempotent_requests), a unique identifier an endpoint uses to recognize a retry, can prevent a duplicate grant but cannot undo the first one.

This is where model alignment can become theater. Anthropic's pre-deployment audit may be valuable within its scope, but it does not record what a deployed agent later accepted. I think an AI Operating Model, meaning the owners, evidence, decisions, and controls around AI work, remains incomplete when state lives mainly in conversation logs. The gap between system assumptions and available proof is verification debt.

The European Union's [AI Act, Regulation (EU) 2024/1689](https://eur-lex.europa.eu/eli/reg/2024/1689/oj), points in the same direction. Article 12 requires automatic event logging for specified high-risk AI systems, and Article 26(6) requires deployers to retain logs under their control. The principal rules for high-risk uses listed in Annex III began applying on August 2, 2026. The law neither prescribes typed state nor makes every access workflow high risk, but it shows why consequential systems need records beyond the prompt.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Types constrain accepted data; they do not establish truth or reverse an external effect. Durable history, evidence, identity controls, and recovery mechanisms turn a state contract into an operating model that can withstand scrutiny.</p></div>

## Start with the action you would regret

On Monday, choose one agent action with an external effect, such as an access grant, payment, deployment, or customer message. Ask the system owner and a senior engineer to write the smallest state contract that identifies the accepted facts, the authority, the attempted transition, and the evidence to retain.

Then test the refusal paths: use approval for the wrong revision, remove the expiry date, retry after a timeout, and crash after `grant_pending` is stored but before the identity service replies. Invalid transitions should fail before the external call, retained history should explain why, and retries should follow the service's idempotency contract.

Keep the scope narrow. A one-shot classifier with no external effect may need only validated input and output records. A long-running agent with write access needs persisted state, transition guards, retained history, and recovery proportionate to the consequence. I think that distinction is more useful than declaring every agent a state machine by default.

Risbrandt ended with the line, “We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt.” Reintroducing code restores responsibility. Agent systems become production software when they can defend what they accepted and refuse what they cannot.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Begin with one consequential action and design its refusal path before expanding the platform. The serious engineering move is to make accepted state, authority, history, and recovery reviewable in code.</p></div>
