On July 21, engineer Jonas Risbrandt [described agentic coding’s progression](https://www.linkedin.com/posts/jonas-risbrandt-8309263_i-find-the-evolution-of-agentic-coding-slightly-activity-7485292345890865152-xymz): “Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state...” He asked, “Haven’t we just invented... a programming language?”

Three days later, Anthropic [said](https://www.anthropic.com/news/claude-opus-5) a pre-deployment audit found Opus 5 to be “our most aligned model to date.” Its [Hacker News thread](https://news.ycombinator.com/item?id=49038433) drew over 1,700 points. I think the timing exposes the fault line: model behavior can improve while production teams still cannot prove which facts authorized an action after a retry.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Model audits leave production teams needing a durable record of an agent’s authority.</p></div>

## Follow one fact through four waves

This article’s brief used an exact HN count. Fact-checking approved “over 1,700,” yet a later revision restored the stale figure. Call them `v7` and `v8`; only `v8` may reach publishing.

A **prompt** is the instruction sent to the model:

```text
Research, draft, fact-check, and publish with approved wording.
```

The policy never stores the approved revision. The prompt is wearing a toolbelt.

A **loop** repeats model reasoning and tool calls:

```python
while card.open:
    result = agent.run(history)
    history.append(result)
```

The history preserves both `v7` and `v8`. I think a larger context retains the disagreement while giving the publish boundary no authoritative value.

A **graph** names the steps and routes between them:

```text
draft -> fact_check -> approved -> publish
   ^          |
   +-- revise-+
```

The route is visible, while a node can still hide the loop and its mixed history. [LangGraph](https://docs.langchain.com/oss/python/langgraph/graph-api) supports shared schemas, so enforcement remains a write-boundary decision. A graph can resemble the Nostromo map in *Alien*: clear corridors, danger inside one room.

**Typed state** is a named record with required fields and allowed values. This pseudocode makes publication atomic and versioned:

```python
class PublishState(BaseModel):
    card_id: str
    revision_id: str
    approved_revision_id: str
    status: Literal["approved", "publishing", "published"]
    evidence_ids: tuple[str, ...]
    version: int

require(s.revision_id == s.approved_revision_id and s.evidence_ids)
with db.transaction():
    changed = db.cards.compare_and_set(
        id=s.card_id, version=s.version,
        status="approved",
        revision_id=s.revision_id,
        approved_revision_id=s.approved_revision_id,
        sources_verified=True,
        next_status="publishing", next_version=s.version + 1,
    )
    require(changed == 1)
    db.outbox.put_once(f"publish:{s.card_id}:{s.revision_id}", s.evidence_ids)
```

`BaseModel` validates incoming data while a type checker catches code misuse. Because the database comparison is versioned, one worker advances. The transaction binds accepted evidence to an outbox, a durable pending send that keeps one idempotency key across retries. A stale `v7` request leaves state unchanged and adds no outbox entry.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state gives the publishing boundary one checked revision to accept or reject.</p></div>

## Keep the engineering disciplines separate

Strong typing is among software’s oldest craft disciplines. It limits representable states while runtime validation checks model data. Because source review still judges truth, I think the engineering win is loud rejection at a known boundary.

In 2005, [Rails 1.0](https://rubyonrails.org/2005/12/13/rails-1-0-party-like-its-one-oh-oh) migrations made persisted changes explicit and reviewable in dynamically typed Ruby. Agent systems need that separate persistence contract beside typed state variants.

A durable workflow engine records where execution resumes. Accepted state records `v8`, its evidence, and the next legal move. A trace authorizes publication only if it reproduces that transition and evidence. I don’t know which orchestration framework will lead. The contract can outlast it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Types define allowed state, persistence protects it over time, and workflow history supports recovery.</p></div>

## Audit production authority

Anthropic scoped its claim to pre-deployment testing. Production accountability begins when model output crosses a write boundary. I think treating the first as proof of the second becomes alignment theater when an incident review cannot replay the authorized state and effect.

For an agent with write access, an AI operating model records who may write, which evidence authorizes action, what was delivered, and its correction path. Traces help diagnosis; this record carries authority.

For high-risk systems, [EU AI Act](https://eur-lex.europa.eu/eli/reg/2024/1689/oj) Articles 12 and 26(5) address event logging and deployer retention. A low-risk, one-shot classifier carries a lighter burden. Repeated writes need retrievable state and an explicit amendment transition.

Every unenforced prompt rule adds verification debt. Persisted transitions expose that debt and make reversibility a system property.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>An authority record connects accepted evidence to a production effect and its correction path.</p></div>

## Put one boundary under contract on Monday

Spend 30 minutes on `approved -> publishing`: record evidence, owner, retention and access, and the illegal condition in a contract diff that engineering, product, and risk can inspect.

First, a `v7` request must remain available for audit, cause no transition or outbox entry, and leave status and version unchanged. A `v8` request must atomically enter `publishing` with one outbox row. Kill the worker, retry elsewhere, and verify one external effect. Then test `published -> amendment_pending` while retaining the original effect ID.

Keep this narrow enough for two engineers to prove within two weeks. My take is that by the end of 2027, teams granting agents write authority will standardize state contracts before migrating frameworks. If traces alone can reproduce authorized effects and evidence, the prediction fails.

Jonas wrote, “We replaced the code with a prompt, and then slowly started reintroducing the code around the prompt.” External authority should begin only when evidence-backed accepted state enters an atomic transition and produces one recoverable effect.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Prove one write boundary under rejection, retry, and correction before expanding agent authority.</p></div>
