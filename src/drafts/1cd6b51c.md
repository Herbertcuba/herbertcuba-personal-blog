I tried to maintain a document-processing agent last year. By month three, the system prompt was thousands of words long. It had instructions for every edge case we had ever hit, including one that only occurred when a PDF had exactly two blank pages followed by a table. I do not know if that was a real pattern or a superstition. The prompt was our only source of truth, and it was a haunted house.

## A system prompt is not a system

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Agentic coding has gone through three waves (prompts, loops, graphs) and is entering a fourth: typed state. Each wave looked like a feature. Each one was actually a fault line. The industry is converging on typed state because it is the only way to make agent systems legible to the people who maintain them.</p></div>

A Swedish engineer named Jonas Risbrandt posted about this on LinkedIn recently. I cannot verify the post word-for-word (I am reconstructing from memory of a screenshot that circulated), and I cannot fully verify who Risbrandt is beyond his self-description as a Swedish engineer, but the substance matches what I have seen elsewhere: agentic coding has gone through three waves (prompts, then loops, then graphs) and is entering a fourth: typed state. His words, as best I can reconstruct them: "Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state."

The same week, Anthropic shipped Opus 5 with the claim "most aligned to date" and the Hacker News thread pulled over 1,700 upvotes and 1,300 comments. I think those two events are the same signal. The industry has stopped betting on bigger models and started betting on smaller loops with typed state.

## The four waves, one example

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The four waves are prompts, loops, graphs, and typed state. Each one hid the failure mode of the one below it. Typed state is the first wave that makes the failure mode visible instead of papering over it.</p></div>

Let me use one example throughout. A document-processing agent that reads invoices, extracts line items, and books them to the general ledger. It is the kind of agent every mid-size company has built by now.

**Wave one: prompts.** The prompt was the program. You wrote instructions, added tools, and hoped the model followed them. This worked for demos. It failed in production because the prompt became a junk drawer. Every incident added another paragraph. Every paragraph created new ambiguities. The prompt was doing the job of a schema, a state machine, and a runbook, and it was bad at all three.

```
You are an invoice processor. Read the invoice.
Extract vendor, date, total, and line items.
Call the booking tool for each line item.
If anything is unclear, ask the human.
```

**Wave two: loops.** A loop is when the agent runs the same "think, act, observe" pattern over and over until it is done. The most famous version of this is called **ReAct** (Reason + Act), a pattern from a 2022 research paper that said: let the model reason out loud about what to do, call a tool, read the result, then reason again. Every major framework shipped a version of this. LangChain, AutoGen, CrewAI, OpenAI's Assistants API — they all wrap a loop around the model.

```python
while not done:
    thought = model.reason(context)        # "The total looks wrong"
    action = model.act(thought)             # "I'll re-read the invoice"
    result = tools[action.name](action.args) # actual re-read
    context.append(result)                   # add result to history
```

The loop let the agent iterate, but the state lived in the message history, mutated in place, invisible to anyone who wanted to audit it. The loop hid state corruption. An agent could misread a total, book the wrong amount, and keep going because the error was just another message in the history. You could not answer "what did the agent believe when it called the booking tool" with a database query. You had to do archaeology on a chat log.

**Wave three: graphs.** A graph is when you draw your agent as nodes (steps) and edges (transitions) instead of one big loop. **LangGraph** is the framework that popularized this. You declare "extract from invoice, then validate, then book" as three connected nodes. You can branch on conditions ("if confidence is low, send to a human"), run things in parallel, and you can finally see the control flow on one page.

```python
graph = StateGraph(MessagesState)
graph.add_node("extract", extract_node)
graph.add_node("validate", validate_node)
graph.add_node("book", book_node)
graph.add_edge("extract", "validate")
graph.add_conditional_edges("validate", route_by_confidence)
graph.add_edge("book", END)
```

The graph made the control flow visible, but it hid the loops. A node could contain a loop, which contained a prompt, which contained a toolbelt. The graph was a map of a city where every building had a secret basement. You could see the roads. You could not see the plumbing. State was still smuggled through untyped message history, mutated in place, and the graph just gave you more places to lose it.

**Wave four: typed state.** This is where we are now. **Typed state** means the agent's state — what it knows and what it is doing — is declared as a structured type, like a schema in a database. In Python, you use `TypedDict` (a dictionary where keys and values have known types) or in LangGraph, you define a `State` class. Every transition between states is checked: you cannot move from "extracting" to "done" without passing through "validating".

```python
class InvoiceState(TypedDict):
    vendor: str | None           # None until extracted
    date: date | None
    total: Decimal | None
    line_items: list[LineItem]
    confidence: float
    status: Literal["extracting", "validating", "booking", "done", "failed"]
    error: str | None

def extract(state: InvoiceState) -> InvoiceState:
    # only valid from "extracting"
    if state["status"] != "extracting":
        raise IllegalTransition(f"cannot extract from {state['status']}")
    # ... actual extraction logic ...
    return {**state, "vendor": "Acme Corp", "status": "validating"}
```

Now the illegal transition is rejected. The state is a database row, not a vibe in a prompt. You can ask "what did the agent believe when it called the booking tool" and get a structured answer. You can replay the run. You can checkpoint it. You can roll it back.

## Why typed state is the engineering win

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Typed state is the engineering win because it makes the system legible. Legibility is what lets you verify, audit, and reverse. The same craft move that made Rails web applications tractable in 2005 is making agent systems tractable in 2026.</p></div>

In 2005, Rails made web applications tractable for small teams. The deeper craft move was the database schema becoming the legible center, versioned through migrations. Twenty-one years later, the same move is arriving for agents.

I think the important thing about Rails was not the scaffolding. It was that the schema became the contract. You could read one file and understand the shape of the data. You could diff two versions and understand what changed. Typed state does the same thing for agent cognition.

Reversibility becomes a property of the state machine, not a vibe in the prompt. If the agent is in state "booking" and the last transition was "validate -> book", you can replay it. You can checkpoint it. You can roll it back. That is not possible when the state is a thousands-of-words prompt and a chat log.

## What breaks without it

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Without typed state, you get a slot machine with a changelog. The failure ladder is: toolbelt prompt, corrupt loop, graph hiding loops, unauditable mess. Alignment at the model layer and accountability at the system layer are different problems.</p></div>

I have seen this pattern repeat across teams and codebases. The first wave ships a prompt wearing a toolbelt. The second wave ships a loop hiding state corruption. The third wave ships a graph hiding loops. The fourth wave ships a stateful mess nobody can audit.

The result is a slot machine with a changelog. You put a document in, you get a booking out, and you cannot explain why. When the auditor asks "how do you know the agent did the right thing", the answer is "we trained it to be aligned." That is alignment theater. "Most aligned to date" is a claim about a model's behavior during training evaluations. It says nothing about what your agent did in production at 3 AM on a Tuesday.

I think the confusion between model-layer alignment and system-layer accountability is the defining error of this moment. They are different problems. The second one is yours.

## Craft discipline is back

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Strong typing is the oldest craft discipline we have in software, finally rediscovered. The industry spent three years rediscovering that systems built on ambiguous state cannot be verified. Craft is catching up to capability.</p></div>

Type theory predates most of the people arguing about agents. We have had the discipline since the 1970s. The industry spent three years rediscovering that systems built on ambiguous state cannot be verified.

I do not know if typed state is the final wave. I suspect it is the first wave that does not hide the failure mode of the one below it. That is progress.

The strongest counter-argument is that short-lived agents do not need durable state. A one-shot classification task does not need a schema. I think that is true, and I also think it is the exception. Most agents worth building are long-running, multi-step, and stateful. The ones that are not are toys.

The next fault line is probably schema governance. Once every team has a typed state schema, we will argue about who owns it, how it evolves, and what happens when two agents disagree about the shape of the world. That is a better problem to have.

## What to do Monday morning

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Monday morning: pick one agent, declare its schema, diff it against reality, instrument one transition. This is a two-engineer, two-week instrumentation project, not a platform rewrite.</p></div>

Pick one agent in your system. The one that scares you the most. Write down its state schema. Five to ten lines. Diff it against the actual state the agent carries. The gap between the two documents is your verification debt, rendered visible.

Instrument one transition. Log the state before and after. Reject the illegal ones. See what breaks. That is the whole exercise. It takes two engineers two weeks. It is not a platform rewrite.

I tried to maintain the other kind. The prompt-as-junk-drawer, the loop-as-archaeology, the graph-as-basement. I do not want to do it again. Typed state is the first wave that lets you see the plumbing. That is the whole point.
