A Swedish engineer named Jonas Risbrandt posted this week that agentic coding has gone through three waves: prompts, then loops, then graphs, and now typed state. His words: "Then we realized one prompt was not enough, so we added loops. Then loops were not enough, so we introduced graphs. Now we are adding typed state."

The same week, Anthropic shipped Opus 5 with the claim "most aligned to date" and the Hacker News thread pulled over 1,700 upvotes and 1,300 comments. I think those two events are the same signal. The industry has stopped betting on bigger models and started betting on smaller loops with typed state.

<div class="chapter-tldr">The four waves are prompts, loops, graphs, typed state. Each one hid the failure mode of the one below it. Typed state is the first wave that makes the failure mode visible.</div>

## The four waves, one example

Let me use one example throughout. A document-processing agent that reads invoices, extracts line items, and books them to the general ledger. It is the kind of agent every mid-size company has built by now.

**Wave one: prompts.** The prompt was the program. You wrote instructions, added tools, and hoped the model followed them.

```
You are an invoice processor. Read the invoice.
Extract vendor, date, total, and line items.
Call the booking tool for each line item.
If anything is unclear, ask the human.
```

This worked for demos. It failed in production because the prompt became a junk drawer. Every incident added another paragraph. Every paragraph created new ambiguities. The prompt was doing the job of a schema, a state machine, and a runbook, and it was bad at all three.

**Wave two: loops.** ReAct gave us a shape: reason, act, observe, repeat. Every framework shipped a version. The loop let the agent iterate, but the state lived in the message history, mutated in place, invisible to anyone who wanted to audit it.

```
while not done:
    thought = model.reason(context)
    action = model.act(thought)
    result = tools[action.name](action.args)
    context.append(result)
```

The loop hid state corruption. An agent could misread a total, book the wrong amount, and keep going because the error was just another message in the history. You could not answer "what did the agent believe when it called the booking tool" with a database query. You had to do archaeology on a chat log.

**Wave three: graphs.** LangGraph and its cousins let you draw nodes and edges, branch on conditions, run agents in parallel. The graph made the control flow visible, but it hid the loops. A node could contain a loop, which contained a prompt, which contained a toolbelt.

```
graph = StateGraph(MessagesState)
graph.add_node("extract", extract_node)
graph.add_node("validate", validate_node)
graph.add_node("book", book_node)
graph.add_edge("extract", "validate")
graph.add_conditional_edges("validate", route_by_confidence)
graph.add_edge("book", END)
```

The graph was a map of a city where every building had a secret basement. You could see the roads. You could not see the plumbing. State was still smuggled through untyped message history, mutated in place, and the graph just gave you more places to lose it.

**Wave four: typed state.** The state is declared, versioned, and inspectable. The agent transitions between states, and every transition is checked against the schema.

```python
class InvoiceState(TypedDict):
    vendor: str | None
    date: date | None
    total: Decimal | None
    line_items: list[LineItem]
    confidence: float
    status: Literal["extracting", "validating", "booking", "done", "failed"]
    error: str | None

def extract(state: InvoiceState) -> InvoiceState:
    # only valid from "extracting"
    if state["status"] != "extracting":
        raise IllegalTransition(f"cannot extract from {state['status']}")
    ...
```

Now the illegal transition is rejected. The state is a database row, not a vibe in a prompt. You can ask "what did the agent believe when it called the booking tool" and get a structured answer.

<div class="chapter-tldr">Typed state is the engineering win because it makes the system legible. Legibility is what lets you verify, audit, and reverse. The same craft move that made Rails web applications tractable in 2005 is making agent systems tractable in 2026.</div>

## Why typed state is the engineering win

In 2005, Rails made web applications tractable for small teams. The deeper craft move was the database schema becoming the legible center, versioned through migrations. Twenty-one years later, the same move is arriving for agents.

I think the important thing about Rails was not the scaffolding. It was that the schema became the contract. You could read one file and understand the shape of the data. You could diff two versions and understand what changed. Typed state does the same thing for agent cognition.

Reversibility becomes a property of the state machine, not a vibe in the prompt. If the agent is in state "booking" and the last transition was "validate -> book", you can replay it. You can checkpoint it. You can roll it back. That is not possible when the state is a 4,000-word prompt and a chat log.

<div class="chapter-tldr">Without typed state, you get a slot machine with a changelog. The failure ladder is: toolbelt prompt, corrupt loop, graph hiding loops, unauditable mess. Alignment at the model layer and accountability at the system layer are different problems.</div>

## What breaks without it

I have now watched it happen at two companies. The first wave ships a prompt wearing a toolbelt. The second wave ships a loop hiding state corruption. The third wave ships a graph hiding loops. The fourth wave ships a stateful mess nobody can audit.

The result is a slot machine with a changelog. You put a document in, you get a booking out, and you cannot explain why. When the auditor asks "how do you know the agent did the right thing", the answer is "we trained it to be aligned." That is alignment theater. "Most aligned to date" is a claim about a model's behavior during training evaluations. It says nothing about what your agent did in production at 3 AM on a Tuesday.

I think the confusion between model-layer alignment and system-layer accountability is the defining error of this moment. They are different problems. The second one is yours.

<div class="chapter-tldr">Strong typing is the oldest craft discipline we have in software, finally rediscovered. The industry spent three years rediscovering that systems built on ambiguous state cannot be verified. Craft is catching up to capability.</div>

## Craft discipline is back

Type theory predates most of the people arguing about agents. We have had the discipline since the 1970s. The industry spent three years rediscovering that systems built on ambiguous state cannot be verified.

I do not know if typed state is the final wave. I suspect it is the first wave that does not hide the failure mode of the one below it. That is progress.

The strongest counter-argument is that short-lived agents do not need durable state. A one-shot classification task does not need a schema. I think that is true, and I also think it is the exception. Most agents worth building are long-running, multi-step, and stateful. The ones that are not are toys.

The next fault line is probably schema governance. Once every team has a typed state schema, we will argue about who owns it, how it evolves, and what happens when two agents disagree about the shape of the world. That is a better problem to have.

<div class="chapter-tldr">Monday morning: pick one agent, declare its schema, diff it against reality, instrument one transition. This is a two-engineer, two-week instrumentation project, not a platform rewrite.</div>

## What to do Monday morning

Pick one agent in your system. The one that scares you the most. Write down its state schema. Five to ten lines. Diff it against the actual state the agent carries. The gap between the two documents is your verification debt, rendered visible.

Instrument one transition. Log the state before and after. Reject the illegal ones. See what breaks. That is the whole exercise. It takes two engineers two weeks. It is not a platform rewrite.

I tried to maintain the other kind. The prompt-as-junk-drawer, the loop-as-archaeology, the graph-as-basement. I do not want to do it again. Typed state is the first wave that lets you see the plumbing. That is the whole point.
