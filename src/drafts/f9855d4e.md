Take a Swedish heat-pump company. A homeowner asks an AI assistant about service coverage, price and open slots. The assistant checks approved company data and books the visit. The homepage never loads.

I think websites will keep serving people for a long time. Their old role as the main hub for company knowledge is already fading. The asset underneath the page now needs more attention. I call it a knowledge catalog: a verified set of answers that software can use safely.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The website is becoming one possible view of your company knowledge. Customers and their agents may use that knowledge without visiting the view.</p></div>

## Search became a conversation, then an action

The click has been weakening for years. A [2024 SparkToro and Datos study](https://sparktoro.com/blog/2024-zero-click-search-study/) found that 58.5% of US Google searches and 59.7% of EU searches ended without one. The figures also include abandoned and changed queries, so AI did not cause the whole number.

The AI-specific data is sharper. [Pew Research Center](https://www.pewresearch.org/short-reads/2025/07/22/google-users-are-less-likely-to-click-on-links-when-an-ai-summary-appears-in-the-results/) found clicks on traditional results in 8% of visits with an AI summary, compared with 15% without one. Cited sources received clicks in 1% of visits.

Risher attributes "2027 is the year of the agents" to Sundar Pichai. No primary Google source confirms that wording. The direction has firmer evidence: Google announced its open [Agent2Agent protocol, A2A](https://developers.googleblog.com/en/a2a-a-new-era-of-agent-interoperability/), at Cloud Next in April 2025 with more than 50 technology partners. A2A lets agents coordinate work across systems.

An agent can check heat-pump coverage and return a confirmed slot. [ServiceTitan already offers AI booking assistants](https://www.servicetitan.com/blog/webinar-recap-ai-virtual-agents-call-booking) for field-service companies. I think rankings remain useful, but mention rate and AI share of voice reveal whether a company enters the answer at all.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Search is keeping more answers inside the interface, and agents can continue from an answer into an action. Company data must be usable before a customer reaches the website.</p></div>

## A knowledge catalog is an approved answer set

Risher describes a knowledge catalog as a verified dataset about a business that an agent can use. The term comes from his framing, and a Google product attribution has not been verified. It still gives us a plain label for a real engineering need.

For the heat-pump company, the catalog could hold service regions, pricing rules and booking constraints. Each entry needs an owner, a source and an expiry date:

```yaml
service: heat_pump_installation
region: SE-C
price_from_sek: 89000
standard_installation_included: true
valid_until: 2026-12-31
answer_owner: pricing@company.example
source: approved_price_list_v12
```

These values are illustrative. When the agent receives `price_from_sek`, it also gets the region, validity period and approved source. An expired entry withholds the price and routes the customer to a person.

Risher calls content "training data for the future internet." Runtime retrieval is often more accurate: the model fetches the current catalog entry when asked and uses it within an allowed scope.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A knowledge catalog is a controlled set of company answers with ownership and expiry built in. The agent retrieves a current answer and can refuse when the supporting data has expired.</p></div>

## Structured content gives the agent less room to guess

A paragraph can hide several facts. Structured content separates them into named fields with types. `price_from_sek` is an integer. `valid_until` is a date. `standard_installation_included` is a boolean, either true or false.

This fits [ReAct](https://arxiv.org/abs/2210.03629), short for reasoning and acting. The model chooses a step, calls a tool, inspects the result and repeats. Our agent reads the postcode, queries the catalog and checks expiry before booking.

[LangGraph](https://langchain-ai.github.io/langgraph/reference/graphs/) builds this workflow as a graph. A `StateGraph` defines its steps and transitions. A Python `TypedDict` describes the keys carried between steps. It helps the type checker, while runtime validation still needs explicit checks or a schema library.

```python
from typing import TypedDict
from langgraph.graph import StateGraph

class BookingState(TypedDict):
    postcode: str
    catalog_entry: dict | None
    outcome: str

workflow = StateGraph(BookingState)
workflow.add_node("lookup_catalog", lookup_catalog)
workflow.add_node("validate_entry", validate_entry)
workflow.add_node("book_slot", book_slot)
```

The names expose the safety boundary. `validate_entry` can block an expired price before `book_slot` runs. I think structured content becomes production infrastructure when expected behavior is this easy to test.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Structured fields turn company knowledge into typed inputs that an agent workflow can check. ReAct supplies the loop, while LangGraph, StateGraph and TypedDict make the steps and shared state easier to inspect.</p></div>

## A headless CMS gives you a head start

A headless CMS stores content separately from the page that displays it. The website reads that content through an API. An app, chatbot or agent can read the same approved entry through another controlled interface.

If the heat-pump company's prices and regions already exist as fields in Contentful, Sanity or Optimizely, the raw material is there. The team can expose a read-only catalog tool without scraping marketing copy first.

Meaning and ownership remain hard. Does the starting price include labor? Who changes the region when crews reach capacity? A platform cannot decide that for the organization.

I think many teams bought headless CMS for frontend freedom and gained an unexpected advantage for the agent web. Its size depends on the content model. I explored the architecture in [The quiet truth about headless CMS](/posts/the-quiet-truth-about-headless-cms/).

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A well-modeled headless CMS already separates knowledge from presentation and exposes it through APIs. That gives teams a faster route to agent access, provided the fields are current and owned.</p></div>

## The Digital Singularity was always heading here

Generative UI, or GenUI, creates an interface for the current request. Google's [A2UI project](https://developers.googleblog.com/introducing-a2ui-an-open-project-for-agent-driven-interfaces/) lets agents send interface descriptions to different renderers.

Our heat-pump customer may get a comparison card, a calendar or a voice answer. Each can call the same catalog entry.

That follows [The Digital Singularity Shift](/books/the-digital-singularity-shift/): interfaces become temporary responses to individual intent. Durable work moves into the knowledge and rules underneath them.

## Choose help by incentives, ownership and exit rights

The consultancy that built your content platform may be the best place to start because it knows the model and approval paths. Valtech is one example. The partner networks around [Contentful](https://www.contentful.com/partners/), [Sanity](https://www.sanity.io/partners/) and [Optimizely](https://www.optimizely.com/partners/) include many more.

Platform expertise can save months. It can also narrow the answer when a supplier earns more from another license. My take is to ask where the dataset lives, how it can be exported and how agent access is revoked. Then ask how the partner gets paid.

The incumbent partner is a strong choice when it accepts those terms. An independent consultancy becomes safer when the architecture crosses several platforms. Your organization should own the schema, test set and access policy either way.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Existing CMS partners can move quickly because they know the content estate. Choose one that leaves the catalog portable, keeps access reversible and earns money from the work rather than a forced product choice.</p></div>

## Build one catalog slice in eight weeks

Start with twenty questions about one domain. For the heat-pump company, use coverage and starting price. Assign a content owner and engineering lead, with pricing and operations in a weekly review.

An eight-week pilot needs a small acceptance bar. Every priority question must return a current answer, name its source and refuse expired data. Release a read-only tool first. Add booking after the answer path is stable.

Test the questions each month across the assistants your customers use. Measure the share that return a current, approved answer with a source. Keep mention rate and AI share of voice beside rankings. [Optimizely already offers this monitoring](https://www.optimizely.com/agents/competitive-ai-share-of-voice-agent/), but a spreadsheet is enough for the first run.

Compliance still requires policy, access controls and legal judgment. A catalog adds ownership evidence and a revocation path. It helps govern agent answers without pretending that a content model solves regulation.

The next interface may be generated in seconds. Your company's answer should be approved before it appears.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Use eight weeks to prove one narrow catalog with named owners, expiry handling and a repeatable question set. Expand after the answer path is current, attributable and safe to revoke.</p></div>
