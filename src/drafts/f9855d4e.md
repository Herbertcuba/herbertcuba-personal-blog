A customer can compare a heat-pump installation, check whether the installer covers Uppsala and book a visit without opening the company's website.

Search keeps answers inside its own interface, and agents can carry them into other systems. Generative UI can build the screen after the request arrives.

I think the website survives as a place for brand and proof. Its role as the center of every customer journey is shrinking. The durable layer moves underneath the page, into structured knowledge that agents can retrieve.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The website is becoming one possible view of company knowledge. Customers and their agents can use that knowledge while the page stays closed.</p></div>

## Search moved from keywords to action

The old path was search, click, website, form. Each step led to a page the company controlled.

A [SparkToro and Datos study](https://sparktoro.com/blog/2024-zero-click-search-study/) found that 58.5% of US Google searches and 59.7% of EU searches ended without a click in 2024. The measure includes abandoned and changed queries, so AI cannot take all the credit.

The AI-specific evidence is newer. In [Pew Research Center's March 2025 sample](https://www.pewresearch.org/short-reads/2025/07/22/google-users-are-less-likely-to-click-on-links-when-an-ai-summary-appears-in-the-results/), visits with an AI summary were associated with traditional-result clicks 8% of the time. Visits without a summary produced clicks 15% of the time. Sources cited inside the summary received clicks in 1% of visits.

At Google Cloud Next in April 2025, Google launched the open [Agent2Agent protocol, or A2A](https://developers.googleblog.com/en/a2a-a-new-era-of-agent-interoperability/) with support from more than 50 technology partners. A2A helps agents exchange information and coordinate across systems. The surrounding applications still handle identity and safe booking.

In the heat-pump example, a customer agent asks an installer agent about coverage and available times. [ServiceTitan offers AI virtual agents](https://www.servicetitan.com/blog/webinar-recap-ai-virtual-agents-call-booking) that can book or reschedule field-service jobs. I think the change becomes strategic when an answer can trigger work. The open-protocol issue runs through [Who owns the agent layer?](/posts/who-owns-the-agent-layer/).

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Zero-click behavior weakens the old search-to-website path. A2A lets agents coordinate after the answer, while the surrounding applications remain responsible for identity and safe action.</p></div>

## A knowledge catalog puts company facts in a form software can use

Phil Risher describes a [knowledge catalog](https://youtu.be/xAIeA3ewRbo) as a verified dataset about a business that an agent can use. Google's documentation does not establish that label as a product category.

A knowledge catalog is a maintained set of business answers that software can retrieve without scraping a page. It can cover prices, policies and real customer questions. Each answer needs a source and a person who owns it.

For the fictional heat-pump installer, one entry could look like this:

```yaml
service: heat_pump_installation
region: SE-C
price_from_sek: 89000
valid_until: 2026-12-31
source_version: price_list_v12
answer_owner: pricing@company.example
permitted_reader: booking_agent
stale_action: price_unavailable
```

The values are illustrative. The price has a region, an expiry date and a named owner. Once it expires, the booking agent returns `price_unavailable` and routes the customer to a person.

Call this answer ownership. A machine-readable answer carries enough context for the company to stand behind it or withdraw it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A knowledge catalog stores company answers as facts that software can retrieve. Source, scope, ownership and expiry keep an agent from turning stale copy into a live promise.</p></div>

## Structured content gives the agent less room to guess

A webpage might say, "Heat-pump installation starts at 89,000 SEK in central Sweden." A model then has to infer the service, region and validity of that sentence.

Structured content separates those details into fields that code can inspect before the model speaks. Google's [guidance for AI search](https://developers.google.com/search/blog/2025/05/succeeding-in-ai-search) describes structured data as machine-readable information.

Risher calls content "training data for the future internet." For a production agent, runtime retrieval offers tighter control. The model fetches the latest entry when the request arrives, and an owner can correct it without retraining the model.

Four common engineering terms describe the path:

- **ReAct** means reasoning and acting. The model calls a tool, reads the result and chooses its next step. Here it reads the postcode, calls the catalog and checks the region before offering a slot. The pattern comes from the [ReAct paper](https://arxiv.org/abs/2210.03629).
- **[LangGraph](https://langchain-ai.github.io/langgraph/reference/graphs/)** is a Python library for agent workflows that keep state across steps. It makes the booking path visible instead of hiding it inside one prompt.
- A **TypedDict** describes the expected keys and types in a Python dictionary. It helps a type checker catch mistakes, although [Python does not enforce those hints at runtime](https://docs.python.org/3/library/typing.html#typing.TypedDict).
- A **StateGraph** connects nodes that update shared state. One node retrieves the catalog entry. Another validates it. The final node offers a slot or returns `price_unavailable`.

Framework choice can vary, but the failure behavior must stay explicit. I think a junior engineer should be able to point to the exact field that allowed an answer and the exact rule that rejected it.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Structured fields let code check a business answer before a model uses it. ReAct describes the tool loop, while LangGraph, TypedDict and StateGraph can make its state and failure path explicit.</p></div>

## A headless CMS gives you a practical head start

A headless CMS stores reusable content separately from the screen that presents it. Websites, apps and agents can read the same content through APIs.

If the heat-pump price and service region already exist as fields in Contentful, Sanity or Optimizely, the team has raw material for a catalog. Page-bound copy requires extraction first.

A headless CMS still leaves work to do. The team must decide which answers an agent may use and what happens when data is missing.

Organizations with strong content models have a structural advantage because their knowledge has already been separated from presentation. That is also the wider argument in [The quiet truth about headless CMS](/posts/the-quiet-truth-about-headless-cms/).

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A modern headless CMS already holds reusable content behind APIs. It provides the raw material for a catalog, while the team still has to add agent access rules and clear failure behavior.</p></div>

## Generative UI moves the durable layer below the screen

Generative UI creates an interface for the request at hand. Google's [A2UI project](https://developers.googleblog.com/introducing-a2ui-an-open-project-for-agent-driven-interfaces/) gives agents a format for sending interface descriptions to different renderers.

The heat-pump customer might hear a voice response in the car and see a booking card later. Both can retrieve the same catalog entry.

The CMS argument also connects to [The Digital Singularity Shift](/books/the-digital-singularity-shift/). The book argues that cheap AI erodes functional differentiation and moves competition toward meaning, story and belief. A knowledge catalog is one operational consequence: generated interfaces become cheap, while company knowledge still needs an owner.

## Choose a partner whose incentives you can inspect

The consultancy that built your content platform may already know its models and approval paths. Valtech is one consultancy in this market. [Contentful](https://www.contentful.com/partners/), [Sanity](https://www.sanity.io/agency-partners) and [Optimizely](https://www.optimizely.com/partners/) also maintain partner directories.

Independence helps when the catalog crosses into pricing or scheduling. A platform specialist may be better when the work stays inside one product.

My take is to inspect incentives before logos. Can your company export the catalog? Can it revoke an agent's access without the supplier? Then check data residency and how the partner gets paid. License incentives shape architecture.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>An existing CMS partner can move quickly because it knows the content model. Choose between a platform specialist and an independent consultancy by testing export rights, access control and supplier incentives.</p></div>

## Build one narrow catalog now

Start with the heat-pump example. Pick twenty questions about one service and one region, including what customers ask before they trust a price.

Weeks one and two: name the owner of each answer and locate its source. Weeks three and four: model the entries and expose a read-only endpoint. Weeks five and six: connect the agent and test failure paths.

Every answer returns its source version and expiry date. An expired price can never become a booking quote. The system logs the catalog version and sends unclear cases to a person.

Measure the share of priority questions that return a current, attributable answer. Keep rankings, then add AI mention rate and share of voice as secondary signals. [Optimizely offers an AI share-of-voice report](https://www.optimizely.com/agents/competitive-ai-share-of-voice-agent/), although a spreadsheet is enough for twenty questions.

I think the first useful catalog will feel disappointingly small: a read-only endpoint covering twenty questions about one service. That scope is enough to learn whether an agent can use a company promise without inventing the missing parts.

When the page never loads, the catalog still has to tell the truth.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A six-week pilot can test one answer domain before booking is enabled. Success means the agent returns a current source, rejects stale facts and leaves a trace of the version it used.</p></div>
