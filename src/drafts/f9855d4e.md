Imagine a homeowner in Uppsala asking an AI assistant for a heat-pump price and installation slot. The assistant checks approved data and books through a service agent. The homepage stays closed.

I think the website will survive for stories and proof. Its role as the hub is shrinking. Junior AI engineers now need to build the approved knowledge underneath every page, answer and tool call.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>The website is becoming one possible view of company knowledge. Customers and their agents can use that knowledge without visiting the view.</p></div>

## Search became a conversation, then an action

Search can hold the answer inside its own interface, while agents can carry that answer into a task.

A [SparkToro and Datos study](https://sparktoro.com/blog/2024-zero-click-search-study/) found that 58.5% of US Google searches and 59.7% of EU searches ended without a click in 2024. The figures include abandoned and changed searches, beyond AI answers.

[Pew Research Center](https://www.pewresearch.org/short-reads/2025/07/22/google-users-are-less-likely-to-click-on-links-when-an-ai-summary-appears-in-the-results/) found traditional-result clicks in 8% of visits with an AI summary, compared with 15% without one. Cited sources received clicks in 1% of visits.

At Google Cloud Next in April 2025, Google launched the open [Agent2Agent protocol, or A2A](https://developers.googleblog.com/en/a2a-a-new-era-of-agent-interoperability/) with more than 50 technology partners. A2A coordinates agents. The surrounding applications still handle identity, authorization and safe booking.

Our assistant could check coverage with one agent and crew availability with another. ServiceTitan offers [AI virtual agents that can book or reschedule field-service jobs](https://www.servicetitan.com/blog/webinar-recap-ai-virtual-agents-call-booking). I think a journey can begin with an answer and end with an action while the website stays in the background.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Zero-click search weakens the old search-to-website path. A2A adds coordination between agents, while each application remains responsible for access and safe action.</p></div>

## A knowledge catalog is a governed promise surface

A knowledge catalog gives the heat-pump agent one controlled place to retrieve answers the company is willing to stand behind.

Phil Risher describes a [knowledge catalog](https://youtu.be/xAIeA3ewRbo) as a verified dataset about a business that an agent can use. His term becomes useful as a governed promise surface, where every answer has a source, owner, scope and revocation path.

```yaml
service: heat_pump_installation
region: SE-C
price_from_sek: 89000
valid_until: 2026-12-31
source_version: approved_price_list_v12
answer_owner: pricing@company.example
permitted_reader: booking_agent
stale_action: price_unavailable
```

The values are illustrative. The price has a region, expiry and approved source. After expiry, the workflow returns `price_unavailable` and routes the customer to a person.

Risher calls content "training data for the future internet." Runtime retrieval offers more control: the agent fetches the current entry, and an owner can correct or revoke it without retraining a model.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>A knowledge catalog is a verified set of business promises that software can retrieve. Provenance, scope, expiry and ownership make each answer safer to use.</p></div>

## Structured content gives agents less room to guess

Structured content turns one business answer into fields that code can inspect and reject.

A paragraph saying "installation starts at 89,000 SEK in central Sweden" leaves an agent to infer region, validity and approval. The catalog exposes each value. Google's [AI search guidance](https://developers.google.com/search/blog/2025/05/succeeding-in-ai-search) describes structured data as machine-readable information.

ReAct means reasoning and acting. The model chooses a step, calls a tool, reads the result and continues. Our agent reads the postcode, calls the catalog and checks the entry before offering a slot.

[LangGraph](https://langchain-ai.github.io/langgraph/reference/graphs/) is a Python library for stateful agent workflows. A `TypedDict` describes expected dictionary keys and types for static checking. Runtime safety still needs validation. A `StateGraph` connects nodes that update shared state, with edges choosing the next node.

```python
from typing import TypedDict
from langgraph.graph import END, START, StateGraph

class BookingState(TypedDict):
    postcode: str
    catalog_entry: dict | None
    outcome: str

workflow = StateGraph(BookingState)
workflow.add_node("lookup_catalog", lookup_catalog)
workflow.add_node("validate_entry", validate_entry)
workflow.add_edge(START, "lookup_catalog")
workflow.add_edge("lookup_catalog", "validate_entry")
workflow.add_edge("validate_entry", END)
booking_agent = workflow.compile()
```

The two functions are application code; the sketch shows graph wiring. `lookup_catalog` retrieves the entry. `validate_entry` checks region, expiry and reader. A ReAct loop may run inside a node, while the graph keeps the path visible.

I think structured content earns its place in production when a junior engineer can point to the exact field and its failure response.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>ReAct describes the reasoning-and-action loop. LangGraph makes the workflow explicit, while TypedDict and StateGraph describe the shared state and the nodes that change it.</p></div>

## A headless CMS gives you a head start

A well-modeled headless CMS has already separated approved content from the screen that displays it.

A headless CMS stores reusable content behind APIs. The website and a controlled agent interface can read the same objects.

If prices and regions already exist as fields in Contentful, Sanity or Optimizely, the team can expose a read-only catalog before adding booking. Page-bound content requires extraction first.

Someone still has to define a standard installation, approve its price and set expiry. I think content modeling is governance expressed as fields. That is the wider argument in [The quiet truth about headless CMS](/posts/the-quiet-truth-about-headless-cms/).

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Headless CMS platforms already store reusable content behind APIs. Strong content models can become an agent-facing catalog faster because the fields and approval paths already exist.</p></div>

## Generative UI moves the durable layer below the screen

Generative UI assembles an interface for the current request instead of relying on one fixed page.

Google's [A2UI project](https://developers.googleblog.com/introducing-a2ui-an-open-project-for-agent-driven-interfaces/) gives agents a standard format for interface descriptions. Our homeowner may receive a laptop card and a voice answer in the car. Both retrieve the same entry.

This fits [The Digital Singularity Shift](/books/the-digital-singularity-shift/): as AI makes functional differentiation cheaper, competition moves toward meaning, story and belief. I think the catalog is an engineering layer beside that thesis, keeping factual promises stable across generated interfaces.

## Choose a partner whose incentives you can inspect

The consultancy that built your content platform may already know its models, APIs and approval paths.

Valtech is one consultancy in this market. The partner directories for [Contentful](https://www.contentful.com/partners/), [Sanity](https://www.sanity.io/agency-partners) and [Optimizely](https://www.optimizely.com/partners/) list many others.

Platform expertise helps when the catalog stays inside one CMS. Independence helps when it crosses content, pricing and operations. Either way, your organization should own the schema and test set, export the data, revoke access and inspect supplier incentives.

My take is to prefer independence where licenses could shape the architecture. The incumbent remains sensible when it accepts those ownership terms.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>An existing CMS partner can move quickly, while an independent consultancy can reduce platform bias across several systems. Ownership, portability and revocation should decide the choice.</p></div>

## Build one narrow catalog now

Start with one answer domain and prove that the controls work before an agent can book anything.

Choose twenty questions about heat-pump coverage and price. Pair one engineer with the content and pricing owners. Review answers weekly.

Ship read-only retrieval first. Each question should return an approved source. Expired prices return `price_unavailable`, and responses log the source version. Add booking after the tests pass and the human route works.

The primary metric is the share of questions with a current, attributable answer. AI mention rate and share of voice sit beside rankings. [Optimizely offers automated reporting](https://www.optimizely.com/agents/competitive-ai-share-of-voice-agent/), although a spreadsheet handles the first twenty questions.

I think this is the right first move. Keep the website for the human story. Build the catalog for every agent expected to act on a promise your company owns.

<div class="chapter-tldr"><span class="chapter-tldr__label">In short</span><p>Begin with twenty high-value questions, read-only retrieval and explicit failure tests. The catalog becomes useful when every agent answer can be traced, expired and revoked.</p></div>
